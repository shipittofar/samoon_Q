# P9.0 — Platform Configuration Architecture

> Phase B/I of P9.0. This is architecture documentation only — no settings
> screens exist yet. Every future settings page (P9.1+) is built on top of
> what's described here. Source: `src/config/*`.
>
> Last updated: 2026-07-04

---

## 1. Why this architecture exists

See `docs/P9.0_PLATFORM_CONFIGURATION_AUDIT.md` for the full audit. In short:
Samoon accumulated five different ad hoc configuration mechanisms across
Phases 1–8 (constants files, the module registry, the feature flag service,
`Tenant.settings`, static data files). None of them share a schema, a
permission model, an inheritance model, or an audit trail. P9.0 introduces one
model — **Platform → Modules → Sections → Fields → Validation → Permissions →
Audit → Versioning** — that every future settings surface plugs into, so a
Console settings page is generated from metadata instead of hand-built per
module.

## 2. The model

```
Platform
  └─ Module            (e.g. "Authentication", "Themes", "Payments")
       └─ Section       (a logical grouping of fields within a module)
            └─ Field    (one configurable value, fully self-describing)
```

- **Module** (`ConfigModuleDefinition`, `src/config/types.ts`) — the unit of
  registration and permission. Carries `id`, `name`, `description`,
  `category`, `version`, `permissions`, optional `featureFlag`, optional
  `dependencies`, and its `sections`. Nothing about a module is duplicated
  elsewhere (Rule 3) — a settings UI reads title/description/permissions
  straight from here.
- **Section** (`ConfigSectionDefinition`) — purely organizational; groups
  related fields for display (e.g. "OTP" vs. "Login Attempts & Lockout"
  inside the Authentication module).
- **Field** (`ConfigFieldDefinition`) — the atomic unit. Every field carries,
  with no exceptions (Rule 5): `id`, `title`, `description`/`helpText`,
  `category`, `type`, `default`, `validation`, `visibility`, `permissions`,
  `preview`, `inheritance`, `audit`, `version`. There is no such thing as an
  anonymous configuration value in this system.

## 3. Registration (Rule 2 — Registry First)

`src/config/registry.ts` exports `platformConfigurationRegistry`, a sealed
singleton copying the safety pattern already proven by
`src/modules/registry.ts`:

1. Each module file under `src/config/modules/*.ts` calls
   `platformConfigurationRegistry.register(MY_MODULE)` **at import time**
   (module body, not inside a request handler or component render).
2. `src/config/index.ts` imports every module file for its registration
   side effect, in an order that respects `dependencies` (e.g. `themes` is
   imported before `website-builder`, which depends on it).
3. The first call to `getModules()`/`getField()`/`getDefaults()` **seals**
   the registry. Any subsequent `register()` call throws — this is what
   makes it safe under Next.js's shared-module-state-per-server-instance
   behavior (the same reasoning documented in
   `src/modules/TENANT_RESOLUTION_STRATEGY.md`).
4. Registering a field id that already exists anywhere in the registry
   throws immediately (Rule 3 — Single Source of Truth enforced at
   registration time, not just by convention).

Development order is always Registry → Schema → Validation → Service → API
Contract → UI — never the reverse. A new module is added by writing its
`ConfigModuleDefinition` and importing it from `src/config/index.ts`; nothing
else needs to change.

## 4. Schema system (Phase D)

`ConfigFieldType` (`src/config/types.ts`) is the closed set of value shapes
every field must be one of: `string | number | boolean | select |
multi-select | color | font | json | array | object | password | secret |
country | language | feature_flag | permission`. `src/config/field.ts`
exports `defineField()`, a terse constructor that fills in the Rule 5
metadata every field needs with safe defaults so module files read as data,
not boilerplate:

```ts
defineField({
  id: 'authentication.otp.length',
  title: 'OTP Code Length',
  category: 'security',
  type: 'number',
  default: 6,
  validation: { min: 4, max: 8, required: true },
  permissions: { view: 'settings.view', edit: 'settings.manage' },
  inheritance: { level: 'platform', canOverride: false, mode: 'locked', fallback: 'inherit' },
})
```

`preview.kind` (`'swatch' | 'font-sample' | 'json' | 'image' | 'none'`) is
how a future generic settings UI picks a renderer per field type without a
hardcoded switch statement per module (Rule 7).

## 5. Configuration inheritance (Rule 4)

Every field declares an owning `inheritance.level` — the level whose value is
authoritative by default — plus whether descendant levels may override it:

```
Platform Default
     ↓ (if canOverride)
Tenant Override
     ↓ (if canOverride)
Branch Override
     ↓ (if canOverride)
User Preference
```

Three knobs per field:

- **`canOverride`** — whether any level below `inheritance.level` may set
  its own value at all.
- **`mode`** — `'override'` (nearest set value wins outright), `'merge'`
  (objects/arrays are shallow-merged onto the resolved ancestor value — e.g.
  `api.cors_allowed_origins`), or `'locked'` (descendants can never win,
  regardless of `canOverride` — used for fields like `authentication.otp.length`
  or `system.maintenance_mode` that must stay platform-controlled).
- **`fallback`** — what an *unset* descendant level resolves to: `'inherit'`
  (use the nearest ancestor's value) or `'default'` (use the field's
  hardcoded `default`, ignoring ancestors).

`ConfigurationResolver.resolveField()` (`src/config/resolver.ts`) walks
`platform → tenant → branch → user` in order, applying these rules, and
returns a `ResolvedConfigValue` that reports which level actually won
(`resolvedFrom`) and whether an override attempt was silently blocked
(`overrideBlocked`) — so a future UI can show "this field is locked by the
platform" instead of a value that quietly didn't take effect.

Example — `themes.primary_color`: owned at `platform`, `canOverride: true`,
`mode: 'override'`. A tenant sets `#0ea5e9`; that wins for every branch/user
under that tenant unless a branch explicitly overrides it too. A *different*
tenant with no override still sees the platform default. Overrides are keyed
per scope id (tenant id / branch id / user id), never globally — this was a
real bug caught by the test suite during Phase E and is now covered by
`src/test/p9-platform-configuration.test.ts` ("overrides scoped to another
tenant do not leak").

## 6. Service layer (Phase E)

Every consumer talks to exactly one facade, `ConfigurationService`
(`src/config/service.ts`) — nothing outside this file touches the registry,
resolver, validator, cache, audit log, or version manager directly:

| Service | File | Responsibility |
|---|---|---|
| `ConfigurationService` | `service.ts` | Facade: `getModules`/`getModule`/`getField`, `resolveField`/`resolveModule`, `updateField`, `canView`/`canEdit`. The only entry point. |
| `ConfigurationResolver` | `resolver.ts` | Pure inheritance-chain resolution (§5). |
| `ConfigurationValidator` | `validator.ts` | Per-type validation (`required`/`min`/`max`/`pattern`/`enumValues`) plus a `registerRule()` escape hatch for named cross-field validators. |
| `ConfigurationCache` | `cache.ts` | TTL memoization of resolved values, keyed by `fieldId::tenantId::branchId::userId`; invalidated by `updateField`. |
| `ConfigurationAudit` | `audit.ts` | Append-only log of every write: who, when, old value, new value, reason. Redacts `audit.sensitive` fields (secrets/passwords) to `••••••`. |
| `ConfigurationVersionManager` | `version-manager.ts` | Per-module version + change-note history, independent of per-field `version` metadata. |

`updateField()` enforces, in order: (1) the field's inheritance rules reject
writes to a locked/non-overridable level, (2) `ConfigurationValidator`
rejects invalid values, (3) `audit.requireReason` rejects writes with no
`reason` when the field demands one, (4) the write is recorded to the
override store, cache is invalidated for that field, and — if
`audit.trackHistory` — an audit entry is recorded. All four steps are
covered by `src/test/p9-platform-configuration.test.ts`.

## 7. React integration (Phase F)

`src/hooks/use-platform-configuration.ts` exposes five hooks — **hooks only,
no screens** (per the P9.0 brief):

- `usePlatformConfiguration()` — all registered modules (metadata only).
- `useConfigurationModule(moduleId)` — one module's metadata + every field
  resolved for the current scope.
- `useConfigurationField(fieldId)` — one field's definition + resolved value.
- `useConfigurationPermissions(fieldId)` — `{ canView, canEdit }` against the
  current user's effective P7 permissions (reuses `usePermissions()` from
  `src/hooks/index.ts` — RBAC is not duplicated, per Rule 3).
- `useConfigurationPreview(fieldId)` — `{ kind, value }` for a future generic
  field renderer.

Scope (`tenantId`/`branchId`/`userId`) is derived automatically from the
existing `useTenantStore`/`useBranchStore`/`useAuthStore` — callers never
thread scope through props by hand.

## 8. How future modules plug in (Rule 9 — extensibility first)

Adding a new platform module (AI, Inventory, CRM, POS, Gift Cards,
Franchise, Delivery, …) is exactly:

1. **Register Module** — write `src/config/modules/my-module.ts` exporting a
   `ConfigModuleDefinition` and calling `platformConfigurationRegistry.register()`
   at the bottom of the file.
2. **Register Schema** — declare its sections/fields with `defineField()`;
   the schema system (§4) already covers every value shape a settings UI will
   ever need (including `feature_flag` and `permission` field types for
   modules that need to reference other modules' flags/permissions).
3. **Register Services** — nothing extra to write; `ConfigurationService` (§6)
   already handles resolution, validation, caching, and audit for any
   registered field with zero module-specific code.
4. **Import it** from `src/config/index.ts` (respecting `dependencies` order
   if the module depends on another).
5. **UI appears automatically** — once P9.1 builds the generic settings
   renderer against this metadata, a new module's fields render, validate,
   and audit themselves with no additional UI code (Rule 7).

## 9. Backend contract (Phase H)

`docs/BACKEND_API_CONTRACT.md` §27 documents the future Platform
Configuration API (`GET`/`PATCH` per module, validation, permissions,
versioning, audit) generated from this exact model — the API is defined by
the configuration schema, never the other way around (Rule 8). No backend
implementation exists yet; that section is contract-only.

## 10. What is explicitly out of scope for P9.0

- No settings screens/UI (P9.1+).
- No migration of existing call sites (`src/constants/index.ts`,
  `Tenant.settings`, `src/data/countries.ts`, `feature-flags.service.ts`) onto
  the new registry — those keep working exactly as before. P9.1+ phases
  migrate individual call sites onto `ConfigurationService` one module at a
  time, verified by the existing test suite (no regressions).
- No backend implementation of the Phase H contract.
