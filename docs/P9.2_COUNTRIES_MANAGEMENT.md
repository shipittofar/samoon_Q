# P9.2 — Countries Management Center

> Companion to `docs/P9.2_COUNTRIES_AUDIT.md` (Phase A). This doc covers what
> was actually built: the `'collection'` field type and its supporting
> framework (bulk engine, filtering engine, search engine, drawer
> architecture), with Countries as the reference consumer — mirroring how
> `docs/P9.1.3_AUTHENTICATION_CONTROL_CENTER.md` used Authentication.
>
> Last updated: 2026-07-04

---

## 1. Architecture — "one schema, many entities"

Every module before P9.2 (Authentication's 17 fields, Themes' 4, …) declares
a fixed, small set of distinct fields. Countries needs the opposite shape:
one ~22-property schema applied to 176 country entities. Registering
176 × 22 individual `ConfigFieldDefinition`s would explode the registry and
violate Rule 3 (Single Source of Truth) by repeating the same schema 176
times. Instead, P9.2 adds a new `ConfigFieldType`, `'collection'`
(`src/config/types.ts`), whose value is a single `ConfigCollectionValue` —
`Record<entityId, Record<propertyId, value>>` — described once by
`field.collection: ConfigCollectionMeta`:

```ts
interface ConfigCollectionMeta {
  entityLabel: string          // "Country"
  entityIdLabel: string        // "ISO Code"
  schema: ConfigFieldDefinition[]   // ~22 properties, authored with defineField() but never separately registered
  entityIds?: string[]         // fixed roster (all 176 codes) — independent of what's actually stored
  getEntityLabel?: (id) => string
  getEntitySearchTerms?: (id) => string[]
  buildPreview?: (values) => Record<string, string>
  defaultGroupBy?: string
}
```

A collection field is still exactly one `ConfigFieldDefinition` — every
existing resolve/validate/audit/cache/version mechanism in
`ConfigurationService` applies to it completely unchanged. Countries
registers one field, `countries.registry`, in
`src/config/modules/countries.ts`; the 176-country dataset and 22-property
schema live in `src/config/modules/countries-registry-data.ts` — this is the
one piece of genuinely Countries-specific content the phase produces (per
the audit doc's conclusion table).

### The fixed-roster fix

`getCollectionEntries()` originally iterated only the keys present in the
*stored* collection value — correct for an ad-hoc collection (entities an
admin creates), wrong for Countries, where all 176 countries must always
appear in the table even with zero stored overrides. `field.collection.
entityIds` now supplies the full roster; `getCollectionEntries` unions it
with whatever the stored blob actually contains, so an override-free country
still renders with pure schema defaults. Collections without a fixed roster
simply omit `entityIds` and keep the original behavior.

### A real bug fixed along the way

`configCollection.resetEntityToDefault(field, current)` — the no-`entityId`
overload meant to reset the *entire* collection — was a no-op: it copied the
current value and returned it unchanged, clearing nothing. Since
`getEntityValues`/`getCollectionEntries` already merge schema defaults onto
whatever is stored, "reset everything" is simply "clear the stored blob" —
fixed to return `{}`. Covered by a regression test
(`resetEntityToDefault(field, current) with no entityId clears the whole
collection`).

## 2. Bulk operation engine (Phase D)

`src/hooks/use-configuration-bulk-actions.ts` — `useConfigurationBulkActions
(field)` — computes a bulk action's effect (`enable` / `disable` / `publish`
/ `archive` / `reset` / `export` / `import`) over a set of selected entity
ids, driven entirely by two schema-property conventions:

- an `enabled` boolean property → `enable`/`disable` set it true/false
- a `status` select property → `publish`/`archive` set it to `'published'`/
  `'archived'`

A collection whose schema declares neither property simply gets a no-op for
that action kind — nothing here reads a Countries-specific id.
`export` returns a JSON snapshot of the selected entities' merged values
(read-only); `import` is a documented placeholder returning `ok: false` with
an explanatory message, per the phase's explicit "placeholder" scope.

**Deliberately pure, no direct persistence.** The hook never calls
`configurationService.updateField()` itself — it returns the computed
`nextValue`, and the caller (`ConfigurationCollectionTable`) feeds it through
the *same* `onChange` prop every other field control already uses, which
routes into `useConfigurationDraft`'s `setFieldDraft`. A bulk action becomes
just another pending edit, validated and saved through the one existing
dirty/save/audit pipeline — not a second, parallel write path that could
drift from it or double-persist.

## 3. Search engine (Phase E)

`matchesSearch(field, query)` (P9.1.3) and the new `matchesCollectionEntrySearch
(field, entry, query)` now share one `buildSearchHaystack(parts)` helper in
`configUiHelpers.ts` — "join a bag of strings, lowercase, and substring-match"
is defined exactly once. Entry search matches the entity id, its resolved
label, every schema property's *current value* on that entity, each
property's own `search.keywords`/`search.aliases`, and — new —
`field.collection.getEntitySearchTerms?.(entityId)`, an optional per-entity
callback. Countries uses it to contribute dial codes, flag emoji, and
reversed `COUNTRY_ALIASES` entries (`uk` → GB) without the framework knowing
what an "alias" is; a future collection with no natural aliases just omits
the callback.

## 4. Filtering engine (Phase F)

`deriveCollectionFilterOptions(field)` derives every available filter
directly from `field.collection.schema` — no per-module filter list to
maintain:

- every `boolean` property → an Enabled/Disabled pair (e.g. "Phone Login:
  Enabled" / "Phone Login: Disabled" for `phone_login_enabled`)
- every `select` property's declared `options` → one filter per option
  (Countries' `status` options surface "Status: Published", "Status: Draft",
  "Status: Experimental" — `testing`'s option label is literally
  "Experimental", satisfying the phase's ask without a separate boolean
  flag; `region`'s 7 options surface as region filters)

Applying a filter is `configCollection.matchesFilters(values, { [propertyId]:
value })` — the same generic property-equality predicate `collection.ts`
already exposed, re-exported from `configUiHelpers.ts` as
`matchesCollectionEntryFilters` purely so Console pages have one import
site. A future Branches collection with a `capacity` select property gets
working capacity filters for free the moment it declares the property.

## 5. Drawer architecture (Phase H)

`ConfigurationEntityDrawer` (`src/components/admin/configuration/
ConfigurationEntityDrawer.tsx`) reuses the shared `Drawer` UI primitive plus
every field-render component already built in P9.1.3 —
`ConfigurationFieldControl`/`Badges`/`Preview` — rendering each schema
property exactly as `ConfigurationFieldRow` would, just once per entity
instead of once per module. Seven tabs:

| Tab | Source |
|---|---|
| Configuration | `schema` properties rendered via `ConfigurationFieldControl`, gated by `evaluateCondition` (the identical P9.1.3 dependency-condition function, evaluated against this one entity's own values) |
| Overrides | properties whose current value differs from the schema default (`JSON.stringify` compare, the same technique `deriveFieldState` already uses at module level) |
| Dependencies | any schema property declaring `hiddenWhen`/`enabledWhen` |
| Audit | `configurationAudit.listForField(field.id)` entries filtered to ones where this entity's slice of `previousValue`/`newValue` actually changed |
| Statistics | property count, overridden-property count, recorded-change count |
| Inheritance | the *field's* inheritance level/mode (collections don't have per-entity inheritance — one field, one owning level) |
| Preview | `field.collection.buildPreview?.(values)` label→value pairs, plus any schema property with its own `preview.kind` rendered via `ConfigurationFieldPreview` |

`buildPreview` is the one new, small, generic escape hatch: the framework
never assumes what "a preview" means for an arbitrary collection, so it's a
plain callback. Countries' `buildPreview` turns `default_phone_prefix` +
`phone_example` (both derived once, in the module file, from
`src/data/countries.ts` — never re-typed in the override data) into
`{ 'Example Phone': '+1 (201) 555-0123', Currency: 'USD', … }`.

`ConfigurationCollectionTable` (search bar, filter/group/sort selects,
statistics badges, bulk-action toolbar, checkbox selection, row click →
drawer) is the list half; `ConfigurationFieldRow` dispatches to it with one
`if (field.type === 'collection')` — no page-level or module-specific
branching, matching the audit doc's Phase C conclusion exactly.

## 6. Countries as the reference consumer

`src/config/modules/countries.ts` registers one new field,
`countries.registry`, alongside the three pre-existing platform-wide list
fields (`enabled_codes`/`pinned_codes`/`default_code`, unchanged — they
answer a different question, per the audit doc §1). Its 22-property schema
covers: `enabled`, `visible`, `supported`, `phone_login_enabled`,
`sms_enabled`, `registration_enabled`, `reservations_enabled`,
`ordering_enabled`, `payments_enabled`, `delivery_enabled`, `pickup_enabled`,
`currency`, `timezone`, `default_language`, `default_phone_prefix`,
`phone_example`, `vat_supported`, `address_format`,
`postal_code_validation`, `national_id_required` (future-ready, off by
default), `region`, `status`, `notes` — every one of them reuses an existing
`uiControl` kind (`switch`, `currency_picker`, `timezone_picker`,
`language_selector`, `radio`, `textarea`, `text`); no new Console control was
needed.

`src/config/modules/countries-registry-data.ts` holds the actual dataset:
`CODE_TO_REGION` maps all 176 ISO codes onto the 7 canonical regions
(North America, South America, Europe, Middle East, Asia, Africa, Oceania),
derived from `src/data/countries.ts`'s own 8 region-comment groups — Central
America/Caribbean folds into North America, Pakistan/Afghanistan move out of
that file's "Middle East" section into Asia for real-world accuracy, and
Georgia/Armenia/Azerbaijan stay under Europe (matching the source file's own
grouping, a deliberate internal-consistency choice over strict Caucasus/Asia
geography). `COUNTRY_OVERRIDES` hand-curates 85 countries across every
region with deliberately mixed `enabled`/`status` states (several disabled
for payment-rail/stability reasons with an explanatory `notes` value, several
`draft`, several `testing` — the "Experimental" status option), a dozen-plus
currencies, and multiple address-format conventions. Countries without a
curated override still fully render — via the `entityIds` fixed-roster fix —
with plain schema defaults plus their derived `region`/`default_phone_prefix`
/`phone_example` (the latter two always computed from `src/data/countries.ts`,
never duplicated).

## 7. Future extensibility

Everything above the Countries-specific dataset is generic and immediately
available to any future module needing "one schema, many entities" —
Branches, Tenants, Payment Providers, Delivery Zones, etc:

1. Define a per-entity schema with `defineField()` (never separately
   registered).
2. Register one field of `type: 'collection'` with that schema plus an
   `entityIds` roster (or omit it for an admin-created, ad-hoc collection).
3. `ConfigurationFieldRow` renders it as a table automatically.
4. Declaring an `enabled` boolean and/or `status` select property on the
   schema turns on working bulk enable/disable/publish/archive for free.
5. Declaring `boolean`/`select` schema properties turns on working filters
   for free.
6. Optionally supply `getEntityLabel`, `getEntitySearchTerms`, and
   `buildPreview` for a nicer table/search/drawer experience — all are
   additive; a collection that supplies none of them still fully works.

## 8. Lessons learned

- **The registry-scale problem was real, not hypothetical.** 176 × 22 ≈
  3,900 individually-registered fields would have made the registry's
  duplicate-id check, the module index page, and any future search-across-
  modules feature genuinely unusable — the audit doc's Phase A concern was
  validated the moment `entityIds.length === 176` was written.
- **"Generic" needs testing against a second real consumer to be believed.**
  The `entityIds` fixed-roster gap and the `resetEntityToDefault` no-entityId
  bug both surfaced only once Countries' actual 176-country roster was
  exercised against code written to satisfy the audit doc's abstract
  description — Authentication alone never needed either.
- **Pure computation + one shared persistence path beats a second write
  path.** The bulk-action hook was initially designed to call
  `configurationService.updateField()` directly (with its own tenant/branch/
  actor scope plumbing duplicated from `useConfigurationDraft`). Recognizing
  that as a second persistence path — one that could silently diverge from
  the existing dirty/validate/save/audit pipeline — led to the simpler,
  final design: bulk actions compute, the existing draft/save flow persists.
- **An optional callback beats a framework guess.** `buildPreview` and
  `getEntitySearchTerms` are two small, additive callbacks rather than the
  framework hardcoding "a preview is phone+currency+timezone" or "aliases
  come from a fixed alias table" — both would have been Countries-shaped
  assumptions baked into supposedly generic code.
