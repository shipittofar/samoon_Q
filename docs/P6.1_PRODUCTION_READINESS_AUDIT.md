## 1. Environment & Secrets

### Findings

#### PASS — No hardcoded secrets or API keys
Searched all `src/**/*.{ts,tsx}` for `sk-`, `pk_`, `password`, `api_key`, `SECRET`. Zero instances of committed credentials. All secrets flow through `process.env`.

#### PASS — Zod validation at startup (`src/lib/env.ts:11–64`)
`NEXT_PUBLIC_API_BASE_URL` and `NEXT_PUBLIC_USE_MOCK` are required; app throws at module load if missing or malformed. Optional fields (Sentry DSN, Stripe key, Firebase) warn but allow startup.


#### PASS — Production mock-mode guard (`next.config.ts:32–37`)
Build aborts at compile time if `NEXT_PUBLIC_USE_MOCK=true` and `NODE_ENV=production`. The demo backdoor (`demo@savor.com / password`) cannot reach a production bundle.

#### PASS — `.env.example` documents every variable
`.env.example` covers all 14 variables used across the codebase. No actual values committed.

#### GAP — `SENTRY_DSN` listed in `.env.example` but not validated
`.env.example:34` lists bare `SENTRY_DSN=` (server-side). `src/lib/env.ts` only validates `NEXT_PUBLIC_SENTRY_DSN`. `sentry.server.config.ts:9` falls back: `process.env.SENTRY_DSN || process.env.NEXT_PUBLIC_SENTRY_DSN`. The bare `SENTRY_DSN` is never validated — a typo silently disables server-side error reporting.

**Fix:** Add `SENTRY_DSN: z.string().url().optional()` to `optionalEnvSchema` in `src/lib/env.ts`.

#### GAP — `NEXT_PUBLIC_WS_BASE_URL` and `NEXT_PUBLIC_APP_NAME` not validated
Both are in `.env.example` and used in `src/constants/index.ts:4–5`. Neither appears in `src/lib/env.ts`. They degrade silently to `localhost` defaults rather than warning of misconfiguration.

**Fix:** Add both to `optionalEnvSchema`.

#### GAP — `NEXT_PUBLIC_GA_MEASUREMENT_ID` in `.env.example` but no usage found
Listed in `.env.example` with no corresponding code or validation. Either dead config or analytics is not wired.

#### INFO — JWT stored in `localStorage` + non-HttpOnly cookie
`src/services/axios.instance.ts:14,23–24`: access token in `localStorage`; mirrored to a `SameSite=Strict` (non-HttpOnly) cookie for Edge middleware. The CSP (`script-src 'self' 'unsafe-inline'`) partially mitigates XSS exfiltration risk, but `unsafe-inline` means an injected `<script>` tag could still read `localStorage`. See §6 for full security classification.

- `isLoading && <Loader2 />` spinner

#### PASS — Optimistic updates have rollback
All five mutation hooks (`useUpdateOrderStatus`, `useUpdateMenuItem`, `useDeleteMenuItem`, `useConfirmReservation`, `useCancelReservation`) implement `onMutate` snapshot + `onError` restore pattern. `src/hooks/index.ts:488,521,546,602,627`.

### Service Layer

#### PASS — Axios 401 triggers token refresh then retry (`src/services/axios.instance.ts:79–120`)
Queue prevents race conditions when multiple requests fail simultaneously. Failed refresh clears tokens and dispatches `auth:logout` custom event.

#### PASS — WebSocket errors logged and reconnect attempted
`src/services/websocket.service.ts:163,181,205` — three `console.error` calls covering parse failures, construction failures, and socket errors. All appropriate for production (prefixed with `[WS]`).

### Checkout / Auth

#### PASS — Checkout error handling (`src/app/checkout/page.tsx:150–151,174–175,190`)
Order mutation `onError` → `toast.error`. Payment init failure → `toast.error`. Stripe payment error → `handlePaymentError` → `toast.error`.

#### GAP — Rate limiters defined but never called
`src/lib/rate-limit.ts:106–112` defines `LOGIN_LIMIT`, `OTP_LIMIT`, `PASSWORD_RESET_LIMIT`. Zero call sites exist in `src/services/auth.service.ts` or any page. The auth flow has **no client-side rate limiting applied**. This is also a security issue (see §6).

**Fix:** Call `LOGIN_LIMIT.check(email)` at the top of the login submit handler. Return early with a user-facing message if `!result.allowed`.

### Failures (WCAG-Impacting)

#### FAIL A — Admin menu form: `<label>Category</label>` not associated with `<select>` (`src/app/admin/menu/page.tsx:394–402`)

```tsx
// Line 394 — label with no htmlFor
<label className="block text-sm font-medium ...">Category</label>
// Line 395 — select with no id
<select value={form.category_id} onChange={set('category_id')} ...>
```

Screen readers cannot associate the label with the control. **WCAG 1.3.1 (Level A).**

**Fix:**
```tsx
<label htmlFor="menu-category" className="...">Category</label>
<select id="menu-category" ...>
```

#### FAIL B — Admin menu form: checkbox `<input>` elements use wrapping `<label>` but inputs have no `id` (`src/app/admin/menu/page.tsx:413,417,421`)

```tsx
<label className="flex items-center gap-2 ...">
  <input type="checkbox" checked={form.available} onChange={set('available')} />
  Available
</label>
```

Wrapping `<label>` is a valid implicit association pattern — **this actually passes WCAG** as the input is a descendant of the label. No fix required.

#### FAIL C — Modal has no focus trap
`src/components/ui/Modal.tsx` implements Escape-to-close and `aria-modal="true"` but does **not** trap Tab focus within the dialog. When the modal is open, Tab can cycle to background content. **WCAG 2.1.2 (Level A)** for keyboard trap (focus must stay inside the modal).

**Fix:** Add a focus-trap `useEffect` that intercepts Tab/Shift+Tab and constrains focus to focusable elements within `ref.current`.

#### FAIL D — Admin menu modal: `aria-labelledby="modal-title"` points to a hardcoded `id`
`Modal.tsx:54` sets `aria-labelledby="modal-title"` when a `title` prop is provided, but the `<h2>` inside the modal must have `id="modal-title"`. Check whether the rendered `<h2>` in Modal carries that id.

```tsx
// Modal.tsx — need to verify the h2 has id="modal-title"
```

If multiple modals exist simultaneously (unlikely but possible), duplicate IDs would fail HTML validity. Use a generated or unique ID.

#### INFO — No `<main>` landmark in admin pages
Admin pages render their content without a `<main>` element or `role="main"`. This makes landmark navigation (screen reader `F6`) non-functional for admin users.

## 6. Security

### Classification

#### MEDIUM — JWT in `localStorage` with `unsafe-inline` CSP

**File:** `src/services/axios.instance.ts:14,23–24` / `next.config.ts:11`

`localStorage` JWT is readable by any inline script. CSP `script-src` includes `'unsafe-inline'` (required for `next/font` and the theme hydration script at `layout.tsx:46`). An XSS injection point in any third-party content rendered by the app could exfiltrate the token.

**Current mitigations:**
- No user-controlled HTML is rendered (no `innerHTML` or unescaped user strings found)
- `dangerouslySetInnerHTML` is only used for JSON-LD (escaped via `serializeJsonLd`) and the theme hydration script (static developer code)
- `SameSite=Strict` cookie reduces CSRF risk

**Residual risk:** The `unsafe-inline` CSP weakens XSS defenses because nonce-based enforcement is not used.

**Classification: MEDIUM** — No known injection vectors, but defense-in-depth is weaker than nonce-based CSP.

**Recommended fix:** Move to nonce-based CSP; store access token in a `HttpOnly` cookie instead of `localStorage`, and adjust the middleware to use that cookie directly.

#### MEDIUM — Middleware JWT guard checks cookie presence, not signature

**File:** `src/middleware.ts:71–74`

```ts
const token = request.cookies.get(JWT_ACCESS_KEY)?.value
if (token) {
  return NextResponse.next({ request: { headers: requestHeaders } })
}
```

The Edge middleware accepts **any non-empty cookie value** as authenticated. A forged or expired cookie bypasses the middleware redirect. The `AuthGuard` component (`src/components/auth/AuthGuard.tsx`) provides a second check using `useAuthStore`, but that is client-side and depends on the Providers bootstrap sequence completing before rendering.

**Classification: MEDIUM** — The true server-side auth validation happens at the Django API layer. Protected page content is not rendered server-side (all admin/dashboard pages are `'use client'`). The risk is an attacker bypassing the redirect and seeing the client shell, not the data.

**Recommended fix:** Verify JWT signature in the Edge middleware using `jose` (Edge-compatible). Reject expired tokens at the Edge before the page shell renders.

#### LOW — Rate limiters defined but disconnected

**File:** `src/lib/rate-limit.ts:106–112`

`LOGIN_LIMIT`, `OTP_LIMIT`, `PASSWORD_RESET_LIMIT` are exported but have **zero call sites** in the application. The auth forms have no brute-force protection at the frontend layer.

**Classification: LOW** — Backend should also enforce rate limits. This is defense-in-depth, not the primary control.

**Fix:** Call `LOGIN_LIMIT.check(email)` before the login API call in the login form's submit handler.

#### LOW — `unsafe-inline` in `script-src` CSP

**File:** `next.config.ts:11`

Production CSP: `script-src 'self' 'unsafe-inline'`. This allows inline `<script>` execution, weakening XSS protection. Required for the theme hydration inline script (`layout.tsx:46`).

**Recommended fix:** Replace the inline theme script with a nonce or use a `data-theme` attribute set via a Next.js server component, eliminating the need for `unsafe-inline`.

#### LOW — Tenant slug reflected into `<meta>` tag without sanitization

**File:** `src/app/layout.tsx:40`

```tsx
{tenantSlug && <meta name="x-tenant-slug" content={tenantSlug} />}
```

`tenantSlug` comes from `request.headers.get('x-tenant-slug')` which is injected by the middleware from the subdomain. React automatically escapes `content` attribute values, so XSS via the meta tag is not possible. However, a specially-crafted subdomain could inject unexpected content into the attribute.

**Classification: LOW** — React escaping prevents XSS. No fix required unless subdomain validation is added.

#### INFO — No HSTS header

**File:** `next.config.ts:54–66`

`Strict-Transport-Security` is absent from the security headers. For a production HTTPS deployment, HSTS should be added: `Strict-Transport-Security: max-age=31536000; includeSubDomains`.

### Recommended Release Decision

**B — Ship Beta**

The frontend codebase is production-quality. TypeScript is clean, the build is deterministic, 1714 tests pass, secrets management is correct, and the core security posture is sound. However:

1. **The 5 blocked backend endpoints** make admin core flows non-functional in production. These are external blockers, not frontend issues, but they prevent admin readiness.
2. **The middleware JWT gap** (risk #2) should be closed before a public launch to prevent authorized page-shell access with stale tokens.
3. **The `unsafe-inline` CSP** (risk #3) is acceptable for a beta but should be migrated to nonce-based for a hardened production release.

**Recommended beta ship criteria:**
- [ ] Backend deploys the 5 blocked endpoints
- [ ] Add `jose` JWT verification in `src/middleware.ts`
- [ ] Wire `LOGIN_LIMIT.check()` into the login form (30 min fix)
- [ ] Wrap admin pages in `<ErrorBoundary>` (1 hr fix)
- [ ] Add HSTS header to `next.config.ts` (15 min fix)
- [ ] Fix `<label htmlFor>` on Category select in admin menu form (15 min fix)

The remaining items (focus trap, nonce CSP, WS env validation) are appropriate for a post-beta hardening sprint.
