# P10.9 — Registration Flow: country_code/phone_number Split

Updates the registration flow (`/complete-profile` → `useRegister()` →
`authService.register()`) to match the backend contract:
`POST /auth/register/` now expects `country_code` and `phone_number` as
separate fields, never concatenated, mirroring the shape the OTP request
(`sendOTP()`/`verifyOTP()`) already used since P10.8. Password/confirm
password are temporarily removed from this flow, per instruction, without
deleting the underlying capability.

## Files Changed

### `src/types/index.ts` — `RegisterData`

```diff
 export interface RegisterData {
   email: string
   phone_number?: string
+  country_code?: string
-  password: string
-  confirm_password: string
+  password?: string
+  confirm_password?: string
   first_name: string
   last_name: string
 }
```

`country_code` was added as optional — only the phone-OTP flow
(`/complete-profile`) sends it; `password`/`confirm_password` were
widened from required to optional rather than removed, because
`RegisterData` is also the type used by the **separate**, unrelated
email+password signup flow at `/register` (`RegisterClientPage.tsx`,
its own form with real password/confirm-password inputs and its own zod
schema requiring them at the UI level). Widening — not narrowing or
removing — keeps that flow's existing behavior completely untouched
while making the fields optional for the phone-OTP flow, which no
longer sends them.

### `src/services/auth.service.ts` — `register()`

- Response type widened to also optionally carry `p7Roles`/
  `ownership`/`staffAssignments`, matching `login()`/`verifyOTP()`'s
  contract (established in P10.6/P10.7) — a brand-new customer
  registering has no tenant roles, so mock mode returns `p7Roles: []`
  explicitly (matching the existing `demo@samoon.com` convention).
- No concatenation logic was added or removed here: `register()` never
  built the phone string itself before this phase and still doesn't —
  it forwards whatever `RegisterData` the caller constructed, unchanged.
  The actual `country_code`/`phone_number` split happens entirely in the
  caller (`complete-profile/page.tsx`), exactly where the equivalent
  split already lived for `sendOTP()`/`verifyOTP()`.

### `src/hooks/index.ts` — `useRegister()`

```diff
 export function useRegister() {
   const setUser = useAuthStore((s) => s.setUser)
   return useMutation({
     mutationFn: (data: RegisterData) => authService.register(data),
-    onSuccess: ({ user }) => setUser(user),
+    onSuccess: ({ user, p7Roles }) => {
+      setUser(user)
+      if (p7Roles && p7Roles.length > 0) {
+        const tenantId = useTenantStore.getState().tenant.id
+        useRbacStore.getState().setTenantRoles(tenantId, p7Roles)
+      }
+    },
   })
 }
```

Mirrors `useLogin()`/`useVerifyOTP()`'s existing pattern exactly —
directly satisfies "Frontend stores tokens, user, and roles after
successful registration" (tokens are already stored inside
`authService.register()` itself, unchanged from before this phase).

### `src/app/complete-profile/page.tsx` — `onSubmit`

**Before:**
```ts
register(
  {
    email: `${phone_number.replace(/\D/g, '')}@phone_number.samoon.local`,
    phone_number,
    password: 'mock-phone_number-auth',
    confirm_password: 'mock-phone_number-auth',
    first_name: data.first_name,
    last_name: data.last_name,
  },
  { ... },
)
```

**After:**
```ts
const localPhoneNumber = dialCode && phone_number.startsWith(dialCode)
  ? phone_number.slice(dialCode.length)
  : phone_number

register(
  {
    email: `${phone_number.replace(/\D/g, '')}@phone_number.samoon.local`,
    country_code: dialCode,
    phone_number: localPhoneNumber,
    first_name: data.first_name,
    last_name: data.last_name,
    // password: data.password,
    // confirm_password: data.confirm_password,
  },
  { ... },
)
```

- `country_code: dialCode` — `dialCode` is read from the `dialCode`
  search param (`params.get('dialCode') ?? ''`), forwarded from
  `/verify` on redirect (already wired in P10.8) — never a literal.
- `phone_number` is stripped of the dial-code prefix using the exact
  same `.slice(dialCode.length)` pattern already established in
  `auth.service.ts`'s `sendOTP()`/`verifyOTP()` for the same purpose —
  no new stripping logic invented, the existing convention reused.
- `password`/`confirm_password` lines are commented out, not deleted —
  the two lines can be uncommented directly once password support
  returns to this flow, and (per "keep the code structure clean")
  nothing else needed removing: this form never had actual password
  *input* UI (no `<Input type="password">` existed here — the previous
  `'mock-phone_number-auth'` literal was a synthetic placeholder to
  satisfy the old required-field type, not real user input), so there
  was no password JSX to comment out, only the payload-construction
  lines.
- `email` and the `first_name`/`last_name` handling are byte-for-byte
  unchanged, per the explicit "Do not modify the existing name/email
  behavior" instruction.

## Final Flow (Implemented)

```
1. User verifies OTP (/verify → useVerifyOTP() → authService.verifyOTP())
2. is_new_user === true → router.push('/complete-profile?phone_number=...&dialCode=...')
   (P10.8: no token/user/RBAC state touched for this case)
3. User fills first_name/last_name, accepts terms, submits
4. complete-profile builds:
   {
     country_code: dialCode,          // user's actual selected dial code
     phone_number: localPhoneNumber,  // stripped of the dial-code prefix
     first_name, last_name, email     // unchanged
     // password/confirm_password: commented out
   }
5. authService.register() → POST /auth/register/ → backend returns
   { user, tokens, p7Roles? }
6. useRegister()'s onSuccess: setUser(user) [tokens already persisted
   inside authService.register()]; setTenantRoles() if p7Roles present
```

## Not Changed

- `/register` (`RegisterClientPage.tsx`) — the separate email+password
  signup flow, its own zod schema, its own password/confirm-password
  UI. Untouched; `RegisterData`'s widening is backward-compatible with
  it (its own schema already supplies required password/confirm_password
  values at the call site, so nothing about its runtime behavior
  changes).
- `email`/`first_name`/`last_name` construction and handling in
  `complete-profile/page.tsx`.
- `authService.login()`, `authService.verifyOTP()`, `useLogin()`,
  `useVerifyOTP()`, `ROLE_PERMISSION_MAP`, `usePermissions()`,
  `useHasDashboardAccess()`, `AuthGuard`, `PermissionGuard` — none of
  these are part of the registration flow and none were touched.
