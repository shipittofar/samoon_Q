## Summary

The Savor frontend applies multiple layers of performance optimization: React Query caching (5-minute stale time, 30-minute cache time), Next.js `output: "standalone"` for Docker optimization, nginx proxy caching for static assets (7-day inactive TTL), gzip compression, and PWA service worker with cache-first static / network-first API strategies.

No performance regressions were introduced during this audit. All identified findings are architectural patterns rather than code bugs.

**Overall Performance Score: 8.0 / 10**

## Findings

### VERIFIED — P-001: React Query Cache Configuration
- **File:** `src/constants/index.ts`
- **Evidence:**
  ```ts
  export const STALE_TIME = 5 * 60 * 1000   // 5 minutes
  export const CACHE_TIME = 30 * 60 * 1000  // 30 minutes
  ```
- **Finding:** All 162 query hooks in `src/hooks/index.ts` use `staleTime: STALE_TIME` and `gcTime: CACHE_TIME`. This prevents redundant API calls during navigation and across component mounts. Configuration is appropriate for a restaurant SaaS (menu data changes infrequently; order data uses WebSocket for real-time updates).

### VERIFIED — P-002: Static Asset Caching via Nginx
- **File:** `nginx.conf` (lines 41–42, 125–131)
- **Evidence:**
  ```nginx
  proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=STATIC:10m inactive=7d use_temp_path=off;

  location /_next/static/ {
      proxy_cache STATIC;
      proxy_cache_valid 200 60d;
      add_header Cache-Control "public, max-age=31536000, immutable";
  }
  ```
- **Finding:** Next.js hashed static assets (`/_next/static/`) are cached for 60 days at nginx and given an `immutable` Cache-Control header. This is optimal — content-addressed URLs guarantee cache correctness.

### VERIFIED — P-003: PWA Service Worker Strategy
- **File:** `public/sw.js`
- **Finding:** Service worker uses cache-first for static assets and network-first for API calls. Firebase messaging service worker is separate (`public/firebase-messaging-sw.js`). PWA manifest has all 8 icon sizes (72px–512px). This enables offline capability for static content and ensures API freshness.

### VERIFIED — P-004: Next.js `optimizeCss: true`
- **File:** `next.config.ts` (line 47)
- **Evidence:** `experimental: { optimizeCss: true }` — uses `critters` to inline critical CSS and defer non-critical stylesheets. This improves First Contentful Paint (FCP).

### VERIFIED — P-005: Image Optimization
- **File:** `next.config.ts` (lines 41–50)
- **Evidence:** `remotePatterns` configured for Unsplash, Cloudinary, localhost, and S3. All images should use `next/image` for automatic WebP conversion, responsive sizing, and lazy loading.
- **Potential Issue:** Not all images in the codebase were verified to use `<Image>` from `next/image`. The `src/test/setup.ts` mocks `next/image` with a plain `<img>` for test isolation, which is correct.

### OPEN — P-006: Large Hook Index File
- **Severity:** Low
- **File:** `src/hooks/index.ts` (2,264 lines, 162 hooks)
- **Evidence:** Single barrel file exports all query and mutation hooks. This file is always loaded but most consumers only need a subset of hooks.
- **Impact:** No direct bundle size impact because tree-shaking removes unused exports. However, the file is parsed in its entirety at startup in dev mode, adding IDE indexing overhead.
- **Recommendation:** Consider splitting into domain-specific hook files (`useMenuHooks.ts`, `useOrderHooks.ts`, etc.) as part of a future refactor. Not blocking for production.

### OPEN — P-007: WebSocket Reconnect State Not Persisted Across Page Reloads
- **Severity:** Low
- **File:** `src/services/websocket.service.ts`
- **Evidence:** `DjangoChannelsWebSocket` maintains reconnect state in class instance memory. On a full page reload, the reconnect counter resets to 0. This is correct behavior and not a bug, but it means that a user with a persistently failing WebSocket connection will retry from scratch on every reload.
- **Recommendation:** No change needed. Document expected behavior.

### OPEN — P-008: Memory-Backed Rate Limiter Accumulates Without TTL Eviction
- **Severity:** Low
- **File:** `src/lib/rate-limit.ts`
- **Evidence:** The `store` Map grows indefinitely — entries for old identifiers are never evicted if those identifiers never make another request (the `prune` function only removes old timestamps, not the Map entry itself). In a long-running server process with many unique IPs, this is a memory leak.
- **Recommendation:** Add a periodic eviction pass or use a `WeakMap`-style approach. For production, replace with Redis-backed limiter (resolves both this and the cluster-safety issue from S-009 in the security audit).

### OPEN — P-009: No Bundle Size Budget Enforcement
- **Severity:** Low
- **Evidence:** `next.config.ts` does not configure `bundleSizeLimit`. There is no automated check preventing large dependency additions from shipping.
- **Recommendation:** Add `@next/bundle-analyzer` and set a budget in CI. The current `npm run build` output should be captured as a baseline.

## Remaining Risks

1. **Rate limiter memory leak under high traffic** (P-008) — low risk for current scale; fix before horizontal scaling
2. **No bundle size budget** (P-009) — risk of undetected bundle growth
3. **No automated Lighthouse CI** — no FCP/LCP/CLS baselines tracked across commits

## Production Recommendations

1. Run `npm run build` and capture bundle sizes as baseline before launch
2. Enable `@next/bundle-analyzer` for bundle composition inspection

5. Confirm all user-facing images use `next/image` — audit with `grep -rn "<img "` in `src/`
