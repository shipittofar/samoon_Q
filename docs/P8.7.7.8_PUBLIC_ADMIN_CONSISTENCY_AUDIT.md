## Phase B — Ownership Audit

### B.1 Tenant Settings

- **Source:** `tenantService.getTenant(slug)` → `MOCK_TENANTS[slug]`
- **Admin path:** `/admin/settings` reads from the same store
- **Isolation:** Each slug maps to exactly one tenant object. `DEFAULT_TENANT` is returned for unknown slugs — no cross-tenant leakage.
- **Status:** ✅ Correct

### B.2 Branch Data — Dual-Source Pattern

Two parallel data sources represent branches:

| Source | Used by | Auth required | Fields |
|---|---|---|---|
| `MarketplaceMeta.branches` (PublicBranchInfo) | Public layouts, `TenantBranchLayout`, public pages | ❌ None | slug, name, address, city, phone, openNow, todayHours, image |
| `branchManagementService.getBranches()` | Admin pages, `AdminBranchSwitcher` | ✅ Admin | id, tenantId, slug, name, location, hours, isActive, ... |

After P8.7.7.6.1 hotfix, `TenantBranchLayout` uses only `MarketplaceMeta.branches`. The dual-source pattern is intentional — not a defect.

**Cross-tenant isolation verified:** `getBranches(tenantId)` filters by `tenantId`. Every branch in every mock dataset has the correct `tenantId`. See ownership-audit.test.ts.

- **Status:** ✅ Correct

### B.3 Menu / Categories / Products

- `menuService` is tenant-scoped. All mock data is keyed by tenantId.
- Public `/menu` page calls `useMenuItems()` which includes tenantId in query key.
- Admin `/admin/menu` calls same service with same tenantId.
- No cross-tenant contamination observed.
- **Status:** ✅ Correct

### B.4 Loyalty

- `loyaltyService` is tenant + user scoped.
- Public page (`/loyalty`) uses `CapabilityGuard` before rendering `LoyaltyContent`.
- Admin page (`/admin/loyalty`) manages reward definitions.
- **Confirmed defect found (R-06) and fixed** — see Phase I.

### B.5 Reservations

- Public form submits via `reservationService`.
- Admin `/admin/reservations` reads submitted reservations.
- No shared mutable state between public form and admin list — correct isolation.
- **Status:** ✅ Correct

### B.6 Reviews

- Public page reads from `reviewService.getReviews()`.
- No admin review management page (reviews are customer-created).
- R-03 (mock reviews not tenant-scoped) documented in P8.7.7.7 as backlog — not a confirmed runtime defect (mock only).
- **Status:** ✅ No new issues

### B.7 Feature Flags

Three-layer resolution (documented in P8.7.7.6):
1. Module `defaultFeatureFlags` (lowest priority)
2. `getCapabilityFeatureFlags` from module capability declarations
3. `tenant.settings.featureFlags` overrides (highest priority)

`CAPABILITY_FLAG_MAP` translates capability names to canonical flag keys (e.g., `'loyalty'` → `'loyalty.enabled'`).

## Phase I — Confirmed Defects

### R-06 — CapabilityGuard loyalty flag mismatch for brew-cafe

**Status:** ✅ FIXED

**Root cause:**

`CapabilityGuard` checks `featureFlags[CAPABILITY_FLAG_MAP['loyalty']]` = `featureFlags['loyalty.enabled']`.

brew-cafe's `tenant.settings.featureFlags` contained only `'cafe.loyalty.enabled': true` — a module-prefixed key used by cafe-specific admin UI and the `TenantHomepageClient` multi-flag check. The canonical `'loyalty.enabled'` key was not set.

The 3-layer feature flag resolution:
- Layer 1 (cafe module `defaultFeatureFlags`): `'cafe.loyalty.enabled': false`
- Layer 2 (`getCapabilityFeatureFlags`): cafe module has `loyalty` as `optional` (not `defaultEnabled`) → sets `'loyalty.enabled': false`
- Layer 3 (brew-cafe tenant override): sets `'cafe.loyalty.enabled': true` — does **not** set `'loyalty.enabled'`

Result: `featureFlags['loyalty.enabled'] = false` → CapabilityGuard blocks the loyalty page.

**Impact:** Any brew-cafe customer clicking the "Loyalty" CTA on the homepage was shown "This feature is not available."

wheels-and-brews was NOT affected: mobile_cafe declares loyalty in `defaultEnabled`, so Layer 2 sets `'loyalty.enabled': true`.

**Fix:** Added `'loyalty.enabled': true` to brew-cafe's `tenant.settings.featureFlags` in `src/services/tenant.service.ts`.

```diff
- featureFlags: { 'menu.enabled': true, 'cafe.loyalty.enabled': true, 'reservations.enabled': true, 'analytics.enabled': true },
+ featureFlags: { 'menu.enabled': true, 'loyalty.enabled': true, 'cafe.loyalty.enabled': true, 'reservations.enabled': true, 'analytics.enabled': true },
```

**Files changed:**

| File | Change |
|---|---|
| `src/services/tenant.service.ts` | Added `'loyalty.enabled': true` to brew-cafe featureFlags (Layer 3) |
| `src/test/context-integrity.test.ts` | Added R-06 regression tests (3 new tests) |

**Regression verification:**

| Scenario | Result |
|---|---|
| brew-cafe loyalty page (CapabilityGuard) | ✅ Now passes — `loyalty.enabled: true` |
| wheels-and-brews loyalty (unchanged) | ✅ Still passes via Layer 2 defaultEnabled |
| savor loyalty (not enabled) | ✅ Still blocked — `loyalty.enabled` not in override |
| All other tenants | ✅ Unchanged |
| TypeScript | 0 errors |
| Full test suite | 4,939 / 4,939 passing |
