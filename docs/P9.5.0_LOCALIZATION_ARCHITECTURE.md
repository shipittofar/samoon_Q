# P9.5.0 — Platform Localization Architecture

> Documentation only — no code in this phase. Designs the permanent
> localization standard for the platform: a `localization.languages`
> collection (150+ entities, exactly the Countries pattern from P9.2) plus
> the surrounding sub-systems (Translation Keys, Namespaces, Versions,
> Import/Export, Coverage, Fallback). Every design decision below extends
> `PlatformConfigurationRegistry`/`ConfigurationService`/the `'collection'`
> field type/the Configuration Studio (P9.0–P9.4) — nothing here proposes a
> parallel engine unless a genuine, documented gap makes that the honest
> choice (see §5).
>
> Last updated: 2026-07-05

---

## 1. Module hierarchy

```
Localization  (IA group — new; see docs/P9.5.0_LANGUAGE_LIFECYCLE.md §4 for why it isn't 'Configuration')
├── localization.languages        Phase 1 — the language registry (this doc, §2)
├── localization.regions          Phase 1 — canonical region taxonomy (reused, not reinvented — §2.3)
├── localization.rtl              Folded into the Languages schema (§2.2) — not a separate module (a per-language boolean, not an independent entity set)
├── localization.fonts            Phase 2 — font stacks available for assignment to a language (§2.4)
├── localization.formatting       Folded into the Languages schema (§2.2) — number/date/time/currency/timezone are per-language properties, not a separate collection
├── localization.translation_keys Phase 2 — see docs/P9.5.0_TRANSLATION_ARCHITECTURE.md
├── localization.translation_memory  Phase 3 — see docs/P9.5.0_TRANSLATION_ARCHITECTURE.md §5
├── localization.import_export    Phase 3 — see docs/P9.5.0_TRANSLATION_ARCHITECTURE.md §4
└── localization.coverage         Phase 2 — a computed view over translation_keys (§ below), not a stored collection
```

"Phase 1/2/3" here are **design-priority labels for the eventual
implementation roadmap (P9.5.1+)**, not phases of this documentation-only
phase — see each doc's closing roadmap section.

## 2. `localization.languages` — the language registry

Mirrors `countries.registry` (`src/config/modules/countries.ts`, P9.2)
exactly: one `'collection'` field, one schema, a fixed `entityIds` roster
of every language the platform will ever support (150+), most of them
`enabled: false` until activated — precisely the "exists in the registry,
disabled until activated" requirement, already proven at 176 entities by
Countries.

### 2.1 Entity id

BCP 47 language tag, not bare ISO 639-1 — `en`, `fa`, `ar`, `zh-Hans`,
`it`, `tr` for the six initially-enabled languages, but the roster also
carries entries like `ar-EG`/`ar-SA` (§2.5 — Locales vs. Languages) and
`zh-Hant` alongside `zh-Hans`. Using BCP 47 from day one avoids a breaking
id migration when the first regional variant is needed — Countries didn't
face this (ISO 3166-1 alpha-2 has no variant concept), so this is a
genuine place Localization's schema differs from copying Countries
verbatim, not an oversight.

### 2.2 Schema (per-language properties)

| Property | Type | Notes |
|---|---|---|
| `enabled` | boolean | Master on/off switch — platform-only, see §"Owner Permissions" |
| `visible` | boolean | Shown in the language switcher. `enabled && !visible` = reachable by direct link/query param but not advertised — the mechanism a beta tester group uses before a language is publicly listed |
| `activation_tier` | select: `stable` \| `beta` \| `experimental` | Independent of `enabled`/`visible` — a *stable* language can still be disabled (e.g. temporarily pulled for a translation error), and a *beta* language can be fully visible to opted-in users. Mirrors Countries' `status` **in spirit** but is a separate axis from lifecycle (§`P9.5.0_LANGUAGE_LIFECYCLE.md` §3 explains why these don't collapse into one field) |
| `status` | select: `draft`\|`testing`\|`published`\|`deprecated`\|`archived` | The same 5 values as `ConfigLifecycleState` (`src/config/types.ts`), hand-listed as select options exactly the way Countries' own `status` property already does — reusing the *vocabulary*, not the field-level `lifecycle` mechanism (which applies to the whole `localization.languages` field, not one entity inside it) |
| `native_name` | string | e.g. "فارسی" |
| `english_name` | string | e.g. "Persian" |
| `region` | select (7 values) | **Reuses** `CountryRegion`'s exact taxonomy (`src/config/modules/countries-registry-data.ts`) — North America/South America/Europe/Middle East/Asia/Africa/Oceania — rather than inventing a second, linguistically-motivated region system. One shared taxonomy across Countries and Languages is a deliberate Rule-3 decision: two different "region" vocabularies on the same Studio would be a worse outcome than an imperfect fit (e.g. Arabic spanning "Middle East" and "Africa" — resolved by `region` meaning "primary/administrative region for platform purposes," matching how Countries already handles multi-region ambiguity) |
| `rtl` | boolean | Right-to-left. Per-language, not a derived array (closes the "3 hardcoded RTL lists" gap from the audit) |
| `plural_rule_locale` | string | **Not a custom plural engine** — this stores the BCP 47 tag `Intl.PluralRules` should be constructed with (usually the entity id itself; occasionally a related tag for a language `Intl.PluralRules` doesn't recognize natively, e.g. a constructed/regional variant). Design decision, §4. |
| `gender_agreement` | select: `none`\|`two_way`\|`three_way` | Whether UI strings in this language need grammatical-gender variants (§`P9.5.0_TRANSLATION_ARCHITECTURE.md` §3 — resolved at the translation-key level, not here; this flag only tells the Studio whether to show gender-variant fields for this language's keys) |
| `default_currency` | select (ISO 4217) | Same `uiControl: 'currency_picker'` already used by Countries |
| `default_timezone` | string | Same `uiControl: 'timezone_picker'`, same `preview: { kind: 'datetime' }` reuse as Countries' `timezone` property (P9.3 Phase J) — zero new preview code |
| `date_style` | select: `short`\|`medium`\|`long`\|`full` | Maps directly to `Intl.DateTimeFormat(locale, { dateStyle })` — **no custom date-pattern string is stored**; formatting is always delegated to `Intl`, never hand-rolled (§4) |
| `hour_cycle` | select: `h12`\|`h23` | Maps directly to `Intl.DateTimeFormat(locale, { hourCycle })` |
| `font_family` | select, sourced from `localization.fonts` (§2.4) | |
| `fallback_locale` | select, options = this same collection's `entityIds` | One-hop fallback pointer; chain resolution (`ar-EG` → `ar` → `en`) is a pure function over this property, see `P9.5.0_TRANSLATION_ARCHITECTURE.md` §6 |
| `translation_coverage_percent` | number (0–100) | **Computed, not hand-edited** — same pattern as Countries' `phone_example` (derived from `src/data/countries.ts` at default-construction time, P9.2): recomputed from `localization.translation_keys` (§3) whenever a translation is added/removed, never manually typed by an admin |
| `notes` | string (textarea) | |

~18 properties — the same order of magnitude as Countries' 22, for the
same reason: broad but not deep, everything else (actual translated
strings) lives in the Translation Keys collection instead of bloating this
schema per-key.

### 2.3 Regions

Deliberately **not** a second collection. `region` is a `select` property
on the Languages schema (§2.2) whose options are the same 7 canonical
`CountryRegion` values Countries already registered. Introducing a
`localization.regions` module would either (a) duplicate that taxonomy —
the exact "duplicated architecture" this phase's constraints forbid — or
(b) require Countries to start reading from a new Localization-owned
region registry, which is a P9.2 rewrite this phase's constraints also
forbid. Reusing the existing constant is the only option that satisfies
both constraints simultaneously.

### 2.4 Fonts

`localization.fonts` is a **second, small collection** (not folded into
the Languages schema) because fonts and languages are a many-to-many
relationship — one font (e.g. "Noto Sans") can serve several languages,
and a language's `font_family` property (§2.2) selects one *primary* font
from this roster:

| Property | Type | Notes |
|---|---|---|
| `family_name` | string | e.g. "Noto Sans Arabic" |
| `source` | select: `google_fonts`\|`local`\|`custom_upload` | |
| `variable_font` | boolean | Whether it's a variable-font file (single file, many weights) vs. static per-weight files |
| `supports_rtl_scripts` | boolean | |
| `fallback_stack` | string | CSS `font-family` fallback list, e.g. `"'Noto Sans Arabic', 'Segoe UI', sans-serif"` |
| `preview_text` | string | Per-script pangram/sample used by the Inspector's Preview tab (reuses `ConfigFieldPreview`'s `'font-sample'` kind, already built for the Themes module, P9.0 — zero new preview code) |

This directly extends the existing **Typography module**
(`src/config/modules/typography.ts`, `group: 'Configuration'`) rather than
replacing it: Typography's fields describe the platform's *default*
font/scale settings; `localization.fonts` is the *catalog* a language can
pick one entry from. The relationship is compositional (Typography reads
one more option from a Localization-owned list), not an architectural
merge of the two modules.

### 2.5 Locales vs. Languages

The phase brief uses "Languages" and "Locales" as separate hierarchy
items. Resolution: **a Locale is a Language entity whose id carries a
region subtag** (`ar-EG` vs. the neutral `ar`). Both are rows in the same
`localization.languages` collection — there is no second "Locales"
collection, because a locale variant needs the exact same schema as a
bare language (its own `enabled`/`rtl`/`date_style`/etc., which can differ
from the neutral entry — Egyptian Arabic's `default_currency` is EGP,
Saudi Arabic's is SAR, both fall back to neutral `ar` for shared strings
via `fallback_locale`). This is a deliberate simplification versus a
"Language has many Locales" two-table design — chosen because the
Collection Framework has no native concept of nested/child collections,
and inventing one for this single use case would be exactly the
"duplicate architecture" this phase must avoid.

## 3. Translation Keys — why they are NOT a `localization.languages`-shaped collection

A translation key (e.g. `checkout.confirm_button`) needs one value **per
enabled language** — a column count that grows every time a language is
enabled. The `'collection'` field type (P9.2) assumes a **fixed schema**
shared by every entity; it has no mechanism for "N columns, where N
changes at runtime." Forcing translation keys into a
language-columns-per-row shape would require either hardcoding a column
per language (defeating the entire "150+ languages, no code change to add
one" goal) or a schema-migration step on every language activation —
neither acceptable.

**Resolution:** flip the entity granularity. `localization.translation_keys`
is a collection whose **entity is one (namespace, key, language) triple**,
not one key. Entity id: `${namespace}.${key}.${languageCode}` (e.g.
`checkout.confirm_button.fa`). Schema:

| Property | Type | Notes |
|---|---|---|
| `value` | string (textarea) | The translated string itself |
| `status` | select: `missing`\|`machine`\|`reviewed`\|`approved` | Per docs/P9.5.0_TRANSLATION_ARCHITECTURE.md §2 |
| `plural_variants` | json | `{ one: "...", other: "..." }` etc. — keys drawn from `Intl.PluralRules(language).resolvedOptions().pluralCategories`, never hardcoded (§4) |
| `gender_variants` | json | Present only when the language's `gender_agreement` (§2.2) isn't `none` |
| `updated_by` | string | Actor id — redundant with the field's own audit trail (`configurationAudit`) but kept as a denormalized display column for the collection table, the same way Countries' `notes` duplicates information also visible in the Inspector |
| `source_namespace_version` | string | Which Translation Version (docs/P9.5.0_TRANSLATION_ARCHITECTURE.md §5) this value was authored against |

This is now a genuinely fixed schema — adding language #151 adds *rows*
(new triples), never a new *column* — exactly the property that makes the
Collection Framework the right tool here after all, once the entity
granularity is corrected. **This is the one real architectural finding of
this phase**: the naive "one row per key" design does not fit the existing
framework, and the fix is a modeling correction, not a new framework
capability — consistent with how P9.2 found the `entityIds` fixed-roster
gap and P9.4 found the auto-namespacing gap: real problems, framework-level
fixes, no bespoke code.

`localization.coverage` is **not a stored module at all** — it's a
computed read (`count(status != 'missing') / count(*)` grouped by
language) over `translation_keys`, surfaced as a Platform Dashboard widget
(reusing `platformDashboardRegistry`, P9.4 Phase D) and as each language
entity's own `translation_coverage_percent` (§2.2).

## 4. Formatting — the one governing principle

**Every number/date/time/currency format is delegated to `Intl.*`,
parameterized by the language entity's stored properties (`date_style`,
`hour_cycle`, `default_currency`) — the platform never stores or
hand-rolls a format pattern string.** This is the single most important
architectural decision in this document, stated once so every other
section can rely on it rather than re-deciding it per feature:

```ts
// illustrative — not implemented in this phase
new Intl.DateTimeFormat(languageEntity.id, {
  dateStyle: languageEntity.date_style,
  hourCycle: languageEntity.hour_cycle,
})
new Intl.NumberFormat(languageEntity.id, {
  style: 'currency',
  currency: languageEntity.default_currency,
})
new Intl.PluralRules(languageEntity.plural_rule_locale)
```

Trade-off accepted: `Intl` doesn't cover every conceivable format
customization (a tenant wanting a genuinely nonstandard date pattern isn't
supported this way) — accepted deliberately, because hand-rolled format
strings are exactly the kind of per-language special-casing that would
prevent "supporting 150+ languages without architectural changes."

## 5. Regional Overrides

A tenant may need to override a language's `default_currency` or
`default_timezone` for its own storefront (e.g. a US-based multi-currency
restaurant group serving a Persian-speaking market wants Persian content
priced in USD, not IRR). This is **not a new mechanism** — it is the
existing inheritance chain (`ConfigInheritanceLevel`: platform → tenant →
branch → user, P9.0) applied to the `localization.languages` field exactly
the way Countries' `countries.registry` field already permits tenant-level
overrides (`inheritance: { level: 'platform', canOverride: true, mode:
'override' }`). No new override mechanism is designed here because none is
needed.

## 6. Currencies & Timezones

Not re-designed. `default_currency`/`default_timezone` (§2.2) reference
the same ISO 4217 / IANA identifiers Countries already uses, through the
same `currency_picker`/`timezone_picker` `uiControl`s. A currency or
timezone is a property value, not an entity Localization needs its own
registry for.
