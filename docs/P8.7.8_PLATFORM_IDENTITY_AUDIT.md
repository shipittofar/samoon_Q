## 1. Executive Summary

The platform has successfully implemented a multi-tenant architecture in its backend, routing, RBAC, and tenant-level pages. However, the **platform-level public face** — the root landing page (`/`), root layout, footer, navigation, `/restaurant` page, JSON-LD schema, and sitemap — still presents as a **single fine-dining restaurant called "Savor"** rather than a hospitality SaaS marketplace.

This creates a fundamental identity contradiction: the platform is architecturally multi-tenant but visually and textually single-restaurant at every entry point a first-time visitor encounters.

### Severity Summary

| Severity | Count | Examples |
|----------|-------|---------|
| 🔴 Critical | 8 | Root metadata, homepage hero, footer address/copyright, `/restaurant` page, JSON-LD schema |
| 🟠 High | 7 | Homepage CTA wording, categories section, stats block, sitemap, footer links, nav item "Restaurant" |
| 🟡 Medium | 6 | OrderTracker copy, CartDrawer copy, empty states, favicon/OG image, push notification title |
| 🟢 Low | 5 | Store persistence keys, admin dashboard landing, JsonLd component, social links, header fallback name |

## 3. Phase B — Information Architecture

### B.1 Current Navigation (Platform Root)

When a user visits the platform homepage (`/`), the header nav is driven by `useModuleNav()` → `getHeaderNav()` with no tenant context, which returns **all enabled modules' navItems**:

```
Menu  |  Reservation  |  Restaurant  |  [Sign In]  [Get Started]
```

This is a restaurant website navigation pattern. It does not communicate that the user is on a multi-business platform.

### B.2 Current Navigation (Tenant Context)

When inside a tenant (`/savor/*`, `/brew-cafe/*`), the nav correctly filters to that tenant's active module navItems. This is correct and should be preserved.

### B.3 Problems with Current Platform-Level IA

1. **No Discover entry point** — the most important platform page (`/discover`) is not in the nav.
2. **"Restaurant" nav item** — links to a single restaurant's about page at platform level.
3. **"Menu" nav item** — sends users to one restaurant's menu, not a browse experience.
4. **"Reservation" nav item** — for one restaurant, not the platform.
5. **No "For Owners" or "List Your Business"** — platform monetisation entry point is absent.
6. **No platform identity signal** — a first-time visitor cannot tell this is a multi-tenant platform.

### B.4 Recommended Platform-Level IA

The platform root should have a navigation that communicates it is a marketplace:

```
Discover  |  Categories  |  For Owners  |  [Sign In]  [List Your Business]
```

**Detail:**

| Nav Item | Path | Purpose |
|----------|------|---------|
| Discover | `/discover` | Browse all registered businesses |
| Categories | `/discover?category=...` (dropdown) | Browse by business type |
| For Owners | `/owners` (new page) | Platform value prop for business owners |
| Sign In | `/login` | Existing |
| List Your Business | `/register` or `/owners#get-started` | Primary owner acquisition CTA |

### B.5 Tenant-Level IA (Preserve)

Inside a tenant context (`/[tenantSlug]/*`), the current module-driven nav is correct. The tenant's own nav items (Menu, Reservation, etc.) are appropriate. No changes needed there.

### B.6 Hierarchy Clarification

```
Platform level (/)
├── Discover (/discover)
├── Categories (/discover?category=X)
├── For Owners (/owners)
└── [tenant landing] (/[tenantSlug])
    ├── Menu (/[tenantSlug]/[branchSlug]/menu)
    ├── Reservation (/[tenantSlug]/[branchSlug]/reservation)
    └── Branch home (/[tenantSlug]/[branchSlug])
```

The current platform homepage bypasses the Discover layer and drops users directly into one restaurant's menu, skipping the entire marketplace value proposition.

## 5. Phase D — Customer Journey

### D.1 Current Journey

```
/ (platform homepage)
→ /menu  (one restaurant's menu — customer never chose a restaurant)
→ /checkout
→ /checkout/success
```

Or:

```
/ (platform homepage)
→ /reservation  (one restaurant's reservation — no business selected)
```

### D.2 Problems

1. **Business selection is skipped.** The homepage CTAs (`Order Now` → `/menu`, `Reserve a Table` → `/reservation`) bypass the entire discovery layer. A user is immediately in one restaurant's context without having chosen it.

2. **Discover page exists but is not linked from homepage.** `/discover` is a working marketplace page but is orphaned — it's not in the homepage CTAs, not in the homepage nav (platform level), and not in the footer.

3. **`/menu` route at platform root.** This route serves a single restaurant's full menu at the platform root URL. In a multi-tenant architecture, `/menu` should either be removed (customers browse via `/{tenantSlug}/{branchSlug}/menu`) or redirect to `/discover`.

4. **`/reservation` route at platform root.** Same issue — this serves one restaurant's reservation form at the platform root.

5. **Branch selection before order.** The journey correctly requires branch selection at the tenant level (`/[tenantSlug]/[branchSlug]/menu`), but the platform root bypasses this.

### D.3 Correct Journey

```
/ (platform homepage — search + discover)
↓
/discover (browse businesses by category, location, name)
↓
/[tenantSlug] (business homepage — logo, description, branches, info)
↓
/[tenantSlug]/[branchSlug] (branch homepage — hours, menu preview)
↓
/[tenantSlug]/[branchSlug]/menu (browse + add to cart)
↓
/checkout (tenant-scoped cart)
↓
/checkout/success
↓
/[tenantSlug]/[branchSlug]/loyalty (optional post-order)
```

### D.4 Journey Verification

| Step | Route | Status | Issue |
|------|-------|--------|-------|
| Platform homepage | `/` | ❌ Wrong | Skips to single restaurant; no discovery |
| Discover | `/discover` | ✅ Exists | Not linked from homepage or footer |
| Business page | `/[tenantSlug]` | ✅ Correct | Uses dynamic tenant data |
| Branch page | `/[tenantSlug]/[branchSlug]` | ✅ Correct | Tenant-scoped |
| Menu | `/[tenantSlug]/[branchSlug]/menu` | ✅ Correct | Tenant + branch scoped |
| Reservation | `/[tenantSlug]/[branchSlug]/reservation` | ✅ Correct | Tenant + branch scoped |
| Checkout | `/checkout` | ✅ Cart is tenant-scoped | OK |
| Loyalty | `/[tenantSlug]/[branchSlug]/loyalty` | ✅ Correct | Feature-flagged |

The tenant-level pages work correctly. The problem is entirely at the platform root entry points.

The `AdminContextBar` (tenant/branch switchers) partially addresses context, but the dashboard landing (`/console/orders`) drops the owner directly into operational data without establishing the platform management frame.

## 9. Phase H — UI Consistency Audit

### H.1 Color / Theme

The platform uses orange (`orange-500`, `orange-400`) as its primary brand color throughout:

- Hero overlays, CTA buttons, stat highlights, hover states, borders, icon accents
- This is a deliberate brand choice and is **consistent**

**Issue:** Orange is strongly associated with the Savor restaurant brand. If "Savor" is meant to be both a tenant (one restaurant) and the platform brand simultaneously, orange is acceptable. If the platform is repositioning itself as a neutral marketplace, the color could be perceived as biased toward the Savor tenant.

**Recommendation:** No immediate change required. Document the design decision: orange = platform brand, applies to all marketplace chrome. Individual tenant themes override this within their pages.

### H.2 Illustrations and Images

| Usage | Current | Problem |
|-------|---------|---------|
| Hero background | Restaurant interior (Unsplash `photo-1414235077428-338989a2e8c0`) | Single restaurant ambiance |
| `/restaurant` gallery | 6 restaurant interior photos | Specific to one aesthetic |
| Category icons | Emoji (🍕🍔🍝🥤🍰) | Food items; correct if these are menu categories, but wrong if they're meant to be business types |
| Business type icons | `CategoryFilter.tsx` uses emoji per type (🍽️ restaurant, ☕ café, 🍸 bar, etc.) | ✅ Correct for marketplace categories |

**Recommendation:**
- Hero: Replace restaurant photo with a platform-appropriate image (diverse food businesses, city food scene, or an abstract/illustration)
- Category icons: Replace menu-item emojis on homepage with business-type icons from `CategoryFilter.tsx`

### H.3 Empty States

| Context | Current Text | Problem |
|---------|-------------|---------|
| Cart empty | "Add some delicious items from our menu" | "our menu" — restaurant framing |
| Kitchen display | "Empty" (generic) | ✅ Acceptable |

| Menu no results | "No items match your current filters." | ✅ Neutral — keep |

### H.4 Loading States

Not explicitly audited. If any loading states say "Loading Savor..." they should use `APP_NAME` or a neutral message.

### H.5 Error States

### H.6 Icons

The `ChefHat` icon from lucide-react is used in:
- `OrderTracker.tsx` (preparing step) — restaurant-specific
- `FoodCard.tsx` (customize button) — acceptable for menu items

**Recommendation:** In `OrderTracker`, make the preparing-step icon parameterised by business type (e.g. `Coffee` for café, `Truck` for food truck, `ChefHat` for restaurant).
