# P9.5.6 — Language Administration Center: Phase A Audit

Read-only audit performed before any code changes, per the phase spec. Covers
P9.2 (Collection Framework), P9.3 (Configuration Studio), P9.4 (Platform
Administration), and P9.5.0–P9.5.5 (Localization).

## 1. P9.2 Collection Framework

`src/config/collection.ts` exports `configCollection`, a pure, side-effect-free
namespace: `getSchema`, `getEntityDefaults`, `getCollectionEntries`,
`getEntityValues`, `buildMergedCollectionValue`, `resetEntityToDefault`,
`getEntityLabel`, `matchesFilters`. A collection-typed `ConfigFieldDefinition`
carries a `collection` metadata block: `entityLabel`, `entityIdLabel`,
`schema: ConfigFieldDefinition[]`, `entityIds?` (fixed roster; omitted for
ad-hoc), `defaultGroupBy?`, `getEntityLabel(id)`, `getEntitySearchTerms?(id)`,
`buildPreview?(values)`.

UI: `src/components/admin/configuration/ConfigurationCollectionTable.tsx`
(search/filter/group/sort/bulk-actions/stats) and
`ConfigurationEntityDrawer.tsx` (7 tabs: configuration, overrides,
dependencies, audit, statistics, inheritance, preview — renders every schema
property through the same `ConfigurationFieldControl`/`Badges`/`Preview`
components used for ordinary fields). `countries.ts` is the reference
implementation: 176-entry fixed roster, 23-property schema, `defaultGroupBy:
'region'`, custom label/search/preview closures.

**Conclusion: the generic table/drawer/bulk-action machinery is complete and
reusable as-is. Any new admin UI for languages should NOT reimplement a
table, drawer, or bulk-action toolbar.**

## 2. P9.3 Configuration Studio

All in `src/components/admin/configuration/`. `ConfigurationModulePage.tsx` is
the one generic page for any `ConfigModuleDefinition` (collection-typed or
not) — dispatch between `ConfigurationFieldControl` and
`ConfigurationCollectionTable` happens inside `ConfigurationFieldRow.tsx`
based on `field.type === 'collection'`. Supporting shell:
`ConfigurationStudioLayout`, `ConfigurationStudioNav`,
`ConfigurationStudioToolbar`, `ConfigurationInspector` (9 tabs, driven by
`fieldId`), `ConfigurationInheritanceTree`, `ConfigurationSaveBar`,
`ConfigurationCommandPalette`, `ConfigurationHistoryTimeline` (full audit
timeline + rollback for one field), `ConfigurationCompareView` (snapshot
diffing across inheritance layers).

**Conclusion: there is no separate "collection module page" — everything a
language admin page needs (search, filters, drawer, history, compare,
rollback) already exists generically for the `platform.languages.registry`
field, because it is an ordinary collection field.**

## 3. P9.4 Platform Administration

- `register-module.ts` — `registerAdminModule()`, the one function every
  platform-admin module calls; auto-namespaces field ids, registers through
  the `@/config` barrel (not the bare registry — see the P9.5.5.1/P9.5.5.2
  incident notes in that file for why).
- `dashboard.ts` — `platformDashboardRegistry`; `PlatformWidgetDefinition`
  supports `kind: 'stat' | 'list' | 'status'`. Widgets already exist that
  read the *live* resolved language collection (`src/platform-admin/
  widgets.ts`, P9.5.5 Phase H) rather than static mock numbers.
- `search.ts` / `search-providers.ts` — `platformSearchRegistry`; existing
  providers (`businesses`, `platform_users`, `countries`) all follow the same
  `searchCollectionField(fieldId, moduleId, query)` pattern against a
  collection field's default/resolved value.
- `permissions.ts` — `platform.localization.view` / `.manage` permissions
  already exist and are already granted to the correct roles.

**Conclusion: dashboard widgets and search providers are both metadata-thin
registrations against existing generic infrastructure — a language search
provider or additional stat widgets are additive, not new UI.**

## 4. P9.5.0–P9.5.5 Localization — two separate systems

**(A) `src/config/modules/languages.ts`** (P9.0/P9.5.1A) — 3 plain fields
(`languages.supported`, `languages.default`, `languages.rtl_locales`)
backing `src/i18n/runtime.ts`, the actual request-time locale resolution
engine. Small, 6-language roster (`src/i18n/language-registry.ts`).

**(B) `src/platform-admin/modules/languages.ts`** (P9.5.5, the "Language
Collection module") — one collection field, `platform.languages.registry`,
30-language roster (6 operational + 24 additional), 30-property schema
already covering identity, lifecycle (`status`, `enabled`, `visibility`,
`default`, `beta`, `experimental`, `lastUpdated`, `translator`), coverage
(`translationCoverage`, `completionPercent`, `machineTranslated`,
`humanReviewed`), Intl-only formatting fields (`currency`, `timezone`,
`dateStyle`, `hourCycle`, `numberNotation`, `pluralRules`,
`fallbackLanguage`), direction (`direction`, `rtl`), and typography
(`fontFamily`, `secondaryFontFamily`, `headingFontFamily`, `monoFontFamily`,
`fontScale`, `lineHeight`, `letterSpacing`, `fontWeight`).

**A cross-entity validation function already exists and is unit-tested**:
`validateLanguageCollection(entries)` in the same file — checks single
default, valid direction, direction/rtl agreement, published-requires-
required-fields, and fallback-chain cycles. **It is not called from any UI
path today** — this is a real, confirmed gap, not something to reimplement.

RTL preview today is just the collection field's `buildPreview()` closure,
rendered by the drawer's existing generic Preview tab — there is no
dedicated live-preview component anywhere.

Dashboard widgets (`operational_languages`, `avg_translation_coverage`,
`human_reviewed_languages`, `lowest_coverage_languages`) already read the
live collection.

**The 30-language Platform Admin collection and the 6-language runtime
(`i18n/runtime.ts`) are not wired together.** Toggling `enabled` in the
Language Administration Center today has no effect on what's actually
selectable/rendered at runtime. This is a real, confirmed gap.

## 5. Version/Diff/Audit framework

- `version-manager.ts` — module-level version bumps + change notes only
  (`recordVersion`, `historyFor`, `currentVersion`). No field- or
  entity-level versioning.
- `diff.ts` — inheritance-chain / scope-to-scope diffing (`diffField`,
  `diffModule`, `diffFieldAcrossScopes`). Not a "release A vs release B"
  diff engine.
- `audit.ts` — flat, in-memory, append-only audit log keyed by `fieldId` +
  `scope`, with rollback support and sensitive-value redaction.
- **No draft/testing/published/archived state machine exists anywhere in the
  framework.** `ConfigLifecycleState` is a flat, descriptive field (defaults
  to `'published'`), not a workflow with gated transitions. The Studio
  toolbar's "Publish" button is an explicit alias for the ordinary save
  pipeline (documented as such in its own source comment). Countries and
  Languages each separately define a per-entity `status` schema property
  with the same 5-value enum — that's a schema field like any other, not a
  framework-level workflow engine.

**Conclusion: P9.5.6's "Publishing Workflow" phase should compose the
existing version-manager + audit + validation function — not invent a new
state-machine framework.**

## 6. Existing test patterns to follow

`src/test/p9-5-5-language-management.test.tsx` is the direct precedent:
module-registration reuse checks → `validateLanguageCollection` unit tests →
widget-correctness-from-real-collection checks → permission checks →
"renders through the exact same Studio shell, zero new component code"
assertions → regression checks that unrelated modules are unaffected. New
P9.5.6 tests should follow this shape.

## Identified gaps (the actual scope of P9.5.6)

1. **Validation not wired to any save/publish path** — `validateLanguageCollection()`
   exists, is correct, and is dead code from the UI's perspective.
2. **30-language admin collection and 6-language runtime are disconnected** —
   no mechanism propagates `enabled`/`default` from the admin collection to
   what `i18n/runtime.ts` actually resolves.
3. **No live preview** of a language's typography/direction against real
   pages.
4. **No translation-quality/missing-key tooling surfaced in Platform Admin**
   — a coverage script exists from P9.5.2/P9.5.4 (`scripts/check-
   translation-coverage.mjs`) but nothing in the admin UI surfaces per-
   language key-level detail (missing/duplicate/broken-ICU/broken-
   placeholder).
5. **No import/export UI**, though the bulk-action framework
   (`useConfigurationBulkActions`) already has `export`/`import` action
   kinds wired to nothing concrete yet.
6. **No language search provider** registered (trivial gap — three other
   providers already demonstrate the exact pattern to copy).
7. **No runtime/performance stats surfaced per language** (bundle size,
   load time, cache hits) — real bundle size is derivable from actual
   locale JSON file sizes on disk; the rest would need real instrumentation
   that doesn't exist yet and would have to be honestly mocked.

## What P9.5.6 must NOT do

- Reimplement `ConfigurationCollectionTable`/`ConfigurationEntityDrawer`/the
  Studio shell.
- Add a new state-machine/workflow framework — compose the existing
  version-manager + audit + the existing validation function.
- Change any tenant-facing route or runtime behavior for requests that don't
  opt into a preview.
- Duplicate the six example pages (Home/Login/Menu/Checkout/Dashboard/
  Console) — any live preview must render the real, existing pages.
