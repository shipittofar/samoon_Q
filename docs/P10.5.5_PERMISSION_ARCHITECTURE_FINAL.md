# Permission Architecture — Final Reference

Authoritative, implementation-independent description of the P7 tenant
authorization model as it exists after P10.4.x (legacy engine removal)
and P10.5.1-P10.5.5 (consolidation, dead-state removal, and this
finalization pass). Written so a backend engineer can implement the
corresponding API without reading frontend source.

This document describes the **frontend's current behavior**, including
its known gaps. Section "Real Backend Migration Requirements" states
what must change before this model is production-safe against a real
backend — see `docs/P10.5.5_RBAC_REAL_MODE_SECURITY.md` for the full
security analysis behind those requirements.

---

## Permission Sources

There are exactly five inputs that combine to produce a user's effective
permission set for the active tenant. No other source exists.

| # | Source | What it is | Where it lives |
|---|---|---|---|
| 1 | **Tenant Role Grants** | A list of role names (`Role[]`) assigned to the user for a specific tenant | `tenantRoles` — client store, populated at login |
| 2 | **User Overrides** | Per-user allow/deny lists layered on top of role grants | `userOverrides` — client store, populated via admin UI |
| 3 | **Role → Permission Map** | The static mapping of each `Role` to its full `P7Permission[]` grant | `ROLE_PERMISSION_MAP` — a constant, ships with the frontend build |
| 4 | **Ownership Resolution** | If the acting identity owns the active tenant, they receive the Owner role's full permission set, regardless of `tenantRoles` | Computed from Owner records + tenant `ownerId` |
| 5 | **Staff Assignment** | If the acting identity holds one or more active, non-expired branch/tenant staff assignments, each assignment's role's permissions are granted (with a `mode: 'read'`-only downgrade for read-scoped assignments) | Computed from `StaffAssignment` records |

A permission's presence in the final effective set does not indicate
which source granted it — sources 1+2+3 and sources 4+5 are unioned, not
layered with priority, **except** that a `deny` in User Overrides removes
a permission even if granted elsewhere in sources 1-3 (see "Permission
Overrides" below; overrides do not apply to the Ownership/Staff branch).

**`Role` is a closed, fixed set** (`owner`, `admin`, `manager`, `cashier`,
`kitchen`, `waiter`, `marketing`, `support`, plus `customer` implicitly
holding zero grants). There is no mechanism today for a tenant to define
a custom role that participates in permission resolution — see "Out of
Scope: Custom Roles" below.

**Platform Administration is a separate authorization domain**, covering
cross-tenant platform-operator routes. It uses its own role set
(`PlatformRole`), its own permission set (`PlatformPermission`), and its
own guard/hook pair, and never intersects with the five sources above.
Not covered further in this document.

## Resolution Flow

For a given authenticated identity and active tenant:

1. Look up the identity's tenant role grants (source 1) for the active
   tenant. If none, start from an empty role list.
2. Expand those roles to a permission set via the Role → Permission Map
   (source 3).
3. Apply User Overrides (source 2): add every `allow`-listed permission,
   then remove every `deny`-listed permission, for that (user, tenant)
   pair. Deny always wins over allow within this step.
4. Independently compute the Ownership/Staff-driven permission set
   (sources 4+5, see next two sections). If the identity is not an
   eligible Owner and holds no active Staff Assignment, this set is
   empty.
5. **Union** the step-3 result with the step-4 result. The final
   effective permission set is the deduplicated union — an identity
   receives everything either path grants; neither path can revoke a
   permission the other path grants (overrides only apply within step 3).
6. A permission's presence in the final set is what a UI-facing
   "may this identity do X" check consults. It does not by itself imply
   "the backend must also allow this" — see "Real Backend Migration
   Requirements".

There is exactly one implementation of this flow. No second resolver
exists anywhere in the codebase that recomputes permissions differently.

## Owner Authorization

An identity is treated as the tenant's Owner when:
1. An Owner record exists for that identity, AND
2. That Owner record is "eligible" (not suspended/deactivated), AND
3. The tenant's `ownerId` references that Owner, AND
4. The tenant itself is "eligible" (active, not archived/suspended).

When all four hold, the identity receives the **full Owner role's
permission set** unconditionally — this is a short-circuit, not a role
grant that could be revoked by a User Override. Owner status is
re-evaluated on every resolution call (not cached at login), so losing
tenant ownership or having the tenant suspended removes access
immediately on the next render, without requiring logout.

## Staff Authorization

An identity is treated as Staff when:
1. A Staff Member record exists for that identity, AND
2. That Staff Member record is eligible (not suspended), AND
3. At least one Staff Assignment for that Staff Member is currently
   **effective** — enabled, not expired (`validUntil` in the future or
   absent), and scoped to the active tenant (optionally a specific
   branch).

Each effective assignment contributes its assigned role's permission
set. Multiple simultaneous assignments (e.g. `cashier` + `kitchen`)
union their permission sets — this is by design, not a bug (verified by
the `multirole@samoon.com` demo account, which holds two separate active
assignment rows rather than one collapsed record).

An assignment with `mode: 'read'` downgrades its role's writes to `.view`
equivalents only — the one piece of resolution logic that has no
equivalent in the plain Role → Permission Map path, since it only makes
sense for a temporary/scoped assignment, not a persistent tenant role
grant.

Expiry is enforced live: a background timer fires at the assignment's
`validUntil` moment to force a permission recomputation, so a temporary
Staff Assignment's access is revoked mid-session without requiring a
page reload or logout.

## Tenant Isolation

`tenantRoles` and `userOverrides` are both keyed by `(tenantId, userId)`
(overrides) or `(tenantId)` (role grants), never globally. Switching the
active tenant re-derives the effective permission set from that tenant's
own role/override entries — a permission granted under Tenant A's role
grants has no effect while Tenant B is active. Ownership/Staff resolution
independently re-checks tenant eligibility on every call, so cross-tenant
bleed cannot occur through either path.

On logout, all four Zustand-held RBAC fields (`tenantRoles`,
`userOverrides`, `customRoles`, `rbacAuditLog`) are cleared in a single
`_resetStore()` call — not the narrower legacy `clearRoles()` this
replaced, which used to leave `userOverrides` behind after logout
(fixed P10.3 Phase G).

## Permission Overrides

An admin can, per (user, tenant) pair, explicitly `allow` permissions
beyond that user's role grants, or explicitly `deny` permissions their
role would otherwise grant. Only one override record exists per
(user, tenant) pair — setting a new override for the same pair replaces
the previous one rather than merging. Overrides only affect the
Role-Map-derived permission set (sources 1-3); they cannot add to or
subtract from what Ownership/Staff Assignment resolution grants (sources
4-5) — an Owner cannot have their Owner-derived permissions denied via
this mechanism, by design.

**Current limitation:** overrides are set entirely client-side today
(see "Real Backend Migration Requirements") — there is no backend
persistence or validation of an override yet.

## Dashboard Access

`dashboard:access` — "may this identity reach `/console` at all" — is
**not a permission** in the P7 sense. It is never present in
`ROLE_PERMISSION_MAP` for any role, including Owner, and must never be
checked via the general permission-check hook. It has its own dedicated
resolution: `true` if and only if the identity is an eligible Owner of
an eligible active tenant, OR holds at least one currently-effective
Staff Assignment for that tenant. This is deliberately independent of
the general permission engine so that console *reachability* can never
regress silently if `ROLE_PERMISSION_MAP` changes — it is the single
source of truth for every console-gating surface (route guard, sidebar
nav filtering, header nav link, customer-dashboard nav link).

## Security Model

- **The frontend's permission checks are UX affordances, not enforcement.**
  They control what renders, what nav items appear, and what routes
  redirect away — they do not, by themselves, constitute authorization
  enforcement against a real backend. See "Real Backend Migration
  Requirements."
- **Ownership and Staff Assignment eligibility are re-evaluated on every
  resolution**, not cached — this is what makes suspension/expiry take
  effect immediately rather than only after the next login.
- **Two of the five sources — Tenant Role Grants and User Overrides —
  are currently stored client-side** (persisted to `localStorage` under
  the `samoon-rbac` key) with no server round-trip for reads or writes.
  In the current implementation, this makes those two sources
  **client-tamperable**: nothing prevents `localStorage` from being
  edited directly to grant a role that was never actually assigned. Full
  analysis and remediation plan: `docs/P10.5.5_RBAC_REAL_MODE_SECURITY.md`.
- **Ownership and Staff Assignment resolution (sources 4-5) are computed
  from mock data services today**, not from a live backend — in a real
  deployment these would need to be backed by the same trust boundary as
  the rest of the backend's data (i.e. the frontend receives them from
  an authenticated API response, it does not compute them independently
  from data it could itself tamper with).
- **The feature-flag gate is inconsistently applied.** `usePermission()`
  (single-permission check) applies a per-resource feature-flag gate;
  `useAnyPermission()`/`useAllPermissions()` (multi-permission checks) do
  not, despite their JSDoc previously implying they did (corrected in
  P10.5.5 Phase E — see `docs/P10.5.5_PERMISSION_MODEL_FINALIZATION_AUDIT.md`).
  This is a UX-affordance inconsistency, not an authorization-bypass risk
  under the current UX-only trust model, but should be resolved before
  any of these hooks are treated as enforcement-adjacent.
- **Custom Roles do not participate in authorization at all.** A role
  created through the Console's "Create Custom Role" form has zero
  effect on any permission resolution — see "Out of Scope: Custom Roles."

## Out of Scope: Custom Roles

The Console exposes a "Create Custom Role" form that writes a
`CustomRoleTemplate` record to a persisted client store. This record is
never read by any part of the permission resolution flow described
above, and is never displayed by the Console's own role-listing page
(which reads a separate, static, built-in role catalog instead). A
backend engineer implementing this API should **not** assume Custom
Roles need a resolution endpoint yet — they are presently a UI-only,
disconnected feature. If/when Custom Roles are wired into authorization,
that will require: (a) extending the closed `Role` union (or introducing
a parallel tenant-defined-role concept), (b) deciding how a custom role's
permission list interacts with `ROLE_PERMISSION_MAP`, and (c) an explicit
migration phase — none of which exists yet.

## Real Backend Migration Requirements

For a backend engineer implementing the API this frontend expects,
without reading frontend source:

1. **Login/session endpoint must return the caller's tenant-scoped role
   grants** (equivalent to source 1: `Role[]` per tenant) as part of the
   authentication response. The frontend currently only receives this in
   its mock-mode login path; the real-mode login response type does not
   yet include it — this is a known gap the backend response contract
   must close (see `docs/P10.5.5_RBAC_REAL_MODE_SECURITY.md` §4).
2. **A permission-override read/write endpoint is required** — source 2
   has no backend counterpart today. Writes must be authorized
   server-side (an admin should not be able to grant themselves
   permissions by calling this endpoint directly) and should return the
   authoritative post-write override state for the frontend to display.
3. **Ownership and Staff Assignment data (sources 4-5) must be served
   from authenticated, tamper-proof endpoints** — an Owner record, a
   tenant's `ownerId`, and Staff Assignment rows must all come from the
   backend's own data, never be derivable or settable by the client.
4. **Every mutating and sensitive-read endpoint must independently
   authorize the request server-side**, re-deriving the caller's
   effective permissions from steps 1-4 above using its own trusted data
   — never trusting a client-supplied permission list or role claim.
   The frontend's permission checks exist to shape the UI, not to gate
   the API.
5. **The Role → Permission Map (source 3) should be treated as shared,
   versioned contract** between frontend and backend — both sides must
   agree on which permissions each role grants; a drift here (e.g.
   backend grants `orders.manage` to `waiter` but the frontend's map
   doesn't) would produce a UI/API mismatch (buttons hidden that the API
   would actually allow, or vice versa).
6. **`dashboard:access` has no backend equivalent required** — it is a
   frontend-only "should the console shell render" computation derived
   entirely from Ownership + Staff Assignment data the backend already
   serves for sources 4-5. No separate endpoint is needed for it
   specifically.
7. **Custom Roles need no backend support yet** — see "Out of Scope:
   Custom Roles" above; do not build an endpoint for a feature the
   frontend doesn't consume.
