# P9.5.5.1 — Localization Runtime Recovery

Bug-fix phase. No new features, no redesign — this restores a broken
production boot sequence introduced as a side effect of P9.5.4/P9.5.5 while
preserving the existing P9.0 configuration architecture exactly as designed.

## Reported crash

```
ConfigurationService unknown field: languages.supported
PlatformConfigurationRegistry register("countries") called after registry was sealed.
```

## Root cause

`PlatformConfigurationRegistry` (`src/config/registry.ts`) seals itself the
first time *anything* reads from it — every getter (`getField`,
`getModule`, `getModules`, `getAllFields`, `getDefaults`, `getDependents`,
`getFieldsByLifecycle`) calls `this.seal()` before returning. This is
intentional P9.0 design: once something has read the registry, no module
may register into it later, because a consumer may already have resolved
against an incomplete config. `register()` throws once sealed.

The only file that actually populates the registry is the barrel,
`src/config/index.ts`, whose body is a fixed sequence of
`import './modules/countries'`, `import './modules/languages'`, … side
effects. Reading the registry through the barrel (`import {
platformConfigurationRegistry } from '@/config'`) is therefore always
safe — the read can't happen before the barrel's imports finish, because
ES module imports execute synchronously, top-to-bottom, before any of the
importing file's own code runs.

Two files bypassed the barrel and imported straight from the
registry/service submodules instead:

- **`src/i18n/runtime.ts`** — `import { configurationService } from
  '@/config/service'`. This is the real trigger: `runtime.ts` is reached
  from `src/app/layout.tsx` (`getDirection`), the root layout every single
  route renders. Whichever route happened to render first in a given
  server process would call `configurationService.resolveField
  ('languages.supported')` → `platformConfigurationRegistry.getField()` →
  seals the registry — without `@/config`'s `import
  './modules/languages'` ever having run, since nothing had imported the
  barrel yet. Hence **"unknown field: languages.supported."**
- **`src/platform-admin/register-module.ts`** — `import {
  platformConfigurationRegistry } from '@/config/registry'`. Every
  Platform Administration module (`src/platform-admin/modules/*.ts`) calls
  `registerAdminModule()`, which calls `.register()` on this same
  singleton. If the registry was already sealed by the `runtime.ts` path
  above (or any other early read) before a route rendering
  `/platform-admin` got to import `'@/config'` and register `countries`
  (first module in the barrel's list), that `register("countries")` call
  would throw **"called after the registry was sealed."** — and because a
  thrown import halts the rest of the importing module's statements,
  every subsequent `import './modules/<name>'` in the barrel (languages,
  authentication, …) would also never run in that same crash, which is
  why both log lines were always reported together: one root cause, one
  shared singleton, two submodule bypasses.
- **`src/platform-admin/widgets.ts`** — same shape of bypass
  (`configurationService` from `@/config/service`), for the P9.5.5
  language-coverage dashboard widgets. Its `compute()` calls are lazy
  (only invoked when a widget renders), so it wasn't itself capable of
  seizing the registry too early — but it was the same latent hazard and
  is fixed for consistency/defense-in-depth.

None of this is a schema regression: `languages.supported`,
`languages.default`, and `languages.rtl_locales` are all still defined,
unchanged, in `src/config/modules/languages.ts`. The "unknown field"
symptom is a registration-race artifact, not a missing field.

## Fix

Route every config-touching import in the three offending files through
the `'@/config'` barrel instead of a submodule path, so importing any of
them forces the barrel's full module registration to complete first,
deterministically, regardless of which route or file happens to load
first in a given process:

- `src/i18n/runtime.ts` — `configurationService` now imported from
  `'@/config'`.
- `src/platform-admin/register-module.ts` — `platformConfigurationRegistry`
  now imported from `'@/config'`.
- `src/platform-admin/widgets.ts` — `configurationService` now imported
  from `'@/config'`.
- `src/platform-admin/index.ts` — `import '@/config'` added as the first
  statement, purely to make the dependency order visible at the one file
  every route imports to trigger Platform Administration registration.
  This doesn't change behavior (`register-module.ts` already forces the
  same ordering transitively) — it's belt-and-suspenders documentation in
  code form.

No business logic, UI, or registry semantics changed. `seal()`/`_sealed`
in `src/config/registry.ts` is untouched — the fix is entirely about
which import path each consumer uses to reach the same singleton.

## Dependency graph — startup → register → seal → runtime

```
process start
  │
  ├─ any file does `import '@/config'` (directly, or transitively via
  │  '@/i18n/runtime', '@/platform-admin/register-module',
  │  '@/platform-admin/widgets', or '@/platform-admin' itself)
  │
  ▼
src/config/index.ts (the barrel) runs its fixed import sequence:
  import './modules/countries'        ─┐
  import './modules/languages'         │  each one calls
  import './modules/typography'        │  platformConfigurationRegistry
  import './modules/themes'            │  .register(module) — registry
  import './modules/authentication'    │  is NOT sealed yet, so every
  import './modules/feature-flags'     │  one of these succeeds
  import './modules/subscriptions'     │
  import './modules/payments'          │
  import './modules/storage'           │
  import './modules/monitoring'        │
  import './modules/notifications'     │
  import './modules/website-builder'   │
  import './modules/rbac'              │
  import './modules/system'            │
  import './modules/api'              ─┘
  │
  ▼
barrel finishes evaluating → re-exports platformConfigurationRegistry,
configurationService, etc.
  │
  ▼
(only now) importing file's own top-level code runs, e.g.
  src/platform-admin/index.ts: import './modules' → each Platform
  Administration module calls registerAdminModule() →
  platformConfigurationRegistry.register(...) — still not sealed,
  still succeeds, because register-module.ts's own import of the
  registry is routed through '@/config' too (same guarantee, one level
  up the tree)
  │
  ▼
first runtime request: a getter is called (getField, resolveField, …)
  │
  ▼
registry.seal() — every core + platform-admin module is already present,
so every read succeeds; no further register() calls are attempted after
this point in normal operation
```

The key invariant this fix restores: **no code path can reach a registry
getter without first having executed the barrel's full registration
sequence**, because every consumer's import graph now bottoms out at
`'@/config'`, never at `'@/config/registry'` or `'@/config/service'`
directly.

## Verification

- `npx tsc --noEmit` — clean.
- `next lint` — no new warnings/errors (pre-existing unrelated warnings
  only).
- `npx vitest run` — 93 test files / 5656 tests passing, including a new
  regression suite, `src/test/p9-5-5-1-runtime-recovery.test.ts`, that
  uses `vi.resetModules()` to force the worst-case ordering — resolving a
  `languages.*` field via `i18n/runtime.ts` before anything has imported
  `'@/config'`, and importing `'@/platform-admin'` before anything has
  imported `'@/config/registry'` — and asserts neither throws and every
  core/platform-admin module resolves correctly afterward.
- `npm run build` — production build succeeds, including `/platform-admin`
  and `/platform-admin/[moduleId]` routes.
