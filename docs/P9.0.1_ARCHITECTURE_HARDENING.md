# P9.0.1 — Architecture Hardening (Phases C–H)

> Design and documentation for six architecture extensions on top of the P9.0
> Platform Configuration Foundation. P9.0 itself is not redesigned or
> replaced — see `docs/PLATFORM_ARCHITECTURE_PRINCIPLES.md` §1 for what was
> actually touched in code (small, additive, test-covered) versus what is
> design-only in this document.

> Last updated: 2026-07-04

## Phase C — Secret Management Architecture

**Rule: Platform Configuration must never store secrets.** This is a
separate rule from Rule 1 ("everything is configuration") — a secret is
configuration in the sense that it varies per tenant and must be
administrable, but its *value* must never live in the same store as a theme
color or a trial-day count.

### The model

```
Configuration                  (ConfigFieldDefinition, type: 'secret')
     ↓  resolves to
Secret Reference                (SecretReference — src/config/types.ts)
     ↓  resolved at runtime by
Secret Provider                 (vault / AWS Secrets Manager / env — not yet implemented)
     ↓
Runtime Resolver                (a backend-only concern — never the frontend)
     ↓
Plaintext value                 (exists only in backend process memory, at point of use)
```

A field like `payments.stripe_secret_key` (type `'secret'`) is registered in
`PlatformConfigurationRegistry` exactly like any other field — schema,
validation, permissions, audit. What differs is what its *resolved value*
means in production: not the plaintext, but a `SecretReference`:

```ts
export interface SecretReference {
  ref: string           // opaque id the Secret Provider resolves at runtime
  provider: string       // 'vault' | 'aws-secrets-manager' | 'env' | ...
  rotatedAt?: string     // ISO timestamp, for rotation-policy reporting
}
```

`ConfigurationService.resolveField()` for a `'secret'`-typed field returns
this reference to any frontend caller. The actual plaintext is fetched
**only** by the backend, at the point of use (e.g. the payment-processing
service resolving `payments.stripe_secret_key` right before calling Stripe),
and is never transmitted to, cached by, or logged by the frontend. This is
why `ConfigurationCache` and `ConfigurationAudit` already redact
`audit.sensitive` fields (§7 of the Principles doc) — that redaction remains
necessary even after a real Secret Provider exists, as defense in depth.

### Rotation

- Rotation is a Secret Provider concern, not a Configuration concern. The
  Configuration layer only stores *which* reference points at *which*
  secret slot, plus `rotatedAt` for display ("last rotated 40 days ago").
- Rotating a secret does not require a `ConfigurationService.updateField()`
  call unless the reference itself changes (e.g. switching which vault path
  a tenant's Stripe key lives at). Provider-side rotation (the provider
  swaps the plaintext behind an unchanged `ref`) is invisible to this layer
  by design — that's the point of indirection.

### Permissions

Secret-typed fields use the same `permissions.view`/`permissions.edit` model
as any field, but `visibility` should default to `'admin_only'` (never
`'public'`) and `audit.sensitive` must be `true`. No new permission strings
are introduced for secrets specifically — reuse the module's existing
`settings.manage`-class permission.

### Audit

Every write to a secret-typed field is audited like any other field
(§7 of the Principles doc) — actor, timestamp, reason — but `previousValue`/
`newValue` are redacted to `••••••`. The audit trail proves *that* a secret
was rotated and *who* did it, never *what* it was.

### Environment separation

Secret references must be environment-scoped by the Secret Provider, not by
Platform Configuration — i.e. `payments.stripe_secret_key` resolves to a
different `SecretReference.ref` in staging vs. production, but the
*field definition* (schema, validation, permissions) is identical in both.
This mirrors Vercel's environment-scoped env vars (see the P9.0 audit's
benchmark table) — the config schema doesn't change per environment, only
which secret slot a reference points to.

### Future vault providers

The `SecretReference.provider` string is intentionally open (not a closed
union) so a new provider (e.g. HashiCorp Vault, Google Secret Manager,
1Password Connect) can be adopted without a schema migration — only the
backend's Secret Provider implementation changes, never
`ConfigFieldDefinition` or `ConfigurationService`.

**Not implemented in P9.0.1** (by design — this phase is architecture only):
any actual Secret Provider, any runtime resolution, any vault SDK
integration. `SecretReference` exists purely as the contract a future
implementation targets.

## Phase D — Configuration Lifecycle

Added to the type system in P9.0.1 (see `src/config/types.ts`,
`src/config/field.ts`, `src/config/registry.ts`):

```ts
export type ConfigLifecycleState = 'draft' | 'testing' | 'published' | 'deprecated' | 'archived'
```

Every `ConfigFieldDefinition.lifecycle` defaults to `'published'` via
`defineField()` — no existing module file needed to change.
`ConfigModuleDefinition.lifecycle` is optional; `registry.getModuleLifecycle(id)`
is the only sanctioned way to read it (defaults to `'published'` when
omitted), so no caller re-implements the default-fallback.

### State meanings

| State | Resolves for real tenants? | Where it shows up |
|---|---|---|
| `draft` | No | Only visible to the authoring team, in an internal/staging registry view. Never resolved by `ConfigurationService.resolveField()` for a real `tenantId` — a future guard should short-circuit to the field's `default` (or refuse) outside internal tooling. |
| `testing` | Behind a feature flag or for explicitly-allowlisted internal tenants only | A "Beta" badge in a future Console; excluded from the default module list shown to a Platform Administrator unless they opt into "show testing fields." |
| `published` | Yes, always | The default and overwhelming majority case — everything shipped in P9.0's 14 modules is `published`. |
| `deprecated` | Yes — existing overrides keep resolving | Hidden from "add a new override" UI; shown with a deprecation notice to anyone who already has a non-default value set; a future lint could warn on new code paths reading a deprecated field. |
| `archived` | No — resolution falls back to `default` only, ignoring any stored override | Effectively retired; kept in the registry (never delete a field id — Rule 3 — since overrides may still reference it in historical audit entries) but functionally inert. |

### How future Console pages use this

- The module list (§H manifest) filters out `draft` modules for anyone
  without an internal/engineering role.
- A field-level settings form renders a "Beta" chip for `testing`, a
  "Deprecated — will be removed" banner for `deprecated`, and refuses to
  render an editable control at all for `archived` (read-only, showing only
  the frozen default).
- `registry.getFieldsByLifecycle('deprecated')` powers a "cleanup backlog"
  report so deprecated fields don't linger silently for years.

No UI is built in P9.0.1 — this section describes the contract a future
Console implementation must honor.

## Phase E — Version Snapshots

`ConfigurationVersionManager` (existing, P9.0) already tracks a module's
`version` string plus a change-note history. This phase documents how that
grows into full snapshot/rollback/comparison support — **design only, no
code added in P9.0.1.**

### Snapshots

A snapshot is an immutable capture of every field's *resolved value* for a
given scope at a point in time — not the schema (that's what `version`
tracks), the *data*. Conceptually:

```ts
interface ConfigSnapshot {
  id: string
  scope: ConfigResolutionScope
  takenAt: string
  takenBy: { id: string; name: string }
  label?: string                    // e.g. "pre-Black-Friday-2026"
  values: Record<string, unknown>   // fieldId -> resolved value at takenAt
}
```

### Named releases

A named release is a snapshot promoted to a first-class, referenceable
artifact — "Q3 2026 Platform Release" — that a Platform Administrator can
tag, diff against, and roll every tenant back to. This is the SaaS-platform
equivalent of a git tag: an immutable pointer at a specific set of resolved
values, not a branch.

### Rollback / restore

Rollback replays a snapshot's `values` back through
`ConfigurationService.updateField()` **one field at a time**, each write
going through the normal validation/permission/audit path — a rollback is
itself an audited change, never a raw data restore that bypasses the write
path (this mirrors §36.5 of the Backend API Contract, already written in
P9.0). `ConfigurationAudit.getRollbackValue(auditEntryId)` already provides
the single-entry building block; snapshot-level rollback is the same
mechanism applied in bulk.

### Comparison

Comparing two snapshots is a diff over their `values` maps — this composes
directly with `ConfigurationDiff` (Phase F, added in P9.0.1): instead of
comparing live resolved values across inheritance levels, compare two
frozen `values` maps field-by-field using the same identical/non-identical
model.

### History / future Git-style timeline

The long-term shape is a timeline per scope: snapshots as commits, named
releases as tags, `ConfigurationAudit` entries as the fine-grained diff
between adjacent commits. None of this requires a new storage model beyond
what `ConfigurationAudit` and a future `ConfigSnapshot` table already
imply — no event-sourcing rearchitecture needed, because every write
already goes through one auditable function.

**Not implemented in P9.0.1:** snapshot creation, storage, or rollback
execution. This section is the design future work targets.

## Phase F — Configuration Diff Engine

**Implemented in P9.0.1** as `src/config/diff.ts` (`configurationDiff`) —
pure functions, no I/O, no UI:

- `diffField(fieldId, scope)` — resolves a field at `platform` plus every
  level present in `scope` (tenant/branch/user), and reports which levels
  agree (`identical`) and which level(s) hold an explicit override
  (`hasOwnValue`).
- `diffModule(moduleId, scope)` — the same, for every field in a module —
  "show me everything this tenant has customized."
- `diffFieldAcrossScopes(fieldId, scopeA, scopeB)` — compares the same field
  between two independent scopes (e.g. Tenant A vs. Tenant B), distinct from
  comparing up the inheritance chain.

### Inheritance visualization

A future Console reads `diffModule()`'s output to render exactly the
Platform → Tenant → Branch → User chain visually — e.g. for Themes:

```
Authentication     [platform: locked]
Country            platform ── tenant (override: "US")
Typography         platform ── tenant (override: "Poppins") ── branch (inherits tenant)
Theme              platform ── tenant (override: "#0ea5e9") ── branch (override: "#111111")
Website Builder     platform [feature-flagged off for this tenant]
Feature Flags      platform ── tenant (3 overrides)
```

Each row is one `ConfigFieldDiff.levels` array rendered as a horizontal
chain, with `hasOwnValue: true` levels highlighted as the point where an
override was actually set (versus levels merely inheriting).

### Composition with snapshots (Phase E)

The same `ConfigFieldDiff` shape is reused to compare two snapshots instead
of two live scopes — the engine doesn't need to know whether its inputs came
from `ConfigurationService.resolveField()` live or from a frozen
`ConfigSnapshot.values` map; both are just `{ fieldId, value }` pairs.

**No UI built** — `src/config/diff.ts` is covered by unit tests only
(`src/test/p9-platform-configuration.test.ts`).

## Phase G — Dependency Graph

**Implemented in P9.0.1:**

- `ConfigModuleDependency.type?: 'hard' | 'soft'` (`src/config/types.ts`) —
  `'hard'` (default) means the registry refuses registration before the
  dependency exists (already enforced by `registry.register()` since P9.0);
  `'soft'` is descriptive only — the dependent reads the dependency's
  values opportunistically but functions without it.
- `registry.getDependents(moduleId)` (`src/config/registry.ts`) — the
  inverse query: "what currently declares a dependency on this module?"

### Example dependency chain (illustrative — not all of this exists yet)

```
Reservations
     ↓
Reservation Widget          (soft — reads Reservations' config for display defaults)
     ↓
Reservation API              (hard — cannot function without Reservations registered)
     ↓
Reservation Notifications    (hard — needs Reservations' notification-channel fields)
     ↓
Reservation Analytics        (soft — richer if Reservations is configured, not required)
     ↓
Reservation Dashboard        (soft — a Console page, degrades gracefully if absent)
```

Today's registered modules only have two real dependency edges
(`themes` → `website_builder` needs `typography`; `website_builder` needs
`themes`) — both already declared and registered in the correct order in
`src/config/index.ts`. The chain above illustrates how a *feature* module
(as opposed to a *platform infrastructure* module like Themes) is expected
to declare its own internal dependency layers once P9.1+ builds it, using
the same `dependencies` array — no new mechanism required.

### What "the registry should eventually know what depends on what" means concretely

`getDependents()` already answers this today for the modules P9.0 shipped.
No runtime graph-traversal utility (topological sort, cycle detection beyond
the register-time existence check, impact-radius calculation) is built in
P9.0.1 — the brief for this phase is explicit that no runtime
implementation is required. A future phase can add a `getDependencyChain(moduleId)`
that walks `getDependents()` transitively if/when a Console "impact preview"
feature needs it; the data (`dependencies` arrays) already supports that
without a schema change.

## Phase H — Module Manifest

**Design-only — no new type introduced.** `ConfigModuleDefinition`
(`src/config/types.ts`, registered via `platformConfigurationRegistry.register()`)
**already is** the module manifest — introducing a second, parallel
"manifest" type would violate Rule 3 (Single Source of Truth) by describing
the same module twice. Instead, this section documents which fields the
manifest already has and which it is expected to grow, additively, as real
needs arrive:

| Manifest field | Status | Notes |
|---|---|---|
| `id`, `name`, `description` | ✅ Have it | |
| `permissions` | ✅ Have it | `{ view, edit }` |
| `dependencies` | ✅ Have it | P9.0.1 added `type: 'hard' \| 'soft'` |
| `configuration schema` | ✅ Have it | `sections` → `fields`, the bulk of the type |
| `feature flags` | ✅ Have it | `featureFlag?: string` gates the whole module |
| `version` | ✅ Have it | Module-level schema version |
| `lifecycle` | ✅ Added in P9.0.1 | Defaults to `'published'` |
| `health checks` | ❌ Not yet | Future: `healthCheck?: { endpoint: string; intervalSeconds: number }` or a pure function reference — add only when a real module needs runtime health reporting (e.g. Payments checking Stripe connectivity). Do not add speculatively. |
| `navigation` | ❌ Not yet | Future: `navigation?: { consoleRoute: string; icon: string; group: string }` — mirrors the existing `NavItem` shape already used by `src/modules/registry.ts`'s business-type modules; reuse that shape rather than inventing a new one when this is built. |
| `documentation` | ❌ Not yet | Future: `docsUrl?: string` pointing at a per-module doc page, once P9.1+ modules have enough of their own documentation to need a dedicated link (today, `docs/P9.0_CONFIGURATION_ARCHITECTURE.md` covers everything). |
| `future migrations` | ❌ Not yet | Future: `migrations?: Array<{ fromVersion: string; toVersion: string; note: string }>`, populated alongside `ConfigurationVersionManager.recordVersion()` calls (Phase E) when a schema change requires a data transformation, not just a version bump. |

Each `❌` row is deliberately **not** added speculatively — Rule 10
("Future-Proof… avoid one-off solutions") cuts both ways: it means designing
for growth, and it means not adding fields nothing reads yet. When a real
module needs one of these, add it to `ConfigModuleDefinition` (a single,
additive, optional field) rather than creating a second manifest type.

### Example manifests (illustrative shape, using fields that already exist today)

```ts
// Authentication — already registered, P9.0
{
  id: 'authentication', name: 'Authentication', category: 'security', version: '1.0.0',
  permissions: { view: 'settings.view', edit: 'settings.manage' },
  sections: [ /* OTP, Login Attempts & Lockout */ ],
}

// AI — future P9.1+ module, hypothetical
{
  id: 'ai', name: 'AI Assistant', category: 'platform', version: '0.1.0',
  lifecycle: 'draft',
  featureFlag: 'feature_flags.ai_assistant',
  permissions: { view: 'settings.view', edit: 'settings.manage' },
  dependencies: [{ moduleId: 'feature_flags', type: 'hard' }],
  sections: [ /* provider selection, prompt limits, model defaults */ ],
}
```
