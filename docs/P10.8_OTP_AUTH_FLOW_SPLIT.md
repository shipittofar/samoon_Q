# P10.8 — OTP Authentication Flow Split

Fixes a real bug: `authService.verifyOTP()` and `useVerifyOTP()` treated
`is_new_user: true` and `is_new_user: false` almost identically —
tokens were minted and persisted, and (at the hook layer) `setUser()`/
RBAC hydration ran, regardless of whether the backend actually
considered the phone number a registered, logged-in user. Per the
backend contract, `is_new_user: true` means registration is **not**
complete — there is no session to initialize yet.

## Root Cause

Traced the full flow: `PhoneInput` (login page) → `useSendOTP()` →
`/verify` (`VerifyPageInner`) → `useVerifyOTP()` → `authService.verifyOTP()`.

Two independent bugs existed:

1. **`authService.verifyOTP()` unconditionally persisted tokens.** Both
   branches — mock mode's "unknown phone → new user" path
   (`src/services/auth.service.ts`, previously line 275) and the
   real-mode branch (previously line 287) — called
   `setTokens(tokens.access, tokens.refresh)` regardless of
   `is_new_user`. This wrote real access/refresh tokens into
   `localStorage` and the auth cookie for a phone number the backend
   had not actually authenticated.
2. **`useVerifyOTP()` unconditionally initialized the session.**
   `onSuccess: ({ user, p7Roles }) => { setUser(user); ... }`
   (`src/hooks/index.ts`) ran for every successful mutation, calling
   `setUser()` and hydrating `tenantRoles` even when `is_new_user` was
   `true`.

A third, standalone file — `src/app/verify-otp/page.tsx` — had the
identical bug in its own hand-rolled `handleVerify()`, which called
`authService.verifyOTP()` directly, always did `setUser(user)`, and
**never checked `is_new_user` at all**, redirecting to `/` unconditionally.
This route has zero incoming links anywhere in the app (confirmed via
repo-wide grep — only `src/app/login/LoginClientPage.tsx` links to
`/verify`, never `/verify-otp`) but was fixed for correctness rather
than left as a broken, buildable duplicate of the real flow.

`country_code`/`dialCode` was audited across the whole flow
(`PhoneInput` → `LoginClientPage` → `useSendOTP()`/`useVerifyOTP()` →
`authService.sendOTP()`/`verifyOTP()`) and found to already correctly
use the user's selected `dialCode` at every call site — no hardcoded
value was found. One real gap was found and fixed: the redirect from
`/verify` to `/complete-profile` for a new user never forwarded
`dialCode` in the query string, even though `/complete-profile` already
reads it (previously silently unused there).

## Expected Flow (Implemented)

### Case 1 — `is_new_user: true`

```
authService.verifyOTP() → { is_new_user: true }   (no user, no tokens)
  → useVerifyOTP()'s onSuccess: returns immediately, does nothing
  → VerifyPage: router.push('/complete-profile?phone=...&dialCode=...')
```

No token is stored, no user is stored, no RBAC state is touched, no
"login bootstrap" logic runs. `/complete-profile` (via `useRegister()`)
is solely responsible for collecting the remaining profile info,
completing registration, receiving tokens/user, and initializing the
session — which it already did correctly before this phase (see
"What Was Already Correct" below).

### Case 2 — `is_new_user: false`

```
authService.verifyOTP() → { is_new_user: false, user, tokens, p7Roles? }
  → setTokens() (inside the service, unchanged)
  → useVerifyOTP()'s onSuccess: setUser(user); hydrate tenantRoles if present
  → VerifyPage: role-aware redirect (Console / Dashboard / Customer area)
```

Behaves exactly like `useLogin()` always has — this path was already
correct and is unchanged in substance, only now correctly isolated from
Case 1.

## Files Changed

### `src/services/auth.service.ts`

- Added `VerifyOTPResult`, a discriminated union:
  ```ts
  export type VerifyOTPResult =
    | { is_new_user: true }
    | ({ is_new_user: false; user: User; tokens: AuthTokens; p7Roles?: Role[] } & AuthSessionRbacPayload)
  ```
  This gives every consumer compile-time safety — `result.user`/
  `result.tokens` are only accessible after narrowing on
  `result.is_new_user`, so a future regression that reads `.user` off
  the new-user branch would fail to type-check rather than crash at
  runtime.
- `verifyOTP()`'s mock branch: the "unknown phone" path now returns
  `{ is_new_user: true }` with no `tokens`/`user` fields, and no longer
  calls `setTokens()`. The known-account path is unchanged in substance
  (still mints tokens, sets `MOCK_SESSION_KEY`) but now explicitly
  documented as the only branch allowed to do so.
- `verifyOTP()`'s real-mode branch: `setTokens()` is now called only
  `if (!data.is_new_user)`.
- `country_code: payload.dialCode` was already correct in the real-mode
  request body — confirmed unchanged, documented with an explicit
  comment stating it must never be hardcoded.

### `src/hooks/index.ts`

- `useVerifyOTP()`'s `onSuccess` now narrows on `result.is_new_user`
  first and returns immediately for a new user, before touching
  `setUser()` or `useRbacStore`. The existing-user path is byte-for-byte
  the same logic as before (`setUser(result.user)`, then
  `setTenantRoles()` if `p7Roles` is present and non-empty).

### `src/app/verify/page.tsx`

- No branching logic changed (`result.is_new_user ? '/complete-profile...' : ...`
  already existed and was already correct) — the redirect URL was fixed
  to include `&dialCode=${encodeURIComponent(dialCode)}`, closing the
  one real "dial code not threaded through" gap found.

### `src/app/verify-otp/page.tsx`

- `handleVerify()` rewritten to check `result.is_new_user` before doing
  anything else: if new, redirect to `/complete-profile` (with `phone`
  and `dialCode`) and return immediately, never calling `setUser()`. If
  existing, behavior is unchanged (`setUser(result.user)`, toast,
  redirect to `/`).

### Not changed — already correct

- **`src/app/complete-profile/page.tsx`** — already calls `useRegister()`,
  which (via `authService.register()`) mints and persists real tokens,
  and (via `useRegister()`'s `onSuccess`) calls `setUser()`. Already
  redirects to `/dashboard` on success. This page already fulfills every
  responsibility the task assigns to it; nothing needed to change.
- **`ROLE_PERMISSION_MAP`, `usePermissions()`, `useHasDashboardAccess()`,
  `AuthGuard`, `PermissionGuard`, Ownership Resolution, `StaffAssignment`**
  — none of these are part of the OTP flow and none were touched.

## Before / After

```
BEFORE:
  unknown phone → verifyOTP() → tokens minted + persisted (WRONG)
                              → setUser(MOCK_USER) called (WRONG, hook layer)
                              → treated as if logged in

AFTER:
  unknown phone → verifyOTP() → { is_new_user: true }, no tokens, no user
                              → useVerifyOTP() onSuccess returns immediately
                              → VerifyPage redirects to /complete-profile
                              → NOT logged in until registration completes
```

```
BEFORE / AFTER (unchanged):
  known phone → verifyOTP() → { is_new_user: false, user, tokens, p7Roles }
                            → tokens persisted, setUser() called, tenantRoles hydrated
                            → role-aware redirect (Console/Dashboard/Customer)
```

## Tests

`src/test/p10.8-otp-auth-flow-split.test.tsx` — 10 new tests:

1. **`authService.verifyOTP()`, `is_new_user: true`**: result has no
   `user`/`tokens` fields; no access token is persisted; `MOCK_SESSION_KEY`
   is never written.
2. **`authService.verifyOTP()`, `is_new_user: false`**: result carries
   `user`/`tokens`/`p7Roles`; access token is persisted;
   `MOCK_SESSION_KEY` is written.
3. **`useVerifyOTP()`**: a new-user result does not call `setUser()` and
   leaves `tenantRoles` empty; an existing-user result (`owner@samoon.com`)
   calls `setUser()` and hydrates `tenantRoles` exactly like a login.
4. **`country_code`**: proves `dialCode` is accepted and passed through
   for arbitrary values (not substituted with a fixed one), and that two
   concurrent calls with different dial codes don't collide.

## Security Note

This closes a real, exploitable-in-spirit gap: before this phase, simply
requesting an OTP for *any* unregistered phone number and entering any
non-`000000` 6-digit code would silently mint and persist a valid mock
access/refresh token pair and set `useAuthStore.user` to a customer
account — an unauthenticated action producing authenticated-looking
client state. In mock mode this was harmless (no real backend to talk
to), but the pattern would have carried the same bug into a real backend
integration once `NEXT_PUBLIC_USE_MOCK=false` is used, since the service
layer's `setTokens()` call was unconditional in both branches. Fixed at
the source (`authService.verifyOTP()`) rather than only at the UI layer,
so no other current or future caller can reintroduce the bug by skipping
a check the hook happened to add.
