# P9.5.5 Phase A — Language Management Center: Audit

## Purpose

Before building the Language Management Center, this audit inventories
the current state of localization data/metadata across the codebase, so
the new Collection module (Phase B) fills real, verified gaps rather than
guessed ones.

## Findings

### 1. Dead, duplicate, incomplete hardcoded locale constants (`src/constants/index.ts`)

```ts
export const DEFAULT_LOCALE = 'en'
export const SUPPORTED_LOCALES = ['en', 'fa', 'ar'] as const
export const RTL_LOCALES = ['fa', 'ar'] as const
```

- **Dead**: `grep` confirms zero real import sites — the only remaining
  reference is a comment in `src/config/modules/languages.ts` documenting
  that P9.5.1A already replaced their *usage* with the config-driven
  `languages.supported`/`languages.default`/`languages.rtl_locales`
  fields (backed by `src/i18n/language-registry.ts`, P9.5.1A).
- **Incomplete/stale even as documentation**: they list only 3 of the 6
  operational languages (missing `zh`/`it`/`tr`, added later in
  P9.5.1A) — if anyone did import them today, they'd silently miss half
  the operational language roster.
- **Fix applied this phase**: removed (see
  `docs/P9.5.5_LANGUAGE_MANAGEMENT.md` §"Bugs discovered and fixed").

### 2. `LANGUAGE_REGISTRY` only contains the 6 operational languages — no disabled roster

`src/i18n/language-registry.ts` (P9.5.1A) defines exactly 6 entries (en,
fa, ar, zh, it, tr), all either operational or on a path to becoming
operational (`hasMessages: false` for zh/it/tr, meaning no translated
message file exists yet, not "disabled by policy"). There is **no
representation at all** of "a language exists in the roster, admin-
disableable, with no messages and no near-term intent to ship it" — the
exact "150+ languages, most disabled" model
`docs/P9.5.0_LOCALIZATION_ARCHITECTURE.md` designed for the eventual
`localization.languages` collection. This is the single largest gap this
phase's Phase B/L closes: a real Collection Framework module with a
fixed `entityIds` roster larger than 6, most entities `enabled: false`.

### 3. Missing metadata entirely absent from `LanguageMetadata`

None of the following exist anywhere in the current codebase for any
language: `visibility` (distinct from `enabled`), `translationCoverage`/
`completionPercent`, `beta`/`experimental`/`machineTranslated`/
`humanReviewed` flags, `region`, `pluralRules` (only `pluralRuleLocale`,
which is the *locale to construct `Intl.PluralRules` with*, not a
category table — correct per P9.5.0 §4's "never hand-roll" principle, but
distinct from what Phase B's schema calls `pluralRules`, which should
mean the same thing, not a duplicate mechanism), `dateFormat`/
`timeFormat`/`numberFormat` (only `defaultTimezone`/`defaultCurrency`
exist — Intl-driven date/time *style* selection is absent), font
metadata of any kind, `searchKeywords`, `lastUpdated`, `translator`,
`notes`, `status` (lifecycle), `default`/`enabled` flags themselves (the
registry has no on/off switch at all — enablement currently lives only
in `languages.supported`, a flat code array, not a per-language record).

### 4. Missing flags

- No per-language `enabled` boolean (existence in `LANGUAGE_REGISTRY` is
  currently conflated with "operational"; there is no way to register a
  language in the registry as disabled).
- No `default` flag on the language record itself — "which language is
  default" lives entirely in `languages.default` (a separate config
  field), not as a property of the language entity. Both are legitimate
  (module-level setting vs. entity-level self-description) but the
  entity-level flag didn't exist before this phase.

### 5. Missing RTL metadata

`direction: 'ltr' | 'rtl'` exists per-language (good — this is exactly
what P9.5.0's audit doc flagged as closing "the 3 hardcoded RTL lists"
gap, and it's true, `direction` is real per-entity data). What's missing
is any *typography* implication of direction (RTL-capable font stacks,
letter-spacing/line-height adjustments RTL scripts often need) — Phase E
of this document's companion implementation doc adds these.

### 6. Missing fallback chains beyond a single hop

`fallbackLocale: LanguageCode | null` is a single pointer (P9.5.0 §3
explicitly designed this as "one-hop fallback pointer; chain resolution
is a pure function over this property" — so multi-hop resolution already
exists as a *computed* traversal, `resolveFallbackChain()` in
`src/i18n/runtime.ts`). What's missing: no validation that following
every language's `fallbackLocale` pointer actually terminates (a cycle
between two disabled languages would silently infinite-loop
`resolveFallbackChain` if ever exercised) — Phase J of the companion doc
adds a cycle-detection validator.

### 7. Missing formatting settings

No per-language `dateFormat`/`timeFormat`/`numberFormat` *style* selector
exists pre-phase (P9.5.0 §4's principle — "every format is delegated to
`Intl.*`, parameterized by stored properties, never a hand-rolled
pattern" — was designed but never implemented as actual fields on
anything). Phase F adds `date_style`/`hour_cycle`/`number_style` fields
using the exact `Intl.DateTimeFormat`/`Intl.NumberFormat` options
vocabulary the design doc specified, continuing to avoid ever storing a
literal format pattern string.

## Summary table

| Gap | Severity | Fixed this phase |
|---|---|---|
| Dead/incomplete hardcoded locale constants | Low (dead code, but misleading) | Yes — removed |
| No disabled-language roster | High (core Phase B/L requirement) | Yes — new collection, 24 additional disabled entries |
| No per-language `enabled`/`default`/`status` flags | High | Yes — new collection schema |
| No coverage/review metadata | High | Yes — new collection schema + dashboard widgets |
| No typography metadata | Medium | Yes — new collection schema (Phase E) |
| No formatting style fields | Medium | Yes — new collection schema (Phase F), Intl-only |
| No fallback-cycle validation | Medium (latent bug risk) | Yes — new `validateLanguageCollection()` |
| Multi-hop fallback resolution | N/A — already correct | No change needed (P9.5.1A already built this correctly) |
