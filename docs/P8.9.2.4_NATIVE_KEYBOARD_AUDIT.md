# P8.9.2.4 — Native Mobile Keyboard Behavior Audit

## Problem (P8.9.2.3 approach)

The previous implementation applied `style={{ bottom: keyboardHeight }}` to the entire Bottom Sheet
container. When the software keyboard opened, the whole sheet translated upward. This caused:

- **Android Chrome / Firefox / Samsung Browser:** Sheet visually bounced up, leaving a gap between
  sheet bottom and the keyboard top, especially on devices with gesture navigation bars.
- **Safari iOS:** Abrupt positional jump during keyboard animation, since `visualViewport` resize
  fires before the keyboard finishes sliding in. Safari also has split-keyboard and floating-keyboard
  modes where the offset is wrong.
- **Chrome iOS (WKWebView):** Same `visualViewport` behavior as Safari; the sheet moved rather than
  the list shrinking.
- **All platforms:** The sheet's spring-animation origin was disrupted mid-flight when `bottom`
  changed — causing a double animation artifact.

## Root Cause

Moving `bottom` moves the entire sheet. That is not how native apps work.

WhatsApp, Telegram, and Stripe all keep the sheet **anchored at the bottom of the screen**. Only the
internal scrollable content region gets shorter when the keyboard appears.

## Correct Architecture

```
Bottom Sheet (fixed; bottom: 0; maxHeight: visualViewport.height × 0.92)
├── Drag handle   (shrink-0 — never scrolls)
├── Header        (shrink-0 — never scrolls)
├── Search input  (shrink-0 — never scrolls; always visible)
└── Country list  (flex-1 overflow-y-auto — absorbs all height changes)
     └── ... rows ...
     └── pb-[safe-area-inset-bottom]
```

When the keyboard opens, `visualViewport.height` shrinks. The sheet's `maxHeight` is capped to
`visualViewport.height × 0.92`. Because the sheet is flex-col and the list is `flex-1`, the list
is the only region that loses height. The sheet bottom stays at 0; only the list scroll area shrinks.

## Platform Behavior After Fix

| Platform | Behavior |
|---|---|
| Android Chrome | Sheet stays at bottom; list scrolls above keyboard; search always visible |
| Android Firefox | Same — VisualViewport API fully supported since Firefox 91 |
| Samsung Browser | Same — VisualViewport API supported since Samsung Browser 14 |
| Safari iOS | Sheet stays at bottom; smooth max-height transition; safe-area-inset-bottom in list padding |
| Chrome iOS (WKWebView) | Same as Safari — shares WebKit VisualViewport implementation |

### Split keyboard (iPad, iOS)
`visualViewport.height` correctly reflects the visible area above a split or floating keyboard.
`sheetMaxHeight` adjusts accordingly; behavior is the same as with a full keyboard.

### Rotation
`visualViewport` emits `resize` on orientation change. The sheet max-height recalculates immediately.
In landscape, available height is smaller; the list gets shorter but remains scrollable.

### Gesture navigation (Android)
Gesture navigation bar height is included in the `window.innerHeight − visualViewport.height`
difference, so `keyboardHeight` naturally incorporates it without special handling.

### 3-button navigation (Android)
The navigation bar is part of the window insets. `visualViewport.height` excludes it on modern
Android. Behavior equivalent to gesture navigation.

### Small-height landscape devices (Android)
In landscape, `viewportHeight × 0.92` may be only ~250px. The list is still scrollable because
`flex-1 overflow-y-auto` still works at any height > 0. The search input stays fixed above the list.

### Dynamic Island (iPhone 14 Pro+)
The safe-area-inset-bottom is independent of Dynamic Island. The list's
`pb-[max(0.75rem,env(safe-area-inset-bottom))]` handles it correctly.

### External keyboard
`visualViewport.height` does not change when an external keyboard is connected (no software keyboard
shown). `keyboardOpen` stays false; sheet uses CSS `max-h-[85dvh]` unchanged.

## Key Implementation Details

- **Threshold:** `keyboardOpen = keyboardHeight > 50` — avoids false triggers from minor viewport
  adjustments (browser chrome show/hide, pull-to-refresh).
- **Ratio:** `viewportHeight × 0.92` — leaves 8% gap showing the page beneath the sheet, matching
  the visual language of WhatsApp/Telegram.
- **Transition:** `transition-[max-height] duration-200 ease-out` — the sheet resize is animated
  smoothly as the keyboard slides in. Disabled when `prefers-reduced-motion` is set.
- **Fallback:** When `window.visualViewport` is unavailable (rare; old WebView), `sheetMaxHeight`
  is `undefined` and the CSS `max-h-[85dvh]` class takes over — safe degradation.
- **Desktop:** `keyboardHeight` stays 0 (desktop keyboards do not resize `visualViewport`), so
  `sheetMaxHeight` is never set and the desktop `md:max-h-[70vh]` class applies unchanged.

## Accessibility

- Focus order is unaffected by keyboard appearance — `useFocusTrap` continues to cycle within the
  sheet; no elements move in or out of the focus ring.
- `aria-activedescendant` is updated on scroll-into-view, which still fires correctly after a
  max-height change because the list DOM is unchanged.
- VoiceOver (iOS): Sheet height change does not cause a focus reset; VoiceOver cursor stays on the
  last focused element.
- TalkBack (Android): Same — no DOM node is unmounted during the resize.
