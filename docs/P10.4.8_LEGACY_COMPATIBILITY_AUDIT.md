# P10.4.8 — Legacy RBAC Compatibility Layer Final Audit

Discovery-only audit. No code, tests, or fixtures were modified in this
phase. Every finding below was verified against the current state of
`claude/v3-p9-platform-config-reo13g` (after P10.4.7).

## Executive summary

Everything named in this phase's "Remaining Legacy Targets" list is
still load-bearing, directly or transitively, except for one dead
branch inside `AuthGuard` that has zero live callers. There is exactly
**one** genuinely live legacy authorization decision left in the whole
system: the `legacyGranted` OR-branch inside `useHasDashboardAccess()`
(`src/hooks/index.ts:355`), which exists solely because two demo
accounts (`staff@samoon.com`, `multirole@samoon.com`) have no matching
`StaffMember` fixture (P10.0 J12/J13 id-space gap). Every other legacy
symbol audited here — `rbacService.hasPermission()`, `ROLE_PERMISSIONS`
and its four sub-tables, `LegacyPermission`, and the `UserRole`-as-
authorization-key usage — exists only to serve that one branch. Nothing
here is Safe To Remove Now; everything is Requires Migration, gated on
closing the id-space gap first.

This audit also surfaced one **unrelated, pre-existing bug**, out of
scope to fix here (Phase G): `Header.tsx` and `app/dashboard/layout.tsx`
compute `canAccessConsole` via `usePermission('dashboard:access')` (the
P7 hook), but `'dashboard:access'` is never granted to any role in
`ROLE_PERMISSION_MAP` — so that computation is structurally always
`false`, and the "Business Console" nav link never renders from either
of those two call sites, regardless of the user's real access (which is
correctly computed by the separate `useHasDashboardAccess()` used by
`AuthGuard`).

## Phase C — `legacyGranted` Analysis

```ts
// src/hooks/index.ts:355
const legacyGranted = rbacService.hasPermission(user?.role ?? null, 'dashboard:access')
```

**Why it exists**: documented in the function's own JSDoc
(`hooks/index.ts:335-351`, written during P10.2.2 and re-verified during
P10.3.1): `useHasDashboardAccess()` is `AuthGuard`'s real `/console` gate.
When the ownership/StaffAssignment-aware branch (Owner-owns-tenant OR
Staff-has-active-assignment) was added in P10.2.2/hardened in P10.3.1, it
could not fully replace the legacy check because two demo accounts have
no backing `StaffMember` record.

**Which users depend on it** (verified this phase, not assumed):
`staff@samoon.com` and `multirole@samoon.com`, per
`src/services/auth.service.ts:74,82`'s `MOCK_CREDENTIALS` table. Both
log in with a `p7Roles` array (`['manager']` and `['cashier','kitchen']`
respectively) but the underlying `User.role` (`UserRole`, legacy) is what
`legacyGranted` actually keys off.

**Which fixtures/accounts require it** — confirmed via direct search:
`grep -n "email:" src/services/staff.service.ts` lists every mock
`StaffMember` (`owner@samoon.com`, `admin@samoon.com`, `manager@samoon.com`,
`cashier@samoon.com`, `waiter@samoon.com`, `kitchen@samoon.com`,
`marketing@samoon.com`, `support@samoon.com`, plus several named individuals
and `new.staff@samoon.com`/`pat.pending@samoon.com`/etc.). **Neither
`staff@samoon.com` nor `multirole@samoon.com` appears in that list.**
`resolveOwnershipIdentity()` (`ownership-resolution.service.ts:112-120`)
calls `staffService.findStaffMemberByEmail(email)` first and returns `{}`
immediately if no match — so for these two accounts,
`identity.owner`/`identity.staffMember` are both `undefined`, and the
ownership/StaffAssignment branch of `useHasDashboardAccess()`
(`hooks/index.ts:366-378`) always evaluates to `false`.

**Whether ownership-resolution fully replaces it**: **No, not for these
two accounts, and not without a data migration.** For every other mock
account (the role-named ones: `manager@samoon.com`, `cashier@samoon.com`,
etc., and `owner@samoon.com`), the ownership/StaffAssignment branch already
grants access independently — `legacyGranted` is redundant for them today
(it was already true before P10.2.2/P10.3.1 added the newer branch, and
remains true now, but isn't the deciding factor). It is the deciding
factor for exactly `staff@samoon.com` and `multirole@samoon.com`.

**What breaks if removed** (without the fixture migration first):
`staff@samoon.com` and `multirole@samoon.com` would fail
`isTenantEligible`/`resolveOwnershipIdentity` checks, `useHasDashboardAccess()`
would return `false` for both, `AuthGuard` on `console/layout.tsx` would
redirect them to `forbiddenPath="/"`, and `useDashboardNav()` would return
an empty nav for them. Both accounts are user-facing demo/login options
(`src/app/login/LoginClientPage.tsx:32,40` lists them with dedicated
icons/colors as selectable demo personas) — this would be an
externally-visible regression of a documented demo flow, not just an
internal test failure.

| `CUSTOMER_PERMISSIONS` | `ROLE_PERMISSIONS.customer`, `STAFF_PERMISSIONS` (spread), `OWNER_PERMISSIONS`/`ADMIN_PERMISSIONS` (transitively via `STAFF_PERMISSIONS`) | Active — module-internal only |

## Phase F — AuthGuard Audit

`src/components/auth/AuthGuard.tsx` (84 lines):

- **`requiredPermission`** (`AuthGuardProps.requiredPermission?: LegacyPermission`): public prop, typed to the full legacy colon-notation union, but in practice only ever passed the literal `'dashboard:access'` by the one real caller (`console/layout.tsx:28`). No other page or test constructs it with a different value.
- **Permission checks**: `isDashboardAccessCheck = requiredPermission === 'dashboard:access'`; if true, uses `useHasDashboardAccess()` (P7/ownership-aware); if false (or no `requiredPermission`), falls through to `rbacService.hasPermission()` (legacy) — the dead branch identified in Phase B.
- **Legacy dependency**: `rbacService` import (line 26), `LegacyPermission` type import (line 28) — both exist solely to type/implement the dead fallback branch, since the one live path (`dashboard:access`) already routes through `useHasDashboardAccess()` and never touches `rbacService` inside `AuthGuard` itself.
- **P7 dependency**: none directly — `AuthGuard` doesn't import `permission.service.ts` or call `usePermission()`/`usePermissions()`. It reaches P7/ownership logic only indirectly, through `useHasDashboardAccess()`.
- **Ownership awareness**: yes, via `useHasDashboardAccess()`, for the one path that's actually used.
- **Migration path**: since the fallback branch has zero live callers, `AuthGuard` could be simplified in a future phase to accept a narrower prop (e.g. a boolean `requireDashboardAccess` instead of a generic `LegacyPermission`), dropping the `rbacService`/`LegacyPermission` imports entirely — with no observed behavior change, since the branch they serve is never exercised today. This is listed under "Requires Migration" (Phase I) rather than "Safe To Remove Now" only because it's a public component API change (`AuthGuardProps`), and this audit's scope forbids modifying `AuthGuard` in this phase regardless of how safe it looks.

## Phase H — Demo Account Dependency

**`staff@samoon.com`** (`auth.service.ts:74`, `p7Roles: ['manager']`) and
**`multirole@samoon.com`** (`auth.service.ts:82`, `p7Roles: ['cashier','kitchen']`):

- **Why they require legacy fallback**: both are valid login credentials
  (`MOCK_CREDENTIALS`) surfaced as demo personas in
  `LoginClientPage.tsx`, but neither has a corresponding entry in
  `MOCK_STAFF_LIST` (`staff.service.ts`). `resolveOwnershipIdentity()`
  looks up `StaffMember` by email and returns `{}` when no match exists,
  so the entire P7/ownership permission-resolution chain
  (`resolveOwnerPermissions`, `resolveStaffAssignmentPermissions`,
  `usePermissions()`) yields nothing for them. `legacyGranted` is the
  only remaining path that grants them `/console` access.
- **Which missing entities cause the dependency**: a `StaffMember` record
  (in `MOCK_STAFF_LIST`) keyed by their email, and at least one active
  `StaffAssignment` (tenant + role + validity window) for that
  `StaffMember` — the same shape every other role-named demo account
  (`manager@samoon.com`, `cashier@samoon.com`, `kitchen@samoon.com`, etc.)
  already has.
- **What data migration is needed to remove the fallback**: add two new
  `MOCK_STAFF_LIST` entries — one for `staff@samoon.com` with a
  `StaffAssignment` matching its `p7Roles: ['manager']`, and one for
  `multirole@samoon.com` with `StaffAssignment`(s) matching
  `p7Roles: ['cashier', 'kitchen']` (a genuine multi-role case, matching
  the account's name/purpose) — pointed at the same tenant(s) the
  existing `manager@samoon.com`/`cashier@samoon.com`/`kitchen@samoon.com`
  fixtures use, so `resolveOwnershipIdentity()` resolves a real
  `StaffMember` and `resolveStaffAssignmentPermissions()` returns a
  non-empty permission set for both. After that, `legacyGranted` can be
  deleted from `useHasDashboardAccess()` with no observed change for
  any account (Phase I, migration task 1-3).

No other `MOCK_CREDENTIALS` entries were found to have this gap — every
other login account's email matches a `MOCK_STAFF_LIST` entry (verified
by cross-referencing `auth.service.ts`'s credential list against the
email list in Phase C).

## Phase I — Final Removal Decision

### Safe To Remove Now

**None.** Every symbol audited (`LegacyPermission`,
`rbacService.hasPermission()`, `legacyGranted`, `UserRole`-as-
authorization-key, `ROLE_PERMISSIONS` and its four sub-tables,
`AuthGuard`'s legacy fallback branch, `dashboard:access`) is either the
one live authorization path (`legacyGranted`) or exists solely to
implement it. This differs from every prior P10.4.x removal (`p7`,
`useHasPermission()`, `getPermissions()`, the duplicate `Role`/`Permission`
types) — those were provably zero-caller. Nothing left is zero-caller;
the caller is just narrowed down to two demo accounts.

### Requires Migration

- **`legacyGranted`** (`hooks/index.ts:355`) — removable only after the
  Phase H fixture migration (add `StaffMember`/`StaffAssignment` records
  for `staff@samoon.com`/`multirole@samoon.com`).
- **`rbacService.hasPermission()`** and its five backing tables
  (`ROLE_PERMISSIONS`, `CUSTOMER_PERMISSIONS`, `STAFF_PERMISSIONS`,
  `OWNER_PERMISSIONS`, `ADMIN_PERMISSIONS`) — removable as one unit,
  immediately after `legacyGranted` is removed (it becomes their last
  caller).
- **`AuthGuard`'s legacy fallback branch** (the `rbacService.hasPermission()`
  call at `AuthGuard.tsx:63`, and the `LegacyPermission` import it
  needs) — already provably dead (Phase B/F), but its removal changes
  `AuthGuardProps`'s public type, so it's grouped with the
  `rbacService.hasPermission()` removal rather than done standalone.
- **`LegacyPermission`** (`types/index.ts:750`) — removable once
  `AuthGuard.requiredPermission` no longer needs the full legacy union
  (i.e., after the `AuthGuard` prop is narrowed, per Phase F's migration
  path) and `rbac.service.ts` no longer references it.
- **`UserRole`'s authorization role** — becomes moot automatically once
  `legacyGranted` and `AuthGuard.tsx:63` are gone; the type itself
  (`types/index.ts:6`) and the `User.role` field stay regardless (Must
  Keep, below), but nothing would read `role` for an authorization
  decision anymore.

### Must Keep

- **`dashboard:access` the literal** — required indefinitely as (a) a
  `P7Permission` union member (so `usePermission()`'s type signature
  stays valid even after any future fix to the Phase G bug) and (b) the
  value `console/layout.tsx` passes to `AuthGuard`.
- **`UserRole` the type, and `User.role` the field** — needed for
  identity (set at login), UI display (`AccessDenied`, `AppShell`,
  `console/users/[id]`), and observability (Sentry), independent of any
  authorization role.
- **`AuthGuard`'s `dashboard:access` path** (`useHasDashboardAccess()`
  call) — the real, correct, currently-working `/console` gate. Not a
  legacy component at all; must not be touched by any future legacy
  cleanup.

### Required Migration Tasks (ordered)

1. Add `MOCK_STAFF_LIST` (+ `StaffAssignment`) fixtures for
   `staff@samoon.com` (role `manager`) and `multirole@samoon.com` (roles
   `cashier` + `kitchen`), mirroring the shape of existing role-named
   demo accounts.
2. Add a regression test proving `useHasDashboardAccess()`'s
   ownership/StaffAssignment branch alone (with `legacyGranted` forced
   `false`) grants access to every `MOCK_CREDENTIALS` account, including
   the two new fixtures — establishing that `legacyGranted` is provably
   redundant before it's deleted (same audit-then-remove discipline as
   P10.4.1→P10.4.3).
3. Remove the `legacyGranted` OR-branch from `useHasDashboardAccess()`
   (`hooks/index.ts`).
4. Remove `rbacService.hasPermission()` and its five backing tables from
   `rbac.service.ts` (now zero callers).
5. Remove `AuthGuard`'s legacy fallback branch and narrow
   `AuthGuardProps.requiredPermission` (or replace it with a boolean),
   dropping the `rbacService`/`LegacyPermission` imports from
   `AuthGuard.tsx`.
6. Remove `LegacyPermission` from `types/index.ts`.
7. Re-audit `UserRole`: confirm zero remaining authorization callers and
   decide whether to leave it as-is (identity/display only) or formally
   wire in `deriveLegacyUserRoleLabel()`.
8. **Separately** (not part of this removal chain — a correctness fix,
   not a legacy removal): switch `Header.tsx` and
   `app/dashboard/layout.tsx` from `usePermission('dashboard:access')` to
   `useHasDashboardAccess()`, fixing the always-false nav-link bug found
   in Phase G.

lose `/console` access — the only real regression risk in this entire
legacy layer.
