What was missing was purely the ownership layer: no `Owner` entity, no `Tenant.ownerId`, no `StaffAssignment`. This phase adds exactly that layer, additively.

## Phase B — Owner Entity

`src/types/ownership.ts` (new) defines `Owner` exactly per P10.1 §1.1: `ownerId`, `userId`, `status`, `plan`, `maxTenants` (nullable = unlimited), `billing` (opaque `BillingRef`), `createdAt`, `verifiedAt?`. `currentTenantCount` is deliberately **not** a field — P10.1 states it's derived, never stored — realized as `ownerService.countOwnedTenants(ownerId, tenants)`.

`src/services/owner.service.ts` (new) implements it as a mock service following the codebase's established `USE_MOCK`/`delay()` convention, with 4 seeded Owners (`MOCK_OWNERS`) and the single source-of-truth tenant→owner map (`MOCK_TENANT_OWNER_MAP`) that `tenant.service.ts` and `staff.service.ts` both read from, so ownership isn't hand-duplicated in three places.

Owner is not a `Role`/`StaffRole` value anywhere in this codebase after this phase, and does not replace `Tenant` — `Tenant` still has its own `id`, and `Owner.ownerId` is a distinct identity space.

## Phase D — Staff Model

`StaffMember` (`src/types/staff.ts`) gains:

```ts
ownerId?: string
```

`tenantId` is **kept, unchanged, still required** — it was not removed. Per the global rule "reuse everything that already works" and "never touch UI," removing it would have broken `staff.service.ts`'s existing CRUD, the Staff Management console pages, and `branch-access.service.ts`'s consumers, none of which this phase is permitted to touch. Its TSDoc is updated to state its new *meaning* (a legacy "home tenant" reference, not an access grant) without changing its *type* or *requiredness*. `branchIds?` is left exactly as-is (still present, still unused, still flagged for the P10.1 §10.3 cleanup) — no permission resolution logic reads it before or after this phase.

`staff.service.ts`'s `INITIAL_MOCK_STAFF` is backfilled the same way `tenant.service.ts` is: a loop deriving each staff member's `ownerId` from their existing `tenantId` via `MOCK_TENANT_OWNER_MAP`. One new fixture, `staff-accountant-01` (Avery Accountant), was added to realize the cross-tenant Staff example from P10.1 §3.2 — everything else in the 22-member roster is untouched except the additive field.

## Phase E — StaffAssignment

`src/types/ownership.ts` defines `StaffAssignment` exactly per P10.1 §1.1/§3: `assignmentId`, `staffId`, `tenantId`, `branchIds: string[] | 'all'`, `role: StaffRole`, `mode: 'read'|'manage'`, `status: 'active'|'future'|'revoked'|'expired'`, `validFrom?`, `validUntil?`, `grantedBy`, `grantedAt`, `revokedBy?`, `revokedAt?`. `StaffRole = Exclude<Role, 'owner'>` — `'owner'` can never appear on an assignment.

`src/services/staff-assignment.service.ts` (new) implements Grant / Revoke / Move exactly per P10.1 §3.5's table:
- **Grant** → `staffAssignmentService.grant()` creates a new row, `status: 'future'` if `validFrom` is ahead of now, else `'active'`.
- **Revoke** → `staffAssignmentService.revoke()` sets `status: 'revoked'`/`revokedBy`/`revokedAt`; the row is never deleted.
- **Move** → `staffAssignmentService.move()` calls `revoke()` on the old assignment then `grant()` for the new one — never an in-place mutation of `tenantId`, exactly as §3.6 specifies.
- **Temporary** / **Future** → `validUntil`/`validFrom` set at grant time.
- **Read-only** / **Management** → `mode: 'read'` / `mode: 'manage'`.
- **All branches** / **specific branches** → `branchIds: 'all'` / `branchIds: string[]`.

No UI, no pages — the entire deliverable is the type, the mock service, and the two data-level helper functions in `src/services/ownership.service.ts`:
- `resolveAssignmentStatus()` — derives `future`/`active`/`expired` from dates, `revoked` always authoritative (pure function, unit-tested for every branch).
- `validateAssignment()` — enforces the P10.1 §3.3 invariant (assignment's tenant must be owned by the same Owner as the assignment's staff) before a grant is written.
- `ownerOwnsTenant()` / `resolveAssignmentBranchIds()` — pure data lookups a later phase's resolution engine can consume directly.

**Explicitly not done here** (per this phase's own instruction, "Do NOT yet change permission resolution"): none of these functions import from, call, or are called by `permission.service.ts`. The full P10.1 §4.4 algorithm (ownership short-circuit → assignment lookup → branch check → union of `ROLE_PERMISSION_MAP` with `mode`'s read/manage downgrade → existing override/capability/flag composition) is **not implemented** — see "Remaining work for P10.2.2" below.

## Phase G — Migration

`src/services/ownership-migration.service.ts` (new) implements the P10.1 §10.3 backfill rule as a pure, tested function — not run against any live store, since Phase F's fixtures were authored fresh (already correct) rather than migrated from a "dirty" dataset:

- `backfillTenantOwnership(tenants, staff, existingOwners)` — for each tenant without an `ownerId`, finds staff with the legacy `'owner'` role on that tenant; exactly one holder → resolves/creates an `Owner` and sets `ownerId`; zero or more than one → flagged in `report.ambiguousTenantIds`, left untouched, never auto-resolved (matches P10.1 §10.3's explicit instruction). Never mutates its inputs; never deletes anything.
- `deriveLegacyUserRoleLabel()` — the P10.1 §8.2 `UserRole` derivation rule (`owner`/`staff`/`customer`, `admin` collapsing into `staff`) expressed as a pure, callable function rather than left as prose — not wired into `auth.service.ts` or any store (that wiring is explicitly deferred by §8.2 itself).

`rbac.service.ts` (already `@deprecated` per P10.0 J4) is untouched. `UserRole` is untouched. `StaffMember.branchIds` is untouched. Nothing legacy was deleted.

### 3. Migration strategy implemented

Exactly P10.1 §10.2/§10.3: every new field (`Tenant.ownerId`, `StaffMember.ownerId`) is optional and nullable; every existing consumer of `Tenant`/`StaffMember` that doesn't know about the new fields keeps compiling and running unchanged (verified by the "backward compatibility" test group). ### 5. Honest completion report

Everything explicitly asked for in Phases A–H was implemented: the Owner entity, the `Tenant.ownerId`/`StaffMember.ownerId` extensions, the `StaffAssignment` entity with full Grant/Revoke/Move/Temporary/Future/Read-only/Management/all-branches/specific-branches support, mock data realizing every example and lifecycle state from P10.1 §3.2/§3.5/§9, migration helpers matching the documented backfill rule, and a clean validation pass (tsc/eslint/tests/build) with zero regressions.

All of the above is scoped to P10.2.2, now reflected in `PLATFORM_ROADMAP.md`.
