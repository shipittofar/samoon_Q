## Phase A — Authorization Graph Re-Verification

Re-traced `usePermissions()` and `useHasDashboardAccess()`
(`src/hooks/index.ts`) and every function they call transitively.

**Confirmed: exactly the 5 claimed sources are live, no sixth exists.**

`usePermissions()` (`src/hooks/index.ts:175-222`):
1. **`tenantRoles`** — `useRbacStore((s) => s.tenantRoles)` (`:179`) →
   `getPermissionsForRole(roles)` → **`ROLE_PERMISSION_MAP`**
   (`src/services/permission.service.ts:97-274`), source #3.
2. **`userOverrides`** — `useRbacStore((s) => s.userOverrides)` (`:180`)
   → `applyOverrides(base, override)` (`permission.service.ts:529-537`).
3. **`ROLE_PERMISSION_MAP`** — single definition, no duplicate map exists
   anywhere in `src/`.
4. **Ownership Resolution** — `resolveOwnershipDrivenPermissions()`
   (`src/services/ownership-resolution.service.ts:236-245`), internally
   calling `resolveOwnerPermissions()` (`:130-139`), reusing
   `ROLE_PERMISSION_MAP`/`ALL_PERMISSIONS` rather than redefining them.
5. **StaffAssignment** — `resolveStaffAssignmentPermissions()`
   (`ownership-resolution.service.ts:207-224`) → the sole read path into
   `staffAssignmentService.getEffectiveAssignments()`
   (`src/services/staff-assignment.service.ts:305-310`).

Composition (`hooks/index.ts:217-219`):
`[...new Set([...tenantRolePermissions, ...ownershipDriven])]` — no
other array is merged in.

`useHasDashboardAccess()` (`src/hooks/index.ts:360-387`) is purely
Owner-or-StaffAssignment gated (`isOwnerEligible`/`ownerOwnsTenant` OR
`isStaffMemberEligible`/`getEffectiveAssignments().length > 0`) — no
`tenantRoles`/`userOverrides`/`ROLE_PERMISSION_MAP` involvement, matching
its doc comment and the P10.4.10 removal of the legacy fallback.

**Other Zustand reads near authorization code, audited and cleared:**
- `useTenantStore((s) => s.featureFlags)` in `usePermission`/
  `useAnyPermission`/`useAllPermissions` — this is the FeatureFlag layer
  of the documented "Permission AND Capability AND FeatureFlag" formula
  (`permission.service.ts:7`), not a 6th source. (See Phase E for an
  inconsistency in how consistently it's applied.)
- `AdminSidebar.tsx`'s `RoleChip` reads `getRolesForTenant` for a
  **display-only label**, never for a grant/deny decision.
- `AdminTenantSwitcher.tsx` reads/writes `getRolesForTenant`/
  `setTenantRoles` — this is source #1's write path, not a parallel read.
- `src/platform-admin/store.ts`/`permissions.ts` implement a
  **deliberately separate** Platform Administration permission model
  (`PlatformRole`/`PlatformPermission`), explicitly documented as
  non-overlapping with tenant RBAC. Not a 6th tenant-RBAC source — a
  distinct domain, out of scope here.

**Duplicate resolvers:** none. `useAdminModuleNav()` explicitly calls
`usePermissions()` rather than recomputing (fixed in P10.2.2 Phase F).

**Hardcoded tables read directly by components instead of the hooks:**
none found. `console/roles/page.tsx` and `console/roles/new/page.tsx`
import `ROLE_TEMPLATES`/`ALL_PERMISSIONS`/`PERMISSION_CATEGORIES` for
**display metadata only** — actual access gating on those pages goes
through `<PermissionGuard permission="staff.manage">`, which calls
`usePermission()`.

**Verdict: the 5-source claim holds exactly.** No dead RBAC source
remains live, no duplicate resolver exists, no hidden permission table
is consulted outside the documented graph.

## Phase C — CustomRoles Reality Audit

**1. Is `customRoles` intended to affect permissions?** No evidence it
ever did. `CustomRoleTemplate.permissions` (the array a custom role
carries) is never read by `getPermissionsForRole()`,
`resolveOwnershipDrivenPermissions()`, or any other resolution function.
`usePermissions()` has no code path that touches `useRbacStore.customRoles`
at all.

**2. Is the Console Roles UI incomplete?** Yes, functionally. The
"Create Custom Role" form (`app/console/roles/new/page.tsx`) is fully
built — name/description/color/permission picker, a working `handleSave()`
that calls `addCustomRole()` (`:81-93`), a "Saved! Redirecting…" state,
and a redirect to `/console/roles`. But `/console/roles` (the listing
page) has **no `useRbacStore` import at all** — it reads exclusively from
the static `ROLE_TEMPLATES` constant (`permission.service.ts`). A role
created through the builder is written to a persisted Zustand store,
never displayed anywhere, and has zero authorization effect. The two
pages were never wired to each other.

**3. Is `ROLE_TEMPLATES` the actual source of truth?** Yes, unambiguously.
It is the only role catalog `console/roles/page.tsx`,
`console/users/page.tsx`, `console/users/[id]/page.tsx`, and
`console/permissions/simulator/page.tsx` read from. `ROLE_TEMPLATES` and
`customRoles` are never unioned or cross-referenced anywhere in `src/` —
confirmed via full-repo grep, they never appear in the same expression.

### Decision: **Option B — `customRoles` is classified as future UI-only data**

Completing the integration (Option A) would require: (a) deciding how a
`CustomRoleTemplate` interacts with the fixed `Role` union type that
`ROLE_PERMISSION_MAP` and every `StaffAssignment`/`TenantRoleAssignment`
are keyed on (custom roles are not part of that union today — `Role` is
a closed set of 8 literals), (b) wiring `getPermissionsForRole()` or
`usePermissions()` to consult `customRoles`, and (c) making
`console/roles/page.tsx` render both catalogs. That is real permission-
resolution design work — explicitly out of scope ("Do NOT implement a
large feature").

Instead, this phase documents the true current state so nobody mistakes
the Role Builder for a working feature:

- `customRoles` is a **persisted, write-only Zustand field with zero
  runtime read consumers and zero authorization effect.**
- The "Create Custom Role" form is real, functional UI, but it currently
  writes to a data structure nothing else in the product reads.
- No misleading assumption should be carried forward that creating a
  custom role does anything beyond locally persisting an unused record.
- No code was changed to fix this — per Phase C's instruction, only the
  misleading assumption is corrected here, in documentation.
- `customRoles`' store field, actions, and type (`CustomRoleTemplate`)
  are kept (as decided in P10.5.4) precisely because a real write path
  exists — removing them would break the form. Completing the wiring is
  a candidate for a future phase; see "Recommended Next Phase" below.

## Phase E — Permission Function Duplication Audit

### Plain functions (`src/services/permission.service.ts`)

| Function | Definition | Runtime call sites (non-test) |
|---|---|---|
| `hasPermission` | `:347-377` | `src/services/branch-access.service.ts:23,48,69`; internally used by the two below |
| `hasAnyPermission` | `:383-390` | None outside its own module/tests |
| `hasAllPermissions` | `:396-403` | None outside its own module/tests |

### React hooks (`src/hooks/index.ts`)

| Hook | Definition | Runtime call sites (non-test) |
|---|---|---|
| `usePermission` | `:228-250` | `AuthGuard.tsx`, `AdminTenantSwitcher.tsx`, `ConfigurationModulePage.tsx`, `PermissionGuard.tsx` |
| `useAnyPermission` | `:261-275` | `PermissionGuard.tsx` |
| `useAllPermissions` | `:282-292` | `PermissionGuard.tsx` |

**Naming consistency:** `useAllPermissions` (hook, plural) correctly
matches `hasAllPermissions` (function, plural). A singular
`useAllPermission` does **not** exist anywhere in `src/` — the
singular/plural mismatch this phase was primed to look for is **not
present**. Stated explicitly since it was a named hypothesis in the task.

**Real finding, not a naming issue — a documentation/behavior gap:**
`usePermission`/`useAnyPermission`/`useAllPermissions` do **not** call
`hasPermission`/`hasAnyPermission`/`hasAllPermissions` at all. They
independently re-implement any/every/single-permission logic directly
against the `usePermissions()`-resolved array. This split (roles-in vs.
permissions-in) is legitimate — the service functions operate on raw
`roles` for `branch-access.service.ts`, which doesn't have a resolved
permission array to hand them — but within the hook layer there is a
genuine inconsistency:

`useAnyPermission()` and `useAllPermissions()` capture `featureFlags` as
a `useMemo` dependency but **never branch on it** inside their
`.some()`/`.every()` callbacks — unlike `usePermission()`, which applies
a real per-resource feature-flag gate (`FLAG_MAP`/`featureFlags[flagKey]`,
`hooks/index.ts:236-246`). Their JSDoc previously claimed *"Respects
user overrides and feature flags"*, which was **not true** — a
documentation defect, not just a naming one.

**Action taken (Phase E — naming/comments only, zero behavior change):**
Corrected the JSDoc on `useAnyPermission()` and `useAllPermissions()` in
`src/hooks/index.ts` to state accurately that they do not apply the
feature-flag gate, and to point at this document. The `featureFlags`
memo dependency, the `.some()`/`.every()` logic, and every call site's
observed return value are byte-for-byte unchanged — this is a comment
correction only, verified by the identical vitest pass/fail counts in
Phase H.

**Not done, and why:** Actually making `useAnyPermission`/
`useAllPermissions` enforce the feature-flag gate would change what
`PermissionGuard` renders for any multi-permission check gated behind a
disabled feature flag — a real authorization-behavior change, forbidden
by this phase's rules ("do not modify UI authorization behavior unless
fixing proven bug" is the one carve-out, but Phase E explicitly restricts
this phase to "naming/comments only"). Recorded as a risk for the next
phase instead (see `docs/P10.5.5_PERMISSION_ARCHITECTURE_FINAL.md`
"Security Model" and this document's "Recommended Next Phase").

`hasAnyPermission()`/`hasAllPermissions()` (service functions) were left
alone entirely — no proof of zero external dependency beyond "no current
call site" (they are exported from `permissionService` and covered by
`phase7-rbac.test.ts`), and the task's rule is explicit: "Do not delete
public utilities without proof."

## Phase F — Permission Type Audit

Read `src/types/rbac.ts` in full (now 243 lines after P10.5.4's
`BranchRoleAssignment`/`RoleAssignment` removal). All 15 exported types
confirmed used at least once outside their own file and outside tests:
`Role`, `P7Permission`, `UserTenantRole`, `TenantRoleAssignment`,
`PermissionCheckOptions`, `AuditEvent`, `MockRbacUser`,
`UserPermissionOverride`, `EffectivePermissionResult`, `RoleTemplate`,
`CustomRoleTemplate`, `PermissionDependency`, `RbacAuditEvent`,
`SimulationResult`, `DependencyValidationResult`.

**Confirmed present, as required:** `P7Permission`, `Role`,
`TenantRoleAssignment`, `UserPermissionOverride`, `CustomRoleTemplate`.

**Confirmed absent, as required:** `LegacyPermission`, the old
dot-notation `Permission` duplicate, `BranchRoleAssignment`,
`RoleAssignment` — zero definitions anywhere in `src/` (removed in
P10.4.7 and P10.5.4 respectively). The only remaining occurrences of
those four names are inside test assertions proving their non-existence.

**Conclusion — Phase F: zero types removed.** Every exported type in
`rbac.ts` is load-bearing. `CustomRoleTemplate` is used to type the
`customRoles` store field and `addCustomRole`'s parameter — it's a
functional dead-end at the feature level (Phase C), not a dead type at
the code level, and stays per the Phase C decision.
