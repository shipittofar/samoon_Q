# P9.0.1 — Developer Guide: Working with Platform Configuration

> Onboarding for anyone adding a new module or field to the Platform
> Configuration System. See `docs/PLATFORM_ARCHITECTURE_PRINCIPLES.md` for
> the rules this guide implements, and
> `docs/P9.0_CONFIGURATION_ARCHITECTURE.md` for the underlying model.

---

## 1. How to create a new module

Create `src/config/modules/my-module.ts`. Copy the shape of an existing
module — `src/config/modules/authentication.ts` is a good template (two
sections, several field types, a mix of locked and overridable fields).

```ts
import { defineField } from '../field'
import { platformConfigurationRegistry } from '../registry'
import type { ConfigModuleDefinition } from '../types'

const PERMISSIONS = { view: 'settings.view', edit: 'settings.manage' }

export const MY_MODULE: ConfigModuleDefinition = {
  id: 'my_module',
  name: 'My Module',
  description: 'One sentence a Platform Administrator would understand.',
  category: 'platform', // or 'security' | 'branding' | 'commerce' | 'communications' | 'infrastructure' | 'content' | 'localization' | 'billing'
  version: '1.0.0',
  permissions: PERMISSIONS,
  sections: [ /* see §2 */ ],
}

platformConfigurationRegistry.register(MY_MODULE)
```

## 2. How to register a module

Registration is the `platformConfigurationRegistry.register(MY_MODULE)` call
at the bottom of the module file — it must run at **import time** (module
body), never inside a hook, component, or request handler. Then add the
import to `src/config/index.ts`:

```ts
import './modules/my-module'
```

If your module depends on another (reads its resolved values, e.g. a
preview that renders using the Themes module), place your import **after**
the dependency's import, and declare it:

```ts
dependencies: [{ moduleId: 'themes', reason: 'Preview renders using the tenant theme.', type: 'hard' }],
```

Registering before a hard dependency exists throws immediately — this is
intentional; fix the import order, don't work around the error.

## 3. How to register schemas

Fields are declared with `defineField()` (`src/config/field.ts`), grouped
into `sections`:

```ts
sections: [
  {
    id: 'my_module.limits',
    title: 'Limits',
    fields: [
      defineField({
        id: 'my_module.max_items',
        title: 'Max Items',
        description: 'Upper bound enforced before the API rejects a create request.',
        category: 'platform',
        type: 'number',
        default: 50,
        validation: { min: 1, max: 1000 },
        permissions: PERMISSIONS,
        inheritance: { level: 'platform', canOverride: true, mode: 'override', fallback: 'inherit' },
      }),
    ],
  },
],
```

Checklist for every field:

- `id` is dotted and globally unique (`my_module.field_name`) — the registry
  throws on collision, so a typo that accidentally matches another module's
  id is caught at boot, not silently ignored.
- `type` matches one of the 16 supported `ConfigFieldType` values (see
  `src/config/types.ts`) — don't invent a new one without first extending the
  schema system itself and updating `ConfigurationValidator`.
- `inheritance.level` is the layer that should own the default. Most
  platform-wide policy (rate limits, security thresholds) is owned at
  `'platform'` with `canOverride: false` (locked). Most branding/preference
  fields are owned at `'platform'` with `canOverride: true` so tenants can
  customize.
- `permissions` reuse an existing key from `src/types/rbac.ts` — do not
  invent a new permission string for a new module unless nothing existing
  fits.
- Secrets: `type: 'secret'`, `visibility: 'admin_only'`,
  `audit: { sensitive: true, requireReason: true, trackHistory: true }`, and
  a default of `''` — never a real-looking value. See
  `docs/P9.0.1_ARCHITECTURE_HARDENING.md` §C.

## 4. How to expose configuration

Nothing extra to write. Once registered, your module's fields are available
through `configurationService` (`src/config/service.ts`):

```ts
configurationService.resolveField('my_module.max_items', { tenantId })
configurationService.resolveModule('my_module', { tenantId, branchId, userId })
configurationService.updateField({
  fieldId: 'my_module.max_items', value: 100, level: 'tenant',
  scope: { tenantId }, actor: { id: userId, name: userName }, reason: 'Increase for enterprise plan',
})
```

## 5. How to write hooks

You almost never need a new hook — `src/hooks/use-platform-configuration.ts`
already covers every registered module generically:

```ts
const { configModule, values } = useConfigurationModule('my_module')
const { field, resolved } = useConfigurationField('my_module.max_items')
const { canView, canEdit } = useConfigurationPermissions('my_module.max_items')
```

Only add a new hook if your module needs behavior the generic hooks
genuinely can't express (rare — if you find yourself needing one, check
whether it's actually a missing capability in the schema system instead,
per Rule 11 in the Principles doc).

## 6. How to update the API contract

Add or extend a section in `docs/BACKEND_API_CONTRACT.md`. For most new
modules, no new section is needed — §36 (Platform Configuration API) already
covers every module generically via `/admin/config/modules/{moduleId}/` and
`/admin/config/fields/{fieldId}/`. Only add a dedicated section if your
module needs an endpoint the generic contract doesn't cover (e.g. a
provider-specific webhook receiver for a payment provider — that's a
*product* endpoint, not a *configuration* endpoint, and belongs in its own
numbered section like the existing Payment/Notification sections).

## 7. How to extend mock data

Add realistic override examples to `src/config/mock-data.ts` (or a
module-scoped mock file if the module has enough data to warrant its own,
following the pattern of `src/services/*.service.ts`'s inline `MOCK_*`
exports). At minimum, demonstrate one non-default value at the tenant level
so a future settings UI has something to render besides "everything is at
its default."

## 8. How to write tests

Follow `src/test/p9-platform-configuration.test.ts`. Key pattern — the
registry seals after first read, so every test needs a fresh module scope:

```ts
async function freshConfig() {
  vi.resetModules()
  return import('@/config')
}
```

Cover, at minimum: that your module registers without throwing, that its
fields carry required metadata, that resolution behaves as declared
(inheritance direction, locked fields reject overrides), and that
validation rejects at least one genuinely invalid value.

## 9. How to document a module

Add one row to the module table in
`docs/P9.0_PLATFORM_CONFIGURATION_AUDIT.md` if your module replaces an
existing hardcoded mechanism (most don't — most are net-new). Add your
module to the relevant phase in `docs/PLATFORM_ROADMAP.md` if it isn't
already listed there. No standalone per-module doc is required — the module
file's own header comment plus its entry in the registry (readable via
`platformConfigurationRegistry.getModule(id)`) is the documentation, by
design (Rule 7 — UI, and by extension docs tooling, should be generatable
from the registry, not hand-maintained per module).
