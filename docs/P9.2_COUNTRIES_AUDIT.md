# P9.2 — Countries Architecture Audit

> Phase A of P9.2. Reviews the current `countries` configuration module and
> the P9.1.3 Configuration Engine against what Countries actually needs, to
> decide what's reusable as-is versus what requires a genuine framework
> improvement (never Countries-specific code, per this phase's mandate).
>
> Last updated: 2026-07-04

---

## 1. Current Countries module

`src/config/modules/countries.ts` registers 3 scalar fields: `countries.enabled_codes`
(multi-select, all 176 ISO codes), `countries.pinned_codes` (array), and
`countries.default_code` (single `country`-typed field). These are genuine,
correctly-modeled platform-wide settings and are **not rewritten** by this
phase — they answer "which countries exist in pickers," a different
question from Phase B's ask: "every country should expose configurable
properties" (enabled, phone login, currency, timezone, …) — i.e., **per-country**
configuration, not platform-wide list configuration.

## 2. The gap: no concept of "one schema, many instances"

Every module built through P9.0–P9.1.3 (Authentication's 17 fields, Themes'
4, Payments' 5, …) follows the same shape: a fixed, small number of
distinct fields, each individually declared once via `defineField()` and
registered once. Countries needs the opposite shape: **one repeating
schema** (≈20 properties: enabled, visible, phone login, SMS, registration,
reservations, ordering, payments, delivery, pickup, currency, timezone,
default language, phone prefix, VAT, address format, postal validation,
national ID, notes, region, lifecycle) **applied to 176 entities** (one per
country). Modeling this as 176 × 20 ≈ 3,500 individually-registered
`ConfigFieldDefinition`s would:

- Explode the registry (every module currently registers 3–17 fields total).
- Violate Rule 3 (Single Source of Truth) by repeating the same 20-property
  schema 176 times instead of declaring it once.
- Make `PlatformConfigurationRegistry`'s duplicate-id check (a real safety
  feature — see `docs/PLATFORM_ARCHITECTURE_PRINCIPLES.md` §1) untenable at
  that scale, and make a future Console module search/list page unusable.

**This is exactly the kind of gap Phase K instructs to fix in the
framework, not paper over with Countries-specific code.** Phase B (§below)
introduces a genuinely new, generic concept — a `'collection'` field type —
directly in `src/config/types.ts`, usable by any future module with the
same "one schema, many entities" shape (e.g., a future Branches or Tenants
configuration module).

## 3. What's already fully reusable, unmodified

| P9.1.3 piece | Reusable for Countries? |
|---|---|
| `ConfigurationService` (resolve/update/validate) | Yes — a collection field is still just one `ConfigFieldDefinition` with a `'json'`-shaped value; every existing resolve/validate/audit/cache mechanism applies with zero changes. |
| `ConfigurationFieldControl` (18 `uiControl` kinds) | Yes — each of the 20 per-country properties reuses an existing control (`switch`, `currency_picker`, `timezone_picker`, `textarea`, …) with **zero new control kinds needed**. |
| `ConfigurationFieldBadges` | Yes — per-country lifecycle/governance badges render identically to Authentication's. |
| `ConfigurationFieldPreview` | Yes — phone format / currency / address previews reuse the existing `preview.kind` mechanism (Phase I). |
| `useConfigurationDraft` | Yes for module-level fields; **not sufficient alone** for per-entity dirty-tracking inside a collection (see below). |
| `configUiHelpers.ts` (`matchesSearch`, `resolveUiControl`, `deriveFieldState`, dependency evaluation) | Partially — `matchesSearch` operates on a `ConfigFieldDefinition`, not an arbitrary searchable record; needs generalizing (not duplicating) to also search collection entries. |

## 4. Missing metadata (addressed in Phase B/K)

- No way to declare "this field's value is a keyed collection of
  sub-records, each shaped like a mini-schema." → new `field.collection`
  metadata block.
- No shared vocabulary for a searchable/filterable "item" that works for
  both a plain field (Authentication) and a collection entry (a country
  record) → `configUiHelpers.ts`'s search logic is generalized to a shared
  `buildSearchHaystack()` helper, not duplicated per call site.
- No generic bulk-operation concept — every write today (P9.1.2/P9.1.3) is
  one field at a time via `updateField()`. Countries' "select 12 countries,
  disable them all" is a new, genuinely generic capability → new
  `useConfigurationBulkActions` hook, framework-level, operating over any
  collection field's selected entity ids.
- No generic detail-drawer component — Phase H explicitly asks for one
  reusable across modules.

## 5. Missing UI capabilities

- List/table rendering with search, filter, sort, grouping, bulk selection,
  and statistics did not exist anywhere in P9.1.3 (Authentication is a flat
  field list, not a searchable table of entities).
- No filter engine beyond live search — Phase F's enabled/disabled/
  published/draft/experimental/region/capability filters need a new,
  generic predicate builder.

## 6. Renderer limitations found

`ConfigurationFieldRow` currently assumes one field = one control. A
collection field needs to render as a **table**, not a single input. The
fix (Phase K) is a single, generic dispatch: when `field.type === 'collection'`,
`ConfigurationFieldRow` renders `ConfigurationCollectionTable` instead of
`ConfigurationFieldControl` — one `if`, no page-level or module-specific
branching, and every other field type's render path is untouched.

## 7. Conclusion — what this phase builds and where

| Requirement | Home | Countries-specific? |
|---|---|---|
| `'collection'` field type + schema metadata | `src/config/types.ts` | No — framework |
| Collection read/merge/reset helpers | `src/config/collection.ts` (new) | No — framework |
| Generalized search + new filter engine | `src/components/admin/configuration/configUiHelpers.ts` | No — framework |
| Generic bulk actions | `src/hooks/use-configuration-bulk-actions.ts` (new) | No — framework |
| Collection table + entity drawer | `src/components/admin/configuration/` (new files) | No — framework |
| Collection dispatch in the row renderer | `ConfigurationFieldRow.tsx` (one-line addition) | No — framework |
| The actual 20-property schema + 176-country dataset | `src/config/modules/countries.ts` + a new data file | **Yes — this is Countries' own module content**, exactly as Authentication's 17 fields are Authentication's own content |

Everything above the last row is the framework improvement this phase's
success criteria demands; the last row is the one piece of genuinely
Countries-specific work — declaring what a country's configurable
properties are, which is Phase B's actual job, not a framework concern.
