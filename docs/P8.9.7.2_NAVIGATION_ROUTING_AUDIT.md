# P8.9.7.2 — Navigation & Routing Integrity Audit

**Date:** 2026-07-04
**Scope:** Full navigation, routing, redirects, labels, and information architecture
**Method:** Read-only static inspection of all navigation sources, layouts, auth utilities, and page components
**Status:** AUDIT ONLY — no code was modified

---

## Executive Summary

The application's three-surface architecture (Public / Customer Dashboard / Business Console) is **structurally sound**. Route separation is clean. Auth guards are correctly placed. Role-based redirect logic is accurate for all nine user types.

Seven findings survived inspection. None are catastrophic. Two are medium severity (stale comment in `auth-redirect.ts`; `AccessDenied` sends any forbidden user to `/console/orders` regardless of context). Three are low severity (footer dead-links; login page hero copy; checkout success `Order More` CTA). Two are informational observations (Navbar component is a separate second sidebar that co-exists with the dashboard inline sidebar; the `AppShell` component is unused in the current dashboard routing).

### High

#### H1 — `AccessDenied` always redirects to `/console/orders` regardless of context

| | |
|---|---|
| **File** | `src/components/admin/AccessDenied.tsx` line 37 |
| **Symptom** | When `PermissionGuard` or `AuthGuard` renders `<AccessDenied />` for a user who lacks a specific permission (e.g. a Kitchen user trying to access `/console/analytics`), the CTA button reads **"Go to Orders"** and hard-links to `/console/orders`. |
| **Problem** | A Kitchen user does not own the Orders module. A Marketing user cannot manage orders. A Support user's natural home is `/console/customers`. The universal fallback to `/console/orders` is role-blind. Any user denied access is dumped somewhere they may not have permission to be either. |
| **Affected surfaces** | Every `<PermissionGuard>` usage across all ~48 console pages. |

Inside the console:
- Root crumb always resolves to `/console` (labelled "Admin"). ✅

## Informational Observations (not findings)

- **`AppShell` component** (`src/components/layout/AppShell.tsx`) defines a sidebar layout with `aria-label="Dashboard navigation"`. The current `/dashboard` layout (`src/app/dashboard/layout.tsx`) does not use `AppShell` — it inlines its own sidebar using `getDashboardNav()`. `AppShell` appears to be an older or alternate implementation. It is not linked from any route. This is not a bug but may cause confusion if a future developer finds `AppShell` and assumes it is the active layout.

- **`Header.tsx` dead conditional** (lines 219–228): renders `BranchSelector` and `NotificationBell` when `pathname.startsWith('/console')`. This is unreachable because `Header` is not mounted inside the console layout. Inert at runtime; potentially misleading in future development.

- **Demo vs. production redirect path divergence**: Demo login uses per-account `DEMO_EMAIL_REDIRECTS` (e.g. staff → `/console/orders` directly). Production email login uses `getPostLoginRedirect(role)` (staff → `/console` → then role-router in `console/page.tsx`). The final destination is equivalent but the demo gives a slightly faster UX. Not a bug; worth noting for parity.

- **`/restaurant` route** serves as both the partner acquisition landing page and the fallback for absent pages (About, Support, Pricing). As long as `/restaurant` is the correct partner page, using it for Pricing and "Become a Partner" is fine. The issue is using it for genuinely different concepts like company info and support.
