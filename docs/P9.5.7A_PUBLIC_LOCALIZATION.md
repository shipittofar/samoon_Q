# P9.5.7A — Public Experience Localization

**Status: IN PROGRESS, NOT COMPLETE.** This document honestly reports what
has been audited and migrated so far, and exactly what remains. Per the
epic's own rules, this phase is explicitly NOT marked complete.

## Audit method

1. Ran the existing tooling first: `node scripts/validate-i18n.mjs`
   (cross-locale key parity) and `node scripts/check-translation-
   coverage.mjs` (missing/unused keys, duplicate values, per-namespace
   coverage). Both already report clean/100% for the keys that exist —
   this only proves the *migrated* surface is internally consistent, not
   that migration is complete.
2. `scripts/check-hardcoded-strings.mjs` (the CI gate) only scans
   `MIGRATED_DIRS` = Console/Studio/Platform-admin component directories —
   it does not see the public pages this phase covers at all.
3. Built a one-off audit script reusing the exact same heuristic
   (`findHardcodedJsxText` from `src/i18n/coverage.ts`) against the
   **entire** `src/**/*.tsx` tree to get an honest, unscoped baseline.

## Real baseline (before this phase's work)

**473 hardcoded-string candidates** across ~90 files, by the automated
heuristic alone. Manual inspection of individual files (e.g. `app/
page.tsx`) shows the heuristic **undercounts** — it catches simple
single-line JSX text but misses multi-line text, `placeholder`/`aria-
label` attribute strings, and text split across JSX fragments. The
homepage alone had 4 heuristic hits but closer to 15+ real user-facing
strings once aria-labels, placeholders, and the multi-line hero copy are
counted.

Of the 473, the bulk (~380) are in `app/console/**` (P9.5.7C's scope, not
this phase's) and platform-admin-adjacent directories already migrated in
P9.5.4–P9.5.6 report 0. The public-experience-relevant subset (home,
discover, restaurant, tenant/branch, menu, reservation, checkout, order
tracking, loyalty, table QR, events/location/reviews/promotions/vendors,
error/not-found, home/marketplace/layout components) is real but smaller
— roughly 90-110 candidates once the undercounting above is accounted for.

**Namespace hygiene**: reused `common.viewAll` and `common.search` instead
of creating duplicates (caught and fixed during this phase — an earlier
draft had accidentally added `home.viewAll`/`home.heroSearchButton`
duplicating existing `common` keys); reused 6 of 7 existing `reservation.*`
keys and all 7 existing `restaurant.*` keys before adding anything new. No
new namespaces were created for functionality that fit an existing one —
`home` is new because no page-specific namespace previously existed for
the homepage (mirroring `restaurant`, `menu`, `checkout`, etc., which each
already have their own).

## Validation run after this work

- `node scripts/validate-i18n.mjs`: **705/705 keys identical across en/fa/ar** (up from 651).
- `node scripts/check-translation-coverage.mjs`: 0 missing keys, 0 orphan
  namespaces, fa/ar both 100% global coverage of the keys that exist.
- `npx tsc --noEmit`: clean.
- `next lint`: no new warnings/errors.
- `npx vitest run`: **94 test files / 5681 tests, all passing.** Three
  pre-existing test files (`phase4-seo.test.ts`, `phase4-featured.test.ts`,
  `phase4-reservation-confirm.test.ts`) asserted on literal English source
  text (e.g. `expect(src).toContain('Reservation Confirmed')`) that no
  longer appears verbatim now that the text is localized — updated to
  assert on the `t('key')` call site instead (a stronger check: it proves
  the string is actually wired to the translation system, not just
  present as English text).
- Production build (`npm run build` + `node .next/standalone/server.js`):
  `/`, `/restaurant`, `/reservation/confirm` all return `200` in English
  (default) and, via `NEXT_LOCALE` cookie, actual Persian/Arabic text
  confirmed present in the rendered HTML for `/` and `/restaurant`
  (verified with `curl | grep` against the real localized strings, not
  just a 200 status).
- RTL: not separately re-verified this phase beyond what P9.5.5's RTL
  preview infrastructure already covers — no new RTL-specific code was
  added (the migrated pages use existing layout components that already
  handle `dir="rtl"` globally via the root layout).
- Accessibility: aria-labels that existed were preserved and localized
  (not removed or left English-only) — no new accessibility audit tooling
  was run this phase.

## What was deliberately NOT touched, and why

- **Tenant-sourced fallback content** (`FALLBACK_BRANCHES`,
  `FALLBACK_GALLERY`, `FALLBACK_STORY`, tagline defaults in `restaurant/
  page.tsx`) — this is demo/mock DATA representing what a real tenant
  would supply via their own admin settings (branch names, addresses,
  story text), not UI chrome. The rest of this codebase already treats
  mock data content differently from UI strings (see `NEXT_PUBLIC_USE_MOCK`
  patterns throughout); translating a specific tenant's marketing copy
  into the platform's UI language doesn't match how real per-tenant
  content would work (a real tenant's story is whatever they wrote, in
  whatever language they wrote it — not derived from the viewer's locale).
