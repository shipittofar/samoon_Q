# P9.5.4 Phase F/G — SEO Localization

## Objective

Every page should generate localized `title`/`description`/`keywords`/
OpenGraph/Twitter/`robots`/canonical/hreflang metadata using next-intl,
with no hardcoded metadata — reusing the runtime localization engine, not
a second one.

## What was built

`src/lib/seo.ts` — `getLocalizedPageMetadata({ locale, path, namespaceKey, baseUrl })`:

- **title/description/keywords**: resolved from `getTranslations({ locale, namespace: 'seo' })`
  against `seo.<namespaceKey>.title`/`.description`/`.keywords` (a
  comma-separated string split into the array Next.js's `Metadata.keywords` expects).
- **OpenGraph/Twitter**: mirror the same localized title/description —
  no separate OG-specific translation content, since this app has no
  OG-specific copy need beyond the page's own title/description.
- **robots**: unchanged platform default (`index: true, follow: true`) —
  no per-locale robots policy exists or was requested.
- **alternates.canonical / alternates.languages (hreflang)**: generated
  from `resolveSupportedLocales()` (`src/i18n/runtime.ts`, P9.5.1A) and
  `getLanguageMetadata()` (`src/i18n/language-registry.ts`, P9.5.1A) — the
  *exact same* enabled-locale list every other locale-aware surface in
  the app already reads. Enabling a 7th language via
  `languages.supported` (Configuration Studio) automatically adds its
  hreflang entry here, with zero code change to this file.

No new registry, no new i18n engine: the helper is a thin composition of
next-intl's server API + the P9.5.1A runtime.

## What was migrated

**`src/app/layout.tsx`** (root layout) — converted its static
`export const metadata: Metadata = {...}` (English-only, hand-written) to
`export async function generateMetadata()` calling
`getLocalizedPageMetadata({ locale, path: '/', namespaceKey: 'root', baseUrl: APP_URL })`.
Static, locale-independent fields (icons, manifest, OG/Twitter image URLs,
`metadataBase`) are layered back on top of the localized fields, unchanged
from before. New `seo.root.title`/`.description`/`.keywords` keys added to
en/fa/ar (3 keys × 3 locales).

## What was NOT migrated (honest accounting)

Six other files in `src/app/**` export their own `metadata`/
`generateMetadata` and were **not** touched this phase:

- `src/app/[tenantSlug]/page.tsx`
- `src/app/[tenantSlug]/[branchSlug]/page.tsx`
- `src/app/restaurant/page.tsx`
- `src/app/page.tsx`
- `src/app/discover/page.tsx`
- `src/app/menu/page.tsx`

Each of these embeds **dynamic, per-entity data** in its metadata (a
tenant's own name, a branch's own name, a menu item's own name/
description) — migrating them isn't a mechanical "replace literal with
`t()`" pass the way the root layout was. Each needs:
1. A decision on which parts of the title/description are genuinely
   translatable copy (e.g. "Menu" — the word) vs. tenant-supplied content
   that passes through unchanged regardless of locale (e.g. "Brew & Co." —
   a business's own name is not translated).
2. Its own `seo.<page>.*` key design reflecting that split.

This is real, non-trivial per-page design work, not a `getLocalizedPageMetadata()`
gap — the helper already supports being called with a different
`namespaceKey`/`path` per page; what's missing is the 6 call sites and
their key content, which is next phase's work.

## Validation

- `npx tsc --noEmit` — clean.
- Regression tests (`src/test/p9-5-4-production-localization.test.tsx`,
  "Localized page metadata helper" suite) verify `seo.ts` reads
  `resolveSupportedLocales()` (not a hardcoded array) and that the real
  `seo.root.*` keys exist and differ between en/fa.
- Not verified: an actual rendered `<head>` snapshot of the hreflang tags
  in a real browser/E2E run — this phase validated the helper function's
  logic and its wiring into `layout.tsx`, not a full Playwright pass
  over rendered metadata tags (out of scope for this phase's time
  budget; flagged as a good E2E addition for P9.5.5).

## Remaining work for a future phase

1. Migrate the 6 remaining page-level metadata exports, with per-page
   `seo.<page>.*` key design distinguishing translatable copy from
   tenant-supplied literal content.
2. Add a Playwright/E2E check that the rendered `<html>` `<head>` actually
   contains the expected `hreflang` `<link>` tags for each enabled locale.
3. Consider whether locale-specific Open Graph images are worth the
   asset-generation cost (not requested this phase; current OG image is
   locale-independent).
