# P10.3 — Enterprise Ownership Enforcement & Security Hardening

Implementation report. This phase closed every verified finding from
`docs/P10.2.3_ENTERPRISE_INTEGRATION_AUDIT.md` (F-1 through F-8). It did
**not** redesign the ownership model, introduce a new permission system,
or remove/rewrite existing architecture — every fix extends
`ownership-resolution.service.ts` (P10.2.2) and reuses the existing
`ownership.service.ts` / `branch-access.service.ts` primitives.

## Architecture decisions

**Centralized eligibility predicates (Phase A/B/C).** `isOwnerEligible()`,
`isStaffMemberEligible()`, `isTenantEligible()` are the single place that
decides whether an Owner/Staff/Tenant record is allowed to participate in
permission resolution at all. Every function in
`ownership-resolution.service.ts` — and both new access guards — call
these instead of re-deriving `.status` checks inline. This is the
concrete answer to the task's "the logic must be centralized, do not
duplicate checks elsewhere" requirement for Phases A–C.

**One branch guard, one tenant guard (Phase D/E).**
`assertOwnershipBranchAccess(email, branchId)` and
`assertOwnershipTenantAccess(email, tenantId)` are the only two new
access-control entry points added this phase. Both are built entirely
from existing pieces — `resolveOwnershipIdentity`, the three eligibility
predicates, `ownerOwnsTenant` (ownership.service.ts),
`buildBranchAccessContextFromAssignments` (P10.2.2),
`branchAccessService.assertBranchAccess` (P7.4, branch-access.service.ts)
— and are called from query `queryFn`s in `hooks/index.ts`, so a denial
surfaces as a normal React Query error state rather than a new UI
pattern.

**Ownership transfer has one field of record (Phase F).**
`Tenant.ownerId` is the field every permission check reads
(`ownerOwnsTenant`, `resolveOwnerPermissions`). `tenantService.transferOwnership()`
is now the only function that mutates it. The legacy
`staffService.transferOwnership()` (P7 `'owner'` role swap within one
tenant) is kept — it is a different, still-valid operation — but now
also calls the new function when both sides of the transfer are backed
by real `Owner` records, so the two mechanisms move together instead of
drifting.

**Expiration is a scheduled event, not a poll (Phase I).**
`getNextAssignmentExpiry()` finds the exact moment a temporary
`StaffAssignment` stops being effective; `usePermissions()` sets exactly
one `setTimeout` for that moment. No interval polling was added anywhere.

## Reasoning per finding

- **F-1 (Owner.status ignored)** → Phase A. `resolveOwnerPermissions()`
  now returns `[]` for any non-`'active'` Owner.
- **F-2 (StaffMember.status ignored)** → Phase B. `resolveStaffAssignmentPermissions()`
  now returns `[]` for any non-`'active'` Staff member, regardless of
  how many effective assignments they hold.
- **F-3 (post-login redirect not ownership-aware)** → Phase H. Routing
  now checks real ownership/staff data before falling back to the role
  string.
- **F-4 (no branch/tenant isolation enforcement in the live data path)**
  → Phases D/E. Every concrete branch-scoped hook that exists in the
  codebase now calls the branch guard; `useStaff`/`useAdminBranches`
  call the tenant guard as representative tenant-scoped surfaces.
- **F-5 (logout doesn't fully clear RBAC store)** → Phase G. `_resetStore()`
  (which already existed, unused) is now wired into `useLogout()`.
- **F-6 (two disconnected ownership-transfer mechanisms)** → Phase F.
  `Tenant.ownerId` and the legacy role swap now move together when both
  sides have real Owner records.
- **F-7 (soft/non-live assignment expiry)** → Phase I. A scheduled
  single-fire timer replaces "wait for an incidental re-render."
- **F-8 (Tenant.status/archived ignored)** → Phase C. Both
  `resolveOwnerPermissions()` and `resolveStaffAssignmentPermissions()`
  now check `isTenantEligible()` before returning anything.

## Security implications

- An Owner or Staff member losing eligibility (suspended, removed,
  pending verification) now loses **all** derived permissions on the
  next resolution, not just on their own tenant's admin UI — the check
  is inside the shared resolution functions, so every caller (hooks,
  guards, nav) benefits automatically.
- Branch- and tenant-scoped reads that previously trusted a caller-
  supplied `branchId`/`tenantId` with no verification now reject access
  outside the caller's assignment. This closes a real cross-branch/
  cross-tenant data-exposure gap in mock mode; the equivalent backend
  enforcement is still required (see Remaining Technical Debt).
- Logout now clears every persisted RBAC field, closing a residual-
  session-state risk on shared/kiosk devices.

## Backward compatibility

- No `P7Permission`, `Role`, or `ROLE_PERMISSION_MAP` value changed.
- Every P10.2.1/P10.2.2 test continues to pass unmodified except the two
  call-site updates required by the `resolveStaffAssignmentPermissions()`
  signature widening (bare `tenantId: string` → `Pick<Tenant, 'id' |
  'status'>`), and those updates are mechanical (the tests construct the
  same tenant id, now wrapped in an object with `status: 'active'`).
- `staffService.transferOwnership()`'s existing behavior, return shape,
  and error cases are all unchanged for callers whose target has no
  Owner record — the common case.
- Every branch/tenant-scoped hook keeps its existing signature; the
  enforcement is inside the `queryFn`, invisible to callers except as a
  new possible `query.error`.

## Migration notes

- `resolveStaffAssignmentPermissions(identity, activeTenant, now)` takes
  a `Pick<Tenant, 'id' | 'status'>` as its second parameter now, not a
  bare `tenantId` string. Any future direct caller must pass an object.
- A denied `assertOwnershipBranchAccess`/`assertOwnershipTenantAccess`
  throws (`BranchAccessError`/`TenantAccessError`); callers that want a
  friendlier UI state should catch and map these in the consuming
  component, the same way any other query error is already handled.
- When a real backend exists, `TENANTS.TRANSFER_OWNERSHIP` needs an
  implementation; until then `USE_MOCK=false` will 404 on it exactly
  like every other "contract only" endpoint in this codebase.

## Remaining technical debt

- **Backend enforcement is not real yet.** Every guard added this phase
  runs against mock data in the frontend. A backend must implement the
  equivalent checks — this phase does not (and cannot) provide server-
  side isolation.
- **Customers and Search have no dedicated branch-scoped read function**
  to wire Phase D into; documented rather than fabricated. If/when such
  functions are added, they should call `assertOwnershipBranchAccess()`.
- **Phase C is scoped exactly to `'archived'`** per the single verified
  finding (F-8); `'trial'`/`'suspended'`/`'churned'` tenant states are
  intentionally untouched — broadening that check was not a verified
  finding.
- **Ownership transfer to a Staff member with no Owner record** does not
  create a new `Owner` record — deliberately, since fabricating billing/
  plan data was out of scope. A future phase should decide whether
  transferring to a non-Owner-backed Staff member should provision a new
  Owner record, and if so, with what defaults.
- **No tenant-selector page exists.** Phase H's "Owner with multiple
  tenants → tenant selection" example could not be built without
  inventing a route; both Owner and Staff currently route to `/console`
  regardless of tenant count. This is deferred, not solved.
- **The pre-existing dead-code branch in `verify/page.tsx`**
  (`getDemoRedirect(phone)` called with a phone number where the map is
  keyed by email) was found again during Phase H but is untouched — it
  predates this phase and is not a P10.2.3-verified finding.
- **`useOwnershipBranchAccessContext()` (hooks/index.ts) still has zero
  live callers** — confirmed again this phase; not removed per this
  phase's "do not remove code" scope (P10.2.3 catalogued it as dead code
  to flag, not to delete).
