# P9.0 — Platform Configuration Audit

> Phase A of P9.0 (Platform Configuration Foundation). Read-only audit performed
> before any code was written for Phase B onward. Produced by scanning
> `src/constants`, `src/services`, `src/stores`, `src/hooks`, `src/providers`,
> `src/modules`, `src/types`, `src/data`, and `docs/BACKEND_API_CONTRACT.md`.
>
> Last updated: 2026-07-04

---

## 1. Why this audit exists

Samoon has grown from a single-tenant restaurant menu app (Phase 1) into a
multi-business-type, multi-tenant platform (Phase 6–8) with RBAC, feature
flags, website builder, loyalty, CRM, and more. Each of those phases invented
its own small config mechanism — a registry here, a constants file there, a
`settings: Record<string, unknown>` bag on `Tenant` everywhere else. That
was the right call at each individual phase (YAGNI), but the result today is
four or five different patterns for "a thing an admin can configure," none of
which know about each other, none of which are auditable, and none of which
generalize to the next module (AI, Inventory, CRM, POS, …).

P9.0 does not invent new product behavior. It gives all of the below a single
home so P9.1+ can build settings UI once, generically, instead of once per
module.

## 2. Inventory of existing configuration mechanisms

| Location | Mechanism | What it configures | Problem |
|---|---|---|---|
| `src/constants/index.ts` | Plain `export const` | `DEFAULT_LOCALE`, `SUPPORTED_LOCALES`, `RTL_LOCALES`, `TAX_RATE`, `SERVICE_CHARGE_RATE`, storage keys | Hardcoded at build time. No per-tenant override. No audit. No schema/validation. Changing a rate requires a deploy. |
| `src/modules/registry.ts` | Sealed in-memory registry (`registerModule`/`getModules`) | Business-type modules: routes, nav, capabilities, `defaultFeatureFlags` | Excellent precedent for "registry that seals after first read" (P9.0's registry copies this pattern) — but it is scoped *only* to business-type modules. Auth, billing, themes, storage, monitoring have no equivalent. |
| `src/services/feature-flags.service.ts` | 3-layer merge function (`resolve`) | Feature flags: module defaults → capability defaults → `tenant.settings.featureFlags` | Good precedent for layered resolution — but it stops at "tenant." No branch or user layer, and it is one-off code that only feature flags get; every other config type reinvents this merge logic (or doesn't get it at all). |
| `Tenant.settings?: Record<string, unknown>` (`src/types/index.ts`) | Untyped bag | Feature flag overrides, `TenantTheme` (`primaryColor`, `accentHoverColor`, `logoUrl`, `fontBody`) | No schema. `as Record<string, unknown>` casts scattered through the codebase (`feature-flags.service.ts:46`, etc). Anyone can put anything under any key; nothing validates it, nothing audits changes to it. |
| `src/data/countries.ts` | Static array + exported constants (`PINNED_COUNTRY_CODES`, `RECENT_COUNTRIES_KEY`) | Country list & pinned countries for the phone_number picker | Hardcoded; a Platform Administrator cannot add a country or change which ones are pinned without a code change and deploy. |
| `src/i18n/locales/*.json` + `SUPPORTED_LOCALES` | Static files + constant | Supported languages | Same problem — adding a language is a PR, not a settings change. |
| `src/services/rbac.service.ts`, `src/types/rbac.ts` | Hardcoded permission catalog + per-tenant `TenantRoleAssignment` | Roles/permissions | Reasonably well-factored already (P7/P8.5/P8.6), but the *platform-level* policy (max custom roles, MFA requirement, default invite role) has no home — it's implicit in code, not configuration. |
| `src/services/tenant-provisioning.service.ts` | Inline defaults in provisioning flow | Default business type, default plan for new tenants | Hardcoded fallback values duplicated with whatever the "real" default should be. |
| `src/services/website-builder.service.ts`, `src/types/website-builder.ts` | Per-tenant page/section data, no schema for *platform* defaults | Which blocks exist, max sections, custom domain eligibility | Block library and limits are implicit in component code, not declared anywhere an admin (or this audit) can list them. |
| Various admin services (`payment.service.ts`, `notification.service.ts`, `audit-log.service.ts`) | Ad hoc | Payment providers, notification channels, audit retention | Each service owns its own notion of "what providers/channels exist" with no shared metadata (permissions, validation, versioning). |

### 2.1 Duplicated configuration found

- **Feature flag defaults** exist in two places per module: `Module.defaultFeatureFlags` (registry.ts) and ad hoc flags referenced directly by string in `useDashboardNav`/`usePermission`'s `FLAG_MAP` in `src/hooks/index.ts:189`. A rename in one place silently breaks the other.
- **Locale lists**: `SUPPORTED_LOCALES` (constants) vs. the literal `en`/`fa`/`ar` folders under `src/i18n/locales/` vs. `next-intl` config — three sources of truth for "what languages exist."
- **Default currency / tax rate**: `TAX_RATE`/`SERVICE_CHARGE_RATE` are single global constants, but per-tenant/per-country tax and currency rules are a real product need (countries already vary: `AED`, `TRY`, `USD` appear across mock data) — currently nowhere to declare this per tenant.
- **Permission strings**: `'settings.view'`, `'settings.manage'`, `'featureflags.manage'`, etc. (`src/types/rbac.ts`) are the right idea (a fixed catalog) but nothing ties a *configuration field* to the permission required to view/edit it — every settings page would have to invent its own gating.

### 2.2 Missing abstraction

- No concept of a configuration **field** with metadata (type, default, validation, help text, preview) — every "setting" today is just a raw value with no self-description.
- No concept of configuration **inheritance** (Platform → Tenant → Branch → User). Feature flags stop at tenant; theme stops at tenant; nothing has ever needed branch- or user-level override, so nothing supports it, even though Branch (`src/types/branch.ts`) and per-user preferences already exist as first-class entities elsewhere in the app.
- No **audit trail** for configuration changes as a category — `audit-log.service.ts` audits business events (orders, reservations) but not settings changes.
- No **versioning** — a module's schema can change shape at any time with no record of when or why.

### 2.3 Future scaling risks (if left unaddressed)

- Every new module in the roadmap (AI, Inventory, CRM, POS, Gift Cards, Franchise, Delivery) would each invent its own settings storage, its own permission checks, its own validation — multiplying the duplication above by 10+.
- A generic Console "Settings" UI is impossible to build once; it would need one hand-written page per module forever, which is exactly what Rule 7 (UI is Generated) is meant to prevent.
- Backend engineers have no single contract to implement against — `docs/BACKEND_API_CONTRACT.md` currently documents endpoints per *feature* (auth, menu, orders, …) with no unifying settings/config endpoint family.

## 3. What already works well (keep these patterns)

- **`src/modules/registry.ts`'s sealed-registry pattern** — register-at-import-time, freeze after first read, throw on late registration. This directly informed `PlatformConfigurationRegistry` (Phase C): same seal semantics, extended with duplicate-id detection across the *entire* registry, not just within one module.
- **`featureFlagsService.resolve()`'s layered merge** — directly generalized into `ConfigurationResolver`, extended from 2 layers (module default → tenant override) to the full 4-level chain (Platform → Tenant → Branch → User) with per-field control over whether merge, override, or lock semantics apply.
- **RBAC's fixed permission catalog** (`src/types/rbac.ts`) — reused as-is. Configuration fields reference existing permission keys (`settings.view`, `settings.manage`, `featureflags.manage`, …) rather than inventing a parallel permission system.

## 4. Benchmark — how comparable platforms structure this

| Platform | Pattern | What P9.0 borrows |
|---|---|---|
| **Shopify** | Settings are declared via `settings_schema.json` per app/theme — each entry has `type`, `id`, `label`, `default`, `info` | Field-as-data (`ConfigFieldDefinition`) instead of hand-written forms; `helpText`/`placeholder` mirror Shopify's `info`/`placeholder`. |
| **Stripe** | Dashboard settings + API resources are versioned (`Stripe-Version` header); every object change is journaled (Events API) | Per-module `version` + `ConfigurationVersionManager`; `ConfigurationAudit` mirrors Stripe's Events-as-audit-trail approach. |
| **Auth0** | Tenant → Connection → Client hierarchy, each level able to override auth rules, with RBAC gating who can change what | Directly maps to our Platform → Tenant → Branch → User inheritance chain (Rule 4) and per-field `permissions.view`/`permissions.edit`. |
| **Firebase** | Remote Config: named parameters with default value + conditional per-app overrides, strongly typed (string/number/boolean/JSON) | `ConfigFieldType` union (string/number/boolean/json/…) and the override-over-default resolution model. |
| **Vercel** | Project → Environment (production/preview/dev) scoped env vars/config, with an explicit inheritance and override UI | Confirms the "declare once, override at a defined set of scopes" shape rather than ad hoc per-feature toggles. |
| **Notion** | Workspace → Team → Page-level permission and property inheritance, generated property UI from a schema | Confirms Rule 7 (UI generated from schema, not hand-built per property) is achievable at scale. |

## 5. Conclusion

Every mechanism above is legitimate work for the phase it was built in — none of it needs to be ripped out. P9.0's job is additive: introduce `PlatformConfigurationRegistry` as the new single source of truth going forward (Rule 2), and treat `src/modules/registry.ts` and `feature-flags.service.ts` as the reference implementations that proved the pattern works. Phase B–J below build that foundation without touching existing call sites; migrating `src/constants/index.ts` values and `Tenant.settings` reads onto the new registry is scoped to P9.1+ (see `docs/P9.0_CONFIGURATION_ARCHITECTURE.md` §6, Future Extension Points).
