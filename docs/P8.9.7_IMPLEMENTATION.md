# P8.9.7 — Customer 360° CRM Implementation Notes

## Overview

P8.9.7 delivers a unified Customer 360° CRM experience for the admin console. All customer data (orders, reservations, loyalty, reviews, notes, tags, marketing, analytics) is surfaced on a single page with 10-tab navigation — no modal pop-ups, no page switches.

The design is comparable to Shopify Customers, HubSpot CRM, Square Customer Directory, Toast Guest Profiles, and Stripe Customer Portal, adapted for a multi-tenant restaurant/hospitality SaaS context.

---

## Architecture

### Three-layer customer model (preserved from P8.9.6)

```
PlatformUser (pu-001)
  └─ BusinessCustomer (bc-001) ── tenantId: tenant-savor-01
       └─ BranchCustomer (brc-001) ── branchId: downtown
```

All P8.9.7 CRM data is scoped to the `(userId, tenantId)` pair (BusinessCustomer level). No data leaks across tenants.

### Tab architecture

10 tabs via `useState<TabId>` — no URL routing, no page remount on tab switch. The profile header card remains visible at all times.

| Tab ID | Content |
|--------|---------|
| `overview` | KPIs, activity summary, relationship details, branch activity, quick links |
| `timeline` | Chronological event log (28 event types), filterable by type group |
| `orders` | Order history with status, items preview, totals |
| `reservations` | Reservation history with date/time/status/guests |
| `loyalty` | Tier, points, progress bar, rewards, transaction history |
| `reviews` | All reviews with star ratings, sentiment, owner replies |
| `notes` | Private tenant-scoped staff notes with inline create/edit/delete |
| `tags` | Customer segmentation tags with toggle UI |
| `marketing` | Channel prefs, campaign history, coupon list |
| `analytics` | LTV, behavioural patterns, favourite items, revenue trend, payment history |

## Production Migration Notes

When migrating from mock to real Django backend:

1. Replace each `if (USE_MOCK)` branch with `apiClient.get/post/patch/delete(endpoints.X)`
2. Endpoints defined in Section 35 of `docs/BACKEND_API_CONTRACT.md`
3. All tenant isolation enforced server-side (the frontend passes `tenant_id` as query param or body field)
4. `CustomerAnalytics` should be served from a materialized view or background job — not computed on request
5. `CustomerMarketing.campaigns` may come from a separate marketing service (e.g., Mailchimp, Brevo) via a backend aggregation layer
6. Notes mutations should emit timeline events (`admin_note` type) server-side for audit trail consistency
