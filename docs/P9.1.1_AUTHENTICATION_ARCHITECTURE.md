# P9.1.1 — Authentication Architecture (Module Definition)

> Phase C of P9.1.1. Defines Authentication as its own Platform Module,
> using the `ConfigModuleDefinition` shape from P9.0
> (`src/config/types.ts`) and the manifest extension points documented in
> `docs/P9.0.1_ARCHITECTURE_HARDENING.md` §H. Design only — the module
> already exists in code (`src/config/modules/authentication.ts`, 7
> fields); this document specifies its target shape once
> `docs/P9.1.1_AUTH_CONFIGURATION_SCHEMA.md`'s 41 proposed fields are
> implemented, plus the manifest metadata around it.
>
> Last updated: 2026-07-04

---

## 1. Module Manifest

Per `docs/P9.0.1_ARCHITECTURE_HARDENING.md` §H, there is no separate
"manifest" type — `ConfigModuleDefinition` *is* the manifest. Target shape:

```ts
export const AUTHENTICATION_MODULE: ConfigModuleDefinition = {
  id: 'authentication',
  name: 'Authentication',
  description: 'Login methods, OTP policy, lockout rules, session lifetime, and identity providers for the entire platform.',
  category: 'security',
  version: '2.0.0',           // bumped from 1.0.0 once the 41 proposed fields land — a schema-shape change, recorded via ConfigurationVersionManager
  icon: 'ShieldCheck',
  lifecycle: 'published',      // core toggles/OTP/lockout are 'published'; Section 9 (fraud/risk) fields ship as 'testing' or 'draft' individually — see §7 below
  permissions: { view: 'settings.view', edit: 'settings.manage' },
  featureFlag: undefined,      // authentication itself is never feature-flagged off wholesale; individual capabilities (social login, passkeys, fraud detection) carry their own featureFlag
  dependencies: [
    { moduleId: 'languages', type: 'soft', reason: 'OTP message language options read languages.supported.' },
    { moduleId: 'countries', type: 'soft', reason: 'Allowed/blocked/default country fields read the countries catalog.' },
    { moduleId: 'feature_flags', type: 'soft', reason: 'Social login / passkeys / magic links / fraud detection are individually feature-flagged.' },
    { moduleId: 'notifications', type: 'soft', reason: 'OTP delivery and verification-email templates route through the Notifications module\'s provider selection.' },
  ],
  sections: [ /* the 9 sections from docs/P9.1.1_AUTH_CONFIGURATION_SCHEMA.md */ ],
}
```

All four dependencies are `'soft'` — Authentication functions with sane
defaults if any of them is absent (a fresh registry with only
`authentication` registered still resolves every field to its own
`default`); they only enrich behavior (localized OTP copy, country
allow-lists, feature-flag-gated capabilities, provider-routed delivery)
when present. This matches Rule 12 (Dependency Rules) in
`docs/PLATFORM_ARCHITECTURE_PRINCIPLES.md` — no hard dependency is declared
because nothing about core authentication *requires* those other modules to
exist first.

## 2. Permissions

No new permission strings are introduced (Rule 3 — reuse the existing
catalog in `src/types/rbac.ts`):

| Action | Permission |
|---|---|
| View any authentication field | `settings.view` |
| Edit any authentication field | `settings.manage` |
| View/edit fields whose `audit.requireReason` is true (lockout policy, JWT TTL) | Same keys — the distinction is enforced by `audit.requireReason`, not a separate permission, per existing P9.0 convention (`authentication.max_login_attempts` already does this). |

A future RBAC refinement (tracked in `docs/PLATFORM_ROADMAP.md` P9.12) could
introduce a narrower `authentication.manage` permission distinct from the
general `settings.manage` if Authentication settings ever need to be
delegated to a role that shouldn't touch, say, Payments — not proposed now,
since Rule 3 disfavors inventing permissions ahead of a real need.

## 3. Dependencies

See §1. Import order in `src/config/index.ts` when these fields are
implemented: `languages`, `countries`, `feature_flags`, `notifications` must
all import before `authentication` (three of the four already do in the
current file; `authentication` currently imports before `feature-flags` —
**this import order will need to change** when the soft dependencies are
added, since `registry.register()` checks hard dependencies only, but soft
dependencies should still be registered first as a matter of convention so
`getDependents()`/documentation tooling reflects reality consistently).

## 4. Feature Flags

Authentication introduces four platform-level feature flags of its own
(field type `feature_flag`, living inside the `authentication` module
itself, not the `feature_flags` module — these are auth-specific
capabilities, not platform-wide rollout switches like
`feature_flags.website_builder`):

- `authentication.social_login_enabled`
- `authentication.passkeys_enabled`
- `authentication.magic_links_enabled`
- `authentication.fraud_detection_enabled` / `risk_scoring_enabled` / `vpn_detection_enabled` (Section 9)

This mirrors the existing precedent of `website_builder.custom_domain_enabled`
(a capability flag that lives inside its own module rather than the
platform-wide `feature_flags` module) — see
`src/config/modules/website-builder.ts`.

## 5. Health Checks

Per `docs/P9.0.1_ARCHITECTURE_HARDENING.md` §H, `healthCheck` is a
manifest field **not yet added** to `ConfigModuleDefinition` anywhere in the
registry — Authentication is the first module with a genuine need for one,
since it depends on external delivery providers (Phase F). When that
manifest field is added platform-wide, Authentication's health check
reports:

- **OTP delivery provider reachability** — can the configured SMS provider
  (Twilio/MessageBird/Vonage/Firebase — see Provider Architecture) currently
  send a message.
- **Email delivery provider reachability** — same, for verification/reset
  emails.
- **Token issuance latency** — p50/p99 time to issue an access+refresh
  token pair, surfaced to `docs/P9.1.1_MONITORING.md`'s "Provider Health"
  panel.
- **Lockout store availability** — once server-side lockout tracking exists
  (Security Architecture), whether that store (likely Redis or equivalent)
  is reachable; a Platform Administrator needs to know immediately if
  lockout enforcement has silently degraded to "always allow."

No implementation in P9.1.1 — this is the target shape for whichever future
phase adds `healthCheck` to `ConfigModuleDefinition`.

## 6. Configuration Groups

The 9 sections in `docs/P9.1.1_AUTH_CONFIGURATION_SCHEMA.md` map directly to
`ConfigSectionDefinition`s: Core Toggles, OTP, Login Methods, Login Attempts
& Lockout, Session & Tokens, Demo/Mock, Geography & Phone, Templates, Fraud
& Risk. This grouping is also the intended Console navigation structure —
each section becomes a tab or accordion group in the eventual Authentication
settings page (Rule 7 — UI generated from this structure, not hand-built).

## 7. Future Extension Points

- **New login method** — add a `boolean`/`feature_flag` field to "Login
  Methods" (Section 3) plus, if it needs its own provider, an entry in
  `docs/P9.1.1_PROVIDER_ARCHITECTURE.md`'s provider registry. No change to
  `ConfigurationService`/`ConfigurationResolver` required (Rule 11).
  Passkeys and Magic Links are already schema-reserved (§Section 3) for
  exactly this reason.
- **New fraud/risk signal** — add a field to Section 9, defaulted `false`/
  disabled, `lifecycle: 'testing'` until proven, `featureFlag`-gated.
- **New OTP delivery language** — no new field needed; the existing
  `authentication.otp.languages` multi-select grows by adding an option
  once the `languages` module supports it — a data change, not a schema
  change.
- **Per-branch auth policy** — every field's `inheritance.level` is
  currently `platform` or `tenant`; if a real branch-level need emerges
  (e.g. a shared-terminal branch wanting a shorter
  `session_timeout_minutes` than its tenant default), change that one
  field's owner level to allow branch overrides — the resolver already
  supports it (`ConfigurationResolver` walks the full four-level chain
  unconditionally); no architecture change required, only a schema edit to
  that field.

## 8. Audit Metadata

Per-field `audit` settings follow this module-wide convention:

- `trackHistory: true` for every field (no field in Authentication opts out
  — every change to auth policy is meaningful enough to audit).
- `requireReason: true` for anything that changes the platform's actual
  security posture: `max_login_attempts`, `lockout_duration_minutes`,
  `permanent_lock_threshold`, `jwt_access_ttl_minutes`,
  `jwt_refresh_ttl_days`, `demo_login_enabled`,
  `mock_authentication_enabled`, `blocked_countries`,
  `phone_normalization_strict`. Cosmetic/UX fields (templates, resend
  cooldown, country auto-detection) do not require a reason.
- `sensitive: true` for none of the fields in this module today — no
  `'secret'`-typed fields exist in Authentication itself (provider API keys
  live in the Provider Architecture's own configuration surface, Phase F,
  where `sensitive: true` does apply, following the `payments.stripe_secret_key`
  precedent from P9.0).

## 9. Versioning & Lifecycle

- **Version**: bump from `1.0.0` → `2.0.0` when the 41 proposed fields are
  implemented (a major schema-shape change, per
  `docs/P9.0.1_ARCHITECTURE_HARDENING.md` §E's module-version vs.
  field-write-audit distinction) — call
  `configurationVersionManager.recordVersion('authentication', 'P9.1.x: added login-method toggles, session/token policy, demo-mode controls, geography/phone_number restrictions, templates, and fraud/risk schema')`
  in the same change that ships the new fields.
- **Lifecycle** (per `docs/P9.0.1_ARCHITECTURE_HARDENING.md` §D):
  - `published`: Sections 1–8 (Core Toggles, OTP, Login Methods, Lockout,
    Session/Tokens, Demo/Mock, Geography/Phone, Templates) — these are
    well-understood, low-risk to expose immediately.
  - `testing`: Section 9 (Fraud & Risk) fields ship individually as
    `testing` until a real provider integration (Phase F) proves them out,
    then promote to `published` one field at a time, not as a block.
