# P8.8.11.2 — Intelligent Tenant Navigation & Context-Aware Header Audit

**Phase A — Pre-implementation audit**
**Scope:** TenantHeader, BranchHomepageClient, TenantHomepageClient, Website Builder nav model, Module Registry, Feature Flags, Branch/Tenant stores

---

## 1. Current Navigation Flow

```
useModuleNav()
  → useTenantStore(featureFlags) + getHeaderNav(tenant.businessTypes)
  → [{ href: '/menu', label: 'Menu' }, { href: '/reservation', label: 'Reservation' }, ...]
  → Already feature-flag filtered

TenantHeader (P8.8.11.1)
  → Reads moduleNav from useModuleNav()
  → Prepends hardcoded "Discover" item
  → Maps each href: /menu → /{tenantSlug}/{branchSlug}/menu
  → Renders nav links
```

---

## 2. Gaps in Current TenantHeader

### G1 — Nav builder is inline, not reusable
All nav construction logic lives inside `TenantHeader`. `BranchHomepageClient` and `TenantHomepageClient` each have their own parallel CTA logic — duplicate knowledge about ordering, reservations, and branch count.

### G2 — "Discover" label is wrong
Phase E requires a clearer label communicating leaving the current business. "Discover" is ambiguous. Should be "Explore Businesses" or similar.

### G3 — No business type badge (Phase F)
TenantHeader shows tenant name but no business-type indication (☕ Cafe, 🍽️ Restaurant, 🚚 Food Truck). This information lives in `tenant.businessTypes` and is already used in `BranchHomepageClient` for the accent color.

### G4 — No single vs. multi-branch intelligence (Phase D)
TenantHeader currently never shows a "Locations" nav item regardless of `branchCount`. It also never suppresses the Locations item for single-branch tenants. `branchCount` is readable from `getMarketplaceMeta(tenant.settings)?.branchCount` but is not consulted in TenantHeader at all.

### G5 — Duplicate CTA logic in heroes (Phase G)
`BranchHomepageClient.HeroSection`:
```tsx
// Inline — reads featureFlags from tenant.settings directly (not from store)
const featureFlags = (tenant.settings?.featureFlags as Record<string, boolean> | undefined) ?? {}
const hasReservations = featureFlags['reservations.enabled'] ?? false
// Then renders: View Menu | Reserve (conditional)
```
`TenantHomepageClient.HeroSection`:
```tsx
const isMultiBranch = meta.branchCount > 1
const primaryLabel = isMultiBranch ? 'Choose a Location' : isNonMenuType ? 'Visit Us' : 'View Menu'
```
These are independent implementations with different logic. Neither is aware of the full CTA priority (ordering + reservations → "Order Online").

### G6 — BranchHomepageClient reads feature flags from wrong source
`BranchHomepageClient` reads `tenant.settings?.featureFlags` directly (raw settings object), not from the resolved `featureFlags` store that merges module defaults + capability flags + tenant overrides. This means capability-derived flags (e.g., `ordering.enabled` derived from the `ordering` capability) may be missing.

### G7 — Website Builder navItems not yet consumed
`HomepageLayout.navItems?: TenantNavItemConfig[]` was added to the type in P8.8.11.1 but TenantHeader never reads it. The Website Builder hook point exists but is wired to nothing.

### G8 — Active state for non-branch nav items
`pathname.startsWith('/discover')` works correctly. But `pathname.startsWith(link.href)` where `link.href = '/{tenantSlug}#branches'` will never match (hash fragments are not in pathname). Locations item will never be active — acceptable since it's a section anchor, not a route.

### G9 — No scalable navigation builder
As new modules add nav items (events, gallery, loyalty), each page that renders CTAs must be updated independently. A single `buildTenantNavigation()` function eliminates this fragility.

### G10 — Logo links to `/{tenantSlug}` on branch page
When on `/{tenantSlug}/{branchSlug}`, the logo correctly links to `/{tenantSlug}`. When on `/{tenantSlug}` itself (tenant homepage), clicking the logo re-navigates to the current page. Minor UX friction but no functional bug.

## 3. Module Registry — Nav Item Coverage

| Module | Current navItems | Missing (future routes) |
|---|---|---|
| Restaurant | /menu, /reservation, /restaurant | /gallery, /events, /contact |
| Cafe | /menu, /reservation, /reviews, /loyalty, /promotions | /gallery, /events |
| Bar | (similar) | /events |
| Food Court | (similar) | |
| Food Truck | (similar) | /schedule |
| Mobile Cafe | (similar) | |

Nav items for routes that don't exist yet MUST NOT be added. The nav builder will only include items from `useModuleNav()` (which reads module navItems). When new routes are added to the registry, the nav will pick them up automatically.

## 4. Feature Flag Integration — Current

`useModuleNav()` reads `useTenantStore((s) => s.featureFlags)` — the fully resolved flag map. This is correct.

`BranchHomepageClient.HeroSection` reads `tenant.settings?.featureFlags` directly — this is WRONG because it bypasses the merge of module defaults + capability flags. Must be fixed to use the resolved flags from the store.

## 5. Branch Store — What's Available

```typescript
useBranchStore((s) => s.activeBranch)
// → Location | null
// .slug, .name, .address, .city, .phone, .lat, .lng, .is_active
// Does NOT have branchCount
```

`branchCount` comes from `getMarketplaceMeta(tenant.settings)?.branchCount` — accessible since `tenant` is in `useTenantStore`.

---

## 6. Tenant Store — Feature Flags

```typescript
useTenantStore((s) => s.featureFlags)
// → Record<string, boolean>
// Fully resolved: module defaults + capability flags + tenant overrides
// Populated after featureFlagsService.resolve(tenant) runs
// Empty {} during bootstrap (safe — useModuleNav handles this)
```

Also available: `useFeatureFlag(key: string): boolean` hook — reads `featureFlags[key] ?? false`.

---

## 7. Website Builder Navigation Model

`HomepageLayout.navItems?: TenantNavItemConfig[]` exists in the type (added P8.8.11.1). Each config entry has `key`, `enabled`, `order`, `label?`. When present, it controls:
- Which nav items are shown/hidden
- Display order
- Custom labels

This field is NOT yet persisted to the database. The Website Builder admin UI does not yet show a "Navigation" tab. Saving/loading `navItems` is a future backend feature (documented in Phase K).

---

## 8. Public URL Builder

`src/utils/public-url.ts` exports `buildPublicUrl` and `hrefToPublicUrl`. These are used by `PreviewButton` to convert admin-relative paths (`/menu`) to full public URLs (`/{tenantSlug}/{branchSlug}/menu`). This is a separate concern from navigation building — both do "href enrichment" but for different consumers. The navigation builder will NOT reuse `buildPublicUrl` to keep concerns separated.

## 9. Scalability Problems

| Problem | Impact |
|---|---|
| Nav logic inlined in TenantHeader | Hard to test, duplicate on each update |
| CTA logic in each hero component | N copies of the same business rule |
| No type-safe nav key enum | Free-form strings, typos possible |
| Website Builder config not consumed | Phase J never lands without this plumbing |
| Feature flags read from wrong source in heroes | Capability-derived flags can be wrong |

---

## 10. Future Backend Requirements

See Phase K below. Only one genuine backend requirement: persisting `HomepageLayout.navItems` via the existing layout save/publish API.

## 11. Implementation Plan

### Phase B: `src/utils/navigation.ts`
- `buildTenantNavigation(opts)` — pure function, no React
- `getSmartCTA(tenantSlug, branchSlug, featureFlags, meta)` — pure, no React
- `getBusinessTypeBadge(businessTypes)` — emoji + label
- Exported types: `TenantNavLink`, `SmartCTA`

### Phase C: Feature-flag filtering
Already done by `useModuleNav()`. `buildTenantNavigation()` receives pre-filtered items — no additional flag checking needed.

### Phase D: Branch awareness in `buildTenantNavigation()`
- If `branchCount > 1`: inject Locations item
- If `branchCount === 1`: no Locations item

### Phase E: "Explore Businesses" label
Replace "Discover" → "Explore Businesses" in `buildTenantNavigation()`.

### Phase F: Business type badge in TenantHeader
Read `tenant.businessTypes[0]`, render `☕ Cafe` etc. beside logo.

### Phase G: `getSmartCTA()` replaces inline hero CTA logic
Update `BranchHomepageClient.HeroSection` and `TenantHomepageClient.HeroSection` to use `getSmartCTA()`. Also fix the feature flag source bug.

### Phase H: Active state audit
- Marketplace: exact match `pathname === '/discover'`
- Business routes: `pathname.startsWith(branchAwareHref)`
- Locations (hash): never active (acceptable)

### Phase I: Website Builder integration
`buildTenantNavigation()` accepts `layoutNavConfig?: TenantNavItemConfig[]` and applies it.

### Phase J: TenantHeader is dumb renderer
All logic moves to `buildTenantNavigation()`. TenantHeader only renders.

### Phase K: Backend contract
`HomepageLayout.navItems` needs persistence. Document requirement.
