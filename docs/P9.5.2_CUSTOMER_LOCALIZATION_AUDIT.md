# P9.5.2 — Customer Localization Audit

> Phase A of P9.5.2. Scope: customer-facing surfaces only (marketplace,
> menu, cart, checkout, reservation, customer dashboard, order tracking) —
> Business Console and Platform Administration are explicitly out of scope
> for this phase (P9.5.3). Numbers below are grep-based counts against the
> repository at the start of this phase, continuing the same audit
> methodology `docs/P9.5.1B_LOCALIZATION_AUDIT.md` established.
>
> Last updated: 2026-07-05

---

## 1. Starting state (before this phase)

At the end of P9.5.1B, exactly 7 files (the authentication flow + root
layout) consumed the localization runtime. Every customer-facing commerce
surface — Menu, Cart, Checkout, Reservation, Dashboard, Order Tracking,
Home/Discover — was still 100% hardcoded English, same as every other
un-migrated page in the app.

```
Customer-facing page.tsx files (excluding console/platform-admin): 42
useTranslations()/getTranslations() call sites in those files (start): 0
toast.success()/toast.error() call sites in customer surfaces:        ~30
z.object() validation schemas in customer surfaces:                    4 (login/register already done; checkout/reservation/complete-profile remained)
```

## 3. Category-by-category findings (within migrated surfaces)

- **Buttons/labels/placeholders**: fully covered in the 6 migrated files —
  every literal string in JSX replaced with a `t()` call and a real
  `validation`/`menu`/`cart`/`checkout`/`reservation`/`dashboard`-namespace
  key in all 3 shipped locales.
- **Validation** (Phase L): `checkout` and `reservation` schemas now store
  `validation` namespace keys (`required`, `invalid_email`,
  `invalid_phone`) instead of literal English zod messages, resolved via
  `tValidation()` at the error-render call site — same pattern
  `docs/P9.5.1B_APPLICATION_LOCALIZATION.md` established for login/register.
  `complete-profile`'s schema (a customer-facing form) was **not** migrated
  this phase.
- **Notifications/toasts** (Phase I): every toast in the 6 migrated files
  now calls `t()`/`tNotifications()`. Toasts in `complete-profile`,
  `verify`, `dashboard/settings`, `dashboard/addresses` remain literal.
- **Accessibility** (Phase K): `aria-label`s in the migrated files (quantity
  controls, favorite toggle, close button, search input, view-mode toggle,
  OTP-adjacent patterns already done in P9.5.1B) are localized. A full
  `aria-label`/`aria-describedby` audit across the ~110 still-unmigrated
  customer files was **not** performed — see §4.
- **RTL** (Phase N): verified — none of the 6 migrated files contain a
  physical-direction Tailwind class (`ml-`, `mr-`, `pl-`, `pr-`, `left-`,
  `right-`); all already used logical properties (`ms-`, `me-`, `ps-`,
  `pe-`, `start-`, `end-`) before this phase, so no CSS changes were needed
  — only the text content itself was localized. See
  `docs/P9.5.2_CUSTOMER_LOCALIZATION.md` §5 for the fuller RTL verification
  method and its limits (static analysis, not visual/browser testing).
- **Formatting** (Phase M): no hand-rolled date/number/currency formatting
  was introduced or found in the migrated files — `formatCurrency()`
  (already `Intl.NumberFormat`-backed, pre-existing) continues to be used
  unchanged; the new `menu.itemsFound` key is the first production use of
  ICU plural syntax (`{count, plural, ...}`), which resolves through
  `Intl.PluralRules` internally via `next-intl`/`use-intl` — no new
  formatting code was written, the existing runtime's ICU support was used
  as designed.
- **Metadata** (Phase J): `src/app/menu/page.tsx`'s `export const metadata`
  (title/description/OG/Twitter) was **not** converted to
  `generateMetadata()` + `getTranslations()` this phase — it remains
  static English. This is a real gap, not silently skipped: converting a
  static `metadata` export to the dynamic `generateMetadata` async function
  is a larger, separate change (affects static rendering/caching
  characteristics) that warranted its own review pass rather than a
  drive-by edit alongside the UI text migration.

## 4. What remains (honest accounting)

- **Marketplace (Phase B)**: `src/app/page.tsx` (home) and
  `src/app/discover/page.tsx` — not migrated. These are large,
  marketing-copy-heavy pages (hero sections, category showcases, business
  cards, promotions) where a full migration is a substantial, separate
  effort in its own right.
- **Dashboard sub-pages (Phase G)**: `orders`, `reservations`, `favorites`,
  `addresses`, `settings` — not migrated. The dashboard's main landing
  page is done; its 5 child routes are not.
- **Order Tracking (Phase H)**: not migrated — status timeline, driver/ETA
  copy, support buttons all remain literal English.
- **`complete-profile` page**: a customer-facing form with its own zod
  schema and toasts — not migrated (Phase E/L/I gap).
- **Metadata (Phase J)**: no page's `<title>`/OpenGraph/Twitter metadata
  is locale-aware yet, on any page (migrated or not) — this phase did not
  touch metadata generation at all.
- **Full accessibility audit (Phase K)**: only the `aria-label`s inside the
  6 migrated files were addressed; a systematic pass across every
  `aria-label`/`aria-describedby`/`aria-live` in the ~36 remaining
  customer-facing pages was not performed.
- **Structured/breadcrumb metadata (Phase J)**: no breadcrumb component was
  found to be shared/localized-in-this-pass across customer routes; not
  audited separately from the page-metadata gap above.

**Do not read the 6 fully-migrated surfaces as "customer experience
complete."** Per the task's own instruction: report accurately — Menu,
Cart, Checkout, Reservation, and the Dashboard landing page are
localization-ready; Home, Discover, Order Tracking, the 5 Dashboard
sub-pages, and `complete-profile` are not, and remain English-only exactly
as they were before this phase, with zero behavior change (nothing broke,
nothing was removed).

See `docs/P9.5.2_CUSTOMER_LOCALIZATION.md` for the full migration report,
coverage statistics, and the prioritized remaining-work list.
