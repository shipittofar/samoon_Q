# P9.1.2 — Authentication Runtime Integration

> First real consumer of the P9.0 Platform Configuration Foundation.
> Authentication runtime now resolves its operational values through
> `ConfigurationService` instead of hardcoded literals. No UI redesign, no
> visual change, no route change, no endpoint change — every default value
> below is identical to what was hardcoded before, so default behavior is
> unchanged; only the *source* of each value changed.
>
> Last updated: 2026-07-04

---

**Not wired this phase (documented, not silently dropped):**

- `authentication.guest_checkout_enabled` — registered (schema exists), but checkout has no auth gate anywhere to attach it to, and touching checkout flow/routing is outside this phase's file scope (`docs/P9.1.1_IMPLEMENTATION_PLAN.md`'s P9.1.2 file list doesn't include checkout). Remains schema-only pending a checkout-focused phase.
- `authentication.otp.length` and `authentication.jwt_access_ttl_minutes` — already registered in P9.0, still have no live runtime consumer. OTP length is implicitly hardcoded as 6 in every OTP input component (`OTPInput`, the 6-box array in `verify-otp/page.tsx`) — changing those to read the config value would touch the input rendering itself (a visual change), which this phase's brief explicitly forbids ("No visual changes"). Access token TTL has no frontend consumer because token expiry is set by whatever issues the token (the backend, or the static mock token) — the frontend never computes it. Both remain documented gaps for a phase whose brief permits touching those specific rendering/token-issuance code paths.
- `authentication.lockout_duration_minutes` / `authentication.max_login_attempts`'s *lockout* semantics — `max_login_attempts` is now wired as the rate limiter's count (see table above), but no lockout *duration* enforcement exists anywhere in the frontend to attach `lockout_duration_minutes` to (per the P9.1.1 audit, this requires a real backend). Unchanged from before this phase.
- `PASSWORD_RESET_LIMIT` (3/hour, `src/lib/rate-limit.ts`) — no config field was proposed for this in `docs/P9.1.1_AUTH_CONFIGURATION_SCHEMA.md`, so none was invented ad hoc here (Rule 10 — don't add speculative fields). Left hardcoded.

## 2. Phase B/C — Configuration integration

Every field consumed above lives in the single `authentication` module
(`src/config/modules/authentication.ts`, bumped `1.0.0` → `1.1.0`), read
exclusively through `configurationService.resolveField()` /
`useConfigurationField()` — no direct registry access anywhere in the
runtime code (per `docs/PLATFORM_ARCHITECTURE_PRINCIPLES.md` Rule: only
`ConfigurationService` is a sanctioned entry point).

### Known limitation: platform-scope-only resolution in `auth.service.ts`

`src/services/auth.service.ts` is a plain service module — it has no access
to `useTenantStore` the way React hooks do, and threading a tenant scope
through every exported function would be a larger refactor than "replace
configuration sources." Its `authFlag()` helper therefore resolves every
field at **platform scope** (`{}`) only.

This surfaced a real design bug during implementation: three fields
(`phone_login_enabled`, `email_login_enabled`, `guest_checkout_enabled`)
were initially registered as **tenant-owned** per
`docs/P9.1.1_AUTH_CONFIGURATION_SCHEMA.md`'s proposal. Per
`ConfigurationResolver`'s inheritance model, a tenant-owned field resolved
with an empty scope can never see an override — there is no way to set a
platform-level override for a field owned at `tenant` level (correctly
rejected by the P9.0.1 direction-check hardening). Registering them
tenant-owned while resolving them at platform scope would have made the
fields **silently inert** — a Platform Administrator could "change" them
with no runtime effect, exactly the kind of decorative-schema problem the
P9.1.1 audit flagged for the *original* 7 fields.

**Fix applied**: all three fields were registered `inheritance.level:
'platform'` instead, matching what `auth.service.ts` can actually resolve
today. Tenant-level override remains the eventual target (per the P9.1.1
schema doc) but requires first threading a tenant scope through
`auth.service.ts` — tracked below as remaining work, not silently dropped.

The client-component pages (`verify/page.tsx`, `verify-otp/page.tsx`,
`login/page.tsx`) use `useConfigurationField()`, which *does* resolve
tenant/branch/user scope automatically via the existing store selectors —
so once a field's `inheritance.level` is promoted to `tenant` and
`auth.service.ts` is refactored to accept scope, the page-level hooks need
no changes at all.

## 3. Phase D — Feature switches: graceful failure

Every gate added throws a plain `Error` with a short machine-readable
message (`'authentication_disabled'`, `'otp_disabled'`,
`'phone_login_disabled'`, `'email_login_disabled'`,
`'registration_disabled'`, or the pre-existing `'Invalid credentials'` for
a disabled demo-login path) — never a stack trace, never an unhandled
rejection. Every call site already routes through React Query mutations
(`useLogin`, `useSendOTP`, `useVerifyOTP`, `useRegister` in
`src/hooks/index.ts`) whose `onError` handlers show a generic, pre-existing
toast message regardless of the specific error — this was true before
P9.1.2 and required no changes: the existing UX (a toast, not a crash) is
exactly the "fail gracefully, display existing UX, never crash" contract
Phase D asked for, verified by a dev-server smoke test (§6) confirming
`/login`, `/register`, `/verify`, `/verify-otp`, `/forgot-password`, and
`/complete-profile` all render `200` with no error markers.

`authentication.maintenance_mode` was not introduced as a separate field —
the platform already has `system.maintenance_mode` (P9.0's `system`
module); duplicating it under `authentication` would violate Rule 3
(Single Source of Truth). `authentication.enabled` is the auth-specific
complement to it, not a replacement.

## 4. Phase E — Validation

No duplicated validation logic was introduced. `authentication.otp.max_verify_attempts`
reuses the existing `ConfigurationValidator` numeric range rules
(`min: 1, max: 10`) already exercised by the P9.0 test suite — no new
validation code paths were written; only new *field* registrations, which
`ConfigurationValidator.validate()` already handles generically for any
`'number'`/`'boolean'`-typed field.

## 5. Phase F — Session runtime

Only `authentication.jwt_refresh_ttl_days` was wired this phase (the
cookie mirror in `axios.instance.ts`). `sessionTimeout`, `rememberMeLifetime`,
`maxDevices`, and `logoutAllBehavior` remain schema-only proposals in
`docs/P9.1.1_AUTH_CONFIGURATION_SCHEMA.md` §5 — none has a runtime home yet
because none of that session-registry/device-list machinery exists in the
frontend (per the P9.1.1 Security Architecture doc, this requires a real
backend session registry). Wiring them now would mean inventing new
behavior, not replacing a hardcoded value — explicitly out of scope
("Business behavior should remain identical using default values").

## 6. Phase G — Mock mode: reviewed, preserved, now configuration-aware

Mock mode was not removed or redesigned. `mockActive()` in
`auth.service.ts` is `USE_MOCK_ENV && authFlag('authentication.mock_authentication_enabled')`
— both must be true, exactly preserving today's behavior (both default
true). Demo accounts continue working identically; a full test suite run
(`src/test/p9-1-2-runtime-integration.test.ts`, 10 new tests) and a
dev-server smoke test confirmed:

- `authService.login()`/`sendOTP()`/`verifyOTP()` succeed with default
  configuration, identical to pre-P9.1.2 behavior.
- Setting `authentication.demo_login_enabled` to `false` makes known demo
  credentials behave as invalid (login) or as a new user (OTP verify),
  without disabling the rest of mock mode.
- Setting `authentication.mock_authentication_enabled` to `false` makes the
  service fall through to the real-API branch (proven by the
  `email_login_disabled` gate — which only exists on that branch — firing
  instead of a mock success).
- `/login` renders the demo account grid and `/verify` renders the mock-mode
  dev hint, both under default configuration, confirmed via a live
  dev-server smoke test (`curl` against a running `next dev` instance, no
  error markers in any of six auth page responses).

## 7. Phase H — Backend contract compatibility

No new endpoint was invented and no existing endpoint documented in
`BACKEND_API_CONTRACT.md` §2 was changed. Of the six reconciliation items
`docs/P9.1.1_IMPLEMENTATION_PLAN.md` §Phase H listed, this phase
deliberately resolved **zero** of them on the runtime side — every new
field's default was set to match the *previously hardcoded frontend
value* (3 attempts, 7-day refresh, 60s cooldown), not the backend
contract's documented value (5 attempts, 30 days), specifically because
this phase's mandate is "business behavior should remain identical," and
jumping straight to the backend contract's numbers would have been a
visible behavior change (a real one: users would see 5 "attempts
remaining" instead of 3). Reconciling to the backend contract's values
is deferred to whichever phase first talks to a real backend (P9.1.6+ per
the Implementation Plan) — changing a default now, with no backend to
match it against, would be reconciling against nothing.

## 8. Remaining P9.1.x work

  `phone_login_enabled`/`email_login_enabled`/`guest_checkout_enabled` can
  become genuinely tenant-overridable (currently platform-only — see §2).
- Wire `authentication.guest_checkout_enabled` once a checkout auth gate
  exists to attach it to.
- Reconcile the six Phase H numeric/design mismatches against a real
  backend once one exists.
- Server-side lockout/rate-limiting, device trust, session registry
  (Security Architecture §1–8) — all require a real backend, out of this
  frontend repository's boundary.
- `authentication.otp.length` / `jwt_access_ttl_minutes` remain
  schema-only pending a phase whose brief permits touching OTP input
  rendering / token issuance.
