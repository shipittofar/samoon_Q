# P10.5.2 — Fix `dashboard:access` Authorization Hook Mismatch

Fixes the `Header.tsx`/`app/dashboard/layout.tsx` bug identified in
`docs/P10.4.8_LEGACY_COMPATIBILITY_AUDIT.md` Phase G, re-confirmed
untouched through P10.4.11, and named as an "Immediate" recommendation
in `docs/P10.5.1_AUTHORIZATION_ARCHITECTURE_AUDIT.md`.

## Root Cause

`dashboard:access` is not a role-scoped CRUD permission like
`orders.view` or `staff.manage` — it's a structural "may this identity
reach `/console` at all" gate that depends on whether the actor is an
eligible Owner of the active tenant, or holds at least one active
`StaffAssignment`. `ROLE_PERMISSION_MAP` (`src/services/permission.service.ts`)
never contains the literal `'dashboard:access'` for any role — confirmed
by `grep -c "'dashboard:access'" src/services/permission.service.ts` →
`0`, including the Owner entry (which itself doesn't grant it either,
since Owner access flows through the ownership short-circuit in
`ownership-resolution.service.ts`, never through the map).

`usePermission(permission)` (`src/hooks/index.ts`) checks exactly one
thing: whether the resolved `P7Permission[]` array (from
`usePermissions()`, itself built from `ROLE_PERMISSION_MAP` +
ownership/`StaffAssignment` resolution) includes the given string. Since
`'dashboard:access'` can never appear in that array — not for Owners,
not for Staff, not for anyone — `usePermission('dashboard:access')` was
**structurally guaranteed to always return `false`**, for every account,
regardless of real console eligibility.

`Header.tsx` and `app/dashboard/layout.tsx` called this always-false
check to decide whether to render the "Business Console" nav link,
so the link never rendered for anyone — including Owners and Staff who
genuinely had console access (verifiable separately, correctly, through
`AuthGuard`/`useHasDashboardAccess()` on the actual `/console` route
itself).

## Why `dashboard:access` Must Remain Outside `ROLE_PERMISSION_MAP`

Adding `'dashboard:access'` as an entry in `ROLE_PERMISSION_MAP` (e.g.
granting it to `admin`/`manager`/etc.) would let a role gain `/console`
access purely by role membership, decoupled from whether that specific
identity holds a real, currently-eligible `StaffAssignment` or Owner
record. This is exactly the class of bug P10.3.1 fixed: a
suspended/removed Staff member, or a Staff/Owner of an archived tenant,
must lose console access immediately, not just lose their listed
CRUD permissions. `useHasDashboardAccess()` enforces this by re-checking
`isOwnerEligible()`/`isStaffMemberEligible()`/`isTenantEligible()` and
`StaffAssignment` existence on every evaluation — a static
`ROLE_PERMISSION_MAP` entry could never do that; role membership alone
says nothing about eligibility or assignment status. `useHasDashboardAccess()`
is therefore the only correct source of truth for `/console` visibility,
and this phase intentionally did not touch `ROLE_PERMISSION_MAP`,
`permission.service.ts`, or `usePermissions()` to preserve that
separation.
