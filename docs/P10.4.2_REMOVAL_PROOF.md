# P10.4.2 — Legacy RBAC Removal Proof Audit

Verification only. No code, tests, or configuration was modified to
produce this document. Every candidate from
`docs/P10.4.1_LEGACY_AUDIT.md` was re-verified from scratch against
current source — imports, re-exports, dynamic imports, type-only
imports, tests, docs, build/eslint config — not assumed correct from the
prior report. **Three of P10.4.1's "Dead code" classifications are
corrected here** after finding real test dependencies P10.4.1's grep
sweep missed; see §0.

## §0 — Corrections to P10.4.1

P10.4.1 classified `branchRoles`, `roleAssignments`, and `customRoles`
as "Dead code... zero consumers anywhere" based on a search that
excluded `src/test/`. Re-running the same search **including** tests
finds:

- `src/test/phase8-5-enterprise-rbac.test.ts` — 15 direct references,
  exercising `setBranchRoles()`/`getRolesForBranch()`/
  `removeBranchRoles()` across dedicated `it()` blocks (a full
  "Branch-Level Role Overrides" contract test suite).
- `src/test/phase8-6-enterprise-rbac.test.ts` — 46 direct references
  (of 60 total `it()` blocks in the file), exercising
  `addRoleAssignment()`/`updateRoleAssignment()`/`removeRoleAssignment()`/
  `getAssignmentsForUser()`/`getAssignmentsForTenant()`/
  `addCustomRole()`/`updateCustomRole()`/`removeCustomRole()`/
  `getCustomRolesForTenant()`, plus a source-text check
  (`expect(storesSrc).toContain('roleAssignments')` /
  `'customRoles'`) that would fail if the fields were renamed or
  removed.
- `src/test/p10.3-logout-cleanup.test.ts` and
  `src/test/p10.3.2-cache-isolation-audit.test.ts` (this program's own
  P10.3 work) also assert `branchRoles`/`roleAssignments`/`customRoles`
  are present and correctly reset by `_resetStore()`.

**Correction: these three fields are not "zero consumers."** They have
zero *application/UI* consumers (P10.4.1's core finding — no page, hook,
or component calls their actions — remains accurate), but they have
substantial, dedicated *test* consumers. This is the difference between
"dead code" and "a built-but-unwired feature with a maintained test
contract." Reclassified below from Dead Code → **KEEP** (not safe to
delete — see §4).

Additionally, P10.4.1 stated `rbacService.getPermissions()` has "zero
consumers." Re-verification finds it IS called in
`src/test/phase4-e2e.test.ts:399` (`rbacService.getPermissions('admin')`,
asserted `.length` > 0). Reclassified from Dead Code → **Test only,
KEEP** (§4).

`hasAnyPermission()`/`hasAllPermissions()` (the standalone
`permission.service.ts` functions): P10.4.1 was correct that the
`hooks/index.ts` import of these is dead, but did not check whether the
functions themselves have test coverage. They do — `src/test/phase7-rbac.test.ts`
calls both via dynamic import across 12 assertions. The functions are
**not** dead; only the specific unused import statement in
`hooks/index.ts` is. Narrowed accordingly in §1/§4.

`rbacService.p7`: re-verified, genuinely zero references anywhere
including tests. P10.4.1's classification stands.

`useHasPermission()`: re-verified, zero `.tsx`/`.ts` application callers
confirmed (matches P10.4.1), but it DOES have two test dependencies:
`src/test/phase1b.test.ts:211` (`typeof useHasPermission).toBe('function')`)
and `src/test/phase4-ops-advanced.test.ts:423` (source-text existence
check: `expect(src('hooks/index.ts')).toContain('export function useHasPermission')`).
Removing the function would fail both tests. P10.4.1's "Dead code /
Can be removed" verdict is corrected to "Dead code (application) /
requires test updates before removal" — see §4 and §6.

`Permission` type (types/index.ts) and the duplicate `Role` type
(types/index.ts): P10.4.1 called these dead/duplicate but did not check
for source-text test assertions. `src/test/phase7-rbac.test.ts:1016-1022`
asserts `types/index.ts`'s raw source contains `"export type Role ="`
and `"'orders.view'"` — both strings appear **exactly once** in that
file, at the `Role` and `Permission` definitions respectively (verified
by `grep -n`). Removing either type breaks the corresponding test
assertion. Corrected below.

## Phase D — Removal Safety Classification

### SAFE TO DELETE
Immediate, no test or build impact.

1. **`rbacService.p7`** (`src/services/rbac.service.ts:78`) — zero
   references of any kind (application, test, docs, config).
2. **The `hasAnyPermission`, `hasAllPermissions` names in
   `hooks/index.ts:58`'s import statement** — dead import only; the
   functions themselves are kept and used elsewhere (`permission.service.ts`
   test suite). Removing just these two names from that one import line
   has zero effect on any test (already confirmed via ESLint's own
   "defined but never used" warning, which will disappear once removed).

### SAFE AFTER MIGRATION
Still participates in a compatibility layer, or requires a coordinated
test update in the same change (not a blind deletion).

3. **`useHasPermission()`** — safe to delete from the application's
   perspective (zero UI callers), but requires updating
   `phase1b.test.ts` (drop the import + contract test) and
   `phase4-ops-advanced.test.ts` (drop the source-text existence check)
   in the same change. Cannot be removed alone under "do not modify
   tests."
4. **`rbacService.getPermissions()`** — same shape: zero application
   callers, one real test assertion (`phase4-e2e.test.ts:399`) that must
   be updated or removed alongside it.
5. **`Permission` type** (`types/index.ts:773`) — zero type-checker
   dependents, but `phase7-rbac.test.ts:1022`'s source-text assertion
   for `'orders.view'` must be accounted for (either the string
   survives removal by coincidence elsewhere in the file, which it does
   not today, or the test needs updating).
6. **Duplicate `Role` type** (`types/index.ts:803`) — requires (a)
   redirecting `stores/index.ts:32`'s import to `@/types/rbac`'s `Role`
   and (b) accounting for `phase7-rbac.test.ts:1016`'s source-text
   assertion. This is a consolidation, not a deletion — after
   consolidation there is still exactly one `Role` type, just
   re-exported instead of duplicated (mirroring how `P7Permission`
   already works).
7. **`legacyGranted` / `rbacService.hasPermission()` / `LegacyPermission`
   type** (per P10.4.1 §5/§7) — confirmed still live and required inside
   `useHasDashboardAccess()` for `staff@savor.com`/`multirole@savor.com`
   (P10.0 id-space gap). Must remain until that gap is closed. Not
   reclassified by this audit — P10.4.1's finding stands.

### KEEP
Still required, or has a maintained test contract that makes removal
unsafe under this phase's "do not modify tests" constraint.

8. **`branchRoles`, `roleAssignments`, `customRoles`** (all fields +
   all 12 associated store actions) — reclassified from P10.4.1's "Dead
   code" per §0. 64 test assertions across 4 files depend on these
   fields existing and behaving exactly as implemented. **Do not
   delete** without a separate, explicit decision to also delete or
   rewrite `phase8-5-enterprise-rbac.test.ts` and
   `phase8-6-enterprise-rbac.test.ts` (51 and 60 `it()` blocks
   respectively — these are not small files to lose).
9. **`ROLE_PERMISSION_MAP`**, **`tenantRoles`**, **`getRolesForTenant()`**,
   **`PermissionGuard`**, **`usePermissions()`/`usePermission()`/
   `useAnyPermission()`/`useAllPermissions()`** — all confirmed Required
   in P10.4.1, re-confirmed here by the same evidence (56 `PermissionGuard`
   consumers, `usePermissions()` as the sole permission-resolution entry
   point). No change.
10. **`hasAnyPermission()`/`hasAllPermissions()` functions in
    `permission.service.ts`** (distinct from the dead import in
    `hooks/index.ts`, item 2 above) — 12 test assertions in
    `phase7-rbac.test.ts`. Keep.

### UNKNOWN
Static analysis cannot prove safety; explained, not guessed.

11. **`usePermission('dashboard:access')` in `Header.tsx`/`dashboard/layout.tsx`**
    (P10.4.1 §12) — proven structurally always-`false` (the string is
    never added to `ROLE_PERMISSION_MAP`/`ALL_PERMISSIONS`), but this
    audit cannot determine from static analysis alone whether any

    intended UI behavior requires product input this audit cannot

## Phase E — Hidden Dependency Findings

- **Zustand persistence**: `useRbacStore` persists under the key
  `'savor-rbac'` (verified `stores/index.ts:630`) and includes
  `branchRoles`/`roleAssignments`/`customRoles` in its serialized shape
  even though nothing writes to them at runtime today — a real device's
  `localStorage` for this app would carry empty arrays for these fields
  forever unless a future feature starts using them. No cleanup risk
  (empty arrays persist harmlessly), but worth noting for anyone
  designing a migration that changes the store's shape — persisted
  clients with an old shape would need a migration function if these
  fields' types ever change.
- **React Query**: no query key or `queryFn` in `hooks/index.ts`
  references any of this audit's candidates — confirmed by the same
  `usePermissions()`/`assertOwnership*` trace done in P10.3.2.
- **Module Registry / Platform modules**: `src/platform-admin/permissions.ts`
  explicitly documents itself as a separate system that "never calls
  `usePermissions()`" (verified comment, unchanged since P10.2.2) — no
  candidate in this audit is referenced there.
- **Middleware**: `middleware.ts` was checked for any of the candidate
  symbols — no matches.
- **Error boundaries / Suspense**: none of the candidates are referenced
  inside any `ErrorBoundary` or `Suspense` boundary component.
- **Dev tools**: no `useRbacStore` devtools middleware wraps
  `branchRoles`/etc. beyond the standard `persist` middleware already
  covered above.

## Phase H — Recommended Removal Order (for P10.4.3, not executed here)

**Step 1 — Remove `rbacService.p7`**
Reason: Zero references anywhere (application, test, docs, config).
Risk: None.

**Step 2 — Remove the dead `hasAnyPermission`/`hasAllPermissions` import
from `hooks/index.ts:58`**
Reason: Confirmed unused import; the underlying functions remain
exported from `permission.service.ts` and keep their test coverage
untouched.
Risk: None.

**Step 3 — Remove `useHasPermission()`, together with its two test
references** (`phase1b.test.ts`'s import/contract test,
`phase4-ops-advanced.test.ts`'s source-text check)
Reason: Zero application callers; test-only existence checks with no
behavioral coverage.
Risk: Low — must be a single coordinated change (function + both test
files) or CI breaks.

**Step 4 — Remove `rbacService.getPermissions()`, together with
`phase4-e2e.test.ts:399`'s assertion**
Reason: Zero application callers; the one test assertion checks a
result shape, not a security property.
Risk: Low — same coordination requirement as Step 3.

**Step 5 — Consolidate the duplicate `Role` type**: redirect
`stores/index.ts:32`'s import to `@/types/rbac`, remove
`types/index.ts:803`'s duplicate definition, add a re-export matching
the existing `P7Permission` pattern, update
`phase7-rbac.test.ts:1016`'s assertion if its exact string match no
longer holds.
Reason: Removes a genuine duplicate-source-of-truth risk.
Risk: Low-Medium — touches a shared type import; run the full
type-check before merging.

**Step 6 — Remove the `Permission` type**, accounting for
`phase7-rbac.test.ts:1022`'s `'orders.view'` string assertion.
Reason: Zero type-checker dependents; fully superseded by `P7Permission`.
Risk: Low.

**Step 7 — Decide the fate of `branchRoles`/`roleAssignments`/
`customRoles` before touching them at all.**
This is explicitly NOT a removal step — it requires a product decision
(is branch-level role overrides / custom role templates still a planned
P10.4 feature?) before any code or test changes. If the decision is "no
longer planned," removing this requires rewriting or deleting
`phase8-5-enterprise-rbac.test.ts` and `phase8-6-enterprise-rbac.test.ts`
(111 combined `it()` blocks) as its own dedicated phase — never bundled
with an unrelated cleanup step.

**Never scheduled for removal by this audit:** `legacyGranted`,
`rbacService.hasPermission()`, `LegacyPermission` type, `tenantRoles`,
`ROLE_PERMISSION_MAP`, `getRolesForTenant()`, `PermissionGuard`,
`usePermissions()`/`usePermission()`/`useAnyPermission()`/
`useAllPermissions()` — all confirmed Required or Temporary
compatibility still in active use.
