## Architecture — Phase Map

### Phase B (Platform vs Tenant Identity)
- Platform pages (`/`, `/discover`, `/admin`, `/dashboard`) → `<Header />` (unchanged)
- Tenant pages (`/{tenantSlug}/*`) → `<TenantHeader />` (new)
- The separation is implemented at the render-site level (each client component chooses which header to render)

### Phase C (Tenant Logo)
```tsx
// Primary — business logo
<Link href={`/${tenantSlug}`}>
  {logoUrl ? (
    <Image src={logoUrl} fill ... />  // tenant custom logo
  ) : (
    <>
      <div className="... bg-gradient-to-br from-orange-400 to-orange-600">
        <span>{tenant.name.charAt(0)}</span>  // tenant initial
      </div>
      <span>{tenant.name}</span>  // tenant name
    </>
  )}
</Link>

// Secondary — platform signature
<Link href="/discover" className="text-[9px] ... text-[var(--fg-subtle)]">
  Powered by
  <span className="text-[11px] font-semibold">Savor</span>
</Link>
```

### Phase D (Navigation Structure)
Default nav order: Discover (always first) + module navItems in module-defined order.
For Restaurant: Discover → Menu → Reservation → About
For Cafe: Discover → Menu → Reservations → Reviews → Loyalty → Promotions
Items are generated dynamically — no hardcoding.

### Phase E (Dynamic Navigation)
Navigation is generated from `useModuleNav()` which reads:
- Active module from `tenant.businessTypes`
- Feature flags from `featureFlagsService.resolve(tenant)`
- Returns only items where `featureFlagKey` is not `false`

The TenantHeader receives the filtered list and converts hrefs to branch-aware paths:
```typescript
const branchNavLinks = moduleNav.map((item) => ({
  ...item,
  href: branchSlug
    ? `/${tenantSlug}/${branchSlug}${item.href}`
    : `/${tenantSlug}${item.href}`,
}))
```

### Phase F (Feature-aware Navigation)
Automatic — `useModuleNav()` already hides items when their feature flag is false.
- `reservations.enabled = false` → Reservations hidden
- `reviews.enabled = false` → Reviews hidden (Cafe module)
- `loyalty.enabled = false` → Loyalty hidden

No changes needed to the hook or registry.

### Phase G (Branch Awareness)
Every nav item href is converted from a relative segment (`/menu`) to a full
branch-scoped path (`/brew-cafe/midtown/menu`) at render time:
```typescript
href: branchSlug
  ? `/${tenantSlug}/${branchSlug}${item.href}`   // branch context
  : `/${tenantSlug}${item.href}`                  // tenant-only context
```
Active state correctly uses `pathname.startsWith(fullHref)`.

### Phase H (Mobile Navigation)
Mobile drawer contains:
- "Powered by Savor" link at top
- All nav items with branch-aware hrefs
- Theme toggle + language switcher
- Sign In / Get Started when unauthenticated
Mirrors desktop behavior identically.

### Phase I (Active Navigation)
```typescript
const isActive = (href: string) =>
  href === '/discover'
    ? pathname === '/discover'   // exact match for platform link
    : pathname.startsWith(href)  // prefix match for business pages
```
Branch switching preserves the active state because the active item is derived
from the current pathname, not stored state.

Added to `HomepageLayout`:

The Website Builder admin UI (Phase J full implementation) will read/write this field.
When `navItems` is set, TenantHeader can merge it with the module nav for custom
ordering and visibility. This hook point is ready for the next sprint.

## BACKEND_API_CONTRACT.md — No Changes Required

The backend API does not expose a navigation configuration endpoint. Navigation is
derived client-side from the module registry and feature flags, both of which are
already populated from the backend.

When the Website Builder Phase J full implementation ships, the `HomepageLayout`
API (which already persists `sections`, `hero`, `theme`, etc.) will naturally
include `navItems` through the same save/publish endpoint — no new endpoint needed.
