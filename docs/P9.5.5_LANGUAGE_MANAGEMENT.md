# P9.5.5 — Language Management Center

## Objective

Build the Platform Administration system for managing languages —
activation, typography, formatting, fallback, and coverage — entirely on
top of the existing Configuration Framework/Collection Engine/Studio/
Platform Administration infrastructure (P9.0–P9.4) and the runtime
localization layer (P9.5.0–P9.5.4). This phase is explicitly **not** about
translating more pages; it's the administration surface for languages
themselves.

## What was built

### `src/platform-admin/modules/languages.ts` — `platform.languages` module

A `ConfigModuleDefinition` registered exactly like every other module,
via `registerAdminModule()` (P9.4) — no new registration mechanism. Its
one field, `platform.languages.registry`, is a `type: 'collection'` field
(P9.2) — the same collection field type Countries and Platform Users
already use. This is the `localization.languages` collection
`docs/P9.5.0_LOCALIZATION_ARCHITECTURE.md` §2 designed but never
implemented, finally built.

### Roster (Phase B/L)

30 languages total:
- **6 operational** (`src/i18n/language-registry.ts`, P9.5.1A — English,
  Persian, Arabic, Chinese, Italian, Turkish), sourced from the existing
  registry rather than re-typed.
- **24 additional real languages**, registered disabled (French, German,
  Spanish, Portuguese, Russian, Japanese, Korean, Hindi, Urdu, Bengali,
  Vietnamese, Thai, Indonesian, Malay, Dutch, Polish, Swedish, Hebrew,
  Greek, Czech, Romanian, Hungarian, Ukrainian, Swahili) — each with real
  BCP 47 code, native name, direction, region, currency, and timezone.
  This proves "exists in the registry, disabled until activated" at a
  genuine (if not yet 150+) scale, the same way Countries proved the
  pattern at 176 entities.

### Schema (Phase B/E/F) — ~30 properties per language entity

| Group | Properties |
|---|---|
| Identity | `nativeName`, `englishName`, `region`, `searchKeywords`, `notes` |
| Lifecycle | `status` (draft/testing/published/deprecated/archived — the same 5-value vocabulary `ConfigLifecycleState` already uses), `enabled`, `visibility`, `default`, `beta`, `experimental`, `lastUpdated`, `translator` |
| Coverage | `translationCoverage`, `completionPercent`, `machineTranslated`, `humanReviewed` |
| Formatting | `currency`, `timezone`, `dateStyle`, `hourCycle`, `numberNotation`, `pluralRules`, `fallbackLanguage` — every one an `Intl.*` option, never a hand-rolled pattern string, per `docs/P9.5.0_LOCALIZATION_ARCHITECTURE.md` §4 |
| Direction | `direction`, `rtl` |
| Typography | `fontFamily`, `secondaryFontFamily`, `headingFontFamily`, `monoFontFamily`, `fontScale`, `lineHeight`, `letterSpacing`, `fontWeight` |

No new `uiControl`/preview kind was added — `font_selector`/`font-sample`
(Typography module, P9.0), `currency_picker`/`timezone_picker` (Countries,
P9.2), `switch`/`radio`/`slider`/`textarea` (every module since P9.0) are
all reused as-is.

### UI (Phase C/D) — zero new component code

`ConfigurationCollectionTable` and `ConfigurationEntityDrawer` (P9.2,
extended P9.5.3/P9.5.4) already render **any** `'collection'` field
generically: table with filters/search/sort/group/bulk actions/export
placeholder, and a per-entity drawer with 7 tabs (Configuration,
Overrides, Dependencies, Audit, Statistics, Inheritance, Preview). This
module gets all of it for free — verified in
`src/test/p9-5-5-language-management.test.tsx` by rendering
`ConfigurationStudioLayout` with `activeModuleId="platform.languages"`
and confirming the table and drawer render with the real roster.

The phase brief's requested drawer tabs (Overview, Configuration,
Typography, Formatting, Fallback, Coverage, History, Dependencies,
Preview) map onto the 7 generic tabs as follows: Overview/Configuration
→ the Configuration tab (every schema property, grouped by `category`
into Identity/Lifecycle/Coverage/Formatting/Direction/Typography
sections within the one tab — see "What was not built" below for the
honest gap here); Fallback → the `fallbackLanguage` field, visible in
Configuration and validated by `validateLanguageCollection()`; Coverage →
the coverage fields, visible in Configuration and Statistics; History →
the Audit tab (reuses `configurationAudit`, unchanged); Dependencies →
the Dependencies tab (empty for this module, since no schema property
declares a `dependency`, same as most of Countries' schema); Preview →
the Preview tab, wired to `buildPreview()` (Phase I, below).

### Typography (Phase E)

Four font-role fields (`fontFamily`/`secondaryFontFamily`/
`headingFontFamily`/`monoFontFamily`), each `uiControl: 'font_selector'`
with `preview: { kind: 'font-sample' }` — the exact live-preview mechanism
Typography (P9.0) already built, reused without modification. Font scale/
line-height/letter-spacing are numeric slider fields. RTL languages'
mock defaults set `Vazirmatn`/`Noto Sans Arabic` as their primary/
secondary fonts and a slightly larger `fontScale`/`lineHeight` — real,
editable starting values, not placeholders.

### Formatting (Phase F)

`dateStyle`/`hourCycle`/`numberNotation` are `Intl.DateTimeFormat`/
`Intl.NumberFormat` option selects — never a stored pattern string, per
the governing principle P9.5.0 established. `currency`/`timezone` reuse
Countries' exact `currency_picker`/`timezone_picker` controls.

### Activation workflow (Phase G) + cross-entity validation (Phase J)

`status` carries the standard 5-state lifecycle vocabulary. The real gap
found this phase: `ConfigurationValidator`'s per-field `custom` validators
(`src/config/validator.ts`) validate one field's value in isolation —
they have no way to express "no two entities may both be the default" or
"does this entity's fallback chain terminate," because they never see
sibling entities. Rather than reshaping that framework for one module (a
"rewrite architecture" the brief forbids), this phase adds a small, pure,
dedicated function:

```ts
export function validateLanguageCollection(entries: ConfigCollectionValue): LanguageCollectionError[]
```

Checking, per the real collection value:
1. At most one entity has `default: true`.
2. Every entity's `direction` is `'ltr'` or `'rtl'`.
3. `rtl` agrees with `direction`.
4. An entity with `status: 'published'` has `nativeName`/`englishName`/
   `fontFamily`/`dateStyle`/`currency` all set (the "cannot become
   Published unless required metadata exists" requirement).
5. Following each entity's `fallbackLanguage` pointer terminates (cycle
   detection) — the latent bug the audit doc flagged: `resolveFallbackChain()`
   (`src/i18n/runtime.ts`, P9.5.1A) already does a correct one-hop-pointer
   traversal, but nothing previously checked that the roster's pointers
   couldn't form a cycle that would make that traversal loop forever.

**A real wiring bug caught while writing this exact section**: the first
draft additionally registered `validateLanguageCollection` as a
`configurationValidator.registerRule()` and pointed the `status` schema
property's `validation.custom` at it, intending to surface it through the
Studio's existing generic validation plumbing. That's wrong —
`ConfigurationValidator.validateField(field, value)`
(`src/config/validator.ts`) calls a custom rule with `value` being **that
one field's own value** (e.g. the string `"published"`), never the whole
collection; nothing in the current Console/Studio ever calls
`configurationValidator.validate()` on a *collection schema property* at
all today (only on the top-level collection field itself, in
`ConfigurationFieldRow`/`ConfigurationInspector`), so the miswiring was
inert rather than crashing — but it would have broken the moment a future
change wired per-entity field validation into `ConfigurationFieldControl`
inside the entity drawer. Removed; `validateLanguageCollection()` is a
standalone, directly-imported, directly-tested pure function, not
threaded through the per-field validator today. Wiring it into the live
save flow is real remaining work — see "Remaining work for P9.5.6" below.

Regression tests (`src/test/p9-5-5-language-management.test.tsx`,
"validateLanguageCollection" suite) cover all 5 checks plus confirm the
real mock data passes cleanly.

### Coverage Dashboard (Phase H)

Four widgets registered in `src/platform-admin/widgets.ts` via the
existing `platformDashboardRegistry` (P9.4 Phase D) — the same registry
every other Platform Dashboard widget uses:

- `operational_languages` — enabled count / roster size.
- `avg_translation_coverage` — average `translationCoverage` across
  enabled languages.
- `human_reviewed_languages` — count with `humanReviewed: true`.
- `lowest_coverage_languages` — the 3 lowest-coverage enabled languages.

Unlike every pre-existing widget (illustrative fixed mock numbers), these
`compute()` by calling `configurationService.resolveField('platform.languages.registry')`
live — editing a language's coverage in the Language Management Center
immediately changes what the dashboard reports, with no separate
"dashboard data" copy to keep in sync.

### RTL Preview (Phase I) — honest scope

`buildPreview()` on the collection field returns a small set of key/value
pairs already rendered generically by `ConfigurationFieldPreview`'s
existing Preview-tab plumbing (P9.3), including a direction-aware sample
string (`"← نص تجريبي"` for RTL entities, `"Sample text →"` for LTR). **Not
built**: a dedicated side-by-side LTR/RTL comparison view or a live
"logical CSS validation" tool — the brief's fuller Phase I ask. What
exists reuses the generic preview mechanism faithfully; a bespoke
comparison UI would be new component surface, which is exactly the kind
of thing this phase's "reuse, don't build a fourth engine" constraint
argues against building hastily. Flagged as real remaining work below.

### Permissions (Phase K)

- New `'Localization'` IA group (`src/platform-admin/nav-groups.ts`),
  distinct from `'Configuration'` (which still houses the simple
  `languages`/`countries`/`typography` config modules tenants and
  Platform Admin both reach).
- New `platform.localization.view`/`platform.localization.manage`
  permissions (`src/platform-admin/permissions.ts`), granted to
  `platform_owner`/`platform_super_admin` (wildcard `*`),
  `platform_admin` (both), `platform_auditor`/`platform_read_only`
  (view only) — no tenant, owner, or branch role can reach this module at
  all, because it's only registered/reachable through
  `registerAdminModule()`'s `platformPermission` gate, the exact
  mechanism every other Platform-Admin-only P9.4 module already uses.

## Bugs discovered and fixed

1. **Dead, incomplete, misleading hardcoded locale constants**
   (`src/constants/index.ts`: `DEFAULT_LOCALE`/`SUPPORTED_LOCALES`/
   `RTL_LOCALES`) — zero real import sites (confirmed by `grep`), and
   even as stale documentation they list only 3 of the 6 operational
   languages. Removed. See `docs/P9.5.5_LANGUAGE_MANAGEMENT_AUDIT.md` §1.
2. **Own-language fallback self-loop in the first mock-data draft** — the
   initial roster construction set every language's `fallbackLanguage`
   default to `'en'`, including `en` itself, which pointed at itself.
   `validateLanguageCollection()`'s cycle detector caught this
   immediately (all 30 languages failed validation) before it was ever
   exercised at runtime. Fixed by adding an explicit "— None —" fallback
   option (empty string) and setting `en`'s fallback to it — the single
   entity that should terminate the chain, not loop through it. This is
   exactly the kind of bug the Phase J validator exists to catch, caught
   during this very phase's own development.
3. **Miswired per-field custom validator** — the first draft registered
   `validateLanguageCollection` via `configurationValidator.registerRule()`
   and pointed the `status` schema property's `validation.custom` at it.
   `ConfigurationValidator.validateField(field, value)` calls a custom
   rule with `value` being that one field's own value (a string like
   `"published"`), never the whole collection — the registered rule would
   have received the wrong argument shape entirely. Caught by re-reading
   `src/config/validator.ts`'s actual signature while documenting this
   phase (before it shipped as a claimed-working feature). Confirmed
   inert today (nothing currently calls `configurationValidator.validate()`
   on a collection schema property), but removed rather than left as a
   latent trap for the next person who wires per-entity field validation
   into `ConfigurationFieldControl`. See "Activation workflow" above for
   the corrected description.

## What was NOT built (honest accounting)

- A dedicated side-by-side RTL/LTR comparison view (Phase I) — the
  generic preview tab shows a direction-aware sample string; no bespoke
  comparison UI.
- Bulk import/export file handling — the Collection Table's Export/Import
  buttons already exist generically (P9.2) but Import has been a
  documented placeholder ("Import is a placeholder for a future phase")
  since P9.3; this phase didn't implement real file I/O for it.
- A dedicated "Coverage Dashboard" *page* — four widgets were added to
  the existing Platform Dashboard (reusing its grid), not a separate
  standalone coverage-focused screen.
- Extending the roster to the full eventual 150+ languages
  `docs/P9.5.0_LOCALIZATION_ARCHITECTURE.md` envisions — 30 real entries
  (6 operational + 24 disabled) demonstrate the pattern at genuine scale;
  reaching 150+ is mechanical roster-list work for a future phase, not
  an architecture gap.
