> Scope executed: a fully-migrated reference vertical (authentication flow),

## 2. Files migrated

**Fully migrated to `useTranslations()`/`getTranslations()`:**
- `src/app/login/page.tsx`
- `src/app/register/page.tsx`
- `src/app/forgot-password/page.tsx`
- `src/app/verify-otp/page.tsx`
- `src/app/not-found.tsx` (server component — uses `getTranslations()` from `next-intl/server`)
- `src/app/layout.tsx` (RTL bug fix, not a translation migration — see audit §3)
- `src/components/layout/Header.tsx`, `src/components/layout/TenantHeader.tsx` (logout toast)

**New infrastructure:**
- `src/lib/i18n-validation.ts` — canonical validation key constants
- `src/i18n/coverage.ts` + `scripts/check-translation-coverage.mjs` — Translation Coverage utility
- `src/i18n/seo.ts` — hreflang/SEO localization infrastructure
- `src/i18n/locales/{en,fa,ar}.json` — expanded from 12 to 20 namespaces, 209 → 249 keys

**Not touched (see audit §4 for the full list):** every other page and
component in the app — all still render literal English text, unchanged in
behavior from before this phase.

## 3. Translation coverage statistics

As measured by `npm run i18n:coverage` against the state at the end of this
phase:

```
scanned 360 files, found 111 translation call sites
reference (en) has 249 keys across 20 namespaces
✓ No missing keys — every t() call resolves to a real en.json entry
✓ No orphan namespaces
ℹ 123 keys defined in en.json with no detected call site
  (expected — many are used by components not yet migrated in this pass,
   or resolved via dynamic/interpolated keys the static scanner can't see)
```

`npm run i18n:validate` (the pre-existing P3.7 cross-locale parity check)
still passes: all 3 shipped locales (en/fa/ar) share identical key sets
(249 keys each) — no locale is missing a key the others have.

**Coverage as a percentage of the whole app**: 111 real call sites across
7 files out of 116 pages + 95 components (211 total UI files) is
**roughly 3% of UI files migrated** by file count — but 100% of the
authentication flow (the highest-traffic, most security-sensitive surface)
by design, not by accident. This is stated plainly rather than inflated:
the phase's own "no full app migration" boundary combined with the sheer
scale (211 UI files, ~zero prior `next-intl` adoption) made an exhaustive
pass in one phase infeasible to do *safely* — every migrated file needed
manual `t()`/key wiring, English-value-preserving verification, and
fa/ar translation, which doesn't scale to 200+ files without either
automation (out of scope: "no machine translation") or many more review
passes.

## 4. Remaining untranslated areas

## 5. Performance comparison (before/after)

- **No regression to the one-language-per-request invariant** — still
  exactly one locale's JSON file is dynamically imported per request
  (`src/i18n/runtime.ts`'s `loadMessages`, unchanged mechanism from
  P9.5.1A). Adding namespaces to that one file doesn't change *how many*
  files load, only the size of the one that does.
- **111 new `useTranslations()`/`getTranslations()` call sites** each cost
  a context read (React context for client components, an async local
  lookup for the one server component) — negligible relative to render
  cost; no measurable difference from a `useState`/`useAuthStore` read
  already common in these same files.
- **Full test suite runtime**: 88 files / 5565 tests, ~149s locally —
  consistent with pre-phase timing (86 files / 5515 tests, ~138s) scaled
  for the 2 new test files added; no slowdown attributable to the
  migration itself.

## 6. Bundle size comparison

Locale JSON file sizes (uncompressed, bytes) — before this phase (commit
`0deb30f`) vs after:

| File | Before | After | Delta |
|---|---|---|---|
| `en.json` | 5,295 | 10,041 | +4,746 |
| `fa.json` | 6,647 | 13,446 | +6,799 |
| `ar.json` | 5,669 | 11,927 | +6,258 |

Each locale file roughly doubled in size (still under 14 KB uncompressed,
well under the "no single language bundle should meaningfully affect TTI"
soft budget `P9.5.0_PERFORMANCE_STRATEGY.md` §8 sets) — and **only one of
these three files is ever loaded per request**, per the unchanged
one-language invariant. zh/it/tr still ship **zero** bytes of their own
(no file exists; they fall back to `en.json`, already loaded for any
English-preferring visitor, or loaded once for a zh/it/tr visitor exactly
as `en.json` would be for an English one — no extra locale bundle is ever
fetched).

New code modules (`coverage.ts`, `seo.ts`, `i18n-validation.ts`,
`language-registry.ts` from P9.5.1A) are small, tree-shakeable, pure
TypeScript with no new dependencies — `coverage.ts` and the coverage script
are dev/CI tooling, never imported by any page, so they add **zero** bytes
to any client or server bundle.

## 7. Remaining work for P9.5.2 (Language Management Center)

Per the phase's explicit boundaries, none of the following were built and
all remain for P9.5.2+:
- **Translation Center UI** — a Console surface for translators to edit
  `(namespace, key, language)` triples, see coverage reports, and manage
  review status (`P9.5.0_TRANSLATION_ARCHITECTURE.md` §2/§7).
- **Language Management UI** — Platform-only screen to enable/disable a
  language, edit its metadata, and run the stable-promotion gate
  (`P9.5.0_LANGUAGE_LIFECYCLE.md` §5), replacing the static
  `language-registry.ts` table with the full `localization.languages`
  collection.
- **Continuing the application migration** — the ~110 remaining
  pages/components from §4, in priority order: customer-facing checkout/
  cart/menu/reservation next (revenue-critical, highest traffic), then
  Business Console, then Platform Administration/Configuration Studio
  (lowest traffic, internal-only).
- **Wiring `src/i18n/seo.ts` into real routes** once a URL strategy
  (path-prefix vs. subdomain vs. cookie-only) is decided — the seam
  (`buildLocalizedUrl`) is ready; the strategy itself is an explicit
  P9.5.1+ decision point `P9.5.0_DEVELOPER_GUIDE.md` §5 already flagged.
- **Real zh/it/tr translation files** — currently intentionally absent,
  falling back to English per design; authoring them is a content task,
  not an architecture one.
- **A CI gate** (not just a report) built on `scripts/check-translation-coverage.mjs`
  once coverage is high enough that failing a PR on a missing key becomes
  useful rather than obstructive.
