# P8.9.3 — Backend Authentication Audit

> Full audit of the existing auth system. Documents every mechanism, every
> weakness, and every migration requirement for phone-first authentication.

---

## 1. Current Login Flow

### 1.1 User Journey (Email / Password)

```
User submits email + password
  → POST /auth/login/
  → Backend validates credentials
  → Returns { user, tokens: { access, refresh } }
  → Frontend: localStorage["access_token"] + cookie mirroring
  → Frontend: useAuthStore.setUser(user)
  → Frontend: useRbacStore.setTenantRoles(tenantId, p7Roles)
  → Router.push(getPostLoginRedirect(user.role))
```

### 1.2 Mock Authentication (Frontend Only)

All mock auth lives in `src/services/auth.service.ts`. The `USE_MOCK` flag
(`NEXT_PUBLIC_USE_MOCK=true`) bypasses every real backend call.

| Component | Mock Behaviour |
|---|---|
| `login()` | Looks up `MOCK_CREDENTIALS[email]`, returns pre-built `{ user, tokens, p7Roles }` |
| `getMe()` | Reads `localStorage["mock_session_email"]`, returns corresponding user |
| `sendOTP()` | Returns `{ message: "OTP sent" }` after `MOCK_DELAY` ms with no real send |
| `verifyOTP()` | Resolves phone from `DEMO_PHONE_TO_EMAIL`, returns user + tokens. Code `000000` always fails |
| `register()` | Returns shallow-cloned `MOCK_USER` with submitted name/email |
| `logout()` | Calls `clearTokens()` + removes `localStorage["mock_session_email"]` |
| Token expiry | All tokens have `exp = 9999999999` (year 2286) — never expire |
| JWT signature | Intentionally fake (`mock_signature`) — middleware can't verify in mock mode |

The mock is production-isolated: `next.config.ts` throws at build if
`NODE_ENV=production && NEXT_PUBLIC_USE_MOCK=true`.

### 1.3 Token Storage

```
localStorage["access_token"]   — primary read path for axios headers
localStorage["refresh_token"]  — used by interceptor for silent refresh
Cookie: access_token           — mirrored synchronously via document.cookie
                                 (SameSite=Strict, NOT HttpOnly)
                                 — read by Edge middleware for SSR auth checks
```

**Critical weakness:** The cookie is not HttpOnly. JavaScript can read it, so it
does not provide meaningful XSS protection beyond what localStorage already provides.

### 1.4 Axios Interceptor (Request)

```
Authorization: Bearer {localStorage["access_token"]}
X-Tenant-Slug: {current tenant slug}
```

### 1.5 Axios Interceptor (401 Response — Silent Refresh)

```
1. POST /auth/token/refresh/ with { refresh: localStorage["refresh_token"] }
2. On success: setTokens(new_access, new_refresh), retry original request once
3. On failure: clearTokens(), redirect to /login
```

## 2. JWT Architecture

### 2.1 Current Token Structure (Frontend Assumption)

The frontend validates mock JWTs with `isValidJWT()` in `src/middleware.ts`:

```typescript
function isValidJWT(token: string): boolean {
  const parts = token.split('.')
  if (parts.length !== 3) return false
  const payload = JSON.parse(atob(parts[1]))
  return payload.exp > Math.floor(Date.now() / 1000)
}
```

This means:
- Any string with 3 `.`-delimited segments is structurally valid
- Only `exp` is checked; `sub`, `iss`, `aud`, and signature are NOT validated
- In production, the backend MUST validate the signature server-side

### 2.2 JWT Claims (Recommended Minimum)

The frontend does not inspect claims beyond `exp`, so the backend is free to
include any claims. Recommended minimum for phone-auth compatibility:

```json
{
  "sub": "user_id",          // user identifier
  "exp": 1234567890,         // expiry Unix timestamp
  "iat": 1234567890,         // issued at
  "jti": "uuid",             // JWT ID (for revocation)
  "phone": "+14155550101",   // primary identifier (phone-first accounts)
  "email": null,             // null for phone-only accounts
  "role": "customer",        // legacy role field
  "tenant": "savor",         // tenant slug for scoping
  "device": "device_uuid"    // device session ID (added P8.9.3)
}
```

### 2.3 Weaknesses in Current JWT Design

| # | Weakness | Impact |
|---|---|---|
| W1 | No `jti` claim — tokens cannot be individually revoked | Token theft is permanent until expiry |
| W2 | No `iss` / `aud` claims — tokens not bound to issuer or audience | Cross-service token reuse possible |
| W3 | Signature not verified in frontend middleware (by design) | Server-side must enforce; no client-side check |
| W4 | Access token stored in non-HttpOnly cookie | Readable by XSS payloads |
| W5 | Refresh token in localStorage — same XSS risk | Long-lived token exposure |
| W6 | No device binding on token | One token valid on all devices |
| W7 | No token family tracking | Refresh token reuse not detected |

## 3. Refresh Token Flow

### 3.1 Current Behaviour

The axios interceptor handles 401 responses:
1. Calls `POST /auth/token/refresh/` with `{ refresh }` from localStorage
2. On success: replaces both tokens in localStorage + cookie
3. On failure: logs out, redirects to `/login`

### 3.2 Weaknesses

| # | Weakness | Impact |
|---|---|---|
| R1 | No refresh token rotation documented in contract — backend may be reusing tokens | Stolen refresh token usable indefinitely |
| R2 | No token family concept — single stolen refresh token cannot be traced | Silent parallel session possible |
| R3 | Refresh token stored in localStorage — XSS extractable | Long-lived exposure |
| R4 | No `logout-all` endpoint — only current session cleared | Compromised account cannot kill all sessions remotely |
| R5 | No device session tracking — can't see where you're logged in | User cannot audit or revoke remote sessions |

## 4. User Model & Role System

### 4.1 Current User Type (Frontend)

```typescript
interface User {
  id: string
  email: string
  phone?: string          // optional — many users have no phone
  first_name: string
  last_name: string
  avatar?: string
  role: 'customer' | 'staff' | 'admin'   // legacy coarse-grained role
  is_verified: boolean
  created_at: string
}
```

**Critical weaknesses for phone-first auth:**
- `email` is required (NOT optional) — phone-only accounts cannot be created
- `phone` is optional — inconsistent: phone-first users have no email
- `is_verified` is a single boolean — cannot distinguish email-verified vs phone-verified
- No `phone_verified_at` timestamp
- No `email_verified_at` timestamp

### 4.2 Legacy Role System

```typescript
type UserRole = 'customer' | 'staff' | 'admin'
```

Used in: `User.role`, `AuthGuard` (`forbiddenPath="/"` for customers), `getPostLoginRedirect`.

This coarse field is preserved for backward compatibility but is secondary to the P7 RBAC system.

### 4.3 P7 Tenant-Scoped Role System

```typescript
type Role = 'owner' | 'admin' | 'manager' | 'cashier' | 'waiter' | 'kitchen' | 'marketing' | 'support'
```

31 granular permissions (e.g. `order.view`, `analytics.view`, `tenant.manage`).

Roles are returned as `p7Roles: Role[]` alongside the user on login/OTP verification. The frontend seeds them into `useRbacStore`. **The backend must return these on every auth response.**

## 5. RBAC & Permission Guards

### 5.1 Dual-Layer System

**Layer 1 — Legacy colon permissions** (`dashboard:access`, `orders:view`):
- Checked by `AuthGuard` component
- Maps directly from `User.role`
- Hard-coded in `src/hooks/index.ts → useAdminModuleNav()`

**Layer 2 — P7 dot permissions** (`order.view`, `analytics.view`):
- Checked by `PermissionGuard` and `usePermission()` hook
- Resolved via `getPermissionsForRole()` in `permission.service.ts`
- Seeded into `useRbacStore` on login success

### 5.2 Permission Loading Weakness

P7 roles are passed on the login response body (`p7Roles: Role[]`). They are
**not embedded in the JWT**. This means:

- On hard refresh, `useRbacStore` persists (it uses `zustand/persist` under `'savor-rbac'` key)
- But `useAuthStore` does NOT persist — user is `null` until `getMe()` resolves
- Race condition: `PermissionGuard` might render before `useRbacStore` is re-hydrated
- **No server-side enforcement of P7 permissions** in the current contract — all gating is frontend-only

### 5.3 AuthGuard Triple Gate

Authenticated routes go through three sequential gates:

```
Edge Middleware (src/middleware.ts)
  Checks: access_token cookie exists + JWT structure + exp > now
  Redirect: /login?redirect=<path>

AuthGuard (src/components/auth/AuthGuard.tsx)
  Checks: useAuthStore().user !== null + legacy permission (e.g. dashboard:access)
  Redirect: forbiddenPath (/ for customer, or custom)

PermissionGuard (src/components/auth/PermissionGuard.tsx)
  Checks: P7 permission via usePermission() hook
  Redirect: /admin (default) or custom
```

## 6. Session Handling

### 6.1 Current Session Storage

```
useAuthStore (Zustand, NOT persisted)
  user: User | null
  isAuthenticated: boolean
  setUser(user)
  logout()

useRbacStore (Zustand, persisted as 'savor-rbac' in localStorage)
  roles: Record<tenantId, Role[]>
  setTenantRoles(tenantId, roles)
  clearRoles()

localStorage["access_token"]
localStorage["refresh_token"]
localStorage["mock_session_email"]   (mock mode only)
localStorage["savor-rbac"]           (persisted Zustand slice)
```

### 6.2 Session Weaknesses

| # | Weakness | Impact |
|---|---|---|
| S1 | `useAuthStore` not persisted — page refresh loses `user` until `getMe()` resolves | Brief unauthenticated flash on every reload |
| S2 | No server-side session record — tokens are stateless | Cannot enumerate or revoke active sessions |
| S3 | No device identifier — all sessions look identical | Cannot show "2 active sessions" to user |
| S4 | No "Remember Me" implementation | All sessions have the same lifetime |
| S5 | No concurrent session limit | Unlimited parallel logins possible |
| S6 | `logout()` only clears frontend state — does NOT call `POST /auth/logout/` reliably | Refresh token remains valid after logout unless server also blacklists it |

## 7. Phone Authentication Weaknesses

### 7.1 Current `sendOTP` / `verifyOTP` Contract

```
POST /auth/send-otp/  { phone: string } → { message: string }
POST /auth/verify-otp/ { phone: string, otp: string } → { user, tokens }
```

**Weaknesses that block production phone auth:**

| # | Weakness | Impact |
|---|---|---|
| P1 | No `challenge_id` — OTP tied only to phone number, not a session | Cannot distinguish concurrent OTP attempts for same phone |
| P2 | No OTP expiry documented in contract | Backend may implement 10 min; frontend doesn't know |
| P3 | No brute-force protection in contract | 1,000,000 attempts to guess 6-digit OTP is viable without rate limiting |
| P4 | No replay protection — same OTP could be reused | One-time guarantee not contractually enforced |
| P5 | No resend endpoint with cooldown — `sendOTP` can be called unlimited times | SMS spam possible |
| P6 | `is_new_user` not in response — frontend cannot differentiate login vs registration | Frontend had to infer from phone lookup table (P8.9.2 workaround) |
| P7 | `p7Roles` not in `verifyOTP` response — roles not returned | Frontend must call `getMe()` separately or roles are missing |
| P8 | Phone stored as optional on User — can't require it for phone-first accounts | `email` stays required, blocking phone-only signup |
| P9 | No `/auth/phone/resend` with cooldown enforcement | |
| P10 | No `/auth/logout-all` — cannot kill all sessions on account compromise | |
| P11 | No `/auth/devices` — no way to see/revoke active sessions | |
| P12 | No `/auth/change-phone` flow — phone number becomes immutable after signup | |
| P13 | No account deletion endpoint | |
| P14 | No `/auth/session` — frontend cannot validate current session health | |

### 7.2 Phone Normalization

The current contract accepts `phone` as-is. No normalization is specified:
- Is `+14155550101` the same as `1 (415) 555-0101`? The contract doesn't say.
- The frontend now outputs E.164 exclusively (P8.9.2), but the backend may not enforce it.

## 8. Migration Blockers Summary

The following changes are REQUIRED to support production phone auth without breaking changes:

| # | Blocker | Resolution |
|---|---|---|
| M1 | `User.email` is required | Make `email` nullable (phone-only accounts have no email) |
| M2 | `User.phone` is optional | Make `phone` required for phone-first accounts; keep optional for email-only accounts |
| M3 | No `is_phone_verified` / `is_email_verified` flags | Add `phone_verified_at` and `email_verified_at` timestamps to User |
| M4 | No `challenge_id` in OTP flow | New `PhoneChallenge` entity + `challenge_id` field in request/response |
| M5 | No `is_new_user` in `verifyOTP` response | Add `is_new_user: boolean` to response |
| M6 | No `p7Roles` in `verifyOTP` response | Already fixed in mock; must be in production response |
| M7 | No refresh token rotation | Must rotate on every use + track token families |
| M8 | No `jti` claim on JWT | Required for revocation |
| M9 | No device sessions | New `UserDevice` entity required |
| M10 | Missing endpoints | `/auth/phone/start`, `/auth/phone/verify`, `/auth/phone/resend`, `/auth/logout-all`, `/auth/session`, `/auth/devices`, `/auth/complete-profile`, `/auth/change-phone`, `/auth/delete-account` |

## 9. Security Posture

### 9.1 Current Protections

- Frontend rate limiter (`LOGIN_LIMIT`) — per-email counter, 5 req/min, resets on success (client-side only)
- Mock credentials hardcoded — cannot be guessed in mock mode
- `NEXT_PUBLIC_USE_MOCK` forbidden in production build
- Edge middleware rejects requests without valid JWT structure + non-expired `exp`

### 9.2 Missing Protections

- No server-side rate limiting on auth endpoints
- No IP-based throttling
- No phone enumeration protection (success vs. "phone not registered" responses differ)
- No OTP hashing at rest — if the OTP store is read, OTPs are exposed
- No suspicious activity detection (unusual country, multiple devices)
- No account lockout policy defined
- No CAPTCHA on auth endpoints

---

## 10. Conclusion

The current auth system is:
- Functional for email+password mock authentication
- Partially implemented for OTP (`sendOTP`/`verifyOTP` endpoints exist in contract)
- Missing 14 endpoints and 10 data model changes for production phone auth
- Missing security controls that would be mandatory in a production deployment

The new contract (Phase B–J) addresses all identified weaknesses without breaking
any existing endpoint contracts.
