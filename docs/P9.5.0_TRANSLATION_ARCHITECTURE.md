# P9.5.0 — Translation Architecture

> Documentation only. Expands `P9.5.0_LOCALIZATION_ARCHITECTURE.md` §3's
> `localization.translation_keys` collection into a full translation
> system: namespaces, lazy/dynamic loading, versioning, detection tooling,
> storage, and fallback resolution.
>
> Last updated: 2026-07-05

---

## 1. Key-based and namespace-based, together

A translation key is always addressed as `{namespace}.{key}` —
`checkout.confirm_button`, matching the existing `src/i18n/locales/en.json`
files' own top-level grouping (`common`, `nav`, `auth`, `menu`, `cart`,
`checkout`, `order`, `reservation`, `dashboard`, `restaurant`,
`notifications`, `errors` — 12 today). Namespaces are not a separate
collection; they are the dotted-path prefix convention already in use,
formalized as a required, validated structure rather than an informal one.
A namespace maps 1:1 to a `next-intl` message bundle (§3) and, in the
Studio, to the section grouping the way Authentication's fields already
group under section titles.

## 2. Key status vocabulary

Every `(namespace, key, language)` triple (the entity granularity chosen in
`P9.5.0_LOCALIZATION_ARCHITECTURE.md` §3) carries a `status`:

| Status | Meaning |
|---|---|
| `missing` | No value exists yet — the language's coverage percentage counts this against it |
| `machine` | Auto-translated (a future MT integration's output), not yet human-reviewed |
| `reviewed` | A human translator has confirmed it |
| `approved` | A second reviewer (or the Platform Admin) has signed off — required before a language can move from `activation_tier: beta` to `stable` (see `P9.5.0_LANGUAGE_LIFECYCLE.md` §5 for the exact gate) |

## 3. Gender and plural variants

**Plurals are never hand-rolled.** `plural_variants` (a JSON property on
the triple) is keyed by whatever `Intl.PluralRules(languageEntity.
plural_rule_locale).resolvedOptions().pluralCategories` returns for that
language — for English that's `['one', 'other']`; for Arabic it's `['zero',
'one', 'two', 'few', 'many', 'other']`. The Studio's collection-entity
drawer (`ConfigurationEntityDrawer`, P9.2) renders one text field per
category the way it already renders one control per schema property — no
new rendering primitive, just a dynamic field *count* driven by the
language's own CLDR category list instead of a fixed schema (the drawer
already tolerates a variable-length `json` field like this for Countries'
`address_format`-adjacent free-form fields).

**Gender variants** are opt-in per language (`gender_agreement`, §2.2 of
the architecture doc). When not `none`, `gender_variants` holds
`{ masculine: "...", feminine: "...", neutral: "..." }` (three-way) or
`{ masculine: "...", feminine: "..." }` (two-way). Selecting which variant
to render at runtime is an application-level concern (the calling
component knows the subject's gender, e.g. from a user profile) — the
translation architecture only stores the variants; it does not decide
which one to show.

## 4. Import / Export

**Export** produces one JSON file per language per namespace — literally
the shape `src/i18n/locales/en.json` already has today, so the export
format requires zero downstream change to `next-intl`'s loading code. A
"export everything" mode concatenates all namespaces into the single flat
file the current 3 languages already use, for exact backward compatibility
during the transition period.

**Import** accepts the same shape, and diffs incoming keys against the
current `translation_keys` collection before applying:
- A key present in the import but not the registry → **new key** (flagged
  for review — see Developer Guide's CI check).
- A key in the registry but absent from the import → **not deleted
  automatically** (a missing key in an import is far more often an
  incomplete translation batch than an intentional deletion) — surfaced as
  a warning, actual removal is a separate, explicit "remove key" action
  (Developer Guide §3).
- A value that differs from the current one → creates a new **Translation
  Version** (§5) rather than silently overwriting, so the change goes
  through the same audit/history/rollback path every other Configuration
  write already does.

## 5. Versioning

Every write to a `translation_keys` entity is an ordinary
`configurationService.updateField()` call against the
`localization.translation_keys` collection field (P9.2's existing
`buildMergedCollectionValue`) — meaning it is **already versioned for
free** by the existing audit trail (`configurationAudit`, P9.0.1) and
**already has rollback for free** (`rollbackAuditEntry`, introduced in
P9.3 for the Configuration Studio's History timeline, reused verbatim). No
new version-storage mechanism is designed here, because the collection
framework's existing write path already is one.

`source_namespace_version` (a property on the triple, §3 of the
architecture doc) additionally tags each translation with *which content
revision* it was translated against — this is the one genuinely new
concept, because content itself (the English source string) can change
independent of any specific language's translation of it, and detecting
"this Persian translation is stale relative to the current English
source" requires comparing the tag, not just looking at audit timestamps.

## 6. Fallback Chain

Resolution order for a given `(namespace, key, requestedLanguage)`:

1. `requestedLanguage` itself.
2. `requestedLanguage`'s `fallback_locale` (one hop, e.g. `ar-EG` → `ar`).
3. Repeat step 2 until a language with no `fallback_locale` is reached, or
   a cycle is detected (validated at write time — the Studio's dependency
   engine, P9.1.3, already knows how to detect and reject a self-referential
   condition; the same check applies here to `fallback_locale` chains).
4. The platform's `languages.default` (existing field,
   `src/config/modules/languages.ts`) as the ultimate root.
5. If still missing: the raw key path itself is rendered (e.g.
   `checkout.confirm_button`) with a `status: 'missing'` flag — never a
   blank string, matching `next-intl`'s existing default behavior for an
   absent key.

This is a pure function over already-designed data (`fallback_locale`
chains + `languages.default`) — no new storage, no new field type.

## 7. Detection tooling

Four checks, each a pure computation over the `translation_keys`
collection plus the source code's actual key *usage* (extracted via a
static scan of `useTranslations()`/`t()` call sites — an implementation
detail of P9.5.1+, not designed further here):

| Check | Definition |
|---|---|
| **Missing key** | A key used in source code with no `translation_keys` entity for the current default language, or `status: 'missing'` for an *enabled* language |
| **Unused key** | A `translation_keys` entity whose `(namespace, key)` is never referenced by a static scan of the codebase |
| **Duplicate detection** | Two keys under the same namespace whose *English* value is byte-identical — a signal (not an error) that they might be consolidatable |
| **Conflict detection** | Two imports (§4) supplying different values for the same `(namespace, key, language)` in the same batch — must be resolved before the import applies, never silently last-write-wins |

These four checks are the CI gate referenced in
`P9.5.0_DEVELOPER_GUIDE.md` §4 — designed here as pure functions over
collection data so they can run in CI without a browser or a live registry
instance, the same way `configCollection`'s helpers (P9.2) are pure
functions today.

## 8. Storage

**Hybrid, not a choice between JSON and a database**: the in-memory mock
store (`overrideStore` in `src/config/service.ts`, unchanged since P9.0)
remains the frontend's storage during this mock-mode era, exactly as
every other Configuration field's overrides already work — the collection
framework doesn't know or care that its backing store is a database table
versus an in-memory map (P9.0.1's `layersFor`/`updateField` already
abstract this). The exported JSON files remain the **seed/bootstrap
format** (imported once to populate the initial `translation_keys`
collection default value, exactly the way `COUNTRY_OVERRIDES` in
`countries-registry-data.ts` seeds `countries.registry`'s default). A real
backend's storage choice (Postgres table vs. a translation-specific store
like a CDN-backed JSON blob per language) is an implementation decision for
P9.5.1+, deliberately not pinned down here, since the collection framework
is agnostic to it either way.
