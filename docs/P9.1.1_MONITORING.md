# P9.1.1 — Authentication Monitoring

> Phase E of P9.1.1. Dashboard design only — no implementation, no charts
> built. Every metric below is something a Platform Administrator needs
> visibility into once the Security Architecture (Phase D) and Provider
> Architecture (Phase F) are real; this document specifies what to measure
> and why, not how to render it.
>
> Last updated: 2026-07-04

---

## 1. Design principle

Every dashboard panel reads from the same two sources everything else in
this phase does: `ConfigurationAudit` (for *configuration* changes — who
changed `max_login_attempts` and when) and a new, distinct **Authentication
Event Log** (for *runtime* events — a login succeeded, an OTP was sent, an
account got locked). These are not the same thing and must not be
conflated (mirrors the Configuration vs. Audit distinction already drawn in
`docs/PLATFORM_ARCHITECTURE_PRINCIPLES.md` §6 for module versioning vs.
field audit). The Authentication Event Log is a new, backend-owned stream —
not part of `src/config/*` — this document only specifies its shape as
consumed by monitoring dashboards.

## 2. Panel — Login Activity

- **Successful Logins** — count over time, segmented by method (phone/OTP,
  email/password, social, passkey once shipped).
- **Failed Logins** — same segmentation, plus failure reason (wrong
  password, invalid OTP, expired OTP, account locked, blocked country).
  Failure *reason* is the single most useful field here — a spike in
  "invalid OTP" specifically (vs. "wrong password") is a different signal
  (credential stuffing vs. OTP brute force) requiring a different response.
- **Blocked Attempts** — attempts rejected before reaching credential
  validation at all: rate-limit rejections, geo/country blocks, permanent
  lock. Kept separate from "Failed Logins" because these represent the
  security controls in Phase D actually doing their job, which is a
  different story to tell a Platform Administrator than "users are
  mistyping their password."

## 3. Panel — OTP Activity

- **OTP Sent** — volume over time, segmented by provider (once Provider
  Architecture ships) and by country — this is also the panel that
  surfaces cost (SMS spend scales with volume) alongside security.
  Directly informs whether `authentication.otp.daily_limit_per_phone` is
  set sensibly.
- **OTP Failed** — segmented by reason: wrong code, expired code
  (`authentication.otp.ttl_seconds` exceeded), max-attempts reached
  (`authentication.otp.max_verify_attempts`). A high "expired" rate might
  mean the TTL is too short for real-world SMS delivery latency in some
  countries — an actionable signal to tune the config, not just observe it.
- **Resend Rate** — how often users hit "resend" relative to how often they
  succeed on the first code — a proxy for SMS deliverability problems by
  country/provider.

## 4. Panel — Locked Accounts

- **Currently Locked (temporary)** — live count, with time-to-unlock,
  filterable by tenant.
- **Permanently Locked** — count requiring manual/support unlock
  (`authentication.permanent_lock_threshold` escalations), with a direct
  action affordance ("review and unlock") once a Console exists.
- **Lockout Trend** — lockouts per day, to catch a platform-wide attack
  pattern (a sudden spike across many unrelated accounts suggests a
  credential-stuffing campaign, not organic user error).

## 5. Panel — Geographic & Device Distribution

- **Country Distribution** — logins/signups by country, cross-referenced
  against `authentication.allowed_countries`/`blocked_countries` — makes
  policy misconfiguration visible (e.g. a country generating heavy traffic
  that isn't in the allowed list would show as 100% blocked-attempts from
  that country, an obvious visual signal something's misconfigured either
  in policy or in a legitimate-user's favor).
- **Device Types** — mobile/desktop/tablet, OS, browser — informs whether
  device-trust UX (Security Architecture §4) is worth prioritizing for a
  given tenant's user base.

## 6. Panel — Providers

- **Authentication Providers in Use** — breakdown by method (phone/OTP,
  email/password, each social provider once live, passkeys once live) —
  answers "is anyone actually using Google login" before investing further
  in a given provider.
- **Provider Health** — the health-check surface designed in
  `docs/P9.1.1_AUTHENTICATION_ARCHITECTURE.md` §5 (OTP/email delivery
  reachability, token issuance latency) rendered as a live status panel —
  this is the one panel a Platform Administrator needs to check *first*
  during an incident, so it should be the most prominent, not buried.

## 7. Panel — Sessions

- **Active Sessions** — live count, platform-wide and per-tenant.
- **Concurrent Devices per User** — distribution; flags users approaching
  or exceeding `authentication.max_concurrent_sessions` (once that policy
  is enforced) and, more importantly, flags the *policy* itself as too
  loose/strict based on real usage before it's tightened.

## 8. Panel — Fraud & Abuse (schema-ready, data source pending Phase F/D)

- **Fraud Events** — count and detail once `authentication.fraud_detection_enabled`
  has a real signal source; until then this panel renders an explicit
  "not yet configured" state rather than fabricating zeros, so a Platform
  Administrator never mistakes "no data" for "no fraud."
- **Bot Attempts** — CAPTCHA challenge/fail rate once
  `authentication.captcha_enabled` is live; same "not yet configured"
  principle applies.
- **Suspicious Login Flow triggers** (Security Architecture §14) — count of
  step-up-challenge events, and how many resulted in a completed vs.
  abandoned login — the completion rate is the key tuning signal for
  whether the risk threshold is too aggressive (locking out real users) or
  too lax.

## 9. Panel — Demo / Mock Usage

Directly closes the audit's finding that mock-mode has no observability
today:

- **Demo Logins** — count of logins via the one-click demo account grid,
  only ever non-zero in environments where
  `authentication.demo_login_enabled` is `true`. **A non-zero count in any
  environment where this panel is expected to read zero is itself the
  single highest-priority alert this entire document proposes** — it means
  demo/mock authentication is live somewhere it shouldn't be.
- **Mock Authentication Usage** — same principle for
  `authentication.mock_authentication_enabled` — this panel doubles as a
  continuous production-safety check, not just a usage metric.

## 10. Panel — System Health

- **Authentication Enabled/Disabled state** — a permanent, always-visible
  banner reflecting `authentication.enabled`
  (Configuration Schema Section 1) and `system.maintenance_mode` (P9.0) —
  so a Platform Administrator never has to go hunting through settings to
  find out why login is down platform-wide.
- **Configuration Change Feed** — the most recent
  `ConfigurationAudit` entries scoped to the `authentication` module,
  surfaced directly on this dashboard (not just in a general audit log
  page) — security-relevant config changes (lockout policy, JWT TTL, demo
  mode) deserve first-class visibility exactly where an administrator is
  already looking for auth health.

## 11. Alerting priorities (design intent, not implementation)

In order of severity, for whichever future alerting mechanism consumes
these panels:

1. Demo/mock usage detected where it shouldn't be (Panel 9).
2. Lockout trend spike (Panel 4) — potential credential-stuffing attack.
3. Provider health failure (Panel 6) — authentication may be down
   platform-wide even if no individual login attempt shows as "failed"
   (e.g. OTP provider unreachable means no code is ever delivered, so
   users never even attempt verification).
4. Fraud/bot event spike (Panel 8), once that data source exists.
5. Everything else is dashboard-only, no alert, by default — avoiding
   alert fatigue is itself a design decision, not an oversight.
