## Phase G — Mock Data Strategy

### Current state (per the audit)

`src/lib/mock-data.ts` defines 10 `User` objects, all hardcoded
`is_verified: true`, no tenant/country variation modeled on the user
object itself (tenant association happens elsewhere, e.g. staff-membership
mock tables), and — critically — **the `User` type itself has no
`status`/`locked`/`suspended`/`disabled` field**. This is a data-model gap,
not a fixture gap: locked, disabled, pending-verification, and suspended
accounts cannot be represented today without a type change.

### Target model

```ts
// Additive to src/types/index.ts — not a redesign of the existing User shape
type AccountStatus = 'active' | 'pending_verification' | 'locked' | 'suspended' | 'disabled'

interface User {
  // ...existing fields unchanged...
  accountStatus: AccountStatus   // new, defaults to 'active' for every existing mock/fixture
  lockedUntil?: string           // ISO timestamp, only meaningful when accountStatus === 'locked'
  lockReason?: string            // audit-friendly, mirrors ConfigFieldAudit.requireReason intent
}
```

This is additive — no existing `User` consumer breaks, since
`accountStatus` defaults to `'active'` everywhere it isn't explicitly set,
matching every one of today's 10 mock users unchanged.

### Expanded mock roster

Building on the existing 10 accounts (customer, staff, admin, owner,
cashier, kitchen, marketing, support, multi-role, platform admin), the
target roster adds:

| New fixture | `accountStatus` | Purpose |
|---|---|---|
| A second tenant's owner/manager/cashier trio | `active` | Proves RBAC/config isolation across tenants (already partially covered by other mock services — this aligns the *auth* mock data with the same multi-tenant fixtures used elsewhere, e.g. `tenant-samoon-01` vs. a second tenant already used in branch/customer mocks). |
| A locked account | `locked`, with `lockedUntil` in the near future | Exercises the lockout UI/flow end to end without needing 5 real failed attempts. |
| A permanently locked account | `locked`, with `lockedUntil: null` (permanent) | Exercises the permanent-lock escalation path (Security Architecture §2). |
| A disabled account | `disabled` | Exercises "account disabled by admin" distinct from lockout (an administrative action, not a security consequence). |
| A pending-verification account | `pending_verification` | Exercises the "must complete OTP/email verification before full access" gate — today every mock user is `is_verified: true`, so this state is entirely unrepresented. |
| A suspended account | `suspended` | Exercises the account-suspension flow (e.g. ToS violation) distinct from both lock and disable. |
| Users across 3+ countries (using the existing `PINNED_COUNTRY_CODES` list) | `active` | Exercises country-specific phone_number formatting/validation and the `authentication.allowed_countries`/`blocked_countries` fields against real-looking international numbers, not just `+1`. |
| An "expired OTP" scenario | n/a (a scenario, not a user field) | Modeled as mock-service *behavior* (verifying a code after `authentication.otp.ttl_seconds` has elapsed returns `OTP_EXPIRED`), not a user property. |
| Demo provider accounts | `active` | One mock user per provider category (Provider Architecture) so a QA/demo environment can exercise "login via Google" / "login via Twilio OTP" / etc. without live provider credentials. |

### Configuration-driven, not hardcoded

Every one of the above stays governed by
`authentication.demo_login_enabled` / `demo_accounts_visible` /
`mock_authentication_enabled` (Configuration Schema Section 6) — the
expanded roster does not change the gating mechanism, only the realism of
what's gated. `MOCK_CREDENTIALS`' role→P7-role mapping continues to be the
single source for demo accounts (no new parallel table); the duplication
already flagged in the audit (`auth-redirect.ts`'s independent demo
phone_number→email map) should be resolved by having that utility import from
`MOCK_CREDENTIALS` directly rather than maintaining its own copy — a small,
low-risk deduplication appropriate for whichever P9.1.x phase touches mock
data next (not done in this architecture-only phase).

## Phase H — Backend Contract Review

### What already exists

`docs/BACKEND_API_CONTRACT.md` §2 (Authentication Endpoints) is
**substantially more complete than the frontend implementation** —
it already specifies, in detail: challenge-bound OTPs, refresh token
rotation with family-reuse detection, device session tracking,
`logout-all` with `token_revoke_version`, phone_number normalization via
`libphonenumber`, a full security-controls table, and a `next_step`
extension point reserved for future MFA. This audit's Phase A findings
about missing session revocation/device management describe the
**frontend implementation gap**, not a specification gap — §2 already
anticipates all of it. Phase H's job is therefore not "invent new
endpoints from scratch" but **(1) reconcile existing documented defaults
against the P9.0/P9.1.1 Configuration schema, and (2) identify the
genuine increment §2 does not yet cover.**

### Reconciliation — numeric mismatches found

| Concept | §2 (Backend Contract) | Configuration field | Status |
|---|---|---|---|
| OTP expiry | 10 minutes (§2.D) | `authentication.otp.ttl_seconds` = 300s (5 min) **[existing P9.0 field]** | **Mismatch.** Recommend reconciling the config default to 600s to match the already-documented backend contract, or updating §2.D if 5 minutes is the intended production value — a decision for whoever implements P9.1.x, not this phase. |
| OTP max attempts | 5 (§2.D, §2.G) | `authentication.otp.max_verify_attempts` = 3 **[proposed in this phase]**, frontend hardcodes 3 (`verify/page.tsx`) | **Three-way mismatch.** Recommend adopting 5 (the backend contract's value, since it's the more production-considered number) as the config default before implementation, and updating the frontend's hardcoded `MAX_ATTEMPTS` to read from it at the same time. |
| Refresh token lifetime | 30 days (§2.E) | `authentication.jwt_refresh_ttl_days` = 7 **[proposed in this phase]** | **Mismatch.** Recommend 30 to match the already-documented contract. |
| OTP resend cooldown | 60 seconds (§2.D) | `authentication.otp.resend_cooldown_seconds` = 60s **[existing P9.0 field]** | **Aligned.** No change needed. |
| OTP daily cap per phone_number | 10/day (§2.D, §2.G) | `authentication.otp.daily_limit_per_phone` = 10 **[proposed in this phase]** | **Aligned.** No change needed. |
| Access token lifetime | 15 minutes (§2.E) | `authentication.jwt_access_ttl_minutes` = 15 **[existing P9.0 field]** | **Aligned.** No change needed. |
| OTP daily cap per IP | 20/day (§2.G) | *(no corresponding field proposed in this phase)* | **Gap.** Add `authentication.otp.daily_limit_per_ip` (number, default 20, platform-owned, locked) to the Configuration Schema in the P9.1.x phase that wires this up. |
| OTP brute-force backoff | Exponential: 1s→2s→4s→8s→16s (§2.G) | `authentication.otp.retry_delay_seconds` = flat 5s **[proposed in this phase]** | **Design mismatch, not just a number.** The contract specifies an exponential backoff curve, not a flat delay. Recommend either (a) changing the field to `authentication.otp.retry_backoff_base_seconds` representing the curve's base (contract computes `base * 2^attempt`), or (b) keeping a flat delay in Configuration and updating §2.G to a flat model instead — a decision for the implementing phase, flagged here rather than silently resolved. |

None of these mismatches are fixed in this phase — per the brief, this
phase does not modify business logic or rewrite `BACKEND_API_CONTRACT.md`'s
existing content. They are logged here as the concrete reconciliation
checklist the first P9.1.x implementation phase must resolve before
registering the real fields in code.

### What §2 does not yet cover (genuine increment)

- **Demo/mock mode as a server-recognized concept.** §2 has no notion of
  `authentication.demo_login_enabled`/`mock_authentication_enabled` — today
  mock mode is a pure frontend concern (`NEXT_PUBLIC_USE_MOCK`). If demo
  login is ever meant to work against a real staging backend (rather than
  the frontend's local mock branch), §2 needs a documented
  `X-Demo-Mode` header or equivalent contract addition — not specified
  further here since it depends on a product decision (does demo mode ever
  talk to a real backend at all?) out of this phase's scope.
- **Provider selection surfaced to the client.** §2's `AuthResponse`/error
  schemas don't currently indicate *which* OTP/email/OAuth provider served
  a given request — useful for the Monitoring dashboards (Phase E, Panel
  6) but not required for the auth flow itself; a future addition to
  `AuthResponse` (e.g. `"provider": "twilio"`) would be additive per §2.0's
  own "superset responses" design principle, so this is a low-risk future
  contract extension, not a breaking one.
- **Country allow/block enforcement response.** §2.1 (`/auth/phone_number/start`)
  doesn't currently document a specific error code for
  "phone_number number's country is not permitted" — `authentication.allowed_countries`/
  `blocked_countries` (Configuration Schema Section 7) will need a new
  error code (e.g. `COUNTRY_NOT_PERMITTED`, 403) added to §2.H's table when
  implemented — additive, consistent with existing error-code conventions.
- **Session timeout / concurrent session cap enforcement signaling.** §2.7
  (`GET /auth/session`)/§2.8 (`GET /auth/devices`) already model the data
  needed for `authentication.max_concurrent_sessions` and
  `authentication.session_timeout_minutes` enforcement — no new endpoint
  needed, just business logic (in the backend, not this frontend repo)
  reading those config values when deciding whether to reject a new login
  or expire an idle session.
- **Fraud/risk/CAPTCHA signals** (Configuration Schema Section 9) have no
  representation in §2 at all yet — appropriately, since Provider
  Architecture (Phase F) for that category is itself schema-only pending a
  real provider decision. When a provider is chosen, its contract addition
  follows the same pattern as `2.A`'s `next_step` extension point — reserve
  a field now (see §2.0 design principle 5 already establishes exactly this
  extensibility pattern), implement later.

### Conclusion

`BACKEND_API_CONTRACT.md` §2 needs **no rewrite** — it is already the
correct shape for nearly everything this phase designed. The concrete
follow-up work is: (1) resolve the six reconciliation rows above before any
field is registered in code, (2) add the four small, additive contract
extensions listed, when their respective P9.1.x phase implements them.

## Phase I — Implementation Plan

The Authentication Control Center is designed; it is not built. Suggested
phased rollout for P9.1.2 onward, each following
`docs/PLATFORM_ARCHITECTURE_PRINCIPLES.md` §3 (Registry → Schema →
Validation → Service → API Contract → UI) and each independently
shippable:

### P9.1.2 — Reconcile & register the core schema

- Resolve the six numeric/design mismatches above.
- Register the ~20 highest-value proposed fields from the Configuration
  Schema (Sections 1–5: Core Toggles, OTP, Login Methods, Lockout,
  Session/Tokens) in `src/config/modules/authentication.ts`, bumping its
  version per `docs/P9.1.1_AUTHENTICATION_ARCHITECTURE.md` §9.
- Wire the frontend's currently-hardcoded values (OTP length/cooldown,
  `MAX_ATTEMPTS`, cookie max-age) to read from `configurationService`
  instead of inline literals — the first real consumer of the P9.0
  foundation from an existing feature, proving the "Registry First"
  principle end to end on a real screen.

### P9.1.3 — Mock data & User type extension

- Add `AccountStatus` to the `User` type (additive).
- Expand `src/lib/mock-data.ts`/`MOCK_CREDENTIALS` per Phase G above.
- Deduplicate `auth-redirect.ts`'s demo maps against `MOCK_CREDENTIALS`.

### P9.1.4 — Demo/mock mode as configuration

- Replace `NEXT_PUBLIC_USE_MOCK` gating with
  `authentication.demo_login_enabled`/`demo_accounts_visible`/
  `mock_authentication_enabled`, wired through
  `configurationService.resolveField()` — closing the audit's
  highest-severity finding (no safeguard beyond a public build flag).
- Add the Monitoring Panel 9 (Demo/Mock Usage) instrumentation as the
  first real Monitoring dashboard panel, since it doubles as a production
  safety check.

### P9.1.5 — Geography & phone_number policy

- Register Section 7 fields (allowed/blocked countries, phone_number
  normalization strictness, auto-detection, default country).
- Add the `COUNTRY_NOT_PERMITTED` error code to §2.H.

### P9.1.6 — Provider Architecture, first provider

- Implement the provider abstraction (Provider Architecture §2) for one
  category first — recommend Phone OTP (Twilio), since it's the platform's
  primary flow — before generalizing to Email/OAuth/Passkeys.
- Add `authentication.otp_provider` selection field.

### P9.1.7 — Security hardening

- Server-side rate limiting and lockout enforcement (Security
  Architecture §1–3) — requires real backend work, tracked but not
  scoped in detail here (out of this frontend repository's boundary).
- Cookie max-age synchronized to `authentication.jwt_access_ttl_minutes`.
- Device trust (§4) and session registry (§7–8) UI, once the backend
  endpoints in §2.6–2.9 are live.

### P9.1.8 — Fraud & risk (schema → real)

- Only after a real provider (CAPTCHA, risk-scoring) is selected — promote
  Section 9 fields from `lifecycle: 'testing'` to `'published'` one at a
  time as each is proven, per
  `docs/P9.0.1_ARCHITECTURE_HARDENING.md` §D.

### P9.1.9 — Console UI

- The first generic settings page (per
  `docs/PLATFORM_ROADMAP.md` P9.1), built against the by-then-complete
  `authentication` module schema — no hand-built form, generated from the
  registered fields' metadata (Rule 7).

Each phase above is independently valuable and independently shippable —
none blocks the others except where explicitly noted (Provider Architecture
before Security Architecture's device-trust UI needs real session data;
Console UI last, since it depends on everything else being real).
