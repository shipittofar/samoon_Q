# P10.4.9 — Legacy RBAC Migration Preparation: Close Demo Account Staff Identity Gap

Executes the migration preparation identified in
`docs/P10.4.8_LEGACY_COMPATIBILITY_AUDIT.md` (Phase H/Phase I task 1-2).
**This is not a removal phase.** `rbacService.hasPermission()`,
`ROLE_PERMISSIONS`, `LegacyPermission`, `legacyGranted`, `AuthGuard`'s
legacy fallback, and `UserRole`'s authorization use are all present and
byte-for-byte unmodified. The only change is mock fixture data plus a
new regression test proving those symbols are no longer *necessary* for
any console-capable demo account.

flagged (P10.4.8 only searched for accounts missing a `StaffMember`

|---|---|---|
| `staff-admin-01` | `admin@savor.com` | `StaffMember` exists, but `staffAssignmentService.getEffectiveAssignments('staff-admin-01')` returned `[]` |
| `staff-kitchen-01` | `kitchen@savor.com` | Same — `staff-kitchen-01` (distinct from `staff-kitchen-02`, which already had `assign-008`) had no assignment |

|---|---|---|---|---|
| `assign-014` | `staff-admin-01` | `admin` | manage | active |
| `assign-015` | `staff-kitchen-01` | `kitchen` | manage | active |

This was necessary because this phase's own Phase C instructions name
`owner@savor.com`, `admin@savor.com`, `manager@savor.com`,
`cashier@savor.com`, `kitchen@savor.com`, `staff@savor.com`, and

the regression test as specified would provably fail for `admin@savor.com`
and `kitchen@savor.com` — not because the test was wrong, but because
those two accounts had a real, pre-existing (unrelated to P10.4.8's
scope) fixture gap of the same kind this phase exists to close. Fixing
it here keeps the phase's own proof honest rather than either silently
narrowing the test's account list or shipping a test that fails.

**No file outside `staff.service.ts`/`staff-assignment.service.ts` was
touched to make this work** — no runtime logic changed.

## Before

**Why `staff@savor.com` and `multirole@savor.com` required `legacyGranted`**:
`useHasDashboardAccess()` (`src/hooks/index.ts`) calls
`resolveOwnershipIdentity(email)`, which calls
`staffService.findStaffMemberByEmail(email)`. Before this phase, neither
email existed in `MOCK_STAFF_LIST` — the lookup returned `undefined`,
`resolveOwnershipIdentity()` returned `{}`, and both the Owner branch
(`identity.owner` undefined) and the Staff branch
(`identity.staffMember` undefined) of `useHasDashboardAccess()` fell
through to `false`. The only remaining path that granted access was the
`legacyGranted` OR-branch:
`rbacService.hasPermission(user?.role ?? null, 'dashboard:access')` —
which worked because both accounts log in with a legacy `UserRole` of
`'staff'` (`MOCK_STAFF_USER.role`/`MOCK_MULTI_ROLE_USER.role` in
`src/lib/mock-data.ts`), and `STAFF_PERMISSIONS` in `rbac.service.ts`
includes `'dashboard:access'`.

`admin@savor.com`/`kitchen@savor.com` had a subtly different flavor of
the same problem: their `StaffMember` records did exist, so
`identity.staffMember` was truthy and `isStaffMemberEligible()` passed —
but `useHasDashboardAccess()`'s Staff branch specifically requires
`staffAssignmentService.getEffectiveAssignments(identity.staffMember.id).length > 0`,
and with zero assignment rows for either `staff-admin-01` or
`staff-kitchen-01`, that check also returned `false`. Access again came
only from `legacyGranted` (both log in with legacy roles — `'admin'` and
`'staff'` respectively — that `STAFF_PERMISSIONS`/`ADMIN_PERMISSIONS`
both grant `dashboard:access` to).

## After

`resolveOwnershipIdentity(email)` now finds a real `StaffMember` for all
four accounts, and `staffAssignmentService.getEffectiveAssignments(staffId)`
returns at least one active row for each:

- `staff@savor.com` → `staff-staffdemo-01` → 1 active assignment (`manager`, `tenant-savor-01`).
- `multirole@savor.com` → `staff-multirole-01` → 2 active assignments (`cashier` + `kitchen`, `tenant-savor-01`).
- `admin@savor.com` → `staff-admin-01` → 1 active assignment (`admin`, `tenant-savor-01`).
- `kitchen@savor.com` → `staff-kitchen-01` → 1 active assignment (`kitchen`, `tenant-savor-01`).

`useHasDashboardAccess()`'s Staff branch —
`isStaffMemberEligible(identity.staffMember) &&
staffAssignmentService.getEffectiveAssignments(identity.staffMember.id).length > 0`
— now evaluates `true` for all four independent of `legacyGranted`.
`resolveStaffAssignmentPermissions()` (used by `usePermissions()`
elsewhere) also now resolves a non-empty `P7Permission` set for them,
since it iterates the same `StaffAssignment` rows and looks up
`ROLE_PERMISSION_MAP[assignment.role]` for each.

## Test Proof

`src/test/p10.4.9-rbac-migration.test.ts` (19 tests, all passing):

- **Phase B — fixture consistency audit** (9 tests): for each of the 7
  target accounts, asserts the `StaffMember` resolves (or the account is
  an Owner, which doesn't need one), an effective `StaffAssignment`
  exists, and `resolveOwnershipDrivenPermissions()` returns a non-empty
  `P7Permission` set. Two more tests specifically assert
  `multirole@savor.com` resolves exactly `['cashier', 'kitchen']` (two
  distinct assignments, not one) and `staff@savor.com` resolves exactly
  `['manager']`.
- **Phase C — regression proof** (10 tests): for every one of the 7
  accounts, first asserts the legacy precondition —
  `rbacService.hasPermission('customer', 'dashboard:access')` is `false`
  — then constructs the user with `role: 'customer'` (the one legacy
  `UserRole` that never grants `dashboard:access`, so `legacyGranted`
  inside the hook is provably `false` for this call) and asserts
  `useHasDashboardAccess()` still returns `true`. Two more tests go
  further for `staff@savor.com`/`multirole@savor.com` specifically,
  re-asserting the legacy precondition and directly inspecting their
  resolved `StaffMember`/assignments. A final sanity-check test confirms
  a genuinely unknown email (no fixture at all) is still correctly
  denied — proving the fixture additions didn't broaden access beyond
  the intended 7 accounts.

This is the exact technique already established in
`src/test/p10.3.1-dashboard-access-audit.test.ts` for `accountant@savor.com`
(constructing the user with a legacy role that can never grant the
permission, to isolate the ownership/StaffAssignment branch) — reused
here at the full account-list scale requested by this phase, rather than
re-derived.

**What this proves**: `legacyGranted` can eventually be removed from
`useHasDashboardAccess()` without regressing any of the 7 accounts this
test covers, *once* this same fixture state ships to whatever backs
production data (today, this is mock-only — see Diff Safety). It does
not yet prove removal is safe for every possible account (only the ones
enumerated), and it does not itself remove anything — per this phase's
explicit scope, `legacyGranted` remains in the code, still doing exactly
what it did before.

## Remaining Removal Blockers

Per `docs/P10.4.8_LEGACY_COMPATIBILITY_AUDIT.md` Phase I, still **not**
safe to remove — this phase does not change that:

- **`legacyGranted`** (`src/hooks/index.ts:355`) — this phase proves it's
  no longer the *deciding* factor for the 7 accounts tested, but it is
  still live code, still executes on every render of
  `useHasDashboardAccess()`, and removing it is a separate future phase
  (P10.4.8's migration task 3).
- **`rbacService.hasPermission()`** and its five backing tables
  (`ROLE_PERMISSIONS`, `CUSTOMER_PERMISSIONS`, `STAFF_PERMISSIONS`,
  `OWNER_PERMISSIONS`, `ADMIN_PERMISSIONS`) — untouched; `legacyGranted`
  is still their only caller and still calls them on every render.
- **`LegacyPermission`** — untouched; still required by
  `rbacService.hasPermission()`'s signature and `AuthGuard.requiredPermission`.
- **`AuthGuard`'s legacy fallback branch** (`AuthGuard.tsx:63`) —
  untouched; still structurally present (though still behaviorally dead,
  as documented in P10.4.8 Phase B/F — unchanged by this phase).

These will be removed in a later phase, in the order P10.4.8 Phase I
specified — this phase only supplies the proof that removal order
depends on.
