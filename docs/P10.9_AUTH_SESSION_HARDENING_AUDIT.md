# P10.9 — Authentication Session Hardening & Real Backend Readiness Audit

Full authentication/session lifecycle audit after the OTP flow split
(P10.8) and registration contract split (P10.9-registration). Finds and
fixes confirmed lifecycle inconsistencies in `AuthBootstrapper`; documents
everything else as already-correct or as a real-backend-migration gap.

No RBAC permission calculation, `ROLE_PERMISSION_MAP`,
`useHasDashboardAccess()`, or authorization logic was touched. No new auth
provider or session source was introduced.

## 1. Current Authentication Graph

```
Identity sources (existing, unchanged):
  authService.login()     → { user, tokens, p7Roles?, ownership?, staffAssignments? }
  authService.verifyOTP() → { is_new_user: true }
                           | { is_new_user: false, user, tokens, p7Roles?, ownership?, staffAssignments? }
  authService.register()  → { user, tokens, p7Roles?, ownership?, staffAssignments? }
  authService.getMe()     → { ...User, tenantRoles?, ownership?, staffAssignments? }

Consumers:
  useLogin()        → setUser() + setTenantRoles(p7Roles)
  useVerifyOTP()     → narrows on is_new_user; only the false branch
                       calls setUser()/setTenantRoles(); true branch is a
                       pure redirect, touches no store (P10.8)
  useRegister()      → setUser() + setTenantRoles(p7Roles)
  AuthBootstrapper   → getMe() on boot; setUser() + setTenantRoles(tenantRoles)
                       (P10.7); now also clearSession() on failure (P10.9, this phase)
  useLogout()        → full teardown via onSettled (reference implementation)

Token storage (single source, axios.instance.ts):
  localStorage['access_token'] / localStorage['refresh_token']
  + one mirrored cookie (Edge middleware read path)
  getAccessToken() / setTokens() / clearTokens() — the only interface
```

Every identity-producing call site funnels `tenantRoles`/`p7Roles` into
`useRbacStore.setTenantRoles()` and the user into `useAuthStore.setUser()`
— one authorization store, one identity store, no parallel session state.

## 2. Session Lifecycle Diagram

```
New user:
  Phone input → sendOTP → verify (is_new_user=true) → NO session created
    → /complete-profile → register() → session created (tokens+user+roles)

Existing user:
  Phone input → sendOTP → verify (is_new_user=false) → session created once

Session restore (browser refresh):
  App boot → AuthBootstrapper effect #2 → getAccessToken()
    → none: setLoading(false), stay logged out
    → present: getMe()
        → success: setUser() + setTenantRoles(tenantRoles) + getFavorites()
        → failure: clearSession() [P10.9 fix — previously left stale state]

Logout (explicit):
  useLogout() → onSettled: logout() + RBAC/branch/cart/dine-in/
    favorites/recently-viewed reset + qc.clear()

Logout (forced — token refresh failure):
  axios.instance.ts response interceptor → clearTokens() +
    dispatchEvent('auth:logout') → AuthBootstrapper effect #1 listener →
    clearSession() [P10.9 fix — previously only setUser(null)]
```

Both logout paths now converge on functionally identical teardown
(`clearSession()` mirrors `useLogout()`'s `onSettled` sequence field-for-field).

## 3. Bugs Discovered (traced root cause, all three fixed)

### Bug 1 — Incomplete `auth:logout` event cleanup

**Location:** `src/providers/index.tsx`, `AuthBootstrapper`.

**Root cause:** the `'auth:logout'` listener (dispatched by
`axios.instance.ts` when a token-refresh attempt itself fails) called only
`setUser(null); clearSentryUser()`. Compared line-by-line against
`useLogout()`'s `onSettled` in `src/hooks/index.ts`, six cleanup steps were
missing: RBAC store reset, active branch reset, cart clear, dine-in table
clear, favorites clear, recently-viewed clear, and `queryClient.clear()`.

**Failure scenario:** a refresh-token expiry mid-session left the user
logged out at the identity layer but with the previous user's RBAC roles,
cart contents, and React Query cache still resident — the next login
(even as a different account, e.g. Phase G Scenario 1) could read stale
permissions or cart items until an unrelated full page reload happened to
clear them.

### Bug 2 — Failed `getMe()` did not clear the invalid session

**Location:** same file, bootstrap effect's `.catch()`.

**Root cause:** on `getMe()` rejection (expired/invalid/revoked token
found in storage at boot), the handler only called `setLoading(false)`. It
never called `clearTokens()`, so the invalid token stayed in `localStorage`
indefinitely and would be resent on every subsequent request until an
explicit logout, and any stale Zustand state (RBAC, cart, etc.) from a
prior session was never reset either.

**Failure scenario:** Phase G Scenario 5 (expired token) — a user whose
token expired between sessions would reload the app, silently fail
`getMe()`, and be left in an inconsistent half-state: `isAuthenticated:
false` at the identity layer, but an unexpired-looking token still in
storage and no RBAC/cart reset.

### Bug 3 — StrictMode double-invoke permanently drops the `auth:logout` listener

**Location:** same file — the `auth:logout` listener registration was
originally inside the same `booted`-guarded effect as the one-time
`getMe()` bootstrap.

**Root cause:** Next.js 15.1.0 (`package.json`) has no
`reactStrictMode: false` override in `next.config.ts`, so React 18
StrictMode's dev-only double-invoke (mount → cleanup → mount) is active.
The `booted` ref persists across that cycle. Sequence: mount #1 adds the
listener and sets `booted.current = true`; cleanup #1 removes the
listener; mount #2 hits `if (booted.current) return` immediately —
`addEventListener` is never reached again. Net result: zero listeners
attached in dev after the double-invoke settles, silently swallowing every
subsequent forced-logout event.

**Failure scenario:** in dev, a token-refresh failure after boot would
never trigger any cleanup at all — not even the incomplete Bug-1 version —
because the listener was gone.

## 4. Fixes Implemented

All in `src/providers/index.tsx`, `AuthBootstrapper`:

1. Split into two independent `useEffect`s:
   - **Unguarded** effect solely for `window.addEventListener('auth:logout', clearSession)` — re-attaches correctly on every mount, including StrictMode's second one, since it carries no `booted` guard (fixes Bug 3).
   - **`booted`-guarded** effect for the one-time `getMe()` identity-restore bootstrap only (unchanged one-shot semantics).
2. Introduced `clearSession()`, a single function performing the exact
   `useLogout()`-equivalent teardown (`setUser(null)`, `clearSentryUser()`,
   `clearTokens()`, `useRbacStore._resetStore()`,
   `useBranchStore.setAdminActiveBranch(null)`, `useCartStore.clearCart()`,
   `useDineInStore.clearTable()`, `useFavoritesStore.setFavorites([])`,
   `useRecentlyViewedStore.clear()`, `queryClient.clear()`), called from
   both the `auth:logout` listener (fixes Bug 1) and the `getMe()` catch
   handler (fixes Bug 2).
3. Replaced the hardcoded `localStorage.getItem('access_token')` string
   literal with `getAccessToken()` from `axios.instance.ts` — removes a
   duplicate-source-of-truth smell (same key, but now the single canonical
   accessor is used everywhere).

No other file needed a code change (see §6 for audited-clean areas).

## 5. Security Findings

- **localStorage tampering**: an attacker with local storage write access
  could forge a token or `RegisterData`/RBAC-adjacent client state, but
  this was already true before P10.9 and is inherent to any
  localStorage-token design — the backend is the sole authorization
  authority (`ROLE_PERMISSION_MAP` and all `usePermissions()` derivations
  are UX-only gates, never enforcement). No change in this phase alters
  that boundary.
- **Token leakage**: confirmed single storage location
  (`localStorage` + one mirrored cookie for Edge middleware), zero
  `sessionStorage` usage anywhere in `src/services`, `src/stores`,
  `src/providers` — no duplicate/orphaned token copies to leak.
- **Session fixation**: `clearSession()` now unconditionally clears tokens
  and all derived state before any new login can populate it — a stale
  token from a prior session (Bug 2) can no longer coexist with, or be
  silently reused by, a subsequent session.
- **Stale user state**: closed by Bugs 1–2's fixes; `qc.clear()` in
  `clearSession()` also prevents React Query from serving cached
  authenticated-user data (e.g. order history, profile) after logout.
- **Unauthorized RBAC persistence**: `useRbacStore._resetStore()` is now
  reachable from every session-ending path (explicit logout, forced
  logout, failed restore), not just explicit logout — no path leaves
  `tenantRoles` resident after the identity layer says logged-out.

Reiterated per task instruction: none of this expands or weakens actual
authorization — the backend remains the sole authority; every
`ROLE_PERMISSION_MAP`/`usePermissions()` check here is UX convenience only.

## 6. Areas Audited, No Fix Needed

- **`useNotificationWebSocket()`** (`src/hooks/client.ts`): already
  reactive to `useAuthStore`'s `isAuthenticated` flag via a `useEffect`
  keyed on it; disconnects automatically in the cleanup when it flips to
  `false`. Both logout paths flip it correctly (`logout()`/`setUser(null)`),
  so WebSocket teardown was already correct.
- **`AdminTenantSwitcher.tsx`**: already calls `qc.clear()` on tenant
  switch — query-cache isolation across tenant switches was already
  correct.
- **Token storage**: single canonical location, no duplicates
  (§5, confirmed by full read of `axios.instance.ts`).
- **Refresh-queue dedup** (`isRefreshing`/`failedQueue` in
  `axios.instance.ts`): correctly serializes concurrent 401s into one
  refresh call; not altered.

## 7. Real Backend Readiness Gaps (documentation only, cross-referencing P10.6/P10.5.5)

Carried forward, not re-derived, from `docs/P10.6_RBAC_REAL_BACKEND_MIGRATION_PLAN.md`
and `docs/P10.5.5_RBAC_REAL_MODE_SECURITY.md`:

- `authService.getMe()`/`login()`/`verifyOTP()`/`register()` are
  synchronous mock functions today; real backend calls will be async over
  the network with real latency/failure modes — `AuthBootstrapper`'s
  `.then()/.catch()` shape already accommodates this (no change needed at
  the call-site level), but retry/backoff behavior for a *flaky* (as
  opposed to *failing*) `getMe()` is not yet designed.
  - **Migration note (P10.9 addition):** `clearSession()`'s only failure
    trigger today is a *rejected* `getMe()` promise. A real backend may
    also return transient 5xx/network errors indistinguishable from an
    invalid token at the `authService` layer; before flipping
    `NEXT_PUBLIC_USE_MOCK=false`, `getMe()`'s error path should
    distinguish "token invalid" (safe to `clearSession()`) from "network
    unreachable" (should NOT clear a possibly-valid session) — this
    phase does not implement that distinction since it requires backend
    error-shape knowledge not yet available.
- `tenantRoles`/`ownership`/`staffAssignments` on the `AuthSessionPayload`
  contract (P10.6 Phase B target) remain optional fields threaded through
  every identity call site (`login`, `verifyOTP`, `register`, `getMe`) —
  confirmed still intact and unbroken by this phase's changes.
- Ownership Resolution and StaffAssignment remain synchronous
  mock-data lookups (`resolveOwnershipIdentity()`); converting these to
  async backend calls is explicitly out of scope per this task's rules
  ("Do not convert StaffAssignment/ownership resolution to async yet" —
  P10.7's rule, still honored here).

## 8. Migration Recommendations

1. Before `NEXT_PUBLIC_USE_MOCK=false`: give `authService`'s real-mode
   branch a way to distinguish token-invalid vs. transient-network errors
   in `getMe()`, so `AuthBootstrapper.clearSession()` isn't triggered by a
   flaky network blip (see §7).
2. No changes to `useLogout()`, `ROLE_PERMISSION_MAP`, or any permission
   hook are required for backend migration — the authorization surface is
   already backend-agnostic.
3. Token storage/refresh-queue design (`axios.instance.ts`) requires no
   changes for real-backend readiness — already speaks to a generic
   `API_BASE_URL` and a generic refresh endpoint contract.
