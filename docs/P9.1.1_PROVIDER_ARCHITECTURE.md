# P9.1.1 — Provider Architecture

> Phase F of P9.1.1. Design only — no implementation, no SDK integration.
> Authentication delivery mechanisms (SMS/OTP, email, OAuth, passkeys)
> become pluggable providers behind a stable interface, the same way
> `docs/P9.0.1_ARCHITECTURE_HARDENING.md` §C designed Secret Management as
> an indirection layer rather than a concrete vault integration.
>
> Last updated: 2026-07-04

---

## 1. Why providers are plugins, not hardcoded integrations

Savor is a multi-tenant platform; different tenants (and different
deployment regions) will need different SMS/email/OAuth providers for
cost, deliverability, or compliance reasons. Hardcoding "Twilio" into
`auth.service.ts` would repeat exactly the pattern the P9.0 audit found
and P9.0 exists to prevent (`docs/P9.0_PLATFORM_CONFIGURATION_AUDIT.md`).
Instead, each provider category is a `ConfigFieldType: 'select'` field
(which provider is active) plus provider-specific configuration fields
(mostly `'secret'`-typed, per the Secret Management architecture) — the
same pattern already shipped for Payments (`payments.enabled_providers`,
`payments.stripe_secret_key`) and Notifications
(`notifications.email_provider`, `notifications.sms_provider`) in P9.0.

## 2. The abstraction

```
AuthProviderCategory        ('phone_otp' | 'email' | 'oauth' | 'passkey')
     ↓
AuthProviderDefinition       (id, category, displayName, configSchema, capabilities)
     ↓
AuthProviderRegistry          (parallel structure to PlatformConfigurationRegistry —
                               NOT the same registry; providers are a plugin catalog,
                               configuration values about *which* provider is active
                               and its credentials live in the `authentication` /
                               `notifications` Configuration modules)
     ↓
Runtime Resolver               (backend-only — resolves the active provider for a
                               tenant and dispatches the actual send/verify call)
```

Illustrative shape (no code introduced in this phase):

```ts
interface AuthProviderDefinition {
  id: string                              // 'twilio' | 'messagebird' | 'vonage' | 'firebase' | ...
  category: 'phone_otp' | 'email' | 'oauth' | 'passkey'
  displayName: string
  capabilities: string[]                  // e.g. ['send_otp', 'verify_otp'] vs. ['send_otp'] only
  configFields: string[]                  // dotted ids into the authentication/notifications modules, e.g. ['payments.stripe_secret_key']-style secret refs
  healthCheckable: boolean
}
```

This mirrors `ConfigModuleDefinition` deliberately (id, category,
capabilities-as-metadata) without being a second `PlatformConfigurationRegistry`
— providers are a **catalog of what integrations exist**, while
Configuration Registry fields (already covered in the Configuration Schema
doc) are **which one is active and its credentials**. Keeping these
separate avoids Rule 3 duplication: the provider catalog doesn't know
tenant-specific values, and the Configuration Registry doesn't know
provider implementation details.

## 3. Phone OTP Providers

| Provider | Capabilities | Notes |
|---|---|---|
| Twilio | send_otp, verify_otp (Twilio Verify API) | Twilio's own Verify product can own attempt-counting server-side, which — if adopted — would let `authentication.otp.max_verify_attempts` become a pass-through configuration to Twilio rather than an independently-enforced counter. Documented as an option, not a decision. |
| MessageBird | send_otp | SMS-only; verify logic stays in Savor's own backend. |
| Vonage | send_otp, verify_otp | Similar to Twilio Verify. |
| Firebase (Phone Auth) | send_otp, verify_otp, session issuance | Notably different: Firebase Phone Auth issues its own ID tokens, which would need to be exchanged for a Savor-issued JWT at the backend boundary — an adapter concern, not a Configuration concern. |

Selection field: `authentication.otp_provider` (proposed addition to the
Configuration Schema, Section 2 — omitted from the 41-field count in that
doc since it's provider-selection, categorized here instead; a future
schema revision folds it in as `select`, default `'twilio'`).

## 4. Email Providers

Already modeled in P9.0's `notifications` module
(`notifications.email_provider`: SendGrid/SES/Postmark). Authentication
reuses this exact field via its `'soft'` dependency on `notifications`
(§Architecture doc §1) rather than declaring its own — verification and
password-reset emails are notifications, not a distinct authentication
delivery channel. This is a deliberate non-duplication decision.

## 5. OAuth / Social Providers

| Provider | Notes |
|---|---|
| Google | Most common first target; standard OIDC flow. |
| Apple | Required by App Store policy if a native app ever ships with any other social login. |
| Microsoft | Relevant for B2B/enterprise tenants (Azure AD tenants logging in with a work account). |
| GitHub | Lower priority for a restaurant SaaS; included per the brief's example list, likely useful only for internal/admin accounts, not customer-facing login. |

Each is a boolean toggle field under `authentication.social_login_enabled`'s
umbrella (Configuration Schema Section 3) plus provider-specific OAuth
client id/secret (`'string'`/`'secret'`-typed fields) — not enumerated
individually in the Configuration Schema doc to avoid speculative field
proliferation (Rule 10); added one provider at a time as each is actually
implemented, following the Developer Guide's "Registry → Schema" order.

## 6. Passkeys (WebAuthn)

Schema-reserved (`authentication.passkeys_enabled`, Configuration Schema
Section 3) but architecturally distinct from the other categories: a
passkey is a per-device credential registered directly with the browser's
platform authenticator, not a provider Savor calls out to — there is no
"passkey provider" in the same sense as Twilio/SendGrid. The only
provider-shaped decision is which relying-party library the backend uses
(e.g. `@simplewebauthn/server`) — an implementation detail with no
Configuration Registry surface beyond the on/off flag.

## 7. Future Providers

The category enum (`'phone_otp' | 'email' | 'oauth' | 'passkey'`) is
intentionally not closed against future additions — a fifth category (e.g.
`'biometric'` for native mobile, if Savor ever ships one) is a pure
addition, not a breaking change, following the same open-ended pattern as
`SecretReference.provider` in `docs/P9.0.1_ARCHITECTURE_HARDENING.md` §C.

## 8. What ties this to Platform Configuration

Every provider selection and every provider credential is, without
exception, a `ConfigFieldDefinition` — there is no provider-specific config
file, env var, or hardcoded SDK initialization outside the Configuration
Registry. This is the same principle Payments already established in P9.0
(`payments.stripe_publishable_key`, `payments.stripe_secret_key`) — Provider
Architecture supplies the *catalog of what's pluggable*; Configuration
Registry supplies *the values*. Neither layer is implemented in this phase.
