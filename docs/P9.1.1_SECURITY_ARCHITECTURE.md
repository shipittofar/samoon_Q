# P9.1.1 — Security Architecture

> Phase D of P9.1.1. Design only — no implementation. Every mechanism below
> is grounded in a specific gap identified in
> `docs/P9.1.1_AUTHENTICATION_AUDIT.md` and specifies the target
> architecture, configured through the fields in
> `docs/P9.1.1_AUTH_CONFIGURATION_SCHEMA.md`.
>
> Last updated: 2026-07-04

---

## 1. Rate Limiting

**Today**: `src/lib/rate-limit.ts`'s in-memory sliding window
(`LOGIN_LIMIT`/`OTP_LIMIT`/`PASSWORD_RESET_LIMIT`) is client-side only —
resets on reload, provides UX throttling, not security.

**Target architecture**: a two-tier model.

1. **Client-side** (keep, unchanged) — the existing rate limiter remains as
   the first line of UX feedback (immediate "too many attempts" toast
   without a round trip). It is explicitly documented as non-authoritative.
2. **Server-side** (new, backend-owned) — the real enforcement point. Keyed
   by `(identifier, action)` where `identifier` is phone/email/IP depending
   on the action, using a distributed counter (Redis or equivalent) with a
   sliding or fixed window matching the relevant config field
   (`authentication.otp.daily_limit_per_phone`,
   `authentication.max_login_attempts`, `authentication.otp.retry_delay_seconds`).
   The backend is the single source of truth; the frontend's rate limiter
   is a courtesy, never trusted for a security decision.

Every server-side rate-limit response includes a `retryAfterSeconds` the
frontend can use to disable the relevant button precisely, rather than the
generic "try again later" copy the audit found today.

## 2. Brute Force Protection

Composes rate limiting (§1) with the lockout fields (Section 4 of the
Configuration Schema): after `authentication.max_login_attempts` failures
for a given identifier within a rolling window, the account (or, for
unregistered identifiers, the IP) is locked for
`authentication.lockout_duration_minutes`. Repeated lockouts within a
longer rolling window (tracked separately, not just "count of failed
attempts") escalate to a permanent lock at
`authentication.permanent_lock_threshold`, requiring manual/support
intervention to clear — this two-tier (temporary → permanent) model
prevents an attacker from simply waiting out the cooldown indefinitely
while still giving a legitimate user who mistyped their password a few
self-service retries.

## 3. OTP Abuse Protection

Three independent controls, all schema-ready (Configuration Schema Section
2):

- **Verify-attempt cap** (`authentication.otp.max_verify_attempts`) — limits
  guesses against one issued code before it's invalidated and a new one
  must be requested. Closes the audit's finding that today's `MAX_ATTEMPTS`
  is a client-side-only, page-reload-resettable `useState`.
- **Retry delay** (`authentication.otp.retry_delay_seconds`) — a minimum
  gap between verify submissions, defeating rapid scripted guessing within
  a code's TTL window even if the attempt cap were somehow bypassed.
- **Daily limit per phone** (`authentication.otp.daily_limit_per_phone`) —
  caps total OTP sends per number per rolling 24 hours, protecting against
  SMS-pumping fraud (an attacker using someone else's phone number to
  trigger paid SMS sends) independent of whether any single session's
  attempts stay under the per-code cap.

All three must be enforced server-side; none can be meaningfully enforced
client-side (an attacker controls their own client).

## 4. Device Trust

Two related but distinct fields (Configuration Schema Section 4):

- `authentication.device_verification_enabled` — an unrecognized device
  triggers a secondary verification step (e.g. "confirm via the email/SMS
  we just sent") before the login completes, regardless of whether the
  password/OTP was correct.
- `authentication.trusted_devices_enabled` +
  `authentication.trusted_device_ttl_days` — once a device passes
  verification, it may be marked trusted (a signed device token, distinct
  from the session token, stored client-side) so subsequent logins from
  that device skip the OTP/verification challenge until the TTL expires.

Device identity itself (fingerprinting mechanism) is a backend/provider
concern not specified here — this document only fixes the configuration
surface (on/off, TTL) and the behavioral contract (what device trust does
and doesn't skip). Device trust never skips the underlying
password/OTP check itself, only the *additional* verification step —
it is a friction reducer, not an authentication bypass.

## 5. Session Security

- Access tokens remain short-lived (`authentication.jwt_access_ttl_minutes`,
  existing field, default 15 min) and are refreshed via the existing
  single-flight rotation flow in `axios.instance.ts` — that mechanism is
  sound and is not being redesigned.
- **Target fix** for the audit's cookie/localStorage duplication finding:
  the non-HttpOnly cookie mirror should carry an expiry synchronized to
  `authentication.jwt_access_ttl_minutes` rather than a hardcoded 7 days —
  a config-driven value instead of a second, disconnected literal. This is
  flagged as a P9.1.x implementation item (see Implementation Plan), not a
  change made in this architecture-only phase.
- Refresh token lifetime becomes config-driven via the new
  `authentication.jwt_refresh_ttl_days` field, replacing the implicit 7-day
  assumption baked into the cookie today.

## 6. Token Rotation & Refresh Policy

The existing rotation behavior (rotate access token always, rotate refresh
token when the backend supplies a new one) is architecturally sound and is
kept as-is. The refinement this phase adds: refresh token rotation should
be **strict** (the old refresh token is invalidated the moment a new one is
issued, and reuse of an already-rotated refresh token is treated as a
signal of token theft and triggers `authentication.max_concurrent_sessions`-
style revocation of all sessions for that user) — a standard "refresh token
reuse detection" pattern, schema-ready via the audit trail
(`ConfigurationAudit` records the security-posture-relevant field changes;
reuse-detection *events* themselves belong in the Monitoring dashboards,
Phase E, not Configuration).

## 7. Concurrent Sessions

`authentication.max_concurrent_sessions` (default `0` = unlimited) caps how
many active sessions a single user may hold simultaneously. When a new
login would exceed the cap, the oldest session is revoked (or the login is
rejected, depending on a future UX decision — not specified here, this
phase fixes the configuration surface and policy intent, not the exact UX).
This requires a session registry on the backend (§8) — the frontend today
has no concept of "list of my active sessions" at all (audit finding).

## 8. Account Lock / Logout All Devices / Session Revocation

All three require a backend-held session registry — genuinely absent today,
not just unimplemented in the UI. Target shape (Console-facing concept, not
built in P9.1.1):

- A user (or a Platform Administrator, for support purposes) can view a
  list of active sessions (device, location, last-active timestamp).
- "Log out this device" revokes one session (refresh token) without
  affecting others.
- "Log out all devices" revokes every refresh token for that user —
  the dispatch mechanism already exists client-side
  (`window` `'auth:logout'` event in `axios.instance.ts`) and needs no
  frontend redesign; it just needs a backend endpoint to call before
  dispatching that event platform-wide instead of only on the current tab.
- Account lock (temporary or permanent, §2) is visible in this same list as
  a distinct account-level state, separate from any individual session.

## 9. Password Policy

Not deeply redesigned in this phase (password login is the fallback flow,
phone+OTP is primary) — the existing zod min-8-character rule in
`/register` remains the baseline. Schema-ready extension point: a future
`authentication.password_policy` object field (type `'object'`, e.g.
`{ minLength, requireNumber, requireSymbol, maxAgeDays }`) can be added to
Section 3 (Login Methods) without any core architecture change, once a real
need (e.g. an enterprise tenant requiring a stricter policy) justifies it —
not added speculatively now, per Rule 10.

## 10. Phone Verification

Unchanged mechanism (OTP), hardened per §3. The
`authentication.phone_normalization_strict` field (Configuration Schema
Section 7) is the toggle for upgrading from today's blunt length heuristic
to real per-country validation — staged as an opt-in toggle specifically so
existing tenants with already-registered "loose" phone numbers aren't
retroactively broken by tightening validation platform-wide on a flag flip.

## 11. Phone Change Flow

Not present in the audited codebase at all. Target flow: changing a
verified phone number requires OTP verification of the *new* number before
the change takes effect, and triggers a notification to the *old* number
(if still active) as a fraud signal — mirroring the "logout all devices"
principle that changing a primary identifier is itself a security-relevant
event worth surfacing, not a silent update. No config field is needed for
this — it's a fixed security invariant, not a tunable policy.

## 12. Delete Account Flow

Not present in the audited codebase. Target flow: requires re-authentication
(password or OTP) immediately before deletion, a confirmation step, and
(per data-retention requirements, out of scope for this doc) a grace period
before permanent data erasure — the grace period, if configurable, would be
a `system` module field (retention policy), not an `authentication` field,
since it concerns data lifecycle, not identity/authentication.

## 13. Recovery Flow

`forgotPassword`/`resetPassword` already exist
(`src/services/auth.service.ts`) for the email/password flow. The
phone-first flow has no equivalent "forgot access to my phone number"
recovery path today — a genuine gap. Target: a support-mediated recovery
flow (verify identity via an alternate channel — email on file, or a
manual support process) rather than a fully self-service one, since a phone
number is often the *only* identifier for a phone-first account and a
self-service "I lost my phone" flow is inherently an account-takeover risk
surface if not paired with a secondary factor.

## 14. Suspicious Login Flow

Composes device trust (§4) and rate limiting (§1): a login attempt from a
new device, a blocked/geo-restricted country (Configuration Schema Section
7), or matching a risk-scoring signal (Section 9, schema-ready) can trigger
an elevated challenge (step-up OTP even on an otherwise-successful
password login) rather than an outright block — configurable per-tenant
via `authentication.risk_scoring_enabled` once a real provider exists
(Provider Architecture, Phase F). Every suspicious-login event is a
Monitoring dashboard entry (Phase E), regardless of whether it was
ultimately allowed or blocked.

---

## Summary — what changes now vs. what's designed for later

**Nothing changes in this phase.** Every mechanism above is a target
architecture, gated on:
1. A real backend to enforce server-side rate limiting, lockout, and
   session registries (none of which exist in this frontend-only
   repository today).
2. The 41 proposed configuration fields
   (`docs/P9.1.1_AUTH_CONFIGURATION_SCHEMA.md`) being registered.
3. A Secret Management implementation (`docs/P9.0.1_ARCHITECTURE_HARDENING.md`
   §C) for provider credentials (Phase F).

See `docs/P9.1.1_IMPLEMENTATION_PLAN.md` for the phased order these land in.
