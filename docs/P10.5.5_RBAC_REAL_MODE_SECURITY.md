# P10.5.5 — RBAC LocalStorage & Real-Mode Security Audit

Documentation-only. No backend or code behavior changes. Analyzes what
happens to the two live, client-persisted authorization sources —
`tenantRoles` and `userOverrides` (`useRbacStore`, `src/stores/index.ts`)
— under mock mode versus a real backend, and what must exist before
`NEXT_PUBLIC_USE_MOCK=false` is safe to run against production traffic.

## 1. Where `tenantRoles` and `userOverrides` Are Populated

### `tenantRoles`

Written in exactly two places:

1. **Login** (`src/hooks/index.ts` — `useLogin()` `:475-483`,
   `useVerifyOTP()` `:508-515`): on a successful `authService.login()` /
   `authService.verifyOTP()`, if the response includes a non-empty
   `p7Roles` array, `useRbacStore.getState().setTenantRoles(tenantId, p7Roles)`
   is called.
2. **Tenant switch** (`AdminTenantSwitcher.tsx`): re-seeds `tenantRoles`
   for the newly selected tenant.

### `userOverrides`

Written in exactly two places, both **Console admin UI, both 100%
client-side with no network call**:

- `src/app/console/users/[id]/page.tsx:124,131,135` — `setUserOverride(...)`
  called directly from the page's local state on save, no `api.post`/
  `fetch` in the same function.
- `src/app/console/permissions/[userId]/page.tsx:130` —
  `saveChanges()` calls `setUserOverride(userId, tenantId, [...currentAllow], [...currentDeny])`
  directly; the function contains no request to any endpoint. `ENDPOINTS`
  (`src/services/endpoints.ts` — used everywhere else the app talks to a
  backend) is not imported by this file's save path.

**Finding: today, granting or revoking a permission override in the
Console UI is a pure client-side write.** Nothing calls a backend to
persist, validate, or authorize the change; it only ever reaches
`localStorage` via the `persist` middleware.

## 2. Backend Validation — Does It Exist?

**No.** Neither write path above makes a network request. There is no
`ENDPOINTS.RBAC.*` or `ENDPOINTS.PERMISSIONS.*` entry in
`src/services/endpoints.ts` at all — confirmed by grep. The mock/real split
that exists everywhere else in this codebase (e.g. `auth.service.ts`'s
`if (mockActive()) { ... } else { await api.post(...) }` pattern) **does
not exist for `tenantRoles`/`userOverrides` writes** — there is no `else`
branch, mock or real, that calls a backend for either.

## 3. Can LocalStorage Override Permissions?

**Yes, directly, today, in any mode.** `useRbacStore` persists via
Zustand's `persist` middleware under the key `samoon-rbac`
(`src/stores/index.ts:568`) with **no `partialize`** — the entire store
state, including `tenantRoles` and `userOverrides`, is serialized to
`localStorage` verbatim and rehydrated on every page load with no
integrity check, signature, or expiry.

Consequence: a user with browser devtools access can run
```js
localStorage.setItem('samoon-rbac', JSON.stringify({
  state: { tenantRoles: [{ tenantId: '<their-tenant-id>', roles: ['owner'] }], ... },
  version: 0,
}))
```
and reload to grant themselves the `owner` P7 role for that tenant client-side.
`usePermissions()` will then return the full owner permission set, and
every `usePermission()`/`PermissionGuard`-gated UI element will render as
if they held that role — **because nothing on the client re-validates
`tenantRoles` against a trusted source.**

This is a `localStorage`-tampering risk, not a bug in the permission
*resolution* logic itself — `usePermissions()` correctly computes
permissions from whatever `tenantRoles`/`userOverrides` say, exactly as
designed. The risk is that those two inputs are currently
**client-authoritative** rather than **client-cached-from-server**.

## 4. What Happens When `NEXT_PUBLIC_USE_MOCK=false`

Traced `authService.login()` (`src/services/auth.service.ts:88-116`):

```ts
async login(credentials: LoginCredentials): Promise<{ user: User; tokens: AuthTokens; p7Roles?: Role[] }> {
  if (!isAuthenticationEnabled()) throw new Error('authentication_disabled')
  if (mockActive()) {
    // ... returns { user: entry.user, tokens, p7Roles: entry.p7Roles }
  }
  if (!authFlag('authentication.email_login_enabled')) throw new Error('email_login_disabled')
  const { data } = await api.post<{ user: User; tokens: AuthTokens }>(
    ENDPOINTS.AUTH.LOGIN,
    credentials,
  )
  setTokens(data.tokens.access, data.tokens.refresh)
  return data
}
```

**Finding: the real-mode branch's response type does not include
`p7Roles` at all** — the `api.post<{ user: User; tokens: AuthTokens }>()`
call is typed without it, and `return data` passes through whatever the
backend sent, which per the type contract has no `p7Roles` field. Back in
`useLogin()`'s `onSuccess`, the check `if (p7Roles && p7Roles.length > 0)`
will be `false` for every real-mode login (since `p7Roles` is
`undefined`), so `setTenantRoles()` is **never called** in real mode
today.

Net effect if `NEXT_PUBLIC_USE_MOCK=false` were flipped on right now,
against a real backend, with no other changes:
- `tenantRoles` would stay empty for every user, permanently (no login
  path populates it).
- `usePermissions()` would fall back entirely to Ownership Resolution +
  StaffAssignment (sources 4 and 5) for any real authorization signal —
  the `ROLE_PERMISSION_MAP`-driven tenant-role grants (source 1+3) would
  never fire for anyone.
- Any tenant role that isn't also expressible as an Owner/StaffAssignment
  fact (e.g. a `marketing` or `support` P7 role with no corresponding
  `StaffAssignment`) would be **completely unreachable** — those users
  would see console access denied everywhere, even if they should have
  role-scoped permissions.
- Conversely, `userOverrides` also stays permanently empty (nothing
  populates it from a backend either), so the Console "Permission
  Overrides" feature would silently do nothing meaningful beyond the
  current browser tab/session.

This is not a hypothetical edge case — it is the literal current
behavior of the `else` branch that already exists in `auth.service.ts`.

## 5. Production Recommendation

**Before a real backend is wired in, `tenantRoles` and `userOverrides`
must become server-populated, client-cached values — never
client-authoritative.**

Concretely, for a future phase (not this one):

1. **Login/session response must include roles.** `ENDPOINTS.AUTH.LOGIN`
   (and the OTP equivalents) must return `p7Roles` (or an equivalent
   server-computed tenant-role list) in the real-mode response body,
   the same shape mock mode already returns. `auth.service.ts`'s real
   branch type must be widened to `{ user: User; tokens: AuthTokens; p7Roles?: Role[] }`
   to match.
2. **Overrides must be a server resource.** `setUserOverride()`'s two
   call sites need a real `ENDPOINTS.RBAC.SET_OVERRIDE`-style API call;
   the Zustand write should follow a successful server response, not
   replace it. The Console pages should re-fetch (or receive back) the
   authoritative override state rather than trusting their own local
   write.
3. **Every permission-bearing token must be re-validated server-side on
   every authorization-relevant API call.** The current UI-side
   `usePermission()` gates are correctly scoped as **UX affordances**
   (hide/show buttons, redirect from disallowed routes) — they must
   never be the only enforcement point once a real backend exists. Every
   mutating endpoint (`orders.manage`, `staff.manage`, etc.) must
   independently check the authenticated user's real, server-known role/
   assignment before acting, regardless of what the client's
   `usePermissions()` returned. This is standard defense-in-depth and is
   already implied by the "backend engineer implements from a doc"
   framing of `docs/P10.5.5_PERMISSION_ARCHITECTURE_FINAL.md`.
4. **Client persistence should be re-scoped to display-cache only.**
   Once (1) and (2) land, `useRbacStore`'s `persist` config should add a
   `partialize` that excludes `tenantRoles`/`userOverrides` from
   `localStorage` (or persists them with a short TTL that forces a
   server re-fetch on every session start), so that even a tampered
   `localStorage` value is immediately overwritten by the next
   authoritative server response instead of being trusted at
   rehydration time. `rbacAuditLog`/`customRoles` (display/notes data)
   can remain persisted as-is.
5. **Until (1)-(4) land, do not run `NEXT_PUBLIC_USE_MOCK=false` in any
   environment where the outcome of a permission check has real
   consequences** — today it silently degrades to Ownership/
   StaffAssignment-only authorization with no tenant-role or override
   support, which is a functional gap, not just a security one.

## Explicitly Out of Scope for This Phase

No backend endpoint, API contract, or client wiring was implemented.
`auth.service.ts`, `src/services/endpoints.ts`, `useRbacStore`'s persist
config, and the two Console override-save call sites are all unchanged.
This document exists to make the gap explicit and actionable for the
phase that does implement a real backend, per the task's instruction:
"Do NOT implement backend changes."
