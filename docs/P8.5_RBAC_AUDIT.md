## Current Architecture

### 1. Role Type
8 roles: `owner | admin | manager | cashier | waiter | kitchen | marketing | support`

### 2. Permission Type (31 permissions)
Dot-notation: `orders.view`, `orders.manage`, `menu.view`, `menu.manage`, `reservations.view`, `reservations.manage`, `customers.view`, `customers.manage`, `vendors.view`, `vendors.manage`, `promotions.view`, `promotions.manage`, `loyalty.view`, `loyalty.manage`, `analytics.view`, `staff.view`, `staff.manage`, `branches.view`, `branches.manage`, `settings.view`, `settings.manage`, `tenant.view`, `tenant.manage`, `audit.view`, `audit.export`, `audit.manage`, `notifications.view`, `notifications.manage`, `notifications.preferences`, `operations.view`, `operations.manage`

### 3. Authorization Formula
`Permission AND Capability AND FeatureFlag`

### 4. Store
`useRbacStore` (Zustand, persisted as `savor-rbac`) stores `TenantRoleAssignment[]` — per-tenant role lists.

### 5. Gaps vs Enterprise Requirements
| Gap | Impact |
|-----|--------|
| No granular action permissions (orders.create vs orders.manage) | Cannot grant create-only without full manage |
| No user-specific overrides | Cannot grant/deny per-user exceptions |
| No branch-scoped roles | Users have same roles across all branches |
| No multiple roles UI | Admin cannot assign roles from panel |
| No role management UI | Role→permission mapping is code-only |
| Limited permission granularity | Cannot support per-action RBAC |
