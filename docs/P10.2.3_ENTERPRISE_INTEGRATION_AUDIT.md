post-login destination. It is invoked with `result.user.role` — the
legacy `UserRole` field — and has no knowledge of `Owner`,

itself has not been updated to reflect the ownership model (e.g., an

Severity: **Low** (UX/completeness gap, not a security issue) — flagged

## Phase F — Branch isolation

`branch-access.service.ts`'s filtering functions (`getAccessibleBranches`,
`canAccessBranch`, `filterByAccessibleBranches`) are unchanged and
structurally sound (confirmed by direct read, matches P10.2.1/P10.2.2's
claims). However:

**Finding F-4 (re-confirmation, not new — but with a sharper conclusion
than prior reports drew):** grep for every consumer of
`BranchAccessContext`/`useAccessibleBranches`/`branchAccessService.*`
across `src/app/**` (actual pages: orders, reservations, kitchen, staff,
analytics, dashboard, customer lookups) returns **zero results**. None of
the named surfaces in this phase's Phase F list (Orders, Reservations,
Inventory, Kitchen, Staff, Analytics, Dashboard, Search, Customer
lookups) perform branch filtering through this engine — or through any
other mechanism found in this audit. Data returned by `adminService`,
`branchAnalyticsService`, etc. is fetched by `branchId`/`tenantId`
*parameters the caller already supplies* (e.g. `useBranchOrders(branchId)`
takes a `branchId` argument), not filtered by *the current actor's
accessible branches*. In other words: **there is currently no
branch-isolation enforcement anywhere in this application's live code
path** — mock services return whatever `branchId`/`tenantId` a caller
asks for, with no check that the caller is allowed to ask for it. This
matches P10.0's finding J16 ("Order/Menu services have zero tenant/branch
isolation") — **confirmed still true**, and shown here to extend beyond
Order/Menu to every branch-scoped surface this audit checked. This is a
**pre-existing gap**, not introduced by P10.2.1/P10.2.2, and both of
those phases correctly scoped it out — but it means the StaffAssignment
branch-scoping model (§3, the "Accountant sees Branch2 but not Branch1"
feature) has **no live enforcement point in the UI/data layer today**,
even though the *data* to support it (`StaffAssignment.branchIds`) now
exists and is correctly resolvable via `buildBranchAccessContextFromAssignments()`.

No cross-tenant leakage was found either, for the same reason in
reverse: nothing filters *by* tenant at read time beyond callers already
supplying the right `tenantId` — there is no enforcement, so there is
also no cross-tenant leakage *through the ownership engine specifically*,
because the ownership engine isn't in this data path at all yet.

## Phase G — React Query cache keys

Sampled every `useQuery`/`useMutation` call in `hooks/index.ts` that is
permission- or ownership-adjacent:

| Hook | Query key includes tenant? | Includes branch? | Includes owner? |
|---|---|---|---|
| `useAccessibleBranches(context, allBranches)` | Yes — `context.tenantId` | Yes — `context.branchIds` | No (no owner dimension in `BranchAccessContext`) — not applicable, since ownership grants full access without a context |
| `useStaff(tenantId)`, `useInvites(tenantId)` | Yes | N/A | No |
| `useBranchOrders(branchId)`, `useBranchReservations(branchId)`, `useBranchAnalytics(branchId)` | No (keyed only by `branchId`) | Yes | No |
| `useEffectivePermissions(userId, tenantId)` | Yes | No | No |

**`usePermissions()`, `usePermission()`, etc. are NOT React Query
hooks** — they are `useMemo`-based Zustand selectors, recomputed on every
render when their dependency array changes (confirmed: no `useQuery`
wrapper anywhere in the permission hook chain). This means **there is no
cache to go stale** for the resolution engine itself — a genuinely
favorable property this audit can confirm structurally, not just assert.
`resolveOwnershipIdentity()`'s underlying mock-service reads
(`staffService.findStaffMemberByEmail`, `ownerService.getOwnerByUserIdSync`,
`staffAssignmentService.getEffectiveAssignments`) are synchronous
in-memory array scans with no cache layer of their own — every call
re-reads current mock state.

**Where staleness CAN occur:** `useTenantStore.tenant` (which now carries
`ownerId`) is a **persisted** Zustand store (see Phase H) and IS the
input to `usePermissions()`'s owner short-circuit. If the persisted
`tenant` object is stale (e.g. after a server-side ownership transfer the
client hasn't refetched), `usePermissions()` will compute against the
stale `ownerId` until something calls `setTenant()` with fresh data.
`grep` found exactly 2 call sites for `useTenantStore.getState().setTenant()`
(`hooks/index.ts:1778` inside `useUpdateTenantSettings`, and `:2522`
inside website-builder's `saveBranchOverrides`-adjacent flow) — **neither
is related to an ownership-transfer flow**, because no ownership-transfer
flow exists in the codebase yet (P10.3 scope). This is not a bug today
(there is nothing to go stale from), but it is the exact mechanism that
will need explicit cache invalidation once P10.3 implements a live
transfer endpoint — flagged for that phase's design.

# Phase M — Final Report

## 1. Verification Matrix

See Phase A (P10.2.1, 9 claims: 8 VERIFIED, 1 PARTIALLY VERIFIED) and
Phase B (P10.2.2, 15 claims: 12 VERIFIED, 2 VERIFIED-with-caveat, 1
PARTIALLY VERIFIED). **Zero FALSE claims found** in either report — both
implementation reports accurately describe what was built. The gaps this
audit found are things neither report claimed to have done, not
misrepresentations of what they did.

## 2. Remaining Technical Debt (ranked)

**Critical:** none found. Nothing in this audit rises to "actively
broken in a way that corrupts data or is trivially exploitable in the
current application's actual reachable state" — the two High findings
below require a specific, currently-unreachable-in-mock-mode combination
(a suspended Owner/Staff account whose credentials someone still has and
who still passes login) rather than being reachable by an ordinary user.

**High:**
- **F-1** — Owner short-circuit ignores `Owner.status` (§ Phase J).
- **F-2** — StaffAssignment resolution ignores `StaffMember.status` (§ Phase J).
- **F-4** — No branch/tenant isolation enforcement anywhere in the live data path (pre-existing, P10.0 J16, reconfirmed broader in scope).

**Medium:**
- **F-6** — Two disconnected ownership-transfer mechanisms.
- **F-8** — Permission resolution ignores `Tenant.status`.
- **F-5** — Incomplete `useRbacStore` logout clearing.
- Owner's `ROLE_PERMISSION_MAP` array under-provisioned relative to `ALL_PERMISSIONS` (pre-existing, previously documented in P10.2.2).
- `reviews.view`/`reviews.manage` missing from `ALL_PERMISSIONS` (P10.0 J3, reconfirmed still true).

**Low:**
- **F-3** — Post-login redirect not ownership-aware.
- **F-7** — Time-based assignment expiry is soft (no live re-render trigger).
- `useOwnershipBranchAccessContext`/`useAccessibleBranches`/`order-routing.service.ts` unwired (by design, pending P10.3).
- `useHasPermission()` dead code.
- `useTenantStore` persisted `tenant.ownerId` with no invalidation hook for a future transfer flow (not a bug today — no transfer flow exists to invalidate from).

## 3. Hidden Bugs (not previously documented anywhere in P10.0–P10.2.2)

1. **F-1**, **F-2** — status-blind Owner/Staff resolution (see Phase J).
2. **F-6** — the legacy `transferOwnership()` and the new ownership model are silently disconnected; a developer calling the "obvious" transfer function would not affect real ownership at all.
3. **F-8** — archived/suspended tenants don't lose access.
4. **F-5** — logout doesn't fully clear RBAC store state.
5. **F-3** — post-login routing hasn't been touched by the ownership work.

## 4. Security Risks (complete list, cross-referenced to Phase J)

F-1 (High), F-2 (High), F-4 (High, pre-existing/reconfirmed), F-6
(Medium), F-8 (Medium), F-5 (Medium). No privilege-escalation path, no
credential/secret exposure, no injection-class vulnerability found. The
risk profile is "the new engine grants correctly when it grants, but
doesn't yet check every deny-condition it should" — not "the new engine
can be tricked into granting something it shouldn't for an otherwise-
valid, active account."

## 5. Architecture Drift (implementation vs. P10.1 design)

- **None found in the resolution algorithm itself** — §4.4 is implemented exactly as specified, including the priority order, the union-not-substitution rule, and the deliberate absence of Platform Admin/Customer handling.
- **Drift by omission, not contradiction:** P10.1 never explicitly says "check Owner.status"/"check StaffMember.status"/"check Tenant.status" either — §1.1 defines these fields exist, but §4.4's algorithm description doesn't mention consulting them. So this is arguably a spec gap in P10.1 itself, inherited faithfully by the implementation, rather than the implementation drifting from a spec that said otherwise. Worth a P10.1 addendum or explicit note in P10.3's scope.
- **The post-login redirect (F-3)** was never in P10.1/P10.2.x's scope to begin with — not drift, just an adjacent surface neither phase touched.
