# P9.5.4 Phase A — Production Localization Completion: Exact Audit

## Purpose

Before building any infrastructure, this audit inventories exactly what
remains hardcoded across the platform, with real counts (not estimates),
so the rest of this phase — and the honest reporting required at the end
— is grounded in verified numbers.

## Method

`grep -c` over the actual source tree, plus the automated tools built
this phase (`scripts/check-translation-coverage.mjs`'s hardcoded-string
heuristic, `node scripts/check-hardcoded-strings.mjs`). Every number below
was re-run against the final state of the repo at the end of this phase,
not estimated at the start.

## Real architectural finding: flat dotted-key namespace entries never resolve

While migrating the `configFields`/`seo` namespaces this phase, an
authoring pattern that looked reasonable — storing a translation as a
flat JSON property whose *name* contains literal dots, e.g.
`"authentication.core.title": "Core Toggles"` — turned out to be
silently broken. next-intl treats every dot in a translation key as a
level of object nesting, not a literal character; `t.has('authentication.core.title')`
against a flat key returns `false` always (or, when routed through a live
`NextIntlClientProvider`, next-intl's `validateMessages()` rejects it
outright with `INVALID_KEY`). This was caught by direct experimentation
with `use-intl/core`'s `createTranslator()` before it shipped to
production, not after — see `docs/P9.5.4_IMPLEMENTATION.md` §"Bugs
discovered" for the full account and the fix (genuinely nested JSON
objects instead of flat dotted keys), and
`src/test/p9-5-4-production-localization.test.tsx`'s
"resolveConfigText — the real architectural bug this phase found and
fixed" suite for the regression tests that lock the correct shape in.
