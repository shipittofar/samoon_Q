# P10.5.3 — Permission Model Consolidation & Dead Data Audit

Final cleanup audit of the permission model. Only allowed code change
made: a local variable rename inside `usePermissions()` (Phase A). No
authorization logic, no store logic, no service logic was touched.

## Phase A — Rename Misleading Variable

`usePermissions()`'s local variable `legacyEffective`
(`src/hooks/index.ts`) was renamed to `tenantRolePermissions`.
`docs/P10.5.1_AUTHORIZATION_ARCHITECTURE_AUDIT.md` already concluded
this variable represents the live `useRbacStore.tenantRoles`-based
permission set, not the retired `rbacService`/`ROLE_PERMISSIONS` engine
(fully deleted in P10.4.12) — the old name was accurate when written
(P10.2.2-era, when a real legacy engine coexisted) and became misleading
once that engine was removed.

```diff
-    const legacyEffective = applyOverrides(base, override)
+    const tenantRolePermissions = applyOverrides(base, override)

     const ownershipDriven = resolveOwnershipDrivenPermissions(user?.email, tenant)
-    if (ownershipDriven.length === 0) return legacyEffective
+    if (ownershipDriven.length === 0) return tenantRolePermissions

-    return [...new Set([...legacyEffective, ...ownershipDriven])]
+    return [...new Set([...tenantRolePermissions, ...ownershipDriven])]
```

Zero logic change — every operator, every comparison, every returned
value is byte-identical; only the two identifier occurrences and the
one `return` site changed. A comment was added explaining the rename
and pointing to this document and P10.5.1. `grep -rn "legacyEffective"
src` after the change returns only that explanatory comment — no other
file referenced the old name.

## Phase C — Runtime Graph Verification

Every runtime authorization decision in the application was traced to
confirm it originates from exactly one of the six sanctioned decision
points. Re-verified after the Phase A rename (no behavior change
expected or found):

| Decision point | Verified single implementation? |
|---|---|
| `PermissionGuard` | Yes — delegates entirely to `usePermission()`/`useAnyPermission()`/`useAllPermissions()` via three internal sub-components; no independent logic. |
| `usePermission()` | Yes — the only place a single P7 permission is checked against `usePermissions()`'s resolved array plus feature-flag/capability gates. |
| `usePermissions()` | Yes — the single aggregation point (tenant-role base ∪ ownership-driven set). |
| Ownership Resolution (`ownership-resolution.service.ts`) | Yes — `resolveOwnerPermissions()`/`resolveStaffAssignmentPermissions()`/`resolveOwnershipDrivenPermissions()` have one implementation each, consumed by `usePermissions()` and `useHasDashboardAccess()`. |
| `StaffAssignment` (`staff-assignment.service.ts`) | Yes — `getEffectiveAssignments()` is the one query surface; consumed by ownership resolution and `useHasDashboardAccess()` directly. |

**One near-duplicate found, not a violation:** `permission.service.ts`
exports plain (non-hook) `hasAnyPermission()`/`hasAllPermissions()`
functions (role-array → boolean), and `hooks/index.ts` separately
implements `useAnyPermission()`/`useAllPermissions()` (resolved-permission-array
→ boolean) with its own inline logic rather than calling the
`permission.service.ts` versions. These are not duplicate *decision
paths* in the graph sense — the hook versions are the only ones any
runtime UI code calls (confirmed: `hasAnyPermission()`/`hasAllPermissions()`
have exactly one non-definition reference each, both in
`src/test/phase7-rbac.test.ts`, zero application callers) — but they are
a conceptual duplication worth flagging under Technical Debt below,
since a future maintainer could reasonably assume the hooks wrap the
service functions when they don't.

**`branch-access.service.ts`** calls `permission.service.ts`'s plain
`hasPermission()` directly (not `checkPermission()`, not the hooks) —
this is a legitimate seventh call site of an existing function, not a
new decision point; it consumes the same `ROLE_PERMISSION_MAP` via the
same function every hook uses.

**No other duplicate authorization implementation was found.**

## Phase E — Custom Role Readiness

**`customRoles` cannot currently affect authorization.** Full trace:

1. `app/console/roles/new/page.tsx` calls `useRbacStore().addCustomRole(role)`
   on form submit, appending a `CustomRoleTemplate` to
   `useRbacStore.customRoles`.
2. **No function reads `useRbacStore.customRoles` or calls
   `getCustomRoles()` anywhere in application code** — confirmed via
   `grep -rn "\.customRoles\b\|getCustomRoles(" src` restricted outside
   `stores/index.ts`/`src/test`, which returns nothing.
3. `usePermissions()` (the sole permission-aggregation point) reads only
   `useRbacStore.tenantRoles` and `useRbacStore.userOverrides` — it has
   no reference to `customRoles` at all.
4. `ROLE_PERMISSION_MAP` (`permission.service.ts`) is a static,
   compile-time object keyed by the fixed `Role` union
   (`'owner' | 'admin' | 'manager' | 'cashier' | 'waiter' | 'kitchen' |
   'marketing' | 'support'`) — it has no mechanism to accept a
   dynamically-created custom role at all, even if one were looked up.

**Conclusion:** a custom role created through the Console UI is
persisted to `localStorage` and has zero effect on any user's actual
permissions. The feature's data-entry form works; the feature itself
does not exist end-to-end.

## Phase F — Branch Role Readiness

**`branchRoles` cannot currently influence authorization.** Trace:

1. No UI writes to `useRbacStore.branchRoles` (Phase B — zero non-store,
   non-test call sites for `setBranchRoles()`).
2. No function reads `useRbacStore.branchRoles` or calls
   `getRolesForBranch()` anywhere in application code.
3. Branch-scoped authorization is instead handled entirely by a
   different, fully-wired system: `StaffAssignment.branchIds` (resolved
   via `resolveAssignmentBranchIds()` in `ownership.service.ts`,
   consumed by `buildBranchAccessContextFromAssignments()` in
   `ownership-resolution.service.ts`, and enforced by
   `branch-access.service.ts`). This is the real, live branch-scoping
   mechanism — `useRbacStore.branchRoles` is a separate, unconnected
   data structure that predates it and was never removed or wired in.

**Missing integration point:** even if `branchRoles` were to be wired
up, it's unclear it should be — `StaffAssignment.branchIds` already
solves branch-scoped role assignment, more precisely (per-assignment,
not per-branch-blanket) and with test coverage
(`p10.2.1-ownership-data-model.test.ts` and others). Wiring
`branchRoles` in would create the exact "two paths to the same
decision" problem Phase C confirms does not currently exist. The
recommended integration point, if this is ever pursued, is not "make
`branchRoles` feed authorization" but "confirm `branchRoles` is
superseded by `StaffAssignment.branchIds` and formally retire it" (see
Recommended Cleanup Order below).

## Phase G — Role Assignment Readiness

**`roleAssignments` is not read anywhere by runtime authorization.**
Trace:

1. No UI writes to `useRbacStore.roleAssignments` (Phase B — zero
   non-store, non-test call sites for `addRoleAssignment()`).
2. No function reads `useRbacStore.roleAssignments`,
   `getRoleAssignmentsForUser()`, or
   `getActiveRoleAssignmentsForUser()` anywhere in application code.
3. `usePermissions()` derives tenant-scoped role membership exclusively
   from `useRbacStore.tenantRoles` (a `TenantRoleAssignment[]`, a
   *different*, similarly-named but structurally distinct type from
   `RoleAssignment`) — not from `roleAssignments`.

**Future integration point (if ever needed):** `RoleAssignment`
(`src/types/rbac.ts:197`) appears designed for a more granular,
per-user (not per-tenant-blanket) role-grant model with its own
lifecycle (`grantedAt`/`grantedBy`/`revokedAt`/`status`, per the store
action names). If this granularity is ever required, the integration
point would be inside `usePermissions()`, unioning
`getActiveRoleAssignmentsForUser(user.id, tenantId)`-derived roles
alongside the existing `tenantRoles.find(...)` lookup — structurally
identical to how `StaffAssignment` was integrated for ownership-driven
permissions. This is documented as a possible future path, not a
recommendation to build it — no evidence in the codebase indicates it's
currently planned.

## Phase H — Security Review

`useRbacStore` uses Zustand's `persist` middleware with `{ name:
'samoon-rbac' }` and **no `partialize`**, meaning every field —
`tenantRoles`, `userOverrides`, `branchRoles`, `roleAssignments`,
`customRoles`, `rbacAuditLog` — is written to `localStorage` in full and
rehydrated on every page load.

| Field | Acceptable in Mock mode? | Must move to backend-derived state before production? |
|---|---|---|
| `tenantRoles` | **Yes** — this is the live P7 role-grant source `usePermissions()` reads. In mock mode there is no backend to be a trusted source of truth, so client-persisted state is the only option and is by design. | **Yes, mandatory.** The moment `USE_MOCK=false`, a client can edit `localStorage['samoon-rbac']` and grant themselves any `Role` for any tenant, which `usePermissions()` will trust unconditionally — a direct privilege-escalation vector. Must be re-derived from a trusted backend session/token on every load, never read from `localStorage` as an authorization input in real mode. |
| `userOverrides` | Same as `tenantRoles` — live authorization input, same mock-mode justification. | **Yes, mandatory** — same escalation risk (`applyOverrides()` can grant or deny arbitrary permissions per-user). |
| `branchRoles` | Acceptable — confirmed dead state (Phase B/F), has zero effect either way. | **No current urgency** — since it's not read by anything, it poses no *current* security risk regardless of persistence. If it is ever wired into authorization in the future, it would inherit the same mandatory-backend-derivation requirement as `tenantRoles`. |
| `roleAssignments` | Acceptable — confirmed dead state (Phase B/G). | Same as `branchRoles` — no current risk; would require backend derivation if ever activated. |
| `customRoles` | Acceptable — confirmed to have zero effect on authorization (Phase E), even though it has a live write path. | No current risk. If custom roles are ever wired into `ROLE_PERMISSION_MAP`-equivalent resolution, that resolution must be backend-validated (a client should not be able to invent a custom role granting itself `tenant.manage`, for instance) before real mode. |
| `rbacAuditLog` | Acceptable in mock mode as a demo/UI data source (`useAuditLogs()` and the Console's Audit Log pages read it for display). Not an authorization *input* anywhere — it's a record of past actions, not a permission grant. | Should move to a backend-owned, tamper-evident log before production regardless of authorization concerns — a client-editable `localStorage` array is not a credible audit trail once real users can inspect devtools. This is a data-integrity concern, not a privilege-escalation one. |

**Summary:** the two fields that actually drive authorization decisions
today (`tenantRoles`, `userOverrides`) are the two that carry real
production risk if `USE_MOCK=false` is ever set without first replacing
their persistence source. This matches and reaffirms
`docs/P10.5.1_AUTHORIZATION_ARCHITECTURE_AUDIT.md`'s "Security risks"
finding — this phase adds the field-by-field breakdown P10.5.1 didn't
go into.

## Technical Debt

1. The `hasAnyPermission()`/`hasAllPermissions()` (service) vs.
   `useAnyPermission()`/`useAllPermissions()` (hook) naming near-collision
   (Phase C) — same conceptual operation, two separate implementations,
   only the hook versions are actually called by the app.
2. `checkPermission()`/`auditHooks`'s permission-check audit trail is
   inert in the running application (zero real callers) — distinct from,
   and easily confused with, the live `rbac-audit.service.ts`/
   `addRbacAuditEvent()` audit system.
3. The Console Roles UI's `customRoles` write-path/listing-page
   disconnect (Phase B/E) — a half-built feature, not a bug in the strict
   sense, but a genuine trap for anyone extending that page later
   expecting `addCustomRole()` to actually do something visible.
4. `useRbacStore`'s full (`partialize`-free) `localStorage` persistence
   of `branchRoles`/`roleAssignments`/`customRoles`/`rbacAuditLog`
   alongside the two live authorization fields — no current risk (Phase
   H), but persisting dead state indefinitely is itself a small
   maintenance/confusion cost.

## Recommended Cleanup Order

Documentation only — no implementation performed, per this phase's
scope. In order of increasing risk/decision-weight:

1. **Lowest risk — test-only exports.** Remove or explicitly mark
   `hasAnyPermission()`/`hasAllPermissions()`/`checkPermission()`/
   `resolveWithDependencies()`/`validatePermissionGrant()`/`auditHooks`
   as intentionally-retained test-coverage-only utilities, OR delete
   them following the same audit-then-remove discipline used for the
   legacy RBAC engine (P10.4.1→P10.4.12) if they're confirmed to have no
   product roadmap.
2. **Low risk — dead Zustand state.** `branchRoles`/`roleAssignments`
   are the safest candidates for removal — zero application callers in
   either direction. Would need the same test-impact audit pattern
   (P10.4.2-style) since `phase8-5`/`phase8-6-enterprise-rbac.test.ts`
   exercise them directly.
3. **Medium risk — product decision required first.** `customRoles`:
   either wire `roles/page.tsx` to read from it (making the feature
   real) or remove the write path and the store field together (making
   the feature's absence honest). This is a product call, not a
   mechanical cleanup — do not remove code before that decision is made.
4. **No cleanup needed, just clarity.** Rename `hasAnyPermission()`/
   `hasAllPermissions()` (the `permission.service.ts` versions) to avoid
   the naming collision with the hooks, OR add a doc-comment
   cross-reference so a future reader isn't misled into thinking the
   hooks wrap them.

## Production Readiness

**Not production-ready as-is for the two live authorization fields.**
Before any `USE_MOCK=false` launch: `tenantRoles` and `userOverrides`
must be re-derived from a trusted backend response on every load rather
than trusted from `localStorage` (Phase H) — this is the single
blocking item. Every other finding in this report (`branchRoles`,
`roleAssignments`, `customRoles`, the test-only `permission.service.ts`
exports) is either fully inert or UI-display-only and carries no
production-authorization risk in its current, unwired state.
