# P9.5.7D.1 — Localization Architecture Completion (Schema Translation IDs)

**Status: COMPLETE for both named blockers.** The 86 collection-schema strings and the ~137 `ConfigFieldOption` labels flagged as architecturally blocked at the end of P9.5.7D are now translatable — not worked around, but resolved by extending the actual lookup-key architecture with stable, scoped translation ids. A small number of option sets remain deliberately untranslated (currency/language ISO codes, font family names, numeric font weights, country names, and the language-fallback picker's per-language roster) — these are proper nouns/codes by the codebase's own established convention (already never translated anywhere else in the project), not architectural limitations; the mechanism now supports translating them the moment anyone chooses to author those keys.

## Root cause (Phase A)

`resolveConfigText(t, id, kind, fallback)` (`src/config/i18n.ts`, P9.5.4) keyed every lookup off a single `id: string` → `configFields.<id>.<kind>`. That is exactly correct for module ids, section ids, and top-level field ids, because `PlatformConfigurationRegistry.register()` already enforces those as globally unique (Rule 3, `registry.ts:64-70`, a duplicate-id throw). Two categories of object were never covered by that uniqueness check, and the flat key silently mis-served both:

1. **Collection item schemas** (`ConfigCollectionMeta.schema`, P9.2) — `COUNTRY_SCHEMA`, `LANGUAGE_SCHEMA`, `PLATFORM_USER_SCHEMA`, `TENANT_SCHEMA`. These are ordinary `ConfigFieldDefinition[]` arrays built with `defineField()`, but by design (`types.ts`'s own doc comment on `ConfigCollectionMeta`) they are **never** passed to `platformConfigurationRegistry.register()` individually — they exist purely so `ConfigurationEntityDrawer`/`ConfigurationCollectionTable` can render one property per entity generically, without per-collection code. Skipping registration means skipping the uniqueness check: `COUNTRY_SCHEMA` and `LANGUAGE_SCHEMA` both legitimately have a boolean field literally called `'enabled'`; `ConfigurationEntityDrawer.tsx` (pre-fix) called `resolveConfigText(tFields, prop.id, 'title', prop.title)` with that **bare** `'enabled'`, so a translation authored for one collection's `enabled` field would silently render on the other's too, and there was no way to author both. One collection (`countries.ts`) even had this collide with *itself*: its section and its own collection field shared the literal id `'countries.registry'`, so only one of the two could ever be translated under the old scheme.
2. **`ConfigFieldOption`** (`select`/`radio`/`*_picker` option lists) — this type never had an id of its own, only `value` and `label`. There was no id to build a `resolveConfigText` key from in the first place, so **no** module's option labels were ever translatable, full stop — not a collision, a complete absence of a translation identity.

## Stable Translation IDs (Phase B)

`resolveConfigText`'s `id: string` parameter became `idPath: string | string[]` — an ordered list of scope segments joined with `.`. A bare string is a one-segment path, so **every pre-existing call site is unaffected**; this is purely additive. Two new pieces complete the id system:

- `ConfigFieldOption.id?: string` (`types.ts`) — an optional stable identity for an option, independent of `value`. Fully optional: every existing option array (176 countries' worth of `{ value, label }` pairs, every module's `select` options) keeps compiling and rendering exactly as before with zero edits.
- `getConfigOptionId(option)` (`src/config/i18n.ts`) — derives a deterministic id when `option.id` is absent: a sanitized slug of `String(option.value)` (e.g. `'North America'` → `'North_America'`, `'image/png'` → `'image_png'`). Same option, same key, every time — no runtime registry, no drift from what a translator sees reading `value` in source.
- `resolveConfigOptionText(t, scopeId, option, kind, fallback)` — the option-specific convenience wrapper: builds `${scopeId}.options.${getConfigOptionId(option)}.${kind}`.

Every id path used in this phase:

| Object | Path |
|---|---|
| Module / section / top-level field (unchanged) | `<id>` |
| Collection schema property | `[<collectionFieldId>, 'schema', <propertyId>]` |
| Top-level field's own option | `[<fieldId>, 'options', <optionId>]` |
| Collection schema property's own option | `[<collectionFieldId>, 'schema', <propertyId>, 'options', <optionId>]` |

## Collection Schema Localization (Phase C)

`ConfigurationEntityDrawer.tsx`'s `propTitle`/`propDescription` now resolve through `[field.id, 'schema', prop.id]` instead of bare `prop.id` — `field` here is the collection field passed into the drawer (e.g. `'countries.registry'`, `'platform.languages.registry'`), so `COUNTRY_SCHEMA`'s `enabled` and `LANGUAGE_SCHEMA`'s `enabled` now resolve independently: `configFields.countries.registry.schema.enabled.title` vs `configFields.platform.languages.registry.schema.enabled.title`. `ConfigurationCollectionTable.tsx`'s group-by/sort-by dropdowns and `configUiHelpers.ts`'s `deriveCollectionFilterOptions()` (the boolean Enabled/Disabled filter chips and select-property filter chips) were updated the same way, so every place a collection schema property's text renders — drawer, table headers, filter chips — now goes through the identical scoped lookup with zero per-collection code, satisfying "automatic resolution" (Phase E) for this category.

`Countries.name`, `Languages.name`, `Tenants.name`, `PlatformUsers.name` (the four named test cases in this phase's own brief) never collide: `configFields.countries.registry.schema.*`, `configFields.platform.languages.registry.schema.*`, `configFields.platform.tenants.registry.schema.*`, `configFields.platform.users.registry.schema.*` are four disjoint key trees.

The one same-file self-collision (`countries.ts`'s section and field sharing id `'countries.registry'`) was fixed at the source: the section id was renamed to `'countries.registry_section'` (data-safe — section ids are never a stored configuration key, only field ids are, per `registry.ts`) and its existing "Country Management" translation was moved to the new key; `configFields.countries.registry.title`/`.description` was then free to hold the *field's* own "Countries" text, which had never been translatable before this phase.

## Option Localization (Phase D)

`ConfigFieldOption` gained the optional `id` field described above — no schema-breaking change, no migration required for any existing option array. `ConfigurationFieldControl.tsx` gained an optional `optionScopeId?: string | string[]` prop (defaults to `field.id`, correct for every ordinary module field) and an `optionLabel(opt)` helper wired into all three option-rendering call sites (radio buttons, `select`/`country`/`language`/`currency`/`timezone` pickers, font selector). `ConfigurationEntityDrawer.tsx` passes `optionScopeId={[field.id, 'schema', prop.id]}` when rendering a collection-schema property's control, so option labels inside a collection entity drawer are scoped exactly like the property's own title/description.

## Automatic Resolution (Phase E)

No module-specific code was added anywhere. Every change is in the five shared rendering components (`ConfigurationFieldControl`, `ConfigurationEntityDrawer`, `ConfigurationCollectionTable`, `configUiHelpers`, `ConfigurationFieldRow`/`ConfigurationModulePage`/`ConfigurationInspector`/`ConfigurationStudioNav`/`ConfigurationCommandPalette` — the last five needed no code change at all, since they already called the now-widened `resolveConfigText` with a bare string, which remains valid). A future module registering a new field, a new collection schema, or a new option list becomes translatable automatically the moment its author writes the corresponding `configFields.*` key — exactly the pre-existing "additive, zero-code" guarantee `src/config/i18n.ts`'s original doc comment promised, now extended to cover the two categories it previously couldn't reach.

## Migration (Phase F)

All four collection schemas and every top-level module field with a literal inline `options: [...]` array were migrated to the new scoped keys:

- **Collection schemas**: `COUNTRY_SCHEMA` (23 properties: 26 title/description entries + 17 option entries across `region`/`status`/`address_format`), `LANGUAGE_SCHEMA` (35 properties: 52 title/description entries + option entries for `direction`/`status`/`dateStyle`/`hourCycle`/`numberNotation`), `PLATFORM_USER_SCHEMA` (4 properties, including the 10-entry `role` option list previously computed from `PLATFORM_ROLE_LABEL`), `TENANT_SCHEMA` (6 properties, including `status`'s 4 options and `plan`'s 3 options).
- **Top-level module field options**: 25 fields across 12 files (`payments.ts`, `themes.ts`, `storage.ts`, `subscriptions.ts`, `rbac.ts`, `notifications.ts`, `monitoring.ts`, `system.ts`, `website-builder.ts`, `automation.ts`, `security.ts`, `developer.ts`, `platform.ts`, `infrastructure.ts`) — 86 option labels.

No key was duplicated: every new key was checked against the existing `configFields` namespace before being authored (the same `python3` load-and-check discipline used throughout every prior localization sub-phase), and the one genuine pre-existing collision (`countries.registry`) was resolved by rename, not by picking a winner and dropping data.

## Cleanup (Phase G)

No fallback logic was removed. `resolveConfigText`'s literal-fallback behavior and `PLATFORM_ROLE_LABEL`/`STATUS_OPTIONS`/etc.'s in-source English literals remain exactly as they were — they are the correct, required compatibility shim: every option/property that doesn't yet have an authored translation key still renders its literal text in every locale, exactly as the mechanism has worked since P9.5.4. Nothing in this phase's design introduces a second lookup path, a second `ConfigFieldOption`-like type, or a parallel translation system — it is the same `configFields` namespace, the same `resolveConfigText`/`t.has()` pattern, with a wider id-path input type.
