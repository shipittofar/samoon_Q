## Summary

The Savor deployment stack consists of: a Next.js standalone Docker image, nginx reverse proxy (handling TLS termination, static caching, rate limiting), and a Docker Compose orchestration layer. The GitHub Actions CI/CD pipeline covers lint, type-check, test, and build gates. Several critical deployment gaps were identified and fixed in this audit cycle.

## Findings

### FIXED — D-001: CI Build Job Missing Required Environment Variables
- **Severity:** Critical
- **File:** `.github/workflows/ci.yml`
- **Evidence:** The `build` job only set `NEXT_PUBLIC_USE_MOCK: 'false'`. The `src/lib/env.ts` Zod schema requires `NEXT_PUBLIC_API_BASE_URL` as a valid URL — without it, the Next.js build throws at module initialization and the CI build would fail on every commit.
- **Fix applied:** Added to build job `env` block:
  ```yaml
  NEXT_PUBLIC_API_BASE_URL: 'http://localhost:8000/api'
  NEXT_PUBLIC_APP_URL: 'http://localhost:3000'
  ```
- **Commit:** `dfed710`

### FIXED — D-002: Nginx Missing HTTP→HTTPS Redirect and TLS Configuration
- **Severity:** High
- **File:** `nginx.conf`
- **Evidence:** Original config had no `listen 80` server block and no SSL configuration. The application was not enforcing HTTPS in production.
- **Fix applied:**
  - Added HTTP server block: `listen 80; return 301 https://$host$request_uri;`
  - Added HTTPS server block: `listen 443 ssl; ssl_protocols TLSv1.2 TLSv1.3; ssl_ciphers HIGH:!aNULL:!MD5; ssl_session_cache shared:SSL:10m;`
  - Added HSTS preload header: `Strict-Transport-Security "max-age=63072000; includeSubDomains; preload"`
  - Added security headers: `X-Frame-Options DENY`, `X-Content-Type-Options nosniff`, `X-XSS-Protection`, `Referrer-Policy`, `Permissions-Policy`
  - Added SSL certificate path comments with Certbot/Let's Encrypt convention paths
- **Commit:** `dfed710`

### FIXED — D-003: Docker Compose Missing App Healthcheck
- **Severity:** High
- **File:** `docker-compose.yml`
- **Evidence:** The `app` service had no `healthcheck` entry. The `nginx` service `depends_on: app` had no condition, meaning nginx could start before Next.js was ready to serve requests, causing 502 errors on cold start.
- **Fix applied:**
  - Added healthcheck to `app` service:
    ```yaml
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/api/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 20s
    ```
  - Changed nginx `depends_on` to `condition: service_healthy`
- **Commit:** `dfed710`

### VERIFIED — D-004: Health and Readiness Probes
- **Files:** `src/app/api/health/route.ts`, `src/app/api/ready/route.ts`
- **Finding:**
  - `/api/health` — liveness probe; returns `{ status: "ok", version, uptime, memory, timestamp }` at HTTP 200. Does not check external dependencies (correct design for liveness).
  - `/api/ready` — readiness probe; validates `NEXT_PUBLIC_API_BASE_URL` (must be a URL) and `NEXT_PUBLIC_USE_MOCK` (must be `"true"` or `"false"`) via Zod. Returns 503 if invalid.
- **Finding:** Both probes are correctly implemented. The healthcheck in docker-compose.yml uses `/api/health` (correct — liveness for container orchestration).

### VERIFIED — D-005: Docker Standalone Build
- **File:** `next.config.ts` (line 39)
- **Evidence:** `output: "standalone"` — Next.js produces a minimal Node.js server bundle without the full `node_modules`. The `Dockerfile` uses this output.
- **Finding:** Correct configuration. Standalone output reduces the Docker image size significantly.

### VERIFIED — D-006: CI Pipeline Completeness
- **File:** `.github/workflows/ci.yml`
- **Gates:** lint → type-check → test → build (build requires all three to pass via `needs:`)
- **Finding:** Pipeline is complete. Build is only attempted when lint, types, and tests are green. The i18n key validation script runs in the test job.
- **Note:** No deployment step exists in CI — this is expected for a frontend-only repository. Deployment is handled externally (per the docker-compose.yml and nginx setup).

### OPEN — D-007: Nginx Using `envsubst` Variables Without Runtime Substitution
- **Severity:** Medium
- **File:** `nginx.conf` (line 51)
- **Evidence:**
  ```nginx
  server ${DJANGO_HOST:-smartrestaurant-web}:${DJANGO_PORT:-8000};
  ```
  Standard nginx does not support shell variable substitution syntax. The `nginx:alpine` image does not run `envsubst` by default. This line will cause nginx to fail to start, treating `${DJANGO_HOST:-smartrestaurant-web}` as a literal host name.
- **Fix Recommended:** Either:
  1. Use the `nginxinc/nginx-unprivileged` image with an entrypoint that calls `envsubst`, OR
  2. Replace with the literal default value `server smartrestaurant-web:8000;` (matches the docker-compose service name) and use a separate override conf for custom hosts, OR
  3. Add a docker-compose entrypoint that runs `envsubst < /etc/nginx/nginx.conf.template > /etc/nginx/nginx.conf`
- **Status:** Not auto-fixed — requires docker-compose entrypoint change. Flagged for immediate manual fix before production deployment.

### OPEN — D-008: SSL Certificates Not Provisioned
- **Severity:** High (blocks production)
- **File:** `nginx.conf` (lines 70–71), `docker-compose.yml` (lines 47–49)
- **Evidence:**
  ```nginx
  ssl_certificate     /etc/nginx/ssl/fullchain.pem;
  ssl_certificate_key /etc/nginx/ssl/privkey.pem;
  ```
  The cert paths are configured but the actual certificates are not present. Volume mount comments exist in `docker-compose.yml` but are commented out.
- **Status:** Infrastructure concern — cannot be resolved from the frontend repository.
- **Recommendation:** Before production deployment:
  1. Run Certbot (`certbot certonly --webroot`) against the production domain
  2. Uncomment the SSL certificate volume mounts in `docker-compose.yml`
  3. Add a cron job or cert-manager integration for auto-renewal

### OPEN — D-009: No `.env.example` File
- **Severity:** Low
- **Evidence:** No `.env.example` exists in the repository root. New developers or deployment engineers have no reference for required environment variables.
- **Recommendation:** Create `.env.example` documenting all required env vars:
  - `NEXT_PUBLIC_API_BASE_URL`
  - `NEXT_PUBLIC_WS_BASE_URL`
  - `NEXT_PUBLIC_APP_URL`
  - `NEXT_PUBLIC_USE_MOCK`
  - `NEXT_PUBLIC_SENTRY_DSN` (optional)
  - `NEXT_PUBLIC_FIREBASE_*` (optional, for push notifications)

### OPEN — D-010: `external: true` Volume May Not Exist
- **Severity:** Low
- **File:** `docker-compose.yml` (lines 55–57)
- **Evidence:**
  ```yaml
  volumes:
    static_volume:
      external: true
      name: backend_static_volume
  ```
  Docker Compose will fail to start if `backend_static_volume` does not exist as a pre-created Docker volume. This requires the backend container stack to be running and to have already created this volume.
- **Recommendation:** Document the startup order requirement: backend stack must be running first. Alternatively, add a `docker volume create backend_static_volume` step to the deployment runbook.
