## 1. Adding a language

Once P9.5.1+ exists, adding language #151 requires exactly one thing:
**adding one entity id to `localization.languages`'s `entityIds` roster**
(and, if it needs a new region/currency/plural-rule-locale value not
already covered by an existing `select` option, extending that option
list) — no new file, no new route, no Studio code, per the same guarantee
`docs/P9.2_COUNTRIES_MANAGEMENT.md` §19 already established for Countries
and `docs/P9.4_PLATFORM_ADMIN_CENTER.md` §9 established for Platform
Administration modules. Concretely (illustrative, matching the existing
`countries-registry-data.ts` pattern):

```ts
// illustrative — P9.5.1+, not implemented in this phase
ALL_LANGUAGE_CODES.push('sw') // Swahili
LANGUAGE_OVERRIDES.sw = {
  english_name: 'Swahili', native_name: 'Kiswahili',
  region: 'Africa', rtl: false,
  plural_rule_locale: 'sw', default_currency: 'KES',
  status: 'draft', activation_tier: 'experimental', enabled: false,
}
```

The new row appears in the Studio automatically (fixed-roster rendering,
the same `entityIds` mechanism Countries uses) with `enabled: false` —
present, inert, exactly the "150+ languages in the registry, 6 active"
requirement.

## 2. Adding a translation key

1. Add the key to the default language's source (today: `en.json`; post-
   P9.5.1: a `localization.translation_keys` entity with
   `id: '{namespace}.{key}.en'`).
2. This creates `status: missing` entities for every *other enabled*
   language automatically (the collection's fixed schema means the write
   path can eagerly create placeholder rows, the same way
   `configCollection.buildMergedCollectionValue` already merges a patch
   onto whatever exists — no manual per-language step).
3. A missing-key CI check (§4) fails the build if a key is used in source
   but has no `en` entity at all — catching the "forgot to add the English
   string" class of mistake before it reaches any translator.

## 3. Removing / renaming a key

- **Removing**: an explicit action (never an automatic side effect of an
  import, per `P9.5.0_TRANSLATION_ARCHITECTURE.md` §4) — deletes every
  `(namespace, key, *)` triple. Reversible via the same rollback mechanism
  (`rollbackAuditEntry`) every other Configuration write already has.
- **Renaming**: modeled as (create new key with all current values) +
  (remove old key) rather than an in-place id change, because entity ids
  in this framework are stable identifiers (Rule 3) — the same reason a
  Country's ISO code or a Platform Administration module's id is never
  edited in place, only ever added or (rarely, explicitly) removed.

## 4. Review process & CI checks

A translation change (new key, edited value, or import) goes through:
1. **The four detection checks** (`P9.5.0_TRANSLATION_ARCHITECTURE.md`
   §7 — missing/unused/duplicate/conflict), run as pure functions over the
   collection data, in CI, on every PR touching a namespace.
2. **A required reviewer** for any key transitioning to `status: reviewed`
   or `approved` (§2 of the Translation Architecture doc) — enforced the
   same way `audit.requireReason` already gates certain Configuration
   writes (P9.0.1), not a new approval-workflow engine.
3. **The stable-promotion gate** (`P9.5.0_LANGUAGE_LIFECYCLE.md` §5) before
   any language-level `beta` → `stable` transition, independent of
   individual key reviews.

## 5. SEO strategy

- **`hreflang`**: generated from `localization.languages` where
  `enabled && visible` — one `<link rel="alternate" hreflang="...">` tag
  per active language/locale, using each entity's own BCP 47 id (§2.1 of
  the architecture doc) directly as the `hreflang` value — no separate
  hreflang-code mapping table needed, since BCP 47 *is* the hreflang
  format.
- **Localized sitemap**: one sitemap entry set per enabled+visible
  language, generated at build/request time from the same registry query
  — not hand-maintained per language.
- **Canonical URL**: the platform's default language's URL is canonical;
  every other enabled language's page declares `rel="canonical"` pointing
  at the default-language equivalent unless the platform is configured for
  per-language canonical URLs (a Localization Configuration field, not a
  hardcoded choice) — this mirrors how `languages.default` already governs
  fallback behavior for the existing 3-language setup.
- **Language negotiation**: unchanged from today's actual mechanism
  (`Accept-Language` header → `NEXT_LOCALE` cookie → `languages.default`
  fallback, `src/i18n/request.ts`) — only the *set of valid values* being
  negotiated over grows from a hardcoded 3 to a registry-driven 150+.
- **URL strategy**: this phase does not mandate path-prefixed
  (`/fa/checkout`) vs. subdomain (`fa.savor.com`) vs. cookie-only (today's
  actual mechanism, no URL change at all) routing — that's a P9.5.1+
  implementation decision with real trade-offs (path-prefixing is the most
  SEO-friendly but is a routing change explicitly out of scope for this
  documentation-only phase, per the phase's own constraints: "No routing
  changes"). Recorded here as the first decision the next phase must make,
  not deferred silently.

## 6. What doesn't change

Every existing `next-intl` call site (`useTranslations()`, `t()`) keeps
working unmodified — the architecture designed across these six documents
changes *where the message data comes from* (a registry-driven collection
instead of 3 hardcoded JSON files) and *what tooling exists around it*
(versioning, coverage, detection), never the runtime API application code
already calls.

## 7. Adding a language today (P9.5.1A interim workflow)

Until P9.5.1B's `localization.languages` collection ships, adding language
#7 is a two-file change (full detail in `docs/P9.5.1_RUNTIME_ENGINE.md` §6):

1. Add one entry to `LANGUAGE_REGISTRY` in `src/i18n/language-registry.ts`
   (native name, direction, fallback locale, default currency/timezone,
   `hasMessages: false` until a real translation file exists).
2. Add its code to `languages.supported` (and `languages.rtl_locales` if
   applicable) — either the config module's default array in
   `src/config/modules/languages.ts`, or a platform-level override through
   `configurationService.updateField()` at runtime, no redeploy required.

Nothing else changes: the language switcher (`Header.tsx`/`TenantHeader.tsx`),
the fallback chain, and the formatting runtime all pick it up automatically
because they read `resolveSupportedLocales()`/the registry rather than a
literal list. It ships enabled with **no translation file** — every key
falls back to English via the Missing Translation Handler
(`src/i18n/runtime.ts`'s `loadMessages`) until `src/i18n/locales/{code}.json`
is added, at which point `hasMessages` flips to `true` and the fallback
stops firing for that language. This is exactly the "Enabled + no file yet"
state zh/it/tr ship in today.
