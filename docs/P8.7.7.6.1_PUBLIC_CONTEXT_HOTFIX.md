# P8.7.7.6.1 — Public Context Initialization Hotfix (Pre-P8.8)

**Date:** 2026-06-27  
**Branch:** `claude/magical-gauss-gy7ndu`  
**Type:** Minimal architectural fix — R-01 from P8.7.7.6 audit  
**Result:** ✅ Fixed — public layouts now use only public data. Zero regressions.

---

## 1. Root Cause

`src/app/[tenantSlug]/[branchSlug]/layout.tsx` called `useAdminBranches(tenantId)` to resolve the active branch from the URL slug. `useAdminBranches` invokes `branchManagementService.getBranches(tenantId)` — an admin branch management API call that requires authentication in production.

**In mock mode:** Works for all users because the mock service has no auth check.  
**In production:** Anonymous visitors (incognito, logged-out, direct deep links, preview links in new tabs) trigger a 401 from the admin branches endpoint. The branch context is never initialized. All public pages under `/{tenantSlug}/{branchSlug}/*` render without branch context.

The data needed to initialize public branch context already exists in `MarketplaceMeta.branches` — a public array embedded in the tenant's settings object, which is loaded by `tenantService.getTenant()` (a public, unauthenticated call).

## 3. Before / After Initialization Flow

### Before (broken for anonymous users in production)

```
GET /{tenantSlug}/{branchSlug}/menu (anonymous user)
  ↓
TenantBranchLayout renders
  ↓
useAdminBranches(tenant.id)
  ↓
branchManagementService.getBranches(tenantId)   ← admin API, requires auth
  ↓
401 Unauthorized in production
  ↓
branches = []   → useEffect guard: "if (branches.length === 0) return"
  ↓
setActiveBranch never called
setAdminActiveBranch never called
  ↓
Child pages render with activeBranch = null   ← broken context
```

### After (public-safe)

```
GET /{tenantSlug}/{branchSlug}/menu (any user, including anonymous)
  ↓
TenantBranchLayout renders
  ↓
useTenantStore: tenant loaded by loadTenant(tenantSlug) via tenantService.getTenant()
  (public service, no auth required)
  ↓
getMarketplaceMeta(tenant.settings).branches   ← already in memory, no API call
  ↓
branches.find(b => b.slug === branchSlug)   ← pure client-side lookup
  ↓
setActiveBranch(publicBranchToLocation(match, tenant.id))
  ↓
Child pages render with correct activeBranch   ✅ works for all users
```

**Data flow difference:**

| | Before | After |
|---|---|---|
| Branch data source | `branchManagementService.getBranches()` (admin API) | `MarketplaceMeta.branches` (embedded in tenant settings) |
| Auth required | ✅ Yes (admin endpoint) | ❌ No (public data already loaded) |
| Extra network request | Yes (`['admin-branches', tenantId]` query) | No (zero extra requests) |
| `adminActiveBranch` set | Yes (incorrectly set from public layout) | Not set (admin context managed by admin flows only) |
| `activeBranch` set | Yes (via `adminBranchToPublic` adapter) | Yes (via `publicBranchToLocation` adapter) |

## 4. Production Impact

### What breaks without this fix (production, anonymous visitor)

- `/savor/main/menu` — branch context null → menu renders but no branch header/address/hours
- `/savor/main/reservation` — branch null → reservation form has no branch pre-selected
- `/savor/main/loyalty` — branch null → loyalty context missing
- All `/{tenantSlug}/{branchSlug}/*` pages — degraded or broken for anonymous users

### What is fixed

- Anonymous visitors, incognito browsers, logged-out users, and shared/direct URLs all get correct branch context initialized from public MarketplaceMeta.
- Zero additional API calls — `MarketplaceMeta.branches` is already loaded as part of `tenantService.getTenant()`.

### What is not affected

- Preview flow from admin: admin opens new tab `/savor/main/menu` → `TenantBranchLayout` loads correctly using public data → `activeBranch` initialized → page renders with correct branch context. ✅
- `adminActiveBranch` for admin sessions: not set by this layout (was never appropriate for a public layout). In admin sessions, `adminActiveBranch` is managed solely by `AdminBranchSwitcher` and persists to localStorage. ✅
- No routing changes. No URL changes. No public API changes.

## 6. Risk Assessment

### Risks introduced: None

The change is strictly narrowing:
- Removes one admin API call from a public layout.
- Replaces it with a synchronous in-memory lookup.
- Does not touch routing, RBAC, admin switchers, query keys, or any other system.

### `adminActiveBranch` no longer set by public layout

Before this fix, `TenantBranchLayout` set `adminActiveBranch` as a side effect. This was architecturally incorrect — a public layout should not manage admin store state. The admin context is now solely the responsibility of:
- `AdminBranchSwitcher` (interactive switch)
- `useBranchStore` persistence (rehydrated on load from localStorage for returning admin sessions)

**No admin feature depends on `TenantBranchLayout` setting `adminActiveBranch`.** Admin pages use their own context path through `AdminLayout` → `AdminContextBar` → `AdminBranchSwitcher`. The only scenario where the old behavior was relevant was preview tabs — and preview tabs don't render admin components, so `adminActiveBranch` in a preview tab has no effect on the visible page.

### `publicBranchToLocation` adapter — synthetic id and zero lat/lng

`PublicBranchInfo` does not carry a database `id`, `lat`, or `lng`. The adapter uses `b.slug` as `id` and `0` as lat/lng defaults. This is safe because:
- `Location.tenant_id` is optional — no consumer should fail on a defined value.
- `lat`/`lng` = 0 is the same default used in the previous `adminBranchToPublic` (which had `b.location.latitude ?? 0`).
- `id` as slug is internally consistent for public page use (React keys, display). No public page makes admin API calls using this id.

### Remaining architectural risk (deferred to P8.8)

**R-02** (favorites/recently-viewed localStorage keys not tenant-scoped) remains documented from P8.7.7.6 but is out of scope for this hotfix.
