## 2. The authentication surface today

Savor's auth model is **phone_number-first with an email/password fallback**:
primary flow is `PhoneInput` → `sendOTP()` → `/verify` (6-digit code) →
`complete-profile` for new numbers. A secondary, older 6-box OTP page
(`/verify-otp`) and a plain email/password `/register` + `/login` fallback
also exist, side by side. `USE_MOCK` (a public, build-time
`NEXT_PUBLIC_USE_MOCK` env var) switches every service method between a
hardcoded mock implementation and (presumably) a real backend call — no
other environment safeguard gates this switch.

## 3. Critical architectural flaw considered — and the decision

Per this phase's instructions ("do NOT modify business logic unless a
critical architectural flaw is discovered"), the following candidates were
evaluated and **none were treated as requiring an immediate code fix** —
each is a real gap, but none is an active vulnerability being exploited by
existing tests, existing routes, or existing data; each is scoped instead as
a P9.1.x implementation item (see `docs/P9.1.1_IMPLEMENTATION_PLAN.md`):

- **No server-side lockout enforcement** — real gap, but there is no server
  in this frontend-only repository to enforce it against; the config schema
  correctly anticipates it (§8 below) and fixing it means implementing the
  Security Architecture (Phase D) against a real backend, not patching the
  frontend.
- **Access token in both `localStorage` and a non-HttpOnly cookie** — a real
  hardening target, but changing token storage is a breaking change to the
  auth flow (session behavior for every logged-in user) and squarely
  "business logic," explicitly out of scope for this architecture-only
  phase. Flagged for a dedicated P9.1.x security hardening phase instead.
- **Two parallel role/permission systems** (`UserRole`/legacy vs. P7
  `Role[]`) — real duplication, but P8.5/P8.6 already built substantial
  surface on top of both; unifying them is a migration with real blast
  radius, not an architecture-phase change. Flagged for the roadmap.

**Conclusion: no code changes made in P9.1.1.** Everything below is
audit + design, per the phase brief.

## 4. Findings by area

### 4.1 Login / Register / OTP / Complete Profile / Forgot Password

- `src/app/login/page.tsx` — phone_number+OTP primary, collapsible email/password
  fallback; demo one-click login grid rendered only when `USE_MOCK` is true,
  but that flag is a public client bundle constant, not a server secret.
  Client-side `LOGIN_LIMIT` rate limiting applied to phone_number-continue,
  demo-login, and email-submit actions.
- `src/app/register/page.tsx` — email/password only, zod min-8-char
  password; **no OTP step, no rate limiting** (unlike every other auth page).
- `src/app/verify-otp/page.tsx` — an older, parallel 6-box OTP UI. Hardcoded
  60s resend countdown; `OTP_LIMIT` rate limiter; always-generic "Invalid
  OTP" toast (no attempt count shown).
- `src/app/verify/page.tsx` — the primary/newer OTP page (P8.9.2). Hardcoded
  `RESEND_SECONDS = 60` and `MAX_ATTEMPTS = 3`, neither derived from the P9.0
  `authentication.otp.*` config fields despite those existing. Shows the
  user a live remaining-attempts count. After 3 failures, a
  `'tooManyAttempts'` UI state requires a fresh code — this is `useState`,
  reset by page reload, so it is UX only, not a real lockout. In `USE_MOCK`
  mode, renders the literal hint **"Mock mode: any code works except
  000000"** directly in the page — correctly gated behind `USE_MOCK`, but a
  strong signal this must never reach a real deployment with that flag on.
- `src/app/complete-profile/page.tsx` — synthesizes a fake email
  (`{phone_number}@phone_number.savor.local`) and a hardcoded placeholder password
  (`'mock-phone_number-auth'`) to route phone_number-only signups through the
  email/password `register()` contract. This is a structural workaround, not
  a first-class phone_number-only account type — a real backend contract needs a
  dedicated phone_number-only registration path (see Phase H).
- `src/app/forgot-password/page.tsx` — email-only, `PASSWORD_RESET_LIMIT`
  applied, always shows a generic success message regardless of whether the
  email exists (good practice, though not documented as deliberate anywhere
  in the code).

**Duplication found:** the 60-second resend cooldown is hardcoded
independently in *two* pages (`verify-otp/page.tsx`, `verify/page.tsx`)
instead of both reading `authentication.otp.resend_cooldown_seconds` — two
sources of truth for one policy value, coincidentally in sync today, with
nothing preventing drift.

### 4.2 Auth Service (`src/services/auth.service.ts`)

Nine methods (`login`, `register`, `logout`, `getMe`, `forgotPassword`,
`resetPassword`, `sendOTP`, `verifyOTP`, `changePassword`), all branching on
`USE_MOCK`. No `refreshToken()` here (lives in `axios.instance.ts`), no
lockout-check method, no session-list/session-revoke method.

Mock mechanism: `MOCK_CREDENTIALS` — 10 hardcoded demo accounts, **all
sharing the literal password `'password'`**; `MOCK_ACCESS_TOKEN`/
`MOCK_REFRESH_TOKEN` are static JWT-shaped strings with `exp` in the year
2286, committed to source; "session" in mock mode is just an email string
in `localStorage` (`MOCK_SESSION_KEY`), trivially spoofable via devtools to
assume any of the 10 demo roles. OTP mock validation treats `'000000'` as
the only invalid code — any other 6 digits succeed.

Inconsistent mock latency: `MOCK_DELAY = 800ms` (`src/constants/index.ts`)
used everywhere except `getMe()`, which uses an independent, hardcoded
`300ms`.

**No login-attempt counter or lockout state exists anywhere in this
service** — `authentication.max_login_attempts`/`lockout_duration_minutes`
(P9.0 config) have no enforcement code path reading them.

### 4.3 PhoneInput / Country Picker

- Country detection priority: explicit prop → parsed from E.164 value → last
  explicitly selected (`localStorage`) → browser locale → browser timezone →
  hardcoded fallback `'US'`.
- **No allow/block-list concept** — every country in `COUNTRIES` is always
  selectable; no per-tenant restriction, no "disable OTP for country X."
- Normalization is hand-rolled (`digitsOnly`, `buildE164`, `isValidLength`
  accepting a blunt 5–15-digit range for *any* country) — no libphonenumber-
  grade validation. Ambiguous dial codes (`+1` for US/CA/DO/PR/JM/TT/BB,
  `+7` for RU/KZ) always resolve to the first array match.
- `PINNED_COUNTRY_CODES` (10 hardcoded codes) and `MAX_RECENT = 5` are fixed
  constants with an uncited "~70% of users" justification comment — good
  configuration candidates (§7 below), low security relevance.
- `TIMEZONE_COUNTRY_MAP` is a hand-curated ~80-zone partial map; most of the
  world's ~430 IANA zones fall through silently to locale/US default.

### 4.4 Session & Token Handling

- Access + refresh tokens stored in `localStorage`
  (`JWT_ACCESS_KEY`/`JWT_REFRESH_KEY`); **the access token is additionally
  mirrored into a non-HttpOnly, JS-writable cookie** purely so Edge
  middleware can read it, with a **hardcoded 7-day `max-age`** entirely
  unrelated to and unsynchronized with the token's actual `exp` claim or
  `authentication.jwt_access_ttl_minutes` (config default: 15 minutes).
  Both storage locations are readable by any injected script — doubled XSS
  blast radius, not mitigated by any token-binding or rotation-detection.
- Refresh flow: single-flight refresh on `401`, queued concurrent requests,
  rotates the access token (and the refresh token if the backend supplies a
  new one, else reuses the old one). On failure, clears tokens and
  dispatches a `window` `'auth:logout'` event.
- **No "remember me" concept** — every session gets the identical fixed
  cookie lifetime regardless of user choice.
- **No logout-all-devices / session revocation / concurrent-session concept
  anywhere** — absent from the type system, the store, and the service
  layer, not just unimplemented in the UI.
- CSRF cookie/header handling coexists with the JWT bearer approach — a
  mixed auth model (Django-session convention layered onto token auth).
- `useAuthStore` is **not persisted** (unlike Cart/Theme/Branch/RBAC stores)
  — on hard refresh, `isAuthenticated` starts false until something
  re-hydrates it from the stored JWT via a `getMe()`-style call.

### 4.5 Guards & Middleware

- `middleware.ts` protects three route prefixes
  (`/dashboard`, `/checkout`, `/console`) uniformly — no method or role
  distinction at this layer. `isValidJWT()` checks structure + `exp` only —
  **no signature verification** (explicitly, by design: Edge runtime lacks
  Node crypto; verification is deferred to the real backend on every API
  call). This is exactly the property that lets the mock tokens (exp: year
  2286) pass the middleware gate — an accepted tradeoff for a
  frontend-only environment, not a bug, but one that must be stated
  explicitly in the Security Architecture (Phase D) so it is never
  mistaken for real protection.
- `AuthGuard.tsx` — client-side second layer; redirects unauthenticated
  users, and checks the **legacy** colon-notation permission
  (`rbacService.hasPermission`) when a `requiredPermission` prop is given —
  a separate system from the P7 dot-notation RBAC used elsewhere.
- `CapabilityGuard.tsx` — unrelated to authentication; gates UI by
  tenant/business-type capability flags, not identity. Included in this
  audit for completeness per the brief, but out of scope for the
  Authentication Control Center itself.
- `auth-redirect.ts` — pure utility mapping demo phone_number numbers → emails →
  post-login redirect routes. **Duplicates** the same demo phone_number/email
  pairs already present in `auth.service.ts`'s `MOCK_CREDENTIALS` — two
  hardcoded tables for the same ten accounts, kept in sync only by
  convention.

### 4.6 RBAC / Permissions tie-in

Two role vocabularies coexist: `UserRole` (`customer|staff|admin` on
`User.role`, checked by the legacy `rbac.service.ts` + `AuthGuard`) and P7
`Role[]` (`owner|admin|manager|cashier|waiter|kitchen|marketing|support`,
checked by `permission.service.ts` + `useRbacStore`, gated additionally by
Capability AND FeatureFlag). Reconciliation between the two happens **only**
via the hardcoded demo-credential table (`MOCK_CREDENTIALS`'s `p7Roles`
field) — there is no canonical mapping enforced at the type level, and no
real backend contract observed for how a real login response supplies P7
roles (the destructuring path `{ user, p7Roles }` exists but nothing
verifies the claim server-side from this codebase's vantage point).

### 4.7 Mock Users / Demo Data

`src/lib/mock-data.ts` defines 10 base `User` objects (customer, staff,
admin, owner, cashier, kitchen, marketing, support, multi-role, platform
admin) — every one hardcoded to `is_verified: true` and the same
`created_at`. **The `User` type has no `status`/`locked`/`suspended`/
`disabled` field at all** — `is_verified` is the only state flag and it's
binary. This is a genuine data-model gap, not just a missing fixture:
locked/disabled/pending-verification/suspended account states (all
requested by this phase's Phase G) cannot be represented today without
first extending the `User` type.

### 4.8 Existing P9.0 `authentication` Configuration Module

`src/config/modules/authentication.ts` registers 7 fields today: OTP length
(locked, default 6), OTP TTL (300s), OTP resend cooldown (60s), max login
attempts (5), lockout duration (15min), registration enabled (true, boolean),
JWT access TTL (15min, locked). **None of these are actually consumed by
any code in §4.1–4.5** — the module was built ahead of enforcement, exactly
as the P9.0 architecture intended (Registry → Schema → Validation → Service
→ ... → UI, with wiring-up as a later step) but as of today it is schema
without a live read path. This audit's Phase B extends the schema; wiring
it up is explicitly a P9.1.x implementation item (Phase I), not this
phase's job.

### 4.9 Feature Flags

No auth-specific feature flag keys exist anywhere in
`src/modules/registry.ts` or `feature-flags.service.ts` — the capability
flag system is entirely about business-type capabilities (loyalty,
reservations, delivery), never authentication behavior. The only thing
resembling a flag for auth is the non-feature-flag `NEXT_PUBLIC_USE_MOCK`
env var and the unused `authentication.registration_enabled` config field.
This is itself a gap: registration/social-login/passkey rollout has no
feature-flag-driven kill switch today.

### 4.10 Rate Limiting, CAPTCHA, Fraud, Device Trust, Geo, VPN

| Concept | Status |
|---|---|
| Rate limiting | **Exists, client-side only.** `src/lib/rate-limit.ts` — in-memory sliding window (`LOGIN_LIMIT` 5/min, `OTP_LIMIT` 3/5min, `PASSWORD_RESET_LIMIT` 3/hour). Resets on page reload/new tab; not a real security control, UX throttling only. |
| CAPTCHA | Absent. |
| Fraud / risk scoring | Absent. |
| Device trust / trusted devices | Absent. |
| Concurrent session limits | Absent. |
| Geo-blocking | Absent (the country picker is a UX convenience, not a security control). |
| VPN detection | Absent. |

## 5. Configuration candidates surfaced by this audit

Every hardcoded value identified above that varies (or should be able to
vary) per platform/tenant/branch is carried forward into
`docs/P9.1.1_AUTH_CONFIGURATION_SCHEMA.md` as a registered field, including
items with no config field today: OTP max-verify-attempts (distinct from
login attempts), demo/mock-mode visibility, country allow/block lists,
remember-me duration, session cookie lifetime, and the phone_number-normalization
length-validation range.

## 6. Summary

The authentication surface is functionally complete for a single-tenant
demo experience but has **zero live enforcement of the policy already
modeled in P9.0's `authentication` config module**, a mock-mode design that
is safe only as long as `USE_MOCK` never reaches production, two
un-reconciled role systems, and a complete absence (not partial — complete
absence) of rate limiting beyond client-side UX throttling, CAPTCHA, fraud
scoring, device trust, session revocation, and geo/VPN controls. None of
this is a regression to fix in this phase — it is exactly the gap the
Authentication Control Center (Phases B–H, and the P9.1.x roadmap in
`docs/P9.1.1_IMPLEMENTATION_PLAN.md`) exists to close.
