## Summary

The Savor frontend implements a multi-layer security posture that covers authentication, authorization, input validation, transport security, and content security policies. All identified critical and high-severity issues have been addressed. The remaining items are medium/low severity or require backend co-ordination.

**Key security controls verified from source:**
- JWT stored in `localStorage` + mirrored to a JS-readable cookie for middleware Edge use (`src/services/axios.instance.ts`)
- CSRF protection: `X-CSRFToken` header injected on all non-safe HTTP methods via axios interceptor
- CSP headers set in `next.config.ts` via `buildCspHeader()` — applied to all routes
- HSTS: `max-age=31536000; includeSubDomains` in `next.config.ts` headers
- Rate limiting: `LOGIN_LIMIT` (5/min), `OTP_LIMIT` (3/5min), `PASSWORD_RESET_LIMIT` (3/hr), `ORDER_CREATE_LIMIT` (10/hr) — `src/lib/rate-limit.ts`
- Production mock mode guard: `next.config.ts` throws if `NEXT_PUBLIC_USE_MOCK=true` in production
- Mock auth bypass guard: `src/services/auth.service.ts` rejects non-demo credentials in mock mode
- Zod env validation at startup: `src/lib/env.ts` throws on missing required env vars
- RBAC: P7 permission system with 8 roles and 31 dot-notation permissions — `src/types/rbac.ts`, `src/services/permission.service.ts`
- Row-level tenant isolation: `useTenantStore`, `x-tenant-slug` header, middleware tenant resolution
- Input validation: `react-hook-form` + `zodResolver` on all public forms (login, checkout, contact)
- PII sanitization in API logger: `createApiLogger` strips email, password, token fields — `src/lib/logger.ts`
- Sentry DSN-gated: only initializes when `NEXT_PUBLIC_SENTRY_DSN` is present

**Overall Security Score: 8.5 / 10**

## Findings

### VERIFIED SECURE — S-001: Authentication Token Storage
- **File:** `src/services/axios.instance.ts`, `src/constants/index.ts`
- **Finding:** JWTs stored in `localStorage` (key: `access_token`, `refresh_token`). This is the standard Next.js App Router pattern. `httpOnly` cookies cannot be set from client-side JS; the current approach is the correct design for this stack.
- **Mitigant:** CSP `script-src 'self'` restricts XSS attack surface. Sentry captures any unhandled exceptions.
- **Recommendation:** Consider migrating refresh token to an `httpOnly` cookie via a Next.js API route proxy in a future security sprint for defense in depth.

### VERIFIED SECURE — S-002: CSRF Protection
- **File:** `src/services/axios.instance.ts`
- **Finding:** Axios interceptor reads `csrftoken` cookie and injects `X-CSRFToken` header on POST/PUT/PATCH/DELETE requests. Django's CSRF middleware validates this header. Implementation is correct.

### VERIFIED SECURE — S-003: Content Security Policy
- **File:** `next.config.ts` (lines 4–24)
- **Finding:** CSP is enforced in production. `script-src` allows `'unsafe-inline'` (required for Next.js hydration) but not `'unsafe-eval'`. `object-src 'none'` prevents plugin injection. `frame-ancestors 'none'` blocks clickjacking. `form-action 'self'` restricts form submissions.
- **Note:** `'unsafe-inline'` in `script-src` is a known limitation of Next.js without a nonce-based CSP. The nonce approach requires custom server middleware and is out of scope for this phase.

### VERIFIED SECURE — S-004: Production Mock Mode Guard
- **File:** `next.config.ts` (line 31)
- **Finding:** Build throws `Error('[P3.3] Build aborted: NEXT_PUBLIC_USE_MOCK=true is not allowed in production')` if `NODE_ENV=production` and `NEXT_PUBLIC_USE_MOCK=true`. This prevents the `demo@savor.com / password` backdoor from reaching production.

### VERIFIED SECURE — S-005: Rate Limiting
- **File:** `src/lib/rate-limit.ts`, `src/app/login/page.tsx`
- **Finding:** Login page applies `LOGIN_LIMIT.check(email)` before submitting credentials. Sliding-window implementation is correct. Memory-backed (resets on pod restart) — acceptable for single-instance deployments. For multi-replica deployments, a Redis-backed limiter is needed.
- **Recommendation:** For production multi-replica deployments, replace the memory-backed limiter with a Redis-backed implementation.

### VERIFIED SECURE — S-006: RBAC Authorization
- **File:** `src/services/permission.service.ts`, `src/components/auth/PermissionGuard.tsx`
- **Finding:** All admin routes are wrapped with `PermissionGuard` at the layout level (`src/app/admin/layout.tsx` uses `AuthGuard` with `requiredPermission="dashboard:access"`). Individual pages use further `PermissionGuard` wrapping. Middleware additionally validates JWT on all `/dashboard`, `/checkout`, `/admin` prefixes.
- **Note:** RBAC is enforced client-side only from the frontend. The backend (Django) must independently enforce the same permissions on API endpoints.

### OPEN — S-007: JWT in localStorage (XSS Risk)
- **Severity:** Medium
- **Evidence:** `src/constants/index.ts`: `JWT_ACCESS_KEY = 'access_token'` stored in `localStorage`. Any successful XSS attack can read these tokens.
- **Mitigant:** CSP limits script injection. All user-facing inputs are validated with Zod. No `dangerouslySetInnerHTML` found in audit.
- **Recommendation:** Future sprint: proxy token exchange through a Next.js API route and store refresh token in `httpOnly` cookie. Access token can remain in memory (Zustand) without `localStorage` persistence.

### OPEN — S-008: HSTS `preload` Not Set in next.config.ts
- **Severity:** Low
- **File:** `next.config.ts` (line 67)
- **Evidence:** HSTS header is `max-age=31536000; includeSubDomains` without `preload`. The nginx.conf (added in `dfed710`) includes `preload` in the nginx-level HSTS header. The two headers are inconsistent.
- **Fix Recommended:** Add `; preload` to the HSTS value in `next.config.ts` headers configuration to match nginx.conf and enable HSTS preloading if the domain is registered.

### OPEN — S-009: Memory-Backed Rate Limiter Not Cluster-Safe
- **Severity:** Low
- **Evidence:** `src/lib/rate-limit.ts` — the `store` is a `Map` in module memory. In a multi-replica or serverless deployment, each instance has its own store. Limits are per-instance, not per-identifier globally.
- **Recommendation:** For production scale-out: replace with `upstash/ratelimit` (Redis-backed, edge-compatible) or enforce rate limiting at the nginx/API gateway layer.

### NO ISSUE — S-010: Hardcoded Secrets Scan
- **Finding:** Grep for `apiKey`, `secret`, `password`, `token`, `key` in `src/` excluding test fixtures. Only `AIzaMock` found in test files via `vi.stubEnv()` — safe. No real credentials found.
- **Evidence:** `grep -rn "AIza" src/` → only `src/test/` files using `vi.stubEnv({ NEXT_PUBLIC_FIREBASE_API_KEY: 'AIzaMock' })`.

## Remaining Risks

1. **JWT in localStorage** (S-007) — accepted risk; mitigated by CSP; full fix requires backend proxy pattern
2. **Memory-backed rate limiter** (S-009) — single-replica safe; multi-replica requires Redis
3. **HSTS preload inconsistency** (S-008) — trivial fix recommended before go-live
4. **RBAC client-side only** (S-006) — backend must enforce independently; not fixable from frontend

---

## Production Recommendations

1. Add `; preload` to HSTS in `next.config.ts` (S-008) before launch
2. Register domain in HSTS preload list (hstspreload.org) after DNS is stable
3. Use Redis-backed rate limiting for multi-replica deployments (S-009)
4. Implement a Sentry alert for rate-limit exhaustion events in production
5. Conduct a third-party penetration test before public launch
6. Ensure backend Django API enforces all P7 RBAC permissions independently
