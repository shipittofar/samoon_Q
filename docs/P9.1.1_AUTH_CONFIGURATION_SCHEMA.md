# P9.1.1 — Authentication Configuration Schema

> Phase B of P9.1.1. Design document only — no code registered in this
> phase. Every field below is specified in the exact shape
> `ConfigFieldDefinition` (`src/config/types.ts`) requires, ready to be
> authored with `defineField()` in a future P9.1.x implementation phase
> (see `docs/P9.1.1_IMPLEMENTATION_PLAN.md`). Builds on, and does not
> duplicate, the 7 fields already registered in
> `src/config/modules/authentication.ts` (P9.0) — those are marked
> **[existing]**; everything else is **[proposed]**.
>
> All fields belong to the single `authentication` module (see
> `docs/P9.1.1_AUTHENTICATION_ARCHITECTURE.md` for the module manifest).
> Grouped into sections mirroring how a future Console would present them.
>
> Last updated: 2026-07-04

---

## How to read this document

Each field is listed as: `id` — title — type — default — inheritance owner
level (`P`=platform, `T`=tenant, `B`=branch, `U`=user) — override mode
(`locked`/`override`/`merge`) — one-line rationale. Full validation rules
are given for fields where they matter; trivial boolean/select fields omit
an explicit validation row.

## Section 1 — Core Authentication Toggles

| id | Title | Type | Default | Owner | Mode | Notes |
|---|---|---|---|---|---|---|
| `authentication.enabled` **[proposed]** | Authentication Enabled | boolean | `true` | P | locked | Platform-wide kill switch — false puts the entire platform into maintenance-style auth lockout. Composes with `system.maintenance_mode` (P9.0 `system` module) but is a distinct, auth-specific switch a Platform Administrator can use without invoking full maintenance mode. |
| `authentication.registration_enabled` **[existing]** | Self-Service Registration Enabled | boolean | `true` | P | override | Already registered (P9.0). Audit finding: currently unread by `/register` — wiring is a P9.1.x implementation item. |
| `authentication.guest_checkout_enabled` **[proposed]** | Guest Checkout Enabled | boolean | `true` | T | override | Whether an unauthenticated user may complete checkout without creating an account. |
| `authentication.anonymous_browsing_enabled` **[proposed]** | Anonymous Browsing Enabled | boolean | `true` | P | locked | Whether menu/discovery pages are visible without authentication at all — a platform-level policy, not tenant-overridable, since it affects SEO/crawlability platform-wide. |

## Section 2 — OTP

| id | Title | Type | Default | Owner | Mode | Notes |
|---|---|---|---|---|---|---|
| `authentication.otp.enabled` **[proposed]** | OTP Login Enabled | boolean | `true` | P | override | Master switch for the phone+OTP flow, independent of `authentication.phone_login_enabled` (Section 3) which governs whether phone is an available identifier at all — this one specifically gates the OTP *mechanism* (a future passkey-only phone flow could disable OTP but keep phone login). |
| `authentication.otp.length` **[existing]** | OTP Code Length | number | `6` | P | locked | min 4 / max 8. |
| `authentication.otp.ttl_seconds` **[existing]** | OTP Expiry (seconds) | number | `300` | P | override | min 60 / max 900. |
| `authentication.otp.resend_cooldown_seconds` **[existing]** | Resend Cooldown (seconds) | number | `60` | P | override | min 15 / max 300. Audit finding: hardcoded identically in two pages today instead of read from here. |
| `authentication.otp.max_verify_attempts` **[proposed]** | Max OTP Verify Attempts | number | `3` | P | override | min 1 / max 10. Distinct from `authentication.max_login_attempts` (password login) — the audit found a hardcoded `MAX_ATTEMPTS = 3` in `verify/page.tsx` with no backing config field; this closes that gap. |
| `authentication.otp.daily_limit_per_phone` **[proposed]** | Daily OTP Limit (per phone number) | number | `10` | P | override | min 1 / max 100. Abuse-prevention ceiling independent of the per-attempt resend cooldown — caps total SMS spend/abuse per number per rolling 24h. |
| `authentication.otp.retry_delay_seconds` **[proposed]** | OTP Retry Delay (seconds) | number | `5` | P | override | min 0 / max 60. The minimum gap enforced between successive *verify* submissions (distinct from the *resend* cooldown) — prevents rapid-fire brute-force guessing of a 6-digit code within its TTL window. |
| `authentication.otp.languages` **[proposed]** | Supported OTP Message Languages | multi-select | `['en','fa','ar']` | P | override | Options sourced from the P9.0 `languages` module's `languages.supported` field — a `dependencies: [{ moduleId: 'languages', type: 'soft' }]` entry, not a duplicated list (Rule 3). |

## Section 4 — Login Attempts & Lockout

| id | Title | Type | Default | Owner | Mode | Notes |
|---|---|---|---|---|---|---|
| `authentication.max_login_attempts` **[existing]** | Max Login Attempts | number | `5` | P | override | min 3 / max 10, `requireReason` on change. |
| `authentication.lockout_duration_minutes` **[existing]** | Lockout Duration (minutes) | number | `15` | P | override | min 1 / max 1440. |
| `authentication.permanent_lock_threshold` **[proposed]** | Permanent Lock Threshold (lockouts) | number | `5` | P | locked | min 1 / max 20. Number of *temporary* lockouts within a rolling window before an account is escalated to a permanent lock requiring manual/support unlock — a distinct, more severe policy from the temporary lockout duration above. |
| `authentication.device_verification_enabled` **[proposed]** | Device Verification Enabled | feature_flag | `false` | P | override | Whether a login from an unrecognized device requires an additional verification step (e.g. email confirmation link) before completing. See Security Architecture §"Device Trust." |
| `authentication.trusted_devices_enabled` **[proposed]** | Trusted Devices Enabled | boolean | `false` | T | override | Whether users may mark a device as trusted to skip repeat OTP/verification challenges for a bounded period (see `authentication.trusted_device_ttl_days` below). |
| `authentication.trusted_device_ttl_days` **[proposed]** | Trusted Device TTL (days) | number | `30` | P | override | min 1 / max 365. Only meaningful when `trusted_devices_enabled` is true. |

## Section 5 — Session & Tokens

| id | Title | Type | Default | Owner | Mode | Notes |
|---|---|---|---|---|---|---|
| `authentication.jwt_access_ttl_minutes` **[existing]** | Access Token TTL (minutes) | number | `15` | P | locked | min 5 / max 120. |
| `authentication.jwt_refresh_ttl_days` **[proposed]** | Refresh Token Lifetime (days) | number | `7` | P | override | min 1 / max 90. Closes the audit finding that the current 7-day cookie `max-age` is a hardcoded literal in `axios.instance.ts`, unsynchronized with any config value. |

| `authentication.session_timeout_minutes` **[proposed]** | Idle Session Timeout (minutes) | number | `0` (disabled) | T | override | min 0 / max 1440. `0` means no idle timeout — an explicit opt-in for tenants wanting auto-logout after inactivity (e.g. a shared POS terminal). |
| `authentication.max_concurrent_sessions` **[proposed]** | Max Concurrent Sessions | number | `0` (unlimited) | P | override | min 0 / max 20. `0` means unlimited. See Security Architecture §"Concurrent Sessions." |

## Section 6 — Demo / Mock

| id | Title | Type | Default | Owner | Mode | Notes |
|---|---|---|---|---|---|---|
| `authentication.demo_login_enabled` **[proposed]** | Demo Login Enabled | boolean | `false` | P | locked | Explicit, auditable, platform-locked replacement for today's implicit `NEXT_PUBLIC_USE_MOCK` client bundle flag (audit finding: that env var has no secondary safeguard). Locked so no tenant can turn demo login on for themselves. |
| `authentication.demo_accounts_visible` **[proposed]** | Demo Accounts Visible in UI | boolean | `false` | P | locked | Governs whether the one-click demo account grid renders at all — separate from whether demo login *works*, so a Platform Administrator can leave the mechanism available for internal QA while hiding it from any public-facing build. |
| `authentication.mock_authentication_enabled` **[proposed]** | Mock Authentication Enabled | boolean | `false` | P | locked | The full mock-mode switch (mock users, mock tokens, mock OTP bypass) as an auditable configuration value rather than a build-time env var — this is the field a real deployment pipeline checks and fails a build/deploy against if `true` in production, closing the audit's "no safeguard" finding. |

## Section 7 — Geography & Phone

| id | Title | Type | Default | Owner | Mode | Notes |
|---|---|---|---|---|---|---|
| `authentication.allowed_countries` **[proposed]** | Allowed Countries (auth) | multi-select | all ISO codes | T | override | Distinct from the P9.0 `countries.enabled_codes` field (which governs country pickers platform-wide for *any* purpose) — this specifically restricts which countries may *authenticate*, e.g. a tenant operating only in one region. `dependencies: [{ moduleId: 'countries', type: 'soft' }]`. |
| `authentication.blocked_countries` **[proposed]** | Blocked Countries (auth) | multi-select | `[]` | P | override | Explicit deny-list, evaluated before `allowed_countries`; closes the audit's "no allow/block-list concept" finding. |
| `authentication.phone_normalization_strict` **[proposed]** | Strict Phone Normalization | boolean | `false` | P | override | When `true`, requires real per-country length/format validation (e.g. a libphonenumber-backed check) instead of today's blunt 5–15-digit heuristic. Kept a toggle, not a forced-on change, so rollout can be staged per the audit's finding that current validation is looser than ideal but not exploited. |
| `authentication.supported_phone_formats` **[proposed]** | Supported Phone Formats | select | `'e164'` | P | locked | Reserved for future formats if a non-E.164 storage/display format is ever needed; locked since this affects every stored phone number platform-wide. |
| `authentication.country_auto_detection_enabled` **[proposed]** | Country Auto-Detection Enabled | boolean | `true` | T | override | Governs the locale/timezone-based guessing chain in `PhoneInput`/`countries.ts`; a tenant serving one specific region might disable it to always show their default country first. |
| `authentication.default_country` **[proposed]** | Default Country (auth) | country | `'US'` | T | override | The auth-flow-specific counterpart to `countries.default_code` (P9.0) — kept separate because a tenant may want a different default for checkout-country vs. auth-phone-country. `dependencies: [{ moduleId: 'countries', type: 'soft' }]`. |

Every field in this section is intentionally schema-only in P9.1.1 — see
`docs/P9.1.1_SECURITY_ARCHITECTURE.md` and
`docs/P9.1.1_PROVIDER_ARCHITECTURE.md` for why no implementation exists yet.

| id | Title | Type | Default | Owner | Mode | Notes |
|---|---|---|---|---|---|---|
| `authentication.fraud_detection_enabled` **[proposed]** | Fraud Detection Enabled | feature_flag | `false` | P | override | Master switch for a future risk-scoring integration. |
| `authentication.captcha_enabled` **[proposed]** | CAPTCHA Enabled | feature_flag | `false` | T | override | Per-tenant toggle once a provider is selected (Provider Architecture). |
| `authentication.captcha_trigger_threshold` **[proposed]** | CAPTCHA Trigger Threshold (failed attempts) | number | `3` | P | override | min 1 / max 10. Only meaningful once `captcha_enabled` is true — CAPTCHA challenges appear after this many consecutive failures rather than on every attempt. |
| `authentication.risk_scoring_enabled` **[proposed]** | Risk Scoring Enabled | feature_flag | `false` | P | override | |
| `authentication.geo_blocking_enabled` **[proposed]** | Geo-Blocking Enabled | boolean | `false` | T | override | Composes with `blocked_countries` (Section 7) but operates on live request IP geolocation rather than the user-selected phone country — a distinct signal. |
