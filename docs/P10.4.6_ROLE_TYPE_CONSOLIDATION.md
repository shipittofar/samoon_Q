# P10.4.6 — Consolidate Duplicate Legacy/P7 `Role` Type

Removes the duplicate `Role` type definition identified in
`docs/P10.4.2_REMOVAL_PROOF.md` (Step 5), leaving `src/types/rbac.ts` as
the single authoritative source and re-exporting it from `@/types` using
the same pattern already used for `P7Permission`.

## Removed

**Duplicate `Role` definition** in `src/types/index.ts` (lines 799–811):

```ts
/**
 * P7 enterprise roles — always tenant-scoped.
 * Never use legacy UserRole for staff authorization; use Role instead.
 */
export type Role =
  | 'owner'
  | 'admin'
  | 'manager'
  | 'cashier'
  | 'waiter'
  | 'kitchen'
  | 'marketing'
  | 'support'
```

This was structurally identical to the canonical definition in
`src/types/rbac.ts:9`, which remains unchanged.

## Changed

### `src/types/index.ts`

Replaced the duplicate declaration with a re-export, added to the
existing P7-type re-export block (same pattern as `P7Permission`,
`UserTenantRole`, etc.):

```ts
// Re-export P7 types from rbac module for consumers that import from '@/types'
export type {
  Role,
  P7Permission,
  UserTenantRole,
  TenantRoleAssignment,
  PermissionCheckOptions,
  AuditEvent,
  MockRbacUser,
} from './rbac'
```

`@/types` consumers that only need the type (not a migrated import) keep
working unchanged, since `Role` is still importable from `@/types` — it
just resolves to the canonical `rbac.ts` definition instead of a second
copy.

### `src/stores/index.ts`

The one known application consumer importing `Role` from `@/types`
(per P10.4.2) was migrated to import it directly from the canonical
source:

```diff
-import type { Branch, CartItem, Extra, MenuItem, Notification, Tenant, TenantLifecycle, User, Role } from '@/types'
+import type { Branch, CartItem, Extra, MenuItem, Notification, Tenant, TenantLifecycle, User } from '@/types'
 import type { Branch as AdminBranch } from '@/types/branch'
+import type { Role } from '@/types/rbac'
```

### Audit confirming no other consumers were missed

`grep -rn "\bRole\b" src --include="*.ts" --include="*.tsx"` (excluding
`UserRole`/`RoleGuard`/`RoleId`/`StaffRole`/`RolePermission`/`role:`
matches) was run across the entire `src/` tree before editing. Every
other consumer already imports `Role` from `@/types/rbac` directly (or
from `./rbac` relatively): `types/notification.ts`, `types/staff.ts`,
`types/branch-routing.ts`, `types/ownership.ts`,
`types/realtime-operations.ts`, `types/audit-log.ts`,
`services/ownership-resolution.service.ts`, `services/permission.service.ts`,
`services/rbac-audit.service.ts`, `services/staff.service.ts`,
`services/auth.service.ts`, all `app/console/**` pages, and all
`src/test/**` files. `src/stores/index.ts` was the only file importing
`Role` from `@/types`.

## Regression Analysis

No runtime behavior changes, no permission changes, no authorization
changes. The `Role` type is a compile-time-only construct (`export
type`), so removing the duplicate declaration and replacing it with a
re-export of the same literal union has zero effect on any running
code — TypeScript resolves `import type { Role } from '@/types'` to the
exact same set of 8 string literals both before and after this change.
`ROLE_PERMISSION_MAP`, `permission.service.ts`, `rbacService.hasPermission()`,
and every authorization code path are byte-for-byte unchanged. The only
consumer whose import statement changed (`src/stores/index.ts`) now
imports the same type from its canonical source instead of the
re-export; its behavior is identical.
