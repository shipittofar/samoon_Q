## Section 2 — Current Sidebar Taxonomy

### 2.1 Current groups (7) and items (21)

| Group | Items |
|---|---|
| Operations | Orders, Reservations, Kitchen Display, Live Operations |
| Content | Menu, Promotions, Reviews, Loyalty |
| Customers | Customers |
| Analytics | Analytics, Branch Analytics |
| People | Staff, Users, Permissions, Roles |
| Platform | Tenants, Branches, Website Builder, Audit Logs |
| System | Notifications, Settings |

**Findings:**
- "Website Builder" belongs conceptually under **Content** (it edits the public-facing website), not Platform (which is infrastructure). Currently grouped with infrastructure items.
- "Analytics" and "Branch Analytics" are two separate nav items in the same group. Branch Analytics is a detail view of Analytics — it should be a sub-item or tab of Analytics, not a top-level peer.
- "People" contains 4 items (Staff, Users, Permissions, Roles) that are conceptually duplicated. Staff = operational schedule; Users = account access; Permissions = individual overrides; Roles = templates. For most operators, "Team" is more intuitive than "People".
- "System" conflates system-level operational items (Notifications = incoming events) with configuration (Settings). Notifications belong under Operations or as a global inbox.
- "Customers" is a single-item group — unnecessary group overhead for one item; could be merged into the Operations group or remain standalone.
- Business-type-specific items (bar/events, cafe/happy-hour etc.) have no `group` field — they render ungrouped at the bottom of whatever section the module uses.

### 2.2 URL depth analysis

| Depth | Count | Examples |
|---|---|---|
| 1 (`/console`) | 1 | Dashboard |
| 2 (`/console/x`) | 20 | orders, menu, settings |
| 3 (`/console/x/y`) | 15 | settings/feature-flags, branches/analytics, bar/events |
| 4 (`/console/x/[id]/y`) | 4 | customers/[id]/reviews, branches/[id]/analytics |

Depth-3 URLs that are type-specific sub-pages (bar/events, cafe/happy-hour, food-court/seating) violate the otherwise clean `/console/<entity>` pattern. These would be better under `/console/operations/events`, `/console/content/happy-hour`, etc., but a rename is out of scope.

## Section 3 — Settings Architecture

### 3.1 Current Settings (7 tabs)

| Tab key | Label | Status |
|---|---|---|
| general | General | ✅ Implemented (contact email/phone_number, tenant info) |
| branding | Branding | ✅ Implemented (primary color, logo, font) |
| hours | Business Hours | ✅ Implemented (Mon–Sun hours matrix) |
| publicprofile | Public Profile | ✅ Implemented (tagline, description, social links, media) |
| integrations | Integrations | 🚧 Placeholder ("coming soon") |
| notifications | Notifications | ✅ Implemented (channel × event matrix) |
| advanced | Advanced | 🚧 Placeholder ("coming soon") |

**Findings:**
- 2 of 7 tabs are placeholder stubs. The "Advanced" placeholder is the natural home for Feature Flags, but Feature Flags already exist at `/console/settings/feature-flags` — disconnected from the Settings page.
- "publicprofile" tab key is inconsistent with the others (no camelCase boundary). Minor UX issue: tab URL state is not persisted (refreshing resets to "general").
- Settings uses its own sticky header with `bg-white` — inconsistent with the admin theme system that uses `var(--card)` and CSS variables. Settings page also uses Tailwind raw colors (gray-50, blue-600) instead of design tokens.
- Settings page renders its own header bar with "Settings" title, duplicating the breadcrumb function.

### 3.2 Feature Flags orphan (critical)

`/console/settings/feature-flags` exists and works, but:
- No sidebar nav item points to it.
- The Settings page has no link to it.
- Only accessible by knowing the URL or breadcrumb navigation from within the page (which has a back-arrow link to `/console/settings`).
- The page requires `settings.manage` permission; the Settings nav item requires `settings.view`. Users with only `settings.view` see Settings in the sidebar but cannot reach Feature Flags.

## Section 4 — Navigation Hierarchy Issues

### 4.1 Merge candidates

| Issue | Current | Proposed |
|---|---|---|

- Order list page has no "View Customer" link to `/console/customers/[id]`.
- Customer detail has no "View Orders" shortcut to `/console/orders?customerId=X`.
- Branch list has no shortcut to Branch Analytics.
- Settings page has no link to Feature Flags.
- Feature Flags page has a back-arrow to Settings but no breadcrumb.

## Section 5 — Context Persistence

### 5.1 Current state

| Context | Stored where | Persisted? |
|---|---|---|
| Tenant | `useTenantStore` (memory) | ❌ Session only |
| Active branch | `useBranchStore` (memory) | ❌ Session only |
| Sidebar open/closed (mobile) | local `useState` | ❌ Not persisted |

| Auth / RBAC | Zustand persist | ✅ localStorage |
| Last visited page | — | ❌ Not tracked |

**Findings:**
- Refreshing the page resets the active branch to "All Branches" — users must re-select their branch every session.
- Mobile sidebar state is not persisted between page navigations (within an SPA session it's fine, but a full refresh closes it).
- Settings active tab is not URL-driven, so sharing a link to "Settings → Branding" is impossible.

## Section 6 — Quick Actions

No quick actions mechanism exists anywhere in the current admin. To create a menu item, a user must: navigate sidebar → Content → Menu → find "Add Item" button on the menu page. Same depth for any creation task.

**Missing quick actions (by frequency):**
1. Create Menu Item → `/console/menu` (scroll to add form)
2. Create Promotion → `/console/promotions`
3. Invite Staff Member → `/console/staff`
4. Add Branch → `/console/branches/new`
5. Create Reservation → `/console/reservations`
6. Export Analytics → `/console/analytics`

---

## Section 7 — Global Search

No search capability exists. Users of the admin panel cannot search across orders, customers, menu items, staff, or promotions without navigating to each page and using per-page filters.

**Impact:** High for operations with more than ~50 customers or orders. A cashier looking up a specific order must scroll through the orders list. A manager looking for a staff member by name must scroll through the staff list.

Proposed: `⌘K` / `Ctrl+K` command palette surface that:
- Searches navigation items (client-side, instant)
- Provides direct links to common actions
- Is a UX surface only — no backend search API required

## Section 8 — Cross-Navigation

### 8.1 Admin ↔ Public site

| Link | Present? | Location |
|---|---|---|
| Admin → Public site (current tenant) | ✅ | AdminHeader ("Public Site" link → `/`) |
| Public site → Admin | ❌ | Not in public Header for authenticated staff |
| Admin → Marketplace listing for this tenant | ❌ | Missing |

The "Public Site" link in AdminHeader goes to `/` (homepage), not to the tenant's own public page (e.g. `/restaurant/savor-demo`). This is a missed opportunity — the operator wants to preview their own page.

### 8.2 Admin → Website Builder

Website Builder (`/console/website`) is navigable from the sidebar but there is no "Preview" link from the Website Builder back to the live website. The `PreviewButton` component exists and is used in Settings, but not in Website Builder.

## Section 9 — Mobile IA

Current state after P8.9.4:
- Mobile sidebar is a slide-over triggered by a hamburger button.
- 21 nav items + 7 group headers visible in sidebar — at least 28 rows at 44px = 1232px minimum height. On a 667px phone_number, users must scroll extensively.
- No bottom navigation bar (common mobile pattern for 3–5 top destinations).
- The BranchSelector in the header is hidden on mobile (`hidden sm:flex`) — branch context is lost on mobile.

## Section 10 — Future Scalability

### 10.1 Registry growth projection

Current: 6 modules, 22 nav item constants, 7 groups, 54 admin pages.

At 300 pages / 100 modules (spec target):
- Sidebar at current density = ~100 nav items → unusable without a major hierarchy change.
- Module-specific items without group fields will be unsorted.
- `GROUP_ORDER` array in AdminSidebar is hardcoded — new groups require code change.

**Mitigation needed:**
- Workspace-level grouping above the current 7 groups.
- Sidebar collapse/expand per group.
- Search as primary navigation for power users.

## Proposed Workspace Model (Phase B)

The current 7 sidebar groups map to 4 logical workspaces:

| Workspace | Current Groups | Target audience |
|---|---|---|
| **Operations** | Operations, Customers | Kitchen, Cashier, Manager |
| **Sales & Content** | Content, Analytics | Marketing, Manager |
| **Team** | People | Owner, Admin |
| **Business** | Platform, System | Owner, Admin, Platform Admin |

This model is not yet surfaced to users — the sidebar shows all groups to all roles. The workspace model will inform future tab-bar navigation and role-based sidebar filtering, but is not implemented as a switcher in this phase.
