## §1 — Phase A: Real Backend RBAC Contract Gap Audit

Traced every flow named in the task against `NEXT_PUBLIC_USE_MOCK=false`'s
actual current behavior (the `else` branches already exist in the
codebase's services — this is not hypothetical).

| Flow | Current frontend expectation | Missing backend response | Required API contract | Migration impact |
|---|---|---|---|---|
| **Auth login** | `authService.login()` real branch: `api.post<{ user, tokens }>(ENDPOINTS.AUTH.LOGIN)` (`auth.service.ts:110-115`) | `p7Roles` (or equivalent) — real-mode response type has no such field | Login response must include a tenant-scoped role array, see §2 | `useLogin()`'s `if (p7Roles && p7Roles.length > 0)` guard already handles an absent field gracefully — no frontend code change strictly required to consume it once the backend adds it, only the response type needs widening |
| **OTP verification** | `authService.verifyOTP()` real branch: `api.post<{ user; tokens; p7Roles?: Role[]; is_new_user?: boolean }>(...)` (`auth.service.ts:255-260`) | Type already declares `p7Roles?: Role[]` optional — same gap as login, but the *type* is already correct here, only the backend needs to populate it | Same shape as login | None — this path is already contract-ready, just waiting on backend data |
| **Tenant switching** | `AdminTenantSwitcher.tsx` re-seeds `tenantRoles` for the new tenant via `setTenantRoles()`, from client-known mock data | A tenant-switch (or re-auth) response must return the caller's role grants **for the newly selected tenant specifically** — today it's read from a client-side lookup, not fetched per switch | `GET /api/v1/tenants/:tenantId/me/roles/` (or equivalent) called on switch, or roles for all tenants returned once at login and cached | `AdminTenantSwitcher.tsx` needs a new fetch call; `setTenantRoles()` itself is unchanged |
| **StaffAssignment loading** | `staffAssignmentService.getEffectiveAssignments()` reads a synchronous, hardcoded in-memory array (`_assignmentStore`) | A real, authenticated endpoint returning the caller's active assignments | `GET /api/v1/staff/:staffId/assignments/?active=true` (endpoint constants already reference `/admin/staff/{staffId}/assignments/` in the `grant()`/`revoke()` real-mode branches — `getEffectiveAssignments()` itself has no `else`/real branch yet, it's synchronous-only) | `getEffectiveAssignments()` needs an async real-mode branch; every caller (`ownership-resolution.service.ts`, `useHasDashboardAccess()`) currently calls it synchronously — becoming async would ripple into `usePermissions()`'s `useMemo`, which is a real architectural change, not a config swap. Flagged as the single largest remaining piece of work — see §8 |
| **Ownership resolution** | `resolveOwnershipIdentity()`/`ownerService.getOwnerByUserIdSync()` read synchronous mock Owner records | A real, authenticated endpoint returning the caller's Owner record if any | `GET /api/v1/owners/me/` | Same synchronous→async ripple concern as StaffAssignment above |
| **tenantRoles population** | Populated only at login/OTP-verify/tenant-switch, from `p7Roles` | Covered above | Covered above | — |
| **userOverrides population** | `setUserOverride()` called directly from two Console pages, 100% client-side, no network call at all (confirmed in P10.5.5, re-confirmed here — `grep` for `ENDPOINTS.RBAC` / `ENDPOINTS.PERMISSIONS` still returns nothing) | An entire resource doesn't exist yet | See §4 for the full contract proposal | Both Console pages need to call the new endpoint instead of writing directly to the store |
| **Permission resolution** | `usePermissions()` combines all 5 sources purely client-side, synchronously | No change needed **if** sources 1/2/4/5 above are populated from trusted backend responses — the resolution formula itself does not need to talk to a backend, only its inputs do | N/A — this is correctly a client-side computation over server-provided facts | None to the resolution logic itself |
| **Console access** | `useHasDashboardAccess()` re-derives Owner/Staff eligibility on every call from the same synchronous mock services | Same StaffAssignment/Ownership data dependency as above | Covered above | Same synchronous→async ripple concern |

**Overall finding:** every gap traces back to exactly two root causes —
(1) the login/session response contract doesn't carry RBAC data in
real mode yet, and (2) `staffAssignmentService`/`ownerService`/
`ownershipResolution` are built as **synchronous** functions that
`usePermissions()`/`useHasDashboardAccess()` call directly inside
`useMemo()`, which cannot survive becoming real (necessarily async)
network calls without a hook-level refactor. Nothing here requires a new
authorization *model* — only new data plumbing into the existing one.

## §2 — Phase B: Authentication RBAC Response Contract

### Current state (traced in `auth.service.ts`/`hooks/index.ts`)

Mock mode returns, and `useLogin()`/`useVerifyOTP()` already consume:
```ts
{ user: User; tokens: AuthTokens; p7Roles?: Role[] }
```
Real mode's `login()` is typed `Promise<{ user: User; tokens: AuthTokens }>`
— `p7Roles` is absent from the type entirely, not just empty at runtime.

### Final frontend contract (target, not implemented this phase)

```ts
interface AuthResponse {
  user: User
  tokens: AuthTokens
  tenantRoles?: Role[]        // renamed from p7Roles for backend clarity —
                               // frontend field name (`tenantRoles`) stays;
                               // wire name is the backend's choice
  permissions?: P7Permission[] // OPTIONAL — see "which fields" below
  ownership?: { ownedTenantIds: string[] }         // OPTIONAL, see below
  staffAssignments?: StaffAssignment[]              // OPTIONAL, see below
}
```

### Which fields must come from the backend

- **`user`, `tokens`** — already backend-authoritative today, unchanged.
- **`tenantRoles`** — **must** come from the backend. This is source 1
  of the 5-source model; the frontend has no way to know a user's role
  grants except by being told. Required for real-mode parity with mock
  mode.
- **`ownership` / `staffAssignments` (raw facts)** — **must** come from
  the backend once StaffAssignment/Ownership stop being mock services.
  The frontend needs the *facts* (does this user own tenant X, do they
  hold assignment Y), not a pre-computed verdict.

### Which fields should remain derived client-side

- **`permissions`** — **should NOT be sent by the backend as a
  precomputed array**, and the frontend should not consume it even if
  offered. `usePermissions()` already correctly computes the union of
  `ROLE_PERMISSION_MAP`-expanded `tenantRoles` + override application +
  ownership/staff-driven grants — that computation is deterministic,
  pure, and identical on both sides *if* `ROLE_PERMISSION_MAP` is kept
  as a shared, versioned contract (§1's finding, restated). Sending a
  precomputed `permissions` array would create a second source of truth
  that could drift from `ROLE_PERMISSION_MAP`, and would violate the
  task's explicit instruction: "Do NOT duplicate permission calculation
  if backend already provides authoritative data" — the backend's
  authoritative data is `tenantRoles`/`ownership`/`staffAssignments`
  (the *inputs*), not a computed `permissions` array (the *output*),
  which the frontend already derives correctly and must keep deriving to
  avoid two divergent implementations of the same formula.
- **`dashboard:access`** — stays entirely frontend-derived via
  `useHasDashboardAccess()`, computed from the same ownership/staff facts
  above. No backend endpoint needed for it specifically (confirmed in
  `docs/P10.5.5_PERMISSION_ARCHITECTURE_FINAL.md` §"Real Backend
  Migration Requirements" point 6, reaffirmed here).

### Not implemented this phase, and why

Widening `auth.service.ts`'s real-mode return type and consuming
`tenantRoles` in `AuthBootstrapper` (`providers/index.tsx`) would be the
natural next step, but doing so exposed a **real, previously-undocumented
gap** during this phase's research (see §3) — `AuthBootstrapper`'s
session-restore path (`authService.getMe()`) doesn't carry RBAC data
either, and `getMe()`'s return type (`Promise<User>`) is consumed
directly by `useMe()` and asserted on directly by
`src/test/phase4-e2e.test.ts:80-88` (`user.id`, `user.role`,
`user.email` read straight off the resolved value). Changing `getMe()`'s
contract to also carry `tenantRoles` would be a breaking change to an
established, widely-used function — real feature work with a broad
blast radius, not "prepare frontend contracts." Documented as the
concrete next implementation step in §8, not done here.

## §3 — Phase C: RBAC Store Hardening

### Current state (re-confirmed from P10.5.5, unchanged by this phase)

`useRbacStore` persists via `{ name: 'savor-rbac' }` with **no
`partialize`** (`src/stores/index.ts:568`) — the entire store,
including `tenantRoles` and `userOverrides`, round-trips through
`localStorage` on every load with no integrity check.

### Target migration plan

```ts
persist(
  (set, get) => ({ /* ...unchanged state/actions... */ }),
  {
    name: 'savor-rbac',
    partialize: (state) => ({
      // REMOVE FROM PERSISTENCE — must become server-populated,
      // client-cached values, never client-authoritative (P10.5.5):
      // tenantRoles: excluded
      // userOverrides: excluded

      // KEEP — no authorization impact if tampered:
      customRoles: state.customRoles,       // future custom-role drafts (§6)
      rbacAuditLog: state.rbacAuditLog,      // audit *display* data, not an authorization input
    }),
  },
)
```

`tenantRoles`/`userOverrides` would still exist as **runtime** state
(read/written normally within a session) — only their `localStorage`
persistence is removed. `customRoles` and `rbacAuditLog` are correctly
kept: neither is read by any permission-resolution code path (confirmed
in P10.5.5 §Phase C/F), so tampering with either has zero authorization
consequence — they're UI-only.

### Why this was NOT implemented this phase

Removing `tenantRoles` from persistence surfaces a **real regression**
discovered during this phase's research, not a hypothetical one:
`useAuthStore.user` is **not itself persisted** (no `persist` wrapper on
`useAuthStore`, confirmed `src/stores/index.ts:50-57`) — session
continuity across a page reload today comes entirely from
`AuthBootstrapper` (`src/providers/index.tsx:195-214`) reading the
`access_token` from `localStorage` and calling `authService.getMe()` to
restore `useAuthStore.user`. **`getMe()` never calls `setTenantRoles()`.**

Today, `tenantRoles` survives a page reload *only* because
`useRbacStore`'s own `persist` middleware writes it to `localStorage`
independently of the auth-restore flow. If `partialize` excluded
`tenantRoles` right now, with no other change, every page reload in
mock mode would restore the user's identity (via `getMe()`) but silently
drop their tenant role grants — breaking every admin/staff demo account
the moment they refresh the page. This is a confirmed, reproducible
functional regression, not a theoretical risk.

Fixing it correctly requires `AuthBootstrapper`'s session-restore path
to also repopulate `tenantRoles` — which needs `getMe()` to carry RBAC
data, which is exactly the same "would require a breaking contract
change to a function three other things depend on" problem identified
in §2. **This phase declines to implement the persistence removal until
that session-restore gap is closed**, per the task's own instruction:
"Do not implement unless clearly safe." Removing persistence today is
not clearly safe — it is provably unsafe against the current
`AuthBootstrapper` implementation. §8 lists closing this gap as the
required precondition, in the correct order.

`userOverrides` has no equivalent survive-a-reload dependency (nothing
currently restores it on session-restore either way — it's already only
as durable as the browser tab's `localStorage`), so excluding it from
persistence is lower-risk in isolation, but was left alone this phase to
keep the `partialize` change atomic (both fields moving together, once
both have a correct restore story) rather than shipping a partial,
inconsistent persist config.

## §4 — Phase D: Permission Override API Preparation

Audited `console/users/[id]/page.tsx` and `console/permissions/[userId]/page.tsx`
— both call `setUserOverride(userId, tenantId, allow, deny)` directly on
`useRbacStore`, with no request to any endpoint (confirmed via `grep` for
`ENDPOINTS`/`api.` in both files' save paths — neither imports `api` or
`ENDPOINTS`).

### Contract proposal (not connected this phase)

```
GET /api/v1/tenants/:tenantId/users/:userId/permissions/
```
**Response 200:**
```json
{
  "userId": "u1",
  "tenantId": "t1",
  "roles": ["cashier"],
  "rolePermissions": ["orders.view", "orders.manage", "..."],
  "allow": ["analytics.view"],
  "deny": ["staff.manage"],
  "effective": [
    { "permission": "orders.view", "fromRole": true, "fromOverride": false, "denied": false, "effective": true }
  ]
}
```
Matches the existing `EffectivePermissionResult` shape
(`src/types/rbac.ts`) already used by the Console's permission simulator
— no new response type needed, the frontend type already exists and is
unused only because there's no endpoint to hydrate it from yet.

```
PUT /api/v1/tenants/:tenantId/users/:userId/permissions/
```
**Request body:**
```json
{ "allow": ["analytics.view"], "deny": ["staff.manage"] }
```
Mirrors `setUserOverride()`'s existing parameter shape exactly
(`allow: P7Permission[]`, `deny: P7Permission[]`) — the frontend function
signature would not need to change, only what happens inside it (await
a PUT, then apply the *response's* confirmed state to the store, rather
than writing the local values directly).

**Response 200:** same shape as the `GET` above (server echoes back the
authoritative post-write state).

**Validation (server-side):**
- `allow`/`deny` must be valid `P7Permission` string literals (the
  server needs its own copy of the permission catalog, or validates
  against the same `ROLE_PERMISSION_MAP`-equivalent it maintains as the
  shared contract described in §1/§2).
- `allow` and `deny` must not both contain the same permission
  (frontend's `applyOverrides()` already resolves this by applying deny
  after allow — `permission.service.ts:529-537` — but the API should
  reject an ambiguous request rather than silently pick a winner).
- The target `userId` must have some relationship to `tenantId` (an
  active `StaffAssignment`, Owner record, or existing role grant) —
  granting an override to a user with zero relationship to the tenant is
  meaningless and should 404 or 400.

**Permission required to call this endpoint:** `staff.manage` in the
caller's own effective permission set for `tenantId` — matching the
`PermissionGuard permission="staff.manage"` gate already present on both
Console pages that call `setUserOverride()` today. This is not a new
permission; it's the existing one this feature has always been gated
behind, now also enforced server-side (defense-in-depth, per
`docs/P10.5.5_PERMISSION_ARCHITECTURE_FINAL.md` "Real Backend Migration
Requirements" point 4).

**Audit requirements:** every successful `PUT` must append an entry to
the tenant's audit log — the frontend already has a client-side
`rbacAuditLog`/`addRbacAuditEvent()` mechanism (`src/services/rbac-audit.service.ts`)
that exists for exactly this kind of event; the backend's audit trail
should be the authoritative one once this endpoint exists, with the
client-side log becoming either a cache of server-audit events or
retired in favor of fetching them — a decision for the phase that
actually implements this endpoint, not this one.

### Why not connected yet

Per the task's explicit instruction ("Do not connect API yet unless
existing service architecture supports it cleanly") — no `permission
service` currently has a mock/real split pattern to extend (unlike
`auth.service.ts`, `staff-assignment.service.ts`, etc., there is no
`rbac.service.ts`-equivalent left after P10.4.12's removal to add an
`if (mockActive()) {...} else {...}` branch to). Building one from
scratch, wiring it into both Console pages, and updating their save
flows to be async-aware (loading/error states they don't have today) is
real feature implementation, correctly out of this phase's "prepare
contracts" scope.

## §5 — Phase E: Tenant Role Loading Architecture

Confirmed ownership of each fact today, and that the target architecture
in the task's own diagram is **already exactly the frontend's current
shape** — this phase found no architectural change needed here, only the
backend-wiring gaps documented in §1-§4.

| Fact | Owner today | Owner in target architecture | Match? |
|---|---|---|---|
| Tenant role truth (`tenantRoles`) | Mock `MOCK_CREDENTIALS` registry, read at login | Backend | Same *role*, different *source* — frontend already only ever stores what it's told, never invents a role |
| Assignment truth (`StaffAssignment`) | Mock `staff-assignment.service.ts` in-memory array | Backend | Same |
| Ownership truth | Mock `owner.service.ts`/`ownership.service.ts` | Backend | Same |
| Permission *calculation* | Frontend (`usePermissions()`, deterministic function of the facts above) | Frontend | **Already correct** — see §2's "which fields should remain derived" |
| UI hide/show, route guards | Frontend (`PermissionGuard`, `AuthGuard`, `useHasDashboardAccess()`) | Frontend | Already correct |

The frontend was never architected to compute role/assignment/ownership
*truth* — it has always treated `tenantRoles`/`StaffAssignment`/Owner
records as **given facts** to expand into permissions, whether those
facts came from a mock registry (today) or a real backend (target). The
"backend remains final authority" requirement in the task is therefore
**already satisfied at the architecture level** — the only work is
literally connecting the wires (§1's gap list), not changing who's
responsible for what.

## §6 — Phase F: Custom Roles Decision

**Decision: Option B — disclosed, not removed.**

Per P10.5.5's audit: `customRoles` has one write path
(`app/console/roles/new/page.tsx`), zero read consumers, and is never
unioned with `ROLE_TEMPLATES` (the actual role catalog every other
Console page reads). Completing it (Option A) requires extending the
closed `Role` union, wiring `ROLE_PERMISSION_MAP`/`usePermissions()` to
consult it, and reconciling it with `ROLE_TEMPLATES` — real permission-
model design work explicitly forbidden this phase ("Do NOT create a new
RBAC system").

Fully removing the creation UI (`app/console/roles/new/page.tsx`) was
considered and rejected in favor of the smallest change that satisfies
"do not leave a misleading half-feature": the form still works exactly
as before (nothing about its data flow changed), but now visibly
discloses, above the fold, that saving a custom role does not yet grant
any permissions or appear in the role list. This was chosen over
removal because:
- The `addCustomRole()` write path is real, tested
  (`phase8-6-enterprise-rbac.test.ts`), and harmless — persisting a
  named permission set for later is legitimate even before it's wired
  into resolution.
- Removing the route/form would be a larger, more disruptive change than
  the finding warrants, and the task explicitly allows disclosure as an
  outcome ("Implement only if scope allows. Otherwise document final
  decision.").

**Implementation:** added a translated warning banner
(`customRoleNotActiveWarning` — `src/i18n/locales/{en,ar,fa}.json`) to
`src/app/console/roles/new/page.tsx`, rendered unconditionally above the
role-builder form. No change to `addCustomRole()`, `useRbacStore`,
`ROLE_TEMPLATES`, or `app/console/roles/page.tsx`.

## §7 — Phase G: Feature Flag Authorization Consistency

**Decision: yes, all three permission hooks should share identical
feature-flag behavior** — `PermissionGuard`'s own doc comment already
claimed the formula is "Permission AND Capability AND FeatureFlag" for
*all* modes (single/any/all), but only `usePermission()` actually
enforced the FeatureFlag term (P10.5.5 finding).

**Implemented:** extracted the per-resource flag lookup
(previously inlined only in `usePermission()`) into a shared
`isPermissionFeatureFlagGated()` helper plus a module-level
`PERMISSION_FEATURE_FLAG_MAP` constant in `src/hooks/index.ts`.
`useAnyPermission()` and `useAllPermissions()` now call it inside their
`.some()`/`.every()` callbacks, identically to how `usePermission()`
always has. Zero change to `usePermission()`'s own behavior (still the
same map, same lookup, same short-circuit) — purely additive to the
other two.

**Tests:** `src/test/p10.6-rbac-real-backend-readiness.test.ts` Phase G
section (5 tests) — proves: `usePermission()`'s existing flag-denial
behavior is unchanged; `useAnyPermission()` now denies when its only
matching permission is flag-gated off; `useAllPermissions()` now denies
when any required permission is flag-gated off; `useAnyPermission()`
still grants when a non-gated alternative passes (proving `.some()`
short-circuit logic is intact, not broken by the new check); and all
three hooks agree when no flag is disabled (the common, unaffected
case). All 11 tests in the new file pass; full suite is unchanged at 14
pre-existing failures (see §9).

**PermissionGuard behavior preserved:** `PermissionGuard.tsx` calls these
hooks without any wrapping logic of its own — it now correctly renders
its documented formula for every mode, closing a gap where "any"/"all"
mode checks could have rendered permission-gated UI behind a disabled
feature the "permission" mode would have correctly hidden.

## §8 — Recommended Implementation Order For a Future Phase

In dependency order (each step is a precondition for the next):

1. **Widen `getMe()`'s real-mode contract** to optionally carry RBAC
   data (`tenantRoles`, and later `staffAssignments`/`ownership`),
   update `src/test/phase4-e2e.test.ts` and `useMe()`'s consumers for
   the new shape, and have `AuthBootstrapper` call `setTenantRoles()`
   after a successful `getMe()`, mirroring `useLogin()`'s existing
   pattern. This closes the session-restore gap identified in §3 and is
   the direct precondition for step 2.
2. **Only after (1):** add `partialize` to `useRbacStore`'s persist
   config per §3's target config, excluding `tenantRoles`/`userOverrides`.
3. **Widen `auth.service.ts`'s real-mode login/OTP response types** to
   include `tenantRoles` (§2), matching what mock mode already returns.
4. **Build the permission-override endpoint** per §4's contract, add a
   mock/real split to a new `rbac.service.ts`-equivalent (name TBD, not
   the retired legacy one), and wire both Console override pages to call
   it instead of writing to `useRbacStore` directly.
5. **Convert `staffAssignmentService.getEffectiveAssignments()` and the
   Ownership resolution read path to async**, and refactor
   `usePermissions()`/`useHasDashboardAccess()` to consume them via
   React Query (the pattern already used everywhere else data comes from
   a service in this codebase) instead of a synchronous call inside
   `useMemo()`. This is the largest single piece of remaining work and
   should be its own phase with its own test suite, not folded into
   anything above.
6. **Only after (5) is real and backend-backed:** revisit whether
   `customRoles` (§6) should move to Option A, now that a real role/
   permission backend contract exists to extend.

## §11 — Security Model (Restated, Unchanged From P10.5.5)

Frontend permission checks remain UX affordances, not enforcement. Every
gap this phase found and left unfixed (real-mode `tenantRoles` staying
empty, `userOverrides` having no backend, session-restore not carrying
RBAC data) is a **functional/UX gap in mock-vs-real parity**, not a new
security hole beyond what P10.5.5 already documented — the underlying
risk (client-persisted, client-tamperable `tenantRoles`/`userOverrides`)
is unchanged by this phase, because §3 explicitly declined to remove
persistence until the session-restore precondition is met. The Phase H
localStorage-tampering test in
`src/test/p10.6-rbac-real-backend-readiness.test.ts` deliberately encodes
today's actual (unmitigated) behavior as a passing assertion, specifically
so that whichever future phase implements §8 step 2 will see that test
**start failing** — the intended signal that the migration has reached
the point where tampering should no longer be trusted, at which point
that test's assertions must be flipped to their target (post-migration)
form.
