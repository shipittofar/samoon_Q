# P10.4.11 — Remove Legacy AuthGuard Permission Fallback

Removes the last runtime reference to the legacy RBAC permission engine
from `AuthGuard`, completing the sequence started by P10.4.9 (fixture
migration) and P10.4.10 (`legacyGranted` removal from
`useHasDashboardAccess()`). After this phase, `AuthGuard` — the only
other application-code reference to `rbacService` remaining per
`docs/P10.4.8_LEGACY_COMPATIBILITY_AUDIT.md` Phase B/F — no longer calls
`rbacService.hasPermission()` at all.

## Removed

**`src/components/auth/AuthGuard.tsx`**:

- The `rbacService.hasPermission(user?.role ?? null, requiredPermission)`
  call (the fallback branch for any `requiredPermission` other than
  `'dashboard:access'`).
- The `import { rbacService } from '@/services/rbac.service'` statement
  (dead once its only call site was removed).
- The `import type { LegacyPermission } from '@/types'` statement and
  `requiredPermission`'s `LegacyPermission` type.
- The `user` destructure from `useAuthStore()` (it was only read by the
  removed `rbacService.hasPermission()` call).

**AuthGuard's legacy permission fallback** — the mechanism that let
`AuthGuard` gate access to *any* colon-notation legacy permission string
via a direct `rbacService` lookup, independent of the P7 permission
engine. In practice this fallback was already dead code (confirmed in
P10.4.8 Phase B/F: `AuthGuard` is invoked with `requiredPermission` in
exactly one place across the whole application —
`app/console/layout.tsx`, always with the literal `'dashboard:access'`
— so the fallback branch was structurally present but never actually
executed). It has now been replaced, not just deleted, so `AuthGuard`
remains a generically reusable guard for any future caller that needs a
non-`dashboard:access` permission check.

## Before

```
requiredPermission provided?
        │
        ├─ no  → permissionGranted = true
        │
        └─ yes → requiredPermission === 'dashboard:access'?
                        │
                        ├─ yes → useHasDashboardAccess()  (P7/ownership-aware)
                        │
                        └─ no  → rbacService.hasPermission(user.role, requiredPermission)
                                  (legacy UserRole → LegacyPermission lookup,
                                   src/services/rbac.service.ts)
```

`requiredPermission` was typed `LegacyPermission` (colon-notation, e.g.
`'orders:manage'`), so any non-`dashboard:access` value necessarily
routed through the legacy engine — there was no way to ask AuthGuard for
a P7 (dot-notation) permission at all.

## After

```
requiredPermission provided?
        │
        ├─ no  → permissionGranted = true
        │
        └─ yes → requiredPermission === 'dashboard:access'?
                        │
                        ├─ yes → useHasDashboardAccess()  (P7/ownership-aware,
                        │        unchanged — this special case stays, because
                        │        ROLE_PERMISSION_MAP never grants the literal
                        │        'dashboard:access' permission to any role —
                        │        see docs/P10.4.8_LEGACY_COMPATIBILITY_AUDIT.md
                        │        Phase G)
                        │
                        └─ no  → usePermission(requiredPermission)  (P7 engine,
                                  src/hooks/index.ts → permission.service.ts)
```

`requiredPermission` is now typed `P7Permission` (dot-notation, plus the
single `'dashboard:access'` legacy-compat member `P7Permission` already
included — see `src/types/rbac.ts`). `console/layout.tsx`'s existing
`requiredPermission="dashboard:access"` usage compiles unchanged, since
`'dashboard:access'` is a valid `P7Permission` literal.

`usePermission()` (`src/hooks/index.ts`) is the same hook `PermissionGuard`
and other P7-aware components already use — no new permission-checking
logic was written; `AuthGuard` now calls the existing engine instead of
re-implementing a lookup against the legacy tables.

- **Legacy isolation** (3 tests): `AuthGuard.tsx`'s source contains no
  executable `rbacService.hasPermission(` call and no `LegacyPermission`

  the repo-wide comment-stripped search described above returns zero
  offenders.

### Known gap discovered (not fixed — out of scope)

While writing the `dashboard:access` coverage per this phase's required
account list (Owner/Staff/Manager/Cashier/Kitchen/Marketing/Support),
`marketing@savor.com` was found to still be denied `dashboard:access`.
Its `StaffMember` record (`staff-marketing-01`) has **zero** active
`StaffAssignment` rows in `src/services/staff-assignment.service.ts`
(the only `marketing`-tagged assignment, `assign-009` on
`staff-marketing-02`, has `status: 'revoked'`). This is the same class
of gap P10.4.9 closed for `admin@savor.com`/`kitchen@savor.com` — but
P10.4.9's explicit scope named only those two accounts, so
`marketing@savor.com` was never covered.

This is **not** caused by, or related to, this phase's `AuthGuard.tsx`
change — `AuthGuard` already routed `dashboard:access` through
`useHasDashboardAccess()` before this phase (P10.2.2/P10.3.1), and this
phase didn't touch that path at all. It's a pre-existing fixture gap,
independently discovered here. Per this phase's explicit scope ("Modify
only: `src/components/auth/AuthGuard.tsx`"), fixing it would mean
editing `staff-assignment.service.ts`, which is out of scope for this
phase. It is documented here, and the test suite asserts the *current*
(denied) behavior for `marketing@savor.com` rather than either silently
omitting it from coverage or silently "fixing" fixtures outside this
phase's stated boundaries. A future phase should add the missing
`StaffAssignment` row, following the exact pattern P10.4.9 used for
`admin@savor.com`/`kitchen@savor.com`.
