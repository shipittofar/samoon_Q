# P9.4 — Platform Administration Center

> Companion to `docs/P9.4_PLATFORM_ADMIN_AUDIT.md` (Phase A). Documents what
> was actually built: the Platform Administration Center — the control
> surface for the whole SaaS platform, distinct from both the per-tenant
> Console and the Configuration Studio's settings-only scope — built
> entirely as a new layer on top of the P9.0–P9.3 foundation.
>
> Last updated: 2026-07-05

---

## 1. Architecture

P9.4 adds exactly one new source directory, `src/platform-admin/`, plus a
handful of small additive touches to P9.0–P9.3 files. Nothing in
`src/config/`, `src/components/admin/configuration/`, or any P9.0–P9.3
route was rewritten:

```
src/platform-admin/
├── permissions.ts        Phase G — PlatformRole/PlatformPermission model
├── store.ts               Phase G — usePlatformAdminStore (zustand)
├── hooks.ts               Phase G — usePlatformRole / usePlatformPermission
├── nav-groups.ts          Phase B — the 12 IA groups
├── register-module.ts     Phase C — registerAdminModule() convenience wrapper
├── modules/               Phase C — ~55 new ConfigModuleDefinitions, by IA group
├── dashboard.ts           Phase D — PlatformWidgetDefinition + registry
├── widgets.ts             Phase D — ~23 registered dashboard widgets
├── icon-map.ts            Phase D/E — shared lucide icon lookup
├── search.ts              Phase F — PlatformSearchProvider registry
├── search-providers.ts    Phase F — Businesses/Platform Users/Countries providers
└── index.ts               Public entry point (registers everything as a side effect)
```

Every module registered here is an ordinary `ConfigFieldDefinition`/
`ConfigModuleDefinition` flowing through the exact same
`PlatformConfigurationRegistry` → `ConfigurationService` →
`ConfigurationStudioLayout` pipeline Authentication (P9.1.3) and Countries
(P9.2) already use. **This is the central architectural decision of the
phase**: the Platform Administration Center is not a second UI — it is the
Configuration Studio, given more modules to render and a dashboard as its
landing page.

## 2. What's genuinely new vs. what's reused

| Capability | Status |
|---|---|
| Registry, resolver, service, validator, cache, audit, version manager | **Reused unchanged** (P9.0/P9.0.1) |
| `'collection'` field type + table/drawer/bulk-actions/filter/search engine | **Reused unchanged** (P9.2) — backs Tenants, Platform Users, and continues backing Countries |
| Studio shell — nav/toolbar/Inspector/Inheritance-tree/History/Compare/command palette | **Reused unchanged** (P9.3) — see §3 for the two additive props that made this possible |
| Information Architecture (12 nav groups) | **New** (Phase B) — `ConfigModuleDefinition.group`, optional, falls back to `category` |
| ~55 Platform Administration modules | **New** (Phase C) |
| Platform permission model (`PlatformRole`) | **New** (Phase G) — deliberately separate from tenant RBAC |
| Platform Dashboard (widget registry + 23 widgets) | **New** (Phase D) |
| Cross-entity global search provider registry | **New** (Phase F) — merges into the existing P9.3 command palette, not a second search UI |
| `/platform-admin` and `/platform-admin/[moduleId]` routes | **New** — mirror the P9.1.3/P9.3 route pattern exactly |

## 3. How the Studio was extended without being rewritten

Three small, additive changes made the existing P9.3 Studio serve a second,
much larger module set and a dashboard landing page:

1. **`ConfigModuleDefinition.group?: string`** (`src/config/types.ts`) — an
   optional top-level IA grouping key. `ConfigurationStudioNav` now groups
   by `mod.group ?? mod.category`; every P9.0–P9.3 module (which never sets
   `group`) renders identically to before. The 15 pre-existing Configuration
   modules were each given one `group: '...'` line (e.g. `authentication.ts`
   → `'Security'`, `countries.ts` → `'Configuration'`) so they slot into the
   new IA instead of sitting outside it.
2. **`ConfigModuleDefinition.platformPermission?: string`** — gates a
   module's visibility in `ConfigurationStudioNav` against the new platform
   permission model. Absent on every P9.0–P9.3 module, so they stay visible
   to every platform role exactly as before.
3. **`ConfigurationStudioLayoutProps.emptyWorkspace?: ReactNode`** — what
   the workspace pane shows with no module selected. Omitted by the
   Configuration Studio's own routes (unchanged "Select a module…" prompt,
   verified by the pre-existing P9.3 test still passing unmodified in
   assertion, only relocated to scope on the new `<header>` landmark — see
   §6); the new `/platform-admin` routes pass `<PlatformDashboard />`.

`configurationService.getFieldLayers()` (added for P9.3's Inheritance tree)
and `configCollection`'s helpers (P9.2) are reused as-is by the new search
providers and the Tenants/Platform Users collection modules — no
duplicate "read an entity's values" implementation exists anywhere in P9.4.

## 4. Information Architecture (Phase B)

Twelve top-level groups (`src/platform-admin/nav-groups.ts`): **Platform,
Users, Businesses, Subscriptions, Configuration, Security, Monitoring,
Infrastructure, Automation, Developer, Support, System.** Every module —
old and new — belongs to exactly one. The nav (`ConfigurationStudioNav`,
P9.3, unmodified in structure) already grouped modules by a string key;
Phase B only changed which key it reads.

## 5. Module Registry (Phase C)

`registerAdminModule()` (`src/platform-admin/register-module.ts`) is a thin
convenience wrapper — not a new registration mechanism — around
`defineField()`/`platformConfigurationRegistry.register()`, reducing ~55
modules' worth of repeated permissions/version/section boilerplate to
compact data. It also **auto-namespaces field ids** under the module id
(`${moduleId}.${fieldId}`) unless already namespaced, because
`PlatformConfigurationRegistry.register()` enforces globally-unique field
ids (Rule 3) — a real bug (`'primary_provider'` colliding between Email and
SMS provider modules) was caught by this exact check the first time the
full module set was imported together, fixed by this auto-namespacing
rather than hand-editing every field id.

Per the phase's explicit instruction ("do not build everything, just
register them"), most modules are compact — 2–4 scalar settings fields.
**Three are real `'collection'` fields**, not stubs, to concretely prove
the Collection Framework (P9.2) generalizes to entirely different domains:

- `platform.tenants` — the platform's 6 seed tenants (mirroring
  `src/services/tenant.service.ts`'s mock data, not duplicating its logic)
- `platform.users` — 5 illustrative platform staff accounts, each with a
  `PlatformRole`
- Countries (`countries.registry`, P9.2, untouched) continues to
  demonstrate the same framework a third time

## 6. Platform Permission Model (Phase G)

`src/platform-admin/permissions.ts` defines `PlatformRole` (Owner, Super
Admin, Admin, Support, Operations, Finance, Security, Developer, Auditor,
Read Only) and a flat, additive `PLATFORM_ROLE_PERMISSIONS` map (`'*'`
wildcard for Owner/Super Admin, resource-scoped grants for the rest) —
deliberately simpler than tenant RBAC (no per-user overrides, no per-branch
scoping), because platform staff counts are small and roles map cleanly to
job functions. `usePlatformAdminStore` (a standalone zustand store, not an
addition to `useAuthStore`/`useRbacStore`) holds the current role, defaulting
to `platform_super_admin` for the same mock-mode-friendly reason every other
demo default in this codebase does.

**This is intentionally a second, separate system from tenant RBAC**, not
an extension of it — see `docs/P9.4_PLATFORM_ADMIN_AUDIT.md` §1 for why
conflating "what can this user do in one tenant's console" with "what can
this user do across the whole platform" would have been the actual
architectural mistake. `PlatformPermissionGuard` (`src/components/auth/`)
is the platform-scoped counterpart to the existing tenant `PermissionGuard`
— same shape, different permission source, never the same component.

## 7. Platform Dashboard (Phase D)

`platformDashboardRegistry` (`src/platform-admin/dashboard.ts`) mirrors
`PlatformConfigurationRegistry`'s register-once/duplicate-id-guard shape —
a proven pattern reused for a new domain, not the same registry repurposed
(a widget computes a live value; a field resolves an inheritance chain —
forcing a widget through `ConfigurationService.resolveField` would have
been the real duplication to avoid). 23 widgets
(`src/platform-admin/widgets.ts`) covering every example the phase named
(Active Businesses, MRR/ARR, Failed Payments, Server Health, Queue Status,
Top Countries/Businesses, …), each declaring which `PlatformPermission` it
requires and a synchronous `compute()` — illustrative mock values today,
with the extension point (§9) documented for a real backend.
`PlatformDashboardWidgetCard` dispatches on `widget.kind` (`'stat'` |
`'list'` | `'status'`) exactly the way `ConfigurationFieldRow` dispatches on
`field.type` — one dispatch point, no per-widget branching.

## 8. Platform Search (Phase F)

`platformSearchRegistry` (`src/platform-admin/search.ts`) is a pluggable
provider registry — a provider never touches React or a router, it returns
`{ id, label, hint, moduleId }` hits, and the consumer (the P9.3 command
palette) decides what "select this hit" means (navigate to that module).
Three real providers (`search-providers.ts`) search the Tenants, Platform
Users, and Countries collections using the exact same
`configCollection.getCollectionEntries`/`getEntityLabel` helpers P9.2
already ships — not a second search implementation. `ConfigurationCommandPalette`
imports only `@/platform-admin/search` (the registry/types, no providers) —
never the `@/platform-admin` barrel — so the Configuration Studio has zero
build/runtime dependency on P9.4; the dependency direction is strictly
Platform Admin → Studio, never the reverse.

## 9. Extension guide — a real backend, or a future module

**Swapping mock data for a real backend**, in order of how much of P9.4
depends on it:
1. `platformDashboardRegistry`'s `compute()` functions → replace with a
   data-fetching hook per widget (the registry/rendering contract is
   unchanged; only where the numbers come from changes).
2. `search-providers.ts`'s three providers → replace
   `configCollection.getCollectionEntries` (reading the in-memory
   collection value) with an API call returning the same
   `PlatformSearchHit[]` shape.
3. Every registered module's fields → already backend-ready via
   `ConfigurationService`; see §36/§37 of `docs/BACKEND_API_CONTRACT.md`.

**Adding a future module** (CRM, Inventory, POS, Accounting, Delivery,
Franchise, AI, …) needs only:
1. Call `registerAdminModule({ id, name, description, group, fields })` —
   picking one of the 12 existing IA groups, or add a 13th to
   `PLATFORM_ADMIN_GROUPS` if genuinely none fit.
2. Optionally declare `platformPermission` for role-gating and a
   `'collection'` field if the module has a "many entities, one schema"
   shape — it inherits the full P9.2 table/drawer/bulk-actions engine for
   free.
3. Optionally register a dashboard widget or search provider the same way.

No route, nav, Inspector, history, compare, or search code needs to change
— this was true for Authentication (P9.1.3) and Countries (P9.2), and
remains true here for every module Phase C registered.

## 10. UX (Phase I) — inherited vs. new vs. deferred

Most of what an enterprise admin surface needs was already built in
P9.1.3/P9.2/P9.3 and is inherited unchanged: sticky save experience,
dependency engine, dark mode (CSS variables throughout, no new light/dark
branching needed), keyboard shortcuts (Ctrl/Cmd+S, Ctrl/Cmd+K, Esc),
command palette, responsive nav/inspector-as-drawer, bulk actions
(enable/disable/publish/archive/reset/export), full history with rollback,
compare mode, and the resizable/collapsible 3-pane split view. P9.4 added
the dashboard and cross-entity search on top of these.

**Deferred, and explicitly not silently implied as done:**
- **Virtualized tables.** `ConfigurationCollectionTable` (P9.2) renders
  every filtered row into the DOM; at 176 rows (Countries) this is fine, but
  a future collection with 10k+ entities would need real windowing
  (react-window or similar) — not added here to avoid touching P9.2's
  tested rendering path without a concrete need driving it yet.
- **Context menus.** Right-click menus were not added; all actions remain
  reachable via visible buttons/toolbars, which satisfies keyboard-only
  and screen-reader users better than a context-menu-only affordance would
  have anyway.
- **Widget-level "undo".** Dashboard widgets are read-only presentational
  data — there is nothing on the dashboard itself to undo. Undo/rollback
  for actual configuration changes is fully implemented (§11 of
  `docs/P9.3_CONFIGURATION_STUDIO.md`).

## 11. Known Limitations

- **Dashboard/search/widget data is illustrative**, not live — see §9 for
  the exact swap points.
- **The platform permission model has no persistence beyond localStorage**
  (`usePlatformAdminStore`) — a real deployment would derive `PlatformRole`
  from the authenticated session, not a client-persisted default.
- **`platform.tenants`'s roster is the 6 hand-known seed tenant slugs**,
  not dynamically read from `tenant.service.ts` (which is `async`; a
  synchronous collection default can't await it) — see
  `src/platform-admin/modules/businesses.ts`'s doc comment.
- Everything already listed in `docs/P9.3_CONFIGURATION_STUDIO.md` §18
  (Known Limitations) still applies, since the Studio itself is unchanged.

## 12. Future Roadmap

- Real backend for §37 of `docs/BACKEND_API_CONTRACT.md`.
- A genuine draft→published workflow for a module-as-a-whole (today
  "Publish" in the toolbar is still an alias for Save, per P9.3 §18).
- Table virtualization once a collection module's roster is large enough
  to need it.
- A 13th+ IA group if a future domain (e.g. "Franchise") doesn't fit the
  current 12.
