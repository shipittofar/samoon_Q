# P10.7 — RBAC Session Hydration: First Production-Safe Backend Migration Step

Implements the first dependency-safe stage of
`docs/P10.6_RBAC_REAL_BACKEND_MIGRATION_PLAN.md` §8 step 1: closing the
session-restore gap that blocked removing `tenantRoles`/`userOverrides`
from `useRbacStore`'s `localStorage` persistence. Does not redesign
authorization, does not touch `ROLE_PERMISSION_MAP`, does not remove
persistence yet, and does not convert `StaffAssignment`/Ownership
Resolution to async reads.

## Pre-Implementation Inspection (as required by the task)

### 1. Current RBAC hydration flow (before this phase)

Two independent, disconnected write paths populated `tenantRoles`:

1. **`useLogin()`/`useVerifyOTP()`** (`src/hooks/index.ts`): on a
   successful `authService.login()`/`authService.verifyOTP()`, if the
   response included a non-empty `p7Roles` array, called
   `useRbacStore.getState().setTenantRoles(tenantId, p7Roles)`.
2. **`useRbacStore`'s own `persist` middleware**: independently wrote
   the entire RBAC store, including `tenantRoles`, to `localStorage`
   under the `samoon-rbac` key, with no `partialize`.

**`AuthBootstrapper`** (`src/providers/index.tsx`) — the component
responsible for restoring a session on page load — called
`authService.getMe()` and only ever did `setUser(user)`. It had **zero**
RBAC-hydration step. This meant `tenantRoles` survived a page reload
*exclusively* because of write path 2 above (localStorage persistence),
never because of write path 1 (login) being re-run — `getMe()` isn't a
login, it's a session restore, and nothing re-derived `tenantRoles` from
it. This is the exact gap documented in
`docs/P10.6_RBAC_REAL_BACKEND_MIGRATION_PLAN.md` §3 and re-confirmed
here before any code was touched, per the task's own instruction.

### 2. Files required for the change

- `src/services/auth.service.ts` — `login()`, `verifyOTP()`, `getMe()`
  return type contracts.
- `src/types/ownership.ts` — new shared `AuthSessionRbacPayload` type
  (imports `Owner`/`StaffAssignment`, already defined there).
- `src/providers/index.tsx` — `AuthBootstrapper`'s session-restore
  effect.
- `src/stores/index.ts` — comment-only documentation on `tenantRoles`/
  `userOverrides` and the `persist()` call (Phase F — no config change).
- `src/test/p10.7-rbac-session-hydration.test.ts` — new test file
  (Phase E).
- `docs/P10.7_RBAC_SESSION_HYDRATION_IMPLEMENTATION.md` — this document.

### 3. Conflicts with previous P10 phases

None found. Specifically checked:
- **P10.5.4** removed `branchRoles`/`roleAssignments` from `useRbacStore`
  — neither field is touched by this phase.
- **P10.5.5** renamed `legacyEffective` → `tenantRolePermissions` inside
  `usePermissions()` and fixed the `useAnyPermission()`/
  `useAllPermissions()` feature-flag gate — neither function is modified
  here; `usePermissions()` itself is untouched.
- **P10.6** documented (but explicitly did not implement) exactly this
  gap and named it as the required precondition for persistence removal

  consistent with P10.6 §8's stated order.
- `permission.service.ts`, `ownership-resolution.service.ts`,
  `staff-assignment.service.ts`, `AuthGuard.tsx`, `PermissionGuard.tsx`

## Phase A/C — Fix Auth Session RBAC Hydration + Update `auth.service.ts`

### `getMe()` (the core fix)

**Before:**
```ts
async getMe(): Promise<User> {
  if (mockActive()) {
    await delay(300)
    if (typeof localStorage !== 'undefined') {
      const email = localStorage.getItem(MOCK_SESSION_KEY)
      if (email && MOCK_CREDENTIALS[email]) return MOCK_CREDENTIALS[email].user
    }
    return MOCK_USER
  }
  const { data } = await api.get<User>(ENDPOINTS.AUTH.ME)
  return data
}
```

**After:**
```ts
async getMe(): Promise<User & AuthSessionRbacPayload & { tenantRoles?: Role[] }> {
  if (mockActive()) {
    await delay(300)
    if (typeof localStorage !== 'undefined') {
      const email = localStorage.getItem(MOCK_SESSION_KEY)
      if (email && MOCK_CREDENTIALS[email]) {
        const entry = MOCK_CREDENTIALS[email]
        return { ...entry.user, tenantRoles: entry.p7Roles }
      }
    }
    return { ...MOCK_USER, tenantRoles: [] }
  }
  const { data } = await api.get<User & AuthSessionRbacPayload & { tenantRoles?: Role[] }>(ENDPOINTS.AUTH.ME)
  return data
}
```

This is a **structural widening** (`User` → `User & {...}`), not a
reshape — every field `User` had is still present at the top level, so
every existing consumer that reads `user.id`/`user.role`/`user.email`
off `getMe()`'s result (`useMe()`, `AuthBootstrapper`,
`src/test/phase4-e2e.test.ts:80-88`) keeps working unmodified. Mock mode
now returns the session email's `p7Roles` under the new `tenantRoles`
key — the same fact `login()`/`verifyOTP()` already returned, now also
available from session restore.

### `login()` and `verifyOTP()`

`verifyOTP()`'s real-mode branch already typed `p7Roles?: Role[]` —
unaffected, only widened with `& AuthSessionRbacPayload` for the two
forward-compatible fields (`ownership`, `staffAssignments`).
`login()`'s real-mode branch was missing `p7Roles` entirely (the exact
gap `docs/P10.6_RBAC_REAL_BACKEND_MIGRATION_PLAN.md` §2 flagged) — now
widened to `{ user: User; tokens: AuthTokens; p7Roles?: Role[] } & AuthSessionRbacPayload`,
matching mock mode's shape. Both are optional; a backend that sends none
of these fields yet behaves exactly as before.

### Naming: why `getMe()` uses `tenantRoles` but `login()`/`verifyOTP()` keep `p7Roles`

The task's target `AuthResponse` contract names the field `tenantRoles`.
`getMe()` had no pre-existing field name to preserve, so it uses
`tenantRoles` directly, matching the target contract exactly.
`login()`/`verifyOTP()` already return `p7Roles` today, consumed by
`useLogin()`/`useVerifyOTP()` and asserted by
`src/test/p9-1-2-runtime-integration.test.ts:29`
(`expect(login.p7Roles).toEqual([])`). Renaming `p7Roles` → `tenantRoles`
on those two functions would be a field rename across working code and
an existing test assertion, for a purely cosmetic gain — the task
explicitly says "Do not change consumers unnecessarily" and "Preserve
existing return compatibility." `p7Roles` already **is** the
`tenantRoles` fact the target contract describes; it is not a
different, legacy concept that needs migrating. Kept as-is; flagged as a
trivial, optional future rename, not forced through this phase.

### `AuthSessionRbacPayload` (new type, `src/types/ownership.ts`)

```ts
export interface AuthSessionRbacPayload {
  ownership?: Owner[]
  staffAssignments?: StaffAssignment[]
}
```

Placed in `ownership.ts` (not `rbac.ts`) specifically to avoid a
circular import — `ownership.ts` already imports `Role` from `rbac.ts`,
so defining a type here that also needs `Owner`/`StaffAssignment` (both
already declared in this file) has zero import risk, whereas the reverse
(`rbac.ts` importing from `ownership.ts`) would create one.

Both fields are optional and, per the task's explicit constraints
("Do NOT convert StaffAssignment async yet", "Do NOT convert ownership
resolution async yet"), are **not wired into any store or resolution
path this phase** — see Phase D below for exactly what happens if they
are present on a response.

## Phase B — Auth Contract (target vs. implemented)

Target from the task:
```ts
interface AuthResponse {
  user: User
  tokens: AuthTokens
  tenantRoles?: Role[]
  ownership?: OwnershipRecord[]
  staffAssignments?: StaffAssignment[]
}
```

Implemented equivalent, split across the three functions that actually
need it (no single `AuthResponse` type was introduced, to avoid
reshaping three independently-typed, independently-tested functions
into one shared interface they'd all have to conform to exactly — each
already has a slightly different shape, e.g. `verifyOTP()` also carries
`is_new_user`):
- `login()` → `{ user: User; tokens: AuthTokens; p7Roles?: Role[] } & AuthSessionRbacPayload`
- `verifyOTP()` → `{ user: User; tokens: AuthTokens; p7Roles?: Role[]; is_new_user?: boolean } & AuthSessionRbacPayload`
- `getMe()` → `User & AuthSessionRbacPayload & { tenantRoles?: Role[] }`

All RBAC fields optional on all three — mock mode is unaffected for any
account that doesn't hit the code paths touched (registration, OTP
"unknown phone" branch, etc. are unchanged), and no backend availability
is required for any of this to type-check or run.

## Phase D — `AuthBootstrapper` Update

**Before** (`src/providers/index.tsx`):
```
getMe() -> setUser()
```

**After:**
```
getMe() -> setUser() -> setTenantRoles() [only if tenantRoles present and non-empty]
                      -> (ownership/staffAssignments: received, not hydrated — see below)
```

```ts
authService.getMe().then((user) => {
  setUser(user)
  setSentryUser({ id: user.id, email: user.email, role: user.role })
  if (user.tenantRoles && user.tenantRoles.length > 0) {
    const tenantId = useTenantStore.getState().tenant.id
    useRbacStore.getState().setTenantRoles(tenantId, user.tenantRoles)
  }
  userService.getFavorites().then(setFavorites).catch(() => {})
}).catch(() => setLoading(false))
```

This calls **the store's pre-existing `setTenantRoles()` action** —
identical to the pattern already used in `useLogin()`/`useVerifyOTP()`
(`src/hooks/index.ts`). No new RBAC logic was written; this is purely a
hydration call, matching the task's explicit instruction: "Do not create
duplicate RBAC logic here. This only hydrates stores."

### Why `ownership`/`staffAssignments` are received but not hydrated

If a backend response ever includes `ownership`/`staffAssignments`,
`AuthBootstrapper` reads them off the same `user` object (they're part
of the widened `getMe()` return type) but takes no action with them.
This is deliberate, not an oversight: Ownership Resolution and
`StaffAssignment` are still **synchronous, mock-service-backed reads**
(`ownerService`, `staffAssignmentService`) — there is no client store
these facts could be written into without either (a) converting those
services to async/store-backed, which the task explicitly forbids this
phase, or (b) inventing a new piece of client state to hold them, which
would be exactly the "new client authority" the task's Phase G
explicitly prohibits. The fields exist on the type contract for forward
compatibility only, and are proven not to crash anything when present
(see Phase E test "missing RBAC payload").

### Known, pre-existing limitation (not introduced by this phase)

`AuthBootstrapper` and `TenantBootstrapper` mount and run their bootstrap
effects concurrently (`src/providers/index.tsx`'s `Providers` tree nests
`AuthBootstrapper` inside `TenantBootstrapper`, but both `useEffect`s
fire independently on mount). `useTenantStore.getState().tenant.id` is
read at the moment `getMe()` resolves, which could theoretically be
before `TenantBootstrapper`'s async `loadTenant()` finishes, causing
`setTenantRoles()` to seed the *default* tenant's id rather than the
URL-resolved tenant's id in a narrow race window. This exact same
pattern already exists, unchanged, in `useLogin()`/`useVerifyOTP()`
(`src/hooks/index.ts:497,528` read the same `useTenantStore.getState().tenant.id`
at mutation-success time) — this phase does not introduce a new risk,
it reuses the codebase's established convention. Not fixed here; flagged
for whoever eventually addresses `docs/P10.6_RBAC_REAL_BACKEND_MIGRATION_PLAN.md`
§8 step 5 (converting these reads to React Query, which would naturally
resolve bootstrap ordering).

## Migration Impact

- **Mock mode:** `getMe()` now returns each demo account's tenant roles;
  every existing demo login continues to work identically (proven by
  Phase E's 7-account round-trip test), and a page reload during a mock
  session now restores `tenantRoles` via `AuthBootstrapper` in addition
  to (not instead of) the still-unchanged `localStorage` persistence.
- **Real mode:** `login()`/`verifyOTP()`/`getMe()` can now optionally
  receive `p7Roles`/`tenantRoles` (and, for forward compatibility,
  `ownership`/`staffAssignments`) from a real backend without any
  further frontend change — the type contracts and the hydration call
  already exist. A backend that sends nothing behaves exactly as it did
  before this phase (all fields optional, verified by the "missing RBAC
  payload" tests).
- **No behavior change for any currently-passing test or currently-
  working UI flow.** Confirmed by the validation results below.

## Before / After Flow Summary

```
BEFORE (P10.6 baseline):
  Login          -> setTenantRoles()        [only write path during a session]
  Page reload    -> getMe() -> setUser()    [tenantRoles NOT restored here]
  (tenantRoles survives reload ONLY because useRbacStore's own
   localStorage persistence still holds the last-written value)

AFTER (this phase):
  Login          -> setTenantRoles()        [unchanged]
  Page reload    -> getMe() -> setUser() -> setTenantRoles() [if present]
  (tenantRoles now restored from an explicit hydration call — the
   localStorage persistence dependency is no longer the ONLY thing
   keeping it alive, though it remains in place, per Phase F, until
   the remaining §8 preconditions in docs/P10.6_RBAC_REAL_BACKEND_MIGRATION_PLAN.md
   are also met)
```
