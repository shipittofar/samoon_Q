# P10.4.1 — Legacy RBAC Discovery & Dependency Audit

Discovery only. No code was modified, refactored, or removed while
producing this document. Every claim below was verified directly against
current source via `grep`/`Read`, not inferred from prior reports or
comments.

## How to read this document

For every symbol: **File**, **Function/consumer**, **Purpose**,
**Classification** (Required / Temporary compatibility / Dead code /
Deprecated), and **Migration disposition** (Can be removed / Must be
migrated / Keep as-is).

Two coexisting permission systems exist in this codebase:

- **Legacy (P1B.1)** — colon-notation (`'orders:read'`), `UserRole`
  (`'customer' | 'staff' | 'owner' | 'admin'`), `rbacService`,
  `useRbacStore.tenantRoles`.
- **P7 (current)** — dot-notation (`'orders.view'`), `Role`
  (`'owner' | 'admin' | 'manager' | ...`), `permission.service.ts`,
  `usePermissions()`, and since P10.3, the ownership-resolution engine
  layered on top.

Some symbols named in this audit's brief (`branchRoles`, `roleAssignments`,
`customRoles`) turn out to belong to neither system in active use — they
are a **third, fully-built but entirely unconsumed** RBAC subsystem
inside `useRbacStore`. See §4.

## §1 — `ROLE_PERMISSION_MAP` (P7 role → permission array)

**File:** `src/services/permission.service.ts:97`
**Definition:**
```ts
export const ROLE_PERMISSION_MAP: Readonly<Record<Role, readonly P7Permission[]>>
```
**Purpose:** The canonical, current-generation role→permission table for
the P7 system. Read by `getPermissionsForRole()`, `hasPermission()`, and
(directly) by `ownership-resolution.service.ts`'s
`resolveStaffAssignmentPermissions()` to derive a StaffAssignment's
granted permissions from its `role` field.
**Consumers:**
| File | Use |
|---|---|
| `src/services/permission.service.ts` | definition, `getPermissionsForRole()`, and the `ROLE_METADATA` display array (owner/admin/manager/cashier/waiter/kitchen/marketing/support entries) |
| `src/services/ownership-resolution.service.ts:219` | `resolveStaffAssignmentPermissions()` looks up `ROLE_PERMISSION_MAP[assignment.role]` |
| `src/app/console/permissions/[userId]/page.tsx` | imported for the permission-simulator UI |
| `src/app/console/permissions/page.tsx` | imported for the RBAC admin roles table |

**Classification:** **Required.** This is the current, active permission
table — not legacy in the "colon-notation" sense, but it is the *P7*
system that P10.4 presumably targets for further ownership-model
integration. Not dead, not deprecated.
**Disposition:** Keep as-is / evolve in place.

## §2 — `tenantRoles` (legacy per-tenant role assignment store)

**File:** `src/stores/index.ts` — `useRbacStore.tenantRoles: TenantRoleAssignment[]`
**Purpose:** Persisted array of `{ tenantId, roles: Role[] }`, one entry
per tenant the current browser session has assumed a role in. Written by
`setTenantRoles()`/`addRole()`/`removeRole()`, read by
`getRolesForTenant()`.

**Write sites:**
| File | Function | Trigger |
|---|---|---|
| `src/hooks/index.ts:474` | `useLogin()` onSuccess | seeds `tenantRoles` from `MOCK_CREDENTIALS[email].p7Roles` after email/password login |
| `src/hooks/index.ts:505` | `useVerifyOTP()` onSuccess | same seeding after OTP login |
| `src/components/admin/AdminTenantSwitcher.tsx:84` | `switchTenant()` | re-seeds roles for the newly selected tenant (from `getMockRoles()` or carried-forward `originRoles`) |

**Read sites:**
| File | Function | Use |
|---|---|---|
| `src/hooks/index.ts:217` (`usePermissions()`) | `tenantRoles.find((t) => t.tenantId === tenantId)?.roles ?? []` → `getPermissionsForRole()` → unioned with ownership-driven permissions (P10.2.2/P10.3) |
| `src/components/admin/AdminSidebar.tsx:148-151` | `RoleChip()` | cosmetic role badge in the sidebar, read via `getRolesForTenant()` |
| `src/app/console/page.tsx:19-24` | `/console` index redirect | computes `getPermissionsForRole(getRolesForTenant(tenantId))` to decide which sub-route to redirect to — **entirely independent of `usePermissions()`/the ownership engine**; see §5 finding F-1 |
| `src/app/console/permissions/page.tsx:29,91` | RBAC admin page | reads raw `tenantRoles` to display/simulate session roles (this page's whole purpose is to inspect/manage the legacy table, so this is expected) |

**Classification:** **Required (with a bypass gap).** This is the live
source of "legacy-derived" permissions unioned into `usePermissions()` —
still load-bearing for every demo account whose email has no matching
`StaffMember` fixture (P10.0 id-space gap, documented since P10.2.2).
Not deprecated, not dead. But it is read *directly*, bypassing the
ownership engine, in two places (`AdminSidebar` role chip,
`/console` index redirect) — flagged in §5.
**Disposition:** Must be migrated (the two direct-read call sites should
route through `usePermissions()`/the ownership engine instead of reading
`tenantRoles` directly) or explicitly documented as an accepted
exception if P10.4 keeps the union model.

## §3 — `getRolesForTenant()`

**File:** `src/stores/index.ts:452,529` (definition) — `(tenantId: string) => Role[]`
**Consumers:** `AdminSidebar.tsx:148`, `AdminTenantSwitcher.tsx:64`,
`app/console/page.tsx:19,24,72` (see table in §2).
**Classification:** **Required**, but every consumer reads the legacy
table directly rather than through `usePermissions()`. None of these
three call sites is itself a security decision (`RoleChip` is cosmetic;
`AdminTenantSwitcher`'s `originRoles` capture is documented
pre-P10 platform-admin behavior, P10.3.2 F-`AdminTenantSwitcher` note;
`console/page.tsx` is a redirect-destination choice, not an access
grant) — but see F-1 in §5 for why the redirect logic can silently
misroute ownership-only identities.
**Disposition:** Must be migrated if/when P10.4 wants `/console`'s
landing redirect and the sidebar role badge to reflect ownership-derived
roles too, not just legacy `tenantRoles`.

## §4 — `branchRoles`, `roleAssignments`, `customRoles`: a fully-built, entirely unconsumed subsystem

**File:** `src/stores/index.ts` (all three defined here; lines 461-627)

| Field | Type | Setter/getter actions defined |
|---|---|---|
| `branchRoles` | `BranchRoleAssignment[]` | `setBranchRoles`, `getRolesForBranch`, `removeBranchRoles` |
| `roleAssignments` | `RoleAssignment[]` | `addRoleAssignment`, `removeRoleAssignment`, `updateRoleAssignment`, `getAssignmentsForUser`, `getAssignmentsForTenant` |
| `customRoles` | `CustomRoleTemplate[]` | `addCustomRole`, `updateCustomRole`, `removeCustomRole`, `getCustomRolesForTenant` |

**Verified consumer search** (`grep -rn` across `src/**/*.{ts,tsx}`,
excluding `stores/index.ts` itself): the ONLY other occurrence of any of
these three identifiers anywhere in the codebase is a single code
**comment** in `src/hooks/index.ts:535-536` (P10.3 Phase G's logout
cleanup note listing every field `_resetStore()` clears). No component,
page, hook, or service calls `setBranchRoles`, `getRolesForBranch`,
`removeBranchRoles`, `addRoleAssignment`, `removeRoleAssignment`,
`updateRoleAssignment`, `getAssignmentsForUser`, `getAssignmentsForTenant`,
`addCustomRole`, `updateCustomRole`, `removeCustomRole`, or
`getCustomRolesForTenant` anywhere.

**Classification:** **Dead code.** A complete, type-safe, persisted
sub-store for branch-level role overrides and custom role templates was
built (presumably for a P8-era "granular RBAC admin" feature — the
`console/roles/page.tsx` / `console/roles/new/page.tsx` pages exist and
use `PermissionGuard`, but do NOT call any of these three stores'
actions; they operate on `MOCK_RBAC_USERS`/`ROLE_PERMISSION_MAP`
directly instead) but never wired to any UI or business logic. It is
correctly included in `_resetStore()`'s logout cleanup (so it can't leak
across sessions even though nothing writes to it), which is the only
reason it's referenced outside its own file at all.
**Disposition:** Can be removed, OR must be migrated into the P10.4
model if branch-level role overrides / custom role templates are still
a planned feature — this audit cannot tell which from the code alone.
Flagging for a product decision, not a technical one.

## §5 — `legacyEffective` / `legacyGranted` / `LegacyPermission`

**Type definition:** `src/types/index.ts:750`
```ts
/**
 * Legacy permission strings (P1B.1 — colon-notation).
 * Used by the old rbacService and AuthGuard.
 * @deprecated Use P7Permission from @/types/rbac for new code.
 */
export type LegacyPermission = 'orders:read' | 'orders:write' | ... // 17 literals
```
Explicitly marked `@deprecated` in its own JSDoc.

**`legacyEffective`** — local variable name inside `usePermissions()`
(`src/hooks/index.ts:220`): the `tenantRoles`-derived permission array
(P7Permission[], NOT LegacyPermission — the naming is about "the legacy
*code path*," not the legacy *permission type*) before unioning with
ownership-driven permissions. Internal to the function, not exported.
**Classification:** Required (it's half of the currently-load-bearing
union in `usePermissions()`).

**`legacyGranted`** — local variable inside `useHasDashboardAccess()`
(`src/hooks/index.ts:370`): `rbacService.hasPermission(user?.role ?? null, 'dashboard:access')`,
a true `LegacyPermission` (colon-notation) check against `UserRole`
(customer/staff/owner/admin), OR'd with the P10.3.1-fixed
ownership-eligibility branches. Comment at `hooks/index.ts:355-363`
explains it is kept specifically because `staff@samoon.com` and
`multirole@samoon.com` have no matching `StaffMember` fixture (P10.0
id-space gap) and would lose console access if this branch were removed.
**Classification:** Temporary compatibility, explicitly documented as
such in-line. Cannot currently be removed without breaking two live demo
accounts.

**`LegacyPermission` consumers** (full search):
| File | Use |
|---|---|
| `src/services/rbac.service.ts` | `ROLE_PERMISSIONS` table (`CUSTOMER_/STAFF_/OWNER_/ADMIN_PERMISSIONS` constants), `rbacService.hasPermission()`, `rbacService.getPermissions()` |
| `src/components/auth/AuthGuard.tsx:63` | `requiredPermission` prop type; only live call site passes `'dashboard:access'` (see F-2 below) |
| `src/hooks/index.ts:166` | `useHasPermission(permission: LegacyPermission)` parameter type |
| `src/hooks/index.ts:370` | `legacyGranted` (above) |

**Disposition:** `LegacyPermission` itself: must be migrated eventually
(it's the type marked `@deprecated` in its own doc comment) but is still
structurally required by `rbacService`/`AuthGuard`/`useHasPermission()`
until those are migrated too — see F-2, F-3.

## §6 — `useHasPermission()`

**File:** `src/hooks/index.ts:166`
```ts
export function useHasPermission(permission: LegacyPermission): boolean {
  const role = useAuthStore((s) => s.user?.role ?? null)
  return rbacService.hasPermission(role, permission)
}
```
**Verified consumer search:** zero `.tsx` call sites anywhere in
`src/app/**` or `src/components/**`. The only references are its own
export line and two test files (`phase1b.test.ts`,
`phase4-ops-advanced.test.ts`) that assert the hook exists and is a
function — contract tests, not usage.
**Classification:** **Dead code.** Confirmed identically by the P10.3.1
audit (this finding is being re-confirmed here, not newly discovered).
It entirely bypasses the P7/ownership engine (`rbacService.hasPermission`
only, no `usePermissions()` call).
**Disposition:** Can be removed. If a future component starts using it,
it would silently reintroduce an ownership-engine bypass — flagged
previously in `docs/P10.3_IMPLEMENTATION.md`'s residual-risk section.

## §10 — Standalone `hasAnyPermission()` / `hasAllPermissions()` functions (permission.service.ts)

**File:** `src/services/permission.service.ts:383,396` — plain functions,
**not** the React hooks in §9 (different symbols, same names as the

**Verified consumer search:** imported into `hooks/index.ts:58`
alongside `hasPermission`/`getPermissionsForRole`/`applyOverrides`/

file (confirmed both by direct `grep` for a second occurrence of each

and `'hasAllPermissions' is defined but never used` at that exact import

**Classification:** Dead code (the import is dead; the functions

**Disposition:** Can be removed from the `hooks/index.ts` import list.
The underlying functions in `permission.service.ts` may still be
intentional public API surface for future direct callers — no
disposition claimed for those without a product decision.

## §11 — Duplicate/divergent type definitions found during this audit

Not explicitly named in the brief's symbol list, but discovered while
tracing `Role`/`Permission` dependencies — documented since they are
direct legacy-vs-P7 duplication artifacts relevant to the P10.4 migration
map.

**`Role` is defined twice**, structurally identical, in two different
files:
- `src/types/rbac.ts:9` (canonical, re-exported nowhere from `types/index.ts`)
- `src/types/index.ts:803` — an independent, literal-for-literal
  duplicate (`'owner' | 'admin' | 'manager' | 'cashier' | 'waiter' |
  'kitchen' | 'marketing' | 'support'`), NOT a re-export (contrast with
  `P7Permission`, which IS re-exported from `./rbac` at
  `types/index.ts:814-820`).
**Classification:** Both are structurally compatible (TypeScript
structural typing means this doesn't currently cause a type error
anywhere), but it is a genuine duplicate-source-of-truth: a future edit
to one `Role` union (e.g. adding a new P7 role) could silently diverge
from the other. **Disposition:** Should be migrated to a single
definition (re-export, matching the `P7Permission` pattern) — not a
functional bug today, but a maintainability risk.

**`Permission` (dot-notation, `src/types/index.ts:768-793`) is a
distinct, smaller type from `P7Permission`** (`src/types/rbac.ts:27`) —
overlapping but non-identical literal sets (e.g. `P7Permission` has
`orders.create`/`orders.edit`/`orders.delete`; `Permission` does not).
**Verified consumer search:** zero uses of `Permission` as a type
annotation anywhere in the codebase (`grep` for `: Permission\b`,
`<Permission>`, `Permission[]` outside its own definition/doc-comments
returns no matches).
**Classification:** Dead code — an unused, superseded type.
**Disposition:** Can be removed.

## §12 — Broken/unreachable legacy-hybrid string: `usePermission('dashboard:access')`

Discovered while tracing `usePermission()` consumers (§9). Documented
here as a dependency-audit finding, not fixed (out of scope for a
discovery-only phase).

`'dashboard:access'` is a literal member of **both** `LegacyPermission`
(`types/index.ts:762`, colon-notation) **and** `P7Permission`
(`types/rbac.ts:98`, otherwise dot-notation) — a deliberate string
collision so the same literal can be passed to either system.
`src/app/dashboard/layout.tsx:48` and `src/components/layout/Header.tsx:53`
both call `usePermission('dashboard:access')` (the **P7** hook, §9) to
compute `canAccessConsole`. But `'dashboard:access'` is never added to
`ROLE_PERMISSION_MAP` (verified: no occurrence of the string in
`permission.service.ts`) nor to `ALL_PERMISSIONS`, so
`usePermissions()`'s returned array can never contain it —
`usePermission('dashboard:access')` is **structurally always `false`**
in these two call sites, for every role including Owner. This is
distinct from `useHasDashboardAccess()` (`hooks/index.ts:364`, the
correct, P10.3.1-fixed mechanism `AuthGuard` uses) — these two
`Header.tsx`/`dashboard/layout.tsx` call sites use the wrong hook
entirely.
**Classification:** Not legacy-vs-P7 migration debt — a pre-existing,
independently-broken call site using the right *hook family* with the
wrong *permission string* for what it needs. Included here because it
was directly discovered via this audit's `usePermission()` consumer
trace and belongs in the P10.4 migration map regardless of its root
cause.
**Disposition:** Must be migrated — likely to call
`useHasDashboardAccess()` instead of `usePermission('dashboard:access')`.
