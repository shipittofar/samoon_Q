# P9.5.1B — Application Localization Audit

> Phase A of P9.5.1B. Quantifies exactly what P9.5.1A's runtime engine
> found waiting for it: near-zero actual consumption. Numbers below are
> grep-based counts taken directly against the repository, not estimates.
>
> Last updated: 2026-07-05

---

## 1. Starting state (before this phase)

```
useTranslations()/next-intl usage in src/app or src/components:  1 file
toast.success()/toast.error() call sites:                        54
z.object()/z.string() validation schemas:                          9 files
hardcoded aria-label="...":                                      187
hardcoded placeholder="...":                                     107
```

Despite P9.0–P9.5.1A building a complete Configuration/Localization
Runtime Engine, the application itself never called into it — every
user-facing string in the 116-page, 95-component app was still a literal.
This is the gap P9.5.1B closes, as far as its scope allows in one pass
(see §4, "What remains").

## 3. A real bug found during the audit (not part of P9.5.1A's scope)

`src/app/layout.tsx` — the root layout — computed RTL direction via
`const isRTL = ['fa', 'ar'].includes(locale)`, a **5th hardcoded-locale
site** that P9.5.0's original audit (`P9.5.0_LOCALIZATION_AUDIT.md`) and
P9.5.1A's Phase A/C migration missed entirely, because it lives in
`layout.tsx`, not in `stores/index.ts` or `providers/index.tsx` where the
other RTL checks were. Fixed in this phase: `layout.tsx` now calls
`getDirection(locale)` from the Localization Runtime Service, the same as
every other RTL call site. This means **zh/it/tr now render `dir="ltr"`
correctly at the `<html>` tag level** for the first time — previously they
would have inherited whatever `['fa','ar'].includes()` evaluated to (`ltr`,
by luck, but for the wrong reason — a hardcoded list that happened to not
include them, not a real language-direction lookup).

## 4. What remains (honest accounting, not deferred silently)

- **~110 pages/components** with hardcoded English JSX text not yet
  migrated — customer-facing flows (menu, cart, checkout, reservation,
  dashboard) and all of Business Console/Platform Administration/
  Configuration Studio/Countries Management/Authentication Center (Phase F's
  named targets) are **not migrated in this pass**. Those UIs remain fully
  functional in English only; nothing broke, nothing was removed — they
  simply don't yet call `useTranslations()`.
- **3 validation schemas** (`complete-profile`, `checkout`, `reservation`
  pages) still use literal English zod messages — not converted to
  `validation` namespace keys this phase. `src/lib/i18n-validation.ts`
  (the centralized key list) is ready for them.
- **34 toast call sites** outside the auth flow (cart, menu, checkout,
  reservation, Configuration Studio) still pass literal strings.
- **185 `aria-label`** and **102 `placeholder`** attributes outside the
  migrated auth pages remain hardcoded.
- **Metadata** (`generateMetadata`/OpenGraph/Twitter/manifest) — no page's
  metadata was made locale-aware this phase; `src/i18n/seo.ts`'s hreflang
  helpers are built and tested but not wired into any route, per the
  phase's own "no routing changes" constraint (hreflang requires a
  distinct URL per language, which doesn't exist yet).
- **Namespace scaffolding** (`console`, `platform`, `countries`,
  `languages`, `marketing`, `analytics`, `system`) exists in `en.json` as
  single-key placeholders (`{"title": "..."}`) — real content for these
  namespaces is written as each of those UI surfaces is actually migrated,
  not invented ahead of need.
- **Marketing copy** (register page's `PERKS` array, login page's demo
  account labels/descriptions, hero taglines) intentionally left as literal
  English — copywriting content, not a translation-infrastructure gap, and
  lower priority than functional UI strings for this pass.

This list is the direct input to P9.5.2's scope, not a gap to paper over.

## 5. What this phase did instead of attempting the above exhaustively

Rather than making shallow, mechanical edits across 100+ files (high risk
of breaking build/tests for low individual value, and impossible to
verify manually within this phase), P9.5.1B focused on:

1. **One fully-migrated reference vertical** (the entire authentication
   flow: login, register, forgot-password, verify-otp, plus the shared
   Header/TenantHeader logout toast) — proving the pattern end-to-end,
   including the centralized validation-message approach (§Phase E).
2. **Namespace reorganization** or genuine ones added — `validation`,
   `console`, `platform`, `countries`, `languages`, `marketing`,
   `analytics`, `system` — so the next migration pass has a home for its
   keys instead of inventing namespace conventions ad hoc.
3. **The Translation Coverage utility** (`src/i18n/coverage.ts` +
   `scripts/check-translation-coverage.mjs`) — a real, working detection
   tool for missing/unused/orphan translation usage, so future migration
   passes (and CI) can verify their own completeness instead of guessing.
4. **Fixing the layout.tsx RTL bug** (§3) — a real correctness fix found
   during the audit, not left for later.
5. **SEO/hreflang infrastructure** (`src/i18n/seo.ts`) — ready for whichever
   URL strategy is chosen, without pre-committing to one.

See `docs/P9.5.1B_APPLICATION_LOCALIZATION.md` for the full migration
report and `docs/P9.5.1_RUNTIME_ENGINE.md` §7 (updated) for how this phase
changes the P9.5.1B/P9.5.2 roadmap.
