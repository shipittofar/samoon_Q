# P9.5.0 — Localization Performance Strategy

> Documentation only. The audit (`P9.5.0_LOCALIZATION_AUDIT.md` §4) found
> that the platform's *current* loading mechanism — `next-intl`'s
> `getRequestConfig()` dynamically importing exactly one locale's JSON file
> per request — is already the correct shape at 3 languages. This document
> specifies what has to stay true, and what has to generalize, to keep it
> correct at 150+.
>
> Last updated: 2026-07-05

---

## 1. The one invariant: never load all languages

At 3 languages, loading all of them (~187 lines total, per the audit's
`en.json` line count) is harmless. At 150+, it is not — even at a modest
~200 lines/locale, the full set would be 30,000+ lines of JSON shipped
somewhere. **The architecture's one non-negotiable performance rule:
exactly one language's translation data is ever loaded for a given
request/session — never the full 150+-language set, at any layer
(server render, client hydration, or an admin editing screen).**

## 2. Server-side: request-scoped dynamic import (already correct, extend the source)

`src/i18n/request.ts` already does the right thing —
`await import(`./locales/${locale}.json`)` is a per-request dynamic
import, which Next.js code-splits automatically (each locale file becomes
its own chunk, only the requested one is ever fetched/evaluated). The only
generalization needed: **the `supported = ['en', 'fa', 'ar']` array
becomes a read from `localization.languages` where `enabled: true`**,
not a hardcoded list — the loading *mechanism* doesn't change, only where
the list of valid values to look up comes from. This is a 1-line
conceptual change (swap a literal array for a registry query) precisely
because the mechanism was already sound.

## 3. Translation Keys at 150+ languages: still one file per language

Per `P9.5.0_TRANSLATION_ARCHITECTURE.md` §8, the export format is one JSON
file per `(language)` (optionally split further per namespace for large
namespaces) — never one file containing all languages. This is what makes
"load only the current language" possible at the storage layer, not just
the request layer: there is no "all languages" artifact to accidentally
import in the first place.

## 4. Namespace-level code splitting

Beyond per-language splitting, namespaces (`checkout`, `dashboard`, …)
should be independently dynamically importable, so a customer-facing page
never pulls in `dashboard`'s translations and an admin page never pulls in
`checkout`'s. `next-intl` supports partial/namespaced message loading;
today's 12-namespace, single-file-per-locale setup doesn't yet split this
way (all 12 namespaces load together) — this is called out as a
concrete P9.5.1+ implementation task (`P9.5.0_DEVELOPER_GUIDE.md`'s
roadmap), not solved by this document, since it requires touching
`src/i18n/request.ts`.

## 5. CDN caching

Exported per-language(/per-namespace) JSON files are immutable-content-hash
addressable artifacts (the same pattern static asset pipelines already use)
— `checkout.en.a1b2c3.json`. A new Translation Version (§5 of the
Translation Architecture doc) produces a new hash, so CDN edge caches never
need invalidation, only a new URL — the standard "cache forever, bust via
filename" strategy, requiring no new CDN configuration or purge logic
beyond what already exists for any other hashed static asset in this
build.

## 6. Browser caching

The `NEXT_LOCALE` cookie (already set by `useLangStore.setLocale`,
`src/stores/index.ts`) continues to be the client-side signal for which
locale's chunk to request on next navigation — unchanged. The dynamically
imported locale module, once loaded, stays in the browser's module cache
for the session's lifetime (standard ES module/webpack chunk caching,
nothing localization-specific to add).

## 7. Server caching

`getRequestConfig()`'s resolved `{ locale, messages }` result is
per-request today; a real backend-backed Translation Key store (vs. a
static JSON import) should cache the resolved message bundle per
`(locale, translationVersion)` pair at the server/edge layer — invalidated
only when a new Translation Version is published (§5 of the Translation
Architecture doc), not on every request. This is a standard cache-key
design (version-scoped, not time-scoped) and needs no new infrastructure
beyond whatever HTTP/edge cache the platform's real backend eventually
uses for any other versioned resource.

## 8. Bundle-size budget

A soft budget: **no single language's compiled message bundle should
exceed a size that meaningfully affects Time-to-Interactive on a
mid-tier mobile device** — concretely, tracked the same way any other
performance budget in this codebase would be (a CI check comparing
bundle size against a threshold, per `P9.5.0_DEVELOPER_GUIDE.md` §4), not
a hardcoded number in this architecture document, since the right number
depends on measurement, not upfront design.

## 9. RTL and font loading

- **RTL** requires zero extra network payload — it's a CSS
  direction/logical-property concern (see §7 of
  `P9.5.0_LOCALIZATION_ARCHITECTURE.md`'s sibling design intent — logical
  properties like `margin-inline-start` instead of `margin-left` mean the
  *same* compiled CSS serves both directions, so switching direction never
  requires loading a second stylesheet).
- **Fonts** (`localization.fonts`, architecture doc §2.4) load exactly
  like RTL — only the active language's assigned `font_family` is
  requested, using the browser's native `font-display: swap` (or
  equivalent) so text renders immediately in a fallback font rather than
  blocking on the webfont — a rendering-layer decision, not a
  localization-architecture one, but stated here because it's the same
  "never load what isn't needed" principle applied to a second asset type.

## 10. What this document does not solve

Actual measurement (real bundle sizes, real TTI impact) is inherently an
implementation-phase activity — this document fixes the *strategy*
(one-language-at-a-time, version-hashed CDN caching, namespace splitting)
so that when P9.5.1+ implements it, there is no performance-architecture
decision left to make, only execution.
