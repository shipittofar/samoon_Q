# P10.4.10 — Remove Legacy Dashboard Access Fallback (`legacyGranted`)

Removes the final runtime dependency on the legacy RBAC permission path
inside dashboard access resolution. `rbacService.hasPermission()` is no
longer called by `useHasDashboardAccess()` — the hook now decides
`/console` access purely through ownership/`StaffAssignment` resolution.

## Removed

**`legacyGranted`** (`src/hooks/index.ts`, inside `useHasDashboardAccess()`):

```ts
const legacyGranted = rbacService.hasPermission(user?.role ?? null, 'dashboard:access')
```

and its use as the first OR-branch of the hook's return expression
(`if (legacyGranted) return true`, and its presence in the `useMemo`
dependency array). The now-unused `import { rbacService } from
'@/services/rbac.service'` at the top of the file was also removed —
required so the removal doesn't introduce a new "unused import" ESLint
warning, not an unrelated cleanup.

**Legacy dashboard permission fallback**: this was the mechanism that
let a user reach `/console` purely because their legacy `UserRole`
(`'staff'`/`'admin'`/`'owner'`) mapped to `'dashboard:access'` in
`rbac.service.ts`'s `ROLE_PERMISSIONS` table, independent of whether
they had a real `StaffMember`/`StaffAssignment`/`Owner` record. It no
longer exists as an executable code path in this hook.

## Before

```ts
export function useHasDashboardAccess(): boolean {
  const user = useAuthStore((s) => s.user)
  const tenant = useTenantStore((s) => s.tenant)
  const legacyGranted = rbacService.hasPermission(user?.role ?? null, 'dashboard:access')
  return useMemo(() => {
    if (legacyGranted) return true
    if (!tenant?.id || !isTenantEligible(tenant)) return false
    const identity = resolveOwnershipIdentity(user?.email)
    if (identity.owner && isOwnerEligible(identity.owner) && ownerOwnsTenant(...)) return true
    if (identity.staffMember && isStaffMemberEligible(identity.staffMember)) {
      return staffAssignmentService.getEffectiveAssignments(identity.staffMember.id).length > 0
    }
    return false
  }, [legacyGranted, user?.email, tenant?.id, tenant?.ownerId, tenant?.status])
}
```

`legacyGranted` short-circuited the whole computation: if the user's
legacy `UserRole` mapped to `dashboard:access`, the ownership/
`StaffAssignment` checks below were never evaluated at all — this
existed because `staff@samoon.com`/`multirole@samoon.com` (and,
discovered during P10.4.9, `admin@samoon.com`/`kitchen@samoon.com`) had
no `StaffMember`/`StaffAssignment` fixture, so the two branches below it
always evaluated to `false` for them.

## After

```ts
export function useHasDashboardAccess(): boolean {
  const user = useAuthStore((s) => s.user)
  const tenant = useTenantStore((s) => s.tenant)
  return useMemo(() => {
    if (!tenant?.id || !isTenantEligible(tenant)) return false
    const identity = resolveOwnershipIdentity(user?.email)
    if (identity.owner && isOwnerEligible(identity.owner) && ownerOwnsTenant(...)) return true
    if (identity.staffMember && isStaffMemberEligible(identity.staffMember)) {
      return staffAssignmentService.getEffectiveAssignments(identity.staffMember.id).length > 0
    }
    return false
  }, [user?.email, tenant?.id, tenant?.ownerId, tenant?.status])
}
```

`ownershipAccess || staffAccess || legacyGranted` became
`ownershipAccess || staffAccess`. Every other line in the function body
— the tenant eligibility gate, `resolveOwnershipIdentity()`, the Owner
branch, the Staff branch, the P10.3.1 eligibility-predicate comment —
is untouched. This is a pure subtraction, not a rewrite: no new logic
was added, no existing conditional was restructured, no line outside
the `legacyGranted` declaration/branch/dependency-array-entry was
touched.

## Proof

### Fixture migration reference

This removal was only possible because
`docs/P10.4.9_RBAC_MIGRATION_PREPARATION.md` closed the P10.0 J12/J13
id-space gap first: `staff@samoon.com`, `multirole@samoon.com`,
`admin@samoon.com`, and `kitchen@samoon.com` all now have real
`StaffMember` records (`src/services/staff.service.ts`) with active
`StaffAssignment` rows (`src/services/staff-assignment.service.ts`), so
`identity.staffMember` and `staffAssignmentService.getEffectiveAssignments(...)`
resolve correctly for them without `legacyGranted`'s help. That phase's
own regression test (`src/test/p10.4.9-rbac-migration.test.ts`) already
proved this while `legacyGranted` was still present in the code (by
forcing the user's legacy role to `'customer'`); this phase's test
(below) proves the same thing now that the branch has actually been
deleted.

### Test results

`src/test/p10.4.10-remove-legacy-dashboard-fallback.test.ts` (16 tests,
all passing):

- **Owner access** (1 test): `owner@samoon.com` still grants access —
  confirmed to route through `resolveOwnerPermissions()`/
  `ownerOwnsTenant()`, not any legacy path (there is no legacy path left
  to route through).
- **Staff assignment access** (6 tests): `admin@samoon.com`,
  `staff@samoon.com`, `manager@samoon.com`, `cashier@samoon.com`,
  `kitchen@samoon.com`, `multirole@samoon.com` all pass, each verified to
  resolve through `StaffMember` + an effective `StaffAssignment` +
  `resolveOwnershipIdentity()`.
- **Legacy isolation proof** (7 tests): for every one of the 7
  console-capable accounts (Owner + the 6 Staff accounts above), each
  test first asserts `rbacService.hasPermission('customer',
  'dashboard:access')` is `false` (the precondition that would have
  made the old `legacyGranted` branch `false` for a `'customer'`-role
  user), then constructs the test user with `role: 'customer'` and
  confirms `useHasDashboardAccess()` still returns `true` — meaning
  access can only be coming from the ownership/`StaffAssignment` path,
  which is now the *only* path in the function.
- **Negative test** (2 tests): a genuinely unknown account
  (`unknown@samoon.com`, no `StaffMember`, no `Owner` record) still
  returns `false`, and would also have failed the old legacy check
  (`rbacService.hasPermission('customer', 'dashboard:access')` is
  `false`) — proving the removal didn't accidentally *widen* access to
  unknown identities either.
