# P9.1.3 — Authentication Control Center

> The first complete Platform Configuration Console module, and the
> reference implementation every future module (Countries, Themes,
> Payments, RBAC, Website Builder, Notifications, Storage, Monitoring, API,
> System, and beyond — see `docs/PLATFORM_ROADMAP.md`) is meant to reuse
> without writing new UI code. Builds on P9.0 (Configuration Registry),
> P9.0.1 (hardening), P9.1.1 (audit/schema design), P9.1.2 (runtime
> integration), and P9.1.2.1 (Console-readiness metadata).
>
> Last updated: 2026-07-04

## 1. Architecture

```
Route                          Component                              Data
──────────────────────────────────────────────────────────────────────────────
/console/settings/              ConfigurationIndexPage                usePlatformConfiguration()
  configuration                 (module index — lists every                → platformConfigurationRegistry
                                 registered module as a card)

/console/settings/               ConfigurationModulePage               useConfigurationDraft(moduleId)
  configuration/[moduleId]       (the reusable Control Center shell)        → useConfigurationModule()
                                     ├─ ConfigurationFieldRow (×N)           → configurationService
                                     │    ├─ ConfigurationFieldControl       → configurationValidator
                                     │    ├─ ConfigurationFieldBadges        → configurationAudit
                                     │    └─ ConfigurationFieldPreview
                                     └─ save bar
```

Every piece below `[moduleId]` is **generic** — nothing in
`src/components/admin/configuration/*` or `src/hooks/use-configuration-draft.ts`
references `authentication` by name. The Authentication Console is what you
get when `moduleId="authentication"`; a future Countries Console is what you
get when `moduleId="countries"`, with zero new component code. This is
verified directly: `/console/settings/configuration` already lists all 15
registered modules (screenshot-verified during this phase), and clicking
into any of them renders through the exact same
`ConfigurationModulePage` component Authentication uses.

### Files

| File | Role |
|---|---|
| `src/components/admin/configuration/configUiHelpers.ts` | Pure functions: control inference, dependency evaluation, search matching, state derivation. No React, fully unit-testable. |

| `src/app/console/settings/configuration/page.tsx` | Module index — reads the registry, not a hardcoded list. |

## 2. Rendering flow

1. `useConfigurationDraft('authentication')` resolves the module's sections
   and every field's current value via the existing P9.0
   `useConfigurationModule()` hook — no new resolution logic.
2. `ConfigurationModulePage` filters each section's fields by, in order:
   `configurationService.canView()` (permission), `governance.internalOnly`
   (platform-admin-only fields), `isFieldVisible()` (dependency
   `hiddenWhen`), and `matchesSearch()` (live search query) — then sorts by
   `display.displayOrder`. **No field ordering or grouping is hardcoded
   anywhere in this file** — Rule 2's "no hardcoded forms" is satisfied by
   construction, not by convention.
3. Each visible field renders as a `ConfigurationFieldRow`, whose control is
   picked by `resolveUiControl()` — `field.uiControl` if the module author
   set one, otherwise a `type`-based default (`docs/P9.1.2.1_CONFIGURATION_METADATA.md`
   §2's mapping table).

## 3. Dependency flow (Phase E)

The phase brief's own example — "OTP OFF → hide OTP Length, OTP Timeout,
OTP Attempts, Resend Delay" — surfaced a real design gap during
implementation: evaluating `hiddenWhen` against `values` (the *saved*
resolved state) means toggling a switch doesn't hide dependents until after
clicking Save, which fails the brief's expectation of immediate,
UI-reactive hide/show. The fix: `ConfigurationModulePage` computes
`effectiveValues` — `values` overlaid with any in-progress `drafts` — and
every dependency check reads `effectiveValues`, not `values`. This was
verified two ways: an automated test
(`src/test/p9-1-3-authentication-control-center.test.tsx`, "hides
OTP-dependent fields immediately … before saving") and a live
Playwright-driven smoke test against a running dev server.

The dependency chain actually registered in `authentication.ts`:
`authentication.enabled` (false) hides `otp.enabled`, `phone_login_enabled`,
`email_login_enabled`, `registration_enabled`; `authentication.otp.enabled`
(false) hides every OTP-section field beneath it. No page-specific `if`
statements exist for any of this — it is entirely metadata-driven per the
phase's own requirement.

## 4. Validation flow (Phase F)

`ConfigurationFieldRow` calls `configurationValidator.validate(field,
currentValue)` on every render (cheap, pure) and displays: the field's
`min`/`max` range, `validation.warningMessage` (soft, non-blocking), and
either `validation.errorMessage` (a friendlier override) or the validator's
generated message when the current draft value is invalid. Badges
(`ConfigurationFieldBadges`) surface every governance/lifecycle flag from
`docs/P9.1.2.1_CONFIGURATION_METADATA.md` — Dangerous, Experimental, Beta,
Deprecated, Internal Only, Restart Required, Publish Required, Requires
Approval, Security-Sensitive, Locked — with **zero per-field badge logic**;
the component only reads `field.governance`/`field.lifecycle`.

`useConfigurationDraft.save()` re-validates every dirty field before
writing anything (`validateDrafts()`) and refuses to save if any field's
`audit.requireReason` is set but no reason was supplied — matching the
existing `ConfigurationService.updateField()` contract (P9.0) rather than
inventing a parallel validation path.

## 5. Save experience (Phase J)

Writes always target each dirty field's own `inheritance.level`
(`field.inheritance.level`), not a hardcoded `'platform'` — every
Authentication field happens to be platform-owned today (P9.1.2), but this
makes the hook correct, unmodified, for a future module with tenant/branch-
owned fields. The save bar appears only when dirty (Shopify pattern, see
`docs/P9.1.3_AUTH_UI_RESEARCH.md`), shows a live unsaved-change count, a
reason input when any dirty field requires one, and Discard/Save actions.
"Optimistic UI" is a deliberate light-touch simulation: `ConfigurationService`
is synchronous (in-memory), so `save()` adds a 400ms delay purely to give a
realistic "Saving…" state in mock mode, matching the `MOCK_DELAY` convention
used everywhere else in the mock service layer — there is no real network
round trip to be optimistic about yet.

Per-field, per-section, and per-module reset are all one function each
(`resetField`/`resetSection`/`resetModule`) operating on the same `drafts`
map — no duplicated reset logic.

## 6. Configuration states (Phase H)

`deriveFieldState()` returns `default | modified | tenant_override |
branch_override | user_override`. A genuine subtlety discovered while
building this: `ConfigurationResolver` reports `resolvedFrom: 'platform'`
identically whether a field was never touched (still its literal default)
or was explicitly overridden at platform level to a different value — there
is no separate signal for "touched at the owning level." So "Modified" is
derived by comparing the resolved value to `field.default` directly, not by
reading `resolvedFrom` alone; `resolvedFrom` is only decisive for
descendant levels (tenant/branch/user), where its presence unambiguously
means an override exists there. This is documented in
`configUiHelpers.ts`'s `deriveFieldState()` docstring so a future module
author doesn't rediscover it the hard way.

**Known limitation, stated plainly**: because every Authentication field is
platform-owned (P9.1.2), the Tenant/Branch/User Override states have no
live example within this module today — the generic logic supports them
(and is exercised by other modules' tenant-owned fields, e.g.
`themes.accent_hover_color`), but Authentication itself only demonstrates
Default/Modified in practice, plus the lifecycle states (`published` is the
only one any current field uses) and the lock badge (`inheritance.mode ===
'locked'`).

## 7. Preview (Phase I)

`ConfigurationFieldPreview` renders `field.preview.kind` — none of
Authentication's 17 fields set anything other than the default (`'none'`),
so no preview renders on this page today, exactly matching the brief's own
words ("Authentication fields without preview simply render normally").
The component itself supports all four kinds (swatch/font-sample/json/image)
and is already exercised by other modules (`themes.primary_color`'s swatch,
`typography.body_font`'s font-sample) without any Authentication-specific
code — proving the reusability claim rather than asserting it.

## 8. Search (Phase G)

`matchesSearch()` matches a query against `displayName`, `title`,
`description`, `helpText`, `category`, `subcategory`, `group`, `tags`,
`search.keywords`, and `search.aliases` — joined and lowercased. Verified
searching "brute force" (a keyword on `authentication.max_login_attempts`,
not present in its title) correctly surfaces that field while excluding
unrelated ones, both in the automated test suite and the live smoke test.

## 9. Permissions (Phase L)

Three independent gates, composed, not layered ad hoc: `configurationService.canView()`
(hides the field entirely), `field.governance.internalOnly` combined with
`usePermission('tenant.manage')` as the Platform Administrator proxy (no
new permission string invented — reuses the existing RBAC catalog per
`docs/PLATFORM_ARCHITECTURE_PRINCIPLES.md` Rule 3), and
`configurationService.canEdit()` (renders the control but disabled, with an
inline explanation, rather than hiding it — distinguishing "you can't see
this" from "you can see but not change this"). `field.lifecycle ===
'archived'` additionally forces read-only regardless of permission, per
P9.0.1's lifecycle model.

## 10. Responsive design (Phase M)

Tailwind responsive utilities throughout (`sm:` breakpoints on the header,
field grid, and save bar layout); collapsible sections via a `Set<string>`
of collapsed section ids (no external accordion dependency); the save bar
is `fixed inset-x-0 bottom-0`, always reachable regardless of scroll
position or viewport size. Existing project-wide conventions (CSS variable
theme tokens, `reduced-motion`-aware patterns already established elsewhere
in the codebase) were reused rather than reintroduced. Full keyboard/
screen-reader semantics: every control has an accessible name (`aria-label`
or associated `<label htmlFor>`), the switch/checkbox controls use
`role="switch"`/`role="checkbox"` with `aria-checked`, and section headers
use `aria-expanded`.

## 11. Mock data (Phase N)

`seedAuthenticationMockOverrides()` (`src/config/mock-data.ts`) is a real
function — it calls `configurationService.updateField()`, not a static
data table — so the Console shows genuine "Modified" state and real audit
history on first load: `otp.resend_cooldown_seconds` (60→45),
`max_login_attempts` (5→7), and `guest_checkout_enabled` (true→false, with
a fraud-investigation reason). It deliberately does **not** run as a side
effect of importing `@/config` (that import is shared with the test suite,
which asserts default values — see `docs/P9.1.2_RUNTIME_INTEGRATION.md`'s
own note on this exact hazard). Instead it's called during
`ConfigurationModulePage`'s render body, gated to
`moduleId === 'authentication' && NEXT_PUBLIC_USE_MOCK`, and is idempotent
(a module-level guard) so re-renders/re-navigations never double-apply it.

## 12. Navigation (Phase B)

A new "Platform Configuration" nav item (`src/modules/registry.ts`) was
added to all six business-type modules' `adminNavItems`, alongside the
existing `SETTINGS_NAV_ITEM`, following the exact precedent already set by
`TENANTS_NAV_ITEM`/`AUDIT_LOGS_NAV_ITEM` — a shared constant spread into
every module rather than duplicated. This bumped every module's
`adminNavItems`/`getAdminNav()` length by one (or three, for the one test
aggregating three modules together) — a real, expected cascading effect
across **12 pre-existing test files** (64 individual count assertions),
all updated in this same change. This is the established pattern in this
codebase's own history for adding a platform-wide shared nav item; it is
not a regression, but it is a large, mechanical diff worth calling out
explicitly for anyone reviewing this change.

## 13. Test infrastructure change

Rendering an actual React component tree for the first time in this
project's Vitest suite surfaced that `vitest.config.ts` had no JSX
transform configured — every existing `.tsx` source file already omits
`import React` (relying on Next.js's SWC automatic-runtime compilation),
but Vitest's default esbuild config uses the classic transform, which
requires `React` in scope. Fixed by setting `esbuild: { jsx: 'automatic' }`
in `vitest.config.ts` — no new dependency, and it makes Vitest match how
Next.js already compiles every component in this codebase, rather than
requiring every future component test to add a redundant React import.

## 14. Lessons learned

- **Dependency evaluation must read live state, not saved state** — the
  single most important correctness fix in this phase (§3). A generic
  rendering engine that only reacts to committed values will always feel
  laggy for exactly the interactions a Platform Administrator does most
  (toggle something, watch dependents react).
- **`resolvedFrom` alone cannot express "modified"** — a resolver built to
  answer "what level won" needs a second signal (comparison to `default`)
  to answer "did anything actually change," and that distinction has to
  live in the Console layer, not be assumed available from the P9.0
  resolver's existing return shape (§6).
- **Adding one shared nav item touches every module's nav count** — worth
  treating as a known, mechanical cost of Phase B in this codebase's
  specific test style (count-based assertions), not something to route
  around by skipping test updates.
- **Seed data that mutates global state needs an explicit, documented
  non-import-time trigger** — the instinct to "just seed it in `@/config`'s
  registration chain" would have silently broken unrelated tests; the
  right home for demo-state mutation is the one component that actually
  wants it, gated and idempotent.
