# P10.5.1 — Authorization Architecture Final Audit & Cleanup

Documentation and verification only. No runtime code was modified to
produce this report. This is the architectural baseline for P10.5
feature work, following the legacy RBAC engine's full retirement in
P10.4.12.

### Decision points, documented

1. **`PermissionGuard`** (`src/components/auth/PermissionGuard.tsx`) — declarative
   wrapper. Delegates entirely to `usePermission()`/`useAnyPermission()`/
   `useAllPermissions()` via three internal sub-components (to keep hook
   calls unconditional per-render). No logic of its own.
2. **`usePermission()`/`useAnyPermission()`/`useAllPermissions()`**
   (`src/hooks/index.ts:221,249,268`) — all three call `usePermissions()`
   for the base set, then apply an inline feature-flag gate
   (`FLAG_MAP` keyed by permission resource) and an optional capability
   gate (`opts.capabilities`). Memoized on `[permissions, permission,
   featureFlags]` (single) or `[effectivePermissions, permissions.join(','),
   featureFlags]` (any/all).
3. **`usePermissions()`** (`src/hooks/index.ts:175`) — the actual
   aggregation point, composing two independent sources (see "Permission
   Sources" below) via `[...new Set([...legacyEffective, ...ownershipDriven])]`.
   Also schedules a one-shot `setTimeout` at a `StaffAssignment`'s
   `validUntil` to force recomputation when a temporary grant expires
   (P10.3 Phase I) — the only non-trivial "cache invalidation" logic in
   the whole graph.
4. **`useHasDashboardAccess()`** (`src/hooks/index.ts:353`) — deliberately
   NOT part of the `usePermissions()`/`P7Permission` graph. `dashboard:access`
   is resolved as a hand-written boolean (Owner-owns-tenant OR
   Staff-has-effective-assignment), because `ROLE_PERMISSION_MAP` never
   grants the literal `'dashboard:access'` string to any role (see
   "dashboard:access Audit" below). This is the sole authorization
   function `AuthGuard` and `useDashboardNav()` read for console access.
5. **`branch-access.service.ts`** — the one non-hook, service-layer
   consumer of `hasPermission()` (the plain function, not the hook),
   used to compute branch-scoping (`getAccessibleBranches()`,
   `getScopeForContext()`). Same `ROLE_PERMISSION_MAP`, same function
   family — not a duplicate implementation.

### Why the Header/dashboard-layout bug exists (unchanged since P10.4.8)

`Header.tsx` and `app/dashboard/layout.tsx` were written to gate the
console-nav link with the generic P7 hook (`usePermission`), presumably
under the assumption that `dashboard:access` would resolve through
`ROLE_PERMISSION_MAP` like every other `P7Permission`. It never has —
`dashboard:access` was deliberately kept *outside* the role→permission
map because it isn't a resource-scoped CRUD permission like
`orders.view`; it's a structural "may this identity reach `/console` at
all" gate that depends on ownership/`StaffAssignment` existence, not a
role's permission list. `useHasDashboardAccess()` is the correct,
purpose-built implementation of that gate — `Header.tsx`/`dashboard/layout.tsx`
simply call the wrong hook.

### Best architecture (documented, not applied)

`dashboard:access` should **not** become a first-class entry in
`ROLE_PERMISSION_MAP`. Doing so would let a role like `admin` or
`manager` gain `/console` access purely by role membership, decoupled
from whether they hold a real, eligible `StaffAssignment`/Owner
record — reintroducing exactly the class of bug P10.3.1 fixed (a
suspended/removed Staff member reaching `/console`). The correct fix —
out of scope for this audit-only phase — is for `Header.tsx` and
`app/dashboard/layout.tsx` to call `useHasDashboardAccess()` (the
existing, already-correct hook) instead of `usePermission('dashboard:access')`.
This is a one-line hook swap in each file, already scoped and documented
as a discovered-but-unfixed finding in
`docs/P10.4.8_LEGACY_COMPATIBILITY_AUDIT.md` Phase G and
`docs/P10.4.11_AUTHGUARD_MODERNIZATION.md`. Repeating it here because
this phase's instructions explicitly ask for the architectural
recommendation, not because it's new.

### Naming inconsistency worth flagging

`usePermissions()`'s local variable is named `legacyEffective`
(`src/hooks/index.ts:207`). This name predates P10.4.12 and was accurate
when written (P10.2.2-era, when a genuine legacy colon-notation engine
existed alongside the P7 one). It is now misleading: this variable is
the **live, necessary** `useRbacStore.tenantRoles`-based P7 permission
set (source #5 above), not a reference to the retired
`rbacService`/`ROLE_PERMISSIONS` engine (which shared no code with this
variable even before deletion). Renaming it is a trivial, safe,
zero-behavior-change cleanup candidate for a future phase — not done
here, since this phase is audit-only.

## Permission Resolution Flow

For every path in the graph above:

| Path | Resolved by | Cached/memoized? | React Query? | Zustand? |
|---|---|---|---|---|
| `usePermission()`/`useAnyPermission()`/`useAllPermissions()` | Wraps `usePermissions()` + inline feature-flag/capability gates | `useMemo`, keyed on the composed permission array + flags | No | Reads `useTenantStore.featureFlags` |
| `usePermissions()` | `getPermissionsForRole()` ∪ `resolveOwnershipDrivenPermissions()` | `useMemo`, keyed on `[user.id, user.email, tenantId, tenant.ownerId, tenant.status, tenantRoles, userOverrides, expiryTick]`; a `setTimeout`-driven `expiryTick` state forces recompute exactly at a temporary `StaffAssignment`'s `validUntil` moment (not polling) | No | Reads `useAuthStore.user`, `useTenantStore.tenant`, `useRbacStore.tenantRoles`/`userOverrides` |
| `useHasDashboardAccess()` | Hand-written boolean (Owner/Staff branches) | `useMemo`, keyed on `[user.email, tenant.id, tenant.ownerId, tenant.status]` | No | Reads `useAuthStore.user`, `useTenantStore.tenant` |
| `resolveOwnershipIdentity()` | Synchronous `staffService.findStaffMemberByEmail()` + `ownerService.getOwnerByUserIdSync()` | None — recomputed on every call, no memoization inside the function itself (callers memoize around it) | No | No — reads mock in-memory arrays inside `staff.service.ts`/`owner.service.ts` (not Zustand-backed) |
| `staffAssignmentService.getEffectiveAssignments()` | Filters `_assignmentStore` (module-level mock array) by `resolveAssignmentStatus() === 'active'` | None | No | No |
| `branch-access.service.ts` | Direct `hasPermission()` calls per invocation | None (stateless service functions) | No | No |
| `useRbacStore.tenantRoles`/`userOverrides` | Zustand `persist` middleware, `localStorage` key `savor-rbac`, no `partialize` (everything persists, including `branchRoles`/`roleAssignments`/`customRoles`/`rbacAuditLog`) | Persisted across sessions/reloads client-side | No | Yes — this IS the Zustand layer |

**No React Query participation anywhere in the authorization graph.**
Every permission/role/assignment read is either a synchronous mock-data
lookup (`staff.service.ts`, `owner.service.ts`, `staff-assignment.service.ts`
— all gated by `USE_MOCK`, would become `await api.get(...)` in real
mode with no caching layer currently wired for that path) or a Zustand
selector. This is consistent with the mock-mode-first architecture
documented throughout P10.x, but is a real-mode readiness gap worth
noting under Architecture Risks.

## Architecture Risks

**Duplicate concepts:**
- `usePermissions()`'s `legacyEffective` variable name vs. its actual
  (non-legacy, live) purpose — naming debt, not a functional risk.
- Five permission sources instead of the four this phase's own
  instructions expected — not a risk in itself (source #5 is legitimate
  and necessary), but worth calling out so future audits don't
  rediscover it as a surprise.

**Remaining inconsistencies:**
- `Header.tsx`/`app/dashboard/layout.tsx` call the wrong hook for
  `dashboard:access` (documented above, unresolved since P10.4.8).
- `branchRoles`/`roleAssignments`/`customRoles` are fully-built,
  fully-tested data models with zero wiring into the actual
  authorization graph — not broken, but a half-finished feature surface
  (the P8.5/P8.6 Console Roles UI writes to them; nothing downstream
  reads them for real permission decisions).

**Technical debt:**
- The `legacyEffective` naming (trivial rename candidate).
- `deriveLegacyUserRoleLabel()` (`ownership-migration.service.ts`) —
  a fully-implemented, tested, but never-called specification function
  for a `UserRole` retirement path that was never executed (P10.1 §8.2).
  Since `UserRole` no longer has any authorization usage (per this
  audit's Phase B), the migration this function specifies may no longer
  be necessary at all — worth a product decision, not a code change,
  in a future phase.

**Future migration candidates:**
- Wiring `branchRoles`/`roleAssignments`/`customRoles` into
  `usePermissions()`'s resolution (if the Console Roles UI is meant to
  eventually affect real access) — or formally declaring them
  UI-data-only and removing the unused-authorization framing from their
  docstrings.
- Fixing the `dashboard:access` hook mismatch in `Header.tsx`/`dashboard/layout.tsx`.

**Performance risks:**
- None identified as urgent. `usePermissions()`'s `useMemo` dependency
  array is correctly scoped; the single `setTimeout` for assignment
  expiry is bounded (one timer per mount, not a poll). Mock-mode data
  lookups are synchronous in-memory array scans — fine at current mock
  fixture scale (dozens of records), would need indexing (e.g. a
  `Map<email, StaffMember>`) before this pattern scales to a real
  multi-tenant dataset size, but that's a real-mode concern, not a
  current one.

**Security risks:**
- `useRbacStore`'s full persistence to `localStorage` (`tenantRoles`,
  `userOverrides`, `branchRoles`, `roleAssignments`, `customRoles`,
  `rbacAuditLog`, no `partialize`) means client-side-writable state
  currently contributes directly to `usePermissions()`'s output via
  `tenantRoles`/`userOverrides`. In mock mode this is by design (there
  is no backend to be the source of truth). **This becomes a real
  security concern the moment `USE_MOCK=false` is set**, unless
  `tenantRoles`/`userOverrides` are re-derived from a trusted backend
  response on every load rather than trusted from `localStorage` — this
  is exactly the kind of gap a real-mode readiness pass should check for
  before launch, flagged here as a risk, not fixed.
- The `Header.tsx`/`dashboard/layout.tsx` bug is fail-*closed* (link
  never shows, even for eligible users) — a usability bug, not a
  security hole. No escalation risk from it.

## Recommendations

**Immediate** (safe, mechanical, near-zero risk — suitable for the very
next phase):
1. Fix `Header.tsx`/`app/dashboard/layout.tsx` to call
   `useHasDashboardAccess()` instead of `usePermission('dashboard:access')`.
   One-line swap per file, already fully specified by this audit and by
   `docs/P10.4.8_LEGACY_COMPATIBILITY_AUDIT.md` Phase G.
2. Rename `usePermissions()`'s `legacyEffective` local variable to
   something accurate (e.g. `tenantRoleBasedPermissions`) — zero
   behavior change, removes a genuinely confusing name.

**Short term:**
3. Decide the product status of `branchRoles`/`roleAssignments`/
   `customRoles`: either wire them into `usePermissions()`'s resolution
   (if the Console Roles UI is meant to be more than a data-entry form)
   or update their docstrings/tests to explicitly state they are
   UI-data-model-only, not part of authorization, so future audits don't
   need to re-derive that finding.
4. Re-evaluate `deriveLegacyUserRoleLabel()`
   (`ownership-migration.service.ts`) now that `UserRole` has zero
   authorization callers — determine whether the P10.1 §8.2 retirement
   path it specifies is still a planned migration or can be closed out.

**Long term:**

No implementation was performed for any of the above — architecture

## Final Verdict

**Remaining inconsistencies are listed above.**

The authorization architecture is coherent and has no duplicate live
decision paths, no dead-but-reachable legacy code, and no discovered
runtime dependency on anything outside `permission.service.ts` /
`ROLE_PERMISSION_MAP` / Ownership Resolution / `StaffAssignment` / the
Zustand tenant-role layer. It is not, however, *fully* internally
consistent: one confirmed, previously-documented bug remains live
(`Header.tsx`/`dashboard/layout.tsx`'s `dashboard:access` hook
mismatch), and two areas of technical debt (the `legacyEffective`
naming, and the unwired `branchRoles`/`roleAssignments`/`customRoles`
data model) are real but non-urgent. None of these block P10.5 feature
work — they are documented, scoped, and none require legacy-engine
removal (already complete) to address.
