# P9.5.0 — Platform Localization Architecture: Audit

> Phase A (documentation only — no code changes). Audits the platform's
> current localization implementation against what a 150+-language,
> platform-only-governed localization system requires, and benchmarks it
> against Shopify Markets, Crowdin, Lokalise, Phrase, and the next-intl
> ecosystem's own conventions (the library this codebase already uses).
>
> Last updated: 2026-07-05

---

## 1. Current implementation, precisely

Localization today is **three small, disconnected pieces**, none of them
registry-driven:

1. **`src/constants/index.ts`** — hardcoded constants:
   ```ts
   export const DEFAULT_LOCALE = 'en'
   export const SUPPORTED_LOCALES = ['en', 'fa', 'ar'] as const
   export const RTL_LOCALES = ['fa', 'ar'] as const
   ```
2. **`src/i18n/request.ts`** — `next-intl`'s `getRequestConfig()`, with the
   supported-locale list **re-declared** (`const supported = ['en', 'fa', 'ar']`,
   a second hardcoded copy of the same three codes), reading a
   `NEXT_LOCALE` cookie or `Accept-Language` header, and dynamically
   importing `./locales/${locale}.json` — this dynamic `import()` is
   already exactly the lazy-loading pattern §`P9.5.0_PERFORMANCE_STRATEGY.md`
   formalizes; it is not being thrown away, only generalized.
3. **`src/i18n/locales/{en,ar,fa}.json`** — three flat, hand-maintained
   translation files, 12 top-level namespaces (`common`, `nav`, `auth`,
   `menu`, `cart`, `checkout`, `order`, `reservation`, `dashboard`,
   `restaurant`, `notifications`, `errors`), 157 leaf keys each, no
   versioning, no coverage tracking, no detection of missing/unused/
   duplicate keys beyond what a human reviewer notices.
4. **`useLangStore`** (`src/stores/index.ts`) — client-side locale
   selection; on change it sets `document.documentElement.lang`/`dir`
   (RTL check is the same hardcoded `['fa', 'ar'].includes(locale)` array,
   a *third* copy of the RTL list) and writes the `NEXT_LOCALE` cookie.
5. **`languages` Configuration module** (`src/config/modules/languages.ts`,
   P9.0) — the *fourth* place the same 3-locale list appears, as a
   `multi-select` field with 3 hardcoded `LANGUAGE_OPTIONS`. This module
   already proves the Configuration Studio can represent language settings
   generically (`languages.supported`, `languages.default`,
   `languages.rtl_locales` — three ordinary fields going through the same
   registry/resolver/audit/Studio pipeline as every other module) — but it
   models locales as **values inside 3 fields**, not as **entities in a
   collection**, so adding language #4 means editing a hardcoded array in
   four different files, not registering one new record.

## 2. The core gap

**Every one of the four locale lists above must be edited by hand, in
lockstep, to add a single language** — and even then, "supported" only
means "appears in the language switcher." There is no representation of:

- A language that exists in the system but is **not yet enabled** (the
  audit's central ask — 150+ languages present, 6 active).
- Locale variants of one language (`ar-SA` vs `ar-EG` vs `ar` neutral).
- Translation coverage (what % of the 157 keys does Turkish actually have?).
- A translation's own history — who changed key `checkout.confirm_button`,
  when, and what it said before (the Configuration Studio's per-field audit
  trail, History timeline, and rollback, P9.1.3/P9.3, have no counterpart
  here at all).
- Per-language fonts, number/date/currency formats, plural/gender rules —
  today the app has none of these; `Intl` calls elsewhere in the codebase
  (e.g. Countries' `'datetime'` preview kind, P9.3) hardcode `undefined`
  (browser default locale) rather than reading the active locale.
- A distinction between "this language is disabled" (hidden from tenants
  entirely) and "this language is in beta" (visible, opt-in, not
  production-guaranteed) — Countries already draws exactly this
  distinction (`enabled`/`visible`/`status: draft|testing|published`,
  P9.2) and localization currently draws none of it.

## 3. What already generalizes cleanly (no rework needed)

| P9.0–P9.4 piece | Reusable for Localization? |
|---|---|
| `PlatformConfigurationRegistry` / `ConfigurationService` | Yes — a language is just another entity; no resolver/validator/cache/audit change needed (proven twice already: Countries in P9.2, Tenants/Platform Users in P9.4). |
| `'collection'` field type + table/drawer/bulk-actions/filter/search engine | Yes — directly. A `localization.languages` collection with one schema (see `P9.5.0_LOCALIZATION_ARCHITECTURE.md`) is the exact shape Countries already validated for a 176-entity, many-region, mixed-state roster. 150+ languages is comfortably the same order of magnitude. |
| Configuration Studio Inspector — Inheritance/History/Compare tabs | Yes — a language's audit trail, inheritance (platform default vs. tenant override), and version comparison are the same primitives already built for every other field. |
| Platform permission model (P9.4) | Yes — `platformPermission: 'platform.localization.manage'` is the same mechanism `platform.security_center` etc. already use; satisfies this phase's "Business Owners MUST NOT enable/disable languages" requirement with zero new code. |
| `ConfigLifecycleState` (`draft`\|`testing`\|`published`\|`deprecated`\|`archived`) | Yes — already the exact 5-state lifecycle this phase asks for (§`P9.5.0_LANGUAGE_LIFECYCLE.md` reuses it verbatim rather than inventing a second lifecycle enum). |
| `next-intl`'s `getRequestConfig` + dynamic `import()` | Yes, as the loading mechanism — it already lazy-loads one locale file per request; it only needs to read its supported-locale list from the registry instead of a hardcoded array. |

## 5. Current / Missing / Future

**Current (reusable as-is):** the registry/resolver/service/Studio/
collection/audit/permission stack (P9.0–P9.4, entirely unmodified by this
phase); `next-intl`'s runtime loading mechanism; the 3 existing translation
JSON files (become the seed content for the `en`/`fa`/`ar` language
entities, not replaced).

**Missing (what `P9.5.0_LOCALIZATION_ARCHITECTURE.md` designs):** a
`localization.languages` collection (150+ entities, 6 enabled) with region/
RTL/font/format/lifecycle/activation-tier metadata; a Translation Key
registry (namespace + key + per-language value + version history); an
Import/Export/Coverage/Fallback-chain design; a documented performance and
developer workflow.

**Future (explicitly out of scope until P9.5.1+ implements it):** any
actual code change to `src/i18n/request.ts`, `useLangStore`,
`languages.ts`, or the JSON files; a real translation-memory storage
backend; CI key-diffing automation; hreflang/sitemap generation. This
phase produces the architecture these implementation phases will follow —
it changes zero lines of source code, per its own explicit constraint.
