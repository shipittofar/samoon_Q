## 2. Identified Gaps

### D1 — `getMarketplaceMeta()` called in five separate places

`getMarketplaceMeta(tenant.settings)` extracts the same object from the same tenant. It is called in:

1. `TenantHomepageClient.tsx` (client, line 783)
2. `BranchHomepageClient.tsx` (client, line 611)
3. `[tenantSlug]/page.tsx` (server, both `generateMetadata` and page body)
4. `[tenantSlug]/[branchSlug]/page.tsx` (server, both `generateMetadata` and page body)
5. `utils/navigation.ts` (inside `buildTenantNavigation`)

**Impact:** Any change to how meta is extracted must be applied in five places.

---

### D2 — Triple-OR loyalty flag pattern duplicated verbatim in two files

```ts
// TenantHomepageClient.QuickActions  AND  BranchHomepageClient.QuickActions
flags['loyalty.enabled'] ??
flags['cafe.loyalty.enabled'] ??
flags['mobile_cafe.loyalty.enabled'] ??
false
```

Root cause: `CAFE_MODULE` uses `cafe.loyalty.enabled`, `MOBILE_CAFE_MODULE` uses `mobile_cafe.loyalty.enabled`, and the capability map uses `loyalty.enabled`. No canonical resolved key exists in the public surface.

**Impact:** Any change to loyalty flag resolution must be applied in both files. Future modules that add their own loyalty key extend the chain.

---

### D3 — QuickActions CTA logic independent of `getSmartCTA` — three independent codepaths

Hero sections (both homepages) correctly delegate to `getSmartCTA()`. But the QuickActions sub-sections in both homepage clients build CTA links inline, independently, with different logic:

| Codepath | View Menu | Reserve | Loyalty | Locations |
|---|---|---|---|---|
| `HeroSection` → `getSmartCTA()` | ✓ priority-aware | ✓ conditional | — | ✓ multi-branch |
| `TenantHomepageClient.QuickActions` | Always shown | Conditional | Conditional | Always shown (bug: even single-branch) |
| `BranchHomepageClient.QuickActions` | Always shown | Conditional | Conditional | N/A |

The "Choose Location" link in `TenantHomepageClient.QuickActions` is **always rendered** even for single-branch tenants — it is not gated on `branchCount > 1`. This is a bug.

---

### D4 — `HomepageLayout.sections` completely ignored in public pages

`SectionConfig[] (10 entries)` is defined in `website-builder.ts` and writeable by the admin Website Builder. However:

- `TenantHomepageClient` never calls `useHomepageLayout()` and never reads `sections`
- `BranchHomepageClient` same
- `TenantHeader` reads only `layout.navItems` (not sections)

Result: the owner can enable/disable sections in the admin UI and nothing changes on the public site. `HomepageLayout.sections` is wired to nothing.

---

### D5 — `BASE_URL` constant duplicated in four files

```ts
const BASE_URL = process.env.NEXT_PUBLIC_APP_URL || 'https://www.savor.com'
```

Declared locally in:
1. `[tenantSlug]/page.tsx`
2. `[tenantSlug]/[branchSlug]/page.tsx`
3. `lib/json-ld.ts`
4. `components/common/JsonLd.tsx`

---

### D6 — `generateMetadata` object shape duplicated in two server files

Both `[tenantSlug]/page.tsx` and `[tenantSlug]/[branchSlug]/page.tsx` build identical-shaped metadata objects (title, description, url, image, openGraph, twitter). The entire block is copy-pasted with minor field differences.

---

### D7 — Inline JSON-LD instead of `lib/json-ld.ts` builders

Both server pages build JSON-LD as raw `JSON.stringify({...})` strings instead of using the purpose-built `buildRestaurantJsonLd()` + `serializeJsonLd()` from `lib/json-ld.ts`.

Additionally, the `@type` differs between the two pages without documented rationale:
- `[tenantSlug]/page.tsx`: `'@type': 'Restaurant'`
- `[tenantSlug]/[branchSlug]/page.tsx`: `'@type': 'LocalBusiness'`

`lib/json-ld.ts:buildRestaurantJsonLd()` uses `['Restaurant', 'FoodEstablishment']` — more correct than either.

---

### D8 — TenantFooter: hardcoded flat `/reservation` link (not branch-aware, not flag-gated)

```tsx
// TenantFooter.tsx line 92
<Link href="/reservation" className="hover:text-orange-500 transition-colors">
  Reservations
</Link>
```

Two bugs:
1. URL is `/reservation` — should be `/{tenantSlug}/{primaryBranchSlug}/reservation`
2. Shown unconditionally — should be gated on `featureFlags['reservations.enabled']`

`TenantFooter` currently has no access to `featureFlags` (no store import).

---

### D9 — `buildPublicUrl` / `hrefToPublicUrl` unused by public pages

`src/utils/public-url.ts` exports URL builders that construct branch-aware public paths. They are used only by the admin `PreviewButton`. The homepage clients build `/${tenantSlug}/${branchSlug}/menu` etc. as inline template literals.

---

### D10 — JSON-LD: AggregateRating emitted regardless of `reviews.enabled` flag

Both server pages emit AggregateRating JSON-LD whenever `meta.rating` exists, without checking whether the reviews module is enabled. If reviews are disabled, the rating still appears in structured data — metadata contradicts visible content (Phase G/H gap).

---

### D11 — Route-level feature flag guards missing

Sub-pages (`reservation/page.tsx`, `loyalty/page.tsx`, etc.) are pure re-exports with no flag guard at the route level. A user who navigates directly to `/{tenantSlug}/{branchSlug}/reservation` when `reservations.enabled = false` will land on the reservation page regardless. This is a client-side concern (the page itself should handle it), but no canary check exists at the route level.
