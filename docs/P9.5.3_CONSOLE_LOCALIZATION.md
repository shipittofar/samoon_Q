# P9.5.3 — Business Console & Platform Administration Localization

## Summary

This phase migrated the **generic, module-agnostic UI chrome** of the
Configuration Studio, Console module-page shell, and Platform
Administration dashboard to `next-intl`, reusing the existing `console`
namespace established in prior phases. It did **not** achieve full
localization of every Business Console / Platform Administration surface —
see "What remains" below for the complete, honest accounting.

**Do not read this as "Business Console fully localized."** It is not. The
shared chrome every module/widget renders through is now localized; the
per-module field content (titles, descriptions) and several secondary
Studio panels are not.

## What remains (honest accounting — NOT fully localized)

Per-module and per-widget **content** — as distinct from shared chrome —
remains in English:

1. **~150+ `ConfigFieldDefinition.title`/`.description` literals** across
   ~18 files in `src/config/modules/*.ts` and ~9 files in
   `src/platform-admin/modules/*.ts`. These are consumed by the
   now-localized `ConfigurationFieldRow`/`ConfigurationEntityDrawer` via
   `prop.display?.displayName ?? prop.title`, so the rendering path is
   ready, but the underlying data is still literal English.
2. **`PlatformDashboardWidgetCard.tsx`** widget rendering, and the ~23
   widget definitions in `src/platform-admin/dashboard.ts` (title, stat
   labels, trend labels) — untouched.
3. **`src/platform-admin/search.ts`** — platform global search result
   labels/descriptions — untouched.
4. **Ten secondary Studio panel components** not touched this phase:
   `ConfigurationInspector.tsx`, `ConfigurationInheritanceTree.tsx`,
   `ConfigurationCompareView.tsx`, `ConfigurationHistoryTimeline.tsx`,
   `ConfigurationFieldRow.tsx`, `ConfigurationFieldControl.tsx`,
   `ConfigurationFieldPreview.tsx`, `ConfigurationFieldBadges.tsx`,
   `ConfigurationWorkspaceSkeleton.tsx`, `ConfigurationStudioLayout.tsx`.
5. Per the P9.5.3 spec's scope list (Customer CRM, Analytics, Orders,
   Reservations, Kitchen, Marketing, Support, Staff, Website Builder,
   Settings, etc.) — these are rendered through the now-localized
   `ConfigurationModulePage`/`ConfigurationCollectionTable` shell, so their
   *chrome* (search, filters, save bar, empty states, bulk actions) is
   localized, but each module's own field titles/descriptions (item #1
   above) are not.

### Estimated coverage

- **Shared chrome components:** 8/8 migrated (100%)
- **Per-module field content:** 0/~27 modules' field definitions migrated
  (field-level `title`/`description` remain English)
- **Overall Console/Platform-admin file-level migration:** 8 of
  approximately 120 total console/platform-admin component + module-data
  files touched this phase (~7%) — the 8 touched files are the
  highest-leverage ones (every module/widget renders through them), but
  the bulk of remaining literal content by file count is the per-module
  metadata, not yet migrated.

**This phase is honestly a partial migration of the Console/Platform-admin
surface: the shared framework chrome is fully localized; the majority of
per-module content is not.**

## Namespace organization

No new namespaces were created. All 121 new keys were added to the
existing `console` namespace (established in P9.1.3/P9.3/P9.4), consistent
with the instruction to reuse namespaces whenever possible. Two
pre-existing but previously-unused `notifications` namespace keys
(`exported`, `configurationRefreshed`) were wired into
`ConfigurationStudioToolbar.tsx`'s toasts, converting them from dead keys
into live ones.

## RTL verification

Fixed 4 physical-direction Tailwind classes (`ml-*` → `ms-*`) directly
adjacent to text being localized in this same pass:
- `ConfigurationSaveBar.tsx`: `ml-1.5` → `ms-1.5` (⌘S hint)
- `ConfigurationStudioToolbar.tsx`: `ml-2` → `ms-2` (search `<kbd>` hint)
- `ConfigurationStudioNav.tsx`: `ml-auto` → `ms-auto` (lifecycle badge)
- `ConfigurationCollectionTable.tsx`: `ml-1.5` → `ms-1.5` (entity-id mono
  span)

Per the phase's "fix only localization-related RTL issues" instruction, no
broader systematic RTL audit was performed on the migrated files or on the
still-English per-module content; a full RTL pass (breadcrumbs, drawers,
modals, table alignment) across the entire Console/Platform-admin surface
remains outstanding for a future phase.

## Accessibility

All migrated aria-labels, empty-state titles/descriptions, and dialog
titles route through `next-intl`. No new landmark roles or focus-hint
patterns were introduced or changed — this phase only replaced literal
string values with translated ones inside already-existing accessible
markup.

## Performance impact

Identical pattern to P9.5.1B/P9.5.2: `useTranslations('console')` is a
lightweight client-side hook resolving against the already-loaded locale
bundle (no new network requests, no additional bundle chunks beyond the
121 new JSON string entries × 3 locales, on the order of a few KB
uncompressed). No measurable runtime overhead expected; not separately
benchmarked, consistent with prior phases' treatment of chrome-level
migrations.

## Lessons learned

- Adding `useTranslations()` to widely-reused framework components breaks
  any pre-existing test that renders them outside a `NextIntlClientProvider`.
  The fix (a shared `renderWithIntl` test helper + import-swap in affected
  test files) generalizes cleanly and should be the default pattern for
  future component migrations that touch shared framework pieces.
- Drawing the line between "shared chrome" (safe, high-leverage,
  in-scope) and "per-module content" (large, mechanical, better as its own
  phase) was the key scoping decision that made honest, verifiable
  progress possible within one phase, rather than either stalling on an
  impossible full migration or silently claiming completeness.
