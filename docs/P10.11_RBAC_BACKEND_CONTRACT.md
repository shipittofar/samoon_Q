# RBAC Backend Contract

This document specifies the complete Role-Based Access Control system the
Savor / Samoon Q frontend implements today, translated into a backend
contract a Django (or any backend) engineer can implement without asking
the frontend anything further. It is a **transcription of the existing,
working frontend RBAC model** (`src/services/permission.service.ts`,
`src/services/ownership-resolution.service.ts`,
`src/services/branch-access.service.ts`, `src/hooks/index.ts`) — not a
redesign. No permission, role, or authorization rule described here
differs from what the frontend already enforces client-side.

**The frontend's RBAC is UX only.** Every rule in this document must be
independently re-enforced by the backend on every request — see Part 8.

---

## 1. RBAC Architecture Overview

The frontend resolves a user's effective permission set through **three
independent, unioned sources**, not one:

```
                    ┌─────────────────────────┐
                    │   usePermissions()       │  (src/hooks/index.ts)
                    └───────────┬──────────────┘
                                │ unions
              ┌─────────────────┼──────────────────┐
              ▼                                     ▼
  ┌───────────────────────┐          ┌──────────────────────────────┐
  │ 1. tenantRoles-based   │          │ 2. Ownership-driven           │
  │    (RBAC store)        │          │    (ownership-resolution.svc) │
  │                        │          │                                │
  │  tenantRoles[tenantId] │          │  Owner short-circuit:         │
  │    → ROLE_PERMISSION_  │          │    owns tenant → ALL_PERM.    │
  │      MAP[role]         │          │                                │
  │    → + userOverrides   │          │  StaffAssignment:              │
  │      (allow/deny)      │          │    role → ROLE_PERMISSION_MAP │
  │                        │          │    mode:'read' → .view only   │
  └───────────────────────┘          └──────────────────────────────┘
```

A third, **completely separate** system — Platform Admin
(`PlatformPermissionGuard`, `src/platform-admin/permissions.ts`) —
governs `/platform-admin/*` routes and is **out of scope for this
document**: it never calls `usePermissions()`, has its own permission
set, and is not part of tenant-scoped RBAC. It is mentioned only so the
backend engineer does not conflate the two systems.

**Every permission check ultimately composes three gates** (all three
must pass):

```
Permission AND Capability AND FeatureFlag
```

- **Permission**: is this permission in the role's/owner's/staff's
  effective set?
- **Capability**: is the tenant's business-type module capability for
  this resource enabled? (e.g. a `food_truck` tenant has no `vendors`
  capability)
- **FeatureFlag**: is the tenant-level feature flag for this resource
  enabled? (e.g. `ordering.enabled`)

Capability and FeatureFlag are **tenant configuration**, not part of
RBAC proper — documented here only because `hasPermission()` composes
them at the same call site. The backend should apply the same
three-gate composition when authorizing API requests, sourcing
Capability/FeatureFlag from the tenant's own configuration record.

## 2. Database Schema

```sql
-- Identity (see docs/P10.10_AUTH_BACKEND_API_CONTRACT.md for full User contract)
CREATE TABLE users (
    id              UUID PRIMARY KEY,
    email           VARCHAR(255) UNIQUE,
    phone_number    VARCHAR(32),
    first_name      VARCHAR(100) NOT NULL,
    last_name       VARCHAR(100) NOT NULL,
    status          VARCHAR(20) NOT NULL DEFAULT 'active', -- active|suspended|pending_verification
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE tenants (
    id              UUID PRIMARY KEY,
    name            VARCHAR(255) NOT NULL,
    slug            VARCHAR(100) UNIQUE NOT NULL,
    type            VARCHAR(50) NOT NULL,  -- restaurant|cafe|bar|food_court|food_truck|mobile_cafe|hotel|other
    status          VARCHAR(20) NOT NULL,  -- active|trial|suspended|churned|archived
    owner_id        UUID REFERENCES owners(id),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE locations (
    id              UUID PRIMARY KEY,
    tenant_id       UUID NOT NULL REFERENCES tenants(id),
    name            VARCHAR(255) NOT NULL,
    code            VARCHAR(50),           -- short slug/code, e.g. branch identifier
    status          VARCHAR(20) NOT NULL,  -- active|inactive|maintenance
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Ownership — distinct from Tenant, distinct from Role/StaffAssignment.
-- One Owner (a business entity) owns zero-or-more Tenants via tenants.owner_id.
CREATE TABLE owners (
    id                  UUID PRIMARY KEY,
    user_id             UUID NOT NULL REFERENCES users(id),
    status              VARCHAR(30) NOT NULL, -- active|suspended|pending_verification
    plan                VARCHAR(50) NOT NULL,
    max_tenants         INTEGER,               -- NULL = unlimited
    billing_customer_id VARCHAR(100),
    billing_email       VARCHAR(255),
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    verified_at         TIMESTAMPTZ
);

-- Role — the 8 system roles below are fixed and MUST NOT be renamed,
-- removed, or have their slug changed (see Part 5/9 "Do not redesign").
CREATE TABLE roles (
    id              UUID PRIMARY KEY,
    slug            VARCHAR(50) UNIQUE NOT NULL, -- 'owner'|'admin'|'manager'|'cashier'|'waiter'|'kitchen'|'marketing'|'support'
    name            VARCHAR(100) NOT NULL,
    description     TEXT,
    system_role     BOOLEAN NOT NULL DEFAULT true,
    tenant_id       UUID REFERENCES tenants(id) NULL -- NULL = system role (all 8 below); non-NULL = future custom role
);

CREATE TABLE permissions (
    id              UUID PRIMARY KEY,
    resource        VARCHAR(50) NOT NULL,   -- e.g. 'orders'
    action          VARCHAR(50) NOT NULL,   -- e.g. 'manage'
    key             VARCHAR(100) UNIQUE NOT NULL, -- 'orders.manage' — resource + '.' + action
    description     TEXT
);

CREATE TABLE role_permissions (
    role_id         UUID NOT NULL REFERENCES roles(id),
    permission_id   UUID NOT NULL REFERENCES permissions(id),
    PRIMARY KEY (role_id, permission_id)
);

-- A user's role assignment scoped to a tenant (owner/admin — tenant-wide roles).
CREATE TABLE user_tenant_roles (
    id              UUID PRIMARY KEY,
    user_id         UUID NOT NULL REFERENCES users(id),
    tenant_id       UUID NOT NULL REFERENCES tenants(id),
    role_id         UUID NOT NULL REFERENCES roles(id),
    UNIQUE (user_id, tenant_id, role_id)
);

-- Fine-grained, location-scoped grants — the primary mechanism for
-- Manager/Cashier/Waiter/Kitchen/Marketing/Support roles.
CREATE TABLE staff_assignments (
    id              UUID PRIMARY KEY,
    user_id         UUID NOT NULL REFERENCES users(id),  -- staff member
    tenant_id       UUID NOT NULL REFERENCES tenants(id),
    location_ids    UUID[] NULL,            -- NULL/empty array with all_locations=true = every current+future location
    all_locations   BOOLEAN NOT NULL DEFAULT false,
    role_id         UUID NOT NULL REFERENCES roles(id), -- never 'owner'
    mode            VARCHAR(10) NOT NULL DEFAULT 'manage', -- 'read'|'manage'
    status          VARCHAR(20) NOT NULL,   -- active|future|revoked|expired
    valid_from      TIMESTAMPTZ,
    valid_until     TIMESTAMPTZ,
    granted_by      UUID NOT NULL REFERENCES users(id),
    granted_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_by      UUID REFERENCES users(id),
    revoked_at      TIMESTAMPTZ
);

-- Per-user, per-tenant permission overrides (P8.5) — applied on top of
-- role-derived permissions. allow[] adds, deny[] subtracts, deny wins.
CREATE TABLE user_permission_overrides (
    user_id         UUID NOT NULL REFERENCES users(id),
    tenant_id       UUID NOT NULL REFERENCES tenants(id),
    permission_id   UUID NOT NULL REFERENCES permissions(id),
    effect          VARCHAR(10) NOT NULL,  -- 'allow'|'deny'
    PRIMARY KEY (user_id, tenant_id, permission_id)
);
```

## 3. Entity Relationship Diagram

```
users ──1:N── owners ──1:N── tenants ──1:N── locations
  │                             │
  │                             │
  ├──N:M── user_tenant_roles ───┤ (owner/admin: tenant-wide)
  │              │
  │              └──N:1── roles ──N:M── role_permissions ──N:1── permissions
  │
  ├──N:M── staff_assignments ───┤ (manager/cashier/waiter/kitchen/
  │              │                marketing/support: location-scoped)
  │              └──N:1── roles
  │
  └──N:M── user_permission_overrides ──N:1── permissions
```

**Key structural fact — Owner is not a Role.** `owners` is a business
entity distinct from `roles.slug = 'owner'`. A tenant's Owner receives
**every** permission structurally (by owning the tenant — see Part 4),
never through a `role_permissions` row lookup. `roles.slug = 'owner'`
exists as a `Role` string value for typing/display purposes and appears
in `staff_assignments.role_id`'s exclusion list (an Owner is never
granted via a StaffAssignment — see `StaffRole = Exclude<Role, 'owner'>`
in the frontend's `src/types/ownership.ts`), but the actual grant
mechanism for an Owner bypasses `role_permissions` entirely.

these warnings when constructing `role_permissions` rows via the Assign
Role API (Part 6).

## 6. Authorization Evaluation Chain

```
User
  │
  ├─→ [Platform Admin?] ──yes──→ separate system, not this document
  │
  ▼
Tenant Membership (is this user an Owner or Staff of the active tenant?)
  │
  ├─→ Owner of active tenant (tenants.owner_id → owners.user_id)?
  │      │
  │      ├─→ Owner.status must be 'active' (else: zero access)
  │      ├─→ Tenant.status must not be 'archived' (else: zero access)
  │      └─→ YES → ALL 48 permissions, ALL locations. STOP. (short-circuit)
  │
  └─→ Not the Owner → check StaffAssignment
         │
         ├─→ StaffAssignment.status must be 'active' (not future/revoked/expired
         │    — 'future'/'expired' are ALSO derived at read time from
         │    valid_from/valid_until even if the stored status column
         │    hasn't caught up — see "Assignment status derivation" below)
         ├─→ StaffMember.status must be 'active' (else: zero access)
         ├─→ Tenant.status must not be 'archived' (else: zero access)
         └─→ Role Assignment → Permission Set
                │
                ├─→ role_permissions for StaffAssignment.role_id
                ├─→ mode = 'read' → downgrade to `.view`-suffixed subset only
                │    (a permission whose resource has no `.view` sibling,
                │    e.g. `payments.process`, is dropped entirely)
                └─→ mode = 'manage' → full role permission set
                       │
                       ▼
                Location Scope
                       │
                       ├─→ all_locations = true → every current AND future
                       │    location of this tenant
                       └─→ all_locations = false → exactly
                            staff_assignments.location_ids
```

On top of whichever base set above applies, **`user_permission_overrides`**
is applied: `deny` always wins over both role grants and `allow`
overrides. Evaluation order: **User Deny → User Allow → Role
Permissions → Default Deny.**

A user may hold **multiple StaffAssignments to the same tenant** with
different location scopes (e.g. `manage` mode at Location A, `read` mode
at Location B) — permissions from all effective assignments are unioned;
location scope is unioned separately (see Part 4 below).

### Assignment status derivation

`staff_assignments.status` is the **last explicitly-set** value
(via grant/revoke actions), but the *effective* status at read time is
derived, not trusted blindly:

```
effective_status =
  if status == 'revoked': 'revoked'
  elif valid_until is not null and valid_until < now(): 'expired'
  elif valid_from is not null and valid_from > now(): 'future'
  else: 'active'
```

Only `effective_status == 'active'` assignments grant permissions. This
mirrors the frontend's `resolveAssignmentStatus()` /
`getEffectiveAssignments()` (`ownership.service.ts` /
`staff-assignment.service.ts`) — the backend must replicate this exact
derivation, not just read the stored `status` column, or a
past-`valid_until` assignment will incorrectly continue granting access.

## 4. Tenant and Location Scoping (detailed rules)

**Owner:** access to **all** locations of every tenant they own,
unconditionally — this is structural (via `tenants.owner_id`), never via
a `staff_assignments` row. An Owner is never location-restricted.

**Admin** (via `user_tenant_roles`, tenant-wide role, not
location-scoped): same as Owner for location access — Admin is a
tenant-wide role, not scoped to specific locations, in the current
model. (Admin lacks `tenant.view`/`tenant.manage` — the *only*
permission difference from Owner — but has the same all-locations
reach.)

**Manager / Cashier / Waiter / Kitchen / Marketing / Support** (via
`staff_assignments`): scoped to **exactly the locations listed in their
assignment(s)** — `location_ids`, or every location (present and
future) if `all_locations = true`. A staff member with no matching
assignment for a location sees **nothing** at that location, regardless
of their role's permission grants elsewhere.

**Special case — `branches.manage` permission overrides location
scoping for read access:** per `branch-access.service.ts`
(`getAccessibleBranches()`), a holder of `branches.manage` sees **every**
branch of the tenant regardless of their `staff_assignments.location_ids`
— this permission is specifically the "see all branches" override, used
today only by roles that already have tenant-wide reach (owner, admin,
manager). The backend must replicate this: location-scoped read
endpoints should return all tenant locations for a caller holding
`branches.manage`, and only assigned locations otherwise.

### Preventing cross-tenant access

Every tenant-scoped API request must verify the caller is **either**:
1. The `owner_id` (via `owners.user_id`) of the tenant in the URL/body, with `owners.status = 'active'` and the tenant not `'archived'`, **or**
2. Holds at least one `staff_assignments` row for that `tenant_id` with `effective_status = 'active'`.

Anyone else → `403 TENANT_ACCESS_DENIED` (see Part 7), even if they hold
a valid session token — token validity proves identity, not tenant
membership.

### Preventing cross-branch/location access

Every location-scoped API request must verify the caller's resolved
location set (per the rules above) includes the `location_id` in the
URL/body. This is a **second, independent check** from tenant
membership — a Manager who is a legitimate member of Tenant A but has no
assignment to Location A-3 must be denied access to Location A-3's data
even though they pass the tenant check. → `403 LOCATION_ACCESS_DENIED`.

**Never derive location access from tenant access alone** — this is
precisely the check `branch-access.service.ts`/
`assertOwnershipBranchAccess()` exists to enforce and is a named,
previously-fixed bug class in this codebase's history (P10.2.3 finding
F-4: "BranchAccessContext existed but no read path ever called it").

## 5. Auth Session RBAC Payload

Exact fields the frontend expects on every identity-producing response
(`login`, `verifyOTP` existing-user branch, `register`, `getMe`) — this
section is the RBAC-specific elaboration of
`docs/P10.10_AUTH_BACKEND_API_CONTRACT.md`'s `AuthSessionPayload`, not a
new contract.

```json

  "first_name": "Maria",

  "role": "staff",
  "is_verified": true,

      "grantedAt": "2025-01-15T00:00:00Z"
    }
  ]
}
```

### Field documentation

| Field | Type | Required | Description | Example |
|---|---|---|---|---|
| `tenantRoles` | array | optional | Tenant-wide role grants for this user (Owner/Admin only — Manager and below use `staffAssignments`, not this array, for location-scoped grants). Empty/absent for a customer or location-scoped staff member. | see above |
| `tenantRoles[].tenant_id` | string | yes (within object) | Tenant this role applies to | `"tnt_savor01"` |
| `tenantRoles[].tenant_slug` | string | yes | Tenant's URL slug — lets the frontend avoid a second lookup | `"savor-downtown"` |
| `tenantRoles[].role` | string | yes | One of the 8 system role slugs (Part 5) | `"manager"` |
| `tenantRoles[].permissions` | string[] | recommended | Pre-resolved effective permission keys for this role. **The frontend can derive this itself from `ROLE_PERMISSION_MAP` (mirrored client-side), so sending it is a convenience/consistency safeguard, not a hard requirement** — but if the backend later adds custom per-tenant role permission edits, sending the resolved list becomes load-bearing. | `["orders.view", "orders.manage", ...]` |
| `ownership` | array | optional | Every `Owner` record for this user (usually 0 or 1; a user could theoretically own multiple Owner entities in edge cases, hence array) | see above |
| `staffAssignments` | array | optional | Every currently-effective StaffAssignment this user holds, across all tenants | see above |

**Critical: `tenantRoles` and `staffAssignments` are not interchangeable
and both may be present simultaneously** (a multi-tenant user could be
Owner of Tenant A and a location-scoped Cashier at Tenant B). The
frontend's `usePermissions()` unions permissions from both sources for
whichever tenant is currently active (see Part 6 in this doc, or Part 1
architecture diagram) — the backend does not need to pre-union these; it
sends both raw arrays and the frontend composes them, exactly as it does
today client-side with mock data.

## 6. Required Backend API Routes

### 6.1 `GET /api/auth/me/permissions`

**Auth:** Bearer token required.
**Required permission:** none (any authenticated user may read their own permissions).

**Response** (200 OK):

```json
{ "permissions": ["orders.view", "orders.manage", "..."] }
```

Resolved for the caller's **currently active tenant** (frontend sends
`X-Tenant-Slug` header or the backend infers it from the caller's sole
tenant membership if unambiguous — see
`docs/P10.10_AUTH_BACKEND_API_CONTRACT.md` for tenant-resolution
precedent via subdomain). This is the single-source-of-truth companion
to `GET /auth/me/`'s embedded `tenantRoles[].permissions` — useful for a
lightweight refresh without re-fetching the whole session.

**Errors:** `401 TOKEN_INVALID`.

---

### 6.2 `GET /api/tenants/{tenant_id}/roles`

**Auth:** Bearer token required.
**Required permission:** `staff.view` for `{tenant_id}`.

**Response** (200 OK):

```json
[
  { "id": "role_manager", "name": "Manager", "slug": "manager", "permissions": ["orders.view", "..."] },
  { "id": "role_cashier", "name": "Cashier", "slug": "cashier", "permissions": ["orders.view", "..."] }
]
```

Returns the 8 system roles (tenant-agnostic — every tenant sees the same
8 unless/until custom roles are implemented, which is out of scope —
see Part 13 Migration Checklist).

**Errors:** `401 TOKEN_INVALID`, `403 PERMISSION_DENIED`, `403 TENANT_ACCESS_DENIED`.

---

### 6.3 `GET /api/permissions`

**Auth:** Bearer token required.
**Required permission:** none (static reference data — used to populate the role editor's permission picker).

**Response** (200 OK):

```json
[
  { "key": "orders.view", "resource": "orders", "action": "view", "description": "View orders" },
  { "key": "orders.manage", "resource": "orders", "action": "manage", "description": "Manage orders" }
]
```

Returns all 48 canonical permissions (Part 4). Static/rarely-changing —
safe for the frontend to cache aggressively.

**Errors:** `401 TOKEN_INVALID`.

---

### 6.4 `POST /api/tenants/{tenant_id}/users/{user_id}/roles`

**Auth:** Bearer token required.
**Required permission:** `staff.manage` for `{tenant_id}`.

**Request:**

| Field | Type | Required | Description |
|---|---|---|---|
| `role_id` | string | yes | Role to assign — must not be the `owner` role (Owner is granted structurally, never via this endpoint — see Part 3) |
| `location_ids` | string[] | conditionally | Required unless `all_locations: true`. Locations this grant applies to. |
| `all_locations` | boolean | no (default `false`) | Grant applies to every current AND future location of the tenant |
| `mode` | `'read' \| 'manage'` | no (default `'manage'`) | `'read'` downgrades the role's grant to `.view`-only |
| `valid_from` | string (ISO 8601) | no | Grant becomes effective at this time |
| `valid_until` | string (ISO 8601) | no | Grant expires at this time |

**Response** (201 Created):

```json
{
  "success": true,
  "assignment": {
    "id": "sa_42",
    "userId": "usr_123",
    "tenantId": "tnt_savor01",
    "locationIds": ["loc_downtown"],
    "role": "manager",
    "mode": "manage",
    "status": "active",
    "grantedBy": "usr_owner_1",
    "grantedAt": "2025-07-10T00:00:00Z"
  }
}
```

**Errors:** `401 TOKEN_INVALID`, `403 PERMISSION_DENIED`, `403 TENANT_ACCESS_DENIED`, `404 ROLE_NOT_FOUND`, `409 ROLE_ALREADY_ASSIGNED` (same user+tenant+location+role combination already active).

---

### 6.5 `DELETE /api/tenants/{tenant_id}/users/{user_id}/roles/{assignment_id}`

**Auth:** Bearer token required.
**Required permission:** `staff.manage` for `{tenant_id}`.

**Request:** none (assignment identified by path).

**Response** (200 OK): `{ "success": true }`

Revokes (soft-deletes — sets `status = 'revoked'`, `revoked_by`,
`revoked_at`) rather than hard-deleting, preserving audit history.

**Errors:** `401 TOKEN_INVALID`, `403 PERMISSION_DENIED`, `403 TENANT_ACCESS_DENIED`, `404` (assignment not found or already revoked).

### 6.6 Staff Assignment CRUD

| Method | Endpoint | Purpose | Required Permission |
|---|---|---|---|
| `POST` | `/api/tenants/{tenant_id}/staff-assignments/` | Create an assignment (identical body/response to 6.4 — 6.4 is a convenience alias scoped to a specific user) | `staff.manage` |
| `GET` | `/api/tenants/{tenant_id}/staff-assignments/` | List all assignments for the tenant (optionally `?user_id=` or `?location_id=` filtered) | `staff.view` |
| `GET` | `/api/tenants/{tenant_id}/staff-assignments/{id}/` | Single assignment detail | `staff.view` |
| `PATCH` | `/api/tenants/{tenant_id}/staff-assignments/{id}/` | Update `location_ids`, `mode`, `valid_from`/`valid_until` (NOT `role_id` or `user_id` — those require revoke + re-grant, preserving the audit trail, per the frontend's "Move" convention in `src/types/ownership.ts`'s `MoveStaffAssignmentPayload`) | `staff.manage` |
| `DELETE` | `/api/tenants/{tenant_id}/staff-assignments/{id}/` | Same as 6.5 | `staff.manage` |

**`PATCH` request body** (all fields optional, only provided fields change):

```json
{ "location_ids": ["loc_downtown", "loc_uptown"], "mode": "read", "valid_until": "2025-12-31T00:00:00Z" }
```

**Response** (200 OK): the updated assignment object (same shape as 6.4's `assignment`).

**Errors (all four):** `401 TOKEN_INVALID`, `403 PERMISSION_DENIED`, `403 TENANT_ACCESS_DENIED`, `404 ROLE_NOT_FOUND` (or assignment not found).

## 7. Error Contract

| HTTP | Code | Meaning | Frontend behavior |
|---|---|---|---|
| 401 | `TOKEN_INVALID` | Access token missing/expired/malformed | Same category-A handling as `docs/P10.10_AUTH_BACKEND_API_CONTRACT.md` §4 — triggers `AuthBootstrapper.clearSession()`, full teardown |
| 403 | `PERMISSION_DENIED` | Authenticated, correct tenant, but lacks the specific permission for this action | Frontend shows an "Access Denied" state (via `PermissionGuard`'s `fallback` prop or `AuthGuard`'s `forbiddenPath` redirect) — **does not** clear the session; this is expected, routine UX, not a security event |
| 403 | `TENANT_ACCESS_DENIED` | Authenticated, but not a member (Owner or Staff) of the tenant in the request | Frontend should treat this as "wrong tenant context" — trigger a tenant-switch prompt or redirect to the user's actual tenant list, never a logout |
| 403 | `LOCATION_ACCESS_DENIED` | Authenticated, correct tenant, but lacks assignment to the requested location | Frontend filters the location out of pickers/switchers; if reached via direct navigation, redirect to an accessible location or show empty state |
| 404 | `ROLE_NOT_FOUND` | `role_id` in a role-assignment request doesn't exist, or (for DELETE/PATCH) the assignment itself doesn't exist | Frontend shows a generic "not found" toast; role picker should have prevented this client-side (stale cache) — frontend should refetch `GET /api/permissions` / role list on this error |
| 409 | `ROLE_ALREADY_ASSIGNED` | Attempting to create a duplicate active assignment (same user+tenant+location+role) | Frontend shows "already assigned" inline validation error, does not retry |

**None of these RBAC errors should ever trigger `clearSession()`**
except `TOKEN_INVALID` (401) — this mirrors
`docs/P10.10_AUTH_BACKEND_API_CONTRACT.md`'s category A/B split exactly:
a `403`/`404`/`409` here means the session is perfectly valid, just the
specific action isn't allowed or doesn't exist. Logging the user out on
a `403 PERMISSION_DENIED` would be a bug, not a security feature.

## 8. Backend Security Requirements

1. **The backend is the only authorization authority.** Every rule in
   this document (role → permission map, ownership short-circuit,
   location scoping, override precedence) must be independently
   re-implemented and re-checked server-side. The frontend's
   `usePermissions()`/`PermissionGuard`/`AuthGuard` exist purely to hide
   UI a user isn't allowed to use — they are UX conveniences, not a
   security boundary.
2. **Frontend permission state must never be trusted as an authorization
   input.** No API endpoint should accept a `permissions` list, `role`,
   or `tenantRoles` value *from the request* and act on it — these are
   always derived server-side from `user_tenant_roles` /
   `staff_assignments` /  `user_permission_overrides`, looked up by the
   authenticated user's ID from the validated access token. The payload
   in Part 5 is something the backend **sends**, never something a
   client **sends back** as an authorization claim.
3. **`localStorage` is not a security boundary.** The RBAC state
   currently persisted client-side (`useRbacStore`'s `savor-rbac`
   localStorage key) is a cache for UX responsiveness — the backend must
   assume it can be arbitrarily tampered with and must never treat a
   request's absence of a 403 as proof the client-side check passed;
   independently verify on every request.
4. **Every API request handling tenant- or location-scoped data must
   validate, in this order:**
   - User identity (valid access token → known user)
   - Tenant membership (Part 4's cross-tenant check)
   - Role (what role does this user hold for this tenant/location?)
   - Permission (does that role — after overrides — grant the specific
     action being performed?)
   - Location scope (if the resource is location-scoped, is the target
     location within the user's resolved location set?)

   Skipping any one of these five checks — e.g. checking permission but
   not location scope — reproduces exactly the class of bug this
   codebase's own history has already found and fixed once client-side
   (P10.2.3 finding F-4, referenced in Part 4).

## 9. Django Implementation Guide

### Suggested app structure

```
apps/
  authentication/     # User model, login/OTP/register — see P10.10 contract
  tenants/             # Tenant, Location models + membership resolution
  permissions/         # Permission model, ALL_PERMISSIONS fixture/migration
  roles/               # Role, RolePermission — the 8 system roles as a data migration
  staff/               # StaffAssignment, UserTenantRole, override models + assignment services
```

### Models (one-to-one with §2's schema)

- `authentication.User`
- `tenants.Tenant`, `tenants.Location`, `tenants.Owner`
- `permissions.Permission` — seed via a data migration with the exact 48
  keys from Part 4 (do not let admins freely create arbitrary
  permission rows — this is a fixed, code-level contract with the
  frontend, not a dynamic entity)
- `roles.Role`, `roles.RolePermission` — seed the 8 system roles + their
  exact grant lists from Part 5 via a data migration; keep
  `system_role=True` for all 8 and reject `DELETE`/rename attempts on
  them at the API layer
- `staff.UserTenantRole` (Owner/Admin — tenant-wide)
- `staff.StaffAssignment` (Manager and below — location-scoped)
- `staff.UserPermissionOverride`

### Serializers

- `UserSerializer` — see `docs/P10.10_AUTH_BACKEND_API_CONTRACT.md` §3.1
- `RoleSerializer` — `{ id, name, slug, permissions: [key,...] }`
- `PermissionSerializer` — `{ key, resource, action, description }`
- `RBACSerializer` — composite serializer producing the exact Part 5
  payload shape (`tenantRoles`, `ownership`, `staffAssignments`) for
  embedding in `/auth/me/`, `/auth/login/`, etc.

### Services (business logic — keep out of views/serializers)

- **`PermissionResolver`** — given `(user, tenant)`, returns the
  effective permission set following the exact chain in Part 6: Owner
  short-circuit → StaffAssignment union (with `mode='read'` downgrade)
  → override application (deny wins). This is the server-side twin of
  `usePermissions()` + `resolveOwnershipDrivenPermissions()`.
- **`TenantAccessResolver`** — given `(user, tenant_id)`, returns
  boolean membership (Owner or effective StaffAssignment) — the
  server-side twin of `assertOwnershipTenantAccess()`.
- **`LocationAccessResolver`** — given `(user, tenant_id, location_id)`,
  returns boolean access, honoring the `branches.manage` all-locations
  override — the server-side twin of
  `branch-access.service.ts`/`assertOwnershipBranchAccess()`.
- **`RoleAssignmentService`** — encapsulates create/revoke/update for
  both `UserTenantRole` and `StaffAssignment`, enforcing: role_id is
  never `'owner'` for a `StaffAssignment`, revoke is soft (audit trail
  preserved), "move" operations are revoke+grant not in-place mutation
  (mirrors `MoveStaffAssignmentPayload`'s documented semantics in the
  frontend types).

### Recommended DRF permission class shape

```python
class HasTenantPermission(BasePermission):
    required_permission: str  # e.g. 'orders.manage'

    def has_permission(self, request, view):
        tenant_id = view.kwargs.get('tenant_id')
        resolver = PermissionResolver(request.user, tenant_id)
        if not resolver.is_tenant_member():
            raise TenantAccessDenied()
        if self.required_permission not in resolver.effective_permissions():
            raise PermissionDenied()
        return True
```

A location-scoped variant (`HasLocationPermission`) additionally checks
`LocationAccessResolver` before the permission check, per Part 4/8.

## 10. Frontend Integration Contract

**After login** (`login`/`verifyOTP` existing-user branch/`register`):
frontend stores `access`/`refresh` tokens (`localStorage`), `user`
(`useAuthStore`, in-memory only, not persisted — see
`docs/P10.9_AUTH_SESSION_HARDENING_AUDIT.md`), and if present,
`tenantRoles` → `useRbacStore.setTenantRoles(tenantId, roles)`. `staffAssignments`/`ownership` are not yet
wired into a dedicated store today (documented gap, see Part 13) but the
fields are already accepted by every call site's TypeScript type
(`AuthSessionRbacPayload`).

**After refresh** (browser reload → `AuthBootstrapper` → `GET
/auth/me/`): identical hydration to login — `setUser()` +
`setTenantRoles()` if `tenantRoles` present. The frontend does **not**
rely on `useRbacStore`'s localStorage persistence to reconstruct RBAC
state after a refresh — `getMe()`'s response is the sole source of
truth on every boot (P10.7's fix — see
`docs/P10.7_RBAC_SESSION_HYDRATION_IMPLEMENTATION.md`).

**After tenant switch** (`AdminTenantSwitcher.tsx`): no dedicated RBAC
re-fetch endpoint is called today — the frontend re-derives permissions
client-side from the already-loaded `tenantRoles` array (which may
contain entries for multiple tenants simultaneously) plus a fresh
ownership-resolution recompute, keyed off the newly active
`tenant.id`. `AdminTenantSwitcher` does call `queryClient.clear()` on
switch (confirmed in the P10.9 audit) to prevent any other
tenant-scoped React Query cache from leaking across the switch — RBAC
state itself is not React-Query-cached, so this doesn't affect
permissions specifically, only other tenant-scoped data.
**Recommendation for a future phase (not implemented here):** if a
user's `tenantRoles` array does not already contain an entry for the
newly-switched-to tenant (e.g. it was granted after their last full
session hydration), the frontend has no live path to discover that —
`GET /api/tenants/{tenant_id}/roles` (§6.2) combined with a
`GET /api/auth/me/permissions` (§6.1) refetch on tenant switch would
close this gap. This is a documented recommendation, not a change made
in this phase (see Migration Checklist).

**After role change** (an admin grants/revokes another user's role):
the frontend has **no realtime invalidation mechanism today** — the
affected user's `tenantRoles`/`staffAssignments` only refresh on their
next full session hydration (page reload, or their own next `getMe()`
call). This is a documented gap: a role change does not currently
invalidate anything for the *target* user's already-open session in
real time. See Migration Checklist item 3.

## 11. Tenant Isolation Rules

Restated concisely from Part 4/8 as a standalone checklist for backend
review:

- [ ] A request for Tenant A's data from a user who is neither Owner nor
      effective-Staff of Tenant A → `403 TENANT_ACCESS_DENIED`, always,
      regardless of what permission they hold at Tenant B.
- [ ] A request for Location A-3's data from a Staff member whose
      assignment only covers Location A-1/A-2 → `403
      LOCATION_ACCESS_DENIED`, even though they are a legitimate Tenant
      A member.
- [ ] An Owner's structural all-access grant is scoped to tenants they
      actually own (`tenants.owner_id`) — never a blanket "any tenant"
      grant. Verify `ownerOwnsTenant`-equivalent logic checks the
      specific tenant ID in the request, not just "is this user *an*
      owner of *something*."
- [ ] `branches.manage` permission grants all-locations read access
      *within the tenant the permission was resolved for* — it must not
      leak into a different tenant's locations even if the same user
      also holds `branches.manage` there (each tenant's grant is
      evaluated independently).
- [ ] Archived tenants (`status = 'archived'`) grant **zero** access to
      everyone, including the Owner — matches `isTenantEligible()`'s
      exact rule (Part 6). `trial`/`suspended`/`churned` are
      **NOT** included in this zero-access rule per the frontend's own
      documented scope limitation (P10.2.3 F-8 was scoped exactly to
      `'archived'`) — do not silently broaden this without a frontend
      decision, as it would deny access the current frontend still
      grants for those three statuses.

## 12. Django Implementation Notes (see also Part 9)

- Permission and Role tables are **fixed, code-owned data**, not
  freely-editable admin content — seed via migrations, gate creation/
  deletion of the 8 system roles and 48 permissions behind
  `is_staff`/superuser-only Django admin access if exposed there at all.
- `StaffAssignment.role_id` must never reference the `'owner'` role —
  enforce via a model-level `clean()`/`CheckConstraint`, not just
  serializer validation, since Owner access is granted structurally
  (Part 3) and a StaffAssignment row claiming `role='owner'` would be a
  data integrity bug with no code path that actually reads it that way.
- `PermissionResolver`'s Owner short-circuit must check
  `Owner.status == 'active'` — a suspended or pending-verification
  Owner grants zero permissions, exactly like an ineligible Staff
  member. This is not optional/best-effort; the frontend already treats
  it as absolute (`isOwnerEligible()`).
- Prefer materializing `effective_status` for `StaffAssignment` as a
  computed/annotated queryset property (or a scheduled job that syncs
  the stored `status` column from `valid_from`/`valid_until`) rather
  than only computing it in Python at check time — for admin-facing
  list views (`GET /api/tenants/{id}/staff-assignments/`) that need to
  filter/display "active" assignments efficiently at scale.

## 13. Migration Checklist

Documented gaps and recommendations for a **future** phase — nothing in
this list is implemented in this documentation-only phase, per the
task's explicit rule against redesigning frontend permissions:

1. **`ownership`/`staffAssignments` have no dedicated frontend store
   yet.** They are accepted by every auth call site's TypeScript type
   (`AuthSessionRbacPayload`) and available in the returned object, but
   nothing today writes them into a Zustand store the way `tenantRoles`
   is written into `useRbacStore`. `usePermissions()` currently
   recomputes ownership/staff-assignment-driven permissions via a
   **separate, synchronous, mock-data-only** code path
   (`resolveOwnershipDrivenPermissions()` in
   `ownership-resolution.service.ts`) rather than reading the
   `ownership`/`staffAssignments` fields the backend contract (Part 5)
   already sends. Wiring these together — so a real backend's
   `ownership`/`staffAssignments` payload actually drives
   `usePermissions()` instead of mock lookups — is the next real
   RBAC-migration implementation phase, not this one.
2. **No realtime role-change invalidation** (Part 10, "After role
   change"). A WebSocket or Server-Sent Events push, or at minimum a
   short-TTL polling refetch of `GET /api/auth/me/permissions`, would
   close this gap for already-open sessions.
3. **No tenant-switch RBAC refetch** (Part 10, "After tenant switch").
   `GET /api/tenants/{tenant_id}/roles` + `GET
   /api/auth/me/permissions` on switch would ensure a session that
   started before a new grant was issued still sees it without a full
   reload.
4. **Custom roles are out of scope.** The `roles.tenant_id` column in
   §2's schema is included as a forward-compatible nullable FK (a
   `NULL` tenant_id = system role, all 8 today), but no custom-role
   creation UI/API exists on the frontend yet — this document defines
   only the 8 system roles' contract. A prior phase
   (`docs/P10.5.5_...`) documented `customRoles` as "future UI-only
   data" — this remains true; do not build custom-role backend support
   speculatively ahead of frontend demand.
5. **`reviews.view`/`reviews.manage`** (Part 4) are reserved but unused
   — do not seed `role_permissions` rows for them until a frontend
   phase actually gates UI on them.
