### Invalidation Pattern Analysis

React Query `invalidateQueries({ queryKey: ['orders'] })` uses **prefix matching** — it invalidates ALL queries whose key starts with `['orders']`, including `['orders', 'tenant-samoon-01']`. This is an intentional React Query pattern, not a bug.

All mutation invalidations that use shorter keys are correct because:
1. Prefix matching ensures all tenantId-variants are invalidated
2. `qc.clear()` on tenant switch eliminates cross-tenant leakage
3. At any given time, only one tenant's data is in the cache

**Verdict**: No invalidation bugs. Pattern is intentional and functionally correct.

### ❌ Real Defect — Staff Service Missing Non-Samoon Mock Data

`staffService.getStaff(tenantId)` correctly filters by `tenantId`. However, `INITIAL_MOCK_STAFF` contains **only `tenant-samoon-01`** staff records. When an admin switches to any non-samoon tenant:
- `getStaff('tenant-brew-cafe-01')` → `[]`
- Admin staff management page → empty list
- No invites, no existing staff to display

This is a **real functional gap** (not a mock limitation) because:
1. The staff service is correctly structured to support multi-tenant (filtering exists)
2. P8.7.7.3/P8.7.7.4 established the pattern of adding mock records for each tenant
3. The admin staff page is functionally broken for any non-samoon tenant

**Fix**: Add minimal owner records for each non-samoon tenant in `staff.service.ts`.  
See [Section 7 — Fixes Applied](#7-fixes-applied).

## 10. Remaining Architectural Risks

### Risk 1: Global Mock Data (Low — Mock Limitation, Not Architecture)

Menu, orders, promotions, analytics, and reservations return the same global mock data for all tenants. React Query keys ensure cache isolation (each tenant fetches its own cache entry), but the underlying data is identical. This is an acceptable dev/mock limitation — in production, all these endpoints would be tenant-scoped server-side.

**Risk level**: Low. No security or correctness issue in mock mode. Would be fixed automatically by a real API.

### Risk 2: Legacy `branchService.getBranches()` Not Tenant-Scoped (Low)

`branchService.getBranches()` from `combined.service.ts` returns all `MOCK_BRANCHES` (the original global legacy branches). Used by `BranchSelector.tsx` (customer header branch picker), `/reservation`, and `/console/reservations`. Query key `['branches', tenantId]` isolates cache per tenant but all tenants get the same 5 branches.

**Risk level**: Low. Legacy hook is not used in the new `[tenantSlug]/[branchSlug]` experience. New branch resolution uses `usePublicBranch()` and `useAdminBranches()`. This hook can be deprecated in favor of these in a future phase.

### Risk 3: `useFeaturedItems` Uses Global Key (Low — Intentional)

`['featured-items']` has no tenantId. Featured items are the same for all tenants in mock mode. This is intentional for the public discovery experience.

**Risk level**: Low. Would be tenant-scoped in production.

### Risk 4: Loyalty Service Single-Account Mock (Low — Demo Limitation)

`loyaltyService` operates on a hardcoded `mockAccount.id: 'loyalty-account-mock-1'`. All tenants share the same mock loyalty account. Query keys include `tenantId` so cache is isolated, but the data is from one account.

**Risk level**: Low. Loyalty is user+tenant-scoped in production. Mock limitation only.
