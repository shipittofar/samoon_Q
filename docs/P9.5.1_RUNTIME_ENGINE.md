# P9.5.1A — Platform Localization Runtime Engine

> Implementation phase. Builds the actual runtime designed (but not built)
> in P9.5.0's six architecture documents. Scope: the engine only — language
> resolution, fallback, RTL, formatting, dynamic loading, and a developer
> hook API wrapping (never replacing) `next-intl`. No UI, no Translation
> Center, no Language Management screen, no app-wide migration, no routing
> change. 100% backward compatible: every existing route, URL, and
> `next-intl` call site keeps working unmodified.
>
> Last updated: 2026-07-05

---

## 1. What shipped

| File | Role |
|---|---|
| `src/i18n/language-registry.ts` | Single per-language metadata table — the 6 initially-enabled languages (en, fa, ar, zh, it, tr), their BCP 47 id, direction, fallback locale, plural-rule locale, default currency/timezone, and whether a real translation file exists yet. |
| `src/i18n/runtime.ts` | The Localization Runtime Service — pure functions, no React, safe on server and client. Language/locale/fallback resolution, RTL detection, dynamic message loading with fallback, the missing-translation handler, and the `Intl.*`-backed formatting runtime. |
| `src/i18n/request.ts` | Rewritten to call into `runtime.ts` instead of its own hardcoded `['en', 'fa', 'ar']` array and manual `import()` — same `next-intl` `getRequestConfig()` shape, now also wires `onError`/`getMessageFallback`. |
| `src/i18n/hooks.ts` | The developer API (Phase J) — `useLanguage`, `useLocale`, `useDirection`, `useTranslation`, `useFormatter`, `useLocalizedDate`, `useLocalizedNumber`, `useLocalizedCurrency`. Thin wrappers; `useTranslation`/`useFormatter` delegate straight to `next-intl`. |
| `src/config/modules/languages.ts` | Extended (not replaced) — `languages.supported`/`languages.rtl_locales` defaults now generated from the registry (6 languages instead of 3); still the Configuration-driven source of truth for which locales are enabled. |
| `src/stores/index.ts`, `src/providers/index.tsx`, `Header.tsx`, `TenantHeader.tsx` | The 4 remaining hardcoded-locale call sites found in `P9.5.0_LOCALIZATION_AUDIT.md` — each now calls `runtime.ts`'s `getDirection`/`resolveSupportedLocales`/`getLanguageInfo` instead of a literal `['fa', 'ar']` array or `LANGUAGES` constant. |
| `src/test/p9-5-1a-localization-runtime.test.ts` | 32 new regression tests across all six required areas (below). |

## 2. Architecture

```
                     ┌─────────────────────────────┐
                     │ src/config/modules/languages │  ← Configuration Service
                     │  languages.supported          │    (platform/tenant
                     │  languages.default             │     override chain,
                     │  languages.rtl_locales         │     unchanged from P9.0)
                     └──────────────┬────────────────┘
                                    │ resolveField()
                     ┌──────────────▼────────────────┐
                     │  src/i18n/runtime.ts           │  ← the new engine
                     │  resolveSupportedLocales()      │
                     │  resolveDefaultLocale()         │
                     │  resolveRTLLocales/isRTLLocale   │
                     │  resolveFallbackChain()          │
                     │  resolveRequestLocale()          │
                     │  loadMessages()                  │
                     │  format*() (Intl.*)              │
                     └───┬───────────────┬─────────────┘
                         │               │
        ┌────────────────▼───┐   ┌───────▼─────────────┐
        │ src/i18n/request.ts  │   │ src/i18n/hooks.ts     │
        │ (server, next-intl   │   │ (client, wraps         │
        │  getRequestConfig)   │   │  next-intl hooks)       │
        └───────────────────────┘   └─────────────────────────┘
                         │               │
                 ┌───────▼───────────────▼────────┐
                 │ existing next-intl call sites    │
                 │ useTranslations()/t() — unchanged │
                 └───────────────────────────────────┘

        ┌─────────────────────────────────────┐
        │ src/i18n/language-registry.ts         │  ← static per-language facts
        │ (native name, direction, currency,     │    (not Configuration-driven —
        │  timezone, fallback, hasMessages)       │    same role countries-
        └─────────────────────────────────────┘    registry-data.ts plays)
```

Two data sources, on purpose (mirrors the Countries pattern, P9.2): the
*enabled/default/RTL lists* are Configuration-driven (overridable per
platform/tenant, audited, versioned) via `languages.ts`; the *per-language
facts that never need a per-tenant override* (a language's own native name,
direction, plural rules) live in the static `language-registry.ts` table.
Collapsing these into one collection is P9.5.1B's job (the full 18-property
`localization.languages` schema `P9.5.0_LOCALIZATION_ARCHITECTURE.md`
already designed) — this phase deliberately keeps the smaller, faster
6-language table so the runtime engine can ship without waiting on that
UI-facing collection work.

## 3. Runtime flow (a single request)

1. **`src/i18n/request.ts`** runs per request (`getRequestConfig()`, unchanged
   `next-intl` mechanism). It reads the `NEXT_LOCALE` cookie and
   `Accept-Language` header, same as before.
2. **`resolveRequestLocale()`** (Phase I) applies the priority chain:
   explicit override (not wired to a URL param in this phase — no routing
   change — but the function already accepts one for P9.5.1B) → cookie →
   parsed `Accept-Language` primary tag → `languages.default` (Configuration)
   → `'en'`. Every candidate is checked against `resolveSupportedLocales()`
   so a disabled/removed language can never be selected mid-flight.
3. **`loadMessages(locale)`** (Phase D/E) does one dynamic
   `import(`./locales/${locale}.json`)` — same code-splitting behavior as
   before. If that file doesn't exist (zh/it/tr today), it walks
   `resolveFallbackChain(locale)` (registry `fallbackLocale` → platform
   default → `'en'`) until a file resolves, and logs a
   `missing-namespace` event (Phase F) rather than throwing.
4. `next-intl`'s `getMessageFallback`/`onError` hooks (Phase F) catch any
   individual missing *key* within an otherwise-loaded bundle and log a
   `missing-key` event, rendering `namespace.key` instead of a blank string
   — matching `next-intl`'s own existing default, now also observable via
   `getMissingTranslationLog()`.
5. Client-side, `src/i18n/hooks.ts` and the updated stores/components read
   the same `runtime.ts` functions for direction, formatting, and the
   language switcher's option list — no separate client-side data path.

## 4. Backward compatibility

- `next-intl`'s `getRequestConfig()` return shape is unchanged (`{ locale,
  messages }`, now with two optional callbacks next-intl already supports).
- Every `useTranslations()`/`t()` call site in the app is untouched.
- The 3 existing translation files (`en.json`, `fa.json`, `ar.json`) are
  untouched — no migration, no reformat.
- `languages.supported`'s **default** grew from 3 to 6 entries, but this is
  additive: `en`/`fa`/`ar` keep their exact prior values/positions, and a
  platform/tenant that had already overridden `languages.supported` to a
  custom list keeps that override untouched (Configuration inheritance,
  P9.0, unchanged).
- All 87 existing test files / 5547 existing tests pass unmodified (verified
  before and after this phase's changes).

## 5. Performance impact

- **No change** to the one-language-per-request invariant
  (`P9.5.0_PERFORMANCE_STRATEGY.md` §1) — `loadMessages()` still issues
  exactly one `import()` per request in the common case (en/fa/ar), or two
  in the worst case (a `hasMessages: false` language falling back to `en`'s
  already-tiny bundle). Never more than one language's messages are held in
  memory for a given request.
- `resolveSupportedLocales()`/`resolveSupportedLocales()`-adjacent calls go
  through `configurationService.resolveField()`, which is already cached
  per-field (`configurationCache`, P9.0) — no new per-request cost beyond
  what every other Configuration read already pays.
- Formatting functions (`formatNumber`/`formatDate`/etc.) are direct
  `Intl.*` constructor calls with no memoization added in this phase — Intl
  object construction is cheap relative to the request, and premature
  caching would be optimizing before measuring (`P9.5.0_PERFORMANCE_STRATEGY.md`
  §10's own stated principle).

## 6. Bundle-size impact

- `language-registry.ts` adds one small static array (6 objects, no assets)
  to whatever chunk imports it — negligible (<1KB).
- `runtime.ts` and `hooks.ts` are plain functions; `hooks.ts` is `'use
  client'` and only pulled into client bundles that actually import from
  `@/i18n/hooks` (none of the existing pages do yet in this phase — it's an
  additive API for new call sites, per the phase's "wrap, don't replace"
  constraint).
- No new translation JSON files were added — zh/it/tr ship with **zero**
  message-bundle weight until a real translation file is authored, by
  design (they fall back to the already-loaded `en.json`).
- Net bundle delta: two new small modules (~3KB combined, uncompressed,
  before minification/treeshaking) plus a few line-level edits to 4
  existing files. No new dependencies were added — everything routes
  through `Intl.*` (built into the JS runtime) and `next-intl` (already a
  dependency).

## 7. Future work — P9.5.1B

- Replace the static `language-registry.ts` table with the full
  `localization.languages` **collection** (`P9.5.0_LOCALIZATION_ARCHITECTURE.md`
  §2) — 150+ rows, `configCollection` helpers, Console-editable, the two
  lifecycle axes from `P9.5.0_LANGUAGE_LIFECYCLE.md`.
- Wire an actual Translation Keys store
  (`localization.translation_keys`, `(namespace, key, language)` triples)
  behind `loadMessages()` instead of static JSON imports, per
  `P9.5.0_TRANSLATION_ARCHITECTURE.md`.
- Namespace-level code splitting (`P9.5.0_PERFORMANCE_STRATEGY.md` §4) —
  today's `loadMessages()` still loads all 12 namespaces together per
  locale, matching current behavior; splitting per-namespace requires
  touching how `next-intl`'s `messages` object is assembled, deferred here.
- Build the Language Management Console UI (Platform-only, per
  `P9.5.0_LANGUAGE_LIFECYCLE.md` §6) and the Translation Center — both
  explicitly out of scope for this phase.
- Decide and implement the URL strategy
  (`P9.5.0_DEVELOPER_GUIDE.md` §5) — `resolveRequestLocale()`'s
  `explicitLocale` parameter exists specifically so a P9.5.1B router can
  plug in without another shape change to this engine.
- Author real `zh.json`/`it.json`/`tr.json` translation files (a content
  task, not an architecture one) — until then, the Missing Translation
  Handler's fallback-to-English behavior is the intended, working state for
  those 3 languages.
