# P8.9.6 — Platform Customer Identity & Business Relationship Architecture: Audit

## Scope

Full audit of the current customer model as delivered at end of P8.9.5.1. Covers: type definitions, mock data, services, hooks, stores, pages, and every cross-cutting assumption about customer ownership. Identifies every location where a customer is incorrectly scoped to a tenant rather than modeled as a platform-wide identity.

Audit date: post-P8.9.5.1 (console namespace migration complete, 5063/5063 tests passing).

---

## Section 1 — Current Type Model

### 1.1 `User` (`src/types/index.ts` line 8)

The base identity type. Completely platform-wide; zero tenant or branch scoping.

```typescript
export interface User {
  id: string
  email: string
  phone?: string
  first_name: string
  last_name: string
  avatar?: string
  role: UserRole          // 'customer' | 'staff' | 'admin'
  is_verified: boolean
  created_at: string
}
```

**Finding:** `User` is correctly modeled as platform-wide. A customer who orders from two different restaurant brands has exactly one `User` record. This is architecturally correct. No changes to this type are needed.

---

### 1.2 `AdminCustomer` (`src/types/index.ts` line 834)

Admin-extended view of a customer. Extends `User` with aggregated commerce metrics.

```typescript
export interface AdminCustomer extends User {
  order_count: number
  total_spent: number
  avg_order_value: number
  tier: AdminCustomerTier   // 'new' | 'regular' | 'vip'
  last_order_at?: string
}
```

**Critical finding — metrics are unscoped:** `order_count`, `total_spent`, `avg_order_value`, and `tier` carry no `tenant_id` or `branch_id`. It is impossible to determine from this type whether these numbers represent:
- All orders across the entire platform (cross-tenant total)
- All orders at this tenant only (the correct semantic for a business owner)
- All orders at a specific branch only (the correct semantic for a branch manager)

This is the core architectural defect. A restaurant owner looking at their customer list sees aggregate numbers that may include orders the customer placed at a completely unrelated business on the same platform.

---

### 1.3 `AdminCustomerStats` (`src/types/index.ts` line 843)

Per-customer stats returned by the stats endpoint.

```typescript
export interface AdminCustomerStats {
  customer_id: string
  order_count: number
  total_spent: number
  avg_order_value: number
  favorite_item?: string
  last_order_at?: string
}
```

**Critical finding:** Same unscoped aggregation problem. No `tenant_id` or `branch_id`. The `favorite_item` field references a menu item ID with no tenant context — a customer's favorite item at one business could be returned when viewing them in a completely different business's admin panel.

---

### 1.4 `AdminCustomerFilters` (`src/types/index.ts` line 900)

Filter parameters for `getCustomers()`.

```typescript
export interface AdminCustomerFilters {
  tier?: AdminCustomerTier
  search?: string
  page?: number
  page_size?: number
}
```

**Critical finding:** No `tenant_id` or `branch_id` filter. The filter type assumes the tenant context is either implicit (from auth headers) or does not exist. Tier filtering across tenants is meaningless — a "VIP" customer at one restaurant may be a first-time customer at another.

---

### 1.5 `LoyaltyAccount` (`src/types/index.ts` line 526)

```typescript
export interface LoyaltyAccount {
  id: string
  userId: string
  points: number
  lifetimePoints: number
  tier: LoyaltyTier
  tierExpiresAt?: string
  createdAt: string
  updatedAt: string
}
```

**Critical finding:** `userId` references the platform `User.id`. There is no `tenantId`. This means loyalty is currently modeled as a single global account per user — points earned at Coffee Roasters would count toward a customer's tier at Savor Restaurant. This violates the fundamental principle that loyalty programs are per-business.

---

### 1.6 `LoyaltyTransaction` (`src/types/index.ts` line 539)

```typescript
export interface LoyaltyTransaction {
  id: string
  accountId: string          // references LoyaltyAccount.id
  type: LoyaltyTransactionType
  points: number
  description: string
  createdAt: string
  referenceId?: string       // order or reward ID
}
```

**Finding:** No `tenantId` or `branchId`. Transactions inherit the same unscoped problem from `LoyaltyAccount`.

---

### 1.7 `Order` (`src/types/index.ts` line 169)

```typescript
export interface Order {
  id: string
  order_number: string
  user?: User                // optional customer reference
  branch_id: string          // required branch scoping
  branch?: Branch
  items: OrderItem[]
  // ... payment, status, totals fields
}
```

**Finding — indirect tenant scoping only:** `branch_id` provides implicit tenant scoping (every branch belongs to exactly one tenant), but this relationship is not traversed in any customer-facing service. There is no `tenant_id` field, and no service resolves `branch_id → tenant_id` when assembling a customer's order history. The `user` field is optional and absent in the current mock data.

---

### 1.8 `Reservation` (`src/types/index.ts` line 206)

```typescript
export interface Reservation {
  id: string
  user?: User                // optional customer reference
  branch_id: string          // required
  branch?: Branch
  date: string; time: string; guests: number
  name: string               // denormalized — can exist without a user account
  phone: string
  email?: string
  status: ReservationStatus
  created_at: string
}
```

**Finding:** Same indirect scoping via `branch_id`. Denormalized `name` / `phone` / `email` fields allow walk-in reservations without a platform account, but there is no link back from the `User` to all their reservations across the platform.

## Section 2 — Current Service Layer

### 2.1 `adminService` customer methods (`src/services/admin.service.ts`)

| Method | Signature | Tenant-aware? |
|---|---|---|
| `getCustomers(filters)` | `→ PaginatedResponse<AdminCustomer>` | No — no `tenantId` param |
| `getCustomer(id)` | `→ AdminCustomer` | No |
| `getCustomerStats(id)` | `→ AdminCustomerStats` | No |
| `getCustomerReviews(id)` | `→ Review[]` | No |

**Mock filter logic (`applyCustomerFilters`):** Filters by `tier` and `search` only. No tenant filtering. All 5 mock customers are returned regardless of which tenant is active.

**Backend endpoints** (`src/services/endpoints.ts`):
```
CUSTOMERS:       '/admin/customers/'
CUSTOMER_DETAIL: (id) => `/admin/customers/${id}/`
CUSTOMER_STATS:  (id) => `/admin/customers/${id}/stats/`
```

**Finding:** Endpoints are at `/admin/customers/` with no tenant slug in the URL path. Backend filtering by tenant would have to happen implicitly via auth token. There is no way for the frontend to explicitly request "customers of tenant X" — the tenant context is assumed to be carried by authentication, not the request URL.

---

### 2.2 No `customer.service.ts` exists

All customer operations are embedded inside `admin.service.ts`. There is no dedicated customer service module. The `User` type is used as both the authenticated user (staff/admin context) and the customer identity, with no separation.

---

### 2.3 `loyaltyService` (`src/services/loyalty.service.ts`)

Mock maintains a single global `mockAccount` object:
```typescript
const mockAccount: LoyaltyAccount = {
  id: 'la-001',
  userId: 'user-mock-1',
  points: 1240,
  lifetimePoints: 5820,
  tier: 'gold',
  // ...
}
```

No tenant ID. One loyalty account globally per user. Points accumulate across all businesses on the platform.

## Section 3 — Current Hook Layer

### 3.1 Customer hooks (`src/hooks/index.ts`)

| Hook | Query key | Enabled condition | Tenant-aware? |
|---|---|---|---|
| `useAdminCustomers(filters)` | `['admin-customers', tenantId, filters]` | `!!tenantId` | Cache key only — mock data ignores tenantId |
| `useAdminCustomer(id)` | `['admin-customer', id]` | always | No |
| `useAdminCustomerStats(id)` | `['admin-customer-stats', id]` | always | No |
| `useAdminCustomerReviews(id)` | `['admin-customer-reviews', id]` | always | No |
| `useBulkExportCustomers()` | — | — | No |

**Critical finding:** `useAdminCustomers` is `enabled: !!tenantId` — it correctly requires an active tenant before loading customers. The React Query cache key includes `tenantId`, so switching tenants invalidates the cache correctly. **However,** the actual `adminService.getCustomers()` call does not pass `tenantId` to the API or mock filter. The tenant gating is cosmetic — the same 5 customers are returned for every tenant.

## Section 4 — Current Mock Data

### 4.1 Mock customers (5 records in `admin.service.ts`)

```
u1 — Alice Johnson    | vip     | 14 orders | $420.50
u2 — Bob Smith        | regular |  6 orders | $180.00
u3 — Carol Davis      | vip     | 22 orders | $890.75
u4 — David Wilson     | new     |  1 order  |  $29.99   (unverified)
u5 — Emma Brown       | vip     | 18 orders | $650.00
```

**Findings:**
- All 5 records have no `tenant_id`. They represent a single global pool.
- All 5 have no `branch_id`. Branch history is not modeled.
- No cross-business relationships. A customer who visits both a restaurant and a bar managed on the same platform cannot be represented.
- 5 customers is insufficient to test any analytics, cohort analysis, or relationship-based views.

### 4.2 Mock orders (`src/lib/mock-data.ts`)

- 2 orders (`ord-001`, `ord-002`). Neither has `user` populated.
- Cannot link an order to a customer from the current mock data.
- Cannot build "this customer's orders" from the current data model.

### 4.3 Mock loyalty (single account)

- 1 loyalty account globally (`userId: 'user-mock-1'`). Not linked to any of the 5 `AdminCustomer` mock records (different ID).
- 0 loyalty accounts for the other 4 mock customers.

### 4.4 Scale deficit

The current mock has 1 tenant active at a time, 5 global customers, 2 orders, 1 reservation, 1 loyalty account. It cannot represent:
- A customer who orders from 2 different businesses
- A business with 50+ customers for realistic list/analytics UX
- Per-branch customer frequency data
- Cross-business loyalty independence

## Section 5 — Current Page Inventory

### 5.1 `/console/customers` (list page)

- Renders all customers from `useAdminCustomers(filters)`.
- Filters: tier (all / vip / regular / new), search string.
- Columns: Customer (name + avatar + verified badge), Contact (email + phone), Orders, Total Spent, Avg Order, Joined, Tier.
- **No branch column.** A restaurant chain with 5 branches cannot see which branch a customer prefers.
- **No last-visit column.** No recency data.
- Bulk export available (CSV: id, name, email only — spend/order data not exported).

### 5.2 `/console/customers/[id]` (detail page)

- Profile header: name, avatar, tier badge, verified status, email, phone, join date.
- 4 stat cards: Total Orders, Total Spent, Avg Order Value, Customer Tier.
- Activity summary: favorite item, last order date, order count.
- Quick Links: `/console/orders?search=<email>` and `/console/reservations?search=<email>`.

**Critical finding — cross-tenant data leak risk:** The "View Orders" quick link searches orders by email across the entire orders list. If the backend does not filter by tenant, a business owner viewing a customer detail could see orders the customer placed at a competitor on the same platform. This is a security concern in production.

**Critical finding — no branch breakdown:** A customer who visits the Downtown branch 10 times and the Airport branch once is shown as a single aggregate. Branch managers have no visibility into branch-specific customer behavior.

### 5.3 `/console/customers/[id]/reviews` (reviews page)

- Shows all reviews by this customer.
- No tenant scoping — shows reviews across all businesses if backend doesn't filter.

## Section 6 — Architecture Gap Summary

### 6.1 Missing domain models

| Missing type | Purpose | Current substitute |
|---|---|---|
| `PlatformUser` | Platform-wide customer identity (phone-first) | `User` (partial) |
| `BusinessCustomer` | Customer's relationship to one tenant | `AdminCustomer` (conflated) |
| `BranchCustomer` | Customer's relationship to one branch | Absent |

The current `AdminCustomer` conflates the platform identity with tenant-scoped metrics. These must be separated.

### 6.2 Missing tenant scoping on loyalty

| Concern | Current | Required |
|---|---|---|
| Loyalty points | Global per user | Per tenant per user |
| Loyalty tier | Global | Per tenant |
| Loyalty rewards | Global | Per tenant |
| Loyalty analytics | Global aggregate | Per tenant aggregate |

### 6.3 Missing customer lifecycle events

Currently there is no `BusinessCustomer` creation trigger. In the target model, a `BusinessCustomer` record should be created only on first interaction (order, reservation, QR scan, or payment) — not on account creation. The current model has no concept of "first interaction" at all.

### 6.4 Role-based customer visibility

| Role | Should see | Currently sees |
|---|---|---|
| Owner / Admin | All customers of their tenant, with per-branch breakdowns | All 5 global mock customers, no branch breakdown |
| Branch Manager | Customers of their active branch | Same 5 global mock customers |
| Cashier / Waiter | Not applicable (no customer list access) | N/A |
| Platform Admin | All PlatformUsers + all BusinessCustomer relationships across all tenants | Not implemented |
| Support | PlatformUser detail + their BusinessCustomer relationships | Not implemented |

### 6.5 Missing cross-navigation

- No link from customer detail → their loyalty account (tenant-specific).
- No link from order detail → customer detail.
- No link from reservation detail → customer detail.
- Customer quick links use email search rather than ID join — fragile and cross-tenant.

## Target Architecture (to be implemented in P8.9.6 Phases B–M)

```
PlatformUser (1)
  └── BusinessCustomer (many — one per tenant where they've interacted)
        ├── loyaltyPoints: number       ← per-tenant, not global
        ├── loyaltyTier: LoyaltyTier   ← per-tenant
        ├── totalSpent: number          ← at this tenant only
        ├── ordersCount: number         ← at this tenant only
        └── BranchCustomer (many — one per branch within this tenant)
              ├── visits: number
              ├── lastVisit: string
              └── favoriteBranch: boolean
```

**Key invariants:**
1. A `PlatformUser` is created once at account creation. It is never duplicated.
2. A `BusinessCustomer` is created only on first interaction (order, reservation, QR scan, or payment) at a tenant. It is never pre-created.
3. A `BranchCustomer` is created only on first branch-level interaction. It is never pre-created.
4. Loyalty points, tier, and rewards are scoped to `BusinessCustomer` — completely independent per business.
5. A business owner can only see `BusinessCustomer` records for their own tenant. They cannot see records from other tenants.
6. Platform Admin can see `PlatformUser` records and navigate to all associated `BusinessCustomer` relationships across all tenants.
7. All commerce aggregates on `BusinessCustomer` (`totalSpent`, `ordersCount`, `reservationsCount`) represent activity at that tenant only.
