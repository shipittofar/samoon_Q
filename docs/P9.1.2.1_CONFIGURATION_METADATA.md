# P9.1.2.1 — Configuration Metadata & UI Readiness

> Prepares `PlatformConfigurationRegistry` for a future Console: every
> field can now optionally carry enough metadata to render, validate,
> gate, wire up dependencies for, and be found in search — automatically,
> without page-specific code. **No UI was built in this phase.** No
> resolver, validator, cache, audit, or service logic reads any of the new
> metadata — it is purely descriptive, consumed by nothing yet.
>
> Last updated: 2026-07-04

---

## 1. Phase A — Audit: what was missing

Before this phase, `ConfigFieldDefinition` (`src/config/types.ts`) already
satisfied Rule 5 (every field has metadata) for the concerns P9.0 designed
around: `id`, `title`, `description`, `helpText`, `placeholder`, `category`,
`type`, `default`, `validation`, `visibility`, `permissions`, `preview`,
`inheritance`, `audit`, `version`, `lifecycle`. Reviewing all 70 fields
across the 15 registered modules against what an enterprise configuration
console (Shopify's `settings_schema.json`, Auth0's tenant dashboard, Vercel's
project settings) actually needs to render itself surfaced five categories
of missing metadata:

| Gap | Consequence without it |
|---|---|
| No organizational metadata beyond `category` (no `subcategory`, `icon`, `displayOrder`, `group`, `badge`, `tags`) | A Console could list fields but not lay them out, order them, or visually group related fields within a section — every settings page would need hand-tuned layout code per module. |
| No rendering hint distinct from `type` | `type: 'number'` doesn't say whether a field wants a bare number input or a slider; `type: 'string'` doesn't say text vs. textarea vs. secret input. Every Console field would need a hardcoded `switch` statement per field id — exactly the "no hardcoded forms" outcome this phase exists to prevent. |
| No governance/risk metadata beyond `permissions`/`audit` | A Console has no way to know a field is dangerous enough to warrant a confirmation dialog, requires an approval workflow, or needs a restart to take effect — every module author would have to communicate this out-of-band (Slack, a wiki page) instead of it being queryable. |
| No dependency metadata | A Console can't show/hide/disable one field based on another's value without hand-written per-field logic (e.g. hiding OTP fields when `authentication.otp.enabled` is false) — exactly the kind of per-page logic Rule 7 forbids. |
| No search metadata | A "search all settings" Console feature (standard in Shopify, Stripe, Auth0 dashboards) would have nothing to rank or match against beyond `title`/`description` substring matching. |

No existing behavior was wrong — P9.0/P9.0.1/P9.1.x's metadata was complete
for what had been built so far (resolution, validation, audit). This phase
extends it forward for what hasn't been built yet (the Console).

## 2. The field metadata model

Every addition in this phase is an **optional** top-level property on
`ConfigFieldDefinition`, grouped into five named blocks so a 20-property
flat object doesn't become unreadable:

```ts
interface ConfigFieldDefinition<T> {
  // ...existing P9.0/P9.0.1 fields, unchanged...
  uiControl?: ConfigUIControlType        // Phase C
  display?: ConfigFieldDisplayMeta       // Phase B
  governance?: ConfigFieldGovernanceMeta // Phase D
  dependency?: ConfigFieldDependencyMeta // Phase F
  search?: ConfigFieldSearchMeta         // Phase G
}
```

Because every one of these — and every property inside them — is optional,
**all 70 pre-existing field registrations remain valid, byte-for-byte,
with zero edits required.** `defineField()` (`src/config/field.ts`) needed
no changes either: its type signature already generically accepts any
optional property `ConfigFieldDefinition` declares, since it's built from
`Partial<Omit<ConfigFieldDefinition<T>, 'inheritance' | 'audit' | 'preview'>>`.

### Phase B — `ConfigFieldDisplayMeta`

```ts
interface ConfigFieldDisplayMeta {
  displayName?: string        // short label when `title` is too long for compact UI
  subcategory?: string        // finer grouping within `category`
  icon?: string                // lucide-react name, same convention as ADMIN_NAV_ICON_MAP
  displayOrder?: number        // sort position within its section
  group?: string                // cross-section visual grouping
  badge?: string                // e.g. "New", "Recommended"
  tags?: string[]
  documentationLink?: string
  previewComponent?: string    // named Console component for fields ConfigFieldPreview.kind can't express
  exampleValue?: unknown        // guidance value, distinct from `default` and `placeholder`
  defaultExplanation?: string  // prose on *why* the default is what it is
}
```

Example (`src/config/modules/authentication.ts`):

```ts
display: { icon: 'ShieldAlert', displayOrder: 1, badge: 'Kill Switch',
  defaultExplanation: 'Left on so the platform is usable out of the box; flipping it off is an explicit, audited, reason-required action.' }
```

### Phase C — `uiControl: ConfigUIControlType`

A closed enum, not a nested object — it's a single rendering hint:

```
text | textarea | number | slider | switch | checkbox | radio
| country_selector | language_selector | color_picker | font_selector
| json_editor | secret_input | otp_provider_picker | timezone_picker
| currency_picker | file_upload | table_editor
```

`uiControl` is deliberately **distinct from `type`** (the value's data
shape). A `'boolean'`-typed field is usually `'switch'` but could be
`'checkbox'` in a dense table layout; a `'number'`-typed field might be
`'number'` (bare input) or `'slider'` (bounded, continuous) depending on
its `validation.min`/`max`/`step`. When `uiControl` is omitted, a future
Console falls back to a default purely from `type`:

| `type` | Default control when `uiControl` omitted |
|---|---|
| `string` | `text` |
| `number` | `number` |
| `boolean` | `switch` |
| `select` | `radio` (small option count) or a dropdown (large) |
| `multi-select` | checkbox list |
| `color` | `color_picker` |
| `font` | `font_selector` |
| `json` / `object` / `array` | `json_editor` |
| `password` / `secret` | `secret_input` |
| `country` | `country_selector` |
| `language` | `language_selector` |
| `feature_flag` | `switch` |
| `permission` | radio/dropdown over the RBAC permission catalog |

Every control type in the enum is exercised by at least one real field in
this phase (`switch`, `slider`, `radio`, `color_picker`, `file_upload`,
`font_selector`, `country_selector`, `language_selector`, `secret_input`,
`currency_picker`, `table_editor` — see the module diffs in
`src/config/modules/*.ts`), except `textarea`, `checkbox`,
`otp_provider_picker`, `timezone_picker`, and `json_editor`, which have no
naturally-fitting field yet (no long-text field, no provider-selection
field per `docs/P9.1.1_PROVIDER_ARCHITECTURE.md` §3's still-unregistered
`authentication.otp_provider`, no timezone-specific field). They remain
valid enum members for the first field that needs them — not spurious.

## 3. Permission (governance) model

```ts
interface ConfigFieldGovernanceMeta {
  editableBy?: string[]      // narrower than permissions.edit alone
  visibleTo?: string[]        // narrower than permissions.view alone
  auditLevel?: 'none' | 'basic' | 'detailed' | 'forensic'
  securityLevel?: 'low' | 'medium' | 'high' | 'critical'
  requiresApproval?: boolean
  requiresRestart?: boolean
  requiresPublish?: boolean
  runtimeReloadable?: boolean
  dangerous?: boolean
  experimental?: boolean
  beta?: boolean
  internalOnly?: boolean
}
```

This is **additive** to, never a replacement for, the existing
`permissions: { view, edit }` (RBAC gate) and `audit: { trackHistory,
requireReason, sensitive }` (write-time audit behavior) — both remain the
enforced mechanisms; `governance` is Console-facing risk communication.
`securityLevel` and `auditLevel` are deliberately separate axes: a field
can be `securityLevel: 'critical'` (a Console should visually flag it) while
`audit.sensitive` stays `false` (its value isn't a secret needing
redaction) — `payments.stripe_secret_key` is the inverse case: `sensitive:
true` (redacted in the audit trail) *and* `governance.securityLevel:
'critical'` (visually flagged in the Console) — the two properties agree
here but are not the same mechanism and can diverge.

`dangerous: true` (e.g. `authentication.enabled`,
`authentication.demo_login_enabled`,
`authentication.mock_authentication_enabled`,
`payments.stripe_secret_key`) is the signal a future Console uses to insert
a confirmation step before a write — no such step is implemented in this
phase; `ConfigurationService.updateField()`'s existing `requireReason`
enforcement (P9.0) remains the only *enforced* friction today.

## 4. Dependency model

```ts
interface ConfigFieldCondition {
  fieldId: string
  equals?: unknown
  notEquals?: unknown
  in?: unknown[]
}

interface ConfigFieldDependencyMeta {
  dependsOn?: string[]
  enabledWhen?: ConfigFieldCondition
  hiddenWhen?: ConfigFieldCondition
  conflictsWith?: string[]
  requires?: string[]
  mutuallyExclusive?: string[]
}
```

A future Console reads `hiddenWhen`/`enabledWhen` to show/hide or
enable/disable a control **without any per-field UI code** — the condition
references another field's *resolved* value (via
`ConfigurationService.resolveField()`, already built), not a raw override.
Example chain registered in this phase
(`src/config/modules/authentication.ts`): every OTP field's `hiddenWhen`
points at `authentication.otp.enabled`, and `authentication.otp.enabled`
itself is `hiddenWhen` the platform-wide `authentication.enabled` — a
future Console renders the whole OTP section hidden the moment the master
switch is off, purely by walking this metadata, never by hardcoding "if
this section, check that field."

`requires`/`conflictsWith`/`mutuallyExclusive` are documentation-strength
only in this phase — `authentication.demo_login_enabled.dependency.requires
= ['authentication.mock_authentication_enabled']` communicates the real
runtime relationship established in P9.1.2 (`demoLoginEnabled()` is only
meaningful when `mockActive()` is true) as queryable data, but no validator
enforces it — `ConfigurationValidator.registerRule()` remains the
mechanism for that if it's ever needed, and would read this same metadata
rather than duplicating the field-id list.

## 5. Search model

```ts
interface ConfigFieldSearchMeta {
  keywords?: string[]
  aliases?: string[]
  searchWeight?: number
  favorite?: boolean
  recent?: boolean
  popular?: boolean
}
```

Not consumed by any implementation in this phase. The intended future
consumer: a global "search all configuration" Console feature that indexes
every field's `title` + `description` + `search.keywords` +
`search.aliases`, ranked by `search.searchWeight`, so a Platform
Administrator can type "brute force" and land on
`authentication.max_login_attempts` even though neither the id nor the
title contains that phrase (its `search.keywords` does — see the module
file). `favorite`/`popular` are platform-wide curation flags, distinct
from any future per-administrator personal-favorites feature (not modeled
here — that would be user-scoped state, not module-registered metadata).

## 6. Rendering philosophy — why this and not a competing approach

Two alternatives were considered and rejected:

- **A separate "UI schema" registry parallel to `PlatformConfigurationRegistry`.**
  Rejected — this is exactly the "duplicated concept" anti-pattern
  `docs/PLATFORM_ARCHITECTURE_PRINCIPLES.md` §17 warns against. A field's
  rendering metadata is metadata *about that field*, not a second field
  describing the first.
- **Per-module React components hand-built to render each section.**
  Rejected — this is what P9.0's Rule 7 ("UI is generated") exists to
  prevent; it would mean every new module (P9.1.15+ per
  `docs/PLATFORM_ROADMAP.md`) needs bespoke Console code, the exact
  scaling problem the whole Platform Configuration Foundation was built to
  eliminate.

The chosen approach — optional, grouped, purely descriptive fields on the
existing `ConfigFieldDefinition` — keeps Rule 3 (Single Source of Truth)
intact: one object per field describes everything about it, forever.

## 7. Future UI generation (not built here)

Once a Console exists, generating a settings page for any module becomes:

1. `configurationService.getModule(id)` → sections → fields (existing, P9.0).
2. For each field, pick a control: `field.uiControl` if set, else the
   `type`-based default table (§2 above).
3. Evaluate `field.dependency.hiddenWhen`/`enabledWhen` against
   `configurationService.resolveField()` for the referenced field id to
   decide visibility/enablement.
4. Render `field.display.icon`/`displayName`/`badge`/`group` for layout,
   sorted by `field.display.displayOrder`.
5. Gate the control's edit affordance by `configurationService.canEdit()`
   (existing, P9.0) intersected with `field.governance.editableBy` if set.
6. Show `field.governance.dangerous ? <confirm dialog> : null` before
   calling `configurationService.updateField()`.
7. Index `field.search.keywords`/`aliases`/`title`/`description` into a
   client-side search index for the global search box.

No code implementing steps 1–7 exists yet — this is the specification a
Console-building phase implements against, not a preview of code already
written.

## 8. What was validated

- `tsc --noEmit` — clean; all 70 pre-existing field literals across 15
  modules typecheck unchanged.
- `next lint` — clean.
- Full test suite plus 10 new tests
  (`src/test/p9-1-2-1-configuration-metadata.test.ts`) proving: every
  field still resolves to its own default with no override (unchanged
  runtime behavior), untouched fields expose no new metadata (nothing was
  silently defaulted in), and every enriched field's metadata round-trips
  correctly through the registry.
- No UI, route, endpoint, or business-logic changes — registry metadata
  only, per this phase's mandate.
