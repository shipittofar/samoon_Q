# P9.5.5.2 — Startup Registration Recovery

Bug-fix phase, follow-on to P9.5.5.1. That phase fixed a real hazard (config
submodules bypassing the `@/config` barrel) but did not, on its own, stop the
production crash — this phase found and fixed the actual runtime root cause,
plus a second, unrelated pre-existing bug that P9.5.5.1's fix exposed once
the first crash stopped masking it.

## Reported symptom

```
Every page returns HTTP 500
Error
digest: 669271681
```
No stack trace in production logs (minified build).

## Reproduction

Enabled `experimental.serverSourceMaps: true` temporarily, ran `npm run
build && npm start` (via `node .next/standalone/server.js`, since `output:
standalone` doesn't support `next start`), and hit `/`, `/login`,
`/register`, `/forgot-password`, `/platform-admin`.

## Root cause #1 — the registry singleton was never actually a singleton

`src/config/registry.ts` exported `export const platformConfigurationRegistry
= new PlatformConfigurationRegistryClass()` at module scope, and the whole
"register at startup, seal on first read" safety model (`src/config/
registry.ts`, unchanged since P9.0) assumes that line runs exactly once per
process.

Instrumenting the class constructor and `register()` proved it doesn't:
across a single `node server.js` process, **three separate instances** of
`PlatformConfigurationRegistryClass` were created — one when `src/
instrumentation.ts`'s `register()` hook ran at boot (added in this
investigation to force early registration; it fully succeeded, in
isolation), and two more when the root layout's render-time webpack bundle
and a page's own lazily-loaded bundle each re-evaluated `registry.ts`'s
module body. Next.js App Router's production SSR resolves `import
'./modules/<name>'` (and the registry module itself) from separately
compiled bundle graphs per route/segment; each graph gets its own module
instantiation of anything not deduplicated into one shared vendor chunk in
that specific request's dependency graph. The result: whichever bundle's
copy of the registry got read first (a `getField()`/`getModule()` call,
which seals as its first action) sealed *its own* copy — but a *different*
copy, still unsealed moments earlier, had already registered nothing yet,
so a later `registerAdminModule()` call against that second copy hit
`register("platform.overview") called after the registry was sealed`. Task
B's report was correct in effect ("registration happens after sealing") but
the actual defect was one level deeper: there wasn't one registry to
seal-too-early, there were several, and no import-ordering fix inside
`platform-admin/` or `i18n/` could close that gap, because the race was
between *separate object instances*, not *import order within one*.

### Fix

`src/config/registry.ts` now caches the singleton on `globalThis` (the same
pattern Next.js's own documentation recommends for Prisma Client, for
exactly this class of "module re-evaluated across bundles/hot-reload"
problem):

```ts
const GLOBAL_REGISTRY_KEY = Symbol.for('samoon.platformConfigurationRegistry')
const globalStore = globalThis as unknown as Record<symbol, PlatformConfigurationRegistryClass | undefined>
export const platformConfigurationRegistry =
  globalStore[GLOBAL_REGISTRY_KEY] ?? (globalStore[GLOBAL_REGISTRY_KEY] = new PlatformConfigurationRegistryClass())
```

Every bundle that evaluates `registry.ts` now gets the exact same object,
regardless of how many separate webpack module graphs resolve it in the
same Node process.

That alone isn't sufficient: with one true shared instance, a **second**
bundle re-evaluating `import './modules/countries'` (etc.) would call
`register("countries")` again — previously this threw `duplicate module id`
unconditionally. `register()` is now idempotent for a module id that's
already present (a no-op, checked *before* the sealed check), since a
repeat call with the same id is exactly what happens when the same source
file's module body runs again in a different bundle — not a genuine
authoring mistake. A genuinely different module accidentally reusing
someone else's id is `id`-indistinguishable from this at runtime, so this
narrows (but doesn't eliminate) that one, low-probability class of bug the
old check also caught; the tradeoff was accepted to fix a app-breaking
production crash.

`src/instrumentation.ts` was also added: Next.js calls its `register()`
export exactly once at process boot, before any request. It imports
`@/config` and `@/platform-admin`, so registration is attempted at the
earliest possible point regardless of which route/bundle serves the first
real request. Belt-and-suspenders with the `globalThis` fix — either one
closes the immediate crash; both together make the invariant ("nothing
reads before everything registers") true from the very first line of the
process rather than "usually true, depending on route order."

## Root cause #2 — a pre-existing, unrelated bug the first crash was masking

Once the registry crash stopped happening, every route *still* returned
500, from a completely different error (empty message + digest, root
`next-intl`'s compiled `NextIntlClientProvider.js`, confirmed via a real
source-map lookup against `4743.js.map` and via `instrumentation.ts`'s
`onRequestError` hook).

`src/i18n/ClientIntlProvider.tsx` (added in P9.5.4, commit `6186ccd`, months
before this phase) destructures `locale` from its own props but never
forwards it to `<NextIntlClientProvider>`:

```tsx
export function ClientIntlProvider({ locale, messages, children }: {...}) {
  return (
    <NextIntlClientProvider
      messages={messages}      // <-- locale prop never passed
      onError={...}
      getMessageFallback={...}
    >
```

This app has no `[locale]` route segment, so next-intl cannot infer the
locale itself — `NextIntlClientProvider` requires it explicitly and throws
when it's missing. Since `ClientIntlProvider` wraps every page via the root
layout, this has broken **every single route** since P9.5.4 — it just never
surfaced, because the registry-seal crash (root cause #1) failed even
earlier in the same render, on every request, so this bug's own throw was
never reached until root cause #1 was fixed.

### Fix

One line, `src/i18n/ClientIntlProvider.tsx`:

```tsx
<NextIntlClientProvider
  locale={locale}
  messages={messages}
  ...
```

## Why P9.5.5.1 did not actually fix the crash

P9.5.5.1 diagnosed a real, demonstrable hazard (direct `@/config/registry`
/`@/config/service` submodule imports bypassing the barrel) and fixed it
correctly — that fix is still correct and still necessary. But it assumed
the registry was a single object whose *import order* determined whether
registration raced ahead of a read. In production, the deeper problem was
that the registry wasn't a single object at all across the different
bundles Next.js's App Router compiles per route/layout/instrumentation —
so no amount of import reordering inside `platform-admin/`, `i18n/
runtime.ts`, or `platform-admin/index.ts` could fix a race between three
independent instances. P9.5.5.1's regression test
(`src/test/p9-5-5-1-runtime-recovery.test.ts`) passed because it exercises
the source-level import graph directly through Node's/Vitest's own single
module cache — it cannot reproduce Next.js's production multi-bundle
re-evaluation, which is exactly what actually broke.

Separately, and independently, P9.5.5.1 could never have caught the
`ClientIntlProvider` bug — it's unrelated to configuration registration
entirely and had been broken since P9.5.4.

## Files changed

- `src/config/registry.ts` — `globalThis`-backed singleton; idempotent
  `register()` for an already-registered module id.
- `src/instrumentation.ts` (new) — `register()` hook imports `@/config` and
  `@/platform-admin` at true process startup.
- `src/i18n/ClientIntlProvider.tsx` — forwards the `locale` prop to
  `NextIntlClientProvider` (one line).
- `src/test/p9-5-5-1-runtime-recovery.test.ts`,
  `src/test/p9-platform-configuration.test.ts` — both use
  `vi.resetModules()` to simulate a fresh process per test case; since the
  registry singleton now deliberately survives that (the whole point of the
  `globalThis` fix), both call `platformConfigurationRegistry
  .__resetForTests()` explicitly to restore per-test isolation.
