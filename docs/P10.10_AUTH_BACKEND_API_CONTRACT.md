# Authentication API Contract

This document specifies the complete backend authentication API the Savor
/ Samoon Q frontend expects. It is written for backend developers
implementing the real API — the frontend already has a fully-functional
mock implementation of every endpoint described below
(`src/services/auth.service.ts`, `mockActive()` branches), so this
contract is a faithful transcription of what the mock currently promises,
not a wishlist. Fields marked **optional** are safe to omit at launch —
the frontend already treats them as such (see "Frontend Expectations").

No RBAC permission calculation, `ROLE_PERMISSION_MAP`, or authorization
logic is described or changed here — this is exclusively about the shape
of the identity/session HTTP contract.

---

## 1. Endpoint Table

| Method | Endpoint | Purpose | Auth Required | Request | Response |
|---|---|---|---|---|---|
| POST | `/auth/login/` | Email+password login | No | `LoginRequest` | `SessionResponse` |
| POST | `/auth/send-otp/` | Send OTP to a phone number | No | `SendOTPRequest` | `SendOTPResponse` |
| POST | `/auth/verify-otp/` | Verify OTP code | No | `VerifyOTPRequest` | `VerifyOTPResponse` (discriminated) |
| POST | `/auth/register/` | Complete registration (new user) | No¹ | `RegisterRequest` | `SessionResponse` |
| GET | `/auth/me/` | Restore session from access token | Yes (Bearer) | — | `MeResponse` |
| POST | `/auth/token/refresh/` | Exchange refresh token for new access token | No (refresh token in body) | `RefreshRequest` | `RefreshResponse` |
| POST | `/auth/logout/` | Invalidate the current session server-side | Yes (Bearer) | `LogoutRequest` | `{ success: true }` |
| POST | `/auth/forgot-password/` | Trigger password reset email | No | `{ email: string }` | `{ message: string }` |
| POST | `/auth/reset-password/` | Complete password reset | No | `{ token: string, password: string }` | `{ message: string }` |
| POST | `/auth/change-password/` | Change password (authenticated) | Yes (Bearer) | `{ old_password: string, new_password: string }` | `204 No Content` |

¹ `/auth/register/` is unauthenticated but, per the current frontend
flow, is only ever called immediately after a successful
`is_new_user: true` OTP verification — the backend may optionally require
a short-lived `registration_token` (see §2.3) to prevent registration
without a verified phone number.

## 2. Request / Response Schemas

### 2.1 `POST /auth/login/`

**Request — `LoginRequest`**

| Field | Type | Required | Description | Example |
|---|---|---|---|---|
| `email` | string | yes | Account email | `"owner@savor.com"` |
| `password` | string | yes | Plaintext password (sent over TLS) | `"hunter2"` |

**Response — `SessionResponse`** (200 OK)

| Field | Type | Description |
|---|---|---|
| `user` | `User` | See §3.1 |
| `tokens` | `Tokens` | See §3.5 |
| `tenantRoles` | `Role[]` | *(optional)* Tenant-scoped roles for the current tenant context. Empty/absent for a plain customer. |
| `ownership` | `Owner[]` | *(optional)* Businesses this user owns. |
| `staffAssignments` | `StaffAssignment[]` | *(optional)* Staff grants this user holds. |

**Errors:** `401 INVALID_CREDENTIALS`, `403 ACCOUNT_SUSPENDED`, `429 LOGIN_RATE_LIMIT`.

**Frontend consumer:** `authService.login()` → `useLogin()`
(`src/hooks/index.ts`) → on success: `useAuthStore.setUser(user)`,
`useRbacStore.setTenantRoles(tenantId, tenantRoles)` if present.

> **Naming note:** the frontend's internal field for tenant roles on
> `login()`/`verifyOTP()` responses is currently named `p7Roles`
> (historical — P7 was the RBAC implementation phase). This document
> specifies the wire field as `tenantRoles` for backend clarity; the
> frontend adapter is responsible for the rename (see §6 Migration
> Checklist item 3) — backend implementers should use `tenantRoles`,
> not `p7Roles`.

### 2.2 `POST /auth/send-otp/`

**Request — `SendOTPRequest`**

| Field | Type | Required | Description | Example |
|---|---|---|---|---|
| `country_code` | string | yes | Dial code, always separate from the number, never concatenated | `"+1"` |
| `phone_number` | string | yes | Local number without the country prefix | `"4255552222"` |

**Response — `SendOTPResponse`** (200 OK)

| Field | Type | Description |
|---|---|---|
| `success` | boolean | Whether the OTP was dispatched |
| `expires_in` | number | Seconds until the OTP code expires |
| `retry_after` | number | *(optional)* Seconds the client must wait before requesting another OTP |

**Errors:** `429 OTP_RATE_LIMIT`, `400 INVALID_PHONE_NUMBER`.

**Frontend consumer:** `authService.sendOTP()` → `useSendOTP()`. No
session state is touched — this call is a pure side-effecting trigger.

---

### 2.3 `POST /auth/verify-otp/`

**Request — `VerifyOTPRequest`**

| Field | Type | Required | Description | Example |
|---|---|---|---|---|
| `country_code` | string | yes | Same dial code sent to `/send-otp/` | `"+1"` |
| `phone_number` | string | yes | Same local number sent to `/send-otp/` | `"4255552222"` |
| `code` | string | yes | The 6-digit OTP the user entered | `"482913"` |

**Response — `VerifyOTPResponse`** — **discriminated on `is_new_user`.**
This is the single most important contract detail: the two branches are
mutually exclusive and the frontend enforces this at compile time via a
TypeScript discriminated union (`VerifyOTPResult` in `auth.service.ts`).

**Existing user (`is_new_user: false`)** — identical shape to
`SessionResponse` plus the discriminant:

| Field | Type | Description |
|---|---|---|
| `is_new_user` | `false` | Discriminant |
| `user` | `User` | |
| `tokens` | `Tokens` | |
| `tenantRoles` | `Role[]` | *(optional)* |
| `ownership` | `Owner[]` | *(optional)* |
| `staffAssignments` | `StaffAssignment[]` | *(optional)* |

**New user (`is_new_user: true`)** — carries **no** identity/token state:

| Field | Type | Required | Description |
|---|---|---|---|
| `is_new_user` | `true` | yes | Discriminant |
| `registration_token` | string | recommended | Short-lived, single-use token proving this phone number was just verified. The frontend should forward it in the `/auth/register/` request body so the backend can trust `country_code`/`phone_number` without re-verifying. |
| `missing_fields` | string[] | optional | Informational hint for the frontend on what `/complete-profile` should collect (e.g. `["first_name", "last_name"]`). Not currently consumed by the frontend but reserved for forward compatibility. |

**Critical contract requirement:** the backend must **never** include
`user`/`tokens` on the `is_new_user: true` branch, and must **never**
omit them on the `is_new_user: false` branch. The frontend's P10.8 fix
depends on this exclusivity — it does not defensively check for a
`user` field's presence when `is_new_user` is `true`; it trusts the
discriminant alone.

**Errors:** `400 OTP_INVALID`, `410 OTP_EXPIRED`, `429 OTP_RATE_LIMIT`.

**Frontend consumer:** `authService.verifyOTP()` → `useVerifyOTP()`.
`is_new_user: true` → zero store writes, pure redirect to
`/complete-profile`. `is_new_user: false` → identical hydration to
`useLogin()`.

### 2.4 `POST /auth/register/`

**Request — `RegisterRequest`**

| Field | Type | Required | Description | Example |
|---|---|---|---|---|
| `country_code` | string | conditionally¹ | Dial code, never concatenated with `phone_number` | `"+1"` |
| `phone_number` | string | conditionally¹ | Local number without the country prefix | `"4255552222"` |
| `registration_token` | string | recommended | Token returned by `/auth/verify-otp/`'s `is_new_user: true` branch (see §2.3) | |
| `first_name` | string | yes | | `"Alex"` |
| `last_name` | string | yes | | `"Kim"` |
| `email` | string | no² | Currently NOT sent by the phone-OTP flow (P10.9) | |
| `password` | string | no² | Currently NOT sent by the phone-OTP flow (P10.9, temporarily disabled) | |
| `confirm_password` | string | no² | Same as above | |

¹ Required for the phone-OTP registration path (`/complete-profile`
after `is_new_user: true`). The frontend also has a **separate**
email+password registration flow (`/register`,
`RegisterClientPage.tsx`) that is out of scope for this document — it
posts `email`/`password`/`confirm_password` instead and does not go
through OTP at all. The backend should treat `/auth/register/` as
accepting either shape (phone-based OR email+password-based), keyed off
which fields are present, exactly as it does today (mock mode already
branches this way implicitly by what the caller sends).

² **Password fields are temporarily not sent by the phone-OTP flow** —
this is an intentional, temporary frontend state (P10.9), not a backend
requirement. The backend contract should keep accepting these fields
(optional) so the frontend can re-enable them later without a breaking
change. Do not make `password` required on this endpoint's phone-based
path.

**Response — `SessionResponse`** (201 Created) — same shape as §2.1.

**Errors:** `409 ACCOUNT_EXISTS`, `400 VALIDATION_ERROR`, `401 REGISTRATION_TOKEN_INVALID`.

**Frontend consumer:** `authService.register()` → `useRegister()`. On
success: `setUser(user)`, `setTenantRoles()` if `tenantRoles` present.
This is the **only** place a phone-OTP-flow session is ever created —
see §5 Session Lifecycle Diagram.

### 2.5 `GET /auth/me/`

**Request:** none (Bearer token in `Authorization` header).

**Response — `MeResponse`** (200 OK)

| Field | Type | Description |
|---|---|---|
| *(all `User` fields, flattened — see §3.1)* | | |
| `tenantRoles` | `Role[]` | *(optional)* |
| `ownership` | `Owner[]` | *(optional)* |
| `staffAssignments` | `StaffAssignment[]` | *(optional)* |

Note: unlike `login()`/`verifyOTP()`, this endpoint's response is `User`
extended in place with the RBAC fields (not a wrapper object with a
`user` key) — this matches the existing TypeScript return type
`User & AuthSessionRbacPayload & { tenantRoles?: Role[] }`. Do not wrap
the user fields in a nested `user` object for this endpoint specifically.

**Errors:** `401 TOKEN_EXPIRED`, `401 TOKEN_INVALID`.

**Frontend consumer:** `AuthBootstrapper` (`src/providers/index.tsx`) on
every app boot — the sole session-restore mechanism. A `401` here
triggers full session teardown (`clearSession()` — see §5, §7).

---

### 2.6 `POST /auth/token/refresh/`

**Request — `RefreshRequest`**

| Field | Type | Required | Description |
|---|---|---|---|
| `refresh` | string | yes | The refresh token. *(Note: the frontend's existing interceptor sends the field as `refresh`, not `refresh_token` — see `axios.instance.ts` line 109. Keep this field name unless the backend contract is renegotiated; changing it is a breaking change to the already-implemented interceptor.)* |

**Response — `RefreshResponse`**

| Field | Type | Required | Description |
|---|---|---|---|
| `access` | string | yes | New access token |
| `refresh` | string | no | New refresh token (rotation). If omitted, the frontend keeps reusing the existing refresh token (`axios.instance.ts`: `data.refresh \|\| refresh`). |

**Errors:** `401 REFRESH_TOKEN_INVALID`, `401 REFRESH_TOKEN_EXPIRED`.

**Frontend consumer:** `axios.instance.ts`'s response interceptor,
transparently, on any `401` from any other endpoint. Never called
directly by application code. On failure: `clearTokens()` +
`window.dispatchEvent('auth:logout')` → `AuthBootstrapper` performs full
teardown (see §7 Error Contract, category A).

---

### 2.7 `POST /auth/logout/`

**Request — `LogoutRequest`**

| Field | Type | Required | Description |
|---|---|---|---|
| `refresh` | string | recommended | Allows the backend to revoke/blacklist this specific refresh token server-side. |

**Response:** `{ "success": true }` (200 OK), or `204 No Content`.

**Frontend consumer:** `authService.logout()` — called by `useLogout()`.
The frontend clears all local state (tokens, RBAC, cart, query cache)
**regardless of this call's success or failure** (`finally` block in
`authService.logout()`) — a failed logout API call must never prevent
the client from locally logging out.

## 4. Error Contract

Standard error response body shape (all endpoints):

```json
{
  "code": "TOKEN_EXPIRED",
  "message": "Human-readable description",
  "errors": { "field_name": ["Field-specific validation message"] }
}
```

| HTTP Status | Code | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Malformed/missing request fields |
| 400 | `INVALID_PHONE_NUMBER` | Phone number failed format validation |
| 400 | `OTP_INVALID` | Wrong OTP code |
| 401 | `INVALID_CREDENTIALS` | Login email/password mismatch |
| 401 | `TOKEN_EXPIRED` | Access token's `exp` has passed |
| 401 | `TOKEN_INVALID` | Access token malformed/tampered/revoked |
| 401 | `REFRESH_TOKEN_INVALID` | Refresh token malformed/tampered/revoked |
| 401 | `REFRESH_TOKEN_EXPIRED` | Refresh token's `exp` has passed |
| 401 | `REGISTRATION_TOKEN_INVALID` | `registration_token` missing/expired/reused |
| 403 | `PERMISSION_DENIED` | Authenticated but not authorized (rare at the auth layer — RBAC enforcement lives elsewhere) |
| 403 | `ACCOUNT_SUSPENDED` | Login blocked by account status |
| 404 | `USER_NOT_FOUND` | |
| 409 | `ACCOUNT_EXISTS` | Registration email/phone already registered |
| 410 | `OTP_EXPIRED` | OTP code's TTL has passed |
| 429 | `OTP_RATE_LIMIT` | Too many OTP requests for this number |
| 429 | `LOGIN_RATE_LIMIT` | Too many failed login attempts |
| 500 | `SERVER_ERROR` | Unhandled backend error |

### Frontend error-handling categories (critical for backend implementers)

The frontend must be able to distinguish two categories from the HTTP
response alone, and **the codes above are chosen specifically to make
that distinguishable**:

**(A) `clearSession` required** — the session is definitively invalid;
the frontend calls `AuthBootstrapper`'s `clearSession()` (full teardown:
tokens, RBAC, cart, branch, dine-in, favorites, recently-viewed, query
cache — see `docs/P10.9_AUTH_SESSION_HARDENING_AUDIT.md` §4):
- `TOKEN_EXPIRED`, `TOKEN_INVALID` (from `/auth/me/` or any 401 that
  survives a refresh attempt)
- `REFRESH_TOKEN_INVALID`, `REFRESH_TOKEN_EXPIRED` (from
  `/auth/token/refresh/`)

**(B) retry required, session preserved** — the frontend must **NOT**
log the user out:
- Any `5xx` (`SERVER_ERROR` or unclassified)
- Network timeout / no response (Axios `ECONNABORTED`, `ERR_NETWORK`)
- `429` rate limits (retry after backoff, not a logout condition)

**Fixed this phase:** `AuthBootstrapper`'s `getMe()` catch handler
(`src/providers/index.tsx`) now inspects `err.response?.status` and only
calls `clearSession()` when it is exactly `401`. Any other rejection
(no `response` at all — network error/timeout — or a `5xx`) only stops
the loading spinner; it does not touch tokens or any store. Mock mode's
`getMe()` never rejects, so this change only affects real-backend mode
and has no observable effect while `NEXT_PUBLIC_USE_MOCK=true`. **This
means the backend's HTTP status code is load-bearing** — a 401 must be
used for every "this token is no good" case, and everything else
(`5xx`, connection failures) must NOT be a 401, or a genuinely invalid
session will appear to survive.

## 5. Token Lifecycle

- **Storage:** access + refresh tokens live in `localStorage` only
  (`JWT_ACCESS_KEY`/`JWT_REFRESH_KEY`, `src/constants`), plus one
  **non-HttpOnly** mirrored cookie for the access token so Next.js Edge
  middleware can read it (`src/middleware.ts`). No `sessionStorage`
  usage anywhere in the codebase.
- **Attachment:** every outgoing request gets `Authorization: Bearer
  <access>` from the request interceptor
  (`axios.instance.ts:58`), if a token is present.
- **Refresh:** on any `401` (except from the refresh call itself), the
  response interceptor attempts exactly one refresh, deduplicating
  concurrent 401s via an `isRefreshing`/`failedQueue` module-level queue
  so N simultaneous 401s produce exactly 1 refresh call, and the other
  N−1 requests wait and retry with the new token once it resolves.
- **Refresh failure:** `clearTokens()` + `window.dispatchEvent(new
  CustomEvent('auth:logout'))` — `AuthBootstrapper` listens for this
  event and performs full session teardown (§4 category A).
- **Expiry check (client-side, Edge):** `middleware.ts`'s `isValidJWT()`
  decodes the JWT payload (no signature verification — Edge runtime has
  no Node crypto) and checks `exp * 1000 > Date.now()`. This is a
  **UX-only** pre-check to redirect unauthenticated users to `/login`
  before a page even renders; **the backend remains the sole
  authority** on token validity for every actual API call.

## 6. Session Lifecycle Diagram

```
─── New user (phone-OTP) ──────────────────────────────────────────────
Phone input
  → POST /auth/send-otp/               (no session state)
  → POST /auth/verify-otp/             is_new_user: true
                                        → NO tokens, NO user, NO RBAC hydration
  → redirect /complete-profile
  → POST /auth/register/               (registration_token + profile fields)
                                        → SessionResponse
  → tokens stored, setUser(), setTenantRoles() if present
                                        ═══ session created HERE, exactly once ═══

─── Existing user (phone-OTP) ─────────────────────────────────────────
Phone input
  → POST /auth/send-otp/
  → POST /auth/verify-otp/             is_new_user: false
                                        → SessionResponse
  → tokens stored, setUser(), setTenantRoles() if present
                                        ═══ session created HERE ═══

─── Existing user (email+password) ────────────────────────────────────
  → POST /auth/login/                  → SessionResponse
  → tokens stored, setUser(), setTenantRoles() if present

─── Session restore (browser refresh / new tab) ───────────────────────
  App boot → AuthBootstrapper
  → getAccessToken() from localStorage
      → none: isAuthenticated stays false, no API call
      → present: GET /auth/me/
          → 200: setUser(), setTenantRoles() if tenantRoles present
          → 401 (or any rejection): clearSession() — full teardown

─── Explicit logout ────────────────────────────────────────────────────
  useLogout() → POST /auth/logout/ (best-effort; local cleanup happens
  in a `finally`/`onSettled` regardless of this call's outcome)
  → logout() [auth store] + RBAC/branch/cart/dine-in/favorites/
    recently-viewed reset + queryClient.clear()

─── Forced logout (refresh failure) ───────────────────────────────────
  Any API 401 → refresh attempt → refresh fails
  → clearTokens() + dispatchEvent('auth:logout')
  → AuthBootstrapper.clearSession() — same full teardown as explicit logout
```

## 7. Frontend Expectations

These are hard constraints the backend must honor for the existing
frontend code to work without further changes:

1. **`is_new_user` is a strict boolean discriminant** — `verifyOTP()`'s
   response must never include `user`/`tokens` alongside
   `is_new_user: true`, and must always include them alongside
   `is_new_user: false`. The frontend does not runtime-validate this; a
   violation is a silent contract break.
2. **`tenantRoles`/`ownership`/`staffAssignments` are all optional on
   every identity-producing response.** The frontend already treats
   their absence as "empty" (`p7Roles && p7Roles.length > 0` gates
   before ever writing to the RBAC store) — a backend that doesn't send
   them yet is fully supported today, no frontend change required to
   launch without them.
3. **`country_code` and `phone_number` are always sent as two separate
   fields, never concatenated**, on `/auth/send-otp/`,
   `/auth/verify-otp/`, and the phone-based path of `/auth/register/`.
   This is enforced by P10.8/P10.9 frontend changes already shipped —
   the backend must accept this shape, not `"+14255552222"` as one
   field.
4. **A failed logout API call never blocks local logout.** Do not
   expect the frontend to retry `/auth/logout/` or block navigation on
   its response.
5. **Refresh token request field is `refresh`, not `refresh_token`**
   (see §2.6) — this is already implemented in
   `axios.instance.ts` and changing it requires a frontend code change,
   not just a backend contract update.
6. **`GET /auth/me/` returns a flat `User`-shaped object with RBAC
   fields merged in**, not `{ user: {...}, tenantRoles: [...] }`. This
   differs intentionally from `/auth/login/`'s wrapper shape — match the
   existing TypeScript return type exactly (§2.5).

## 8. Backend Implementation Checklist

- [ ] `POST /auth/login/` — email+password, returns `SessionResponse`
- [ ] `POST /auth/send-otp/` — accepts split `country_code`/`phone_number`
- [ ] `POST /auth/verify-otp/` — discriminated response on `is_new_user`,
      never mixes the two branches' fields
- [ ] `POST /auth/register/` — accepts phone-based fields (`country_code`,
      `phone_number`, `registration_token`) and/or email+password fields;
      does not require `password` when absent
- [ ] `GET /auth/me/` — flat `User & RBAC-fields` response shape
- [ ] `POST /auth/token/refresh/` — request field named `refresh`;
      response `access` (+ optional `refresh` for rotation)
- [ ] `POST /auth/logout/` — best-effort revocation; idempotent
- [ ] All error responses use the `{ code, message, errors? }` shape
      with the HTTP status codes in §4
- [ ] 401s for invalid/expired tokens are distinguishable (by status
      code alone) from 5xx/transient failures — see §4 gap note
- [ ] OTP rate limiting returns `429 OTP_RATE_LIMIT` with a `retry_after`
      hint where possible
- [ ] `access_token`'s JWT payload includes a standard `exp` claim
      (seconds since epoch) — required by `middleware.ts`'s Edge-runtime
      `isValidJWT()` check

## 10. `NEXT_PUBLIC_USE_MOCK` Switch — Current State (Part 5 audit result)

The task asked for an `authService` adapter structure
(`authService { mock implementation, real implementation }`) to be
"prepared." Auditing the current code: **this structure already exists
and needs no change.**

Every `authService` method (`src/services/auth.service.ts`) already
follows the exact shape:

```ts
async login(credentials) {
  if (!isAuthenticationEnabled()) throw new Error('authentication_disabled')
  if (mockActive()) {
    // ── mock implementation ──
    ...
    return { user, tokens, p7Roles }
  }
  // ── real implementation ──
  const { data } = await api.post(ENDPOINTS.AUTH.LOGIN, credentials)
  setTokens(data.tokens.access, data.tokens.refresh)
  return data
}
```

`mockActive()` resolves `NEXT_PUBLIC_USE_MOCK === 'true'` AND a
Platform-Configuration-driven `authentication.mock_authentication_enabled`
flag (`src/config/modules/authentication.ts`) — so
`NEXT_PUBLIC_USE_MOCK=false` alone is already sufficient to route every
`authService` call to its real (`api.post`/`api.get`) branch, with zero
further code changes required. This confirms the switch the task asked
for is already fully wired — no new adapter code was introduced this
phase, per "keep mock mode working, do not break existing tests."

The only work needed to go live with a real backend is: (1) the backend
implements the endpoints in §1 matching the schemas in §2–§4, (2)
`API_BASE_URL` (`src/constants`) points at it, (3) the two documented
gaps in §9 are resolved when convenient.
