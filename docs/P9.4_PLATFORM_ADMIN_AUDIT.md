# P9.4 — Platform Administration Center: Audit

> Phase A of P9.4. Audits what currently exists across the codebase that
> could plausibly serve platform-administration needs, identifies the real
> gap, and benchmarks it against Shopify/Stripe/Cloudflare/Firebase/Auth0/
> Vercel/Linear/GitHub Enterprise. No code changes in this document.
>
> Last updated: 2026-07-05

---

## 1. What "platform administration" means here — and what it is not

Savor's codebase already has two admin-shaped surfaces, and it's important
this phase not conflate them:

1. **The Tenant Console** (`src/modules/registry.ts`, routes under
   `/console/*`) — per-business-type (restaurant/cafe/bar/food-court/
   food-truck/mobile-cafe) admin dashboards: orders, menu, staff, branches,
   reviews, tenant-scoped RBAC, audit logs, notifications, website builder.
   Every one of these is **scoped to one tenant** — a restaurant owner logs
   in and only ever sees their own business.
2. **The Platform Configuration Studio** (P9.0–P9.3, routes under
   `/console/settings/configuration/*`) — the metadata-driven registry/
   resolver/service/Studio built across P9.0–P9.3, covering 15 *settings*
   modules (Authentication, Countries, Languages, Typography, Themes,
   Feature Flags, Subscriptions, Payments, Storage, Monitoring,
   Notifications, Website Builder, RBAC, System, API). This is genuinely
   platform-wide *configuration*, but it answers "what are the platform's
   settings," not "who are the platform's users, businesses, subscriptions,
   incidents, and jobs" — it has no concept of an actual tenant *list*, a
   platform *employee* directory, an *incident*, a *background job*, or a
   *billing invoice* as a real object to browse/manage.

**Neither of these is what P9.4 asks for.** A Platform Administration
Center is the internal control surface *Savor the company* uses to run
the SaaS itself — closer to Shopify's own internal ops tooling than to
Shopify Admin (which *is* the tenant console equivalent). This phase adds
that missing layer, built on top of (never replacing) the Configuration
Studio's registry/resolver/Inspector/History/Compare machinery.

## 2. Current state, mapped to the phase's requested module list

| Requested module | Current state |
|---|---|
| Platform Overview / Dashboard | Absent. No cross-tenant metrics surface exists. |
| Platform Users | Absent as a concept — `useAuthStore`'s `user` is one signed-in user; there's no "Savor employee" directory distinct from tenant staff. |
| Business Owners / Tenants / Branches | Tenant *data* exists (`src/data/tenants.ts`, `tenant.service.ts`, `branch.service.ts`) and each tenant manages its *own* branches via the Tenant Console — but there is no platform-wide "list every tenant, drill into any of them" surface. |
| Subscriptions / Plans / Billing / Invoices / Payments | `subscriptions` and `payments` **Configuration modules** exist (P9.0) — but those are platform *settings* (e.g. default trial length, supported payment providers), not a browsable list of real subscriptions/invoices per tenant. |
| Roles / Permissions | Tenant-scoped RBAC (P7/P8.6) is thorough (`useRbacStore`, custom role templates, per-branch roles, audit trail) — but it is entirely tenant-scoped. There is no *platform* role (a Savor support engineer, a Savor finance admin) distinct from any tenant's roles. |
| Feature Flags / Countries / Languages / Typography / Themes / Authentication | All exist as Configuration Studio modules (P9.0–P9.2) — reusable as-is, no gap. |
| Email/SMS/Push/OAuth Providers | Partially covered — Authentication's config fields reference `otp_provider_picker` etc., but there's no dedicated provider-management module (credentials, delivery stats, failover). |
| Storage / Media / CDN / Cache / Queues / Jobs / Scheduler | `storage` Configuration module exists (settings only). Media/CDN/Cache/Queues/Jobs/Scheduler as *manageable resources* don't exist anywhere. |
| Notifications | `notifications` Configuration module (settings) exists; a platform-wide sent-notification log/browser doesn't. |
| Audit Logs / Activity Logs | Tenant-scoped audit logs exist (P7/P8, `/console/audit-logs`) plus the Configuration Studio's own per-field audit trail (P9.0.1/P9.1.3). Neither is a *platform-wide* cross-tenant activity feed. |
| Monitoring / Metrics / Health / Incidents / Errors | `monitoring` Configuration module (settings only, e.g. alert thresholds) exists; no actual health/incident/error-tracking surface. |
| Backups / Restore | Absent entirely. |
| API Keys / Webhooks / Integrations / Marketplace / Plugins | `api` Configuration module (settings) exists; no key/webhook/integration management. |
| AI Providers | Absent. |
| Support Tickets / Announcements / Maintenance Mode / System Status | Absent (though `system` Configuration module could host a maintenance-mode *setting*, which is different from a status-page *feature*). |
| Developer Tools / Environment / Secrets / Licenses / Version Management / Migration Center / Database / Search | Absent. |
| Analytics | Tenant-scoped analytics exist (P7.13 enterprise analytics); no platform-wide cross-tenant analytics. |
| Fraud / Abuse / Security Center / Compliance / GDPR / Rate Limits / Session Management / Device Management | Absent as manageable surfaces (rate limiting exists as *runtime behavior* per P9.1.2, not as an admin-configurable/browsable module beyond its Configuration fields). |

**Conclusion: the gap is real and large**, but the *foundation* to close it
(registry, resolver, service, Inspector, History, Compare, dependency
engine, collection type for "one schema many entities") is already fully
built and reusable. P9.4's job is registering the missing modules onto
that foundation and adding the platform-wide shell (dashboard, IA,
permissions, search) around it — not building 70 bespoke admin pages.

## 4. Current / Missing / Future

**Current (reusable as-is, zero rework):**
`PlatformConfigurationRegistry`, `ConfigurationService` (resolve/update/
validate/audit/cache/version), the `'collection'` field type + its
generic table/drawer/bulk-actions/filter/search engine (P9.2), the
Configuration Studio shell — nav/toolbar/Inspector/Inheritance-tree/
History-timeline/Compare-view/command-palette (P9.3), 15 existing
Configuration modules, tenant-scoped RBAC (P7/P8.6, untouched — a
different, valid system for a different scope).

**Missing (this phase's job):**
A platform-wide module registry surface organized by Information
Architecture group rather than flat category; a platform permission
model distinct from tenant RBAC; ~40–70 registered (metadata-only, per
the phase's explicit "do not build everything, just register them")
modules covering the requested list; a metadata-driven platform
dashboard with configurable widgets; cross-entity global search; a
documented backend contract for all of the above; a documented
information architecture and extension guide.

**Future (explicitly out of scope for P9.4, called out so it isn't
silently implied as done):**
Real backend-backed data for any of the newly-registered modules (they
render through the Configuration Studio exactly like Countries does —
metadata and, where sensible, illustrative mock defaults, not live
cross-tenant production data); a real incident-management workflow;
real background job execution/monitoring; a real backup/restore
mechanism; virtualized rendering for genuinely large (10k+ row) tables;
a fully separate visual identity from the Configuration Studio (this
phase deliberately reuses the Studio shell rather than inventing a
second one, per the "no duplicate implementations" constraint).
