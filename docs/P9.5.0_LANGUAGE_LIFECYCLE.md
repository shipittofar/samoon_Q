# P9.5.0 — Language Lifecycle & Activation

> Documentation only. Defines the two independent state axes every
> language entity in `localization.languages` carries (§2.2 of
> `P9.5.0_LOCALIZATION_ARCHITECTURE.md`), their transitions, and the
> platform-only governance model — reusing `ConfigLifecycleState`
> (`src/config/types.ts`, P9.0.1) and the platform permission model
> (`src/platform-admin/permissions.ts`, P9.4) verbatim.
>
> Last updated: 2026-07-05

---

## 1. Two axes, not one

The phase brief lists two lists that look like they could be one state
machine — "Draft/Testing/Published/Deprecated/Archived" and "Enabled/
Disabled/Hidden/Beta/Experimental" — but collapsing them would lose real
information: a language can be `status: published` (translation-complete,
reviewed, production-quality) and still be **temporarily disabled**
(a payment-provider outage in that market, a content compliance hold,
etc.), or conversely `status: testing` (still being translated) yet
**visible** to an internal QA team. Two axes:

| Axis | Values | Answers |
|---|---|---|
| **`status`** (content lifecycle) | `draft` → `testing` → `published` → `deprecated` → `archived` | "How translation-complete and reviewed is this language?" |
| **`enabled` + `visible` + `activation_tier`** (activation) | booleans + `stable`\|`beta`\|`experimental` | "Is this language actually reachable right now, and with what quality guarantee?" |

This mirrors exactly how Countries (P9.2) already separates its own
`status` property from its `enabled`/`visible`/`supported` booleans — the
same reasoning applies here without modification: a country can be fully
configured (`status: published`) yet temporarily disabled for a real
operational reason unrelated to how complete its configuration is.

## 2. Content lifecycle (`status`)

Reuses `ConfigLifecycleState` (`src/config/types.ts` line ~163,
`'draft' | 'testing' | 'published' | 'deprecated' | 'archived'`)
**by value, not by mechanism** — see
`P9.5.0_LOCALIZATION_ARCHITECTURE.md` §2.2's note that this is a `select`
schema property on the language entity, the same pattern Countries already
uses, not the field-level `lifecycle` property every `ConfigFieldDefinition`
also independently carries (that one still describes the whole
`localization.languages` *field*, e.g. "this entire collection module is
`published`" — unrelated to any single language's own content maturity).

| State | Meaning | Typical `activation_tier` while here |
|---|---|---|
| `draft` | Language added to the registry; no/minimal translation started | N/A — never enabled |
| `testing` | Actively being translated; internal QA only | `experimental` |
| `published` | Translation-complete, reviewed, coverage ≥ the platform's minimum threshold (a `localization` Configuration field, not hardcoded) | `beta` → `stable` (see §5 gate) |
| `deprecated` | Being phased out (e.g. superseded by a more specific locale variant) — still enabled for existing users, hidden from new signups | `stable` (still), `visible: false` |
| `archived` | No longer maintained; `enabled: false` | N/A |

Transitions are validated the same way any dependent-field condition is
validated in the Studio today (`field.dependency`, P9.1.2.1) — e.g.
`published` requires `translation_coverage_percent` above threshold, the
same class of check `authentication.otp.length`'s `dependency.hiddenWhen`
already demonstrates, just expressed as an `enabledWhen`/validation rule
on the `status` transition instead of on field visibility.

## 3. Activation state

`enabled`, `visible`, and `activation_tier` are independent, not a single
5-way enum, because their cross-product is meaningful and each combination
maps to a real product state:

| `enabled` | `visible` | `activation_tier` | Reads as |
|---|---|---|---|
| false | — | — | **Disabled** — fully unreachable, regardless of tier |
| true | false | `experimental` | **Hidden** — reachable only by direct link/query param, for internal testing |
| true | true | `beta` | **Beta** — publicly listed, opt-in expectation, no quality SLA |
| true | true | `stable` | **Published/GA** — the "just works" state every one of the 6 initial languages ships in |

This table is the full activation-state vocabulary the phase brief asks
for (Enabled/Disabled/Hidden/Beta/Experimental) expressed as combinations
of three independent, individually simple fields rather than a single
enum that would need a 5th, 6th, 7th value the moment a new combination is
needed — the same extensibility argument `P9.5.0_LOCALIZATION_ARCHITECTURE.md`
§4 makes for delegating formatting to `Intl` instead of a closed enum.

## 4. The 6 initially-enabled languages

English, Persian, Arabic, Chinese (Simplified), Italian, Turkish ship as
`enabled: true, visible: true, activation_tier: stable, status: published`.
Every other entry in the 150+-row roster ships as
`enabled: false, visible: false, activation_tier: experimental, status: draft`
— identical to how Countries seeds 176 rows with only a curated subset
(85, P9.2) holding non-default overrides; here the "curated subset" is
exactly 6, and the other 144+ are pure schema defaults (§`P9.5.0_LOCALIZATION_ARCHITECTURE.md`
§2's default-construction pattern, unchanged).

## 5. The stable-promotion gate

Moving a language from `beta` to `stable` requires, as a validated
precondition (not a manual checklist item):
1. `status: published` (content lifecycle already at the terminal
   "good" state).
2. `translation_coverage_percent` ≥ the platform-configured minimum (a new
   field on the existing `languages`/Localization Configuration module,
   not hardcoded).
3. At least one `approved`-status translation review pass across every
   namespace (`P9.5.0_TRANSLATION_ARCHITECTURE.md` §2) — i.e. no
   namespace still entirely at `machine`/`reviewed` without a second
   sign-off.

This gate is a dependency/validation rule expressed in the same metadata
language (`ConfigFieldDependencyMeta`, `ConfigFieldValidation`, P9.0/
P9.1.2.1) every other Configuration field already uses — not a new
workflow engine.

## 6. Owner Permissions — platform-only, by construction

**Business Owners cannot enable, disable, edit, or otherwise touch any
language, locale, font, or RTL setting.** This isn't a UI-level hide; it's
the same `platformPermission` gate P9.4 introduced for the Platform
Administration Center:

- `localization.languages`, `localization.fonts`, and
  `localization.translation_keys` are registered with
  `platformPermission: 'platform.localization.manage'` (view:
  `'platform.localization.view'`) — the module is filtered out of
  `ConfigurationStudioNav` entirely for any session without a
  `PlatformRole` holding that permission (`hasPlatformPermission`,
  `src/platform-admin/permissions.ts`), exactly the mechanism already
  gating `platform.security_center`, `platform.billing`, etc.
- The field-level `permissions.view`/`permissions.edit` (tenant
  `P7Permission` keys, checked by `configurationService.canView`/`canEdit`)
  stay set to the standard `settings.view`/`settings.manage` pair — **not**
  a tenant-visible permission — so even a tenant `owner` role (which does
  hold `settings.manage` for its *own* tenant-scoped fields, e.g.
  `languages.default`) never sees these fields rendered at all, because
  the module itself is already filtered out at the nav/permission layer
  before individual field checks would even run. This mirrors the exact
  bug-and-fix pattern documented in `docs/P9.4_PLATFORM_ADMIN_CENTER.md`
  §"Bugs found and fixed" — field-level tenant permissions and module-level
  platform permissions must never be conflated, and this design applies
  that lesson from the start rather than repeating the mistake.
- **What a tenant/Business Owner *can* still do**: override
  `languages.default` (the existing P9.0 field, tenant-scoped,
  `canOverride: true`) to pick *which already-enabled* language their
  storefront defaults to, and (per §5 of the architecture doc) override a
  language's `default_currency`/`default_timezone` for their own tenant.
  Neither action can enable a disabled language, edit a translation, or
  change RTL/font behavior — the inheritance chain's `canOverride` only
  ever narrows a value among what the platform has already made
  available, never grants new platform-level capability (Rule 4, unchanged
  since P9.0).
