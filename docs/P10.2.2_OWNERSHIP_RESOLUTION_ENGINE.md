> Implements **only** the permission resolution layer described in
> `docs/P10.1_OWNERSHIP_RBAC_ARCHITECTURE.md` §4.4. No architecture

## Phase B — Resolution Graph: Current → Target

**Current (before this phase), for a tenant-scoped `P7Permission` check:**

```
usePermission(perm)
  └─ usePermissions()
       └─ tenantRoles.find(tenantId) → getPermissionsForRole(roles) → applyOverrides(base, override)
  └─ capability gate (opts.capabilities)
  └─ feature-flag gate (FLAG_MAP)
```

Ownership never entered this pipeline at all — there was no way to express
"this actor owns this tenant" or "this actor holds a StaffAssignment
here" in a permission check. `StaffMember`/`Owner`/`StaffAssignment` (P10.2.1)
existed as data but were never read by anything that decided access.

**Target (P10.1 §4.4), implemented by this phase:**

```
usePermission(perm)
  └─ usePermissions()
       ├─ [UNCHANGED] tenantRoles.find(tenantId) → getPermissionsForRole(roles) → applyOverrides(base, override)
       │                                                    = legacyEffective
       └─ [NEW] resolveOwnershipDrivenPermissions(user.email, activeTenant)
            ├─ resolveOwnershipIdentity(email)          — email → StaffMember → Owner (session bridge)
            ├─ resolveOwnerPermissions(identity, tenant) — §4.4 step 2: ownerId match → ALL_PERMISSIONS, return
            └─ resolveStaffAssignmentPermissions(...)    — §4.4 step 3: effective StaffAssignments for
                                                            this tenant → union(ROLE_PERMISSION_MAP[role],
                                                            mode==='read' ? downgradeToReadOnly(...) : as-is)
            = ownershipDriven
       └─ return [...new Set([...legacyEffective, ...ownershipDriven])]   — UNION, never substitution
  └─ [UNCHANGED] capability gate
  └─ [UNCHANGED] feature-flag gate
```

- **Where ownership enters:** exactly one call, inside `usePermissions()`,
  to `resolveOwnershipDrivenPermissions()`. Nowhere else.
- **Where StaffAssignment enters:** the same call (permission side), plus
  a second, independent entry point for branch scope —
  `useOwnershipBranchAccessContext()` → `buildBranchAccessContextFromAssignments()`
  → (existing, unchanged) `useAccessibleBranches()` / `branchAccessService.*`.
- **Where existing logic remains untouched:** `getPermissionsForRole`,
  `applyOverrides`, the capability gate, the feature-flag gate,
  `PermissionGuard`, `PlatformPermissionGuard`, `usePlatformPermission`,
  `branch-access.service.ts`'s filtering functions, `ROLE_PERMISSION_MAP`
  for every role except the single documented `admin` change (Phase E).
- **Platform Admin (§4.4 step 1)** and **Customer (§4.4 step 4)** are
  correctly *absent* from this pipeline, by design — see the file header
  of `ownership-resolution.service.ts` for why forcing them in would
  violate P10.1 §4.1/§4.5.

## Phase C — Resolution Engine Implementation

`src/services/ownership-resolution.service.ts` (new) implements exactly
the algorithm above:

- `resolveOwnershipIdentity(email)` — the session→Owner/Staff bridge (see
  "Known limitation" below).
- `resolveOwnerPermissions(identity, activeTenant)` — §4.4 step 2, the
  short-circuit. Returns `ALL_PERMISSIONS` (including the now
  owner-exclusive `tenant.manage`/`tenant.view`) or `[]`.
- `resolveStaffAssignmentPermissions(identity, tenantId, now)` — §4.4 step
  3. Unions `ROLE_PERMISSION_MAP[role]` (mode-downgraded if `read`) across
  every currently-effective `StaffAssignment` for that tenant.
- `downgradeToReadOnly(permissions)` — the one genuinely new piece of
  permission logic in this entire phase (P10.1 §3.4's `mode` dimension
  did not and could not exist before StaffAssignment existed).
- `resolveOwnershipDrivenPermissions(email, activeTenant, now)` — the
  full priority chain (owner short-circuits over staff).
- `buildBranchAccessContextFromAssignments(email, tenantId, branches, now)`
  — Phase D's branch-scope wiring.

## Phase D — StaffAssignment → branch-access.service.ts integration

`branch-access.service.ts` itself is **not modified** — its filtering
functions (`getAccessibleBranches`, `canAccessBranch`,
`filterByAccessibleBranches`) already had the correct shape (P10.1 §1.1
calls this out explicitly). What was missing was a *caller* that actually
populated a `BranchAccessContext` from real data. `buildBranchAccessContextFromAssignments()`
is that caller: it expands each effective `StaffAssignment.branchIds`
(`'all'` or explicit) via `resolveAssignmentBranchIds()` (P10.2.1), unions
the results, and returns a `BranchAccessContext` ready to feed straight
into the unchanged `useAccessibleBranches()`/`branchAccessService.*`
functions. New hook: `useOwnershipBranchAccessContext(tenantId, branches)`
in `hooks/index.ts`.

No branch-filtering logic was duplicated — `resolveAssignmentBranchIds`
(a pure expansion helper) and `getAccessibleBranches` (a pure filtering
function) each do exactly one job, called in sequence, not merged.

## Phase E — ROLE_PERMISSION_MAP review

Reviewed every role's array. **Exactly one change was made**, to `admin`:

```diff
- admin: ALL_PERMISSIONS,
+ admin: ALL_PERMISSIONS.filter((p) => p !== 'tenant.manage' && p !== 'tenant.view'),
```

**Removed permissions, documented:**

| Permission | Removed from | Why |
|---|---|---|
| `tenant.manage` | `admin` | P10.1 §4.2/§4.3: tenant-level ownership actions are Owner-exclusive, never delegable to any Staff role. Closes P10.0 finding J1 ("`admin` silently granted `tenant.manage`, identical to `owner`, with no structural way to say 'only the actual owner can do this'"). An Owner still receives this via the ownership short-circuit (Phase C), not via this map. |
| `tenant.view` | `admin` | P10.1 §7.2 states explicitly that Owner access includes "**both** now-owner-exclusive permissions `tenant.manage`/`tenant.view`" — this task's Phase E instruction names both by permission key. Same rationale as above. |

**Nothing else was removed.** `manager`, `cashier`, `waiter`, `kitchen`,
`marketing`, `support` were reviewed and are unaffected — none of them
ever granted `tenant.manage`/`tenant.view` (verified by test). The
`owner` role's array (a separate, manually-curated, already-incomplete
entry — P10.0 found it missing `orders.delete`, `customers.manage`,
`analytics.export`, `settings.manage`, `featureflags.manage`,
`audit.export`/`audit.manage`, `notifications.manage`/`preferences`,
`operations.manage`, all commented out in source) was **deliberately not
touched** — Phase E's instruction is "remove ONLY incorrect grants," not
"add missing ones," and `owner`'s array is under-provisioned, not
over-provisioned. Fixing it is a separate, larger change than this
phase's scope (see "Remaining technical debt" below) — and, in the
target architecture, is expected to become moot once P10.3/P10.4 retire
role-based `'owner'` grants entirely in favor of the ownership
short-circuit this phase already implements.

**Test impact (Phase H, "update only if architecture intentionally
changed"):** two pre-existing tests asserted the *old*, incorrect
behavior (`admin has tenant.view: true`; `admin has all permissions
except tenant.manage` with a length of `ALL_PERMISSIONS.length - 1`).
Both were updated, not deleted, with an inline comment explaining the
intentional architecture change (`src/test/phase7-rbac.test.ts`,
`src/test/phase8-rbac-navigation.test.ts`). Every test that already
asserted the *target* behavior (`admin does NOT have tenant.manage`, the
`hasAllPermissions` check) was already correct and required no change —
it simply started passing.

- `src/services/owner.service.ts` — added `getOwnerByUserIdSync()`.
- `src/services/staff.service.ts` — added `findStaffMemberByEmail()`

- `docs/PLATFORM_ROADMAP.md` — P10.2.2 marked complete, P10.3 updated to

### Files created

- `src/services/ownership-resolution.service.ts` — the resolution
  engine itself (§4.4).
- `src/test/p10.2.2-ownership-resolution-engine.test.ts` — 44 tests.
- `docs/P10.2.2_OWNERSHIP_RESOLUTION_ENGINE.md` — this document.

### Obsolete code identified (not deleted — flagged per "never delete legacy models")

- `useHasPermission()` (`hooks/index.ts`) — zero live call sites outside
  tests, wraps the deprecated `rbac.service.ts`. Deletion is a P10.4 task.
- The dead commented-out `owner`/`admin` alternatives in
  `ROLE_PERMISSION_MAP` (P10.0 J2) — the `admin` one was activated
  (Phase E); the `owner` one remains commented, unrelated to this phase's
  scope, left as-is.
- `rbac.service.ts` itself — still `@deprecated`, still the fallback path
  inside `AuthGuard` for any `requiredPermission` other than
  `dashboard:access` (none exist today). Untouched, per the rules.

### Duplication removed

- `useAdminModuleNav()`'s inline re-implementation of
  `usePermissions()`'s exact computation — this was the one genuine
  "parallel permission engine" this audit found. Removed by delegating to
  `usePermissions()`.
- `useDashboardNav()`'s independent `rbacService.hasPermission(role,
  'dashboard:access')` call, now unified with `AuthGuard`'s via
  `useHasDashboardAccess()`.

### Remaining technical debt (honest — not fixed here, out of scope for a permission-resolution phase)

1. **Session identity bridge (email lookup)** —
   `resolveOwnershipIdentity()` bridges `useAuthStore.user.email` to
   `StaffMember`/`Owner` records because `User.id` (auth mock ids
   `'1'`–`'10'`) and `StaffMember.userId`/`Owner.userId` (`'user-owner-01'`
   etc.) are disjoint id spaces in this codebase's mock data — a
   pre-existing gap (P10.0 J12/J13), not created or fixed by this phase.
   The bridge works correctly for every account tested but is a real
   seam: consolidating the id spaces requires editing `auth.service.ts`'s
   login flow and `mock-data.ts`'s `User` fixtures, which is out of scope
   for a permission-*resolution* phase.
2. **`dashboard:access` keeps its legacy OR-branch** — `useHasDashboardAccess()`
   is `legacy OR ownership-derived`, not a full replacement, specifically
   because two demo accounts (`staff@savor.com`, `multirole@savor.com`)
   have no matching `StaffMember` record and would lose console access if
   the legacy path were removed outright. Full replacement is a P10.3/P10.4
   cleanup once every demo account has a real Staff/Owner backing.
3. **`owner`'s `ROLE_PERMISSION_MAP` array is still under-provisioned**
   relative to `ALL_PERMISSIONS` (missing `orders.delete`,
   `customers.manage/create/edit`, `analytics.export`, `settings.manage`,
   `featureflags.manage`, `audit.export/manage`,
   `notifications.manage/preferences`, `operations.manage` — all
   commented out in source). Not fixed, per Phase E's "remove ONLY
   incorrect grants" scope, and expected to become moot once P10.3/P10.4
   retire role-based `'owner'` in favor of the ownership short-circuit
   this phase implements.
4. **`/platform-admin` route middleware gap** (P10.0 J7) — confirmed
   still present, correctly out of scope (a routing/middleware
   configuration change, not a permission-resolution change).
5. **`resolveOwnershipIdentity`/mock service calls are synchronous
   mock-mode-only** — `getOwnerByUserIdSync()`/`findStaffMemberByEmail()`
   return `undefined` when `USE_MOCK` is false, since `usePermissions()`
   is a synchronous memoized selector and cannot await a real backend
   call. A real-backend integration needs either a session payload that
   already carries `ownerId`/`staffId`/resolved permissions (the more
   likely real-world shape) or a caching layer — out of scope until a
   backend exists (consistent with every other "contract only, no
   implementation" surface already documented in this codebase, e.g.
   Backend Contract §36/§38/§39).
6. **`useOwnershipBranchAccessContext` has no live page-level consumer
   yet** — it closes P10.0 J20 structurally (the primitive is no longer
   unpopulated), but wiring it into an actual branch-scoped console page
   is P10.3 UI work, explicitly out of scope here ("Do not build UI. Do
   not build pages.").

### Migration impact

- **Zero breaking changes.** `usePermissions()`'s return type and every
  existing caller's behavior for accounts with no Owner/StaffAssignment
  record is unchanged (verified: `ownershipDriven.length === 0` short-circuits
  to the exact pre-existing `legacyEffective` value, same array identity
  behavior as before for those callers).
- **One intentional, documented permission reduction**: `admin` no longer
  implicitly receives `tenant.manage`/`tenant.view`. Any real (non-mock)
  workflow relying on `admin` for tenant-level actions would need the
  actual `Owner` account or a scoped exception — flagged in P10.1 §10.1
  as the one unavoidable breaking change in the whole rewrite, now live.
- **Two test files updated**, both with inline comments explaining the
  intentional change — reviewable, not silent.
- Every other role, every existing mock-login flow, every existing
  `PermissionGuard`/`CapabilityGuard`/`PlatformPermissionGuard` usage is
