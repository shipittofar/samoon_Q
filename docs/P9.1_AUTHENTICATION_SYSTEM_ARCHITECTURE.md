- **OTP-first phone/email authentication** with challenge-bound verification

## 1. Authentication Flow & State Machine

### 1.1 End-to-End Sequence

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        AUTHENTICATION FLOW DIAGRAM                           │
└─────────────────────────────────────────────────────────────────────────────┘

[Guest User]
      ↓
      │ Initiate Login (Phone or Email)
      ↓
[Send OTP Challenge]
      ├─── SMS Provider (Twilio/etc.)
      ├─── Email Provider (SendGrid/etc.)
      ├─── Store in OTP Table + Login_Attempts
      └─── Respond with challenge_id + timeout
      ↓
[User Receives OTP]
      ↓
      │ Submit OTP Code
      ↓
[Verify OTP]
      ├─── Validate code + challenge_id
      ├─── Check attempt limits
      ├─── Check replay protection
      ├─── Check rate limits
      └─── Increment attempt counter
      ↓
   ┌─ YES ─────────────────────────────────────────┐
   │  OTP Valid + User Exists                       │
   │         ↓                                      │
   │  [Existing User Path]                          │
   │         ↓                                      │
   │  • Revoke old sessions (optional)              │
   │  • Create new session (device)                 │
   │  • Issue access + refresh tokens               │
   │  • Return user object + tokens + device_id    │
   │         ↓                                      │
   │  [Dashboard / Console Access]                  │
   └────────────────────────────────────────────────┘

   ┌─ NO ──────────────────────────────────────────┐
   │  OTP Valid + User Does Not Exist              │
   │         ↓                                      │
   │  [New User Path]                               │
   │         ↓                                      │
   │  • Check registration.enabled config          │
   │  • Create pending registration record         │
   │  • Update registration.status → "OTP_VERIFIED"│
   │  • Issue temporary registration token         │
   │  • Respond with is_new_user=true              │
   │         ↓                                      │
   │  [Redirect to Complete Profile]               │
   │         ↓                                      │
   │  • User submits name, email (optional)        │
   │  • Create user account                        │
   │  • Create session + issue tokens              │
   │  • Update registration.status → "COMPLETED"   │
   │         ↓                                      │
   │  [Dashboard / Console Access]                 │
   └────────────────────────────────────────────────┘

   ┌─ FAIL ────────────────────────────────────────┐
   │  OTP Invalid, Expired, or Limit Hit           │
   │         ↓                                      │
   │  Increment attempt counter                    │
   │  Remaining attempts: max - current            │
   │         ↓                                      │
   │  if (attempts >= max):                        │
   │     • Temporary lock (lockout_duration_min)   │
   │     • Status: "LOCKED_TEMPORARY"              │
   │     • Audit log: otp_verification_failed      │
   │     • Respond 429 (Too Many Requests)         │
   │  else:                                        │
   │     • Respond 401 with attempts_remaining     │
   │     • User can retry or request resend        │
   └────────────────────────────────────────────────┘
```

### 1.2 State Machine Definition

**Auth State Transitions:**

```
┌─────────┐      Send OTP       ┌──────────────┐      Verify OTP      ┌─────────────┐
│ GUEST   │ ───────────────────→ │ OTP_PENDING  │ ────────────────────→ │ LOGGED_IN   │
└─────────┘ challenge_id issued  └──────────────┘  tokens issued       └─────────────┘
      ↑                               ↓                                      │
      │                          [RESEND]                                    │
      │                               ↓                                      │
      │                          ┌──────────────┐                            │
      │                          │ OTP_PENDING  │ (cooldown enforced)       │
      │                          └──────────────┘                            │
      │                                                                      │
      │                          ┌──────────────┐                            │
      └──────────────────────────│ LOCKED_TEMP  │◄───────────────────────────┘
                                 │ (after N     │  Logout
                                 │  failures)   │
                                 └──────────────┘
                                      ↓
                            (wait lockout_duration)
                                      ↓
                                  [UNLOCKED]
                                      ↓
                                   Back to GUEST
```

### 1.3 Challenge-Bound OTP Architecture

OTPs are **never** bound to just a phone number. Instead:

1. **Challenge** is created: UUID `challenge_id`
2. OTP code is generated and **hashed** (bcrypt, not plaintext)
3. Challenge record stores:
   - `challenge_id` (primary key)
   - `contact` (phone or email)
   - `contact_type` (enum: phone | email)
   - `hashed_otp` (bcrypt of the 6-digit code)
   - `created_at` (timestamp)
   - `expires_at` (created_at + ttl_seconds)
   - `attempt_count` (incremented on each failed verify)
   - `verified_at` (null until verified)
   - `used_by_session_id` (tracking which session verified this OTP — replay protection)

**Why?** 
- Prevents OTP reuse across different login attempts
- Allows multiple parallel OTP challenges (one per device)
- Session-binding provides replay attack mitigation
- Support for concurrent "Send OTP" requests (user clicks retry button)

## 2. Registration Lifecycle

### 2.1 Registration States & Transitions

Every registration attempt traverses a state machine:

```
┌──────────────────────────────────────────────────────────────────────┐
│                    REGISTRATION STATE MACHINE                         │
└──────────────────────────────────────────────────────────────────────┘

User Initiates Sign-Up
         ↓
    ┌────────────────┐
    │ PENDING        │  (OTP sent, awaiting verification)
    │                │
    │ Fields:        │
    │ • contact      │
    │ • contact_type │
    │ • challenge_id │
    │ • created_at   │
    │ • expires_at   │
    └────────────────┘
         ↓ [Send OTP]
    ┌────────────────┐
    │ OTP_SENT       │  (challenge created, SMS/email dispatched)
    │                │
    │ Field updates: │
    │ • status       │
    │ • otp_sent_at  │
    └────────────────┘
         ↓ [Resend OTP]
    ┌────────────────┐
    │ OTP_SENT       │  (resend cooldown enforced, new challenge created)
    │ (new challenge)│
    └────────────────┘
         ↓ [Verify OTP]
    ┌────────────────┐
    │ OTP_VERIFIED   │  (OTP valid, user does not exist in users table)
    │                │
    │ Field updates: │
    │ • status       │
    │ • verified_at  │
    │ • temp_token   │  (for completing profile step)
    └────────────────┘
         ↓ [Complete Profile]
    ┌────────────────┐
    │ PROFILE_PEND   │  (name/email received, awaiting account creation)
    │                │
    │ Field updates: │
    │ • first_name   │
    │ • last_name    │
    │ • email        │
    └────────────────┘
         ↓ [Account Creation]
    ┌────────────────┐
    │ COMPLETED      │  (user created, session issued, registration closed)
    │                │
    │ Field updates: │
    │ • status       │
    │ • completed_at │
    │ • user_id      │ (foreign key to users table)
    └────────────────┘

Failure Paths:

[PENDING/OTP_SENT] ─[TTL expired]──→ [EXPIRED]
[PENDING/OTP_SENT] ─[Admin cancel]──→ [CANCELLED]
[OTP_VERIFIED]     ─[Admin block]───→ [BLOCKED]
[*]                ─[Admin delete]──→ [DELETED]
[OTP_VERIFIED]     ─[Timeout 24h]───→ [EXPIRED]
```

### 2.2 Registration Table Schema

```sql
Table: registrations

Columns:
├── id (UUID, PK)
├── contact (VARCHAR 255, NOT NULL, UNIQUE per status)
├── contact_type (ENUM: phone | email, NOT NULL)
├── status (ENUM: PENDING, OTP_SENT, OTP_VERIFIED, PROFILE_PENDING, COMPLETED, CANCELLED, EXPIRED, BLOCKED, DELETED, NOT NULL)
├── challenge_id (UUID, FK → otp_challenges.id, NULLABLE)
├── otp_sent_at (TIMESTAMP, NULLABLE)
├── otp_sent_count (INTEGER, DEFAULT 0)
├── verified_at (TIMESTAMP, NULLABLE)
├── first_name (VARCHAR 100, NULLABLE)
├── last_name (VARCHAR 100, NULLABLE)
├── email (VARCHAR 255, NULLABLE)
├── temp_token (VARCHAR, NULLABLE) — JWT with 1-hour TTL, used for profile completion
├── completed_at (TIMESTAMP, NULLABLE)
├── user_id (UUID, FK → users.id, NULLABLE after COMPLETED)
├── created_at (TIMESTAMP, NOT NULL)
├── updated_at (TIMESTAMP, NOT NULL)
├── expires_at (TIMESTAMP, NULLABLE) — auto-set to created_at + registration.otp.ttl_seconds
└── deleted_at (TIMESTAMP, NULLABLE, soft-delete flag)

Indexes:
├── UNIQUE(contact, contact_type, deleted_at) — allow retry after soft-delete
├── INDEX(status, created_at) — cleanup queries
├── INDEX(user_id) — lookups after account creation
└── INDEX(expires_at) — cleanup job
```

### 2.3 Registration State Validations

| Current State | Allowed Transitions | Validation Rules |
|---------------|-------------------|------------------|
| **PENDING** | → OTP_SENT | Contact not already in users table; registration.enabled = true |
| **OTP_SENT** | → OTP_SENT (resend) | Cooldown elapsed (resend_cooldown_seconds); attempt count < max_resend (recommend 3) |
| **OTP_SENT** | → OTP_VERIFIED | OTP code matches; attempt count < otp.max_verify_attempts |
| **OTP_VERIFIED** | → PROFILE_PENDING | Temp token is valid |
| **PROFILE_PENDING** | → COMPLETED | First name provided; email (optional) provided; no account with this contact exists |
| **OTP_VERIFIED** | → EXPIRED | TTL exceeded (24h recommended) |
| **Any** | → CANCELLED | Admin-initiated only |
| **Any** | → BLOCKED | Admin-initiated only |
| **Any** | → DELETED | Admin-initiated only (soft-delete) |

## 3. Login Lifecycle

### 3.1 Login Flow Variants

Backend must support three login methods, all using the OTP pathway:

#### 3.1.1 Phone Login

```
POST /auth/phone/login → (phone: string) → challenge_id + contact confirmation

Phone number validation:
• Must match pattern: +{country_code}{number}
• Normalized to E.164 format before storage/lookup
• Lookup in users table: SELECT * FROM users WHERE phone = ?
```

#### 3.1.2 Email Login

```
POST /auth/email/login → (email: string) → challenge_id + contact confirmation

Email validation:
• Must match RFC 5322
• Normalized to lowercase
• Lookup in users table: SELECT * FROM users WHERE email = ?
```

#### 3.1.3 Guest Checkout Login

```
POST /auth/guest/login → (email: string) → create temporary user + challenge_id

Behavior:
• Check guest_checkout_enabled config
• Create temporary users.guest_session record
• TTL: from guest.session_ttl_minutes config
• Bypass normal email verification (or verify email post-checkout)
```

### 3.2 Session Restore (Remember Me)

```
POST /auth/session/restore → (device_id: string, refresh_token: string) 

Lookup:
• Find session WHERE device_id = ? AND refresh_token = ?
• Check refresh_token not revoked
• Check session not invalidated
• Check device not marked as untrusted
• Issue new token pair (rotation)
```

### 3.3 Login Attempt Tracking

```sql
Table: login_attempts

Columns:
├── id (UUID, PK)
├── contact (VARCHAR 255) — phone or email
├── contact_type (ENUM: phone | email)
├── challenge_id (UUID, FK → otp_challenges.id)
├── user_id (UUID, FK → users.id, NULLABLE if user not found)
├── attempt_result (ENUM: SUCCESS | FAILED | LOCKED)
├── failure_reason (VARCHAR) — e.g., "otp_invalid", "otp_expired", "attempt_limit_exceeded"

├── device_id (UUID, NULLABLE)

├── is_vpn (BOOLEAN) — populated if VPN detection enabled
├── created_at (TIMESTAMP, NOT NULL)
└── location (POINT, PostgreSQL GEOMETRY, NULLABLE)

Indexes:
├── INDEX(contact, created_at DESC) — rate limit checks
├── INDEX(user_id, created_at DESC) — user login history
├── INDEX(ip_address, created_at DESC) — IP-based rate limits + fraud detection
└── INDEX(challenge_id) — link to OTP challenge
```

## 4. OTP System

### 4.1 OTP Generation & Storage

**Generation:**
```
• Algorithm: Cryptographically secure random 6 digits (default from config)
• Format: Zero-padded, e.g., "012345"
• Storage: Never store plaintext
  - Hash with bcrypt (cost 10, consistent with password hashing)
  - Store hash in otp_challenges.hashed_otp
• Delivery:
  - SMS: Via Twilio (or configured SMS provider)
  - Email: Via SendGrid (or configured email provider)
```

**OTP Challenge Table:**

```sql
Table: otp_challenges

Columns:
├── id (UUID, PK)
├── contact (VARCHAR 255, NOT NULL)
├── contact_type (ENUM: phone | email, NOT NULL)
├── hashed_otp (VARCHAR, NOT NULL) — bcrypt(code)
├── attempt_count (INTEGER, DEFAULT 0, NOT NULL)
├── max_attempts (INTEGER, DEFAULT 3, from config)
├── created_at (TIMESTAMP, NOT NULL)
├── expires_at (TIMESTAMP, NOT NULL) — from otp.ttl_seconds config
├── verified_at (TIMESTAMP, NULLABLE)
├── verified_by_session_id (UUID, FK → sessions.id, NULLABLE) — replay protection
├── used_at (TIMESTAMP, NULLABLE) — consumed after login success
├── cancellation_reason (VARCHAR, NULLABLE) — e.g., "user_requested", "admin_override"
└── cancelled_at (TIMESTAMP, NULLABLE)

Indexes:
├── INDEX(contact, contact_type, expires_at) — lookup by contact
├── INDEX(created_at DESC) — cleanup queries
├── INDEX(expires_at) — TTL enforcement job
└── INDEX(verified_at) — audit queries
```

### 4.2 OTP Lifecycle Operations

#### Send OTP
```
Preconditions:
• authentication.enabled = true
• authentication.otp.enabled = true
• contact not in rate-limit blacklist for this operation
• contact not locked (recent failed attempts)

Steps:
1. Validate contact format (phone or email)
2. Check rate limit: max 3 sends per 24h per contact (configurable)
3. Generate 6-digit code
4. Hash code with bcrypt
5. Create otp_challenges record
6. Queue SMS/email task (async)
7. Return challenge_id + estimated delivery time

Errors:
• 429: Rate limit exceeded
• 400: Invalid contact format
• 503: SMS/email provider unavailable (queue retry)
```

#### Verify OTP
```
Preconditions:
• OTP Challenge exists
• Challenge not expired
• Challenge not already verified
• Attempt count < max_attempts
• User submitting challenge_id + code

Steps:
1. Load otp_challenges by challenge_id
2. Compare provided code vs hashed_otp (bcrypt.compare)
3. If mismatch: increment attempt_count, return 401
4. If attempts exhausted: mark challenge as "LOCKED", return 429
5. If match:
   a. Set verified_at = now()
   b. Set verified_by_session_id = current session
   c. Look up user by contact (phone or email)
   d. If user exists: issue tokens (existing user path)
   e. If user doesn't exist: issue temp registration token (new user path)
6. Return AuthResponse or RegistrationResponse

Errors:
• 401: OTP invalid or expired
• 429: Too many attempts, temporary lock
• 400: Missing challenge_id or code
```

#### Resend OTP
```
Preconditions:
• Challenge exists
• Challenge not yet verified
• Resend cooldown elapsed (resend_cooldown_seconds)
• Resend count < max_resend (suggest 3)

Steps:
1. Load existing otp_challenges by challenge_id
2. Check created_at + resend_cooldown_seconds > now()
3. If cooldown not elapsed: return 429 with wait time
4. Generate new code, hash, create NEW otp_challenges record
5. Queue SMS/email task
6. Mark old challenge as cancellation_reason="resend_requested"
7. Return new challenge_id

Errors:
• 429: Cooldown not elapsed (include retry_after header)
• 400: Invalid challenge_id
```

#### OTP Cleanup Job

**Runs every 5 minutes:**
```sql
-- Mark expired OTPs
UPDATE otp_challenges 
SET cancelled_at = NOW(), cancellation_reason = 'ttl_expired'
WHERE expires_at < NOW() AND cancelled_at IS NULL AND verified_at IS NULL;

-- Archive old records (optional, after 30 days)
DELETE FROM otp_challenges 
WHERE created_at < NOW() - INTERVAL '30 days';
```

### 4.3 Replay Protection

**Problem:** Attacker intercepts OTP code → uses it on a different device.

**Solution:** OTP is bound to **session**.

```
On verify request:
1. Backend creates/identifies session_id for this device (from cookies/headers)
2. After successful OTP verification, set verified_by_session_id = session_id
3. When issuing tokens, link access_token to same session_id
4. On subsequent requests, validate token session_id matches request session

If an intercepted OTP is replayed:
• verified_by_session_id already set
• Return 409 Conflict: "OTP already used by another session"
• Do NOT issue tokens
• Flag as potential fraud in audit logs
```

## 5. Token Architecture

### 5.1 Token Types & Lifecycle

#### Access Token (JWT)

```
Claims:
{
  "type": "access",
  "sub": "{user_id}",
  "iat": 1234567890,
  "exp": 1234569090,  // iat + 15 minutes (from jwt_access_ttl_minutes config)
  "session_id": "{session_uuid}",
  "device_id": "{device_uuid}",
  "tenant_id": "{tenant_id}",
  "roles": ["owner", "admin"],
  "scopes": ["read:profile", "write:orders"],
  "token_family": "{refresh_token_family_id}",  // for family revocation
}

Signature: HS256 or RS256 (from jwt.algorithm config)
Storage: localStorage (not HttpOnly)
Transmission: Authorization: Bearer {token}
Lifetime: 15 minutes (jwt_access_ttl_minutes)
Rotation: Issued on every refresh
```

#### Refresh Token (JWT)

```
Claims:
{
  "type": "refresh",
  "sub": "{user_id}",
  "iat": 1234567890,
  "exp": 1234567890 + (7 * 86400),  // 7 days (jwt_refresh_ttl_days config)
  "session_id": "{session_uuid}",
  "device_id": "{device_uuid}",
  "token_family": "{refresh_token_family_id}",
  "jti": "{unique_token_id}",  // for blacklist/revocation
}

Signature: HS256 or RS256
Storage: localStorage (alternative: httpOnly cookie if client supports)
Transmission: POST /auth/token/refresh/ body
Lifetime: 7 days (jwt_refresh_ttl_days)
Rotation: Issued on every refresh (old token invalidated)
Blacklist: Track via refresh_token_revocations table
```

### 5.2 Token Refresh Flow

```
Client receives 401 on any API request
    ↓
    POST /auth/token/refresh/
    {
      "refresh_token": "{old_refresh_token}"
    }
    ↓
Backend:
1. Decode refresh_token (don't verify exp yet)
2. Look up in blacklist: SELECT * FROM refresh_tokens WHERE jti = ?
3. If blacklisted: return 401, log security alert
4. Get current time
5. If token.exp < now(): return 401 (expired)
6. Load session by session_id from token
7. Validate session not revoked
8. Generate new token_family_id (NEW or same?)
   → If NEW: revoke all tokens with old family_id (logout other devices)
   → If SAME: allow refresh (continue session)
9. Issue new access_token + new refresh_token
10. Add old refresh_token.jti to blacklist
11. Return new tokens

Response:
{
  "access": "{new_access_token}",
  "refresh": "{new_refresh_token}",
  "expires_in": 900  // seconds
}
```

### 5.3 Refresh Token Rotation & Family Revocation

**Challenge:** Refresh token theft detection.

**Solution:** Token Family IDs + Family Revocation.

```
Scenario:
• User logs in on Device A → issued token_family "fam_123"
• Attacker steals refresh token on Device A
• Attacker refreshes on Device Z → we issue new token_family "fam_123"
• Device A tries to refresh → token_family "fam_123" already rotated
• System detects: old token from family being replayed

Implementation:
1. Each login issues a NEW token_family_id
2. When refresh succeeds: generate NEW token_family_id for next pair
3. If refresh with OLD token_family_id: flag as potential theft
   • Revoke ALL sessions for this user
   • Audit log: potential_token_theft_detected
   • Return 401 + send security notification to user email

Exceptions:
• If client gracefully handles 401, refresh retries are normal (allow 1 retry window)
• Implement retry window: if two refresh attempts within 10 seconds, allow both
  (covers race conditions in client-side interceptors)
```

### 5.4 Token Blacklist Table

```sql
Table: refresh_token_revocations (blacklist)

Columns:
├── jti (VARCHAR, PK) — unique token ID from JWT
├── user_id (UUID, FK → users.id, NOT NULL)
├── session_id (UUID, FK → sessions.id, NULLABLE)
├── token_family_id (VARCHAR) — for family revocation
├── reason (ENUM: logout | session_revoked | theft_detected | password_reset | device_removed | admin_revoke)
├── revoked_at (TIMESTAMP, NOT NULL)
├── revoked_by (ENUM: user | admin | system)
├── created_at (TIMESTAMP, NOT NULL)
└── expires_at (TIMESTAMP) — when to auto-purge from blacklist (refresh_ttl_days + 1)

Indexes:
├── UNIQUE(jti) — fast lookup on verify
├── INDEX(user_id, revoked_at DESC) — user's revocation history
├── INDEX(token_family_id) — family revocation lookups
├── INDEX(expires_at) — cleanup job
```

## 6. Session Management

### 6.1 Session Creation & Lifecycle

```
POST /auth/*/verify → Backend creates session

Steps:
1. User submits OTP code + challenge_id
2. Backend verifies OTP (see §4.2)
3. On successful verification:
   a. Load or create session:
      - session_id = UUID()
      - user_id = verified_user_id
      - device_id = from request header or generate new
      - created_at = now()
      - last_activity_at = now()
      - status = "ACTIVE"
   b. Increment login count
   c. Store device info (device_name, user_agent, ip_address, country)
   d. Set default: trusted = false (unless known device)
4. Issue tokens
5. Return AuthResponse with device_id
```

### 6.2 Session Table Schema

```sql
Table: sessions

Columns:
├── id (UUID, PK)
├── user_id (UUID, FK → users.id, NOT NULL)
├── device_id (UUID, NOT NULL) — can be shared across devices, or unique per device
├── status (ENUM: ACTIVE | INACTIVE | REVOKED | EXPIRED, NOT NULL)
├── ip_address (VARCHAR 45, NOT NULL)
├── user_agent (VARCHAR, NOT NULL)
├── device_name (VARCHAR 255, NULLABLE) — e.g., "iPhone 14 Pro"
├── device_type (ENUM: mobile | desktop | tablet | unknown)
├── os (VARCHAR 100, NULLABLE)
├── browser (VARCHAR 100, NULLABLE)
├── country (VARCHAR 2, ISO 3166-1 alpha-2)
├── is_vpn (BOOLEAN)
├── login_attempt_id (UUID, FK → login_attempts.id)
├── trusted_device_id (UUID, FK → trusted_devices.id, NULLABLE)
├── is_trusted (BOOLEAN, DEFAULT false) — user marked as trusted
├── created_at (TIMESTAMP, NOT NULL)
├── last_activity_at (TIMESTAMP, NOT NULL)
├── expires_at (TIMESTAMP) — from jwt_refresh_ttl_days config
├── logged_out_at (TIMESTAMP, NULLABLE) — logout timestamp
```

### 6.4 Session Idle Timeout

**Implementation Option A: Client-Side**
```
Frontend tracks last activity (mouse, keyboard, click).
On idle timeout (e.g., 30 minutes):
• Clear tokens from localStorage
• Redirect to login
• No backend call needed
```

**Implementation Option B: Server-Side**
```
Background job every 5 minutes:
SELECT * FROM sessions WHERE last_activity_at < NOW() - INTERVAL '30 minutes'
UPDATE sessions.status = 'EXPIRED' WHERE id IN (...)
Add tokens to blacklist (reason: idle_timeout)
```

**Recommendation:** Implement both. Client-side for UX, server-side for security (logged-in user leaves browser unattended).

## 8. Security & Fraud Prevention

### 8.1 Rate Limiting

**Layer 1: OTP Send Rate Limit**
```
Max: 3 OTP sends per 24h per contact (phone or email)
Window: 24 hours rolling
Enforcement: Check login_attempts table
Code: Implement in rate-limit middleware
Response on limit: 429 Too Many Requests
Retry-After: X-Retry-After header with seconds to wait
```

**Layer 2: OTP Verify Attempt Limit**
```
Max: 3 failed attempts per OTP code (from otp.max_verify_attempts config)
Window: Per challenge_id
Enforcement: otp_challenges.attempt_count
Action on limit: Temporary lock (15 min default)
Status: LOGIN_LOCKED_TEMPORARY
Response: 429 with locked_until timestamp
```

**Layer 3: Login Attempt Rate Limit**
```
Max: 5 failed logins per contact per 15 minutes (from max_login_attempts)
Window: 15 minutes rolling (lockout_duration_minutes)
Enforcement: login_attempts table
Action on limit: Temporary lock
Unlock: Manual admin action OR wait duration
```

**Layer 4: IP-Based Rate Limit**
```
Max: 10 login attempts per IP per 1 hour
Window: 1 hour rolling
Enforcement: login_attempts.ip_address
Action: 429 response
Use Case: Detect brute-force from automated tools
```

**Layer 5: Global Rate Limit (Infrastructure)**
```
Nginx/HAProxy level:
Max: 100 requests per second per IP
Max: 1000 requests per IP per 1 minute
Purpose: DDoS mitigation
Response: 503 Service Unavailable if exceeded
```

### 8.2 Account Lockout

**Temporary Lock:**
```
Trigger: max_login_attempts exceeded (default: 5)
Duration: lockout_duration_minutes (default: 15)
Status: LOGIN_LOCKED_TEMPORARY
Behavior:
• All login requests return 429 for this contact
• Retry-After header: seconds remaining
• User can see countdown in UI
• Unlock: Automatic after duration, OR admin unlock

Audit:
• Log: account_locked_temporary
• Contact: {phone or email}
• Reason: max_attempts_exceeded
• Locked until: {timestamp}
```

**Permanent Lock:**
```
Trigger: Admin action (security incident)
Status: LOGIN_LOCKED_PERMANENT
Behavior:
• All login requests return 403 Forbidden
• User cannot reset via "Forgot Password"
• User must contact support

Admin Unlock:
• POST /admin/users/{user_id}/unlock
• Requires audit_logs entry
• Can set unlock_date (re-lock after N days if desired)
```

### 8.3 Fraud Detection

#### Risk Scoring Model

```
For every login attempt, calculate risk_score (0-100):

risk_score = 0
if (ip_address not in user's previous logins):
  risk_score += 30
if (country != user's typical country):
  risk_score += 25
if (is_vpn):
  risk_score += 20
if (device_fingerprint is new):
  risk_score += 15
if (login_attempt in rapid succession from different IPs):
  risk_score += 20

Action by score:
• 0-20: Allow
• 21-50: Allow, but send email verification + add to audit log
• 51-75: Require additional CAPTCHA verification
• 76-100: Block + require security verification (security questions, email link)

Store in: login_attempts.fraud_risk_score
```

#### Country Blocking

```
Configuration:
authentication.blocked_countries = ["KP", "IR", ...]  // ISO 3166-1 alpha-2

On login:
1. Resolve IP → country (MaxMind GeoIP2 or similar)
2. If country in blocked_countries:
   • Audit log: login_blocked_by_country
   • Response: 403 Forbidden
   • Message: "This service is not available in your country"
3. Store ip_address → country mapping for future lookups
```

#### IP Reputation

```
Integration: (optional)
• AbuseIPDB API (check if IP is known botnet/proxy)
• On login from unknown IP:
  - Query API
  - If abuse_confidence_score > 75:
    * Require CAPTCHA
    * OR block login
    * Audit log: high_risk_ip_detected

Table: ip_reputation_cache
├── ip_address (VARCHAR 45, PK)
├── last_checked_at (TIMESTAMP)
├── abuse_confidence_score (INTEGER)
├── is_proxy (BOOLEAN)
├── is_vpn (BOOLEAN)
└── is_datacenter (BOOLEAN)
```

### 8.4 CAPTCHA Integration

```
When to trigger:
• Risk score 51-75
• Failed login attempts > 2 from same IP
• Impossible travel detected
• Login from blocked country

Service: Google reCAPTCHA v3 or Cloudflare Turnstile

Flow:
1. Frontend generates token
2. Backend verifies token: POST to reCAPTCHA API
3. If score < 0.5: block request
4. If score >= 0.5: allow + log score in login_attempts.captcha_score

Config:
authentication.captcha.enabled = true | false
authentication.captcha.threshold = 0.5
authentication.captcha.provider = "recaptcha_v3" | "turnstile"
```

### 8.5 Impossible Travel Detection

```
Logic:
last_login_location = user's last known IP → resolved to city
current_login_location = current IP → resolved to city
time_diff = now() - last_login_timestamp

distance = haversine(last_lat_long, current_lat_long)  // kilometers
max_speed = 900 km/h (airplane speed)
travel_time = distance / max_speed

if (travel_time > time_diff):
  // Impossible travel
  fraud_risk_score += 40
  require_email_verification = true
  Audit: impossible_travel_detected

Table: user_locations (for tracking)
├── user_id
├── ip_address
├── latitude
├── longitude
├── city
├── country
├── created_at
└── INDEX(user_id, created_at DESC)
```

### 8.6 Suspicious Activity Response

```
Triggers:
• Rapid login attempts (3+ in 1 minute from different IPs)
• Password change + immediate login attempt
• Email change + login attempt
• Impossible travel detected
• Token family revocation (potential theft)

Actions:
1. Send security email: "Suspicious activity detected"
   - List what was suspicious
   - Link to revoke all sessions
   - Link to change password
2. Audit log: security_alert_triggered
3. Set session flag: security_review_required = true
4. Optionally lock account temporarily (admin decision)
```

### 9.2 Configuration Access Pattern

**Backend must implement a configuration resolver:**

```typescript
class AuthConfigResolver {
  // Inject platform configuration service
  constructor(private configService: PlatformConfigService) {}

  // Usage: resolver.isEnabled('authentication.otp')
  async isEnabled(fieldId: string): Promise<boolean> {
    const config = await this.configService.get('authentication');
    return config[fieldId]?.value ?? config[fieldId]?.default;
  }

  // Usage: resolver.getOtpLength()
  async getOtpLength(): Promise<number> {
    return this.isEnabled('authentication.otp.enabled')
      ? await this.configService.get('authentication.otp.length')
      : null;
  }

  // Usage: resolver.getLockoutDurationMinutes()
  async getLockoutDurationMinutes(): Promise<number> {
    return await this.configService.get('authentication.lockout_duration_minutes');
  }

  // etc.
}
```

### 9.3 Configuration Caching Strategy

```
Problem: Querying database on every request is slow.

Solution:
1. Cache config in-memory (Redis or in-process)
2. TTL: 5 minutes
3. On config change (from admin UI):
   - Invalidate cache immediately (pubsub event)
   - Broadcast to all backend instances
4. Fallback: Use hardcoded defaults if config unavailable

Implementation:
@CacheKey('auth:config')
@CacheTTL(300)  // 5 minutes
async getAuthConfig(): Promise<AuthConfig> {
  return this.configService.get('authentication');
}

On config change event (from admin):
this.cacheService.invalidate('auth:config');
this.pubsub.publish('auth:config:updated', newConfig);
```

```sql
  ON sessions(user_id, status)

  ON trusted_devices(fingerprint_hash, revoked_at)
```

## 13. Production Recommendations

### 13.1 Horizontal Scaling

**Stateless Architecture:**

```
Challenge:
• OTP challenges are stored in database
• Sessions are stored in database
• Rate limits use database counters

Solution:
✓ All auth state is in PostgreSQL (shared, consistent)
✓ Backend is stateless (can scale horizontally)
✓ Use connection pooling (PgBouncer: 100 connections → 10,000 concurrent users)

Load Balancing:
• Sticky sessions NOT required (stateless)
• Round-robin load balancer sufficient
• Can kill instances without losing user sessions

Deployment:
• Deploy N identical auth service instances
• Load balancer distributes requests evenly
• Database is single source of truth
• No state lost on instance restart
```

### 13.2 Redis for Caching & Rate Limiting

```
Use Redis for:
1. Rate limit counters (fast, atomic increments)
   Key: ratelimit:{contact}:{operation} → TTL: 86400 (24h)
   
2. OTP code cache (speed up verification)
   Key: otp:{challenge_id} → {hashed_code} → TTL: 300 (5min)
   
3. Configuration cache
   Key: config:authentication → {json} → TTL: 300 (5min)
   
4. Session validation cache
   Key: session:{session_id} → {status} → TTL: 3600 (1h)
   
5. Refresh token blacklist cache
   Key: blacklist:jti:{jti} → {reason} → TTL: varies

Redis Cluster:
• Single Redis instance for dev/staging
• Redis Cluster (3+ nodes) for production HA
• Sentinel for auto-failover
• Replication factor: 3
• Backup: daily snapshots to S3
```

### 13.3 Message Queues for SMS/Email

**Problem:** SMS sending can take 2-5 seconds; blocking requests is bad.

**Solution:** Async queues.

```
Architecture:
[Backend] → [Queue] → [Worker] → [SMS Provider]
  (send OTP)    (fast)  (fast)   (slow)

Queue Options:
• RabbitMQ (robust, dead-letter queues)
• AWS SQS (managed, simple)
• Bull (Node.js + Redis, lightweight)

Message Format:
{
  "type": "send_sms",
  "contact": "+1234567890",
  "message": "Your code is 123456",
  "challenge_id": "chal_uuid",
  "provider": "twilio",
  "created_at": "2026-07-05T14:30:00Z"
}

Worker Logic:
1. Poll queue
2. Retry up to 3 times on failure
3. Log all attempts to sms_delivery_logs table
4. Move to dead-letter queue if 3 retries fail
5. Alert ops team
```

```
• All API endpoints: HTTPS only (TLS 1.2+)
• Enforce HSTS header: Strict-Transport-Security: max-age=31536000
• No plain HTTP (except health checks to load balancer)
• WebSocket: WSS only (TLS-wrapped WebSocket)
```

### 13.7 High Availability (HA)

**Database HA:**

```
Setup:
├── PostgreSQL Primary (write)
├── PostgreSQL Replica 1 (read-only, replication lag < 100ms)
├── PostgreSQL Replica 2 (read-only, backup)
├── Automated failover (Patroni or AWS RDS Multi-AZ)

Connection Pool:
├── Primary: write operations + auth queries
├── Replicas: read-only queries (get sessions, audit logs, etc.)
├── Fallback: if replica unavailable, use primary (consistency over latency)

Backup:
├── Continuous WAL archiving to S3
├── Full backup daily
├── Point-in-time recovery (PITR) window: 30 days
├── RTO: 15 minutes
├── RPO: 5 minutes
```

**Backend Service HA:**

```
Setup:
├── Minimum 3 auth service instances (multi-region)
├── Load balancer (ALB / NLB) with health checks
├── Auto-scaling: scale up if CPU > 70%, scale down if < 20%
├── Circuit breaker: if service unhealthy, remove from LB

Health Check:
├── Endpoint: GET /health
├── Response: { "status": "ok", "version": "..." }
├── Interval: 30 seconds
├── Unhealthy threshold: 3 failures = remove from LB
```

**Redis HA:**

```
Setup:
├── Redis Cluster 6+ nodes (auto sharding)
├── OR Redis + Sentinel (3 sentinels monitor 1 primary + N replicas)
├── Replication factor: 3
├── Failover time: < 30 seconds

Backup:
├── RDB snapshots: every 12 hours
├── AOF persistence: fsync every 1 second
├── Backup to S3 every 6 hours
```

### 13.8 CDN & Caching

**Not directly applicable to auth endpoints** (too sensitive for CDN caching), but:

```
Cache login page HTML + assets:
├── CloudFlare / CloudFront with short TTL (5 minutes)
├── Purge on deployment
├── Do NOT cache anything with auth tokens

API endpoints:
├── No caching for POST endpoints (side effects)
├── GET /auth/sessions: cache 1 minute (acceptable staleness)
├── GET /auth/devices: cache 1 minute

Public endpoints:
├── GET /auth/phone/login: no cache (rate limit per user, not global)
├── GET /auth/email/login: no cache
```

## Appendix C: Glossary

| Term | Definition |
|------|-----------|
| **OTP** | One-Time Password; single-use code (e.g., 6 digits) |
| **Challenge** | Uniquely identified OTP request; tied to contact (phone/email) |
| **Session** | Authenticated user connection tied to device |
| **Device ID** | Persistent identifier for user's device |
| **Refresh Token** | Long-lived token used to obtain new access tokens |
| **Access Token** | Short-lived token for API requests (15 min default) |
| **Token Family** | Set of related tokens from same login; used for theft detection |
| **Blacklist** | Set of revoked tokens that should be rejected |
| **Fingerprint** | Device identification via user-agent, IP, etc. |
| **Trusted Device** | Device user has manually marked as safe (90-day window) |
| **Fraud Score** | Risk assessment of login (0-100); higher = more suspicious |
| **Lockout** | Temporary (15 min) or permanent account suspension |
| **Rate Limit** | Max requests per time window (e.g., 3 OTPs per 24h) |
