# P9.5.4 — Translation Management: Infrastructure for Automatic Localization-Readiness

## Objective

Per the phase brief: complete the remaining infrastructure so every
future feature *automatically* becomes localization-ready, without
building a second localization system, a second registry, or a second
search engine. This document describes the one piece of new
infrastructure this phase adds (`resolveConfigText()`), why it's shaped
the way it is, and how it interacts with everything P9.0–P9.5.3 already
built.

## The core problem

`ConfigFieldDefinition.title`/`.description` (and the equivalent
`ConfigModuleDefinition.name`/`.description` and
`ConfigSectionDefinition.title`/`.description`) are plain `string` fields
in `src/config/types.ts` — hand-authored literal English in ~27 module
definition files. P9.5.3 explicitly deferred migrating this content
because:
1. Changing the field type to a dedicated "translation key" type would
   touch the schema every module file depends on (an architecture
   change the phase brief forbids: "Never rewrite architecture").
2. Mechanically moving ~235 field titles + ~103 descriptions into locale
   JSON, with real (not placeholder) fa/ar translations, for all ~27
   modules in one pass is a large, error-prone undertaking better done
   incrementally, verified module-by-module.

## The fix: additive, non-breaking resolution

`src/config/i18n.ts` exports `resolveConfigText(t, id, kind, fallback)`:

```ts
export function resolveConfigText(t, id, kind, fallback) {
  const key = `${id}.${kind}`
  if (t.has(key)) return t(key)
  return fallback
}
```

Called as `resolveConfigText(tFields, field.id, 'title', field.title)`
where `tFields = useTranslations('configFields')`. The field's *existing*
`title` string is passed as the fallback — nothing about the field
definition file needs to change for this to be safe. If a translation key
`configFields.<field.id>.title` exists, it's used (localized); if not,
the literal renders exactly as it always has. This is why "every future
feature automatically becomes localization-ready": the rendering layer
(`ConfigurationFieldRow`, `ConfigurationEntityDrawer`,
`ConfigurationInspector`, `ConfigurationModulePage`,
`ConfigurationStudioNav`, `ConfigurationCommandPalette`, the module search
haystack) was wired to call `resolveConfigText()` **once**, generically,
this phase. Migrating a 28th module tomorrow means only adding
`configFields.<newModuleId>.*` keys to `en.json`/`fa.json`/`ar.json` —
zero further code changes anywhere in the rendering/search pipeline.

## The real bug this uncovered (and why it matters for translation management specifically)

The first version of this mechanism authored `configFields` entries as
**flat JSON keys containing literal dots**, e.g.:

```json
"configFields": {
  "authentication.core.title": "Core Toggles"
}
```

This is exactly how a naive "just dot-join the id and the field kind"
implementation looks reasonable to write. It is silently broken: next-intl
interprets every `.` in a translation key as object nesting, so
`t.has('authentication.core.title')` against a flat key always returns
`false` (or, when passed through `NextIntlClientProvider`'s eager
`validateMessages()`, throws `INVALID_KEY` outright — see the reproduction
in `src/test/p9-5-4-production-localization.test.tsx`). The fix: every
`configFields`/`seo` namespace entry is a **genuinely nested JSON object**:

```json
"configFields": {
  "authentication": {
    "core": { "title": "Core Toggles" }
  }
}
```

`resolveConfigText()`'s call sites didn't change at all — the *key
string* passed to `t.has()`/`t()` is still the dot-joined
`${id}.${kind}`; only the JSON *shape* changed, from flat to nested. This
is a durable lesson for any future namespace design in this codebase:
**dotted ids are safe to use as translation keys only when the backing
JSON is actually nested to match** — a flat object with dots embedded in
property names is not an equivalent representation to next-intl, even
though it looks identical to a casual JSON read. The regression test
suite (`src/test/p9-5-4-production-localization.test.tsx`, "resolveConfigText
— the real architectural bug this phase found and fixed") locks this in:
it verifies both that the flat form fails and the nested form succeeds,
and that the real `en.json`/`fa.json` bundles use the nested form.

## What this phase migrated with this mechanism

| Module | Keys added | Scope |
|---|---|---|
| `languages` (config) | 9 | name, description, 1 section title, 3 fields × title+description |
| `authentication` (config) | 6 | name, description, 4 section titles (field-level content NOT migrated — largest module, deferred) |
| `platform.overview` (platform-admin) | 5 | name, description, section title, 2 field titles |
| `platform.maintenance_mode` (platform-admin) | 6 | name, description, section title, 3 field titles |
| `platform.system_status` (platform-admin) | 5 | name, description, section title, 2 field titles |
| `platform.users` (platform-admin) | 5 | name, description, section title, 1 field (title+description) |

**36 keys total, 4 fully-migrated modules + 1 partially-migrated module**,
proof of the mechanism at both config-module and platform-admin-module
shape. The remaining ~22 modules keep rendering their existing literal
`title`/`description` exactly as before — the fallback path, unchanged
behavior, zero regression risk.

## Search integration (no second engine)

`configUiHelpers.ts`'s `matchesSearch()` gained two optional parameters
(`resolvedTitle`, `resolvedDescription`) — the *same* haystack-building
function, now optionally fed already-localized text computed by the
caller via `resolveConfigText()`. `ConfigurationModulePage.tsx`,
`ConfigurationStudioNav.tsx`, and `ConfigurationCommandPalette.tsx` all
pass resolved text through this one function; there is exactly one
search-matching implementation in the whole Console/Studio, as before.

## What remains (explicitly not done, per the phase's honesty requirement)

- ~22 config/platform-admin modules' field-level `title`/`description`
  content (≈ 200 field titles, ≈ 95 descriptions) — the resolution
  mechanism supports them the moment keys are authored; no code changes
  needed, only translation content work.
- `src/platform-admin/dashboard.ts` (~23 widget definitions) and
  `PlatformDashboardWidgetCard.tsx` consuming them.
- `src/platform-admin/search-providers.ts` per-entity search result
  labels/hints (Countries/Businesses/Platform-Users entity search, as
  opposed to the module/field search this phase did wire).
