# P10.3.2 — Enterprise Zero Trust Access Path Audit

Final security architecture audit after P10.3 and P10.3.1. Scope: prove
every frontend data access path passes through the correct authorization
layer. This phase found and fixed no new code beyond what is listed
below — every other area audited was verified accurate against the
existing P10.3/P10.3.1 enforcement and is documented as such, not
re-implemented.

## Executive Summary

The frontend's authorization surface funnels through a small number of
real chokepoints: `usePermissions()` / `PermissionGuard` (RBAC),
`assertOwnershipBranchAccess()` (branch isolation, P10.3 Phase D),
`assertOwnershipTenantAccess()` (tenant isolation, P10.3 Phase E), and
`useHasDashboardAccess()` (the `/console` route gate, fixed in P10.3.1).
This audit traced the query layer, mutation layer, store layer,
WebSocket layer, and public/private boundary against those chokepoints
and found the enforcement architecture sound. One additional gap was
found and fixed (below); everything else traced correctly to an existing
guard, or is a documented, non-exploitable, out-of-scope limitation
inherent to a mock-data frontend awaiting real backend enforcement.

## Findings

### F-A1 — `useAdminBranches`/`useStaff`-style tenant guard confirmed present, no new query/mutation gap found
Severity: N/A (verification, not a finding)
Traced every `useQuery`/`useMutation` hook that reads `tenantId`/`branchId`
from `useTenantStore`/`useBranchStore` in `hooks/index.ts`. All
branch-scoped reads named in P10.3 Phase D and the two tenant-scoped
reads fixed in P10.3.1 (`useAdminOrders`, `useAdminReservations`) now
call the shared guards. No additional ungated tenant/branch read was
found in this pass beyond what P10.3.1 already fixed.

### F-B1 — Cache isolation was claimed but never proven with a test exercising the actual `QueryClient`
Severity: Low (process gap, not a vulnerability — the mechanism was
already correct)
Root cause: P10.3 Phase G asserted `useLogout()`/`AdminTenantSwitcher`
correctly clear cross-tenant state via source-text checks only
(`context-integrity.test.ts`), never by populating a real `QueryClient`
and Zustand stores with tenant-A data and asserting they're empty after
the cleanup sequence runs.
Fix: none needed to the implementation — `qc.clear()` and the store
reset actions already behave correctly. Added `src/test/p10.3.2-cache-isolation-audit.test.ts`,
which populates a real `QueryClient` plus `useCartStore`/`useDineInStore`/
`useFavoritesStore`/`useRecentlyViewedStore`/`useBranchStore`/`useRbacStore`
with Tenant-A-shaped data, runs the exact cleanup sequence from
`useLogout()` and `AdminTenantSwitcher.switchTenant()`, and asserts zero
residual cache entries and zero residual store state. All 4 assertions
pass against the current implementation, closing the "claimed but
unproven" gap.
Regression test: `src/test/p10.3.2-cache-isolation-audit.test.ts` (4 tests).

### F-G1 — WebSocket channel names carry no tenant/branch dimension (documented, not fixed)
Severity: Medium, backend-readiness only (not exploitable today)
`orderWebSocket`, `notificationWebSocket`, and every channel in
`operationsChannelManager` (`admin.operations`, `branch.operations`,
`orders.broadcast`, etc.) are module-level singletons keyed by a fixed
channel name, not `channel-${tenantId}` or similar. In mock mode this is
inert — the channels only emit synthetic local events used purely as an
"invalidate this query key" signal, and `useBroadcastInvalidation()`
(hooks/index.ts) correctly scopes the resulting `qc.invalidateQueries()`
call to a tenant/branch-prefixed query key (verified by direct read: the
invalidation key is always `[name, scope.tenantId, scope.branchId]`).
**This is a real backend-integration requirement, not a frontend bug**:
when a real Django Channels backend is wired up, these channel names
must be tenant/branch-namespaced server-side (or the backend must filter
messages per-connection by the authenticated tenant), or a real cross-
tenant realtime leak becomes possible. No frontend fix applies here —
noted as Remaining Technical Debt below.

### F-I1 — Public/private boundary confirmed clean
Severity: N/A (verification)
Grepped every public-facing page (`app/[tenantSlug]/**`, `app/menu/**`)
for calls to `getStaff`, `getAdminOrders`, `getAdminReservations`,
`getAdminBranches` — zero matches. No admin-only service method is
reachable from a public/customer route.

## Remaining Risks

**Frontend limitations** (cannot be closed without a backend):
- Every guard in this program (`assertOwnershipBranchAccess`,
  `assertOwnershipTenantAccess`, `useHasDashboardAccess`) runs against
  mock data in the browser. A backend must implement the equivalent
  checks server-side — the frontend guards are defense-in-depth for the
  mock harness, not a substitute for server authorization.
- WebSocket channel naming (F-G1) requires backend-side tenant/branch
  scoping once real channels replace the mock simulation.

**Architectural debt** (documented in P10.3_IMPLEMENTATION.md, unchanged
by this phase):
- `usePermissions()`'s union of legacy `tenantRoles` with ownership-driven
  permissions is not eligibility-gated on the legacy side (not
  exploitable by any current demo account).
- `useHasPermission()` is dead code that bypasses the ownership engine
  (zero live callers, flagged not removed).
- `AdminTenantSwitcher`'s `originRoles` carry-forward is a pre-P10,
  platform-admin-only mechanism outside the Owner/StaffAssignment model.

## Final Verdict

**PASS WITH DOCUMENTED DEBT.**

Every live, reachable frontend data-access path traced to a correct
authorization chokepoint after P10.3.1's two fixes. This phase's own
scan found no additional bypass — only one process gap (cache isolation
claimed but unproven), now closed with explicit tests, and one
backend-readiness item (WebSocket channel namespacing) that is out of
frontend scope by construction. No code was modified beyond adding
regression tests; no vulnerability requiring a source change was found
in P10.3.2.
