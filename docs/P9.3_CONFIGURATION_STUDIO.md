# P9.3 — Platform Configuration Studio

> Companion to `docs/P9.3_CONFIGURATION_STUDIO_AUDIT.md` (Phase A). Documents
> what was actually built: the enterprise Studio shell that every registered
> configuration module — Authentication (P9.1.3), Countries (P9.2), and every
> future module — now renders through automatically, with zero per-module UI
> work required.
>
> Last updated: 2026-07-05

---

## 1. Architecture

P9.3 adds one new layer above the existing, unmodified P9.1.3/P9.2 rendering
engine: the **Studio shell**. Nothing below it changed —
`ConfigurationModulePage`, `ConfigurationFieldRow`, `ConfigurationFieldControl`
/`Badges`/`Preview`, and P9.2's `ConfigurationCollectionTable`/
`ConfigurationEntityDrawer` are exactly the same components, reused wholesale.
The Studio only wraps them:

```
ConfigurationStudioLayout                  (Phase B — the permanent shell)
├── ConfigurationStudioToolbar             (Phase D — breadcrumb, save/discard, history, export)
├── ConfigurationStudioNav                 (Phase C — pinned/recent/grouped module list)
├── ConfigurationModulePage                (P9.1.3/P9.2, unmodified — the workspace)
│   └── ConfigurationFieldRow → …          (unmodified)
├── ConfigurationInspector                 (Phase E — 9-tab right panel)
│   ├── ConfigurationInheritanceTree       (Phase F)
│   ├── ConfigurationHistoryTimeline       (Phase K)
│   └── ConfigurationFieldPreview          (P9.1.3, unmodified — reused, not rebuilt)
└── ConfigurationCommandPalette            (Phase H — Ctrl/Cmd+K)
```

Both routes (`/console/settings/configuration` and `/console/settings/
configuration/[moduleId]`) now render `ConfigurationStudioLayout` — the route
files themselves are unchanged in spirit from P9.1.3 ("wire routing + guards,
nothing else"); only the component they render changed.

## 2. Studio Layout (Phase B)

`ConfigurationStudioLayout` is a 3-pane shell: Modules rail, workspace,
Inspector. Each side pane is independently resizable (drag the 4px handle)
and collapsible (chevron button), with both persisted to `localStorage` via
the new generic `useResizablePanel` hook — a framework primitive with no
Configuration Studio-specific logic, reusable by any future multi-pane admin
surface. Below the `lg` breakpoint (Phase P), the nav and Inspector move into
slide-over `Drawer`s (the same `Drawer` primitive already used elsewhere in
the app) instead of fixed panes, so the workspace stays usable on a tablet or
phone.

## 3. Studio Navigation (Phase C)

`ConfigurationStudioNav` lists every module from `PlatformConfigurationRegistry`
— nothing hardcoded — grouped by `category`, with Pinned and Recent sections
above the groups. Pin state and recent-visit history persist via the new
`useConfigurationStudioNav` hook (localStorage-backed, generic). Arrow-key
navigation moves focus between module buttons; Enter activates the focused
one. A future module (Themes, Payments, …) appears in the nav, becomes
pinnable, and tracks its own recency the moment it registers — no nav code
changes required.

## 4. Global Toolbar (Phase D)

`ConfigurationStudioToolbar` shows a breadcrumb (`Configuration / {module
name}`), the module's lifecycle and environment badges, a "Search or jump
to…" affordance that opens the command palette, and action buttons:
Refresh, History (opens a module-wide audit drawer), Export (downloads the
module's resolved values as JSON), Import (a disabled placeholder — see
§10), and, only while dirty, Discard/Save.

**The toolbar never owns save/discard logic itself.** `ConfigurationModulePage`
gained two new optional props — `onDraftStateChange` and `onActionsReady` —
through which it reports its live dirty state and hands up stable
imperative `save`/`discard` handles. The toolbar's buttons call those
handles; the actual persistence still happens in exactly one place
(`useConfigurationDraft`), so there is no second, competing save
implementation to drift out of sync with the bottom sticky bar (Phase G).

### A real bug this design surfaced

The first version of this wiring used a "latest ref" pattern incorrectly at
the layout level: whenever `activeModuleId` changed, a `useEffect` reset
`actions`/`draftStatus` state to `null` "to be safe." Because React flushes
a newly-mounted child's effects *before* its parent's effect in the same
commit, that reset ran *after* `ConfigurationModulePage`'s own
`onActionsReady` call on the very first mount — silently overwriting the
real actions object back to `null` and leaving the toolbar's Save button
permanently inert. A regression test
(`shows an unsaved-changes badge and a working Save button once a field is
dirty`) caught this immediately; the fix was to stop resetting
`actions`/`draftStatus` on module change at all — the freshly-remounted
child (`ConfigurationModulePage` is keyed by `moduleId`) already reports
correct fresh values through its own mount effects.

`ConfigurationModulePage` itself uses the correct version of the "latest
ref" pattern: `onActionsReady` fires exactly once (empty dependency array)
with stable wrapper functions that dereference refs updated every render —
an effect with no dependency array at all would have called the parent's
`setState` every single commit, and since the actions object is a fresh
literal each time, that `setState` would never bail out, causing an
infinite render loop. (This exact mistake was made and caught during
development — see the inline comment at the call site.)

## 5. Inspector Panel (Phase E)

`ConfigurationInspector` is the right-side panel — completely generic,
driven only by a `fieldId` resolved through `configurationService`/
`configurationAudit`/`configurationValidator`. Nine tabs: Overview,
Inheritance, Dependencies, Validation, Audit, History, Preview, Statistics,
Documentation. It has never heard of Authentication or Countries; any field
from any module — including a `'collection'` schema property, which is
itself an ordinary `ConfigFieldDefinition` — renders through the same nine
tabs. It reuses `ConfigurationFieldBadges`, `ConfigurationFieldPreview`,
`ConfigurationInheritanceTree`, and `ConfigurationHistoryTimeline` rather
than re-implementing any of them.

Selecting a field is additive: `ConfigurationFieldRow` gained an optional
`onInspect` callback fired alongside its existing inline inspector toggle
(unchanged, still used by the P9.1.3 tests) — clicking a row's History icon
now *also* tells the Studio which field to show in the Inspector, without
touching the inline panel's own behavior at all.

## 6. Configuration Diff — Inheritance Tree (Phase F)

`ConfigurationInheritanceTree` visualizes one field's Platform → Tenant →
Branch → User chain, highlighting which level is Effective, which are
Overridden, and which overrides are Blocked (present but unreachable due to
`canOverride`/`mode: 'locked'`). It's built on one new, small,
read-only service method: `configurationService.getFieldLayers(fieldId,
scope)`, which exposes the raw per-level values the resolver already
computes internally but never previously surfaced — everything else
(`resolveField`, `CONFIG_INHERITANCE_CHAIN`) already existed.

## 7. Sticky Save Experience (Phase G)

The P9.1.3 save bar was extracted, unchanged in markup and behavior, into
`ConfigurationSaveBar` — existing tests asserting on "N unsaved change(s)" /
"Save Changes" / "Discard" keep passing unmodified. It gained one addition:
a `⌘S` shortcut hint next to the Save button, backed by the new generic
`useKeyboardShortcut` hook (Phase I) so Ctrl/Cmd+S saves from anywhere on
the page, not just by clicking the button.

## 8. Command Palette (Phase H)

`ConfigurationCommandPalette` (Ctrl/Cmd+K) lists every registered module
("Go to {name}") and every field across every module, built by walking
`platformConfigurationRegistry.getModules()` — a future module's fields are
searchable here the instant it registers. It reuses the existing `Modal`
primitive for focus-trap/Escape-to-close rather than re-implementing either,
and the shared `buildSearchHaystack` helper (P9.2) for matching.

## 9. Keyboard Shortcuts (Phase I)

`useKeyboardShortcut(key, handler, options)` is a small, generic global
keydown binder (ignores keystrokes while a text input/textarea/select has
focus unless explicitly allowed) — wired once for Ctrl/Cmd+K (open command
palette) and Ctrl/Cmd+S (save, from `ConfigurationSaveBar`). Esc closes the
command palette and any open Drawer via those primitives' own existing
behavior.

## 10. Visual Preview System (Phase J)

`ConfigFieldPreview.kind` gained two entries: `'datetime'` (formats an IANA
timezone or ISO timestamp via `Intl.DateTimeFormat`) and `'formatted'` — a
plain callback escape hatch (`field.preview.format(value) => string`) for
anything else a module needs (phone numbers, currency, address layouts, …)
so a new preview need never requires a new hardcoded `kind` in the
framework. Countries' `timezone` property now uses `'datetime'` and its
`phone_example` property demonstrates `'formatted'` — both real, working
examples, not speculative code.

## 11. History & Timeline (Phase K)

`ConfigurationHistoryTimeline` (used in the Inspector's History tab) and the
toolbar's module-wide History drawer both read
`configurationAudit.listForField()` and both roll back through one shared
function, `rollbackAuditEntry(entry, actor)` — writing `entry.previousValue`
back via `configurationService.updateField()`, the same single write path
everything else in the Studio uses. Extracting this once (rather than
duplicating the three-line rollback call in both places) is the kind of
"whenever duplicated UI logic appears, generalize it" instruction Phase S
asks for, applied concretely.

## 12. Compare Mode (Phase L)

`ConfigurationCompareView` builds a list of "snapshots" for one field —
Current (effective), Draft (if provided), each inheritance level's raw
layer, the schema default, and every prior audit entry — and renders any
two of them side by side with a visual diff highlight. It's built from the
same `getFieldLayers`/`listForField` primitives as the Inheritance tree and
History timeline, so it works for any field with zero module-specific code.

## 13. Empty States & Loading (Phases M/N)

Every new Studio surface (nav search, collection table "no matches,"
history/audit "no entries," Inspector with nothing selected) uses the
existing `EmptyState` primitive rather than ad hoc text — this was also
retrofitted onto `ConfigurationCollectionTable`'s "No matches." text (P9.2),
consolidating that surface onto the same component. `ConfigurationWorkspaceSkeleton`
renders while the registry hasn't resolved modules yet — today that's only
a transient pre-hydration window (`ConfigurationService` is synchronous, in-
memory), but the skeleton exists now so a future real backend's async fetch
has somewhere to render into without every module inventing its own.

## 14. Motion System (Phase O)

Three short (150–220ms) keyframes — `slide-up`, `fade-in`, `slide-in-right`
— added to `globals.css`, used only via Tailwind's `motion-safe:` variant
(which Tailwind disables automatically under `prefers-reduced-motion:
reduce` — no separate reduced-motion branch needed). The save bar slides up
on appearance; side panels fade in when un-collapsed.

## 15. Responsive Strategy (Phase P)

Desktop (`≥1024px`): fixed 3-pane layout with resizable/collapsible side
panes. Below that: the nav and Inspector become slide-over `Drawer`s,
triggered by icon buttons in a small mobile header bar injected above the
workspace; the workspace itself is unaffected either way, since it's the
same `ConfigurationModulePage` in both modes.

## 16. Accessibility (Phase Q)

- The command palette uses `role="combobox"`/`listbox`/`option` with
  `aria-selected`, plus the existing `Modal`'s focus trap and Escape
  handling.
- Every icon-only toolbar button has an `aria-label`.
- The nav is a `<nav aria-label="Configuration modules">` with arrow-key
  roving focus.
- The Inheritance tree is `role="list"`/`listitem` with a labelled
  container.
- `EmptyState` and the loading skeleton both use `role="status"` so screen
  readers announce them.
- **Known gap**: the resize-handle separators (`role="separator"`) are not
  yet keyboard-operable (no arrow-key resize) — panels can still be fully
  collapsed/expanded via the adjacent button, which *is* keyboard-operable,
  so keyboard-only users retain full access to both panes, just not
  fine-grained width control.

## 17. Design Tokens (Phase R) & Framework Hardening (Phase S)

No new color values, spacing scale, or radius conventions were introduced —
every new Studio component composes the existing UI kit (`Badge`, `Button`,
`EmptyState`, `Skeleton`, `Modal`, `Drawer`) and the existing `--fg`/
`--fg-muted`/`--card`/`--border`/`--bg`/`--input-bg`/`--card-hover` CSS
variable set. That consistency *is* the Phase R/S outcome: there was no
duplicated visual language to reconcile because nothing new was invented.
Two genuine pieces of duplicated logic were caught and generalized during
the build itself (not left for a later pass): the rollback write (§11) and
the resolved-value/layers pattern shared by the Inheritance tree, History
timeline, and Compare view (§12) all route through the same handful of
service-layer primitives rather than each re-deriving values independently.

## 18. Known Limitations

- **"Publish" is an alias for the same save pipeline.** This system has no
  separate draft/staging storage for a *module as a whole* — only per-field
  inheritance levels. The toolbar labels the Save button "Publish" when the
  module's own lifecycle is `draft`/`testing`, but clicking it runs the
  identical save path as "Save" elsewhere. A real draft→published workflow
  for an entire module is future work, not modeled today.
- **Toolbar Save has no reason input.** Fields with `audit.requireReason:
  true` (e.g. Authentication's "Kill Switch") can only be saved via the
  bottom sticky bar, which has the reason field; the toolbar's Save button
  will silently fail validation for such a field until a reason-capable
  variant is added.
- **Resize handles aren't keyboard-operable** (see §16).
- **Import remains a placeholder**, consistent with P9.2's bulk-import
  placeholder — no import format is defined yet.

## 19. Extension Guide — adding a new module

Nothing above requires touching the Studio to add a module. As established
since P9.1.3/P9.2, a new module needs only:

1. Register it via `defineField()`/`platformConfigurationRegistry.register()`
   in `src/config/modules/<name>.ts`.
2. Import it once in `src/config/index.ts`.

The moment it's registered, it appears in the Studio nav (pinnable,
groupable by its `category`), is fully searchable in the command palette,
renders through the exact same workspace/Inspector/toolbar, and — if it
declares a `'collection'` field — gets the P9.2 table/drawer/bulk-actions/
filtering for free. No new route, no new page component, no new Inspector
or nav code.
