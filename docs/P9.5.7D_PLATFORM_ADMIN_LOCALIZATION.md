## Remaining hardcoded strings (honest list — NOT rounded to 100%)

1. **86 collection-item-schema field strings** (68 titles + 18 descriptions) across `COUNTRY_SCHEMA`, `LANGUAGE_SCHEMA`, `PLATFORM_USER_SCHEMA`, `TENANT_SCHEMA`. **Why not fixed**: `ConfigurationEntityDrawer.tsx` resolves these via `resolveConfigText(tFields, prop.id, 'title', prop.title)` using the field's *own bare id* (e.g. `'enabled'`, `'status'`, `'notes'`, `'timezone'`, `'currency'`, `'region'`) — not a collection-scoped id. Multiple different collections reuse the same short id for semantically different fields (confirmed collisions: `enabled` appears in 3 different schemas, `status`/`notes`/`timezone`/`currency`/`region` each appear in 2+), and one collection (`countries.registry`) even has an id collision *within itself* (the section and its own collection field share the literal id `'countries.registry'`, so only one of their two titles could be authored under that key — the section's "Country Management" was kept; the field's "Countries" now falls back to its English literal in every locale). Authoring a translation for one collision target would silently mistranslate the other. Fixing this properly requires either scoping collection-item-schema ids by their parent collection (a `ConfigCollectionMeta`/`ConfigurationEntityDrawer` change) or extending `resolveConfigText`'s key contract to accept a scope prefix — both are schema/architecture changes this phase's rules explicitly forbid ("No architecture changes"). Documented, not silently skipped.
2. **`ConfigFieldOption.label`** (individual `select`/`radio` option text) — never resolved through any translation mechanism, anywhere in the config system, for any module (pre-existing since P9.0, not introduced or expanded by this phase). Roughly 137 `label:` occurrences exist across all module files combined (a mix of option labels, `PLATFORM_ROLE_LABEL`, and widget list-item labels already handled separately). **Why not fixed**: `resolveConfigText`'s `ConfigTextKind` type (`'title' | 'description' | 'name' | 'group'`) has no `'option'` variant, and `ConfigFieldOption` (`src/config/types.ts`) has no id of its own to key off of — extending either is a type/schema change to code every module file depends on, which this phase's rules forbid making without explicit authorization ("No architecture changes... Do NOT introduce new localization systems"). This is a pre-existing platform-wide gap, not specific to Platform Administration; recommend scoping it as its own future phase (e.g. "P9.5.8 — Config Option Label Localization") with an explicit architecture-change authorization, since it cannot be done safely within this phase's constraints.
3. **`ConfigurationCommandPalette.tsx`'s search-result `hint: mod.category`** for pre-P9.0.4-era modules — a secondary, small hint string next to each "Go to module" command-palette result, distinct from the (now-localized) `NAV_GROUP_KEY` nav-section headers because it reads the lowercase `category` field, not the uppercase `group` field. **Why not fixed**: lower priority (secondary hint text, not a primary heading), and the `category` value set (`'security'`, `'platform'`, `'localization'`, `'infrastructure'`, `'billing'`, `'commerce'`, `'communications'`, `'branding'`, `'content'`) only partially overlaps the 13-item `group` set already translated — extending coverage cleanly would need its own small lookup map, deferred to keep this phase's scope bounded and reviewable.

No other hardcoded strings were found in scope. Everything else audited in Phase A — module/section/field titles and descriptions, widget titles, IA group names, accessibility attributes, page metadata, shared component chrome — is fully localized.

## Migration notes

- **Extraction tooling**: a purpose-built two-mode Python parser was used instead of `grep -c` (which the P9.5.4 audit itself used and which over/undercounts): one mode for `config/modules/*.ts` files (which call `platformConfigurationRegistry.register()` directly and always use fully-dotted ids in source, e.g. `'authentication.otp.length'`), and one mode for `platform-admin/modules/*.ts` files (which call `registerAdminModule()`, whose field ids are bare in source, e.g. `'enabled'`, and get auto-prefixed with the module id — `${moduleId}.${fieldId}` — at registration time by `register-module.ts:54`, which the extractor had to replicate to compute the correct runtime lookup key). An earlier, simpler line-based extraction attempt mis-attributed a collection-item-schema's field id (`COUNTRY_SCHEMA`'s `id: 'enabled'`, defined earlier in the same file) as `countries.ts`'s own module id — caught and fixed by scoping extraction to start at each file's `export const XXX_MODULE: ConfigModuleDefinition = {` declaration, not the top of the file.
- **The `countries.registry` id collision**: `countries.ts`'s section (`title: 'Country Management'`) and its own single collection field (`title: 'Countries'`) share the literal id `'countries.registry'` — a pre-existing quirk in the source data, not introduced this phase. Only the section's title/description was authored under `configFields.countries.registry.title`/`.description`; the field's own title continues to render its English literal fallback ("Countries") in every locale. This is a narrow, single-field instance of the broader collection-schema-id-collision problem described in the "Remaining hardcoded strings" section above.
- **Group-name reuse discipline**: the 13 Platform Administration IA groups (`Platform`, `Users`, `Businesses`, …) are each referenced by 3–11 different modules' `group` field. Rather than duplicate the group-name translation once per module (which would already have happened correctly, since each module's own `configFields.<id>.group` key is independent), the *nav section header* rendering (a different, module-independent code path in `ConfigurationStudioNav.tsx`) needed its own single small lookup — `NAV_GROUP_KEY` — to avoid re-deriving the group's translated text from whichever module happened to be first in the list.
