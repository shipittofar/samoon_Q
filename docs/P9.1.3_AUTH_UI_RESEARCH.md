# P9.1.3 — Authentication Control Center: UX Research

> Phase A of P9.1.3. Benchmark of enterprise configuration UX patterns from
> six reference products, and which ideas were adopted (or deliberately
> not adopted) for the Authentication Control Center. This is a design
> reference, not an audit of those products' actual current UI — written
> from general product knowledge of their established patterns.
>
> Last updated: 2026-07-04

---

## 1. Shopify Admin (Settings)

**Pattern**: Settings are organized as a left-hand category list (Payments,
Checkout, Customer accounts, …), each opening a single scrollable page with
grouped sections. Every field has an inline description directly under its
label — never a separate help panel. A persistent "Save" bar appears only
once something has changed, pinned to the bottom of the viewport.

**Adopted**: The single-scrollable-page-with-in-page section anchors
pattern (not a tab-per-section model, which fragments the "see everything
at once" experience an enterprise administrator wants). The
appears-only-when-dirty save bar.

**Not adopted**: Shopify's settings are not searchable in the same page —
navigation is the primary discovery mechanism. We adopted live in-page
search instead (Phase G) since a single Authentication page here already
has 17 fields across 4 sections, more than fits a skim.

## 2. Stripe Dashboard (Developers → API keys / Settings)

**Pattern**: Every sensitive value (API keys, webhook secrets) is masked by
default with an explicit "Reveal" action, never shown in plaintext on page
load. Every settings change that affects live traffic shows a distinct
"Live mode" vs. "Test mode" badge so an administrator always knows which
environment they're editing. Audit-relevant fields show a small "i" icon
with a tooltip explaining downstream effects before the value is even
changed.

**Adopted**: Secret masking by default (our `secret_input` control, driven
by `ConfigFieldGovernance.securityLevel`/`audit.sensitive`). An
environment/mode indicator in the page header (Phase C's "Environment"
slot) — critically important here given the audit's top finding
(`authentication.mock_authentication_enabled`/`demo_login_enabled` being
live in the wrong environment is the single highest-severity risk
identified in `docs/P9.1.1_MONITORING.md` §9).

**Not adopted**: Stripe's live/test mode is a hard environment switch with
entirely separate data; our Platform → Tenant → Branch → User inheritance
model is a different (compatible, not competing) axis — we show
environment as a status indicator, not a mode switch, since P9.0's
inheritance chain already does the job of showing where a value comes from.

## 3. Auth0 (Authentication Settings / Tenant Settings)

**Pattern**: Toggles that gate an entire feature area (e.g. "Enable
Passwordless") visually collapse everything beneath them when off, rather
than merely disabling the controls — reducing visual noise instead of
showing a wall of greyed-out fields. Danger-zone actions (deleting a
tenant, rotating signing keys) are visually isolated in a red-bordered
section at the very bottom of the page, never inline with routine settings.

**Adopted**: The collapse-when-disabled pattern directly informed Phase E's
dependency engine — `hiddenWhen` (not just `enabledWhen`/greyed-out) is the
default choice for `authentication.otp.*` fields hiding when
`authentication.otp.enabled` is false, exactly matching Auth0's approach
rather than showing disabled inputs.

**Not adopted**: A separate physically-isolated "danger zone" section.
Our fields are grouped by the registry's own section structure (Rule 3 —
don't invent a UI-only grouping that duplicates what the registry already
declares); instead, dangerous fields get a persistent red "Dangerous"
badge wherever they naturally sit (`governance.dangerous`), keeping one
layout driven by one source of truth.

## 4. Firebase Authentication (Sign-in method providers)

**Pattern**: Each identity provider (Google, Email/Password, Phone) is a
card in a grid, collapsed by default, expanding inline to reveal its
specific configuration fields only when enabled. A single "Enabled" count
badge shows at a glance how many providers are live.

**Adopted**: The provider-as-expandable-unit metaphor maps directly onto
`docs/P9.1.1_PROVIDER_ARCHITECTURE.md`'s provider abstraction for a future
phase (P9.1.6+) — not built in P9.1.3 since no provider selection field is
registered yet, but the Control Center's generic section renderer already
supports this shape without new code once that field exists.

## 5. Clerk Dashboard (User & Authentication)

**Pattern**: Every settings change shows a small inline "Saved" checkmark
next to the specific field that changed, in addition to (not instead of) a
global save confirmation — so in a page with many fields, the user isn't
left wondering exactly which value took effect. Restrictions (e.g. "this
setting requires a paid plan") are shown as an inline lock icon with a
tooltip, not a separate "why is this greyed out" support page.

**Adopted**: Per-field state indication — our Configuration State model
(Phase H) shows a "Modified" badge on the specific row that has unsaved
changes, not just a page-level dirty flag. Inline explanation of why a
control is disabled (dependency-hidden vs. permission-denied vs. locked by
inheritance) rather than a bare disabled input.

## 6. Supabase Authentication (Providers / Policies)

**Pattern**: A persistent "Configuration" vs. "Advanced" split — common,
low-risk settings surface by default; rarely-touched, higher-risk settings
live behind an explicit "Show advanced settings" disclosure, reducing
first-load cognitive burden without hiding anything permanently.

**Adopted**: The "Advanced" section named in the phase brief's suggested
layout maps onto exactly this pattern — fields with `governance.experimental`,
`governance.internalOnly`, or no natural home in the registry's other
sections group under an "Advanced" disclosure, collapsed by default.

---

## 7. Summary — what the Authentication Control Center adopts

| Idea | Source | Where it lands |
|---|---|---|
| Single scrollable page, section anchors (not tabs) | Shopify | `ConfigurationModulePage` layout |
| Save bar appears only when dirty | Shopify | Phase J save experience |
| Secrets masked by default, explicit reveal | Stripe | `secret_input` control |
| Environment/mode indicator in header | Stripe | Page header "Environment" slot |
| Collapse-on-disabled (not just grey-out) | Auth0 | `hiddenWhen` dependency default |
| Provider-as-expandable-card | Firebase | Reserved for P9.1.6+ (Provider Architecture) |
| Per-field save/modified indicator | Clerk | Field-level state badges |
| Inline reason for disabled controls | Clerk | Dependency/permission tooltips |
| Advanced section, collapsed by default | Supabase | "Advanced" disclosure for experimental/internal fields |

Deliberately **not** adopted: a hard environment-mode switch (Stripe) —
superseded by the existing inheritance model; a physically separate
danger-zone section (Auth0) — superseded by badge-driven risk indication
that doesn't fragment the registry's own section grouping.
