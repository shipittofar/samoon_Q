## 11. Remaining Production Risks

### R-03 — Hardcoded Mock Reviews on Public Homepages (Medium)

**Files:** `src/app/[tenantSlug]/TenantHomepageClient.tsx`, `src/app/[tenantSlug]/[branchSlug]/BranchHomepageClient.tsx`  
**Detail:** Both homepages render `MOCK_REVIEWS` — a hardcoded array of 3 generic review objects. All tenants show the identical 3 reviews regardless of which business is being viewed. The reviews section uses `meta.rating` and `meta.reviewCount` from MarketplaceMeta (which are correct per-tenant) but the review texts are always "Sarah M.", "James K.", "Aisha T."  
**Impact:** No data isolation risk (these are presentation-only fixtures, not business data). No cross-tenant security concern. User-visible: all businesses show the same fake reviews.  
**Fix in P8.8:** Replace with `useReviews()` hook scoped to tenantId; or gate behind a feature flag until real reviews API is ready.

### R-04 — Branch Module Pages Missing Per-Page SEO Metadata (Low)

**Files:** `src/app/[tenantSlug]/[branchSlug]/menu/page.tsx`, `reservation/page.tsx`, `loyalty/page.tsx`, `promotions/page.tsx`, `events/page.tsx`  
**Detail:** These pages are `'use client'` re-exports of flat-URL pages. Client components cannot export `generateMetadata`. These pages inherit the root layout's generic title ("Savor — Fine Dining & Delivery") and description. A visitor to `/savor/main/menu` gets no page-specific SEO metadata.  
**Impact:** SEO quality degraded for branch module pages. Not a functional bug.  
**Fix in P8.8:** Convert page wrappers to server components with `generateMetadata()` that call `tenantService.getTenant(tenantSlug)` and produce per-tenant/branch metadata.

### R-05 — `useCategories()` / `useMenuItems()` Store-Dependency Race Condition (Low)

**Files:** `src/app/[tenantSlug]/TenantHomepageClient.tsx`, `src/app/[tenantSlug]/[branchSlug]/BranchHomepageClient.tsx`  
**Detail:** `useCategories()` and `useMenuItems()` read `tenantId` from `useTenantStore((s) => s.tenant?.id)`. The TenantLayout's `loadTenant()` fires in a `useEffect` (post-render). There is a brief window where `usePublicTenant(tenantSlug)` has resolved (isLoading=false) but the store still holds the previous session's tenant. During this window, categories/items would query with the wrong tenantId.  
**In mock mode:** Both `usePublicTenant` and `loadTenant` have a 300ms delay and start at the same time, so they complete simultaneously. The `LoadingSkeleton` is shown during those 300ms. By the time the page renders, the store is already updated. **No visible bug in mock mode.**  
**In production:** Response times vary. A fast tenant API response could resolve `usePublicTenant` before `loadTenant` updates the store, showing wrong-tenant categories for ~50–200ms before correcting.  
**Fix in P8.8:** Pass `tenant.id` from `usePublicTenant` result directly to category/item hooks, removing the store dependency. Requires adding an optional `tenantId` parameter to `useCategories()` and `useMenuItems()`.
