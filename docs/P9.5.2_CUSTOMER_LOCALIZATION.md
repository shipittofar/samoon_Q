# P9.5.2 — Customer Experience Localization

> Migrates the core customer commerce flow (Menu → Cart → Checkout →
> Reservation → Dashboard landing) to the runtime built in P9.5.1A and
> extended in P9.5.1B. Business Console and Platform Administration are
> explicitly out of scope (P9.5.3). See
> `docs/P9.5.2_CUSTOMER_LOCALIZATION_AUDIT.md` for the exhaustive
> before/after audit this report is based on.
>
> Last updated: 2026-07-05

---

## 1. Architecture

No new architecture — this phase is pure consumption of what P9.5.0/
P9.5.1A/P9.5.1B already built:

- **Runtime**: `src/i18n/runtime.ts` (locale/RTL/fallback resolution,
  `Intl.*`-backed formatting) — unchanged, untouched.
- **Message loading**: `next-intl`'s per-request dynamic import
  (`src/i18n/request.ts`) — unchanged.
- **Namespaces**: reused P9.5.1B's 20-namespace structure; extended
  `menu`, `cart`, `checkout`, `reservation`, `dashboard`, `validation` with
  the keys this phase's UI needed. No new namespaces were created.
- **Validation pattern**: the P9.5.1B-established "schema stores a
  `validation`-namespace key, component resolves it via `tValidation()`"
  pattern, applied to `checkout` and `reservation`'s zod schemas.
- **Coverage tooling**: `src/i18n/coverage.ts` +
  `scripts/check-translation-coverage.mjs`, extended this phase (Phase P)
  with server-component (`getTranslations()`) detection, dead-namespace
  reporting, and duplicate-value reporting in the CLI output (the
  underlying `findDuplicateValues` pure function already existed from
  P9.5.1B; only the report script's surface grew).

## 2. Migration strategy

Same strategy as P9.5.1B, applied to a different vertical: pick one
complete, high-value user journey and migrate it end-to-end rather than
touching every file shallowly. This phase's journey is the **core
commerce path** — the sequence a paying customer actually walks: browse
the menu, open a dish, add to cart, check out, or book a table — plus the
first screen they land on after logging in (the dashboard).

Concretely:
1. Audit (grep-quantified, `docs/P9.5.2_CUSTOMER_LOCALIZATION_AUDIT.md`).
2. Add/extend namespace keys in `en.json`, translate into `fa.json`/
   `ar.json` in the same pass (never left as English-only stubs for
   customer-facing content, unlike P9.5.1B's reserved
   console/platform/etc. namespaces which are genuinely unused so far).
3. Migrate JSX text, toasts, and validation schemas file-by-file:
   `MenuContent.tsx` → `FoodDetailModal.tsx` → `CartDrawer.tsx` →
   `checkout/page.tsx` → `reservation/page.tsx` → `dashboard/page.tsx`.
4. After each file: re-validate JSON syntax (all 3 locales), `tsc
   --noEmit`, then move to the next file.
5. After all files: run the full test suite, fix any pre-existing
   source-string regression tests that asserted a now-translated literal
   (3 such tests existed, from earlier phases' payment/QR/reviews test
   suites — updated to assert the `t('key')` call site instead of the
   literal, not deleted).
6. Extend the coverage tool, run it, verify 0 missing keys / 0 orphan
   namespaces.
7. Add new regression tests for the migrated surfaces.

## 4. Remaining untranslated areas (do not overclaim)

Per the phase's own instruction — **the customer experience is not fully
localized after this phase.** What's done: the core commerce path (menu →
cart → checkout → reservation) and the dashboard landing page. What's not:

- **Home page** (`src/app/page.tsx`) and **Discover**
  (`src/app/discover/page.tsx`) — marketplace browsing, not migrated.
- **5 dashboard sub-pages** — `orders`, `reservations`, `favorites`,
  `addresses`, `settings` — not migrated (only the dashboard's own landing
  page is done).
- **Order tracking** (`src/app/order/[orderId]/page.tsx` and
  `.../track/page.tsx`) — status timeline, driver/ETA copy, not migrated.
- **`complete-profile` page** — a customer-facing form with its own zod
  schema, not migrated.
- **Page metadata** (`<title>`, OpenGraph, Twitter) — no page's metadata
  was converted to locale-aware `generateMetadata()`; `menu/page.tsx`'s
  static `export const metadata` remains English-only, unchanged.
- **Full accessibility pass** — only `aria-label`s inside the 6 migrated
  files were addressed; the remaining ~36 customer-facing files were not
  audited for `aria-label`/`aria-describedby`/`aria-live`.

Business Console and Platform Administration remain **entirely
unmigrated**, as designed — that is P9.5.3's explicit scope, not an
oversight here.

## 5. Performance comparison

- **No change** to the one-locale-per-request invariant — still exactly
  one JSON file dynamically imported per request; the additional ~124
  keys added this phase live inside that same single file per locale, not
  a new file.
- **238 new translation call sites** (`t()`/`useTranslations()`) each cost
  a React context read — the same negligible cost already established in
  P9.5.1B's report; no new pattern, no new measurement needed.
- **Test suite**: 89 files / 5588 tests (up from 88/5565), ~150s locally —
  consistent scaling with the 2 new test files added, no regression in
  per-test timing.

## 6. Bundle size comparison

| File | P9.5.1B (before this phase) | After this phase | Delta |
|---|---|---|---|
| `en.json` | 10,041 bytes | 15,874 bytes | +5,833 |
| `fa.json` | 13,446 bytes | 20,880 bytes | +7,434 |
| `ar.json` | 11,927 bytes | 18,532 bytes | +6,605 |

Still well under the soft per-language budget
(`P9.5.0_PERFORMANCE_STRATEGY.md` §8), and still only one of these three
files loads per request — the growth is proportional to the amount of
real UI now driven by translation keys, not a regression. zh/it/tr
continue to ship zero bytes of their own (fallback to `en.json`,
unchanged since P9.5.1A).

No new runtime dependencies were added. `src/i18n/coverage.ts` and its
CLI script remain dev/CI-only tooling, never imported by any page — zero
bytes added to any shipped bundle.

## 7. Constraints honored

- No backend API changes.
- No routing changes.
- No UI redesign — every migrated file's JSX structure, Tailwind classes,
  and component tree are unchanged; only literal strings became `t()`
  calls.
- No business logic changes — `onSubmit`/`onSuccess`/`onError` handlers,
  cart math, order payload construction all unchanged.
- No existing tests broken — 3 pre-existing source-string regression
  tests were updated (not deleted) to assert the new `t('key')` call site
  instead of the literal they used to check for, since the underlying
  behavior (a translatable string renders there) is unchanged, only its
  *source* is now a key instead of a literal.
- Runtime Engine (P9.5.1A) untouched; only consumed more widely.

## 8. Remaining work for P9.5.3 (Business Console + Platform Admin)

- Migrate Business Console (order management, menu management, staff,
  analytics dashboards) — currently 100% English, larger surface than the
  customer side by page count.
- Migrate Platform Administration Center (P9.4's ~55 modules) and
  Configuration Studio (P9.1.3/P9.3) — internal-only, lowest priority by
  traffic but largest by raw field/label count (every `ConfigFieldDefinition.title`/
  `.description` is currently a literal).
- Countries Management (P9.2) — the 176-country registry's field labels
  and the collection framework's generic UI chrome (`ConfigurationCollectionTable`,
  `ConfigurationEntityDrawer`) are unmigrated.
- Continue this phase's own remaining list (§4): Home/Discover, dashboard
  sub-pages, order tracking, `complete-profile`, page metadata, full
  accessibility audit.
- Turn the Translation Coverage report into an enforceable CI gate (today
  it's informational-only) once coverage is high enough across the whole
  app that failing a PR on a new missing key stops being a false-positive
  risk for the ~90% of the app still mid-migration.
